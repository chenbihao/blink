# Blink 0.7 — 插件生态 + 本地搜索 Fallback + 搜索体验增强

&gt; **范围**:本地文件搜索 Fallback + 翻译插件 + 剪贴板历史 + 性能统计 + 图标/搜索缓存优化 + 历史权重衰减
&gt;
&gt; **定位**:完善插件生态，解决「Everything 没装时搜不了文件」的体验断层，同时优化搜索质量与性能。

## 一、本地文件搜索 Fallback（Everything 不可用时）

### 1.1 问题现状

当前 `FileEngine` 仅依赖 Everything HTTP：
- 用户没装 Everything → 完全搜不了文件
- Everything 没启动 / 端口被占用 → 静默失败

**产品目标**：即使没装 Everything，也能覆盖「80% 常用场景」的文件搜索。

---

### 1.2 选型对比（Windows 本地搜索方案）

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **Windows Search API** | 系统原生、已索引 | COM 接口不稳定、编码问题多、文档少 | ❌ 暂不采用 |
| **`walkdir` 常用目录遍历** | 简单可靠、无依赖、性能达标 | 仅覆盖常用目录 | ✅ 0.7 首选方案 |
| **`jwalk` 并行遍历** | 比单线程快 2-3 倍 | 引入新依赖 | 可选优化 |
| **`sqlite` + 增量索引** | 首次慢，后续极快 | 需维护索引、复杂度高 | 远期方案（0.8+ 考虑） |

**实测数据**：walkdir 遍历 4 个常用目录（桌面/文档/下载/开始菜单）深度 3 层 → **178ms，181 个文件**，性能完全达标。

---

### 1.3 0.7 推荐方案：**两层 Fallback 策略**

```
用户输入文件搜索
    ↓
Layer 1: Everything HTTP（已有）→ 可用 → 返回
    ↓ 不可用
Layer 2: `walkdir` 常用目录遍历
```

**Layer 2 详细设计（walkdir）**：
- **目录清单**（可配置）：桌面、文档、下载、开始菜单
- **深度限制**：最多 3 层子目录
- **并发遍历**：`tokio::spawn_blocking` 包装，各目录并行遍历
- **内存缓存**：遍历结果缓存 5 分钟，重复搜索不用重新扫
- **结果限制**：最多返回 50 条，避免性能问题
- **模糊匹配**：使用 `nucleo` 对文件名做 fuzzy 匹配（和应用搜索一致）

**配置项**：
```toml
[engine:file_search]
fallback_enabled = true          # 是否启用 Fallback
walk_dirs = ["Desktop", "Documents", "Downloads", "StartMenu"]  # 遍历目录
walk_max_depth = 3               # 最大遍历深度
walk_cache_ttl_sec = 300         # 缓存有效期（秒）
walk_max_results = 50            # 最多返回数
```

**前端反馈**：
- 扩展 Tab 显示「Everything 未运行，使用本地目录搜索」状态提示
- Fallback 结果显示 `[本地]` 前缀标识

## 二、翻译插件

### 2.1 核心设计

**多后端架构**：插件支持切换翻译引擎，统一接口，用户可任选供应商。

| 后端 | 免费额度 | 国内可用 | 翻译质量 | 配置项 | 实现优先级 |
|---|---|---|---|---|---|
| **有道智云** | ✅ 50 元体验金（约 100 万字符） | ✅ | ⭐⭐⭐⭐ | `app_key`, `app_secret` | 🔝 最高 |
| **百度翻译** | ✅ 5 万字符/月 | ✅ | ⭐⭐⭐ | `app_id`, `app_key` | ⭐⭐ 高 |
| **DeepL Free** | ✅ 50 万字符/月 | ❌ 需代理 | ⭐⭐⭐⭐⭐ | `api_key` | ⭐ 中 |
| **腾讯 TMT** | ✅ 500 万字符/月（永久免费） | ✅ | ⭐⭐⭐⭐ | `secret_id`, `secret_key` | 后续再做 |

> ❌ **不做谷歌网页爬虫**：不稳定、容易被封 IP，生产环境不可靠。

## 三、剪贴板历史插件

### 3.1 核心设计

**定位**：**默认关闭**，用户手动启用后才生效。常驻内存的剪贴板历史记录，快速检索粘贴。

**特性**：
- 实时监听 `AddClipboardFormatListener` + `WM_CLIPBOARDUPDATE` 消息
- 去重（相同内容 10 秒内不重复记录）
- SQLite 持久化存储，可配置保留天数
- 支持模糊搜索历史内容（复用 nucleo 引擎）
- 敏感应用黑名单（密码管理器等）

---

### 3.2 数据结构

```rust
struct ClipboardItem {
    id: Uuid,
    text: String,                  // 纯文本内容（HTML/RTF/图片暂不支持）
    preview: String,               // 预览（截断前 80 字符）
    created_at: DateTime<Local>,
    source_app: Option<String>,    // 来源应用名（前台窗口进程名）
    hit_count: u32,                // 粘贴次数
}
```

**存储配置**：
- 最大保留条数：默认 500 条（可配置 100-2000）
- 保留天数：默认 7 天（可配置 1-30 天，0=永久）
- 清理策略：每天启动时后台清理过期 + 超量条目

---

### 3.3 交互设计

| 触发 | 行为 |
|---|---|
| `clip` / `剪贴板` | 显示最近 20 条剪贴板历史，按时间倒序 |
| `clip xxx` | 模糊搜索历史内容，匹配度高的置顶 |
| **回车** | 复制选中项回剪贴板 + 关闭窗口（hit_count +1） |
| **右键** | 「删除此项」/「清空全部历史」 |

**敏感应用黑名单**：
- 默认规则：窗口标题包含「密码」「Password」「Bitwarden」「1Password」「KeePass」时不记录
- 用户可在设置页自定义黑名单关键字
- 隐私优先：剪贴板内容仅本地存储，永不上传

---

### 3.4 设置页配置

| 配置项 | 说明 | 默认值 |
|---|---|---|
| `enabled` | 是否启用剪贴板历史 | `false`（默认关闭） |
| `max_items` | 最大保留条数 | `500` |
| `retention_days` | 保留天数 | `7`（0=永久） |
| `search_enabled` | 是否允许搜索剪贴板内容 | `true` |
| `blacklist_keywords` | 敏感窗口标题黑名单 | `["密码", "Password", "Bitwarden", "1Password"]` |

## 四、图标缓存持久化

### 4.1 问题现状

当前图标提取：
- 自定义协议 `blink-icon://` 每次都重新提取
- 进程内 PNG 缓存，但重启后丢失
- UWP 应用、系统图标每次都要重新走 COM 提取

**影响**：冷启动后前几次搜索图标加载慢，有闪烁感。

---

### 4.2 方案设计

**两层缓存架构**：

```
请求图标
    ↓
Layer 1: 内存 LRU Cache（最多 200 个）→ 命中 → 返回
    ↓ 未命中
Layer 2: 磁盘持久化缓存（SQLite BLOB）→ 命中 → 读入内存 → 返回
    ↓ 未命中
提取图标 → 写入两层缓存
```

**缓存表设计**：
```sql
CREATE TABLE icon_cache (
    path_hash TEXT PRIMARY KEY,      -- 路径 SHA256 哈希（避免长路径）
    png_blob BLOB NOT NULL,          -- PNG 编码后字节
    file_mtime INTEGER NOT NULL,     -- 源文件 mtime（失效判定）
    icon_size INTEGER NOT NULL,      -- 图标尺寸（32/64）
    accessed_at INTEGER NOT NULL,    -- 最近访问时间（LRU 淘汰）
    created_at INTEGER NOT NULL
);

CREATE INDEX idx_icon_accessed ON icon_cache(accessed_at);
```

**失效策略**：
- 源文件 mtime 变化 → 缓存失效
- 缓存总数超过 2000 → 按 `accessed_at` 删除最旧的 500 条
- 超过 30 天未访问 → 自动清理

**启动优化**：
- 启动时不预加载缓存，按需读取
- 后台任务定期清理过期项（每天一次）

## 五、搜索缓存增量更新

### 5.1 问题现状

当前 `StartMenuEngine` 缓存：
- 根目录 mtime 变化 → 全量重新扫描
- 定时强制刷新兜底（每 30 分钟）
- 新增/删除一个快捷方式 → 整个开始菜单重新扫一遍

**影响**：大开始菜单目录全量扫描耗时几百 ms。

---

### 5.2 方案设计

**增量 + 全量混合策略**：

| 场景 | 策略 |
|---|---|
| 根目录 mtime 无变化 | 直接用缓存 |
| 根目录 mtime 有变化 | **增量扫描**：遍历目录对比缓存中的 entry，仅增删变化项 |
| 连续 10 次增量后 | 强制执行一次**全量扫描**兜底（防止漏网之鱼） |
| 每 2 小时 | 后台静默全量刷新 |

**缓存结构升级**：
```rust
// 旧：只存 Vec<AppEntry>
// 新：记录每个文件的状态
struct CachedAppEntry {
    entry: AppEntry,
    path: PathBuf,
    file_mtime: SystemTime,
    file_size: u64,
}

struct StartMenuCache {
    entries: Vec<CachedAppEntry>,
    root_mtime: SystemTime,
    incremental_count: u32,  // 已连续增量次数
    last_full_refresh: Instant,
}
```

**增量扫描算法**：
1. 遍历开始菜单目录，收集所有 `.lnk` 文件的 `(path, mtime, size)`
2. 与缓存对比：
   - 新增文件 → 解析并加入缓存
   - 删除文件 → 从缓存移除
   - mtime/size 变化 → 删除旧 entry，重新解析加入
3. `incremental_count += 1`
4. 若 `incremental_count &gt;= 10`，标记「下次需全量刷新」

## 六、历史权重时间衰减

### 6.1 问题现状

当前历史加权公式：
```rust
// scorer.rs
let history_bonus = (hit_count as f32 + 1.0).ln() * 0.3;
// 上限 0.8
```

**问题**：
- 三年前点击过 100 次的应用 ≈ 现在点了几次的应用
- 权重只增不减，旧应用永远排在前面
- 无法体现「最近常用」

---

### 6.2 方案设计：**指数衰减 + 对数加权**

**新公式**：
```
时间衰减因子 = e^(-λ * days_since_last_use)
其中 λ = ln(2) / 14  ≈ 0.0495 （半衰期 14 天）

历史加权 = ln(hit_count + 1) * 0.3 * 时间衰减因子
上限保持 0.8
```

**衰减曲线**：
| 最后使用距今 | 衰减因子 |
|---|---|
| 0 天（今天） | 1.0 |
| 7 天 | 0.707 |
| 14 天（半衰期） | 0.5 |
| 28 天 | 0.25 |
| 56 天 | 0.125 |
| 90 天 | ≈ 0.044 |

**效果**：
- 今天点的应用权重不变
- 两周前点的权重减半
- 三个月前的几乎不影响排序
- 非常用应用自然「沉底」

**配置项**：
```toml
[search]
history_half_life_days = 14   # 半衰期天数，可调
history_max_bonus = 0.8       # 加权上限
```

**迁移**：无需 schema 变更，只改 `scorer.rs` 计算逻辑。

## 七、性能统计与监控

### 7.1 设计目标

量化核心链路的性能表现，便于发现瓶颈、验证优化效果。

**统计范围**：
- 启动耗时（总耗时、各阶段细分）
- 热键唤起耗时（按键 → 窗口显示 → 可输入）
- 搜索响应耗时（各引擎分别统计）
- 插件响应耗时
- 图标提取耗时

---

### 7.2 数据结构

```rust
struct PerformanceMetric {
    id: Uuid,
    category: MetricCategory,       // Startup / Hotkey / Search / Plugin / Icon
    name: String,                   // 指标名称
    value_ms: f32,                  // 耗时（ms）
    metadata: Option<Value>,        // 附加信息（如插件ID、搜索关键字）
    created_at: DateTime<Local>,
}

enum MetricCategory {
    Startup,                        // 启动阶段
    Hotkey,                         // 热键唤起
    SearchEngine,                   // 搜索引擎
    Plugin,                         // 插件查询
    IconExtract,                    // 图标提取
}
```

---

### 7.3 统计指标清单

| 类别 | 指标名 | 说明 |
|---|---|---|
| **启动** | `startup_total` | 从进程启动到窗口就绪总耗时 |
| | `startup_config_load` | 配置加载耗时 |
| | `startup_services_init` | 各服务初始化耗时 |
| | `startup_frontend_ready` | 前端页面加载完成耗时 |
| **热键** | `hotkey_key_to_show` | 按键到窗口显示耗时 |
| | `hotkey_key_to_focus` | 按键到输入框获得焦点耗时 |
| **搜索** | `search_engine_{id}` | 各搜索引擎单次查询耗时 |
| | `search_total_first_result` | 从输入到首个结果显示耗时 |
| **插件** | `plugin_{id}_query` | 各插件查询耗时 |
| **图标** | `icon_extract_hit` | 图标缓存命中提取耗时 |
| | `icon_extract_miss` | 图标缓存未命中提取耗时 |

---

### 7.4 存储与展示

**存储策略**：
- SQLite 表 `performance_metrics` 持久化
- 保留最近 30 天数据，自动清理过期
- 每天自动计算 P50/P90/P99 分位值，写入日报表

**前端展示（设置页 → 调试 Tab）**：
- 实时性能仪表盘：最近 10 次唤起的 P50/P90 耗时
- 趋势图：近 7 天启动/搜索耗时变化
- 慢查询日志：超过阈值（如 200ms）的请求详情
- 「导出性能报告」按钮：导出 JSON 格式供分析

**阈值告警**：
- 热键唤起 > 100ms → 标记为慢，记录堆栈
- 搜索首个结果 > 50ms → 标记为慢
- 插件查询 > 1000ms → 记录警告

## 九、不做什么（边界明确）

| 项 | 原因 |
|---|---|
| 自建文件索引服务 | 复杂度太高，Everything 已够用，Fallback 只做常用目录 |
| 图片/文件剪贴板 | 纯文本覆盖 90% 场景，二进制后续再说 |
| 图标缓存预加载 | 按需加载更省内存，启动速度优先 |
