# Blink 0.5 — 文件搜索 + Builtin 动作

> **范围**：补齐 P1「文件搜索」+ 内置动作（打开设置/锁屏/关机等），让 Blink 从「应用启动器」成长为「统一操作入口」。
> **关系**：承接 `0.4-intent-router.md`「后续做什么 → 0.5+」;文件搜索补全 MVP P1 缺口，builtin 动作验证「本体功能即召回源」架构。
> **技术栈**：Rust 2024 + Tauri 2.x + WebView2。

---

## 一、文件搜索 FileEngine

### 1.1 目标

用户输入文件名或路径片段时，Blink 能召回本地文件（不仅限于 `.lnk` 应用快捷方式）。

| 输入 | 期望结果 |
|---|---|
| `report` | `D:\Work\report.docx` |
| `downloads` | 常用目录快速跳转 |
| `*.pdf` | 最近访问的 PDF 文件 |

### 1.2 调研结论：三层回退架构

Windows 没有「开箱即用」的全局文件索引 API，但存在多条可用路径。按**速度/覆盖率/用户依赖度**分层回退：

```
用户输入 ──► FileEngine
              │
              ├─► ① Everything HTTP API（首选，约 1–10ms）
              │      条件：Everything 已安装且 HTTP Server 已开启
              │
              ├─► ② Windows Search COM API（次选，约 50–200ms）
              │      条件：Windows Search 服务运行
              │
              └─► ③ 本地目录扫描（兜底，约 100–500ms，范围受限）
                     条件：始终可用，但只覆盖「常用目录」
```

#### ① Everything HTTP API（首选增强）

[voidtools Everything](https://www.voidtools.com) 是 Windows 上最快的文件搜索工具，索引全部 NTFS 文件。

- **接口**：Everything 设置中可开启 HTTP 服务器（默认端口 80 或自定义）
- **查询格式**：`GET http://localhost:xx/?search=query&json=1&path=1&size=1&date_modified=1`
- **返回**：JSON 数组，每项含 `name`, `path`, `size`, `date_modified`
- **Rust 调用**：`reqwest` 发 GET（轻量，无需 FFI）
- **依赖**：用户需自行安装 Everything 并在设置中勾选 **Enable HTTP Server**
- **检测**：启动时 probe `http://localhost:xx/`（可配置端口），可用则标记 `everything_available`

> ⚠️ **Everything 不是强制依赖**。未安装/未开启 HTTP 时静默降级到下一层，用户零感知。

#### ② Windows Search COM API（系统内置）

Windows 自带搜索索引服务（`Windows Search` / `SearchIndexer`）。

- **接口**：`ISearchQueryHelper` + `ISearchCatalogManager`（COM）
- **查询语法**：SQL-like，如 `SELECT System.ItemName FROM SystemIndex WHERE CONTAINS('query')`
- **Rust 调用**：`windows` crate COM binding，或走 OLE DB/ADO
- **依赖**：`Windows Search` 服务必须运行（默认开启，部分用户会关闭）
- **检测**：启动时 probe COM 连接，失败则降级
- **局限**：索引有延迟（新文件可能搜不到）；COM 接口较繁琐

#### ③ 本地目录扫描（兜底）

当 ①② 均不可用时，对「常用目录」做实时遍历。

- **接口**：`FindFirstFileExW` + `FindNextFileW`（Win32）
- **范围**：用户配置的常用目录（`Downloads`, `Documents`, `Desktop` 等）
- **策略**：
  - 首次唤起时后台扫描缓存（类似 StartMenuEngine 预扫）
  - 搜索时直接对缓存做 fuzzy 匹配
  - 缓存 mtime 增量失效
- **局限**：范围有限，不覆盖全磁盘；深层目录首次扫描慢

### 1.3 配置化

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `file_search.enabled` | `true` | 是否启用文件搜索 |
| `file_search.provider` | `"auto"` | `"auto"` / `"everything"` / `"windows_search"` / `"local"` |
| `file_search.everything_port` | `80` | Everything HTTP Server 端口 |
| `file_search.local_paths` | `["Downloads", "Documents", "Desktop"]` | 本地扫描目录 |
| `file_search.result_limit` | `20` | 文件结果上限 |

### 1.4 引擎设计

```rust
pub struct FileEngine {
    provider: FileProvider,
    local_cache: Arc<RwLock<Vec<FileEntry>>>,
}

enum FileProvider {
    Everything { port: u16 },
    WindowsSearch,
    Local { paths: Vec<PathBuf> },
}

impl SearchEngine for FileEngine {
    fn id(&self) -> &'static str { "file" }
    fn lane(&self) -> Lane { Lane::Async } // ①② 够快可改 Sync；③ 必 Async
    // ...
}
```

- `FileEngine` 实现 `SearchEngine`，接入 async lane
- ①② 实际很快（<20ms），可评估是否直接放 sync lane；但为稳妥先放 async，实测后再调
- 结果项 `SearchAction::Open { path }`，与 AppEntry 共用 Open 动作
- 文件类型图标复用现有 `search/icon.rs`（按文件扩展名取系统图标）

### 1.5 验收标准

- 安装 Everything 并开启 HTTP Server → 输入文件名 → 1s 内出结果
- 未安装 Everything 但 Windows Search 运行 → 输入文件名 → 有结果（慢一点）
- 两者都无 → 常用目录内文件可搜到
- 失败时静默降级，不报错、不阻塞其他引擎

## 二、Builtin 动作（本体功能召回）

### 2.1 问题

当前 Blink 只能通过 `launch_app` 打开外部程序，**无法通过搜索唤起自身功能**（如打开设置页、锁屏、关机等）。用户期望：

| 输入 | 动作 |
|---|---|
| `settings` | 打开 Blink 设置窗口 |
| `setting hotkey` | 打开设置窗口并定位到「快捷键」Tab |
| `lock` | 锁定工作站 |
| `shutdown` | 关机 |
| `restart` | 重启 |
| `sleep` | 睡眠 |
| `clear history` | 清空搜索历史 |

### 2.2 架构决策：内部 SearchEngine，不走插件协议

**不推荐**把这些动作做成独立进程插件（如 `plugin-settings`），因为：

1. **本体功能是 core 自带能力**，不需要独立进程隔离
2. **需要即时响应**（sync lane），独立进程有启动开销
3. **需要访问 core 内部状态**（AppHandle、配置、窗口句柄），插件协议目前无此通道
4. **与 CalcEngine/StartMenuEngine 同一抽象层级**——都是 core 内部引擎

**方案：新增 `BuiltinEngine`（内部 SearchEngine）**

```rust
pub struct BuiltinEngine;

impl SearchEngine for BuiltinEngine {
    fn id(&self) -> &'static str { "builtin" }
    fn lane(&self) -> Lane { Lane::Sync }

    async fn search(&self, query: &str, _ctx: &QueryContext<'_>) -> Vec<SearchItem> {
        // 1. query 模糊匹配 builtin 动作表
        // 2. 命中则产出 SearchItem，action = SearchAction::Builtin { id }
        // 3. 前端 / commands 层识别 Builtin action 并执行
    }
}
```

### 2.4 协议扩展：PluginAction 增加 `Builtin` 类型（预留）

虽然本体动作走内部引擎，但**插件协议也应预留**「调用本体功能」的能力——未来第三方插件可能需要打开设置页或锁屏。

```rust
// src/plugin/protocol.rs
pub enum PluginAction {
    Copy { text: String },
    Open { path: String },
    /// 调用 Blink 内置功能（预留，0.5 暂不实现插件侧调用）。
    Builtin { id: String },
}
```

- `PluginAction::Builtin` 0.5 仅解析不执行（插件返回此 action 时 warn! 跳过）
- 0.5+ 若第三方插件有真实需求，再补执行链路

### 2.5 前端适配

`AppEntry.action.kind` 当前只有 `Open`/`Copy`。需扩展：

```rust
pub enum ActionKind {
    Open,
    Copy,
    Builtin,  // 新增
}
```

前端 `actions.js` 识别 `Builtin` → 调用 `invoke("execute_builtin", { id })`。

`commands.rs` 新增：

```rust
#[tauri::command]
pub async fn execute_builtin(app: tauri::AppHandle, id: String) -> Result<(), String> {
    match id.as_str() {
        "open_settings" => { /* 打开设置窗口 */ }
        "lock" => { /* LockWorkStation */ }
        // ...
    }
    crate::window::hide(&app, "builtin");
    Ok(())
}
```

### 2.6 与 Intent 路由的关系

`BuiltinEngine` 作为 sync lane 引擎注册到 `SearchService`，与 CalcEngine/StartMenuEngine 平等竞争：

- 输入 `settings` → BuiltinEngine 命中 → 产出「打开设置」项
- 输入 `chrome` → StartMenuEngine 命中 → 产出 Chrome 应用
- 输入 `lock` → BuiltinEngine 命中 → 产出「锁定电脑」

不通过 RuleRouter/插件路由——因为 builtin 动作不是插件，无需 manifest。

## 四、风险与对策

| 风险 | 对策 |
|---|---|
| Windows Search COM API 复杂/不稳定 | ① 先用 Everything HTTP 覆盖核心场景；② COM 部分用 `spawn_blocking` 隔离；③ 失败静默降级 |
| Everything HTTP 端口冲突 | 配置项允许用户自定义端口；探测失败即降级 |
| Builtin 动作关键词与应用名冲突 | fuzzy 打分自然竞争；builtin 动作 score 设中等（如 0.7），不强置顶 |
| `PluginAction::Builtin` 破坏旧插件兼容 | serde tag 新增变体，旧插件不返回此类型，无影响 |
