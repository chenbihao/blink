# Phase 文档规范

> 每个 `phases/{version}-{topic}.md` 必须遵循的结构、要素与生命周期规则。**新建 phase 前先读本文。**
>
> 本文本身就是一个 phase 文档结构的示范——它的章节组织即模板。

---

## 一、为什么需要这份规范

历史 phase（0.1~0.13）结构各不相同：早期 phase（0.1-0.6）只有"已完成清单 + 已知待办"；中期（0.8-0.13）有里程碑和文件索引但章节命名不统一（"关联文件速查"vs"关联文件索引"vs"关键文件索引"）；只有近期的 **0.14 / 0.14.6** 演进出最完整的形态。

本文把 0.14/0.14.6 的成熟结构**固化成模板**，让每个新 phase 从第一天就有清晰骨架，不必再靠默契。已有 phase 不追溯重写——它们在自然演进时按本规范收敛即可。

---

## 二、Phase 文档的三种状态

| 状态 | 标记 | 何时用 | 文档重点 |
|---|---|---|---|
| **规划中** | 📋 | 设计阶段，未动代码 | 背景动机 + 核心决策 + 里程碑 + 关键决策记录(ADR) + 验收标准 + 关联文件速查(规划) |
| **进行中** | 🚧 | 已开工，分子版本推进 | 规划内容 + 各子版本"已完成"标记 + 实施中追加的决策记录 |
| **已完成** | ✅ | 全部子版本落地 | 精简后的实现总结 + 关键教训 + 遗留/已知问题（见 §六 精简规则） |

**状态写在文档开头引用块**（见 §三 模板）。子版本推进时，里程碑表的对应行打 ✅。

---

>
> **动机**：{为什么现在做，一两句}。

> **前置**：{依赖哪个前置 phase 完成，或"无"}。
>
> **原则**：{本 phase 的硬约束，如"不改变对外行为""无 bundler 约束不变"}。

### 结构块速查

| 结构块 | 性质 | 何时可省 |
|---|---|---|
| 引用块（范围/状态/动机/前置/原则） | ★ 必含 | 不可省 |
| 背景与动机 | ★ 必含 | 不可省（含 §"不是问题的"澄清） |
| 核心设计/决策 | ★ 必含 | 不可省 |
| 分子版本展开 | ★ 必含 | 单子版本可合并进核心设计 |
| 里程碑（子版本+复用盘点+不做） | ★ 必含 | 不可省 |
| 关键决策记录（ADR） | 推荐 | 无争议的小改可省 |
| 验收 | ★ 必含 | 不可省 |
| 关联文件速查 | 推荐 | 改动面小可简化 |

## 四、子版本命名与切分

**命名**：`{大版本}.{小版本}`，如 `0.14.0` / `0.14.1`（子版本下也可再带第三段，如 `0.14.6`）。每个子版本是一个可独立验收、可独立提交的单元。

**切分原则**：

| 原则 | 说明 |
|---|---|
| **依赖串行，独立并行** | 有依赖关系的子版本标清（如 0.14.1 依赖 0.14.0）；无依赖的可并行或任意顺序 |
| **先基础后应用** | 基础设施子版本（协议层/抽象层）排在前面，应用层子版本排在后面 |
| **一个子版本一个验收块** | 每个子版本在"验收"段有独立 checkbox 块，完成即全绿 |
| **P0/P1/P2 标优先级** | P0=核心路径必做，P1=重要，P2=可后置/可分批 |

**反例**（避免）：把不相关的事塞进一个子版本（如"配置域下沉 + 顺便改个图标"）；子版本粒度过细（单文件改动单独成子版本）。

## 五、进度更新约定

| 时机 | 动作 |
|---|---|
| 开工某子版本 | 里程碑表对应行状态保持，文档头状态改 🚧 |
| 完成某子版本 | 里程碑表对应行打 ✅；验收段 checkbox 勾上；如有实施中发现的新决策，补进 §五 ADR |
| phase 全部完成 | 文档头状态改 ✅；执行 §六 精简 |
| 发现超范围/需推迟 | 写进 §4.3"不进本版的项"或单列"推迟到 {version}"小节（0.12 §七 示范了推迟项写法） |

**里程碑表状态标记**：📋 规划 / 🚧 进行中 / ✅ 已完成。子版本完成只打行级 ✅，文档头状态仅在全部完成时才改 ✅。

## 六、Phase 完成后的精简规则（重要）

**原则**：完成的 phase 不是"越多越好"的历史档案，而是**后人改这块代码时该读什么的精炼索引**。规划态文档可以详尽（问题溯源、决策推导、代码示例都有助于定方案），但**完成后要大幅瘦身**——读者这时要的是"结论"和"索引"，不是"我们当年是怎么讨论出来的"。

完成后做以下精简：

| 内容 | 处理 |
|---|---|
| **跨版本通用的铁则/约定**（如"错误处理用 thiserror""事件名常量化"） | **迁出**到对应 spec（`spec-backend.md` / `spec-frontend.md`），phase 里改一行指针 |
| **跨版本通用的架构决策**（如四域铁则、Capability/Action 边界） | **迁出**到 `spec-architecture.md`，phase 里改指针 |
| **背景动机、问题溯源推导**（"怎么发现的"、逐个能力审查表格、根因分析链）| **删推导，留结论**——一两句说清"要解决什么问题"即可，删发现过程 |
| **决策推导过程**（"曾考虑 A/B，否决理由 1/2/3"、选型对比）| **删推导，留结论**——决策结论 + 一句关键理由（若有踩坑价值）|
| **代码示例**（Rust struct/enum 定义、JSON 配置示例、函数签名）| **删**——读者直接看源码；phase 只用文字描述字段语义/结构要点 |
| **逐条实施流水账 / 验收 checkbox 清单**（如"0.12.4 修复 15 项"、0.14.5 死链路行号表）| **精简**为一两句总结，细节留在 git log |
| **"规划中"语气的描述**（"建议分步…""考虑用 codegen"）| **改为已完成事实陈述**，删掉犹豫语气 |
| **已被后续 phase 推翻/迁移的决策** | **保留但标注**"已被 {version} 取代"，否则后人会困惑 |

**精简后保留的**：背景一句话（为什么做）+ 核心决策结论（怎么定的，含关键约定/踩坑）+ 里程碑 + 关联文件索引（改了哪些文件）。

**精简后删掉的**：问题溯源推导 + 决策对比过程 + 代码示例 + 实施流水账 + 已迁出 spec 的通用约定 + 过时的规划语气。

> **"重要处可留几句精华"例外**：并非所有推导都该删。若某条决策的**理由本身是后续维护的关键知识**（如"为何不合并 Capability/Action"、"为何选 jsonpath 而非自造"），保留一两句精华理由——判断标准是"后人会不会因为不知道这个理由而走弯路"。0.14 的"轨道 B 实现澄清"（0.14.5 修订）就是这类，应保留。

> **整体判断标准**：精简后，一个新人想改这块代码时，读这个 phase 能快速知道"做了什么、为什么这么定、哪里容易踩坑、改了哪些文件"——结论和索引到位即可，过程留在 git log。

## 七、与 specs 的分工

| 文档 | 回答 | 跨版本？ |
|---|---|---|
| **`specs/spec-*.md`** | 怎么做（HOW 的硬约束/铁则） | ✅ 跨版本通用 |
| **`phases/{version}-*.md`** | 这版做了什么、为什么这么做（WHAT + 决策） | ❌ 单版本档案 |

**铁则**：通用约定写进 spec，单版实现细节写进 phase。完成后把通用约定从 phase 迁到 spec——避免同一铁则在 5 个 phase 里各写一遍（这是当前文档的最大冗余源）。

---

## 八、速查：建一个新 phase 的步骤

1. 看 `00-overview`（或新的 `docs/README.md`）确认版本号未占用、定位主题
2. 复制 §三 模板骨架到 `phases/{version}-{topic}.md`
3. 填引用块（范围/状态 📋/动机/前置/原则）
4. 写背景动机——**包含"不是问题的"澄清**（防止误改）
5. 核心决策——有争议的决策先进 §五 ADR 标"待定"，定案后改"已定"
6. 拆子版本，排里程碑，标依赖和优先级
7. 写验收——每个子版本一个 checkbox 块，条件要可断言
8. 列关联文件速查（可先标"规划"）
9. 开工后按 §五 更新进度；全部完成后按 §六 精简
