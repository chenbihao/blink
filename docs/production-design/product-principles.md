## 11. 工程规范(跨版本统一约束)

### 11.1 日志分级规范(强制执行)

**原则**:日志是排障的基础,但过多日志会掩盖真正问题。统一分级如下:

| 级别 | 数值 | 含义 | 开启场景 | 典型用途 |
|------|------|------|----------|----------|
| **error** | 1 | 致命异常,功能受影响 | 默认全开 | 数据库失败 / 启动失败 / 关键操作异常 |
| **warn** | 2 | 潜在问题,不影响运行 | 默认全开 | 多次重试 / 配置异常但默认值兼容 |
| **info** | 3 | 关键状态变化,里程碑事件 | 默认全开 | 应用启动 / 配置更新 / 插件加载 / 用户关键操作 |
| **debug** | 4 | 主流程节点,开发阶段有用 | 开发/测试 | 收到搜索请求 / 返回结果数 / 分支决策条件 |
| **trace** | 5 | 最详细诊断信息 | 排查特定问题时才开 | HTTP响应体 / 完整参数 / 边界条件触发 / 循环内变量 |

**规范(CLAUDE.md §7 同步)**:
1.  **结构化日志优先**: `tracing::debug!(%query, port, "搜索 Everything")` 而非字符串拼接
2.  **错误必带上下文**: `tracing::error!(%path, %e, "启动应用失败")` 而非仅"失败了"
3.  **预期降级不告警**: Everything没装 / 剪贴板被锁定 / 图标提取失败 → 这些是设计好的降级路径,用debug/trace而非warn/error
4.  **敏感信息永不记日志**:密码 / 剪贴板内容(除trace级谨慎使用) / 用户隐私数据

## 13. 最小操作路径(横切设计准则)

> **核心信念**:blink 的价值不在功能数量,而在**同一目标的操作路径比原来短**。任何新功能加入前,先回答:**这条路径是不是变短了？** 若不是,不做。
>
> **性质**:跨版本通用产品准则;所有 phase 引入的新能力都要经这条尺子度量。**§2 的"任何操作都比原来快"是价值命题,§13 是把它拆成可执行的三层评价指标**。

### 13.1 三条子准则:更快、更丝滑、更智能

| 维度 | 含义 | 衡量方式 |
|---|---|---|
| **更快** | 时间维度——从产生意图到看到结果/执行动作的**总耗时**下降 | 用秒/毫秒对比原路径,列出唤起 / 输入 / 命中 / 执行四段耗时 |
| **更丝滑** | 心智维度——**中断/切换/等待**减少,不打断用户当前专注流(不需要切窗口、不需要复制粘贴、不需要读长提示) | 数一次操作中的**心智切换次数**(键盘 → 鼠标算切换、切窗口算切换、等待可见 loading 算切换) |
| **更智能** | 感知维度——blink **主动利用已知上下文**减少用户输入(选区/剪贴板/前台应用/历史/时间),让"应该输入的东西"变成"不需要输入" | 数用户实际敲键次数 vs 无感知路径的敲键次数 |

三者**同权**,但存在优先级:**优先更快 → 再更丝滑 → 最后更智能**。理由:再"智能"的推荐,若首屏慢/假阳性高,反而增加中断。反面案例见 §13.3 的 0.8.2 教训。

### 13.2 落地时的四问

每个新交互/功能上手前,自问四条,任何一条答"不确定"就先做实验或砍需求:

1. **原路径几步?新路径几步?** 步数下降至少 1 步才值得做。原路径 3 步、新路径 3 步、只是"看起来更潮"——不做。
2. **失败时用户还能回到原路径吗?** blink 假阳性(推错动作/翻译错句/Ghost 干扰)不能让用户比原来还慢。**永远保留 escape hatch**(Esc 关窗、忽略 Ghost 继续输入、常规搜索不受影响)。
3. **P0 主链路会退化吗?** 唤起 → 输入 → ESC 隐藏的可靠性(§2 核心目标)不接受任何回归。新感知/推荐/AI 通道跑在**旁路**上,不阻塞主链路(如 Suggestion 通道独立于 route candidates)。
4. **能被用户关吗?** 感知类/推荐类能力必须能在设置页一键关闭。默认可以激进,但用户学一次就能永久静音,详见 [[context-trigger-user-configurable]] 与 [[configurable-by-default]]。

### 13.3 关键决策沉淀(反面案例 → 正例)

| 决策 | 反面 | 正解 | 出处 |
|---|---|---|---|
| **弱意图信号该 pull 不该 push** | 0.8.2 Context 命中直接 Priority 抢首屏——"复制英文只是想粘贴"就被推翻译,首屏被抢 = **变慢** | 0.8.3 转 Ghost + Tab 采纳:感知在旁路,采纳零打扰,不采纳零代价 | [[context-as-ghost-suggestion]] / phases/0.8 §四 |
| **每加一路信号就多一个字段是设计味道** | 若 0.8.3 继续加 `context_suggestion` 字段,0.9 再加 `ai_suggestion`,前端要写 `pickGhost()` 硬编码优先级链——每次新增等于一次前端重构 | 统一 `Suggestion { source, confidence }` 契约,多路后端竞争 top-1,前端只消费单字段 | [[suggestion-abstraction-for-0-9]] / phases/0.8 §四 |
| **感知类路径要有 escape hatch** | Ctrl+C 兜底方案会污染剪贴板历史——用户无法回到"没被影响"的状态 → 不可接受 | UIA 划词只进内存 snapshot,不改剪贴板;Scintilla/Java 拿不到就是拿不到,不用有副作用的兜底 | phases/0.8 §1.1 |
| **manifest 声明 ≠ 用户启用** | 0.8.2 曾让"翻译 manifest 声明 context trigger 就纳入路由",用户无关闭入口——违反 §13.2 第 4 问 | 0.8.3 集中到"上下文智能感知"面板,黑名单同构 `disabled_builtin_actions` | [[context-trigger-user-configurable]] |
| **变换 keyword 拓扑要保 Tab 采纳可回原路径** | 若 Ghost.replacement 用 `id 末段`(`translate`)而非本地化 keyword(`翻译`),zh 用户 Tab 后 route 找不到命中 → 死态 | Ghost.replacement 反查 Router 内 keyword 表按当前 UI 语言偏好挑,加闭环单测防回归 | phases/0.8 §4.2 |

### 13.4 与其他原则的关系

- **vs §2 P0 至上**:P0 是**底线**(不能倒退),§13 是**方向**(每步都要更好)。
- **vs §11 日志规范**:§11 管排障工具,§13 管产品判断。两者不冲突,可叠加。
- **vs 配置化优先**([[configurable-by-default]]):"能被用户关吗"是 §13.2 第 4 问,也是配置化优先的具体应用场景。

## 14. 可辨识度与视觉一致性(横切设计准则)

> **核心信念**:blink 的 UI 是**功能面**,不是**装饰面**。所有视觉决策先答"这么写用户看得清楚吗",再答"这么写好不好看"。可辨识度输了,一切美感都是负债。

### 14.1 三条子准则:辨识度、对比度、稳定视觉重量

| 维度 | 含义 | 具体规则 |
|---|---|---|
| **辨识度** | 单个字符/单个词能不能被第一眼认出——不是"整段能读",而是"扫一眼就抓到" | 中文不用斜体(§14.2);高频动作 icon + 短标签双通道;结果项 title/subtitle 保留视觉层级 |
| **对比度** | 主题(dark/light)下前景色与背景色的差值必须过 WCAG AA(4.5:1 正文 / 3:1 大字);次要文本用透明度弱化,但**弱化后仍需过 3:1** | Catppuccin Mocha/Latte 双主题,均以 base 色为背景,text 色为正文;弱化用 `opacity: 0.6` 不用低对比度灰 |
| **稳定视觉重量** | 同类元素在不同状态下**块面积/位置不跳变**;新增元素要么完全不出现,要么给出稳定的位置;弱信号(Ghost/hint)不能挤走强信号(结果/输入) | Ghost 用**行内叠加**不占布局;Chord 提示条用**底部固定条**不撑高列表;首屏结果数由屏幕高度算好,不因内容变化跳变(参见 product-interaction §3.5) |

### 14.2 中文不用斜体(强制规则)

**规则**:blink UI 中的**中文文本**一律不使用 `font-style: italic`(含 CSS 显式、编辑器默认、Markdown 渲染衍生)。**英文/代码/引用可保留斜体**。

**为什么**:
- Windows 中文字体(微软雅黑/思源黑体)的斜体渲染是**几何倾斜**而非真正的**意大利体**,笔画粗细不均,小字号下辨识度显著下降(尤其"翻译""上下文"这类高频文案)。
- 中文没有印刷传统上的斜体表达强调/引用的心智,用户对倾斜中文的默认解读是"字歪了 / 是不是 bug",反而分散注意力。

**替代方案**:
- **视觉弱化**(次要文本、hint、subtitle)→ `opacity: 0.6`(或降级用主题的 `overlay1` / `subtext0` 色阶)
- **强调**(重要提示、警告)→ 加粗 `font-weight: 600` + 主题的 `mauve`/`red` 强调色,不用斜体
- **引用/代码/命令行**(如"输入 `翻译 hello`") → 用 `<code>` 或等宽字体 + 弱背景色,不用斜体

**执行边界**:
- 前端 `frontend/css/*.css`:**禁用** `font-style: italic` 出现在含中文的选择器上;若需给英文单独用,选择器要窄到只覆盖英文内容(如 `code`, `.mono`, `.en`)。
- 设置页/i18n 文案:任何 `<em>` `<i>` 若渲染中文,前端 CSS 兜底 `em, i { font-style: normal }`(0.8.3 相关调整已落地)。
- 产品文档(本目录 `.md`):`_文字_` / `*文字*` Markdown 斜体在 GitHub 渲染看着还行,但**导出到 UI 展示时**不要保留。

**来源**:[[no-italic-for-chinese]],0.8.3 Ghost origin 弱化时验证。

### 14.3 主题对比度(强制规则)

- **主题 = 底层配色变量**,不是"皮肤"。所有颜色走 CSS 变量,禁止在业务 CSS 里硬编码 `#xxx`/`rgb(...)`。参见 phases/0.5 §四 主题系统。
- **正文对比度 ≥ 4.5:1**、**大字(≥18px 或粗体≥14px)对比度 ≥ 3:1**(WCAG AA 底线)。0.5.4 引入 Catppuccin 时已按此校准过。
- **次要文本弱化**只允许两条路径:
  1. `opacity: 0.55 ~ 0.75`(推荐)——保色相,只降 alpha,与主题色相协调
  2. 使用主题预设的 `overlay0/1/2` / `subtext0/1`——已在 palette 中校对过对比度
  **禁止**新调低饱和度灰色(如 `#888`),不同主题下对比度不可控。
- **Ghost/hint 类弱信号**:采用 `opacity: 0.5 ~ 0.6`,允许略低于正文 AA,但**信息重复**保底(Ghost 内容以 keyword 表为准,Tab 采纳后能重新出现在结果里,不依赖用户"必须看清")。

### 14.4 稳定视觉重量(强制规则)

- **弱信号绝不撑起布局**:Ghost 行内叠加、Chord 提示条底部固定条,不改变主列表几何。
- **首屏结果条数由屏幕高度决定**,不随内容变化跳变(参见 product-interaction §3.5;下限 4 上限 9)。
- **新加感知/推荐/AI 通道不加高首屏**:感知类候选(如 Context 命中)进入首屏时替换低分候选,不是**追加**到首屏顶部把原有强信号挤下屏。

### 14.5 落地检查清单(每次前端改动自查)

- [ ] 新写的 CSS 里有没有中文选择器叠了 `font-style: italic`?没有 → ✅
- [ ] 新加的颜色是否走了主题变量?硬编码 → ❌
- [ ] 弱化文本用的是 `opacity` 还是新调的低饱和度灰?后者 → ❌
- [ ] 新元素在 dark/light 双主题都测过对比度?未测 → ❌
- [ ] 新元素出现/消失时布局有无跳变?有跳变 → 改成行内叠加或固定位置
- [ ] 涉及键位提示时,走的是 `kbd.js::renderKey/renderCombo` 还是自己拼字符串?后者 → ❌(违反 §14.7)

### 14.6 与其他原则的关系

- **vs §13 最小操作路径**:§13 管**能不能更快**,§14 管**看不清就没意义**——两者叠加。Ghost 采纳能不能更快?能。前提是 Ghost 本身**看得清但不打扰**,这是 §14 的活。
- **vs 主题系统**(phases/0.5 §四):主题系统提供 palette,§14 定义**如何用 palette**。palette 是弹药,§14 是射击原则。

### 14.7 键盘提示样式统一(强制规则)

**准则**:任何呈现键位的地方,视觉与生成路径全项目一致——只有一套 `<kbd>` 组件、一套组合键约定、一套分隔符语义。

**为什么强制**:0.8.5 §6.4 Chord 提示第一版直接 innerHTML 拼字符串,用 macOS 的 `⌥` 符号连接键位——与项目已有 statusbar / 设置页快捷键的 filled pill 键帽完全脱节。用户当场察觉"这块 UI 语言不对"。键盘提示是 launcher 类工具的高频视觉元素,一旦风格分裂,产品显得**是几个不同的人做的**——违背 §14 的"辨识度即品牌"。

**具体约束**:

| 场景 | 生成路径 | 反面案例 |
|---|---|---|
| 单键(如 `Enter`/`Tab`) | `<kbd class="kbd">Enter</kbd>` 或 `renderKey("Enter")` | 直接写 `[Enter]` 或 `<Enter>` 文本 |
| 组合键(如 `Alt+A`/`Ctrl+K`) | `renderCombo("Alt+A")` → 自动嵌 `.kbd-plus` `+` 连接符 | `<kbd>Alt</kbd><kbd>A</kbd>` 无连接符(会被读成两个独立键) |
| 平台差异符号(`⌘`/`⌥`) | **不用**——Blink 是 Windows 定位,坚持 `Alt`/`Ctrl` 文本 | `⌥A` / `⌘K` 之类的 macOS 符号 |
| i18n 文案里插键位 | 用 `{{key:Tab}}` 模板占位符,`renderHint` 替换 | 硬编码字符串再事后 innerHTML 拼装 |

**分隔符语义**:

- 键与键**之间**(同一组合)——`+` 连接符(`kbd-plus`)、贴附间距(`kbd-group gap: 0.15em`)
- 提示之间(不同操作/不同 Chord)——竖线 `│` 加大 margin(`chord-sep margin: 0.7em`)
- `·` 圆点保留给"参数分隔"类语义(如 statusbar 里 `翻页 · 3/5`),不用于组合键分组

**唯一真源**:

- 键帽样式:`frontend/css/kbd.css` 里 `.kbd` / `.kbd-group` / `.kbd-plus`
- 生成工具:`frontend/js/kbd.js` 里 `renderKey` / `renderCombo` / `renderHint`
- 修改任何键位视觉都改这三个文件,**不允许**在业务模块(chord.js/statusbar.js/hints.js/settings.js)里再造轮子

**落地路径**:新 UI 要显示键位时:
1. 静态文案 → i18n 文件写 `{{key:X}}` 模板 → `renderHint` 渲染
2. 动态列表(Chord/命令面板/自定义快捷键) → 遍历时 `renderCombo(comboString)`
3. 命中提示(如 tooltip 上"按 `Ctrl+K` 唤起") → 同 1
