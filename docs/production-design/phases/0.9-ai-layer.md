# Blink 0.9 — Agent 地基(统一 Tool 架构 + Provider + 主窗口文本闭环)

> **范围**:能力描述统一 schema + `Action` trait tool-call 兼容 + Provider 多档抽象 + 主窗口「打字 → 路由 → 执行」纯文本闭环
>
> **前置**:0.8 全部完成(四域架构 + 0.8.6 三个统一入口)。产品定位与护城河见 [product-platform-平台.md §6](../product-platform-平台.md#6-护城河定位--统一-tool-架构)。
>
> **原则**:本体只提供最小抽象,**Provider 全 buildin(rig-core 直编)**;**确定性与 AI 路径分离**;**AI 调用期间必有感知反馈**;**主窗口模式** AI 只产 Suggestion / tool-call 候选,`AgentBuilder` 不用于主窗口;**Agent 窗口模式**(0.10)允许 rig 更多能力。

## 二、已落地的核心设计(0.9.0~0.9.3 精简归档)

### 2.1 统一 Tool 架构

- **一切皆 tool**:builtin(同进程) + 插件(IPC) + MCP/skill(0.11 预留)
- **统一描述层**:向 MCP/OpenAI function calling/rig `ToolDefinition` 对齐,执行路由按 `exec` 字段分流
- **落地**:`ActionSchema` + `to_rig_tool()` 唯一 rig 类型触点

### 2.2 Provider 多档抽象

- **三档配置**:路由模型(快/便宜) → 轻量模型(日常) → 主模型(最强)
- **rig 按模式分层**:主窗口只用 `CompletionModel` + `ToolDefinition`;Agent 窗口(0.10)开放 `AgentBuilder` + memory + tool loop
- **Provider 全 buildin**:LLM 流式转发过 IPC 与「AI 反馈铁则」冲突
- **密钥安全**:Windows Credential Manager + `SecretString` zeroize on drop

### 2.3 主窗口文本闭环

```
用户打字
  ├─ 命中规则? ──→ 确定性快速通道,直接执行(不过 AI)
  └─ 未命中 → 四筛子过滤 → 调路由模型
       ├─ 高置信 + 安全动作 ──→ 直接执行
       ├─ 需多轮 ──→ Ghost "展开对话"(0.10)
       └─ 不确定 ──→ 回退常规搜索
```

**两条路径铁则**:确定性路径(< 1s)不过 AI;AI 永远是回退决策者。

### 2.4 四筛子决策树

| 筛子 | 默认阈值 |
|---|---|
| 最短长度 | ≥ 4 字符(≥ 2 CJK) |
| 含空格 | 必含至少 1 个 |
| 非纯数字/纯符号 | 排除 |
| 非 URL / 文件路径 | Awareness 已判定时不走 AI |

**四铁则**:默认关 / 命中规则不走 AI / 用户可全局关 / 必埋遥测

### 2.5 SLO 分档

- **骨架层**(我们控):硬超时 2500ms / ESC 零延迟取消 / loading 150ms 反闪烁 / Provider 切换零重启
- **观测层**(供应商决定):P50/P95 是用户配的供应商实际表现,设置页调试 tab 展示

### 2.6 插件 Tool-Call(0.9.3)

- manifest 声明 `tools` → 启动时自动注册进 `ActionRegistry`
- `ActionRegistry` 改 `RwLock`,支持动态注册
- Tool 分组聚合:12 内置动作 → 3 个 AI tool,减少 prompt token

### 2.7 类型收窄铁则

主窗口拿到的类型编译期没有 `AgentBuilder` 能力——`AIProvider` trait 只有 `kind / model_id / complete` 三个方法。

## 七、0.9.7 Capability 能力协议层（✅ 2026-07-13）

> **动机**：0.9 的「一切皆 tool」只归一了两源（builtin Action + plugin tool）。第三源——平台能力（截图/剪贴板/文件搜索）——被焊死在交互入口里，没有显式建模。Capability 层补齐这第三源，让能力从「焊死在入口」解放为「可被 AI tool_call / Action 编排 / 未来 CLI / 未来 MCP 共同消费的标准化单元」。

### 7.1 协议设计

**两层投影**（核心架构决策）：
- **协议层**（对外，0.11 派生）：`invoke(Value) → Result<Value, Error>`，纯 JSON 进出。CLI/MCP 派生的输入。
- **进程内层**（对内，0.9.7 落地）：`invoke(args, ctx) → Result<CapabilityResult, CapabilityError>`。带 `InvokeContext`（app_handle + deadline）。

**三件套**：

| 件 | 说明 |
|---|---|
| **schema** | 纯 JSON Schema（不绑 Rust 类型），`CapabilitySchema { name, description, parameters }`。0.11 派生 CLI（→clap）和 MCP（→rmcp）零摩擦 |
| **invoke** | `Capability::invoke(args: Value, ctx: &InvokeContext) → Result<CapabilityResult, CapabilityError>`。运行时依赖通过 `ctx.app_handle` 获取（满足 inventory 零参构造） |
| **result** | 四变体：`Text` / `Items` / `Blob{mime,bytes}` / `Done{summary}`。消费方决定投影形态 |

**错误模型**：六变体 `CapabilityError`（`InvalidArgs` / `Permission` / `Timeout` / `Cancelled` / `NotFound` / `Internal`），`Cancelled` 不报给 LLM（用户已切走）。

### 7.2 五个样板能力

| Capability | 入参 | 出参 | 来源 |
|---|---|---|---|
| `capture_screen` | `{display?}` | `Blob{png}` | 复用 `screenshot::begin_session` + SESSION cache |
| `crop_image` | `{x,y,w,h}` | `Blob{png}` | 复用 `screenshot::crop` + `encode_png` |
| `read_clipboard` | `{}` | `Text` | 新写 `platform::clipboard::read_current_text` |
| `write_clipboard` | `{text?\|image_bytes?}` | `Done` | 复用 `write_bgra` + 新写 `write_text_to_clipboard`（CF_UNICODETEXT） |
| `search_files` | `{query,max_results?}` | `Items` | 包装 `FileEngine`，invoke 时从 SQLite 加载真实 config |

### 7.3 关键设计决策

**Step 3 不改 ScreenshotAction**（实施时确认）：原计划把 ScreenshotAction/capture_region 改成编排 Capability，但精读代码后发现**会性能退化**——Action 需要 `ScreenCaptureMeta` 给 overlay 精确定位，crop 返回 BGRA 直写剪贴板（零编码）。结论：Capability 和现有交互入口**共享底层 platform 函数，各自独立存在**。

**inventory 自动注册**：新增能力只需 `inventory::submit!`，注册表零改动。`CapabilityRegistry::new()` 启动时遍历 `inventory::iter` 收集。

**超时/取消/SLO 三铁则**：
1. 硬超时：`InvokeContext.deadline`，`search_files` 用 `tokio::time::timeout_at` 包裹 + 前置 `is_expired()` 检查
2. 取消：seq 校验（开始前 + 完成后双校验），用户切走则静默丢弃
3. SLO：`MetricCategory::Capability`，`CapabilityRegistry::invoke()` 包装层自动埋点（Cancelled 不计）

### 7.4 AI tool 池接入

- `build_aggregated_tools` 扩展：同时收集 Action 分组 + Capability 独立 schema
- `handle_ai_tool_calls`：**Capability 优先**——先查 `CapabilityRegistry`，命中走 `handle_capability_call`，未命中走 Action 路径
- `CapabilityResult` 前端投影：Text → Copy 条目 / Items → Open 列表 / Blob → 摘要 / Done → 摘要
- `CapabilityResult::to_rig_tool_result()` / `CapabilityError::to_rig_tool_result_text()` 投影函数已就绪（0.10 multi-turn 预备）

### 7.5 为 0.10/0.11 铺的路

| 落地点 | 复用 0.9.7 的什么 |
|---|---|
| 0.10 北极星「语音找文件」 | `search_files` Capability 已进 AI tool 池，AI 可 tool_call 搜文件 |
| 0.10 Agent 窗口 multi-turn | `to_rig_tool_result()` / `to_rig_tool_result_text()` 投影已就绪 |
| 0.11 CLI 暴露 | `CapabilitySchema.parameters` → clap 参数；`CapabilityResult` → stdout |
| 0.11 MCP server | `CapabilitySchema` → rmcp tool（rmcp feature 已启用） |
| 0.11 插件契约统一 | manifest `tools` → `CapabilitySchema` 实例 |
