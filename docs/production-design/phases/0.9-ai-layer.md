# Blink 0.9 — Agent 地基(统一 Tool 架构 + Provider + 主窗口文本闭环)

> **范围**:能力描述统一 schema + `Action` trait 进化为 tool-call 兼容 + Provider 多档抽象 + 主窗口「打字 → 路由 → 执行」纯文本闭环
>
> **主题**:把 builtin / 插件 /(未来)MCP / skill 归一为 **tool 模型**;让 AI 成为路由的回退决策者,在主窗口跑通一个完整的文本闭环。**本版本零语音**——语音入口留 0.10。
>
> **前置**:0.8 全部完成(四域架构 + 0.8.6 三个统一入口:`Action` trait / `SuggestionProducer` / `ConfigStore`)。
>
> **原则**:本体只提供最小抽象,**Provider 全 buildin(rig-core 直编)**;**确定性与 AI 路径分离**;**AI 调用期间必有感知反馈**;**主窗口模式下** AI 只产 Suggestion / tool-call 候选,`AgentBuilder` 不用于主窗口;**Agent 窗口模式**(0.10 展开)允许 rig 更多能力,详见 §五。

---

## 一、为什么重新定义 0.9

原 0.9 规划是「自建 AI 全家桶」——Provider Trait + 云端插件 + Chat View + VectorRouter,一条「blink 自己长出 AI 能力」的路线。

产品复盘后,这条路线有两个问题:

1. **定位稀释风险**:自己做 Chat View,容易变成「又一个对话壳子」,丢掉 Blink 的差异化。
2. **重复造轮子**:MCP / Agent skill 生态已成熟,自建 VectorRouter + Chat 是在重新发明行业已经解决得更好的东西。

**新方向**:Blink 不是「内置 AI 的启动器」,而是**「本地 AI 的感知与执行层」**——推理大脑可插拔(任意 Provider / Agent),但**感知**(划词 / 剪贴板 / 前台 / 语音)和**执行**(本地动作)是 Blink 自己的护城河。

由此 0.9+ 拆成三步:

| 版本 | 主题 | 一句话 |
|---|---|---|
| **0.9** | Agent 地基(本版本) | 统一 tool 架构 + Provider,跑通**纯文本**闭环(零语音) |
| **0.10** | 语音指令闭环 | 换「嘴」替键盘,架构不变只加感知层 |
| **0.11** | 本地化与生态 | 本地模型 / skill 化 / MCP 双向 / A2A |

**关键解耦**:把「AI 能力」和「语音模态」分两个版本。0.9 用最低成本把「路由 → 执行」主链路跑通;如果 0.9 就发现「AI 路由调本地能力」有坑,能在投入语音之前止损。**先验证大脑,再加感官。**

## 二、护城河定位(产品锚点)

Web 端 AI 客户端(ChatGPT / Claude 桌面版)够不着的三样东西,正是 Blink 独有的:

| 护城河 | 说明 | Web AI 能做到吗 |
|---|---|---|
| **全局感知** | 右 Alt 全屏全局唤起 + UIA 划词 + 剪贴板 + 前台应用(系统级) | ❌ |
| **本地执行** | 打开文件 / 运行命令 / 资源管理器定位 / 截图(有系统权限) | ❌ |
| **速度** | 唤起 &lt; 50ms、首个结果 &lt; 20ms | ❌ |

**结论**:AI 是消费者(调 Blink 的 tool)兼生产者(产 Suggestion),Blink 是身体。大脑可换,身体不可换。这个定位钉死后,后续取舍都有锚点——**任何让 Blink 变成「纯对话壳子」的设计都要拒绝**。详见 [product-platform.md §6](./../product-platform.md#6-护城河定位--统一-tool-架构)。

## 三、统一 Tool 架构(纯架构,零 AI,可独立验收)

### 3.1 一切皆 tool

把现在割裂的能力源归一为「tool」心智:

| tool 来源 | 执行方式 | 现状 |
|---|---|---|
| **builtin** | 同进程(Rust) | ✅ 已有,走 `Action` trait |
| **插件** | 子进程 + JSONL IPC | ✅ 已有 |
| **MCP server**(0.11) | 远程,MCP 协议 | 🔜 |
| **skill**(0.11) | 声明式能力(CLI 包装等) | 🔜 |

### 3.2 统一能力描述 schema

向 **MCP tool schema / OpenAI function calling** 靠拢,定义一份能力描述:

```jsonc
{
  "name": "translate",
  "description": "翻译文本到目标语言",
  "parameters": {                    // JSON Schema,tool-call 参数契约
    "type": "object",
    "properties": {
      "text":        { "type": "string" },
      "target_lang": { "type": "string" }
    },
    "required": ["text"]
  },
  "surface": "priority",            // 呈现权(沿用现有 inline/priority/takeover)
  "exec":    "plugin"               // 执行分派:builtin | plugin | (0.11) mcp
}
```

**统一描述层,保留执行分层**——builtin 同进程的性能优势不为了「统一」牺牲成 IPC。schema 统一的是「能力声明」,执行路由按 `exec` 字段分流。

这一步顺带解决了现在 builtin(Rust 枚举)与插件(JSON manifest)**描述风格不一致 + 调用方式不一致**两个老问题——「主窗口命令式参数如何转换为 CLI/IPC 参数」的统一中间表示,就是这个 schema 的 `parameters`。

### 3.3 Action trait 进化为 tool-call 兼容

0.8.6 的 `Action` trait 已经是「统一执行入口」的雏形。0.9 把它往 tool-call 形态靠一步:

- 参数从 `ExecArg::UserExplicit(String)` 进化为**结构化 tool-call arguments**(对齐 §3.2 的 JSON Schema)
- builtin / 插件 / (0.11)MCP 三种执行体各自解析 arguments → `ActionOutcome`
- 前端契约 `Action { kind, payload }` 不变(只是投影)

**关键**:这是 0.8.6 的收口,不是推翻。四域信任边界(`ExecArg::UserExplicit` 类型墙)继续守死——AI 能产 tool-call 候选,但**不能构造用户未确认的执行参数**。

### 3.4 不做的事(0.9 边界)

- ❌ 不统一执行层(builtin 同进程 vs 插件 IPC,分层保留)
- ❌ 不做运行期 skill 探索(留 0.11,且做成配置期而非运行期)
- ❌ 不做 MCP(留 0.11,但 schema 已预留 `exec: mcp` 位置,零成本对接)
- ❌ 不引入向量数据库

## 四、Provider 多档抽象

### 4.1 能力供应商(不只是聊天)

原 0.9 的 `AIProvider` 只有 `chat / embed`,太窄。0.9 重定义为**能力供应商**,按需实现:

| 能力 | 方法 | 0.9 | 0.10 |
|---|---|---|---|
| LLM 对话(流式) | `chat` / `chat_stream` | ✅ | — |
| 语音转文字 | `transcribe` | 接口预留 | ✅ |
| Embedding | `embed` | 接口预留 | —(留 RAG) |

一个 Provider 可只供一两项(本地 whisper 只供 STT),也可全供(OpenAI)。

### 4.2 三档配置(参考 Obsidian YOLO 式配置交互)

设置页 → AI Tab,配置:

1. **供应商**(OpenAI / DeepSeek / 本地 ollama / ...)→ 每个供应商配多个**模型**
2. **角色指派**:从已配模型里独立指派三档

| 档 | 用途 | 特征 |
|---|---|---|
| **路由模型** | 意图分类 + 参数抽取 | 快、便宜、可本地、高频调 |
| **轻量模型** | 日常单轮任务 | 中等 |
| **主模型** | 多步推理 / Agent loop | 最强、最贵 |

**档位降级**:某档空缺 → 自动降级到下一档并提示用户(本地模型可能只够当路由/轻量,当不了主)。

> **不照搬「YOLO 全自动执行」**:Obsidian YOLO 的卖点是放权给 AI 自动执行。Blink **不全盘照搬**——**危险动作**(删除/发送/移动)哪怕模型高置信也必须用户确认(§5.4)。这是四域信任边界,不可让步。

### 4.3 Provider 落地形态(2026-07 定型)

**结论:Provider 全部 buildin,由 `rig-core` 提供实现。**——原规划的「Provider 走插件 JSONL」方案作废,理由:

- LLM 流式转发过 JSONL IPC → 首 token 延迟增几十毫秒,与 §5.3「AI 调用期间感知反馈」铁则冲突
- rig-core 已内置 20+ Provider(Anthropic / OpenAI / Gemini / Ollama / DeepSeek / Groq / Moonshot / Z.ai / xAI / OpenRouter / Cohere / Mistral / HuggingFace / …),多档配置(路由/轻量/主)天然满足
- 依赖复用度极高:reqwest / tokio / serde / tracing 全部已有;真正新增只有 schemars 1.0
- 插件系统的 provider 声明(`provides: ["ai_provider"]`)推迟到 1.0-preview 与 skill / MCP marketplace 合并做

**rig 用法按交互模式分层**(核心边界,0.9 定型,0.10 Agent 窗口落地):

| 交互模式 | 触发 | 用户授权 | rig 能力开放范围 | 危险动作(删除/发送/移动/执行命令) |
|---|---|---|---|---|
| **主窗口打字模式**(0.9) | 右 Alt tap → 打字 | 未显式授权 tool loop——用户在"搜索" | ✅ `providers::*` + `CompletionModel` + `ToolDefinition`;❌ `AgentBuilder` / `Prompt` 自动 dispatch | 一律 Tab 确认 |
| **Agent 窗口模式**(0.10 §5) | 从主窗口 Alt+1 展开 / Alt+Shift+V 语音进入 | 已显式授权——用户就是要跟 AI 对话让它办事 | ✅ 允许 `AgentBuilder` + `Prompt` + `memory` + tool loop | 依然一律 Tab 确认(独立于模式的白名单) |

**主窗口模式的边界原因**:`AgentBuilder` 会自动调用 `Tool::call` 完成 tool-call loop,而在"搜索"心智下用户没有授权 AI 自主执行——CLAUDE.md §9 铁则要求「AI 只能产 Suggestion / tool-call 候选」。Tool schema 走 `ToolDefinition`(标准 OpenAI function calling JSON Schema),兼容 rmcp(`impl From<rmcp::model::Tool> for ToolDefinition` 已存在)。

**主窗口模式代码范例**:

```rust
// ✅ 主窗口:只用 CompletionModel + ToolDefinition,ToolCall 自己路由
use rig_core::providers::anthropic;
use rig_core::client::CompletionClient;
use rig_core::completion::{CompletionModel, ToolDefinition};

let client = anthropic::Client::from_env()?;
let model  = client.completion_model(anthropic::CLAUDE_3_5_HAIKU);
let resp   = model.completion_request(prompt).tools(tool_defs).send().await?;
// resp.tool_calls: Vec<ToolCall { id, name, arguments }>
//   → 走 SuggestionArbiter → Ghost Text 显示"回车执行"
//   → 用户显式确认才穿透 Execution 域
```

**Agent 窗口模式代码范例**(0.10 落地,0.9 只留位):

```rust
// ✅ Agent 窗口:允许 AgentBuilder + tool loop,危险动作走 pre-exec hook
let agent = AgentBuilder::new(model)
    .preamble("You are Blink's assistant...")
    .tools(safe_tool_defs)              // 只挂安全动作(查询/搜索/翻译)
    .build();
// 危险动作(删除/发送/命令)不进 tools,若 AI 想调,产 Suggestion 走人机确认
```

**危险动作白名单是独立铁则**——两种模式下,`ActionKind::Dangerous` 一律走 Tab 确认,即使在 Agent 窗口的 tool loop 里 AI 自主决定要调,也必须弹出确认。这不是模式的属性,是 Action trait 本身的属性(0.9.0 落地时打到 `Action::danger_class()` 元数据里)。

### 4.4 Provider 注册

- **buildin 注册**:启动时按配置构造 `Vec<Arc<dyn AIProvider>>`,由 `AppContext` 持有
- **多档指派**:`AIConfig`(六分片新增一片)记录三档模型 id,运行时按档选 Provider
- **动态切档**:配置变化触发 Provider 重建(reqwest Client 懒构造,冷成本 ~1-5ms,不上热键路径)

### 4.5 密钥安全

- **不进 SQLite**(避免误提交/误备份泄漏)
- Windows Credential Manager / DPAPI 存储
- 内存 zeroize on drop;设置页 `••••••` mask,编辑时清空重填

### 4.6 AIProvider trait 类型收窄(0.9.0 定型,编译期强制)

§4.3「rig 用法按交互模式分层」不能靠代码 review 自觉——**主窗口拿到的类型必须在编译期就没有 `AgentBuilder` 能力**,否则任何开发者一个 `.into_agent()` 就穿透边界。

**落地手法**(0.9.1 引入 `AIProvider` trait 时锁死):

```rust
// src/domain/ai/provider.rs(0.9.1 落地)
/// 主窗口能拿到的 Provider 能力面——**只有 completion + tool-call**
///
/// **绝对不导出**:AgentBuilder / Prompt / TypedPrompt / memory / structured output
pub trait AIProvider: Send + Sync {
    /// 单次 LLM 调用(包 rig 的 CompletionModel)
    async fn complete(&self, req: CompletionRequest) -> Result<CompletionResponse, AIError>;

    /// tool-call 定义投影(不接触 AgentBuilder tool loop)
    fn tool_definitions(&self, tools: &[ActionSchema]) -> Vec<ToolDefinition>;
}

// src/domain/ai/agent.rs(0.10 落地,主窗口路径不 import)
pub struct AgentSession { /* 内部持有 rig::agent::Agent */ }
// AgentSession 只在 domain/agent_window/ 下被引用,主窗口模块无 use path
```

**模块可见性钉死**:

- `AIProvider` trait / `CompletionRequest` / `ToolDefinition` 类型 → `pub`
- `AgentSession` / `rig::agent::Agent` 相关 → `pub(in crate::domain::agent_window)`
- 主窗口路径(`domain/intent/suggestion/ai_producer.rs` 等)**只 use `AIProvider`,拿不到 `AgentSession`**

**为什么 0.9.0 就要决定这个边界**:0.9.1 引入 `AIProvider` trait 时的 method 面是最贵的一次设计——如果 0.9.1 把 `agent_session()` 方法开在 trait 上,后面回改要 breaking 所有主窗口消费点。0.9.0 阶段只需**在 `phases/0.9-ai-layer.md` 里锁定这个边界**,不需要写代码。

## 五、主窗口文本闭环(0.9 验收核心)

### 5.1 闭环流程

```
用户打字
  ├─ 命中 builtin/插件/keyword/regex? ──→ 确定性快速通道,直接执行(不过 AI)
  └─ 未命中
       ├─ 前置过滤未通过(query 太短/纯数字/拼写错)──→ 常规 fuzzy 搜索结果
       └─ 通过 → 调【路由模型】判断
            ├─ 高置信 + 安全动作 ──→ 直接执行(Suggestion + Tab,或可直接执行)
            ├─ 需多轮 ──→ 产 Suggestion「回车展开对话」(0.10 才真展开 Agent 窗口)
            └─ 不确定 ──→ 回退常规搜索结果
```

**这是一个可验证的应用闭环**,也是 0.9 的验收核心。

### 5.2 两条路径铁则(产品)

- **确定性路径**(&lt; 1s):命中规则 → 直接执行,**不过 AI**,保护 P0
- **模糊意图路径**:未命中才走 AI 路由

AI 永远是**回退决策者**,不是默认路径。否则「唤起 → 输入 → 执行 &lt; 1 秒」的铁则被破坏。

### 5.3 AI 反馈铁则(产品)

> **AI 调用期间必须有感知反馈**——路由模型思考时,主窗口要有明确 loading 态(不能空白死等);结果回流要有过渡动画。

这是 P0「按快捷键就能立即输入」的延伸:**不能输入完了又卡住等 AI**,那等于把延迟从「唤起」挪到「路由」,体验一样烂。详见 [product-principles.md §13](./../product-principles.md#13-最小操作路径横切设计准则) 新增铁则。

**AI 路径 SLO(0.9.0 定型,0.9.2 埋点上数据)**——CLAUDE.md §2「首个结果 < 20ms」是**确定性路径**的铁则,AI 路径必须显式分档,避免糊弄成同一 SLO:

| 指标 | 目标 | 触发降级 |
|---|---|---|
| **首个视觉反馈**(loading 态开始渲染) | < 100ms | — |
| **意图返回 P50** | < 800ms | — |
| **意图返回 P95** | < 2000ms | — |
| **硬超时(单次路由调用)** | 2500ms | 静默回退常规 fuzzy 搜索,不弹错 |
| **loading 显示延迟**(避免闪烁) | 150ms 之内不显 | 150ms 后仍未回,才显 loading |

**埋点约定**(0.9.0 只定 target 名,0.9.2 真发数据):

- tracing target: `blink::ai::slo`
- 字段: `first_token_ms` / `intent_total_ms` / `fallback_to_search`(bool) / `timeout`(bool)
- 存 SQLite `perf` 表(§8),设置页调试 tab 展示 P50/P95

### 5.4 信任边界(可直接执行的白名单——独立于交互模式)

轻量路由「能直接执行」的动作必须白名单化,**这条铁则独立于主窗口 / Agent 窗口两种模式**——即使在 Agent 窗口的 tool loop 里 AI 自主决定调用,危险动作依然必须 Tab 确认:

| 类别 | 例子 | 主窗口模式 | Agent 窗口模式(0.10) |
|---|---|---|---|
| **可逆 / 安全** | 打开文件、搜索、翻译、查天气、读文件 | 高置信可直接执行(Suggestion + Tab,或直接) | 允许 AgentBuilder 自主循环调用 |
| **危险 / 不可逆** | 删除、发送、移动、执行命令、写文件 | **必须 Tab / 确认** | **必须 Tab / 确认**——AI 自主决定要调,pre-exec hook 弹确认 |

**落地实现**:`Action` trait 新增 `danger_class()` 元数据方法(`Safe` / `Dangerous`),Agent 窗口的 tool 注册按 danger_class 分流:

- `Safe` → 直接进 AgentBuilder tools 池,自主循环
- `Dangerous` → 不进 tools 池,或走带 pre-exec hook 的封装 tool,hook 里产 Suggestion 走人机确认再决定是否穿透

### 5.5 主窗口模式与 Agent 窗口模式的过渡(0.9 只留位,0.10 完整实现)

- 主窗口打字 → 未命中 Suggestion + 路由判为"需多轮" → Ghost 提示"Alt+1 展开对话"
- Alt+1 展开 → 复用 WebviewWindow 切换到 `view: chat` 模板(0.8.4 view 字段已预留)
- Agent 窗口内可自主循环调 tool / MCP / skill,消息历史交给 rig `Prompt` / memory 管
- ESC 返回主窗口搜索模式,会话可选保留(0.10 §5.4 Context 注入)

**为什么 0.9 现在就写这个衔接**:是为了让 §4.3 rig 用法边界在 0.9 就定型——`Action::danger_class()` 元数据必须在 0.9.0 的"Action trait tool-call 进化"这一步一起加,否则 0.10 展开 Agent 窗口时缺元数据、要回改 Action trait 的所有实现。

### 5.6 待定决策点(开发时敲定,先记)

- **未命中过滤规则**:见 §5.7(0.9.0 已锁定原则,阈值 0.9.2 前 spike)
- **「直接执行」是否需 Tab**:安全动作是直接执行还是 Tab 采纳(应可配置,默认 Tab)
- **多轮在 0.9 的处理**:0.9 仅识别 + 提示「需展开对话」,不真展开(留 0.10)
- **路由模型超时 / 失败**:降级到常规搜索,绝不阻塞主链路(见 §5.3 SLO)

### 5.7 未命中过滤规则(什么样的 query 才走 AI)

**为什么 0.9.0 就要锁原则**:0.9.2 落地 AI 路由时,「进 AI」的判定是**产品体验分水岭**——过严 → AI 白装了,过松 → 每次拼错就打云端(成本 + 隐私 + 延迟三重坑)。这条不能留到「开发时敲定」,晚了前后端契约都要回改。

**四条铁则(0.9.0 定型,不动)**:

1. **默认关**——用户没在设置页显式打开 AI Tab、没配 Provider,一律不走 AI。空 Provider 状态下 `SearchService` 对未命中直接回退 fuzzy。
2. **命中规则不走 AI**——`RuleRouter` / builtin / 插件 keyword / 计算器命中任一 → 确定性路径,零 AI 调用。
3. **用户可全局关**——设置页 AI Tab 一个开关:「让 AI 处理未命中的模糊意图」(默认 off,即使配了 Provider 也要用户明确 opt-in)。
4. **必埋遥测**——任何一次「进 AI」都要在本地 SQLite `perf` 表记录:query 长度、语言、是否有空格、是否命中规则、路由耗时、是否 fallback。设置页调试 tab 可见,不上报。

**四条候选筛子(0.9.2 spike 定阈值,不写死在文档里)**:

| 筛子 | 默认建议 | 备注 |
|---|---|---|
| **最短长度** | ≥ 4 字符 | 单字/双字太短,大概率是拼错前几个字符;命中率低、噪音大 |
| **含空格** | 必含至少 1 个空格 | 「打开 记事本」「翻译 hello」——空格是「短语」信号,单词大概率是拼错 |
| **非纯数字/纯符号** | 排除 `\d+` / `[!-/:-@\[-`\{-~]+` 类 | 数字走计算器,符号大概率是误输入 |
| **非 URL / 文件路径** | Awareness 已判定为 URL/Path 时不走 AI | 走内置动作(打开链接 / 打开路径)——护栏,别让 AI 「解读 URL」 |

**决策树伪代码**(0.9.2 落地时按这个骨架实现,阈值可调):

```
if !ai_enabled_in_config() { return fallback_search }
if rule_router.hit() || builtin.hit() || plugin_keyword.hit() { return }  // 铁则 2
if awareness.is_url() || awareness.is_file_path() { return fallback_search }  // 筛子 4
if query.len() < min_len_config { return fallback_search }
if !query.contains(' ') && !looks_like_phrase(query) { return fallback_search }
if query.chars().all(char::is_numeric) { return fallback_search }
// 通过 → 调 AI 路由
emit_slo_metric("ai_routing_started");
```

**用户开关落地位置(0.9.1 配置页)**:

- `AIConfig.enabled: bool`(总开关,默认 false)
- `AIConfig.min_query_len: u8`(默认 4)
- `AIConfig.require_whitespace: bool`(默认 true)

## 六、VectorRouter 降级(移出 0.9 主线)

原 0.9.3 的 VectorRouter 语义匹配**移出 0.9**。理由:

- AI 路由(§5)直接用 LLM 做意图判断,比向量预匹配更强、更灵活
- 向量匹配的真正归宿是后期 **RAG / 记忆功能**(留 0.11+,需要持久化向量库)

`RuleRouter` 优先、未命中回退的链路不变,只是回退目标从「VectorRouter」换成「AI 路由」。

## 八、决策备忘

- **重新定义 0.9**:从「自建 AI 全家桶」转向「统一 tool 架构 + Provider 接入」,让 AI 成为顺理成章的参与者而非独立子系统
- **解耦 AI 与语音**:0.9 文本闭环先验证「路由→执行」主链路,0.10 才上语音,止损成本低
- **统一描述,保留执行分层**:不为「统一」牺牲 builtin 同进程性能
- **Provider 全 buildin(rig-core)**:2026-07 定,原「Provider 走插件」推翻——LLM 流式转发过 IPC 与「AI 反馈铁则」冲突,rig 生态成熟度和 STT/MCP 免费红利决定性抵消 2-3 MB / 90s 编译成本
- **只用 rig 的 Provider 层(主窗口模式)** / **允许更多能力(Agent 窗口模式)**:rig 用法按交互模式分层——主窗口下用户未授权 tool loop,只用 `CompletionModel` + 自路由;Agent 窗口下用户显式授权,允许 `AgentBuilder` + memory + tool loop。危险动作白名单独立于模式,一律 Tab 确认
- **VectorRouter 让位**:LLM 路由更强,向量留 RAG / 记忆
- **信任边界不拆**:AI 产 Suggestion / tool-call 候选,危险动作必确认
- **(0.9.0 补丁)AIProvider 类型层收窄(§4.6)**:主窗口拿到的类型编译期就没有 AgentBuilder 能力——模块可见性 `pub(in ...::agent_window)` 钉死,不靠 code review
- **(0.9.0 补丁)AI 路径 SLO 分档(§5.3)**:AI 路径的延迟目标与确定性路径分离——首视觉反馈 <100ms,意图 P50 <800ms / P95 <2s,硬超时 2500ms 静默回退。SLO tracing target `blink::ai::slo` 0.9.0 就位
- **(0.9.0 补丁)未命中过滤四铁则(§5.7)**:默认关 / 命中规则不过 AI / 用户可全局关 / 必埋遥测;具体阈值(min_len / require_whitespace)0.9.2 spike 调,不写死在文档
- **(0.9.0 补丁)danger_class 全部显式标注**:12 个 builtin 逐个显式覆盖 `danger_class()`,虽然多数是 `Safe`,但强制开发者思考——防漏于千里之堤
