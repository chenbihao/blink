## 二、0.12.0 基础设施

### 2.1 DB 四层拆分

`DbPools { config, history, ai, cache }`，四库独立连接池和写锁，互不阻塞。

| 数据库 | 表 | 语义 |
|---|---|---|
| `blink_config.db` | `config` | 用户配置 KV |
| `blink_history.db` | `history` / `clipboard_history` | 用户行为历史 |
| `blink_ai.db` | `ai_tool_audit` / `conversations` / `messages` / `conversation_groups` | AI 对话、审计与分组 |
| `blink_cache.db` | `performance_metrics` / `icon_cache` | 可删除缓存 |

旧 `blink.db` → 四库迁移（SQL `ATTACH` + `INSERT INTO ... SELECT`），完成后删除旧库，标记写入配置库。

### 2.2 Tool 适配层

`CapabilityTool` / `ActionTool` 实现 `rig::tool::ToolDyn`，把现有 Capability/Action 接入 rig Agent tool loop。

- `ai_eligible() == false` 的 Action 不进 Agent tool 池（如 `exit_blink`）。
- Dangerous tool 在 `ToolDyn::call` 内 emit 确认事件后**挂起 await 用户确认**（`PendingConfirms` + oneshot + 60s 超时）。
- 错误经 `capability_error_to_string` / `exec_error_to_string` 中文化后返回 `ToolError::ToolCallError`。

### 2.3 Provider 模型统一

`ModelEntry.capabilities` 支持 Chat / Embedding / STT。`AIProviderRegistry` 热更新（`reload` 增量重建 provider 池，密钥版本号 `secret_epoch` 强制重建）。

## 三、对话窗口与机制（0.12.1-0.12.3）

### 3.1 AgentProvider

`ChatAgent` 枚举承载 4 种 `ProviderKind` 的具体 `Agent<M>`（rig `CompletionModel` 非 object-safe，用枚举替代 `dyn`）。

`stream_prompt` → 泛型 `run_stream<M>` 消费 `MultiTurnStreamItem` 转为 `ChatStreamChunk` emit 前端：

```
Text / Thinking / ToolCall / ToolResult / Done / MaxTurnsReached / Error
```

**空响应检测**（0.12.6 修复）：rig 在 SSE 解析失败时 yield 空 `FinalResponse`（0 token + 无内容），转为 `Error` chunk 而非 `Done`，避免前端卡死。

### 3.2 ChatService

- 单 active request（`RequestTracker`：`install` / `abort` / `clear_if` compare-and-clear）。
- `start_gate` 串行化启动，防止并发 IPC 绕过 active 检查。
- `ensure_provider(preamble)` 懒构造 AgentProvider，cache key = `(provider_id, model_id, fingerprint, preamble_hash)`。
- `select_model` / `notify_config_changed` 清缓存，memory 不动。

### 3.3 SQLite ConversationMemory

`SqliteConversationMemory` impl rig `ConversationMemory` trait。

- `messages.content` 存序列化 rig `Message` JSON（完整保留 text / tool_call / tool_result）。
- 滑动窗口策略：`load` 取最近 20 条，持久化层保留完整历史。
- 重启恢复：窗口打开时从 AI 库恢复对话列表和消息历史。

### 3.4 数据表

```sql
CREATE TABLE conversations (
  id TEXT PRIMARY KEY, title TEXT,
  created_at INTEGER NOT NULL, last_active_at INTEGER NOT NULL,
  group_id TEXT  -- 0.12.6 新增
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL, role TEXT NOT NULL,
  content TEXT NOT NULL,  -- 序列化的 rig Message
  created_at INTEGER NOT NULL
);

CREATE TABLE conversation_groups (  -- 0.12.6
  id TEXT PRIMARY KEY, name TEXT NOT NULL,
  system_prompt TEXT, parent_id TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  expanded INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL
);
```

## 五、对话分组（0.12.6）

### 5.1 功能设计

参考元宝网页端——侧边栏分组层级，每分组可配独立系统提示词。

- **多层嵌套**：`parent_id` 支持任意深度，递归渲染 + 缩进。
- **分组操作**：新建 / 重命名 / 删除（组内对话移至默认，子分组 re-parent）/ 系统提示词编辑。
- **折叠状态**：DB 持久化（`expanded` 列），默认组用本地状态。
- **拖拽排序**：HTML5 Drag & Drop（对话跨分组移动 + 分组 sort_order 交换）。
- **分组系统提示词**：`chat_prompt` 时查询分组 `system_prompt`，追加到基础 `chat_system_prompt()` 之后。preamble hash 变化触发 Agent 重建。

### 5.2 实现

### 6.1 设计理念

当前对话窗口的视觉元素是逐版本叠加的——气泡、工具卡、思考块、确认卡、错误消息各自独立设计，缺乏统一的视觉语言。0.12.7 的核心是**建立消息类型体系**，让每种信息形态有明确的视觉归属。

**布局总览**：

### 6.3 Signal 信号消息

**设计参考**：IM 应用中常见的系统通知——Telegram 的「XX 加入群组」、微信的「XX 撤回了一条消息」、Discord 的「频道已创建」。这类消息居中、轻量、无气泡，不干扰对话流但传递重要状态信息。

**视觉规范**：

```
         ⚠ 已达工具调用上限（50轮）
```

- 居中对齐，`align-self: center`
- 小号文字（12px），弱色背景药丸（`var(--surface)`）
- 圆角 `border-radius: 12px`，内边距 `4px 12px`
- 不占据消息流的主视觉空间

**信号类型**：

| 类型 | 颜色 | 场景 |
|---|---|---|
| `info` | `--text-faint` | 「已停止生成」「消息已编辑」 |
| `warning` | `--amber` | 「已达工具调用上限」「模型上下文窗口接近上限」 |
| `error` | `--red` + `--red-bg` | LLM 报错、网络超时（替代当前 `.chat-msg-error`） |
| `success` | `--green` | 「危险操作已执行」「文件已保存」 |

**实现要点**：

- `components.js` 新增 `renderSignal(text, type)` 函数
- 将 `renderErrorMessage` 重构为 `renderSignal(message, 'error')` 的封装
- `max_turns_reached` chunk → `renderSignal(text, 'warning')`
- `handleStop` 后 → `renderSignal('已停止生成', 'info')`
- 消息编辑重发后 → `renderSignal('消息已编辑', 'info')`

### 6.4 时间分隔符

**规则**：相邻两条消息的 `created_at` 间隔超过 **5 分钟**时，自动插入时间分隔符。

**视觉规范**：

```
─────────────── 今天 14:30 ───────────────
```

- 居中，左右各一条细线（`1px solid var(--surface-2)`）
- 中间时间文字（11px，`--text-faint`）
- 最大宽度 400px，两侧线 `flex: 1` 自适应

**时间格式**：

| 间隔 | 格式 | 示例 |
|---|---|---|
| 今天 | `HH:MM` | `14:30` |
| 昨天 | `昨天 HH:MM` | `昨天 14:30` |
| 本周内 | `周X HH:MM` | `周二 14:30` |
| 更早 | `M/D HH:MM` | `7/20 14:30` |
| 跨年 | `YYYY/M/D` | `2025/12/31` |

**后端依赖**：

- `get_chat_messages` IPC 返回值需增加 `created_at` 字段（DB `messages` 表已有此列）
- `ChatMessageSnapshot` struct 增加 `created_at: i64`
- 前端 `state.messages` 增加 `created_at` 字段

**渲染逻辑**：

- 历史加载：遍历消息时，比较前一条 `created_at` 与当前条，超阈值则先插入分隔符
- 实时流式：用户发送消息时记录 `Date.now()`，AI 回复 done 时记录时间，比较插入

### 6.5 系统提示词横幅

**触发条件**：当前对话的直属分组（`group_id`）有非空 `system_prompt`。

**位置**：消息区顶部，header 下方，消息列表上方。不随消息滚动（sticky 或固定在 messages 容器顶部）。

**视觉规范**：

```
┌─ 💬 系统提示词 ─────────────────────┐ ┄ ✕ ┐
│ 你是翻译助手，请将用户输入翻译为...  ▾     │
└────────────────────────────────────────┘
```

- 灰底（`var(--surface)`），圆角 `8px`，边框 `1px solid var(--surface-2)`
- 左侧 prompt 图标（accent 色）
- **折叠态**：单行 + 省略号 + 展开箭头 `▾`
- **展开态**：完整文本，`max-height: 120px` 可滚动
- 右侧 `✕` 关闭按钮（session 级隐藏，不持久化，切换对话后恢复）

**实现要点**：

- `chat.html` 在 `.chat-messages` 上方增加 `#chat-prompt-banner` 容器
- `main.js` 切换对话时查询 `get_effective_system_prompt`，有值则显示横幅
- 折叠/展开状态用 `data-collapsed` 属性切换
- 关闭状态存 `state.dismissedPromptConvs`（`Set<conversationId>`）

### 6.7 消息间距优化

**当前**：所有消息统一 `gap: var(--space-lg)`，缺乏节奏感。

**优化**：

| 场景 | 间距 | 实现 |
|---|---|---|
| 同一轮（user → thinking → tool → AI） | `var(--space-sm)` | 紧凑 |
| 不同轮次（上一轮 AI → 下一轮 user） | `var(--space-lg)` | 宽松 |
| 时间分隔符两侧 | `var(--space-sm)` | 适中 |
| Signal 信号两侧 | `var(--space-sm)` | 适中 |

**实现思路**：

- 给每条消息加 `data-turn` 属性标记所属轮次
- 同 `data-turn` 的消息用小间距，不同 `data-turn` 用大间距
- CSS 用 `has()` 或 JS 动态设置 class
