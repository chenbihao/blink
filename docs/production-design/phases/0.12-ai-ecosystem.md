# Blink 0.12 — AI 能力架构搭建(对话窗口 / 对话机制 / 基础设施清账)

> **范围**:① 基础设施抽取与清账(投影统一 / **DB 四层拆分** / Provider 模型统一管理 / 本地 Provider 接入)+ ② 对话窗口(独立 Agent 窗口 + Alt+Q chord)★ + ③ 对话机制(conversation 隔离 / 持久化 memory / 窗口策略 / tool loop 无限轮)。
>
> **主题**:0.11 把插件 AI toolchain 的内部一致性做扎实;0.12 在此基础上**搭 AI 能力的架构骨架**——从「主窗口单轮 complete」进化到「独立对话窗口多轮 agent loop」,把对话隔离、上下文管理、工具调用、记忆这些 AI 能力的核心机制建立起来。
>
> **产品边界决策**:**Blink 不做 AI 运行时**。本地推理完全靠外部(ollama / lmstudio),Blink 只作 Provider 对接。不引内嵌推理引擎(mistral.rs 等),不重复造轮子,不跟踪推理框架更新,不维护模型下载——产品边界清晰。
>
> **rig 基础**:rig 0.39 的 `AgentBuilder` + `ConversationMemory` trait + `rig-memory` 策略层(SlidingWindow / TokenWindow / Compacting)已覆盖对话窗口绝大部分需求,**核心工作量在前端 chat UI + 持久化 memory 后端 + Provider 模型统一管理**,而非重造 agent loop。
>
> **前置**:0.11 完成(统一结果模型 + 工具元信息 + 提示词管理 + 结果回流 + sensitive 字段铺路)。
>
> **原则**:安装包保持 < 100MB;暴露本地能力(MCP server)推 0.13;Agent 窗口不破主窗口类型收窄铁则;**先抽取再扩展,先架构再功能**。
>
> **范围调整**(相对初版规划):MCP client / RAG / MCP server / Skill / 记忆向量召回 全部推 0.13。0.12 收束到**对话机制打通**——先把「独立对话窗口 + 多轮 agent loop + 持久化记忆」这条核心链路跑通,调用能力扩展(MCP/RAG)在架构骨架稳固后再加。

### 1.2 产品边界:Blink 不做 AI 运行时

**决策**:本地推理完全靠外部进程, Blink 只作 Provider 对接。

| 外部运行时 | 接入方式 | Blink 侧成本 |
|---|---|---|
| **ollama** | rig `providers::ollama` Provider(0.9 已引入 crate) | 加一个 `ProviderKind::OllamaHttp` arm + 设置页 tab |
| **lmstudio** | 走现有 `ProviderKind::OpenAICompatible`(lmstudio 默认起 OpenAI 兼容 API `localhost:1234/v1`) | **零适配**,用户在供应商配置里填 endpoint 即可 |
| 其他 OpenAI 兼容本地服务 | 同上 | 零适配 |

**为什么不做内嵌运行时**:
1. 不重复造轮子——ollama/lmstudio 已是事实标准,用户已经在用
2. 不跟踪推理框架更新——mistral.rs/llama.cpp 迭代频繁,Blink 跟不起
3. 不维护模型下载——GGUF/UQFF 格式、HuggingFace 镜像、断点续传都是负担
4. 安装包不膨胀——本地运行时依赖动辄几十 MB
5. 产品边界清晰——Blink 是 AI 消费者,不是 AI 运行时

**唯一例外**:`all-MiniLM-L6-v2` 这类小 embedding 模型若用户不想装 ollama,可手动指定模型文件路径,Blink 用 `ort`/`candle` 跑——但这不是 0.12 必须,默认走 ollama embedding(`nomic-embed-text`)。

### 1.3 rig 0.39 能力盘点(哪些现成,哪些自己写)

review rig v0.39.0 源码确认,对话窗口功能**绝大部分现成**:

| 能力 | 状态 | 备注 |
|---|---|---|
| `AgentBuilder`(preamble + tools + context + structured output) | ⚠️ 现成但**形态不兼容**(tool 必须是 `impl Tool` 代码,现有 Capability/Action 是数据) | `agent/builder.rs`,**需 0.12.0 抽 Tool 适配层(§2.4)接通** |
| 自动多轮 tool loop | ✅ 现成(tool 适配层接通后) | `max_turns(N)`/`default_max_turns(N)`,**默认 0(=1 轮),需显式设大数** |
| Streaming(含 multi-turn + tool_call delta) | ✅ 现成 | `StreamingPrompt`/`StreamingChat`,产出 `MultiTurnStreamItem` |
| `ConversationMemory` trait(按 conversation_id 自动 load/append) | ✅ 现成 | `memory.rs`,3 个 async 方法 |
| 进程内 memory 后端 | ✅ 现成 | `InMemoryConversationMemory`(重启丢) |
| 窗口策略(滑动窗口 / token 预算 / 摘要压缩) | ✅ 现成 | `rig-memory` crate:`SlidingWindowMemory` / `TokenWindowMemory` / `CompactingMemory` |
| Ollama chat + tools + streaming | ✅ 现成 | `providers/ollama.rs`,`tool_choice` 不支持(Ollama API 限制) |
| Ollama embedding | ✅ 现成 | `client.embedding_model("nomic-embed-text")`,内置维度表 |
| conversation 概念(跨多次 prompt 共享上下文) | ✅ 现成 | `agent.prompt("...").conversation("id").await` |
| **持久化 memory 后端(存 SQLite)** | ⚠️ **自己写** | impl `ConversationMemory` trait(3 个 async 方法),存 `messages` 表 |
| **按语义相关性召回历史** | ⚠️ 推 0.13 | 用 `DemotingPolicyMemory` 钩子接向量库;0.12 只做窗口截断 |
| 同步 tool 调用 | ❌ 不支持 | rig 全 async |

**关键结论**:0.12 对话窗口**不需要自己实现 agent loop**——直接用 rig `Agent` + `AgentBuilder`。核心自己写的工作量:
1. **Tool 适配层**(§2.4)——中,把现有 Capability/Action 包装成 `impl rig::Tool`,**这是形态不兼容的硬要求,不做对话窗口整个走不通**
2. **持久化 memory 后端**(impl trait 存 SQLite)——小,3 个方法
3. **前端 chat UI**(对话历史渲染 + 流式输出 + tool_call 可视化)——中,纯前端
4. **Provider 模型统一管理**(§2.7)——中,embedding + STT 模型统一进 AIConfig

## 二、0.12.0 基础设施抽取与清账

### 2.1 投影函数统一

**目标**:消除"两套回流投影并存"的歧义,确定一条权威路径。

**决策**:**保留 `to_rig_tool_result()`(`result.rs:29`)作为唯一投影入口,删除 service.rs 那两个 project_* 私有函数**。

理由:
- `to_rig_tool_result()` 返回 rig 原生 `ToolResultContent`(可直接喂 LLM),`project_*_to_tool_message` 返回 `String`(还要包一层 text content)——前者是规范路径
- 0.12.2 对话窗口的 tool loop 也要用这份投影,统一在 capability 层而非散在 service.rs
- Blob 摘要策略(不喂原始字节省 token)从 `project_capability_result_to_tool_message` 迁入 `to_rig_tool_result()` 的 Blob 分支

**`ActionOutcome → ToolResultContent` 投影**:新增对称的 `ActionOutcome::to_rig_tool_result()`,与 `CapabilityResult::to_rig_tool_result()` 同一份契约。

### 2.2 DB 拆分与分层修复★

review 发现 DB 现状有几个硬问题,必须在 0.12.0 清账(否则对话窗口的 memory 持久化加进来后会更乱):

#### 2.2.1 现状问题

| 问题 | 证据 | 影响 |
|---|---|---|
| **6 张表挤一个 `blink.db`** | `history.rs:16-21` 唯一 `connect`,`max_connections(1)` | 单写锁,高频写阻塞低频读 |
| **`performance_metrics` 高频写入** | `service.rs:700-706` 每次搜索写一行(用户每按键 1 行);`capability/registry.rs:107/130/146` 每次 capability invoke 写 | DB 膨胀主因,30 天窗口内可累积数十万行;与 config 读互相阻塞 |
| **`icon_cache` 含 BLOB** | `icon.rs:155-178` 每个未命中图标写 PNG BLOB,上限 2000 条 × ~5KB ≈ **10MB** | 占据 DB 大头,与小配置表混在一起 |
| **`ai_tool_audit` 无清理** | `ai_audit.rs` 全表无 `cleanup_old` / 行数上限 | 单调增长,长期使用线性膨胀 |
| **分层违规 1** | `icon_cache` schema 在 `domain/search/icon.rs:51-58`(领域层直持 DB) | 违反 Clean Architecture |
| **分层违规 2** | `performance_metrics` schema 在 `infra/utils/perf.rs:61-68`(不在 data 层) | 同上 |
| **`config` 访问层混在 history.rs** | `history.rs:242-282` 的 `get_config`/`set_config` | 历史遗留 |
| **AGENTS.md §8 表清单过时** | 表名写错(clipboard/perf vs clipboard_history/performance_metrics),漏 ai_tool_audit + icon_cache | 文档失真 |

#### 2.2.2 拆分方案(四层:配置库 + 历史库 + AI 库 + 缓存库)

**方案:按数据域拆四层**

| 库 | 表 | 性质 | 写入频率 | 丢得起吗 | 同步优先级 |
|---|---|---|---|---|---|
| **`blink_config.db`(配置库)** | `config`(所有设置页持久化的 KV:AppConfig 6 分片 + AIConfig + SttConfig + engine:* + plugin:* + clipboard:config + screenshot:config + context:config) | 用户核心配置 | 极低(仅设置页保存时写) | ❌ 不可丢 | ★ 最高(未来跨机同步只同步此库) |
| **`blink_history.db`(历史库)** | `history`(启动历史) / `clipboard_history`(剪贴板历史) | 用户行为数据 | 低(每次启动/复制) | ⚠️ 可选(用户可清空) | 中(可选同步) |
| **`blink_ai.db`(AI 库)** | `ai_tool_audit` / `conversations` / `messages`(0.12.2 新增) | AI 对话与审计域 | 中(每次 AI 交互) | ⚠️ 用户可选(可单独清空对话历史保留配置) | 低(AI 对话历史一般不同步) |
| **`blink_cache.db`(缓存库)** | `performance_metrics` / `icon_cache` | 纯缓存(可重建) | 高(perf 每按键)+ BLOB(icon) | ✅ 可丢可重建 | 不同步 |

**为什么四层不是三层(配置独立拆出的核心理由)**:

1. **配置同步的前瞻性**:用户后续可能想在多台设备间同步 Blink 配置(主题/快捷键/AI 供应商/STT 设置等)。配置库独立后,同步只需导出/导入单个几十 KB 的 `blink_config.db`,不混入历史记录和缓存数据。同步成本最低、心智最清晰。

2. **配置的写入特征独异**:配置库是**极低频写入**(仅设置页保存时写),与历史库的低频写入、AI 库的中频写入、缓存库的高频写入完全不同量级。独立后配置读写永不被其他库的写锁阻塞——设置页打开/保存始终流畅。

3. **配置的全局性**:配置库包含 AI 供应商密钥引用(`secret_ref`)、STT 供应商配置、搜索引擎配置等**跨子系统共享**的配置,与"启动历史"这种纯搜索域数据关注点完全不同。

4. **备份/迁移/重置粒度对齐用户心智**:
   - 「我只想备份设置」→ 导出 `blink_config.db`
   - 「我想重置 AI 对话但不丢设置」→ 删 `blink_ai.db`
   - 「我想清空所有使用痕迹但不丢设置」→ 删 `blink_history.db` + `blink_ai.db` + `blink_cache.db`
   - 「缓存占太多空间」→ 删 `blink_cache.db`(自动重建)

5. **主库保持极小而稳**:配置库只有 `config` 一张 KV 表,几十 KB 级,备份/迁移/跨机同步成本最低。

**历史库说明**:
- `history`(启动历史) + `clipboard_history`(剪贴板历史)是用户行为数据,生命周期独立于配置
- 未来若加入「感知历史」(Awareness 记录),也归入历史库
- 历史库可独立清空/备份,不影响配置

#### 2.2.4 补清理策略

- `ai_tool_audit`(AI 库):加 `cleanup_old(30 天)` + 行数上限 10000,启动时调用
- `performance_metrics`(缓存库):已有 30 天清理,**补行数上限**(如 50000)防极端膨胀
- `messages`(AI 库,0.12.2 新增):按 conversation 级联删除,不单独 cleanup
- `conversations`(AI 库,0.12.2 新增):可选「自动清理 N 天未活跃对话」配置项(默认关)

#### 2.2.5 连接池管理

- 配置库 `blink_config.db`:`max_connections(1)`(写极少,串行可接受)
- 历史库 `blink_history.db`:`max_connections(1)` 独立 pool
- AI 库 `blink_ai.db`:`max_connections(1)` 独立 pool
- 缓存库 `blink_cache.db`:`max_connections(1)` 独立 pool
- 四库各持 `SqlitePool`,分别进 Tauri State(命名 `ConfigDbPool(pub SqlitePool)` / `HistoryDbPool(pub SqlitePool)` / `AiDbPool(pub SqlitePool)` / `CacheDbPool(pub SqlitePool)`)

**注意现有调用点工作量**:当前全项目用 `app.state::<SqlitePool>()` 单 pool 模式取连接。改四层后**所有现有调用点都要改成对应 wrapper 类型**——grep `state::<SqlitePool>` 全仓,按表归属改:
- 访问 `config` 表(所有 `get_config`/`set_config` 调用) → `ConfigDbPool`
- 访问 `history` / `clipboard_history` → `HistoryDbPool`
- 访问 `ai_tool_audit`(及未来 `messages`/`conversations`)→ `AiDbPool`
- 访问 `performance_metrics` / `icon_cache` → `CacheDbPool`

这是 0.12.0 必须一次到位的改动(否则后续混用更乱),工作量约 20-30 处调用点 + 类型 wrapper 定义。

#### 2.2.6 迁移逻辑

启动时检测旧 `blink.db` 是否含 `performance_metrics` / `icon_cache` / `ai_tool_audit` / `config` / `history` / `clipboard_history` 表:
- `config` → 迁移到 `blink_config.db` 后从旧库删除
- `history` / `clipboard_history` → 迁移到 `blink_history.db` 后从旧库删除
- `ai_tool_audit` → 迁移到 `blink_ai.db` 后从旧库删除
- `performance_metrics` / `icon_cache` → 迁移到 `blink_cache.db` 后从旧库删除

一次性迁移,迁移完成后旧 `blink.db` 可删除。版本号写进配置库 `config` 表(`schema_version` / `db_split_done` 标记),避免重复迁移。

### 2.4 Tool 适配层抽取(★ 关键,解决 rig Agent 与现有架构的形态冲突)

**问题背景**:rig `AgentBuilder` 注册 tool 的方式与现有架构根本不同:

| 维度 | 现有架构(主窗口 0.11) | rig Agent(对话窗口) |
|---|---|---|
| tool 形态 | **数据**:`Vec<ActionSchema>` → 投影成 `Vec<ToolDefinition>` 作为 `CompletionRequest` 参数 | **代码**:`impl rig::tool::Tool` trait(`Tool::call(args) -> Output`) |
| 调度方 | **外面驱动**——service.rs 收到 `tool_calls` 后手工执行,结果拼回 message 再 `complete` | **Agent 内部**——`AgentRun` 状态机自动 CallModel ↔ CallTools 循环 |
| 现有实现 | Capability / PluginActionAdapter 都是「外部调度」形态,**都没 `impl rig::Tool`** | — |

**冲突后果**:对话窗口想用 rig Agent,**现有的 Capability + 插件 tool 全部接不进去**。若不解决,0.12.1 直接卡住。

**解决方案**:**0.12.0 抽出 `ToolAdapter` 层**,把 Capability / Action 包装成 `impl rig::tool::Tool`:

```
src/domain/ai/tool_adapter.rs (新建)
  ├─ CapabilityTool { cap: Arc<dyn Capability>, schema: CapabilitySchema }
  │    impl Tool for CapabilityTool  (definition → schema.to_rig_tool, call → cap.invoke + to_rig_tool_result)
  ├─ ActionTool { action: Arc<dyn Action>, schema: ActionSchema }
  │    impl Tool for ActionTool
  └─ 工厂函数 build_agent_tools(registry, cap_registry) -> Vec<Box<dyn ToolDyn>>
```

**Tool::Args 用 `serde_json::Value`**(走 `ToolDyn` 动态分发路径,避免给每个 Capability 写强类型 Args):
- `definition(prompt)` 返回 `schema.to_rig_tool()`(纯 schema 投影,已有)
- `call(args: Value)` 内部调 `cap.invoke(args, ctx)` → `CapabilityResult` → `to_rig_tool_result()`(0.12.0 已激活)
- 危险操作(`danger_class == Dangerous`)在 `call` 内部 emit 确认卡片 + 返回 "等待用户确认" 消息,不直接执行(保持四域墙)

**MCP tool(0.13)同理**——外部 server 拉到的 tool 包装成 `McpTool { server, tool_def }` 也 `impl Tool`,**统一进同一个适配器层**。

**这个抽取是 0.12.0 的硬要求**,不做的话对话窗口整个走不通。完成后:
- 主窗口 Turn 2 仍走现有「数据 + 外部调度」路径(不变,类型收窄铁则保持)
- 对话窗口走新「Tool 适配器 + Agent 内部调度」路径

### 2.7 Provider 模型统一管理(chat + embedding + STT)★

**问题背景**:当前 AI 供应商配置(`AIConfig`)和 STT 供应商配置(`SttConfig`)是两套独立结构:

| 维度 | AIConfig(`ai_config.rs`) | SttConfig(`stt_config.rs`) |
|---|---|---|
| 供应商结构 | `ProviderEntry { id, kind, base_url, secret_ref, models }` | `SttCloudProvider { kind: String, base_url, model_id }` |
| 模型管理 | `ModelEntry { id, display_name, enabled, ... }` 多模型列表 | 单个 `model_id` 字符串 |
| 密钥管理 | `secret_ref` → Credential Manager(`blink/{id}/key`) | `stt:{kind}` 约定 → 复用 CM |
| ProviderKind | 强类型枚举(OpenAICompatible / AnthropicMessages / GeminiGenerateContent) | 字符串(`"openai"` / `"groq"` / ...) |
| 模型能力区分 | 无(所有模型都视为 chat/completion) | 无(固定为 STT) |

**问题**:
1. **embedding 模型无处可配**:0.13 RAG 需要 embedding 模型,0.12 ollama 接入后也需指定 embedding 模型,但 `ModelEntry` 没有能力标记
2. **STT 供应商配置割裂**:用户在 AI 供应商页配了 OpenAI key,STT 还要重新配一遍 kind/base_url/secret——同一个 OpenAI 账号的 chat 和 whisper 是两套配置
3. **本地 ollama 的 embedding 模型管理**:ollama 同时提供 chat 模型和 embedding 模型(`nomic-embed-text`),当前架构无法统一管理

#### 2.7.1 设计方案:模型能力标记 + 统一供应商

**核心思路**:`ProviderEntry` 保持不变(一个供应商 = 一个 endpoint + 一份密钥),`ModelEntry` 增加 `capabilities` 字段标记模型能力。STT 云端配置改为**引用 AIConfig 中的供应商 + 模型**。

**Step 1: `ModelEntry` 增加 `capabilities` 字段**

```rust
/// 模型能力类型。
#[derive(Debug, Clone, Copy, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "lowercase")]
pub enum ModelCapability {
    /// 对话/补全模型(含 tool use)——主窗口 complete + 对话窗口 agent loop
    Chat,
    /// 嵌入模型——0.13 RAG 向量生产(ollama nomic-embed-text / OpenAI text-embedding-3 等)
    Embedding,
    /// 语音转文字模型——云端 STT(OpenAI whisper / Groq whisper 等)
    Stt,
}

/// ModelEntry 新增字段
pub struct ModelEntry {
    // ... 现有字段不变 ...
    /// 模型能力列表。一个模型可同时具备多种能力(如某些 ollama 模型同时支持 chat + embedding)。
    /// 默认 `[Chat]`——老配置缺字段时 serde 填充,零迁移成本。
    #[serde(default = "default_chat_capability")]
    pub capabilities: Vec<ModelCapability>,
}

fn default_chat_capability() -> Vec<ModelCapability> {
    vec![ModelCapability::Chat]
}
```

**向后兼容**:老配置的 `ModelEntry` 没有 `capabilities` 字段 → serde default 填 `[Chat]`,行为不变。

## 三、0.12.1 对话窗口骨架(独立窗口 + AgentProvider + Alt+Q chord)

### 3.1 为什么需要独立对话窗口

0.9 §2.2 预留了"Agent 窗口(0.10)开放 AgentBuilder + memory + tool loop",但 0.10 实际做的是语音输入,Agent 窗口未落地。0.12 补这个债。

**主窗口 vs 对话窗口的定位差异**:

| 维度 | 主窗口(0.9-0.11) | 对话窗口(0.12) |
|---|---|---|
| 交互 | 单轮:打字 → 结果 → 执行 | 多轮:对话 → 追问 → 深入 |
| AI 能力 | `CompletionModel` + `ToolDefinition`(类型收窄) | `AgentBuilder` + memory + tool loop |
| tool 调用 | 有限多轮(0.11 改进 2:固定 2 次 complete) | agent loop(`max_turns` 上限内无限轮) |
| 记忆 | 无 | 有(持久化 conversation memory,§四) |
| 场景 | "打开 VSCode" / "查天气" / "翻译这段" | "帮我分析这个截图" / "整理这些笔记" / "连续调多个工具完成复杂任务" |

### 3.2 不破主窗口类型收窄铁则

0.9 §2.6 铁则:"主窗口 `AIProvider` trait 编译期没有 `AgentBuilder`"。代码已确认:`provider.rs:135` 有显式钉死注释,trait 只有 `kind / model_id / complete`,Turn 2 是手工拼 message 走 `complete`,非 agent loop。

0.12.1 的对话窗口**不修改主窗口的 AIProvider**——而是引入独立的 `AgentProvider`(直接用 rig 的 `Agent` + `AgentBuilder`),只在对话窗口上下文可用。

```
主窗口 AIProvider（0.9，类型收窄）        对话窗口 AgentProvider（0.12，开放）
  ├─ kind / model_id / complete              ├─ rig Agent（AgentBuilder 构建）
  └─ 无 AgentBuilder                         └─ memory + tool loop + streaming
```

## 四、0.12.2 对话机制(conversation 隔离 + 持久化 memory + tool loop)

### 4.1 conversation 隔离(多对话管理)

**模型**:每个对话窗口实例 = 一个 `conversation_id`(UUID)。用户可同时开多个对话窗口(不同话题隔离),每个对话独立 memory。

- 对话列表 UI(侧边栏或下拉),可新建/切换/删除/重命名对话
- 对话元数据(标题/创建时间/最后活跃时间)存 AI 库 `conversations` 表
- 删除对话 = 删 `conversations` 行 + 级联删 `messages` 行 + memory 清除

**conversation_id 贯穿**:`AgentProvider::prompt(conv_id, msg)` → rig `agent.prompt(msg).conversation(conv_id)` → rig 自动 load/append 该 conv 的历史。

### 4.2 持久化 memory(impl ConversationMemory 存 SQLite)

rig 的 `InMemoryConversationMemory` 重启即丢。0.12.2 自己 impl `ConversationMemory` trait 持久化到 AI 库:

```rust
// 新建 src/domain/ai/memory.rs
impl ConversationMemory for SqliteConversationMemory {
    async fn load(&self, conversation_id: &str) -> Result<Vec<Message>, MemoryError>;
    async fn append(&self, conversation_id: &str, messages: Vec<Message>);
    async fn clear(&self, conversation_id: &str);
}
```

**存储 schema**(AI 库新增表):
```sql
CREATE TABLE conversations (
  id TEXT PRIMARY KEY,
  title TEXT,
  created_at INTEGER NOT NULL,
  last_active_at INTEGER NOT NULL
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL,
  role TEXT NOT NULL,          -- user / assistant / tool
  content TEXT NOT NULL,       -- 序列化的 rig Message(含 tool_call / tool_result)
  created_at INTEGER NOT NULL,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE
);
CREATE INDEX idx_messages_conv ON messages(conversation_id, id);
```

`content` 列存序列化的 `rig::message::Message`(serde_json),保留 tool_call / tool_result 完整结构。load 时反序列化回 `Vec<Message>` 喂 rig。

### 4.3 窗口策略(复用 rig-memory)

直接用 `rig-memory` crate 的现成策略层,不自己写截断逻辑:

```rust
use rig_memory::{SlidingWindowMemory, IntoFilter};

let memory = SqliteConversationMemory::new(pool)
    .with_filter(SlidingWindowMemory::last_messages(20).into_filter());
```

**起步策略**:`SlidingWindowMemory::last_messages(20)`(保留最近 20 条消息)。

**后续扩展**(0.13):
- `TokenWindowMemory` 按 token 预算截断
- `CompactingMemory` 摘要压缩旧消息(rolling summary)
- `DemotingPolicyMemory` 截断消息归档到向量库做语义召回

0.12.2 只做滑动窗口,够用且简单。

### 4.4 tool loop 无限轮(放宽 0.11 的固定 2 次)

0.11 改进 2 的 Turn 2 是"固定 2 次 complete"——主窗口快路径的限制。对话窗口用 rig `Agent`,tool loop 由 `max_turns` 控制:

- `default_max_turns(50)`——单次 prompt 最多 50 轮 tool 往返(实际很少触顶,够用)
- 每轮 tool_call 流式可视化(显示"调用 XXX → 结果 → 继续思考")
- tool 结果走 0.12.0 统一投影 `to_rig_tool_result()` 回 rig
- 触顶返回 `MaxTurnsError`,UI 提示"达到工具调用上限,请简化任务或开新对话"

**tool 池**:对话窗口的 agent 挂载所有 Capability(0.9.7 + 0.11.2/0.11.5)+ 插件 tool(经 0.12.0 Tool 适配层包装)。0.13 后加 MCP tool + RAG tool。

### 4.5 与 0.11 结果回流的衔接

对话窗口的 tool loop 完全替代 0.11 改进 2 的"固定 2 次"——对话窗口里 AI 自主决定调几次 tool。主窗口保持 0.11 的固定 2 次(快路径不变)。

**0.11 的三态配置 `ai_tool_result_feedback`**:
- 主窗口:继续按 0.11 语义(auto / on / off)
- 对话窗口:tool loop 是核心机制,不受此配置影响(对话窗口默认就开多轮)

### 4.6 0.12.2 验收

```
 多对话管理:新建/切换/删除/重命名,每个对话独立上下文
 对话历史持久化:重启 Blink 后对话历史完整恢复
 滑动窗口策略生效:超过 20 条消息自动截断旧消息
 tool loop 无限轮:AI 自主连续调多个工具完成复杂任务(截图 → 分析 → 整理 → 写入剪贴板)

```
