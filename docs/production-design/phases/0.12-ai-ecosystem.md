# Blink 0.12 — AI 能力架构搭建

> **目标**：从主窗口单轮 AI 补全，演进到独立对话窗口、多轮 Agent、工具循环与持久化对话。
>
> **产品边界**：Blink 不做 AI 运行时。本地推理由外部 ollama / lmstudio 提供，Blink 只负责 Provider 对接、Agent 编排和能力调用。
>
> **当前状态（2026-07-24）**：
> - ✅ **0.12.0 完成**：基础设施抽取与清账，测试基线 **808 passed**。
> - ✅ **0.12.1 完成**：独立 chat 窗口、AgentProvider、ChatService、chat IPC、正式 chat UI（marked + DOMPurify 流式 Markdown），测试基线 **826 passed**。
> - 📋 **0.12.2 规划中**：多对话管理、SQLite 持久化 memory、滑动窗口。
>
> **范围**：0.12 只打通对话主链路。MCP client / RAG / 记忆向量召回 / MCP server / Skill 推迟到 0.13。

### 1.1 版本主线

### 1.2 产品边界

- 本地模型只对接外部 ollama / lmstudio，不内嵌推理引擎，不负责模型下载。
- ollama 走 rig 原生 Provider；lmstudio 和其他兼容服务走 `OpenAICompatible`。
- 0.12 不引入 MCP / RAG / 向量库。
- 安装包保持轻量，不因 AI 运行时显著膨胀。

### 1.3 两条 AI 路径严格隔离

| 维度 | 主窗口 | 对话窗口 |
|---|---|---|
| 抽象 | `AIProvider` | `AgentProvider` |
| 交互 | 单轮快路径 | 多轮对话 |
| 模型能力 | `complete` / `stream` | rig `AgentBuilder` / memory / tool loop |
| 工具调度 | 外部调度，固定回流 | Agent 内部循环，最大 50 turns |
| 记忆 | 无 | 按 `conversation_id` 隔离 |

**铁则**：主窗口 `AIProvider` 不暴露 `AgentBuilder`、memory 或 agent loop；对话能力只存在于 `agent_provider.rs` 和 chat 服务路径。

### 3.5 正式窗口方案

#### 窗口形态

#### 生命周期

| 操作 | 行为 |
|---|---|
| Alt+Q | 创建或恢复 chat，聚焦成功后隐藏主窗口 |
| 再按 Alt+Q | 聚焦已有 chat，不做 toggle hide |
| 点击关闭 | 隐藏窗口，不销毁 WebView |
| 生成中按 Esc | 中止当前生成 |
| 空闲时按 Esc | 隐藏 chat |
| 隐藏/关闭窗口 | 先中止 active request，避免隐藏 WebView 丢失事件但后台仍消耗模型 |
| Alt+Space | 主窗口仍可独立唤起 |

### 3.6 ChatService 方案（Phase 3B）

`AgentProvider` 只封装 rig Agent；请求生命周期由独立 `ChatService` 管理：

```rust
pub struct ChatService {
    provider: RwLock<Option<Arc<AgentProvider>>>,
    memory: Arc<dyn ConversationMemory>,
    active: Mutex<Option<ActiveChatRequest>>,
    next_request_id: AtomicU64,
}
```

职责：

- 从 `Tier::Main` 解析当前 Provider + Model，并在配置变化时重建 Agent。
- 同一窗口同一时间只允许一个 active prompt。
- 管理 `request_id`、AbortHandle 和过期 chunk 丢弃。
- memory 生命周期独立于 AgentProvider，切换 Provider / Model 不丢当前对话。
- 0.12.1 使用 `InMemoryConversationMemory`；0.12.2 注入 SQLite 实现。

`AgentProvider::new()` 将调整为接收外部 memory：

```rust
AgentProvider::new(entry, model, tools, preamble, memory)
```

### 3.7 IPC 与事件协议（Phase 4）

#### Commands

```text
chat_prompt(conversation_id, message) -> request_id
chat_abort(request_id)
confirm_chat_action(confirm_id, approved)
get_chat_status()
```

#### 事件 envelope

所有事件必须携带请求和对话标识：

```rust
struct ChatStreamEvent {
    request_id: u64,
    conversation_id: String,
    chunk: ChatStreamChunk,
}
```

前端只消费当前 `request_id`，防止已中止请求的尾部 chunk 混入新回复。

事件使用定向发送：

```text
blink://chat-stream
blink://chat-confirm-action
blink://chat-provider-changed
```

通过 `emit_to("chat", ...)` 发往 chat WebView，不向主窗口和其他次级窗口全局广播。

### 3.8 正式前端方案（Phase 5）

#### 布局

```text
顶部：Blink AI / 当前 Provider · Model / 新对话 / 设置
中部：用户消息、Assistant 流、Tool 状态卡、错误与确认卡片
底部：自增高 textarea / 发送或停止按钮
```

#### 交互

- `Enter` 发送，`Shift+Enter` 换行。
- 生成中发送按钮切换为停止按钮。
- 初始 `conversation_id` 由 `crypto.randomUUID()` 生成；新对话生成新 ID 并清空当前视图。
- 0.12.1 不做多对话侧边栏，但协议从第一天贯穿 `conversation_id`。
- AI 已启用但主模型未配置时，显示配置缺失空状态和“打开设置”入口。

#### 流式 Markdown 渲染

**方向**：正式 chat UI 不满足于纯文本，优先调研 **Streamdown 或同类流式 Markdown renderer**，重点解决普通 Markdown renderer 在 AI 增量输出中的未闭合语法、代码块闪烁和全量重排问题。

Streamdown（`vercel/streamdown`）可作为首要候选和设计参照：

- 专门处理不完整/未闭合的 Markdown block，适合 token delta 持续追加。
- 支持 GFM、流式 caret、代码块、链接安全与 HTML hardening。
- 可选 `@streamdown/code` / `@streamdown/cjk` / math / mermaid 插件；Blink 起步只考虑基础 Markdown + code + CJK，不默认引入 math / mermaid。
- 已完成消息冻结为静态渲染，只增量更新当前 assistant 消息，避免历史消息反复 parse。

**接入约束**：Streamdown 当前是 React/npm 组件，并依赖 Tailwind/shadcn 风格变量；Blink 前端坚持纯静态 HTML/CSS/JS、无 npm、无 bundler，因此**不能直接作为常规 npm 依赖接入**。Phase 5 动手前做一次小型 PoC，按以下顺序选择：

1. 优先寻找或实现 framework-agnostic 的流式 Markdown renderer，复用 Streamdown 的 incomplete-block 修复、安全和增量渲染思路。
2. 若 Streamdown 能产出许可清晰、体积可接受、无需运行期 React/Tailwind 环境的独立预构建 bundle，可将 bundle 固定版本 vendoring 到 `frontend/vendor/`。
3. 只有 Streamdown 的效果明显优于静态方案且无法无框架复用时，才单独评估“仅 chat 窗口引入构建步骤”；这属于技术栈变更，不能在 0.12.1 默认发生。

**安全与性能铁则**：

- 模型输出视为不可信内容：禁用 raw HTML，链接使用协议白名单，远程图片默认不加载，最终 DOM 必须经过 sanitizer/hardening。
- token delta 先累计到当前消息 buffer，按 `requestAnimationFrame` 或约 30～50ms 批量刷新，不逐 token 重建整个消息列表。
- 流式阶段允许 renderer 修复临时未闭合语法；`Done` 后用完整原文做一次最终稳定渲染。
- renderer 初始化或解析失败时降级到 `textContent + white-space: pre-wrap`，不影响消息可读性和停止生成。

**PoC 验收**：中文段落、嵌套列表、表格、反引号、未闭合 fenced code block、流中途停止、超长代码块和恶意 HTML/link 输入均能稳定、安全地渲染；记录 bundle 体积、长回复增量更新时间和内存占用后再定案。

参考：<https://github.com/vercel/streamdown> / <https://streamdown.ai/docs/usage>

#### 流式事件

正式 `ChatStreamChunk` 收敛为：

```rust
enum ChatStreamChunk {
    TextDelta { text: String },
    ToolStarted { call_id: String, tool: String },
    ToolFinished { call_id: String, success: bool },
    Done { usage: Option<Usage> },
    Error { code: String, message: String },
}
```

Tool 卡片默认只展示工具名和执行状态，不直接展示完整参数，避免敏感路径或剪贴板内容泄露。

### 3.9 Dangerous Tool 确认

0.12.0 已完成后端挂起机制，0.12.1 前端接入原位确认卡片：

```text
Dangerous Tool 调用
    ↓
blink://chat-confirm-action
    ↓
chat 内显示 [拒绝] [允许执行]
    ↓
confirm_chat_action(confirm_id, approved)
    ↓
```

- 不使用 `window.confirm()`。
- 用户确认后才执行并返回真实结果。
- 拒绝或 60 秒超时均返回“未执行”，Agent 可继续选择其他路径。

### 4.2 SQLite ConversationMemory

AI 库新增：

```sql
CREATE TABLE conversations (
  id TEXT PRIMARY KEY,
  title TEXT,
  created_at INTEGER NOT NULL,
  last_active_at INTEGER NOT NULL
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE
);
CREATE INDEX idx_messages_conv ON messages(conversation_id, id);
```

`content` 直接存序列化的 rig `Message`，完整保留 text / tool_call / tool_result。

```rust
impl ConversationMemory for SqliteConversationMemory {
    async fn load(&self, conversation_id: &str) -> Result<Vec<Message>, MemoryError>;
    async fn append(&self, conversation_id: &str, messages: Vec<Message>) -> Result<(), MemoryError>;
    async fn clear(&self, conversation_id: &str) -> Result<(), MemoryError>;
}
```

持久化层保存完整历史，窗口策略只影响每次发给模型的 active context，不删除数据库历史。
