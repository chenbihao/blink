# Blink 0.12 — AI 能力架构搭建(对话窗口 / 对话机制 / 调用能力 / RAG)

> **范围**:① 基础设施抽取与清账(投影统一 / DB 拆分 / 本地 Provider 接入)+ ② 对话窗口(独立 Agent 窗口)★ + ③ 对话机制(conversation 隔离 / 持久化 memory / 窗口策略)+ ④ 调用能力整合(tool loop 无限轮 / MCP client / 记忆调用)+ ⑤ RAG(知识库检索作为内部 tool)。
>
> **主题**:0.11 把插件 AI toolchain 的内部一致性做扎实;0.12 在此基础上**搭 AI 能力的架构骨架**——从「主窗口单轮 complete」进化到「独立对话窗口多轮 agent loop」,把对话隔离、上下文管理、工具调用、记忆、知识库检索这些 AI 能力的核心机制建立起来。
>
> **产品边界决策**:**Blink 不做 AI 运行时**。本地推理完全靠外部(ollama / lmstudio),Blink 只作 Provider 对接。不引内嵌推理引擎(mistral.rs 等),不重复造轮子,不跟踪推理框架更新,不维护模型下载——产品边界清晰。
>
> **rig 基础**:rig 0.39 的 `AgentBuilder` + `ConversationMemory` trait + `rig-memory` 策略层(SlidingWindow / TokenWindow / Compacting)已覆盖对话窗口绝大部分需求,**核心工作量在前端 chat UI + 持久化 memory 后端 + MCP client 编排**,而非重造 agent loop。
>
> **前置**:0.11 完成(统一结果模型 + 工具元信息 + 提示词管理 + 结果回流 + sensitive 字段铺路)。
>
> **原则**:安装包保持 < 100MB;暴露本地能力(MCP server)推 0.13;Agent 窗口不破主窗口类型收窄铁则;**先抽取再扩展,先架构再功能**。

### 1.2 产品边界:Blink 不做 AI 运行时

**决策**:本地推理完全靠外部进程, Blink 只作 Provider 对接。

| 外部运行时 | 接入方式 | Blink 侧成本 |
|---|---|---|
| **ollama** | rig `providers::ollama` Provider(0.9 已引入 crate) | 加一个 `ProviderKind::OllamaHttp` arm + 设置页 tab |
| **lmstudio** | 走现有 `ProviderKind::OpenAICompatible`(lmstudio 默认起 OpenAI 兼容 API `localhost:1234/v1`) | **零适配**,用户在供应商配置里填 endpoint 即可 |
| 其他 OpenAI 兼容本地服务 | 同上 | 零适配 |

**为什么不做内嵌运行时**:
1. 不重复造轮子——ollama/lmstudio 已是事实标准,用户已经在用
2. 不跟踪推理框架更新——mistral.rs/llama.cpp 迭代频繁,Blink 跟不起
3. 不维护模型下载——GGUF/UQFF 格式、HuggingFace 镜像、断点续传都是负担
4. 安装包不膨胀——本地运行时依赖动辄几十 MB
5. 产品边界清晰——Blink 是 AI 消费者,不是 AI 运行时

**唯一例外**:`all-MiniLM-L6-v2` 这类小 embedding 模型若用户不想装 ollama,可手动指定模型文件路径,Blink 用 `ort`/`candle` 跑——但这不是 0.12 必须,默认走 ollama embedding(`nomic-embed-text`)。

3. **前端 chat UI**(对话历史渲染 + 流式输出 + tool_call 可视化)——中,纯前端

## 二、0.12.0 基础设施抽取与清账

### 2.1 投影函数统一

**目标**:消除"两套回流投影并存"的歧义,确定一条权威路径。

**决策**:**保留 `to_rig_tool_result()`(`result.rs:29`)作为唯一投影入口,删除 service.rs 那两个 project_* 私有函数**。

理由:
- `to_rig_tool_result()` 返回 rig 原生 `ToolResultContent`(可直接喂 LLM),`project_*_to_tool_message` 返回 `String`(还要包一层 text content)——前者是规范路径
- 0.12.2 对话窗口的 tool loop 也要用这份投影,MCP result 投影同理,统一在 capability 层而非散在 service.rs
- Blob 摘要策略(不喂原始字节省 token)从 `project_capability_result_to_tool_message` 迁入 `to_rig_tool_result()` 的 Blob 分支

**`ActionOutcome → ToolResultContent` 投影**:新增对称的 `ActionOutcome::to_rig_tool_result()`,与 `CapabilityResult::to_rig_tool_result()` 同一份契约。

### 2.2 DB 拆分与分层修复★

review 发现 DB 现状有几个硬问题,必须在 0.12.0 清账(否则对话窗口的 memory 持久化加进来后会更乱):

#### 2.2.1 现状问题

| 问题 | 证据 | 影响 |
|---|---|---|
| **6 张表挤一个 `blink.db`** | `history.rs:16-21` 唯一 `connect`,`max_connections(1)` | 单写锁,高频写阻塞低频读 |
| **`performance_metrics` 高频写入** | `service.rs:700-706` 每次搜索写一行(用户每按键 1 行);`capability/registry.rs:107/130/146` 每次 capability invoke 写 | DB 膨胀主因,30 天窗口内可累积数十万行;与 config 读互相阻塞 |
| **`icon_cache` 含 BLOB** | `icon.rs:155-178` 每个未命中图标写 PNG BLOB,上限 2000 条 × ~5KB ≈ **10MB** | 占据 DB 大头,与小配置表混在一起 |
| **`ai_tool_audit` 无清理** | `ai_audit.rs` 全表无 `cleanup_old` / 行数上限 | 单调增长,长期使用线性膨胀 |
| **分层违规 1** | `icon_cache` schema 在 `domain/search/icon.rs:51-58`(领域层直持 DB) | 违反 Clean Architecture |
| **分层违规 2** | `performance_metrics` schema 在 `infra/utils/perf.rs:61-68`(不在 data 层) | 同上 |
| **`config` 访问层混在 history.rs** | `history.rs:242-282` 的 `get_config`/`set_config` | 历史遗留 |
| **AGENTS.md §8 表清单过时** | 表名写错(clipboard/perf vs clipboard_history/performance_metrics),漏 ai_tool_audit + icon_cache | 文档失真 |

#### 2.2.2 拆分方案(三层:主库 + AI 库 + 缓存库)

**方案:按数据域拆三层**

| 库 | 表 | 性质 | 写入频率 | 丢得起吗 |
|---|---|---|---|---|
| **`blink.db`(主库)** | `config` / `history` / `clipboard_history` | 用户核心数据(配置 + 历史 + 剪贴板) | 低 | ❌ 不可丢 |
| **`blink_ai.db`(AI 库)** | `ai_tool_audit` / `conversations` / `messages` / `embeddings` | AI 对话与记忆域(0.12.2/0.12.4 新增) | 中(每次 AI 交互) | ⚠️ 用户可选(可单独清空对话历史保留配置) |
| **`blink_cache.db`(缓存库)** | `performance_metrics` / `icon_cache` | 纯缓存(可重建) | 高(perf 每按键)+ BLOB(icon) | ✅ 可丢可重建 |

**为什么三层不是两层**:
- **AI 域独立性**:对话历史 / 记忆 / 向量是 AI 子系统自洽的数据集,生命周期独立(用户可能想「清空所有 AI 数据但保留剪贴板历史」),与主库的「配置/启动历史/剪贴板」是不同关注点
- **写入特征差异**:AI 库是中频写入(每次对话几行)、缓存库是高频写入(每按键 perf),分库后写锁各不影响
- **可独立清理/备份/迁移**:用户可单独导出对话历史、单独清空 AI 数据、单独删缓存——三层边界与用户心智对齐
- **未来扩展**:0.13 记忆向量召回、Skill 草案、MCP 审计等继续进 AI 库,不污染主库

**主库保持极小而稳**:只有 config / history / clipboard_history 三张表,几十 KB 级,备份/迁移/跨机同步成本最低。

### 2.4 Tool 适配层抽取(★ 关键,解决 rig Agent 与现有架构的形态冲突)

**问题背景**:rig `AgentBuilder` 注册 tool 的方式与现有架构根本不同:

| 维度 | 现有架构(主窗口 0.11) | rig Agent(对话窗口) |
|---|---|---|
| tool 形态 | **数据**:`Vec<ActionSchema>` → 投影成 `Vec<ToolDefinition>` 作为 `CompletionRequest` 参数 | **代码**:`impl rig::tool::Tool` trait(`Tool::call(args) -> Output`) |
| 调度方 | **外面驱动**——service.rs 收到 `tool_calls` 后手工执行,结果拼回 message 再 `complete` | **Agent 内部**——`AgentRun` 状态机自动 CallModel ↔ CallTools 循环 |
| 现有实现 | Capability / PluginActionAdapter 都是「外部调度」形态,**都没 `impl rig::Tool`** | — |

**冲突后果**:对话窗口想用 rig Agent,**现有的 Capability + 插件 tool 全部接不进去**。若不解决,0.12.1 直接卡住。

**解决方案**:**0.12.0 抽出 `ToolAdapter` 层**,把 Capability / Action 包装成 `impl rig::tool::Tool`:

```
src/domain/ai/tool_adapter.rs (新建)
  ├─ CapabilityTool { cap: Arc<dyn Capability>, schema: CapabilitySchema }
  │    impl Tool for CapabilityTool  (definition → schema.to_rig_tool, call → cap.invoke + to_rig_tool_result)
  ├─ ActionTool { action: Arc<dyn Action>, schema: ActionSchema }
  │    impl Tool for ActionTool
  └─ 工厂函数 build_agent_tools(registry, cap_registry) -> Vec<Box<dyn ToolDyn>>
```

**Tool::Args 用 `serde_json::Value`**(走 `ToolDyn` 动态分发路径,避免给每个 Capability 写强类型 Args):
- `definition(prompt)` 返回 `schema.to_rig_tool()`(纯 schema 投影,已有)
- `call(args: Value)` 内部调 `cap.invoke(args, ctx)` → `CapabilityResult` → `to_rig_tool_result()`(0.12.0 已激活)
- 危险操作(`danger_class == Dangerous`)在 `call` 内部 emit 确认卡片 + 返回 "等待用户确认" 消息,不直接执行(保持四域墙)

**MCP tool(0.12.3)同理**——外部 server 拉到的 tool 包装成 `McpTool { server, tool_def }` 也 `impl Tool`,**统一进同一个适配器层**。

**这个抽取是 0.12.0 的硬要求**,不做的话对话窗口整个走不通。完成后:
- 主窗口 Turn 2 仍走现有「数据 + 外部调度」路径(不变,类型收窄铁则保持)
- 对话窗口走新「Tool 适配器 + Agent 内部调度」路径

### 2.5 CapabilityRegistry 运行期动态注册(★ MCP client 前提)

**问题**:`CapabilityRegistry`(`registry.rs:31`)当前只从 `inventory::iter` 链接期收集,**没有运行期 register 入口**:

```rust
pub fn new() -> Self {
    for entry in inventory::iter::<CapabilityEntry> { ... }  // ← 链接期,无运行期入口
}
// caps 字段私有,外部无法注入
```

而 `inventory::submit!` 是链接期静态机制,0.12.3 MCP client 启动时才拉到的 tool 根本走不了这条路。

**解决方案**(参照 `ActionRegistry::register` 范式,`registry.rs:67`):
```rust
impl CapabilityRegistry {
    /// 运行期动态注册(MCP client / 未来 Skill 用)。重复 id → warn + 跳过。
    pub fn register(&self, cap: Arc<dyn Capability>) { ... }
}
```

**注意**:这不是"顺手补"——`caps` 字段可见性、`new()` 与 `register` 的去重逻辑、与 `inventory::iter` 共存策略都要显式设计。0.12.3 启动前必须完成(可放 0.12.0 顺手做掉,但 0.12.3 验收时显式依赖)。

### 2.6 message 序列化核查(rig Message 持久化前提)

**0.12.2 要 impl `ConversationMemory` 存 SQLite,content 列存序列化的 rig `Message`**。前提是 `rig::message::Message: Serialize + Deserialize`——0.12.0 落地前需核查:

**核查结论写入 0.12.0 验收**(二选一标记:走 rig Message serde / 走 ChatMessage 中间层)。

## 三、0.12.1 对话窗口骨架(独立窗口 + AgentProvider)

### 3.1 为什么需要独立对话窗口

0.9 §2.2 预留了"Agent 窗口(0.10)开放 AgentBuilder + memory + tool loop",但 0.10 实际做的是语音输入,Agent 窗口未落地。0.12 补这个债。

**主窗口 vs 对话窗口的定位差异**:

| 维度 | 主窗口(0.9-0.11) | 对话窗口(0.12) |
|---|---|---|
| 交互 | 单轮:打字 → 结果 → 执行 | 多轮:对话 → 追问 → 深入 |
| AI 能力 | `CompletionModel` + `ToolDefinition`(类型收窄) | `AgentBuilder` + memory + tool loop |
| tool 调用 | 有限多轮(0.11 改进 2:固定 2 次 complete) | agent loop(`max_turns` 上限内无限轮) |
| 记忆 | 无 | 有(持久化 conversation memory,§四) |
| 场景 | "打开 VSCode" / "查天气" / "翻译这段" | "帮我分析这个截图" / "整理这些笔记" / "连续调多个工具完成复杂任务" |

### 3.2 不破主窗口类型收窄铁则

0.9 §2.6 铁则:"主窗口 `AIProvider` trait 编译期没有 `AgentBuilder`"。代码已确认:`provider.rs:135` 有显式钉死注释,trait 只有 `kind / model_id / complete`,Turn 2 是手工拼 message 走 `complete`,非 agent loop。

```
主窗口 AIProvider（0.9，类型收窄）        对话窗口 AgentProvider（0.12，开放）
  ├─ kind / model_id / complete              ├─ rig Agent（AgentBuilder 构建）
  └─ 无 AgentBuilder                         └─ memory + tool loop + streaming
```

两个 trait 共享底层 rig Client + Provider 配置(0.12.0 已接 ollama),但能力面不同。**调研 #16 定案:方案 B(直接用 rig AgentBuilder)**,不自己重写 agent loop。

## 四、0.12.2 对话机制(conversation 隔离 + 持久化 memory + tool loop)

### 4.1 conversation 隔离(多对话管理)

**模型**:每个对话窗口实例 = 一个 `conversation_id`(UUID)。用户可同时开多个对话窗口(不同话题隔离),每个对话独立 memory。

- 对话列表 UI(侧边栏或下拉),可新建/切换/删除/重命名对话
- 对话元数据(标题/创建时间/最后活跃时间)存主库 `conversations` 表
- 删除对话 = 删 `conversations` 行 + 级联删 `messages` 行 + memory 清除

**conversation_id 贯穿**:`AgentProvider::prompt(conv_id, msg)` → rig `agent.prompt(msg).conversation(conv_id)` → rig 自动 load/append 该 conv 的历史。

### 4.2 持久化 memory(impl ConversationMemory 存 SQLite)

rig 的 `InMemoryConversationMemory` 重启即丢。0.12.2 自己 impl `ConversationMemory` trait 持久化到主库:

```rust
// 新建 src/domain/ai/memory.rs
impl ConversationMemory for SqliteConversationMemory {
    async fn load(&self, conversation_id: &str) -> Result<Vec<Message>, MemoryError>;
    async fn append(&self, conversation_id: &str, messages: Vec<Message>);
    async fn clear(&self, conversation_id: &str);
}
```

**存储 schema**(主库新增表):
```sql
CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL,
  role TEXT NOT NULL,          -- user / assistant / tool
  content TEXT NOT NULL,       -- 序列化的 rig Message(含 tool_call / tool_result)
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_messages_conv ON messages(conversation_id, id);
```

`content` 列存序列化的 `rig::message::Message`(serde_json),保留 tool_call / tool_result 完整结构。load 时反序列化回 `Vec<Message>` 喂 rig。

### 4.3 窗口策略(复用 rig-memory)

直接用 `rig-memory` crate 的现成策略层,不自己写截断逻辑:

```rust
use rig_memory::{SlidingWindowMemory, IntoFilter};

let memory = SqliteConversationMemory::new(pool)
    .with_filter(SlidingWindowMemory::last_messages(20).into_filter());
```

**起步策略**:`SlidingWindowMemory::last_messages(20)`(保留最近 20 条消息)。

**后续扩展**(0.13):
- `TokenWindowMemory` 按 token 预算截断
- `CompactingMemory` 摘要压缩旧消息(rolling summary)
- `DemotingPolicyMemory` 截断消息归档到向量库做语义召回

0.12.2 只做滑动窗口,够用且简单。

### 4.4 tool loop 无限轮(放宽 0.11 的固定 2 次)

0.11 改进 2 的 Turn 2 是"固定 2 次 complete"——主窗口快路径的限制。对话窗口用 rig `Agent`,tool loop 由 `max_turns` 控制:

- `default_max_turns(50)`——单次 prompt 最多 50 轮 tool 往返(实际很少触顶,够用)
- 每轮 tool_call 流式可视化(显示"调用 XXX → 结果 → 继续思考")
- tool 结果走 0.12.0 统一投影 `to_rig_tool_result()` 回 rig
- 触顶返回 `MaxTurnsError`,UI 提示"达到工具调用上限,请简化任务或开新对话"

**tool 池**:对话窗口的 agent 挂载所有 Capability(0.9.7 + 0.11.2/0.11.5)+ 插件 tool + 0.12.3 的 MCP tool + 0.12.4 的 RAG tool。

### 4.5 与 0.11 结果回流的衔接

对话窗口的 tool loop 完全替代 0.11 改进 2 的"固定 2 次"——对话窗口里 AI 自主决定调几次 tool。主窗口保持 0.11 的固定 2 次(快路径不变)。

**0.11 的三态配置 `ai_tool_result_feedback`**:
- 主窗口:继续按 0.11 语义(auto / on / off)
- 对话窗口:tool loop 是核心机制,不受此配置影响(对话窗口默认就开多轮)

### 4.6 0.12.2 验收

```
 多对话管理:新建/切换/删除/重命名,每个对话独立上下文
 对话历史持久化:重启 Blink 后对话历史完整恢复
 滑动窗口策略生效:超过 20 条消息自动截断旧消息
```

## 六、0.12.4 RAG(知识库检索作为内部 tool)

### 6.1 定位

VectorRouter 在 0.9 移出后在这里找到归宿——对本地文档库 / 笔记做语义检索,作为 AI 回答的上下文。**记忆的「向量召回」语义推 0.13**,0.12.4 只做用户主动加入知识库的 RAG。

### 6.2 embedding 生产 vs 向量存储的边界

| 层 | 技术选择 | 理由 |
|---|---|---|
| **embedding 生产** | 走 rig `EmbeddingsModel`(ollama `nomic-embed-text` / 云端 API) | 复用 0.9 Provider 抽象 + 0.12.0 ollama 接入,零摩擦 |
| **向量存储 / 检索** | 自写 + SQLite BLOB(暴力 cosine 起步) | 贴 Awareness 域,SQLite 已有生态;**不引 rig-vector / sqlite-vec** |

**embedding Provider 复用 0.12.0 的 ollama**:本地 ollama 零成本产 embedding(`client.embedding_model("nomic-embed-text")` 现成)。云端按 token 计费时用户可切云端 embedding Provider。

### 6.3 暴力 cosine 起步

- **起步**:暴力 cosine(1000 条向量内 CPU < 10ms),持久化走 SQLite BLOB(主库 `embeddings` 表)
- **扩展**:真到 10 万+ 再上 `sqlite-vec`(0.13 届时引入,不提前引依赖)

### 6.4 embedding 一致性约束(切模型必重建)

**向量库必须锁 embedding model_id**:向量存 `(model_id, vector)`,切 embedding Provider(维度不同 / 语义空间不同)触发**重建索引 UI 提示**,不隐式失效数据。

### 6.5 RAG 作为内部 Capability

**建模决策**:RAG 检索建模为一个 Capability `search_knowledge_base`,进对话窗口 tool 池。AI 判断需要本地知识时自主调用,结果走 tool loop 回流。

这样 RAG **不需要单独的调用路径**,完全复用 0.12.0 + 0.12.2 铺好的链路:
- 用户加文档 → 后台异步 embedding(走 ollama)→ 写入向量库
- AI 调 `search_knowledge_base(query)` → 暴力 cosine 检索 → `CapabilityResult::Items`
- 结果投影走 0.12.0 统一 `to_rig_tool_result()`
- rig Agent 自主消费 RAG 上下文做总结

### 6.6 0.12.4 验收

```
 设置页「知识库」入口,可添加本地文档(单文件 / 目录)
 后台异步 embedding(走 ollama nomic-embed-text),进度可见,不阻塞 UI
 对话窗口问"我笔记里有没有提到 XXX" → AI 自主调 search_knowledge_base
 切 embedding Provider 提示重建索引
 向量库锁 model_id,切模型不隐式失效
```

- **Tool 适配层(§2.4)是 0.12.0 的硬要求**——不做的话对话窗口整个走不通(rig Agent 的 tool 形态与现有架构冲突,见 §2.4)
- 0.12.1 + 0.12.2 是核心(对话窗口 + 对话机制),构成 AI 能力架构的主干
- 0.12.3 + 0.12.4 可并行推进(都依赖 0.12.0 的 Tool 适配层,但互相独立)
