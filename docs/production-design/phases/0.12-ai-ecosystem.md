# Blink 0.12 — AI 生态完善(本地模型 / Skill 化 / MCP 双向 / A2A / RAG 记忆 / 对话窗口)

> **范围**:① 本地模型按需下载(隐私/离线)+ ② Skill 化(配置期 CLI 探索转静态 tool)+ ③ MCP 双向(消费生态 + 暴露本地能力护城河)+ ④ A2A(视情况)+ ⑤ VectorRouter 真正归宿(RAG/记忆)+ ⑥ 单独对话窗口(Agent 窗口模式)。
>
> **主题**:0.11 把插件通信契约和 AI 调用插件的链路做扎实(内部一致性);0.12 在此基础上扩展 AI 生态杠杆——让 Blink 既能消费外部生态(MCP client/skill),又能被外部生态依赖(MCP server 暴露本地能力),并补齐本地模型、RAG 记忆、对话窗口这些"AI 体验完善"的拼图。
>
> **前置**:0.11 完成(统一结果模型 + 工具元信息 + 提示词管理 + 结果回流 + sensitive 字段铺路)。
>
> **原则**:安装包保持 < 100MB(本地一切按需下载);运行期不实时探索 skill(AI 当 skill 编译器不当运行时决策者);暴露本地能力(MCP server)是护城河方向;Agent 窗口不破主窗口类型收窄铁则(主窗口仍无 AgentBuilder)。
>
> **0.11 衔接**:0.12 大量复用 0.11 铺的基础设施——统一结果模型(改进 1)、`to_rig_tool_result()` 投影接通(改进 2)、`sensitive` 字段(改进 3a/A1/A5)、统一提示词管理(改进 4)、审计日志骨架(改进 2/A3)。

## 一、本地模型(按需下载)

### 1.1 安装包硬约束

本地 LLM / STT / embedding 模型都偏大,**绝不捆绑进安装包**(< 100MB 是硬约束,见 CLAUDE.md §2)。

### 1.2 接入方式(双源分层——与 0.9 rig 选型对齐)

本地模型有**两条独立技术路径**,语义完全不同,设置页分别呈现,不放同栏:

| 接入形态 | 库 | 类型 | 冷启动 | 内存 | 用户体验 | 推荐场景 |
|---|---|---|---|---|---|---|
| **HTTP 型 Provider**(首选) | rig `Ollama` Provider | 远程 / localhost 都可 | 快(仅 HTTP client 构造) | ~0(推理在 ollama) | 用户装好 ollama,Blink 自动连 `localhost:11434` | 已装 ollama 的用户,零改造成本 |
| **内嵌运行时** | `mistral.rs`(GGUF/UQFF) | 内嵌推理引擎 | 慢(加载模型) | 高(推理占用) | Blink 主进程内直跑,零外部依赖 | 追求单文件、离线、免装 ollama |

**为什么分两栏**:一个是网络配置(选 endpoint / model 名),一个是模型文件路径 + 加载器配置——冷启动延迟、内存占用、故障模式完全不同,合成一栏用户会踩坑。

- **HTTP 型 Provider**:core 直接依赖 rig `providers::ollama`(0.9 已引入),无额外重依赖
- **内嵌运行时**:引入 `mistral.rs` 需评估依赖体量(调研 #9),支持自定义模型路径 + 手动下载 GGUF / UQFF
- **自行下载 UI**:设置页「下载模型」进度可见、可暂停/取消;支持自定义本地模型路径

### 1.3 推理栈定位

- 本地 LLM 主要当「路由 / 轻量」档(强推理仍推荐云端主模型)
- 本地 STT 走 [0.10 §4.1](./0.10-voice-agent.md#41-接入形态与-09-rig-抽象对齐) 定型的方式:`whisper-rs` / `sherpa-onnx` + 自实现 rig `TranscriptionModel` trait
- 本地 embedding:`all-MiniLM-L6-v2` 或同级(~20MB),按需下载(详见 §五)

### 1.4 与 0.11 结果回流的协同

本地模型作为"路由 / 轻量"档时,0.11 改进 2 的"结果回流"多一次 complete 调用——本地模型零成本推理,正好适合 Turn 2 总结 + tool chain。云端模型按 token 计费时用户可关回流(`ai_tool_result_feedback=off`);本地模型默认开(`auto` 模式)。**0.11 的三态配置已为此铺路**。

### 1.5 与 Skill 化的协同

Skill 化(§二)的配置期"AI 跑 --help 解析"需要一个 AI 调用入口。本地模型零成本推理,正好适合跑这种"探索性、非实时"的解析任务——不花云端 token。若用户已装本地模型,Skill 生成默认走本地;否则回退云端(用户知情)。

## 二、Skill 化(配置期探索,不是运行期)

### 2.1 为什么放 0.12 而非 0.11

**与 0.11 插件通信契约修复的关系**:中等——共享基础设施(统一结果模型 / 工具元信息 / 提示词管理),但 Skill 的**生成工作流**(AI 跑 --help → 生成描述 → 用户审核 → 固化)是独立的 UI + 流程,与契约修复本身正交。

**放 0.12 的理由**:
1. 0.11 工作量已饱满(改进 1-7 主线),Skill 生成 UI + 审核流程 + 固化存储是不小的工作量
2. Skill 生成需要 AI 调用入口(非主窗口路由 AI),与本地模型(§一)协同——本地跑 --help 解析零成本
3. 0.11 的统一结果模型(改进 1)+ 工具元信息(改进 3)+ 提示词管理(改进 4)是 Skill 化的基础设施,0.11 落地后 Skill 化零摩擦接入
4. Skill 生成的 tool 同样要走 0.11 的 `sensitive` 字段声明(若 CLI 涉及敏感操作)

### 2.2 设计原则:AI 当 skill 编译器,不当运行时决策者

用户思路:「指定 CLI 目录,AI 自行 `--help` 探索转 skill」。

**关键约束**:这是**配置期**能力,不是运行期:

- **配置期**:用户主动点「解析这个 CLI」→ AI 跑一次 `--help` → **生成 skill 描述草案** → 用户审核修改 → 固化为静态 skill
- 之后该 skill 走确定性快速通道(不过 AI)

**为什么不在运行期实时探索**:

- 不确定性(行为不可预测)
- 慢(每次探索)
- **信任边界**:AI 自己探索 skill 自己执行,四域墙就破了(Blink 有本地 Execution 权限,危险)

### 2.3 skill 描述复用 0.9/0.11 schema

生成的 skill 描述直接走 0.9 的统一能力 schema(`name / description / parameters / exec`),对 Blink 来说和 builtin / 插件是同一种 tool。0.11 改进 3a 的元信息字段(`result_type` / `hint` / `examples` / `sensitive`)生成的 skill 也应填——让 AI 调用 skill 时有同等元信息。

### 2.4 skill 的结果模型对齐 0.11

Skill 化生成的 tool 同样要走 0.11 改进 1 的统一结果模型——`result_type` 声明、payload 字段、结果回流(改进 2 的 tool chain)。Skill 本质是"动态生成的插件",通信契约不应有二义性。

### 2.5 Skill 生成的工作流

```
用户在设置页点「解析 CLI」
  → 选 CLI 可执行文件路径(或目录)
  → AI 调用本地模型(首选)/ 云端模型(回退)跑 --help
  → 解析输出 → 生成 skill 草案(name/description/parameters/exec/result_type/hint)
  → 用户审核编辑(可改参数名、补 hint、标 sensitive)
  → 固化存储(%APPDATA%\blink\skills\{skill_id}.json)
  → 启动时自动注册进 ActionRegistry(与插件 tool 并列)
```

**固化后的 skill 是静态 tool**:走确定性快速通道,不实时过 AI。只有"生成"那一次调 AI。

### 2.6 Skill 的执行路径

Skill 的 `exec` 字段指向 CLI 可执行文件 + 参数模板。执行时:

- 走 `PluginActionAdapter` 同模式的子进程调用(或抽一个 `CliActionAdapter`)
- 结果按 `result_type` 投影:`text` → `ActionOutcome::Copy` / `items` → `ActionOutcome::Items` / `done` → `ActionOutcome::Nop` + emit
- 结果回流(0.11 改进 2)同样适用——AI 调 skill 后能总结/链式

**不破四域墙**:Skill 是 Execution 域的 Action,执行需用户显式触发(回车/Tab/AI tool_call)。生成期 AI 只产描述,不执行。

## 三、MCP 双向(生态杠杆)

**技术栈复用**:0.9 引入的 rig-core 已通过 `rmcp` feature 集成 MCP 官方 Rust SDK,`impl From<rmcp::model::Tool> for ToolDefinition` 让 MCP 工具 schema 零适配投影到统一 tool 表述——0.12 MCP 上层只需实现 client / server 编排逻辑,协议层不用重造。

### 3.1 MCP client(消费生态 tool)

- Blink 作为 MCP client,消费生态里海量 server 提供的 tool
- 这些 remote tool 走 0.9 的统一 tool schema(`exec: mcp`),和 builtin / 插件 / skill 并列
- 让 Blink 变强,但护城河浅

**MCP client 的结果契约**:MCP 消费的外部 tool 走 0.11 改进 1 的统一结果模型。外部 tool 返回的 JSON 投影成 `CapabilityResult::Items` 或 `Text`,AI 读 payload,前端展示 title。**统一契约是 MCP 双向的前提**——0.11 把内部一致做扎实,0.12 MCP 派生零摩擦。

### 3.2 MCP server(暴露本地能力 = 护城河)★

**这是 0.12 真正的王牌**:

- 把 Blink 的本地能力暴露成 MCP server:全局划词 / 剪贴板 / 前台应用 / 截图 / 文件操作 / 资源管理器定位 / 应用搜索
- 这样**任何外部 Agent**(Claude Desktop / Cursor / 自建 Agent)都能通过 MCP 调用 Blink 的感知和执行能力
- 这些能力正是 Web Agent 拿不到的——**生态依赖 Blink,而不只是 Blink 依赖生态**

> client 让 Blink 变强,server 让生态离不开 Blink。两个都做,但 **server 才是 Blink 在 AI 时代的独特位置**。

### 3.3 MCP server 的 Capability 投影

0.9.7 已备 `CapabilitySchema → rmcp` 投影路径。0.12 落地时:

- `CapabilitySchema` → `rmcp::model::Tool`(schema 纯 JSON Schema,零摩擦)
- `Capability::invoke()` → MCP tool handler(协议层 `invoke(Value) → Result<Value, Error>`)
- `CapabilityResult` → MCP result(0.11 统一结果模型的四变体投影成 MCP 响应格式)

**★ sensitive 字段授权(0.11 铺路)**:0.11 给 CapabilitySchema + manifest `tools[]` 加了 `sensitive` 字段。0.12 MCP server 暴露时:
- `sensitive=false` 的 Capability(如 `search_files`)默认可暴露
- `sensitive=true` 的 Capability(如 `search_clipboard_history` / `read_clipboard`)需用户在设置页显式授权"允许暴露给外部 Agent"
- 未授权的 sensitive Capability 不进 MCP server 的 tool 列表

**0.11 不做权限强制但铺字段,0.12 落地时不用回头改所有 Capability**——这是 0.11 → 0.12 的关键衔接。

### 3.4 MCP server 暴露的能力清单(候选)

| 本地能力 | MCP tool 名 | sensitive | 说明 |
|---|---|---|---|
| 全局划词(selection) | `get_selection` | true | 读用户当前选中文本 |
| 当前剪贴板 | `read_clipboard` | true | 读剪贴板当前内容 |
| 剪贴板历史 | `search_clipboard_history` | true | 检索剪贴板历史 |
| 前台应用 | `get_foreground_app` | false | 获取前台应用进程名+窗口标题 |
| 截图 | `capture_screen` | false | 截取屏幕(全屏/区域) |
| 应用搜索 | `search_apps` | false | 搜索开始菜单应用 |
| 文件搜索 | `search_files` | false | 搜索本地文件 |
| 打开路径 | `open_path` | false | 打开文件/应用/URL |
| 资源管理器定位 | `reveal_in_explorer` | false | 在资源管理器中显示文件 |

具体暴露哪些由用户在设置页勾选(默认只开 `sensitive=false` 的)。

## 四、A2A(优先级最低)

「本地唤起其他 Claude / 更智能客户端接管内容」——价值最薄(用户为什么不直接开 Claude 客户端?),优先级最低。视 MCP 生态成熟度决定是否做。

**若做**:A2A 本质是"把 Blink 的上下文(选中文本/截图/剪贴板)推给另一个 Agent 接管"。这与 MCP server 的"暴露本地能力"有重叠——MCP server 做好后,A2A 只是"主动推送 vs 被动调用"的交互差异。0.12 先做 MCP,A2A 视 MCP 落地后的用户反馈决定。

## 五、VectorRouter 真正归宿:RAG / 记忆

0.9 移出的 VectorRouter 在这里找到归宿:

- **记忆功能**:记住用户历史意图 / 习惯,个性化路由
- **RAG**:对本地文档库 / 笔记做语义检索,作为 AI 回答的上下文

### 5.1 embedding 生产 vs 向量存储的边界(与 0.9 选型对齐)

**关键分工**——0.9 §11.3/§11.5 已定但需在 0.12 落地时再强调:

| 层 | 技术选择 | 理由 |
|---|---|---|
| **embedding 生产** | 走 rig `EmbeddingsModel`(云端 API + 自实现本地 trait) | 复用 0.9 Provider 抽象,云端 API(OpenAI text-embedding-3-small 等)+ 本地 `all-MiniLM-L6-v2` 都能走 |
| **向量存储 / 检索** | 自写 + `sqlite-vec`(**不引** rig 的 vector store) | 贴 Awareness 域,SQLite 已有生态;rig-vector 生态跟本项目存储心智割裂 |

### 5.2 embedding 一致性约束(切模型必重建)

**向量库必须锁 embedding model_id**:向量存 `(model_id, vector)`,切 embedding Provider(维度不同 / 语义空间不同)触发重建索引 UI 提示,不隐式失效数据。

### 5.3 起步实现

- 仍用「暴力 cosine 起步」(1000 条向量内 CPU < 10ms),持久化走 SQLite BLOB;真扩到 10 万+ 再上 `sqlite-vec` 或独立向量库
- 本地 embedding 首选 `all-MiniLM-L6-v2` ~20MB,按需下载

### 5.4 RAG 与 0.11 结果回流的协同

RAG 检索结果作为 0.11 改进 2 的"Tool 消息"喂回 AI——RAG 本质是一种"内部 tool"(检索本地知识库),走同样的结果回流通道。Turn 2 的 AI 总结正好消费 RAG 上下文。

**RAG 作为内部 tool**:RAG 检索可以建模为一个 Capability(`search_knowledge_base`),进 AI tool 池。AI 判断需要本地知识时自主调用,结果走 0.11 改进 2 的回流通道。这样 RAG 不需要单独的调用路径,完全复用 0.11 铺好的链路。

### 5.5 记忆功能的设计

**记忆 vs RAG 的区别**:
- RAG = 检索本地文档库(用户主动加入的知识)
- 记忆 = 记住用户历史意图/习惯(自动积累,个性化路由)

**记忆的存储**:
- 用户每次 AI 交互的 (query, route, outcome) 摘要进 `memory` 表
- embedding 后存向量库
- 下次 AI 路由时,query 的 embedding 检索相似历史,作为 system prompt 的上下文("用户上次问类似问题时,想的是...")

**隐私边界**:记忆是敏感数据,默认关,用户显式开;用户可查看/删除/导出记忆。MCP server 暴露时 `memory_search` 标 `sensitive=true` 需授权。

## 六、单独对话窗口(Agent 窗口模式)★

### 6.1 为什么需要单独对话窗口

0.9 §2.2 预留了"Agent 窗口(0.10)开放 AgentBuilder + memory + tool loop",但 0.10 实际做的是语音输入,Agent 窗口未落地。0.12 补这个债。

**主窗口 vs 对话窗口的定位差异**:

| 维度 | 主窗口(0.9-0.11) | 对话窗口(0.12) |
|---|---|---|
| 交互 | 单轮:打字 → 结果 → 执行 | 多轮:对话 → 追问 → 深入 |
| AI 能力 | `CompletionModel` + `ToolDefinition`(类型收窄) | `AgentBuilder` + memory + tool loop |
| tool 调用 | 有限多轮(0.11 改进 2:固定 2 次 complete) | agent loop(无限轮,直到 AI 觉得完成) |
| 记忆 | 无 | 有(RAG + 记忆,§五)|
| 场景 | "打开 VSCode" / "查天气" / "翻译这段" | "帮我分析这个截图" / "整理这些笔记" / "连续调多个工具完成复杂任务" |

### 6.2 不破主窗口类型收窄铁则

0.9 §2.6 铁则:"主窗口 `AIProvider` trait 编译期没有 `AgentBuilder`"。0.12 的对话窗口**不修改主窗口的 AIProvider**——而是引入一个独立的 `AgentProvider` trait(或直接用 rig 的 `AgentBuilder`),只在对话窗口的上下文中可用。

```
主窗口 AIProvider（0.9，类型收窄）        对话窗口 AgentProvider（0.12，开放）
  ├─ kind / model_id / complete              ├─ AgentBuilder（memory + tool loop）
  └─ 无 AgentBuilder                         └─ 独立窗口，独立 SLO
```

两个 trait 共享底层 rig Client + Provider 配置,但能力面不同。主窗口仍是"快路径单轮",对话窗口是"慢路径多轮"。

### 6.3 对话窗口的核心能力

| 能力 | 说明 | 复用 |
|---|---|---|
| 多轮对话 | agent loop,AI 自主决定何时调 tool、何时回答 | rig `AgentBuilder` |
| tool loop | 无限轮 tool 调用(主窗口是固定 2 次) | 0.11 统一结果模型 + `to_rig_tool_result()` |
| memory | 对话历史 + RAG 上下文 + 用户记忆 | §五 RAG/记忆 |
| MCP tool | 可调 MCP client 消费的外部 tool | §三 MCP client |
| Skill | 可调用户生成的 skill | §二 Skill 化 |
| 截图/文件 | 可调所有 Capability | 0.9.7 Capability 层 |

### 6.4 对话窗口的入口与形态

**入口候选**(实现时定):
- 主窗口输入框输入特定触发词(如"对话 ")→ 切换到对话窗口
- 独立快捷键(如 Alt+Shift+Space)唤起对话窗口
- Chord 模式的某个手势

**形态**:独立窗口(非主窗口 overlay),有完整的对话历史展示区 + 输入区 + tool 调用可视化。不抢主窗口的焦点 SLO。

### 6.5 与 0.11 的衔接

对话窗口的 tool 调用结果投影复用 0.11 改进 1 的统一结果模型——`CapabilityResult` / `ActionOutcome::Items` 在对话窗口里渲染成"AI 已执行 XXX"的卡片,用户可展开看详情。tool loop 的每一轮结果都走 `to_rig_tool_result()` 投影回 AI(0.11 改进 2 已接通消费方,对话窗口只是把"固定 2 次"放宽为"无限次")。

## 八、验收(按做的项定)

```bash
# §一 本地模型
 设置页「下载模型」→ 进度可见 → 下完自动注册为 Provider
 或:检测到 ollama 运行 → 自动连 localhost:11434 → 模型可选
 本地模型默认开 0.11 结果回流(auto 模式)

# §二 Skill 化
 设置页「解析 CLI」→ AI 跑 --help → 生成 skill 草案 → 用户审核 → 固化
 固化后的 skill 走确定性通道(不过 AI),进 AI tool 池
 skill 结果走 0.11 统一结果模型

# §三 MCP server(护城河)
 Blink 作为 MCP server 暴露 screenshot / selection / clipboard / open_file / search_apps
 外部 Agent(Claude Desktop)能调用这些 tool
 sensitive Capability(search_clipboard_history 等)需用户授权才暴露

# §三 MCP client
 Blink 能消费外部 MCP server 的 tool,进 AI tool 池
 外部 tool 结果走统一结果模型投影

# §五 RAG/记忆
 本地文档加入知识库 → AI 回答时自动检索作为上下文
 用户问"我之前的笔记里有没有提到 XXX" → AI 调 search_knowledge_base
 记忆功能:用户可查看/删除历史意图记忆

# §六 对话窗口
 独立窗口,多轮对话,tool loop 无限轮
 AI 自主连续调多个工具完成复杂任务
 主窗口类型收窄铁则不破(主窗口仍无 AgentBuilder)
```

## 九、0.12 之后候选池(1.0 前的插件市场里程碑)

> 与 [0.11 §六](./0.11-plugin-ai-toolchain.md) 候选池同性质——方向正确但当前无痛点的产品化基础设施诉求,统一在 1.0-preview 插件市场里程碑落地。

### 9.1 插件 / Skill / MCP server 统一分发(合并 0.11 §6.2)

0.11 §6.2 已归档的"插件动态下载与治理",在 0.12 落地 Skill + MCP 后扩展为**三种载体的统一分发**:

- 插件(IPC 子进程)/ Skill(动态生成的 CLI tool)/ MCP server(外部 Agent 调用)在**同一问题域**(远端能力的获取/安装/更新/信任)
- 1.0-preview 应统筹:统一分发协议 / manifest 版本兼容矩阵 / 签名校验 / 权限强制模型 / 国内镜像

### 9.2 result item 支持继续对话(合并 0.11 §6.1)

0.11 §6.1 已归档。0.12.4(对话窗口)落地后,"继续对话"的痛点会被对话窗口吸收一部分——用户在对话窗口里天然能追问。主窗口的 result item "继续对话"按钮可视 0.12.4 后的用户反馈决定是否还需要。
