# Blink 0.11 — 插件通信契约重设计 + AI 调用插件链路完善

> **范围**:修补 0.9.3 Agent 框架的 tool-call 通信契约(主线)+ 补 AI tool 池缺口(应用搜索 / 剪贴板历史 Capability)+ builtin 插件全 Rust 化(翻译插件)。
>
> **主题**:0.9.3 跑通了"插件能被 AI 调用"的骨架,但结果回流 / 元信息 / 提示词三块不严谨,导致"查 IP 只拿到局域网值""查天气拿到城市名""AI 打不开应用"等问题。0.11 系统性清这笔债,让 AI 调用插件的链路真正可用。
>
> **前置**:0.10 完成。
>
> **原则**:tool-call 契约改不破四域墙;有限多轮不破类型收窄铁则(仍是固定次数 complete,不是 agent loop);builtin 插件零 Python 依赖。
>
> **0.12 分流**:本地模型 / skill 化 / MCP 双向 / A2A / RAG 记忆 / 单独对话窗口等 AI 生态完善项,见 [0.12-ai-ecosystem.md](./0.12-ai-ecosystem.md)。

## 一、问题诊断

> 0.9.3 跑通了"插件 tool-call 注册 → AI 调用 → 执行"骨架,但结果处理链路有四个实锤 bug + 一个 tool 池缺口。本节是 0.11 主线的动机。

### 1.1 问题 A:结果列表被截断——"查 IP 永远只拿到局域网值"

`PluginActionAdapter::execute()`(`src/domain/plugin/action.rs:113-138`)拿到插件返回的 `Vec<PluginItem>` 后,**只取第一项**:

```rust
let first = &items[0];          // ← 只取第一项,其余丢弃
let text = first.title.clone();
```

IP 插件实际返回 3 项(本地 IPv6/IPv4、公网 IP),按 score 排序后 `items[0]` 恰好是**本地 IPv4**——所以 AI 调 `get_ip` 永远只拿到局域网地址。

**根因**:`ActionOutcome` 是单结果语义(`Copy`/`Open`/`Emit`/`Nop`),承载不了列表;`PluginActionAdapter` 被迫截断。

### 1.2 问题 B:结果语义混淆——"查天气拿到城市名"

天气插件(`plugins/builtin/weather`)的结果项:

```rust
let title = format!("{city_name} {temp_str} {desc}");  // "北京 25°C 晴"
let action = PluginAction::Copy { text: city_name };    // "北京"  ← 复制的是城市名!
```

`PluginActionAdapter` 优先取 `Copy.text`(城市名"北京")而非 `title`("北京 25°C 晴")。于是 AI tool-call 展示的是"北京",天气数据丢了。

**根因**:`PluginItem` 设计于 0.2 的**查询路径**(用户打字→展示 title、回车执行 action)。`Copy.text=城市名` 在查询路径合理,但 tool-call 路径语义完全不同——AI 要的是**天气数据**。`PluginItem` 没有 `payload`(结构化数据)字段,display 语义和数据语义焊死在一起。对比 `CapabilityResult::Items`(0.9.7 落地)的 `ItemResult`——它有独立 `payload: Value` 字段,"前端展示用 title/subtitle,AI 读 payload",两套消费分离。**Capability 的结果模型比 Plugin 的更正确**。

### 1.3 问题 C:AI 看不到工具结果——单轮直通,无结果回流

主窗口 AI 路径是单轮直通(`service.rs::handle_ai_tool_calls`):

```
用户打字 → AI completion(带 tools) → tool_calls[0]
  → resolve → Action.execute() → ActionOutcome
  → ai_action_done_entry(outcome) → emit 前端 → 结束
```

AI 调完工具就"下班"了,**结果直接 emit 前端,AI 看不到**。这意味着:AI 无法判断"IP 插件返回了 3 个,公网那个最有用,我给你总结一下";无法对天气结果补充"今天有雨,记得带伞";无法在工具失败时自动换参数重试。

0.9.7 已为此铺路:`CapabilityResult::to_rig_tool_result()` 投影函数已就绪(注释写明"0.10 multi-turn 消费"),但主窗口路径**至今未接通**——投影函数定义了却没调用方。

### 1.4 问题 D:工具元信息不友好 + 提示词硬编码

- **D1 系统提示词硬编码**:`build_routing_prompt()`(`service.rs:1288`)是硬编码字符串内联在 SearchService 里。无统一管理模块,插件无法贡献 prompt hint,用户无法配置。
- **D2 参数 schema 不动态注入配置**:天气插件 manifest 声明 `"required": ["city"]`,但插件代码实际支持回退到 `settings.default_city`。AI 看到 `city` 是 required,**被迫追问用户"查询什么城市"**——即使用户已经配了默认城市。
- **D3 无结果类型声明**:AI 不知道 `get_ip` 返回单文本还是列表;`get_weather` 返回的 title 里塞了"城市 温度 天气"三段信息,AI 无法预知结构。缺 `result_type` 元数据。
- **D4 工具列表只给 name+description**:`build_routing_prompt` 给 AI 的工具列表只有 `"- {name}: {description}"`,不含参数摘要。弱模型容易调错参数。

### 1.5 问题 E:AI 打不开应用——应用搜索引擎未进 tool 池

**用户反馈**:"我让 AI 帮我打开某个 app,他似乎不会调用应用搜索然后用 open Action 打开匹配程度最高的。"

现状盘点(`build_aggregated_tools` 三源):

| 来源 | 能否帮 AI 打开应用 |
|---|---|
| 内置 Action(`file_action` 含 `open_path`) | ❌ 需要完整 path,AI 不知道 |
| 插件 tool | ❌ 无 |
| Capability `search_files`(FileEngine) | ❌ 搜文件不搜开始菜单应用 |
| **StartMenuEngine** | ❌ **未进 tool 池——这就是缺口** |

AI 要么放弃(回退文本"我没法打开应用"),要么瞎猜路径(失败)。要满足用户"打开 VSCode"的诉求,需要两步:**①补应用搜索 tool**(search_apps Capability)让 AI 能查到应用路径;**②允许 AI 链式调用**(search_apps → open_path)让 AI 能自动打开。①是改进 5,②依赖改进 2 的 tool chain 能力。

### 1.6 内置能力 tool-call 覆盖盘点

系统性盘点所有内置功能是否进 AI tool 池:

| 内置能力 | 进 AI tool 池? | 0.11 动作 |
|---|---|---|
| 12 个 builtin Action(lock/open_url/...) | ✅ 分组聚合为 3 tool | 无需动 |
| 插件 tool(IP/天气/翻译) | ✅ 独立 tool | 改进 1 修结果截断 |
| Capability: capture_screen / crop_image / read_clipboard / write_clipboard / search_files | ✅ | 无需动(`search_files` 实例化问题见改进 5)|
| **StartMenuEngine(应用搜索)** | ❌ | **改进 5:新增 `search_apps` Capability** |
| **ClipboardEngine(剪贴板历史)** | ❌(takeover_only)| **改进 6:新增 `search_clipboard_history` Capability** |
| CalcEngine(计算器) | ❌ | ⏸ 后置——AI 自身能算,优先级低 |
| BuiltinEngine(内置动作召回) | ❌(搜索召回,非执行)| 无需动——它是搜索召回源,Action 已进 tool 池 |
| ChordAction(截图/语音/剪贴板历史触发)| ❌ | 无需动——chord 是交互入口,截图已有 Capability 覆盖 |
| 文本注入(SendInput) | ❌ | ⏸ 后置——属于 Execution 域底层,AI 场景暂无需求 |

**结论**:0.11 补 `search_apps` + `search_clipboard_history` 两个 Capability 后,**AI tool 池覆盖所有有意义的内置能力**。

## 二、方案设计

> 九个改进,按"主线契约修复(1-4)→ tool 池补缺(5-6)→ builtin Rust 化(7)→ 抽象收敛(9)"组织。每个改进已融入技术 Review(R 方向调整 / O 优化 / M 遗漏 / A 提前铺路)与产品体验(P 系列)的结论。

### 2.1 改进 1:统一结果模型——插件结果对齐 CapabilityResult

**核心思路**:`PluginItem` 增加 `payload` 字段(结构化数据给 AI),`PluginActionAdapter` 不再截断——返回全量 items。

**具体改动**:

| 层 | 改动 |
|---|---|
| `protocol.rs::PluginItem` | 增加 `payload: Option<Value>` 字段(向后兼容,serde default None)|
| `protocol.rs::ToolResultPayload` | `items` 全量保留,不再只取第一项 |
| `action.rs::PluginActionAdapter` | `execute()` 返回新 `ActionOutcome::Items(Vec<ItemResult>)`,投影 PluginItem → ItemResult |
| `execution::ActionOutcome` | 新增 `Items { items: Vec<ItemResult> }` 变体 |
| `service.rs::handle_ai_tool_calls` | `ActionOutcome::Items` → `emit_ai_result_multi`(已存在)|

**投影规则**(PluginItem → ItemResult):

- `payload` 优先取 PluginItem.payload(新字段);缺失时从 action 提取(Copy→{text}, Open→{path})——向后兼容老插件
- 前端展示用 title/subtitle,AI 读 payload——两套消费分离(与 Capability 一致)

**修复效果**:IP 插件 3 个 IP 全部展示;天气插件展示"北京 25°C 晴"(title),payload 携带 `{city, temp, desc, wind_speed}` 结构化数据。

**★ 投影路径统一**(避免分叉):改进 1 引入 `ActionOutcome::Items` 后,Action 路径的 `ai_action_done_entry` 和 Capability 路径的 `capability_result_to_entries` 是两套投影逻辑,必须统一。抽 `items_to_entries(items: &[ItemResult]) -> Vec<AppEntry>` 公用函数,两条路径都调它。避免"插件 Items 走 A 路径、Capability Items 走 B 路径"。

**★ emit 关联 tool_call_id**(审计骨架):`ActionOutcome::Items` 的 emit 加上 `tool_call_id` 关联,为改进 2 的回流 + 审计日志铺路。

### 2.2 改进 2:结果回流 AI(有限多轮 + 有限 tool chain)★

**核心思路**:tool 执行后,结果投影成 `Tool` 消息喂回 AI,AI 做第二轮 completion——既能总结结果(天气→"今天有雨记得带伞"),也能链式调 safe tool(search_apps→open_path)。

#### 2.2.1 两轮 complete 协议

```
Turn 1: complete(messages=[system, user], tools=[all])
       → tool_call_1
       → execute → result_1

Turn 2: complete(messages=[system, user, assistant(tool_call_1), tool(result_1)], tools=[safe_only])
       → 分三种情况:
         (a) text answer → emit 文本回答(总结),结束
         (b) tool_call_2(safe tool) → execute → emit 执行结果,结束
         (c) tool_call_2(dangerous tool) → emit 确认卡片,结束
```

**为什么不违反类型收窄铁则**:0.9 铁则是"主窗口 `AIProvider` trait 编译期没有 `AgentBuilder`"。有限多轮只是**调用固定次数 `complete()`**,不引入 agent loop / prompt / memory。

**关键设计**:Turn 2 `tools=[safe_only]`(非空)——支持 `search_apps → open_path` 链式调用:
- Turn 2 允许 AI 再调一次 **DangerClass::Safe** 的 tool(如 `open_path`),实现 tool chain
- Dangerous tool 在 Turn 2 不自动执行,降级为确认卡片(用户 Enter 才执行)
- **固定上限**:最多 2 次 complete + 1 次 tool 执行。Turn 2 产 tool_call 时执行后直接 emit 结束(不再有 Turn 3 总结)——牺牲一次总结换 SLO 可控;Turn 2 产 text 时就是总结,结束

**满足的场景**:
- `search_apps`(Turn 1)→ `open_path`(Turn 2)→ emit "已打开 VSCode" ✅
- `get_weather`(Turn 1)→ Turn 2 总结"北京 25°C 晴,记得带伞" ✅
- `get_ip`(Turn 1)→ Turn 2 总结"你的公网 IP 是 xxx" ✅
- `lock`(Turn 1,dangerous)→ 走确认卡片(现状不变)✅

#### 2.2.2 三态配置(provider 类型区分)

| 配置项 | 默认 | 说明 |
|---|---|---|
| `ai_tool_result_feedback` | `auto` | `auto`=本地模型开 + 云端模型关;`on`=始终开;`off`=始终关(单轮直通,快) |

✅ **已决策(D2)**:默认保留 `auto`。云端模型省 token(多一次 complete 加 500-1500ms + token 成本),本地模型零成本推理正好适合 Turn 2。体验不一致靠设置页说明缓解(见 §3.7)。开了之后 Turn 2 有独立超时预算(从总预算派生)。

#### 2.2.3 回流内容投影

| 结果类型 | 投影为 Tool 消息内容 |
|---|---|
| `CapabilityResult::Text` | 原文 |
| `CapabilityResult::Items` | JSON 序列化(`to_rig_tool_result()` 已就绪)|
| `PluginActionAdapter` 全量 items | 投影成 Items 格式 JSON |
| `ActionOutcome::Items`(新) | 同上 |
| `ActionOutcome::Copy/Open` | 对应字段 JSON |
| `CapabilityResult::Blob` | 摘要"已获取 {mime} {size}"(不喂原始字节,省 token)|
| `CapabilityResult::Done` | summary 文本 |
| 执行错误 | `"错误: {message}"`——AI 可据此道歉/换方案 |

#### 2.2.4 Turn 2 system prompt 增量

新建 `ai/prompt.rs::tool_result_feedback_prompt()`:

```
你刚才调用了工具,以下是工具返回的结果。
请基于结果用自然语言回答用户,不要简单复述原始数据。
如果结果包含多项,挑用户最可能关心的总结;用户想看全部时可提示"按 ↓ 查看完整列表"。
若需要执行后续操作(如打开搜到的应用),可调用安全工具;危险操作需用户确认。
若工具返回错误,请用自然语言解释错误原因,并给出用户可操作的修复建议
(如"API key 未配置,请到设置页 AI tab 配置天气插件密钥")。不要只说"失败了",要让用户知道下一步怎么办。
```

#### 2.2.5 结果排布与前端交互(AI 总结 ≠ 工具结果,不混排)

**新情况**:Turn 2 可能同时产出"AI 总结文本"和"工具结果 items"。关键决策:**AI 总结 ≠ 工具结果,两者不混排**。

| 情况 | Turn 2 产出 | 前端展示 |
|---|---|---|
| **A. 纯总结**(天气/IP) | text answer | **单条 `.ai-item`**(总结文本,pre-wrap 撑开)。工具结果不展示(AI 已消化)|
| **B. 纯 tool chain**(打开应用) | tool_call_2(safe) | **单条 `.ai-item`**(执行结果,如"已打开 VSCode")。Turn 1 中间结果不展示 |
| **C. 总结 + 原始列表** | text answer + display_items 信号 | **item[0] = AI 总结**(pre-wrap 撑开) + **item[1..] = 工具 items**(普通 nowrap 单行)|

**AI 不挑 a/b 展示,AI 只产总结;列表要么全展要么不展**——AI 挑选意味着 AI 要输出"选哪些"的结构化指令,引入新协议复杂度 + 违背"AI 当编译器不当运行时决策者"。0.x 阶段取"全展或不展"二元策略。AI 挑选留 1.0 的 `display_results` 显式 tool(§6.1)。

**首席位(item[0])永远归 AI**:

```
Turn 2 产 text → item[0] = AI 总结(pre-wrap 撑开)
              → 若 display_items 信号,item[1..] = 工具 items(nowrap 单行)

Turn 2 产 tool_call(safe) → item[0] = 执行结果("已打开 VSCode")
                         → 不展示 Turn 1 中间结果

回流关闭(off) → item[0..] = 工具 items(现状,与 0.9.7 一致)
              → 无 AI 总结(单轮直通)
```

**前端交互调整**:

| 项 | 现状 | 改进 2 后 |
|---|---|---|
| item[0] 弹性撑开 | 单条 AI 文本独占,pre-wrap 自然多行 | **保留**:AI 总结仍是 item[0],仍 pre-wrap 撑开 |
| item[1..] | 不存在(AI 只一条) | **新增**:工具 items 跟在总结后,用普通 nowrap 单行样式(非 `.ai-item`),靠 `source` 区分 |
| 键盘导航 | ↓ 翻页 | 保留:↓ 从总结跳到第一个工具 item |
| 回车行为 | 复制 AI 文本 | item[0] 回车=复制总结;item[1..] 回车=执行各自 action |

#### 2.2.6 tool chain 安全边界

Turn 2 允许调 safe tool,但需明确"safe tool 也可能有害"(如 open_url 打开恶意网址):
- Turn 2 的 safe tool 链式调用仍 emit 执行结果给用户可见(**不静默**)
- `open_path` 在 Turn 2 保持自动执行(用户已明确要"自动打开")
- `open_url` 在 Turn 2 降级为"需确认"(防止打开恶意网址)
- 自动执行后的反馈规范见 §3.6

✅ **已决策(D4)**:`open_path` 在 Turn 2 自动执行,不加确认卡片——用户已明确要"自动打开",加确认退化体验。结果项明确告知"AI 自动打开"(见 §3.6)。

#### 2.2.7 审计日志

回流通道天然记录 tool_call + result,写入 `ai_tool_audit` 表(字段:tool 名 / 参数 / 结果摘要 / 时间戳 / provider)。用户在设置页可查"AI 最近调了哪些工具"。0.9.7 CapabilityRegistry::invoke 已有 SLO 埋点,在此基础上补审计字段。

#### 2.2.8 "2 轮"语义澄清

改进 2 的"有限 2 轮"是 **AI 内部**的 2 次 complete 调用,不是用户的多轮对话:

| 概念 | 是什么 | 0.11 支持? |
|---|---|---|
| **AI 内部多轮**(tool chain) | Turn 1 调工具 → 结果回流 → Turn 2 AI 再调工具或总结 | ✅ 0.11.4 支持 |
| **用户多轮对话**(追问) | 用户问"查 IP"→ 拿到结果 → 用户再问"item2 这个地址的天气" | ❌ 0.11 不支持,0.12 对话窗口 |

**为什么 0.11 不支持用户多轮**:主窗口是**无状态单轮**模型——每次 `Alt+Space` 唤起是一次独立交互,无对话历史(0.9 类型收窄铁则:`AIProvider` 只有 `complete()`,无 memory/session)。用户多轮需要对话上下文持久化,是 0.12 对话窗口(Agent 窗口模式)的职责。0.11 的 Turn 2 上下文是**单次请求内**的,请求结束即丢弃,不跨 `Alt+Space` 唤起。

**0.11 的过渡方案**:用户分两步(两次唤起)实现"查 IP → 问那个地址天气":
1. `Alt+Space` 输入"查 IP" → AI 调 get_ip → 展示 IP 列表
2. 用户看到 item[2] 是公网 IP → 复制 → 再次 `Alt+Space` 输入"查 {那个地址对应城市} 的天气" → AI 调 get_weather

这是"手动多轮",不如对话窗口顺滑,但 0.x 阶段够用。

### 2.3 改进 3:工具元信息增强

#### 3a manifest `tools[]` 新增字段

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `result_type` | `"text"` / `"items"` / `"done"` | 声明返回类型,帮 AI 预期 + 帮 lane 投影 | `"items"` |
| `hint` | `string`(可选) | 给 AI 的额外提示,自动拼入 system prompt | `"返回多个 IP,公网 IP 通常最有价值"` |
| `examples` | `array`(可选) | 示例调用,帮弱模型理解;0.11 默认不拼入 system prompt,0.12 本地模型模式注入 | `[{"city":"北京"}]` |
| `sensitive` | `bool`(可选,default false) | 声明敏感(读隐私数据)——0.12 MCP server 暴露时需授权 | `true` |
| `progress_hint` | `string`(可选) | 占位文案提示词,拼成 `AI 正在{progress_hint}…`(见 §3.2) | `"查询天气"` |

向后兼容:新字段全部 serde `default`,老 manifest 不受影响。

✅ **已决策(D1)**:新增 `progress_hint` 字段。3 个 builtin 插件 + 2 个新 Capability 填,成本低,文案质量高。缺失时回退到 description 前 8 字 + `…`。

✅ **权限模型铺垫**:0.11 不做权限强制,但 CapabilitySchema + manifest `tools[]` 预留 `sensitive: bool` 字段(default false)。`search_apps`/`search_clipboard_history` 标 `sensitive=true`;0.12 MCP server 暴露时敏感 Capability/插件 tool 需用户显式授权。

#### 3b 参数 schema 动态注入配置

构建 AI tool schema 时,若某参数对应插件 setting 已配置,动态调整:
- **required → optional**:weather `city` 在 `default_city` 非空时从 required 移除
- **注入 default**:`default_city="北京"` → city 参数加 `"default": "北京"`
- **description 增强**:自动追加"(默认:{default_city})"
- **enum 动态注入**:天气 `unit` 参数若用户配置了 `temperature_unit`,注入为 enum 的默认值

**★ 签名变化**:`build_aggregated_tools(registry, cap_registry)` 当前不持有 PluginEngine 引用,读不到 settings。调整为 `build_aggregated_tools(registry, cap_registry, plugin_engine)`,或抽 `inject_plugin_settings(schema, settings) -> ActionSchema` 投影函数在调用方做。这是**投影层**改动,不动 manifest 原文。

#### 3c 天气插件 manifest 修正

当前 `"required": ["city"]` 改为不 required(插件代码本就支持空 city 回退 default_city),description 补"不传时用配置的默认城市"。配合 3b 动态注入,AI 在有默认城市时不再追问用户。

### 2.4 改进 4:提示词统一管理

**新建 `src/domain/ai/prompt.rs`**:

| 函数 | 职责 |
|---|---|
| `routing_system_prompt(tools, lang)` | 主窗口路由 system prompt(从 service.rs 迁出)|
| `tool_result_feedback_prompt(lang)` | Turn 2 结果回流 system prompt(改进 2)|
| `tool_list_section(tools)` | 工具列表文字段(含 name + description + 参数摘要)|

**工具列表增强**(D4 修复):文字版工具列表从 `"- {name}: {desc}"` 升级为含参数摘要:

```
- get_weather: 查询指定城市天气。参数: city(城市名,可选,默认用配置城市), unit(温度单位)。返回: 多个 IP（本地+公网）
- get_ip: 获取本机 IP 信息。参数: include_ipv6(是否含 IPv6)。返回: 多个 IP（本地+公网）
- search_apps: 搜索本机应用。参数: query(应用名), max_results(可选)。返回: 应用列表,含路径
```

**插件贡献 prompt hint**:manifest 的 `tools[].hint` 字段(改进 3a)自动拼入 system prompt 的工具描述段——插件作者能用一句话告诉 AI 这个工具的用法窍门。

**配置化**:system prompt 模板存 `AIConfig`(高级设置 tab),用户可自定义。0.x 阶段先给"恢复默认"按钮,不做富文本编辑器。

**token 成本控制**(见 §3.8):工具描述走"分层详略"——system prompt 文字段只含 name + 一句话 description + 参数名(不含 schema,~30 token/工具);完整 JSON Schema 走 `tools` 协议字段(~100 token/工具,协议层不计入 system prompt);`examples` 默认不拼,0.12 本地模型模式注入。每次构建 system prompt 用 `tiktoken-rs` 估算 token 数,超 1500 token `tracing::warn!` 告警;设置页 AI tab(高级)展示当前 system prompt token 数。

### 2.5 改进 5:应用搜索 Capability(`search_apps`)★

**问题**:AI 当前**调不到应用搜索引擎**(问题 E)。用户说"打开 VSCode"时 AI 无法按名字查应用路径。

**方案**:新增 `search_apps` Capability,包装 `StartMenuEngine`(与 `search_files` 包装 `FileEngine` 完全同模式)。

| 项 | 说明 |
|---|---|
| id | `search_apps` |
| 入参 | `{ "query": "vscode", "max_results": 5 }`(max_results 可选,默认 5)|
| 出参 | `Items` —— 每项 `ItemResult { title: "Visual Studio Code", subtitle: "C:\\...\\code.lnk", payload: {"path":"...","name":"...","score":0.95} }` |
| 实现 | 调 `SearchEngine::search()` trait 方法 |
| payload | `{"path": lnk_path, "name": 应用名, "score": 匹配分}` —— AI 读 payload 知道路径+置信度,用户回车走 `Open` 动作 |
| 复用 | StartMenuEngine 的缓存 + 增量扫描 + fuzzy 打分全部白嫖 |
| sensitive | ✅ true(读应用列表属隐私敏感数据) |

**★ payload 携带 score**:前端按 score 排序展示,AI 也能判断"第一条是最佳匹配"。

**★ StartMenuEngine 实例共享**:`search_files` Capability 当前自持 `FileEngine` 实例,`search_apps` 若也自持 `StartMenuEngine` 会重复扫描(StartMenuEngine 有后台预扫 + 定时刷新,重复实例浪费资源)。实现时:**Capability 不持 StartMenuEngine,通过 `AppHandle` 拿 SearchService 的引擎引用**(或抽一个共享 cache)。`search_files` 的同问题一并评估——若 FileEngine 确实无状态,可暂留,但文档记债。

**★ 与改进 2 的 tool chain 联动**:用户反馈要"自动打开匹配程度最高的",依赖改进 2 的 Turn 2 safe tool 链式调用:
- 开启回流(`ai_tool_result_feedback != off`)时:`search_apps`(Turn 1)→ `open_path`(Turn 2)→ 自动打开 ✅
- 关闭回流时:`search_apps` 返回 Items,前端展示,用户**回车打开**(与查询路径一致,零新交互)✅

两种模式都能用,区别是"自动打开"还是"回车打开"。0.11.2(应用搜索)可独立交付,0.11.4(回流)上线后升级为自动打开。

**不破四域墙**:`search_apps` 是 Capability(Execution 域),只返回数据不执行打开;用户回车或 AI 调 `open_path` 才穿过信任边界。与 `search_files` 同构。

### 2.6 改进 6:剪贴板历史 Capability(`search_clipboard_history`)

**问题**:`read_clipboard` Capability 只读**当前剪贴板**,不读历史。用户说"我刚才复制的那个链接呢"——AI 无法查剪贴板历史。

**现状**:`ClipboardEngine`(`search/clipboard_engine.rs`)持有 SQLite pool,存剪贴板历史,走 `SearchEngine` trait。但它是 `takeover_only = true`——只在 keyword 命中("剪贴板"/"clip")时工作,**不在 AI tool 池**。

**方案**:新增 `search_clipboard_history` Capability,包装 `ClipboardEngine` 的历史查询能力(不走 keyword 路径)。

| 项 | 说明 |
|---|---|
| id | `search_clipboard_history` |
| 入参 | `{ "query": "", "max_results": 5 }`(query 空=最近 N 条)|
| 出参 | `Items` —— 每项 `ItemResult { title: 文本片段, subtitle: 时间, payload: {"id":...,"text":...,"kind":...} }` |
| 实现 | 直接查 `clipboard` 表(与 ClipboardEngine 同表,独立查询逻辑)|
| payload | 含 clipboard id + text —— AI 可读,用户回车复制(`Copy` 动作)|
| sensitive | ✅ true(读剪贴板历史属隐私敏感数据) |

**★ 复用 ClipboardEngine 的 kind 分类**:不重写 kind 分类逻辑(text/image/file),抽 `clipboard_query` helper 供 Capability 和 Engine 共用。

**与 `read_clipboard` 的边界**:`read_clipboard` = 当前剪贴板(快,无 DB 查询);`search_clipboard_history` = 历史检索(需 DB,带 query 模糊匹配)。两者并存,AI 按场景选。

**不破四域墙**:只读剪贴板历史(Awareness 数据的持久化投影),不写入、不执行。用户回车复制才穿过边界。

### 2.7 改进 7:翻译插件全量 Rust 化(一次性 1:1 迁移)★

**问题**:翻译插件(`plugins/builtin/translate/main.py`,571 行 Python)依赖系统 Python 环境。用户没装 Python(或版本不对)翻译插件就用不了。IP/天气已是 Rust,翻译是唯一 Python builtin。

**0.10 的 uv 自管理环境不覆盖翻译插件**:uv venv 是给 FunASR(STT)用的,翻译插件走 `PluginProcess` 的系统 Python 探测,不进 uv venv。让翻译也进 uv venv 会增加依赖耦合(翻译需要的 `requests`/`hmac` 等进 venv,污染 STT 环境)。

**方案**:翻译插件全量 Rust 化,走 xtask 编译流水线(与 IP/天气同模式)。✅ **用户反馈:一次性改造,1:1 完整迁移,不分批**——5 个引擎(tencent/ali/baidu/youdao/deepl)全部迁移到同一个 Rust 二进制,功能对齐,除非发现隐藏 bug 才修。

| 项 | 说明 |
|---|---|
| 源码位置 | `plugins/examples/translate/`(Cargo.toml + src/main.rs + 5 引擎模块)|
| 编译产物 | `blink-plugin-translate.exe` → `plugins/builtin/translate/bin/` |
| manifest 改动 | `runtime.type` 从 `python` 改 `process`,`exec` 从 `./main.py` 改 `./bin/blink-plugin-translate.exe` |
| 依赖 | `serde` / `serde_json` / `reqwest`(已有 workspace 依赖)/ `hmac` / `sha2` / `base64` / `chrono` / `urlencoding` |
| 引擎实现 | 5 个引擎(tencent/ali/baidu/youdao/deepl)各一个模块,HMAC 签名用对应 crate |
| HTTP 代理 | **复用插件 HTTP 代理协议**(`http_request` → core 代发),与 IP/天气一致——Rust 插件不直接联网,统一代理 + 超时 + 重试 |
| 降级顺序 | 保留 `fallback_order` 设置项,1:1 对齐 Python 版 |
| 配置迁移 | manifest 版本号 +1;settings schema 不变则零迁移;启动时检测旧配置自动兼容 |

**架构收益**:builtin 插件**全 Rust 化**,无 Python 依赖。0.10 的 uv venv 专属 STT,职责清晰。

✅ **已决策(D6)**:翻译插件 AI tool 路径 `result_type = "text"`——返回首选引擎译文,降级链已处理失败。多引擎对比留查询路径。

**双路径返回**:
- **查询路径**(用户打字"翻译 hello"):返回多引擎 items(tencent / ali / baidu 各一条),用户对比选最佳——现状不变
- **AI tool 路径**(AI 调 translate 工具):返回 text(首选引擎译文),AI 拿到直接用。Turn 2 可总结"翻译结果:Hello"或直接展示译文

### 2.8 改进 9:搜索型 Capability 抽象（✅ 已评估，决定不抽）

`search_apps` / `search_files` / `search_clipboard_history` 都是 `query → Items` 模式,包装各自的 `SearchEngine` 实现。可抽共同 trait:

```rust
trait SearchCapability: Capability {
    fn engine(&self) -> &dyn SearchEngine;
    fn item_title(&self, item: &SearchItem) -> String { item.title.clone() }
    fn item_subtitle(&self, item: &SearchItem) -> Option<String> { item.subtitle.clone() }
    fn item_payload(&self, item: &SearchItem) -> Value { /* 默认从 action 提取 */ }
}
```

**0.11 取舍**:先不抽 trait,`search_apps` 直接复制 `search_files` 模式。等 `search_clipboard_history`(第三个搜索 Capability)落地时再抽——**三次重复才抽象**,避免过早设计。

**✅ 0.11.5 评估结论**:`search_clipboard_history` 落地后评估,决定**不抽 trait**:
- 三者数据获取方式差异太大:`search_files` 自持 `FileEngine` / `search_apps` 通过 `AppHandle` 共享 `StartMenuEngine` / `search_clipboard_history` 直接查 DB
- 共同逻辑仅 deadline 检查 + 入参解析几行,抽 trait 价值有限
- `fn engine(&self) -> &dyn SearchEngine` 不适用——`search_clipboard_history` 不走 `SearchEngine` trait
- 记债:等第四个搜索 Capability 出现时再评估

**★ payload 统一格式**:0.11.5 落地时采取**弱统一**——各 Capability 在 `schema().description` 里描述 payload 结构(path/name? text/id?),配合 `result_type` 字段让 AI 预知结构。不强制统一 payload 字段名（各场景语义不同:文件路径 vs 应用路径 vs 剪贴板文本）。

## 三、产品体验设计规范

> 本节集中定义 0.11 AI 路径的产品体验规范——视觉语言、占位文案、结果排布、错误展示、过渡态、token 控制。实现时按本节执行,确保各版本产品体验一致。各规范的归属版本见 §4。

### 3.1 AI 结果项视觉语言(三种形态)★(0.11.0)

AI 路径的结果项分三种形态,用 `AppEntry` 标记位区分,前端按标记加不同样式:

```
┌─────────────────────────────────────────────────┐
│ [AI]  北京 25°C 晴,今天有雨记得带伞           │  ← AI 总结项(item[0])
│       (pre-wrap 撑开, 24px AI 徽章)            │     is_ai_summary: true
├─────────────────────────────────────────────────┤
│ ◆  Visual Studio Code    C:\...\code.lnk        │  ← AI 工具结果项(item[1..])
│    (nowrap 单行, 12px 小号 AI 图标)            │     is_ai_tool_result: true
├─────────────────────────────────────────────────┤
│    VSCode                   C:\...\code.lnk     │  ← 普通结果项(查询路径)
│    (nowrap 单行, 无标记)                       │     两者皆 false
└─────────────────────────────────────────────────┘
```

| 形态 | 标记位 | 视觉 | 回车行为 | 场景 |
|---|---|---|---|---|
| AI 总结项 | `is_ai_summary` | `.ai-item` 完整样式(pre-wrap + 24px 徽章) | 复制总结文本 | 情况 A/B/C 的 item[0] |
| AI 工具结果项 | `is_ai_tool_result` | nowrap 单行 + 12px 小号 AI 图标 | 执行各自 action(打开/复制) | 情况 C 的 item[1..] |
| 普通结果项 | 两者 false | nowrap 单行(现状) | 执行各自 action | 查询路径结果 |

✅ **已决策(D3)**:AI 工具结果项用 12px 小号 AI 图标放 title 左侧——辨识度最好,与总结项 24px 徽章形成大小层次,不破坏现有布局。

**去重规则**:AI 工具结果项与查询路径同 key(`itemKey()`)时,保留 AI 项(可见 AI 图标,建立 AI 信任),score 取较高值。

### 3.2 占位文案规范(0.11.4)

占位文案随 AI 工作阶段动态变化,让用户感知过程:

| 阶段 | 文案模板 | 文案来源 |
|---|---|---|
| 初始(completion 发起前) | `AI 正在回答…` | 硬编码(现状) |
| Turn 1 工具执行中 | `AI 正在{progress_hint}…` | manifest `tools[].progress_hint`(D1),缺失时 description 前 8 字+`…` |
| Turn 1→Turn 2 过渡 | `AI 正在思考…` | 硬编码 |
| Turn 2 工具执行中(chain) | `AI 正在{progress_hint}…` | 同 Turn 1,Turn 2 工具的 progress_hint |
| Turn 2 流式总结 | 流式输出总结文本 | 走 `emit_ai_stream`,无占位 |
| Turn 2 超时降级 | `AI 回答较慢,已展示原始结果` | 硬编码 |

**典型流程示例**(用户输入"打开 vscode"):
```
"AI 正在回答…" → "AI 正在搜索应用…" → "AI 正在思考…" → "AI 正在打开应用…" → "已打开 VSCode"
```

**实现要点**:
- `handle_ai_tool_calls` 拿到 tool_call 后,先 `emit_ai_result` 一个占位更新(改 name 为阶段文案),再执行工具
- 不引新事件:复用 `blink://results` 的占位更新通道(改 name 即可,前端 `updateAiStream` 已支持改 name)
- `progress_hint` 字段随改进 3a 在 0.11.1 加到 manifest,0.11.4 消费

### 3.3 结果排布规则(情况 A/B/C)(0.11.4)

| 情况 | Turn 2 产出 | 前端展示 | 触发条件 |
|---|---|---|---|
| **A. 纯总结** | text answer | item[0] = AI 总结(pre-wrap) | 默认(AI 消化了工具结果) |
| **B. 纯 tool chain** | tool_call(safe) | item[0] = 执行结果("已打开 VSCode") | AI 链式调 safe tool |
| **C. 总结 + 列表** | text + display_items 信号 | item[0] = 总结 + item[1..] = 工具 items(nowrap) | AI 主动要求展示全量 |

**首席位(item[0])永远归 AI**:Turn 2 产 text → 总结置顶;Turn 2 产 tool_call → 执行结果置顶。工具原始数据跟在后面(情况 C)或不展示(情况 A/B)。

**上限**:item[1..] 最多 5 条工具 items(D5),超出展示文字项 `还有 N 条结果,按 ↓ 查看全部`。AI 总结项不计入上限。Capability `max_results` 默认 5(search_apps / search_clipboard_history),从源头限制 AI 拿到的结果数,省 token。

✅ **已决策(D5)**:AI 路径工具 items 上限 5 条 + 文字提示("还有 N 条,按 ↓ 查看全部")。与查询路径 PAGE_SIZE 9 有区分,AI 更聚焦。

### 3.4 过渡态 UX 规范(0.11.4)

Turn 1→Turn 2 之间的过渡态,**Turn 1 结果不提前 emit**,用户全程看占位文案变化:

```
Tab → "AI 正在回答…"(0.2s)
  → tool_call → "AI 正在查询天气…"(工具执行 0.5-1s)
  → 回流 → "AI 正在思考…"(Turn 2 completion 1-2s)
  → 完成 → 流式总结 或 一次 emit 执行结果
```

**Turn 2 流式策略**:
- text(总结):流式输出(`emit_ai_stream`)——与 0.9 AI 文本回答体验一致
- tool_call(chain):不流式,执行后一次 emit

**为什么 Turn 1 结果不 emit**:Turn 1 结果是"中间产物"(如 search_apps 的应用列表),只有 Turn 2 完成后才确定要不要展示给用户(情况 A 不展 / 情况 C 展)。提前 emit 再替换会造成视觉跳变。用户通过占位文案变化已知道 AI 在工作。

**超时降级**:Turn 2 超时 → 占位变 `AI 回答较慢,已展示原始结果` + Turn 1 结果直接 emit(单轮直通形态)。用户不白等。

### 3.5 错误展示规范(0.11.4)

错误场景走"情况 C"变体——AI 总结 + 原始错误,两者皆橙色:

```
┌─────────────────────────────────────────────────┐
│ [AI]  天气查询失败,可能是 API key 未配置      │  ← item[0] AI 总结(橙色 .ai-item)
├─────────────────────────────────────────────────┤
│ ⚠ 401 Unauthorized — get_weather 工具调用失败   │  ← item[1] 原始错误(橙色 error-item)
└─────────────────────────────────────────────────┘
```

**Turn 2 错误处理 prompt**:AI 拿到错误后,用自然语言解释原因 + 给可操作修复建议(如"请到设置页配 key"),不只说"失败了"。prompt 已在 §2.2.4 的 `tool_result_feedback_prompt` 里。

**回流关闭时**:直接 emit 原始错误 item(橙色),无 AI 总结(单轮直通形态)。

**重试**:0.11 不支持自动重试。Turn 2 只能总结+建议。自动重试留 0.12 对话窗口。

### 3.6 自动执行反馈规范(0.11.4)

Turn 2 自动执行 safe tool(`open_path` 等)后,结果项明确告知,不静默:

| 场景 | item[0] | description | 回车行为 |
|---|---|---|---|
| 自动打开应用 | `已打开 VSCode` | `AI 自动打开 · 如非预期可手动关闭` | 聚焦到该应用窗口 |
| 自动复制 | `已复制到剪贴板` | `AI 自动复制` | 无(已复制) |

不加确认卡片(D4)——用户已明确要"自动打开",加确认退化体验。

### 3.7 回流开关体验一致性(0.11.4)

`ai_tool_result_feedback` 三态(`auto`/`on`/`off`,D2)导致不同 provider 体验不同。缓解:

- **云端关闭回流时**:工具 items 的 description 追加 `(原始数据,可开启回流获得 AI 总结)`
- **设置页 AI tab**:回流开关旁说明 `开启后 AI 会总结工具返回的结果。本地模型默认开(零成本),云端模型默认关(省 token)。可手动切换`
- **0.11.4 实现时**:三个配置项放一起,让用户一眼看到因果关系

### 3.8 token 成本控制(0.11.3)

工具描述走"分层详略",控制 system prompt 体积:

| 层 | 内容 | 位置 | token 成本 |
|---|---|---|---|
| **system prompt 文字段** | name + 一句话 description + 参数名(不含 schema) | `tool_list_section()` 生成 | 低(~30 token/工具) |
| **rig tools 协议字段** | 完整 JSON Schema(参数类型/required/enum) | `tools` 参数传给 complete | 中(~100 token/工具,协议层不计入 system prompt) |
| **examples** | 示例调用 | 默认不拼;0.12 本地模型模式下注入 | 高(每个 example ~50 token) |

**token 监控**:
- 0.11.3 实现时:每次构建 system prompt 用 `tiktoken-rs` 估算 token 数,`tracing::warn!(tokens=N, "system prompt 超过 1500 token")` 告警
- 设置页 AI tab(高级)展示当前 system prompt token 数,让用户感知
- 0.12 本地模型上线前,确保 system prompt < 1500 token(留足 context 给对话)

## 六、未来扩展(1.0 候选)

> 这里存放**方向正确但当前无痛点**的产品化基础设施诉求。0.x 阶段不做(CLAUDE.md §6 铁则「产品化基础设施 1.0 前不做」),等 0.12 生态验证 + 用户量起来后统一在 **1.0-preview 插件市场** 里程碑落地。

### 6.1 result item 支持继续对话

**用户诉求**:改进 2 落地后,result item 后续可扩展"继续对话"能力——AI 结果项带"追问"入口,点击后以该结果为上下文开启多轮。

**方向评估**:✅ 正确。这是"AI 自主决定展示什么 + 用户可深挖"的终极形态,是 `display_results` 显式 tool 的前置。

**为什么放 1.0 前**:
- 需要前端较大改动(结果项交互模型升级)+ 交互设计验证
- 与 1.0-preview 插件市场的"结果项 action 多样化"(追问/收藏/RAG)同一问题域
- 0.x 阶段改进 2 的"Turn 2 文本总结 + tool chain"已能覆盖 80% 场景;若 0.11.4 上线后"追问"诉求强烈,0.12 做轻量版(前端加"基于此结果继续问"按钮,复用 Turn 2 通道),不必等 1.0

**1.0 候选方向**:
- **result item 携带"追问"入口**:AI 结果项可带"继续问"按钮,点击后以该结果为上下文开启多轮
- **`display_results` 作为显式 tool**:AI 显式调用 `display_results(items[])` 把结构化列表推给前端,文本回答走另一通道——这是"AI 自主决定展示什么"的终极形态
- **result item action 多样化**:不只是 Copy/Open,可带"追问""收藏到笔记""加入 RAG"等动作

### 6.2 插件动态下载与治理

**用户诉求**:安装包不带插件,插件目录用户可管理;设置页从仓库拉取列表 → 用户点击下载安装。既减小安装包,也把插件治理权还给用户。

**方向评估**:✅ 正确。Raycase / uTools / Alfred 都这么做,长期必然要走这一步。

**为什么放 1.0 前**:
- 撞 CLAUDE.md §6 铁则(「插件市场 1.0 前不做」)
- 会连锁拉出:仓库托管 / 签名校验 / 版本兼容矩阵 / 更新机制 / 失败恢复 / 国内网络镜像——每一条独立看不重,加起来就是完整的产品化基础设施
- 与 0.12 MCP 双向、skill 化在**同一问题域**(远端能力的获取/安装/更新/信任),应合并到 1.0-preview 一起做基建,一次搭跑三种载体
- 当前**无实际痛点**:0.x 无分发压力、无用户抱怨安装包大、插件数 < 10 还没到需要"管理"的规模

**1.0-preview 插件市场里程碑应统筹的能力**:
- 插件 / skill / MCP server 的统一分发协议(哪里托管、如何索引、如何签名)
- manifest 版本升级 + 兼容矩阵
- 更新机制(手动 / 后台检查 / 增量)
- 权限强制模型(下载来源可信度、能力声明与用户授权)
- 国内网络镜像方案

**0.x 阶段允许的过渡小步**(不引入下载机制,零风险):
- 插件目录改为 `%APPDATA%\blink\plugins\` 优先于安装目录 → 用户手动拖 zip 也能装
- 设置页加"打开插件目录"按钮 → 让用户感知插件是可管理的,顺带验证"用户是否真会自己装插件"的假设

这两步任何小版本都可做,不阻塞主线。
