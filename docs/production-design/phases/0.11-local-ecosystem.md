# Blink 0.11 — 本地化与生态扩展(本地模型 / skill / MCP / A2A)

> **范围**:本地模型按需下载 + skill 化(配置期 CLI 探索)+ MCP 双向 + A2A(视情况)+ VectorRouter 真正归宿(RAG / 记忆)
>
> **主题**:打磨 Agent 框架,接入更大生态。这是「按需增强」版本——每一项都是可选附加,不阻塞 0.9 / 0.10 主线。
>
> **前置**:0.10 完成。
>
> **原则**:安装包保持 &lt; 100MB(本地一切按需下载);运行期不实时探索 skill(AI 当编译器不当运行时决策者);暴露本地能力(MCP server)是护城河方向。

---

## 一、定位:0.11 是「按需增强」

0.9 / 0.10 已经跑通「感知 → 路由 → 执行」完整闭环(文本 + 语音)。0.11 不再是主线演进,而是**给 Agent 框架加生态杠杆和隐私 / 离线选项**:

| 增强项 | 价值 | 是否阻塞主线 |
|---|---|---|
| 本地模型 | 隐私 / 离线 / 零成本推理 | 否,云端已够用 |
| skill 化 | 用自然方式纳入 CLI 工具 | 否,tool 已能调 |
| MCP 双向 | 生态杠杆 | 否 |
| A2A | 跨 Agent 协作 | 否,优先级最低 |
| RAG / 记忆 | 长期上下文 | 否,VectorRouter 归宿 |

每项可独立做、独立验收、独立开关。

## 二、本地模型(按需下载)

### 2.1 安装包硬约束

本地 LLM / STT / embedding 模型都偏大,**绝不捆绑进安装包**(&lt; 100MB 是硬约束,见 CLAUDE.md §2)。

### 2.2 接入方式(双源分层——与 0.9 rig 选型对齐)

本地模型有**两条独立技术路径**,语义完全不同,设置页分别呈现,不放同栏:

| 接入形态 | 库 | 类型 | 冷启动 | 内存 | 用户体验 | 推荐场景 |
|---|---|---|---|---|---|---|
| **HTTP 型 Provider**(首选) | rig `Ollama` Provider | 远程 / localhost 都可 | 快(仅 HTTP client 构造) | ~0(推理在 ollama) | 用户装好 ollama,Blink 自动连 `localhost:11434` | 已装 ollama 的用户,零改造成本 |
| **内嵌运行时** | `mistral.rs`(GGUF/UQFF) | 内嵌推理引擎 | 慢(加载模型) | 高(推理占用) | Blink 主进程内直跑,零外部依赖 | 追求单文件、离线、免装 ollama |

**为什么分两栏**:一个是网络配置(选 endpoint / model 名),一个是模型文件路径 + 加载器配置——冷启动延迟、内存占用、故障模式完全不同,合成一栏用户会踩坑。

- **HTTP 型 Provider**:core 直接依赖 rig `providers::ollama`(0.9 已引入),无额外重依赖
- **内嵌运行时**:引入 `mistral.rs` 需评估依赖体量(候选调研留 0.11 前),支持自定义模型路径 + 手动下载 GGUF / UQFF
- **自行下载 UI**:设置页「下载模型」进度可见、可暂停 / 取消;支持自定义本地模型路径

### 2.3 推理栈定位

- 本地 LLM 主要当「路由 / 轻量」档(强推理仍推荐云端主模型)
- 本地 STT 走 [0.10 §4.1](./0.10-voice-agent.md#41-接入形态与-09-rig-抽象对齐) 定型的方式:`whisper-rs` / `sherpa-onnx` + 自实现 rig `TranscriptionModel` trait
- 本地 embedding:`all-MiniLM-L6-v2` 或同级(~20MB),按需下载(详见 §六)

## 三、Skill 化(配置期探索,不是运行期)

### 3.1 设计原则:AI 当 skill 编译器,不当运行时决策者

用户思路:「指定 CLI 目录,AI 自行 `--help` 探索转 skill」。

**关键约束**:这是**配置期**能力,不是运行期:

- **配置期**:用户主动点「解析这个 CLI」→ AI 跑一次 `--help` → **生成 skill 描述草案** → 用户审核修改 → 固化为静态 skill
- 之后该 skill 走确定性快速通道(不过 AI)

**为什么不在运行期实时探索**:

- 不确定性(行为不可预测)
- 慢(每次探索)
- **信任边界**:AI 自己探索 skill 自己执行,四域墙就破了(Blink 有本地 Execution 权限,危险)

### 3.2 skill 描述复用 0.9 schema

生成的 skill 描述直接走 0.9 的统一能力 schema(`name / description / parameters / exec`),对 Blink 来说和 builtin / 插件是同一种 tool。

## 四、MCP 双向(生态杠杆)

**技术栈复用**:0.9 引入的 rig-core 已通过 `rmcp` feature 集成 MCP 官方 Rust SDK,`impl From<rmcp::model::Tool> for ToolDefinition` 让 MCP 工具 schema 零适配投影到统一 tool 表述——0.11 MCP 上层只需实现 client / server 编排逻辑,协议层不用重造。

### 4.1 MCP client(消费生态 tool)

- Blink 作为 MCP client,消费生态里海量 server 提供的 tool
- 这些 remote tool 走 0.9 的统一 tool schema(`exec: mcp`),和 builtin / 插件并列
- 让 blink 变强,但护城河浅

### 4.2 MCP server(暴露本地能力 = 护城河)★

**这是 0.11 真正的王牌**:

- 把 Blink 的本地能力暴露成 MCP server:全局划词 / 剪贴板 / 前台应用 / 截图 / 文件操作 / 资源管理器定位
- 这样**任何外部 Agent**(Claude Desktop / Cursor / 自建 Agent)都能通过 MCP 调用 Blink 的感知和执行能力
- 这些能力正是 Web Agent 拿不到的——**生态依赖 blink,而不只是 blink 依赖生态**

> client 让 blink 变强,server 让生态离不开 blink。两个都做,但 **server 才是 Blink 在 AI 时代的独特位置**。

## 六、VectorRouter 真正归宿:RAG / 记忆

0.9 移出的 VectorRouter 在这里找到归宿:

- **记忆功能**:记住用户历史意图 / 习惯,个性化路由
- **RAG**:对本地文档库 / 笔记做语义检索,作为 AI 回答的上下文

### 6.1 embedding 生产 vs 向量存储的边界(与 0.9 选型对齐)

**关键分工**——0.9 §11.3/§11.5 已定但需在 0.11 落地时再强调:

| 层 | 技术选择 | 理由 |
|---|---|---|
| **embedding 生产** | 走 rig `EmbeddingsModel`(云端 API + 自实现本地 trait) | 复用 0.9 Provider 抽象,云端 API(OpenAI text-embedding-3-small 等)+ 本地 `all-MiniLM-L6-v2` 都能走 |
| **向量存储 / 检索** | 自写 + `sqlite-vec`(**不引** rig 的 vector store) | 贴 Awareness 域,SQLite 已有生态;rig-vector 生态跟本项目存储心智割裂 |

### 6.2 embedding 一致性约束(切模型必重建)

**向量库必须锁 embedding model_id**:向量存 `(model_id, vector)`,切 embedding Provider(维度不同 / 语义空间不同)触发重建索引 UI 提示,不隐式失效数据。

### 6.3 起步实现

- 仍用「暴力 cosine 起步」(1000 条向量内 CPU &lt; 10ms),持久化走 SQLite BLOB;真扩到 10 万 + 再上 `sqlite-vec` 或独立向量库
- 本地 embedding 首选 `all-MiniLM-L6-v2` ~20MB,按需下载

## 九、0.11 之后候选池(1.0 前的插件市场里程碑)

> 这里存放**方向正确但当前无痛点**的产品化基础设施诉求。0.x 阶段不做(CLAUDE.md §6 铁则「产品化基础设施 1.0 前不做」),等 0.11 生态验证 + 用户量起来后统一在 **1.0-preview 插件市场** 里程碑落地。

### 9.1 插件动态下载与治理(2026-07-08 归档)

**用户诉求**:安装包不带插件,插件目录用户可管理;设置页从仓库拉取列表 → 用户点击下载安装。既减小安装包,也把插件治理权还给用户。

**方向评估**:✅ 正确。Raycast / uTools / Alfred 都这么做,长期必然要走这一步。

**为什么放到 1.0 前而不是 0.9/0.10**:

- 撞 CLAUDE.md §6 铁则(「插件市场 1.0 前不做」)
- 会连锁拉出:仓库托管 / 签名校验 / 版本兼容矩阵 / 更新机制 / 失败恢复 / 国内网络镜像——每一条独立看不重,加起来就是完整的产品化基础设施
- 与 0.11 §四 MCP 双向、§三 skill 化在**同一问题域**(远端能力的获取/安装/更新/信任),应合并到 1.0-preview 一起做基建,一次搭跑三种载体
- 当前**无实际痛点**:0.x 无分发压力、无用户抱怨安装包大、插件数 < 10 还没到需要"管理"的规模

**1.0-preview 插件市场里程碑应统筹的能力**:

- 插件 / skill / MCP server 的统一分发协议(哪里托管、如何索引、如何签名)
- manifest 版本升级 + 兼容矩阵
- 更新机制(手动 / 后台检查 / 增量)
- 权限强制模型(下载来源可信度、能力声明与用户授权)
- 国内网络镜像方案

**0.x 阶段允许的过渡小步**(不引入下载机制,零风险):

- 插件目录改为 `%APPDATA%\blink\plugins\` 优先于安装目录 → 用户手动拖 zip 也能装
- 设置页加"打开插件目录"按钮 → 让用户感知插件是可管理的,顺带验证"用户是否真会自己装插件"的假设

这两步任何小版本都可做,不阻塞主线。
