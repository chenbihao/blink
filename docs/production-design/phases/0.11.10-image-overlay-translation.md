# Blink 0.11.10 — 图上翻译（Image Overlay Translation）+ 截图交互重构

> **范围**：把 0.11.9 word 级 OCR 数据 + translate 插件的能力"接完最后一公里"—— 让截图里的外文**原位置显示译文**，不出面板，不换界面（对标 Google Lens / 微信「翻译屏幕」/ 腾讯翻译君）。同时借这次机会把截图交互整体重构：面板降级为编辑抽屉、加选取工具、误点保护。
>
> **主题**：`overlayLayer` 图层（沿用 0.11.9-a 水印"配置型图层"模式）承载 OCR 嵌图 / 翻译嵌图 / 图层同一份数据源两种视图；面板改为可召唤的编辑/双语对照工具；工具栏加[选取]默认工具解决"识别文字 vs 标注绘制"鼠标冲突；预热 OCR 让"识别/翻译"按钮秒响应。这是 PixPin/Snipaste/系统截图都没做的差异化功能。
>
> **状态**：⏳ 规划中。测试基线目标 **755+ 通过**（+ 字号自适应/背景采样/字符分类等纯函数单测）。
>
> **原则**：沿用四域墙不动；translate 插件协议做**扩展式非破坏升级**（新增 `translate_batch` tool，`translate` 保留）；`overlayLayer` 图层复用 0.11.9-a 水印单例模式；交互重构与图上翻译**同一批做完**（避免中间态尴尬）。
>
> **命名迁移**：`OCR` → `识别` / `文字`（技术黑话下沉，用户词浮上）。

## 二、核心设计

### 2.1 产品形态

**收敛到两个按钮 + 一个抽屉**：

```
┌────────────────────────────────────────────────────────────────────┐
│ [↖选取]* │ [矩形] [箭头] [铅笔] [文本] [马赛克] │ [识别] [翻译]  ≡  │
│    ↑                                                             ↑ │
│ 默认工具         标注工具组                    OCR 视图  面板 toggle │
└────────────────────────────────────────────────────────────────────┘
```

**心智模型（两级）**：

第一级——**图上视图**（默认视觉层，无需展开面板）：
- **点[识别]** → 图上嵌原文（`overlayLayer.mode = 'source'`）
- **点[翻译]** → 图上嵌译文（`overlayLayer.mode = 'translated'`,同一层切内容）
- 两个按钮**互斥切换**同一份数据源;再点当前激活的按钮 → 关闭嵌图回到原图

第二级——**面板抽屉**（用户主动召唤）：
- 点右上角[≡]或热键 → 面板滑出
- 面板显示原文/译文双 tab,支持编辑校对、复制、双语对照
- 面板存在时不影响图上嵌图（两者可共存）

**关键设计原则**：
- **一层内容,两种视图**:嵌图和面板显示的是同一份 OCR 结果,不是两个功能
- **切换零成本**:「翻译」不需要重新截图,不需要重新 OCR,只是 `overlayLayer` 换 `mode`
- **面板是编辑工具而非默认结果**:识别/翻译"结果"是嵌图,面板是"想改一下"的入口

### 2.2 工具栏[选取]工具（鼠标层管理）

**问题**：识别嵌图后,鼠标在图上究竟是选文字还是画标注?两者都在同一 canvas 区域,需要显式模式切换。

**方案**：类比 Figma/PS/Excalidraw 的选择工具:

- **[选取]激活**（默认）:
  - 无选区 → 拖出选区
  - 有选区 + 有嵌图 → word 拖选 / hover 高亮 / Ctrl+C 复制
  - 有选区 + 无嵌图 → 无副作用（暂无交互）
- **[矩形]/[箭头]/etc 激活**:
  - canvas → 走标注绘制(现有行为)
  - **`ocr-hit-canvas` 临时禁用鼠标**（`pointer-events: none`）
  - 视觉上仍能看到嵌图,鼠标穿透到 annot-canvas 画标注

**实现**:`ocr-hit-canvas` 的 `pointer-events` 由**当前工具**决定,不再只看 `data-reading`。改造 `data-reading` 语义为"有 overlay 内容",实际交互开启还要`当前工具 === 'select'`。

**副作用好处**:标注 + 嵌图 + 水印 三层共存,用户可"识别 → 切矩形工具画框圈重点 → 保存"。

### 2.3 预热 OCR（默认开,可关）

**流程**：

```
选区拖完 mouseup
    ↓
后台 spawn OCR(async)     [不阻塞 UI, 200-500ms 后完成]
    ↓
结果存 __ocrCache
    ↓
默认不显示,不弹面板
    ↓
用户点[识别] → 已有缓存 → 瞬间嵌图（0ms 感知）
用户点[翻译] → 已有 OCR 缓存 → 立即 translate → 嵌图
用户不点     → overlay 关闭时丢弃缓存
```

**开关**：`app_config.screenshot.prewarm_ocr: bool`,默认 `true`。设置页可关（笔电场景省电）。

**性能保护**：
- 只对选区面积 > 100x50 的做预热（太小的图可能是纯图无字,浪费）
- 若用户在预热完成前已经点[识别],复用同一 Promise（不重复触发）

### 2.4 `overlayLayer` 图层引擎（架构核心）

**继承 0.11.9-a 水印模式**：单例覆盖式,不进 commands 撤销栈,一次会话只有一份配置。

```js
overlayLayer = {
  mode: 'source' | 'translated' | null,   // null = 关闭嵌图
  lines: [
    {
      rect: {x, y, w, h},                  // 物理像素相对裁剪区
      srcText: "温度 25 度",
      dstText: "Temperature 25°C",         // mode='translated' 时用
      bgColor: "#f0f0f0",                   // 采样得到的行背景平均色
      fontSize: 16,                         // 字号自适应结果
    },
    ...
  ],
  bgStrategy: 'average' | 'blur' | 'solid',
  showOriginal: false,                     // true = 原文半透明可见做对照
  translationCache: {                       // 首次翻译后缓存,再点[翻译]立即切换
    targetLang: 'en',
    completedAt: <timestamp>,
  } | null,
}
```

**渲染时机**：`renderCommandsTo` 尾部——标注 commands 之后、水印之前:

```
底: 原图（screenshot）
   ↓
   标注 commands（矩形/箭头/铅笔/...）
   ↓
   overlayLayer（背景遮罩 + 嵌图文字，按 mode 显示原文或译文）  ← 新
   ↓
顶: watermarkConfig（水印）
```

**`hasAnnotations()` 认这个图层** → 保存/钉图/复制天然带嵌图内容。

**切换成本**:「翻译」按钮切 `mode: 'source' → 'translated'` 只需要重绘,不重跑 OCR;首次点[翻译]时若无 `dstText` 才调翻译 API。

### 2.5 面板改为可召唤抽屉

**现状**（0.11.9）：点 OCR 按钮 → 面板浮层立刻弹出（挡图）。

**目标**：面板定位为**编辑/对照工具**,用户主动召唤。

**改造**：

- **默认收起**:`showOcrResult` 不再自动展开面板
- **召唤方式**:
  - 工具栏右上角[≡]按钮 toggle
  - 双击嵌图任意 word → 打开面板并 focus 到那一行
  - 快捷键 `E`（Edit）
- **视觉形态**（可选升级）:面板从**工具栏正下方**滑出（抽屉式）,与工具栏视觉绑定;或保持浮层但透明度更低
- **内容**:保留 0.11.9 双 tab 结构（原文/译文）+ 三按钮（移除空格/复制/关闭）,加**「同步到嵌图」按钮**（用户编辑后想让嵌图也更新）

### 2.6 误点保护

**现状问题**：暗色蒙版视觉上像"背景",用户点这里可能想"关掉这里的暗色",结果关了整个 overlay。

**规则**（0.11.10-f）：

| 状态 | ESC | 点选区外（蒙版）| 窗口 blur |
|---|---|---|---|
| 拖选区中 | 关窗 | 无(mousemove 中) | 关窗 |
| 有选区无嵌图无面板 | 关窗 | **no-op**（新）| 关窗 |
| 有嵌图 or 有面板 | 关窗 | **no-op**（新）| 保留（不主动关）|

**核心变更**：点选区外从"关窗"改为"no-op"。关窗的正规入口是 **ESC + 工具栏[×]** 两个。

**不做分级 ESC**（决策）：学习成本大,大部分用户按 ESC 就是想关全部。

### 2.7 翻译粒度 + 批量翻译

**line 级翻译**（0.11.10-g）:
- word 级信息论上无意义
- 段级质量更好但位置回填复杂
- **line 级最优取舍**:翻译质量足够 + 位置一对一对齐

**批量翻译一次调用**:把 N 行文本用 `\n\n` 拼成一次请求,大部分引擎按段返回,减少 N-1 次 API 往返。

**translate 插件 tool 扩展**:新增 `translate_batch(texts: string[], target_lang?) → results: string[]`。老 `translate` tool 保留（单字符串路径）。

**保序保护**（应对某些引擎乱序）:每行加不可见 tag（`[[1]] xxx [[2]] yyy`）,解析时按 tag 拆回。

### 2.8 背景遮罩三档

| 策略 | 视觉 | 实现 | 适合场景 |
|---|---|---|---|
| **平均色矩形**（默认） | rect 采样周围像素平均色填充 | 复用 mosaic `sampleAverageColor` | 纯色/浅色背景 |
| **高斯模糊** | rect 区域高斯模糊 3-5px | canvas `filter: blur()` | 复杂背景(图片/照片) |
| **半透明板** | 白/黑矩形 + 60-70% alpha | 兜底最简单 | 视觉不自然但稳 |

**采样策略**:
- 采样带宽=`rect.h`(行高)向外扩 4px 环形区域
- 平均值忽略"文字色"(暗色像素 < 阈值不参与,防污染)
- 空采样退化到 `#ffffff` 白色

### 2.9 字号自适应

**CJK↔Latin 长度比例**：中→英 1.5-2x 变长;英→中 0.5-0.8x 变短。

**算法**：

```
fontSize = min(rect.h * 0.85, rect.h)     // 起始尝试
while measureText(text, fontSize).width > rect.w * 0.95:
    fontSize -= 1
    if fontSize < 8: break                 // 下限
// 超下限还超 → 截断显示 + tooltip 全文
```

**颜色**：`bgColor` 亮度阈值 128 切换深/浅字体。

## 三、UX 决策要点

### 3.1 交互流一图

```
[Alt+A]
   ↓
拖选区 → mouseup → [后台预热 OCR]
   ↓
标注模式激活（默认[选取]工具,可切矩形/箭头等）
   ↓
用户三条路径:
  A) 直接复制/保存 → 走 0.11.9 现有链路（无嵌图,无面板）
  B) 点[识别] → 图上嵌原文（overlayLayer.mode='source'）
     └─ 想编辑? → 点[≡]召唤面板
     └─ 想翻译? → 点[翻译] → mode='translated',同一层切内容
  C) 点[翻译] → OCR 缓存已有 + 立即翻译 → 图上嵌译文（mode='translated'）
     └─ 想看原文对比? → 点[识别] 切回 source
     └─ 想双语对照? → 点[≡]召唤面板（原文/译文双 tab 并列）
```

### 3.2 图上嵌字视觉规范

- **背景遮罩**:默认平均色,采样忽略暗色像素
- **文字**:`system-ui, "Microsoft YaHei", "Noto Sans SC"` fallback 链
- **字号**:自适应到 rect 高度 85%,超宽自动缩到 8px 下限,再超截断 + tooltip
- **对齐**:左对齐,`rect.x + 2px` 内边距
- **颜色**:深底→浅字 / 浅底→深字（亮度阈值 128）

### 3.3 复制/保存/钉图 三条铁则

- **复制**:走前端 canvas 合成 → 图带嵌图入剪贴板
- **保存**:同上,PNG/JPEG 天然带嵌图
- **钉图**:同上,pin 窗口拿到已翻译的图

这就是**"翻译过的截图"作为产品产出**的核心闭环 —— 用户"截完就是翻译好的"。

### 3.4 面板抽屉视觉规范（升级项,0.11.10-e）

- 位置:工具栏正下方（可拖动到选区左右侧）
- 尺寸:520×440 起步,内容多时自适应到 max 480 高
- 内容:双 tab（原文/译文）+ 底部按钮组（移除空格/翻译/同步到嵌图/复制/关闭）
- 视觉:暗色主题一致,与工具栏视觉绑定（同轴出现感）

## 七、风险与开放问题

1. **翻译引擎不保证顺序**：批量翻译时,某些 API 乱序回填错位。**mitigation**:每行 tag 编号,解析拆回。
2. **`filter: blur()` 性能**：WebView2 支持,4K 图可能 200ms 卡顿。**mitigation**:默认平均色策略;模糊仅在用户显式选时启用。
3. **极小字号可读性**：某些图 < 8px 无法在原位置显示。**mitigation**:截断 + tooltip;未来"展开到侧栏"模式（0.12+）。
4. **CJK 字体缺失**：无 CJK 字体的系统显示"豆腐块"。**mitigation**:`system-ui, "Microsoft YaHei", "Noto Sans SC"` fallback 链。
5. **预热 OCR 与用户快速操作竞态**：用户拖完选区立刻点[识别],预热 Promise 未完成 → 复用同一 Promise 而非重启。
6. **面板抽屉与嵌图共存冲突**：面板显示时用户改译文,嵌图不同步?**mitigation**:面板加「同步到嵌图」按钮显式触发。

### 阶段一：交互重构地基（预计 1-2 天）

**目标**：先立骨架。做完后用户能明显感觉到：选取工具在 / 点选区外不炸 / 识别按钮秒响应。

- **0.11.10-a** 工具栏[选取]工具 + 鼠标层管理
- **0.11.10-b** 预热 OCR（异步 cache + 设置开关）
- **0.11.10-f** 误点保护（点选区外 no-op）

**验收**：Alt+A → 选区 → 默认[选取]工具高亮 → 切矩形工具画标注不干扰 → 切回[选取]工具 → 点选区外无反应 → ESC 关窗。

**建议中间 commit** 让用户手动验证方向对齐后再进阶段二。

### 阶段二：视图收敛（预计 1 天）

**目标**：产品心智从"多按钮多面板"收敛到"两按钮 + 一抽屉"。做完前用户会觉得体验割裂，做完后心智才立得住。

- **0.11.10-c** 「识别」按钮 → 图上嵌原文（替代现有 OCR 面板默认路径）
- **0.11.10-d** 「翻译」按钮 → 图上嵌译文（同一层切 mode,不弹面板）
- **0.11.10-e** 面板改召唤抽屉（`[≡]` 按钮 / 双击 word / `E` 键三种召唤方式）

**验收**：点[识别]→图上出原文（不弹面板）→ 点[翻译]→图上切译文 → 再点[翻译]关闭嵌图 → 点[≡]召唤面板改字 → 「同步到嵌图」按钮把编辑回填 canvas。

**注意**：`c`/`d` 依赖阶段三的 `h`（`overlayLayer` 图层引擎），实际开发时**可以让 c/d 先用简单占位实现（先把 mode 切换和按钮联动跑通，图上先画一层平均色矩形+纯文字不做字号自适应），h 完成后再回填**。避免顺序死锁。

### 阶段三：图上翻译真本事（预计 1-2 天）

**目标**：技术含量最高的部分。差异化护城河功能真正落地。

- **0.11.10-g** translate 插件 `translate_batch` tool + `translate_lines` command
- **0.11.10-h** `overlayLayer` 图层引擎（背景遮罩 + 文字渲染 + 字号自适应）
- **0.11.10-i** 背景遮罩策略切换 UI（平均色 / 高斯模糊 / 半透明板）
- **0.11.10-j** 进阶控件（保留原文对照 toggle / 字号微调 / 命名迁移 OCR→识别）

**验收**：翻译原图纯色背景 / 复杂背景 / CJK↔Latin 混排 / 保存后图带译文 / 钉图带译文 / 复制到 QQ 微信粘贴带译文。

### 交付节奏建议

- **阶段一结束**：commit 一次让用户手动跑，确认交互方向对齐再进阶段二
- **阶段二结束**：commit 一次，此时"两按钮 + 一抽屉"的产品心智已成立，可作 0.11.10 rc.1
- **阶段三结束**：commit 归档 0.11.10 完成

### 顺序理由

**为什么先做交互重构（a/b/f）而不是先做技术核心（g/h）？**

- 交互重构是**用户可感知**的，做完立刻能验证方向
- 技术核心（g/h）依赖交互重构（c/d/e）作为消费方，先做 g/h 会没地方接入
- a/b/f 三条**互相独立**，出问题只影响自己
- 阶段一失败仍可回滚到 0.11.9 状态；阶段三失败可保留阶段一/二成果

**为什么面板改造（e）放在阶段二而不是阶段一？**

- 面板改造需要先确认「识别/翻译」新交互的形状，否则改完发现面板要迁就新交互又要重改
- c/d/e 三者应当一起做,同一次 commit 交付完整心智
