### 麦克风采集:waveIn → cpal 替换记录

> **时间**: 0.10 开发期间
>
> **问题**: 原 `windows.rs` 使用 winmm `waveIn` API(手写 FFI),在 Windows 10/11 麦克风隐私设置下
> `waveInOpen` 仍返回成功但采集数据**全是零**(静默拦截)。代码中积累了大量诊断逻辑
> (hex dump / WAV dump / volatile 读取 hack / WAVEHDR 地址固定 workaround)仍无法可靠读数据。
>
> **方案**: 引入 [`cpal`](https://github.com/RustAudio/cpal) 0.18(RustAudio 官方维护),Windows 上走 **WASAPI**。
> 麦克风隐私权限不足时返回明确错误而非静默给零数据。回调驱动替代 5ms 轮询,
> 无 unsafe FFI,代码量 ~450 行 → ~280 行(含重采样/downmix 纯逻辑测试)。
>
> **影响面**: `AudioCapture` trait 不变;`AudioDevice.id` 从 `u32`(waveIn 索引)改为 `String`(设备名);
> `SttConfig.audio_device_id` 同步改为 `Option<String>`。改动收敛在 `platform/audio/` 内部 + 配置类型。
>
> **默认设备透明化**:某些虚拟声卡驱动(如 VR/远程桌面的 Virtual Audio)会劫持 WASAPI
> `GetDefaultAudioEndpoint`,导致 cpal 返回的默认设备与 mmsys.cpl 面板显示的不一致。
> `AudioDevice` 新增 `is_default` 字段标注 cpal 认定的默认设备,设置页设备下拉框的「系统默认」
> 选项旁会显示实际默认设备名(如「系统默认(Virtual Desktop Audio)」),让用户一眼看出
> 默认设备是否被虚拟驱动劫持,从而决定是否手动选择设备。
> 同时用 `build_input_stream_raw` 统一回调类型,消除了原 match-on-format 的 6 个重复闭包分支。

## 一、为什么 0.10 才上语音(解耦的智慧)

语音是 Blink「丝滑」定位的完美放大器——把 P0「按键就能输入」推到「连打字都省了」:Alt+Space → 说 → 结果。

但语音也是工程复杂度最高的模态(STT 流式 / VAD / 降噪 / 中文模型 / 本地体积 / 声纹隐私)。把它和 0.9 的「AI 路由闭环」解耦,先在纯文本里把「路由 → 执行」跑顺,语音只是换个输入入口——**0.9 的 Provider / 路由 / Action / 信任边界全套复用,0.10 只加感知层**。

如果 0.9 就发现「AI 路由调本地能力」有坑,能在投语音前止损;反之 0.9 稳了,0.10 的不确定性收敛到 STT 单点。

## 二、两个目标:用嘴替键盘打字

0.10 的北极星不是某个炫技场景,而是**让用户可以用嘴代替键盘打字**——在两个 surface 上做好这件事:

### 目标一(G1):唤起后主窗口语音输入

> 用户 Alt+Space tap 唤起主窗口 → 再 Alt+Space hold → 按住即录、边说边转文字 → 松开即停 → 文字填进 blink 主窗口 `#query` → 自动触发搜索

```
Alt+Space tap → 主窗口出现
Alt+Space hold → 录音开始 → 边说边转文字(流式 partial 上屏)
松开 → STT 最终结果 → 填进 #query(queryEl.value = text + dispatch input 事件)
  → 0.9 主窗口搜索链路自动接管(防抖 → search_apps → 渲染结果)
```

**为什么这条几乎零新基建**:0.8.5 的 `blink://chord-fill-query` 已经验证了「后端 emit 文本 → 前端填 `#query` 并触发搜索」的链路(剪贴板 chord 用的就是它)。0.10 只需把「文本来源」从剪贴板换成 STT。

**意图分叉交给 0.9 路由**:用户说「找那个用来 balabala 的文件」→ STT 转成这句文字 → 进 `#query` → 0.9 路由判断是命令(命中 `search_files` Capability / Action)→ 搜文件。

### 目标二(G2):语音输入法出字上屏

> 用户在前台任意应用(编辑器、聊天框、文档)→ Alt+Space hold(不先 tap)→ 按住即录、边说边转文字 → 松开即停 → 文字打到前台应用光标处

```
前台应用 ← (光标在此)
Alt+Space hold → 录音开始 → mini overlay 显示流式 partial 文字
松开 → STT 最终结果 → 文本注入前台应用光标处(mini overlay 消失)
```

**这是 0.10 真正的硬骨头**:G2 必须新建一条文本注入通道。详见 §五。

### 两个目标的工程重心对比

| | G1 主窗口语音输入 | G2 语音输入法上屏 |
|---|---|---|
| 触发方式 | Alt+Space tap → 再 hold | Alt+Space hold(无先验 tap) |
| 文字去向 | blink 自己的 `#query` 输入框 | 外部前台应用光标处 |
| 流式展示 | 直接更新 #query | mini overlay 显示 partial |
| 需要新建 | STT 识别 + Hold 事件 | STT 识别 **+ 文本注入通道** + Hold 事件 + mini overlay |
| 复用现有 | `chord-fill-query` 链路 ✅ | 无,全新建 |
| 工程量 | 小 | 中→大(注入通道是难点) |

## 三、语音入口:Alt+Space 长按唤起(hold-to-talk)

### 3.1 设计方案

**核心思路**:Alt+Space 已有 tap/hold 状态机(LL hook 层)。tap → 主窗口(现有);**hold → 语音录音**(新增)。

| 操作 | 触发 | 效果 | 目标 |
|---|---|---|---|
| **Alt+Space tap**(短按) | keyup 时长 ≤ 阈值(~300ms) | 主窗口出现(现有,不变) | — |
| **Alt+Space hold**(长按,无先验 tap) | 按住超阈值时触发 Hold | 开始录音 → 边说边转 → 松开停止 → 注入前台应用 | **G2** |
| **Alt+Space tap → 再 hold** | 先 tap(出窗)→ 再按住 Alt+Space | 开始录音 → 边说边转 → 松开停止 → 填 #query | **G1** |

**G1/G2 区分逻辑**:主窗口是否可见。
- hold 时主窗口**不可见** → G2(文字注入前台应用)
- hold 时主窗口**可见**(先 tap 出窗了)→ G1(文字填 #query)

### 3.2 技术实现:Hold 事件

当前 LL hook 状态机的 tap/hold 判定:keyup 时若 `elapsed > threshold` → 当前是空操作(hold 不触发任何事件)。

**改动**:在 keydown 后起一个 `SetTimer`,超阈值时发 `HotkeyEvent::Hold`。keyup 时:
- 若 timer 已 fire(Hold 已发) → 发 `HotkeyEvent::HoldRelease`
- 若 timer 未 fire(tap) → 取消 timer,发 `Tap`(现有逻辑不变)

```
HotkeyEvent 新增变体:
  Tap(Instant)         — 短按,现有
  Hold(Instant)        — 长按开始(开始录音)
  HoldRelease(Instant) — 长按结束(停止录音→STT→注入)
  VoiceCancel(Instant) — ESC 取消录音
```

**关键保证**:tap 路径(keyup ≤ threshold)的 `send_event(Tap)` 在 keyup 时立即触发,不受 timer 影响。timer 仅在超阈值后才 fire。

### 3.3 与现有 Chord 模式的兼容

现有 Chord:tap 后持续按住 Alt → `chord-visible` → 按 A/C/Q。Voice hold 用的是 Space(hotkey 主键),不进 chord 字母表,**零冲突**。

hold 录音中 hook 线程会吞掉 Alt+Space 的 autorepeat keydown(防止 Windows 弹出系统菜单),keyup 不吞(否则 HoldRelease 收不到)。ESC 录音取消发 `VoiceCancel`。

### 3.4 录音 UX 细节

- **按住即录**:Hold 事件 → 开始麦克风采集 + STT 流式识别
- **边说边转**:STT partial 结果实时上屏(G1: 更新 #query;G2: 更新 mini overlay)
- **松开即停**:HoldRelease → 停止采集 → STT 最终结果 → 注入
- **取消录音**:Hold 期间按 ESC → VoiceCancel,不识别不注入
- **G2 mini overlay**:hold 期间显示一个小型悬浮窗,展示流式 partial 文字 + 录音波形/计时
- **G1 主窗口动画**:hold 期间 emit `blink://voice-level` 事件驱动音量波动条（✅ 已实现：噪声门限 + sqrt 归一化 + CSS idle 呼吸动画 + jitter 独立于 lv）

## 四、STT 选型(FunASR Python 工具箱)

### 4.1 接入形态

- **云端 STT**:走 OpenAI 兼容 API（`/v1/audio/transcriptions`），已内置 7 家供应商。
- **本地 STT**:使用 **FunASR Python 工具箱** 的 `funasr-server`（OpenAI 兼容 API）。
  - Blink 通过 **uv** 自管理 Python 3.12 + funasr 安装（用户零手动操作）
  - `funasr-server --model sensevoice --port 8000 --device cpu` 启动
  - Rust 侧通过 HTTP POST `localhost:8000/v1/audio/transcriptions` 转录
  - **复用 CloudSttEngine 的 HTTP 逻辑**，零额外推理代码
- **流式场景**:hold-to-talk 下用户松开才触发最终识别。0.10 先做非流式(hold → 松开 → 一次性识别),真流式(边说边出字)作为增强(§4.6 + 0.10.3)。

### 4.2 Python 环境自管理（uv）

> **设计方针**：Blink 对依赖的 Python 环境采用「自管理」策略——通过 uv 创建独立 venv，用户无需手动安装任何 Python 包。

#### 为什么用 uv

1. **零 Python 依赖**：uv 是单个 Rust 二进制，能自动下载和管理 Python 版本
2. **版本锁定**：避免用户系统 Python 版本过高（如 3.14）导致 C 扩展（editdistance 等）编译失败
3. **隔离环境**：Blink 的 Python 环境与用户系统完全隔离，互不污染
4. **速度快**：uv 用 Rust 写的，比 pip 快 10-100 倍

#### PyTorch 依赖问题（关键设计决策）

> **问题**：FunASR 的 PyPI 包（`pip install funasr`）**不声明 `torch` 为依赖**。这是 ML 生态惯例——
> PyTorch 有 CPU / CUDA 多种变体（CPU ~200MB / CUDA ~2GB），包作者让用户自己选择安装哪个版本。
> FunASR 的依赖 `torch_complex` 同样不声明 torch 依赖（只依赖 `packaging` + `numpy`）。
>
> **结论**：`uv pip install funasr` **不会自动安装 PyTorch**。Blink 必须手动安装 torch，这是必要的，
> 不是多此一举。

**当前方案（✅ 已迁移到 `--torch-backend` 一步安装）**：

uv 0.4+ 支持 `--torch-backend` 参数，一条命令安装所有包并自动选择正确的 torch 变体：

```bash
# 自动检测 CUDA 版本（推荐）
uv pip install torch torchaudio funasr fastapi uvicorn python-multipart --torch-backend=auto

# 指定 CPU 版
uv pip install torch torchaudio funasr fastapi uvicorn python-multipart --torch-backend=cpu
```

> **⚠️ 关键**：`torch` 和 `torchaudio` 必须显式列在包列表中！`--torch-backend` 只控制 torch 包的 index，
> 不会自动把 torch 加入安装列表。funasr 不声明 torch 依赖（ML 包惯例），如果只列 `funasr fastapi ...`
> 而不列 `torch`，uv 会发现这些包已安装就跳过，torch 永远不会被安装。

支持的 backend 值：`auto`（uv 自动调用 `nvidia-smi` 读取 CUDA 版本）、`cpu`、`cu101`~`cu130`、`rocm*`、`xpu`。

**CUDA 检测**：Blink 在安装前自行调用 `nvidia-smi` 解析 `CUDA Version: X.Y`，若检测到 CUDA 则传 `--torch-backend=auto`，否则传 `--torch-backend=cpu`。

**uv 版本兼容**：安装前检查 uv 是否支持 `--torch-backend`（通过 `uv pip install --help` 输出是否包含该参数）。旧版 uv 回退到两步安装（torch 从 pytorch.org index + funasr 从 PyPI）。

**进度流式输出**：`install_packages_streaming()` 用 `tokio::io::BufReader` + `read_until(b'\n')` + `split('\r')` 并发读取 stdout/stderr，逐行转发到前端日志窗口。设置 `PYTHONUNBUFFERED=1` 确保 Python 输出无缓冲。

**uv zip 解压**：用纯 Rust `zip` crate 替代 PowerShell `Expand-Archive`，消除对 PowerShell 的依赖。

#### funasr-server 的额外依赖

`funasr-server` 命令（`funasr.bin.server:main`）需要 `fastapi` + `uvicorn` + `python-multipart`，
这些**不在 `funasr` 包的依赖声明中**，必须显式安装。

注意：`funasr-server` 的错误信息会提示安装 `vllm`，但 **vLLM 仅用于 `fun-asr-nano` 模型**
（vLLM 推理引擎）。SenseVoice / Paraformer 走 `AutoModel` 路径，不需要 vLLM。Blink 默认使用
SenseVoice，不安装 vLLM。

#### 目录结构

```
%APPDATA%\blink\python\
  uv\
    uv.exe              — uv 二进制（本地安装，不污染 PATH）
  venv\                 — Python 虚拟环境（uv 创建）
    Scripts\
      python.exe        — venv 中的 Python
      funasr-server.exe — funasr 服务启动脚本（pip install funasr 自动生成）
```

#### 工作流（`src/infra/platform/python/mod.rs`）

1. `ensure_uv()` — 查找 PATH 中的 uv → 本地下载安装（GitHub releases ~15MB）
2. `create_venv()` — `uv venv --python 3.12`（uv 自动下载 Python standalone build）
3. `install_packages()` — `uv pip install funasr fastapi uvicorn python-multipart`
4. `venv_python()` — 获取 venv Python 路径，用于启动 funasr-server
5. `setup_with_progress()` — 一键完成上述所有步骤（幂等），带进度 + 日志回调
6. `setup()` — thin wrapper，传入 no-op 回调（供 `start_funasr_server` 自动安装用）

**用户侧体验**：设置页「语音输入」→「本地模式」→ 点击「安装环境」按钮 → 自动完成。无需命令行操作。

#### 模型下载进度

> **FunASR 自动管理模型下载**。首次启动 `funasr-server` 时，FunASR 从 ModelScope（国内 CDN）下载
> 模型权重。下载进度由 `modelscope` 库输出到 stdout（含百分比 + 速度），Blink 的子进程日志转发
> 会将这些行通过 `blink://funasr-server-log` 事件实时发送到前端日志窗口。

**当前实现**：
- `funasr::start_server` 内部 spawn 两个 tokio task 分别读取子进程 stdout/stderr
- 设 `PYTHONUNBUFFERED=1` 确保 Python 输出无缓冲
- 用 `read_until(b'\n')` + `split('\r')` 拆分 tqdm 进度条（modelscope 下载进度用 `\r` 刷新同一行，普通 `lines()` 会吞掉）
- 每行通过 unbounded channel 发送给 `start_funasr_server` 命令
- 命令层将日志行 emit 为 `blink://funasr-server-log` 事件
- 前端 `voice.js` 的日志窗口接收并显示

**ModelScope 下载日志格式示例**：
```
Downloading: 100%|████████████████████████████| 234M/234M [00:12<00:00, 19.5MB/s]
```

前端可解析 `Downloading:` 行中的百分比来驱动进度条（待实现，当前仅显示文本日志）。

**作为 Blink 调用 Python 项目的方针**：后续如果有其他 Python 依赖（如 0.11 本地模型/RAG），同样走 uv 自管理路线——在 `%APPDATA%\blink\python\venv\` 中安装，用户零手动操作。

### 4.3 三层架构(工具箱 × 服务 × 模型)

> | 层 | 职责 | Blink 的定稿 |
> |---|---|---|
> | **① 工具箱** | 模型生态 + 推理 + VAD + 标点 | **FunASR**(modelscope / 阿里达摩院) |
> | **② 服务** | OpenAI 兼容 API | **funasr-server**(Python, localhost:8000) |
> | **③ 模型** | 具体网络 | 按场景挑(SenseVoice 起步 / Paraformer 真流式) |

#### 模型层(FunASR 原生, CPU 可跑)

> **参数量 ≠ 文件大小**：FunASR 官方文档中的「220M」「234M」是模型**参数量**（220 million / 234 million），
> 不是文件下载体积。FP32 PyTorch 格式下，参数量 × 4 bytes ≈ 文件大小
> （如 220M 参数 → ~880MB 文件）。funasr-server 启动时还会自动下载 VAD + 标点模型。

| 模型 | 中文 | 流式 | 参数量 | 下载体积 | 额外能力 | funasr-server 参数 |
|---|---|---|---|---|---|---|
| **SenseVoice-Small** ⭐推荐起点 | ⭐⭐⭐⭐ 强 | ❌ 非流式但极快(CPU 17x 实时) | 234M | ~234MB | 语种识别 + 情绪 + 声学事件 | `--model sensevoice` |
| **Paraformer-zh** | ⭐⭐⭐⭐⭐ SOTA | ❌ 非流式 | 220M | ~880MB | 字符级时间戳 + 热词 | `--model paraformer` |
| Paraformer-zh-streaming | ⭐⭐⭐⭐ | ✅ streaming(zh-en 双语) | 220M | ~880MB | 字符级时间戳 + 热词 | `--model paraformer-zh-streaming` |

> **当前阶段**：funasr-server HTTP 模式为非流式（POST 音频 → 返回文本），
> 无论选哪个模型都是一次性识别。真流式（边说边出字）需要 0.10.3 切换到
> `AutoModel` Python API + WebSocket，届时使用 `paraformer-zh-streaming`。

> **注意**：`funasr-server` 的 `_server_app.py` 中 `FALLBACK_CONFIGS` 只注册了 `sensevoice` 和 `paraformer`。
> 若传入 `paraformer-zh-streaming`，服务端会返回 400 "Unknown model"。
> 真流式场景需要自定义 server 脚本（基于 `AutoModel` + WebSocket），不能用 `funasr-server` HTTP 模式。

**模型管理**:FunASR 在首次启动 `funasr-server` 时自动从 ModelScope（国内 CDN）下载模型，Rust 侧零管理。

**云端**(零体积,走 OpenAI 兼容 API):OpenAI / Groq / Azure / Gemini / HuggingFace / Mistral / OpenRouter。

### 4.4 &lt; 100MB 安装包硬约束

- **模型 weights**:FunASR 自动管理,首次启动 `funasr-server` 时从 ModelScope 下载。Blink 安装包不含模型。
- **Python 依赖**:Blink 通过 uv 自管理（首次使用时自动下载 uv + Python 3.12 + funasr），安装包不含 Python。用户零手动安装。

### 4.5 VAD + 降噪

hold-to-talk 下用户手动控制录音起止,VAD 的「说完判定」职责被消解。VAD 降级为 0.10.2 优化项(静默裁剪 + 可选降噪)。0.10.0 云端 STT 可依赖供应商侧 VAD。

## 五、文本注入通道(G2 的硬骨头,从零搭)

### 5.1 TSF / IME 调研结论

> **用户问题**:IME 形式是否有个打字上屏的缓冲区?其他 AI 语音输入法能边转文字边优化最后一起上屏,怎么实现的?

**Windows 文本注入的三条技术路径**:

| 路径 | 机制 | composition buffer | 适用场景 |
|---|---|---|---|
| **TSF (Text Services Framework)** | `ITfThreadMgr` → `ITfContext` → `ITfComposition`。创建 composition 后可多次更新 text range(流式 partial),commit 时文本"固化"到应用 | ✅ **有**:composition range 就是应用的文本缓冲区,可多次更新 | IME 输入法、高级文本注入 |
| **Clipboard + Ctrl+V** | 暂存剪贴板 → `SendInput(Ctrl+V)` → 恢复剪贴板 | ❌ 无:一次性注入完整文本 | 简单可靠,兼容性最好 |
| **SendInput 逐键** | 逐字符模拟 `WM_KEYDOWN/UP` | ❌ 无:逐字符,中文需走 IME 注入 | ASCII 文本,不碰剪贴板 |

**TSF Composition 的原理**(即 IME 的"打字缓冲区"):
1. 通过 `ITfThreadMgr::GetFocus` 获取前台应用的 `ITfContext`
2. 调 `ITfContextComposition::StartComposition` 创建 composition
3. 在 composition 的 text range 上多次 `SetText` —— 应用会实时显示"正在输入"的文本(就像拼音输入法显示候选词)
4. 调 `ITfComposition::EndComposition` —— 文本"提交",变为应用中的最终文本

**这就是其他 AI 语音输入法的实现原理**:边说边转文字 → `SetText` 更新 composition(用户看到文字逐渐出现)→ 松开时 commit composition(最终文本固化)。还可以在 commit 前做一轮文本优化(标点/分段/纠错),用户只看到最终结果。

**但 TSF 的工程复杂度**:
- TSF 是 COM 接口,需在目标应用的 UI 线程上操作(或通过 `ITfThreadMgrEx` 跨线程)
- 部分应用(游戏、控制台、UAC 窗口)不支持 TSF
- Rust 生态无成熟 TSF 绑定,需手写 COM interop

**Blink 的务实方案——分两阶段**:

| 阶段 | 方案 | 流式展示 | 最终注入 | 复杂度 |
|---|---|---|---|---|
| **0.10.1(先做)** | Mini overlay + Clipboard+Ctrl+V | mini overlay 显示 partial | 松开后 clipboard+Ctrl+V 注入完整文本 | 低 |
| **0.10.2+(后做)** | TSF Composition | composition range 实时更新(真·原地流式) | commit composition | 高(COM interop) |

> **0.10.1 的 mini overlay 就是"可视化 composition buffer"**:hold 期间在小悬浮窗中显示流式 partial 文字,松开时注入最终文本。用户感知与 TSF composition 一致,但实现简单 10 倍。

### 5.2 0.10.1 实现方案:Clipboard + Ctrl+V

**注入时序**:
```
HoldRelease → STT 最终文本
  → 备份当前剪贴板内容
  → 设置剪贴板为 STT 文本
  → SendInput(Ctrl down → V down → V up → Ctrl up)
  → 等待 50ms 让应用处理粘贴
  → 恢复原剪贴板内容
```

**平台抽象**:`src/infra/platform/inject/mod.rs` + `windows_impl.rs`
```rust
pub fn inject_text(text: &str) -> Result<()>;  // Clipboard + Ctrl+V
// 未来: pub fn inject_text_composition(text: &str) -> Result<()>;  // TSF
```

### 5.3 看门狗失焦检测的影响

G2 时主窗口不显示(无 tap),blink 进程不在前台。注入时序为:hold 录音 → release → STT → `inject_text()`。注入时主窗仍隐藏,看门狗不会误触发。但 `SendInput`/`Ctrl+V` 可能改变前台焦点,需验证注入后前台应用 PID 不变。

### FunASR 服务管理

> **用户问题**:funasr 是不是也得有管理服务？还是说启动一次后就不用管了？

**结论**:FunASR server 是一个长期运行的本地 HTTP 服务。启动后常驻后台,每次语音识别通过 HTTP POST 请求调用,无需反复重启。用户可在设置页手动启动/停止。

**当前行为**:
- 点击「启动服务」→ 启动子进程,加载模型到内存 → HTTP API 就绪
  - 启动前打印完整命令到日志（方便排查）
  - **防止重复启动**：检查已有子进程是否仍在运行（`try_wait`），在运行则跳过
- 后续语音识别直接调用 `localhost:8000/v1/audio/transcriptions`
- 点击「停止服务」→ kill 子进程,释放内存
- **Blink 退出时自动停止 funasr-server**：`main.rs` 注册 `RunEvent::Exit` handler，调用 `shutdown_funasr_server_blocking()`（`start_kill` 同步发送信号）

### 10.2 STT Engine trait

```rust
#[async_trait::async_trait]
pub trait SttEngine: Send + Sync {
    /// 接收一段音频 chunk,返回当前累积识别的 partial text。
    async fn transcribe_chunk(&self, samples: &[f32]) -> Result<String, SttError>;
    /// 录音结束,返回最终识别文本。
    async fn finalize(&self) -> Result<String, SttError>;
    /// 重置引擎状态(新录音会话前调用)。
    fn reset(&self);
    /// 引擎显示名称(日志/调试用)。
    fn name(&self) -> &str;
}
```

> ✅ **已迁移到 `#[async_trait]`**。`transcribe_chunk` 和 `finalize` 都是 `async fn`，
> 消除了 `block_in_place` + `block_on` 设计债。`VoiceService::stop_recording` 也改为
> `async fn`，在 `await finalize()` 前释放 `Mutex` 锁，HTTP 超时不再阻塞运行时。

### 10.3 VoiceService 管线

```
Hold 事件 → VoiceService::start_recording()
  → 启动 AudioCapture(独立 tokio task)
  → 循环: audio_chunk → SttEngine::transcribe_chunk → emit partial
  → 同时: emit blink://voice-level(音量驱动动画)

HoldRelease 事件 → VoiceService::stop_recording() (async)
  → 停止 AudioCapture + 释放 Mutex 锁
  → await SttEngine::finalize() → 最终文本
  → G1: emit "blink://chord-fill-query"(文本)
    G2: inject_text(文本) + 隐藏 mini overlay

VoiceCancel 事件 → VoiceService::cancel_recording()
  → 停止采集 → 清除状态 → 隐藏 overlay
```

### 10.4 Hold 事件流转

```
LL hook (hook 线程)
  ├── keydown → armed + SetTimer(threshold)
  ├── timer fire → send_event(Hold)     ← 开始录音
  └── keyup →
       ├── timer 已 fire → KillTimer + send_event(HoldRelease)  ← 停止录音
       └── timer 未 fire → KillTimer + send_event(Tap)           ← 现有 tap

main.rs hotkey rx (主线程, via HotkeyService)
  ├── Hold → spawn VoiceService::start_recording()
  ├── HoldRelease → VoiceService::stop_recording()
  └── VoiceCancel → VoiceService::cancel_recording()
```

### 10.5 已修复问题（历史记录）

> 以下问题均已在本次链路修复中解决（20260715）。保留记录供后续排查参考。

#### Bug 1：~~`is_server_ready` 只检查 TCP 端口,不检查 HTTP 就绪~~（✅ 已修复）

**问题**：`funasr-server` 启动后 uvicorn 先绑定 TCP 端口，但模型还在加载（SenseVoice 首次加载需下载 + 加载 PyTorch，可能 30-60s）。`is_server_ready` 在 TCP 连接成功后返回 `true`，但此时 HTTP API 还没就绪。

**修复**：新增 `is_server_ready_http(port)` 做 `GET /health` HTTP 健康检查。`LocalSttEngine::finalize`（async）用它替换 TCP-only 检查。`is_server_ready(port)` 保留为 TCP 快速预检（用于 `LocalSttEngine::new` 的同步快速失败判断）。

#### Bug 2：~~`finalize` 中 `model` 字段硬编码为 `"sensevoice"`~~（✅ 已修复）

**问题**：`transcribe_async` 的 `model` 字段硬编码为 `"sensevoice"`。`funasr-server` 的 `_server_app.py` 根据此字段选择模型路由，切换到 `paraformer` 时仍发送 `sensevoice`。

**修复**：`LocalSttEngine` 新增 `funasr_model: String` 字段，`new()` 从 `SttConfig.local_engine.funasr_model` 读取。`transcribe_async` 接收 `model` 参数。

#### Bug 3：~~`SttEngine` trait 同步导致 `block_in_place`~~（✅ 已修复）

**问题**：`finalize` 用 `tokio::task::block_in_place` + `block_on` 做 async HTTP，在持有 `Mutex<VoiceSession>` 锁时阻塞。HTTP 超时（30s）会阻塞整个 Tauri 运行时 30s。

**修复**：trait 迁移到 `#[async_trait]`，`transcribe_chunk`/`finalize` 变 `async fn`。`VoiceService::stop_recording` 改为 `async fn`，在 `await finalize()` 前释放 `Mutex` 锁。

#### Bug 4：~~`setup_python_env` 和 `python::setup` 逻辑重复~~（✅ 已修复）

**问题**：`commands.rs::setup_python_env` 手动展开 `python::setup` 的 4 个步骤并添加进度事件，而 `python::setup` 本身也做了同样的事。

**修复**：新增 `python::setup_with_progress(device, on_progress, on_log)` 统一所有逻辑。`setup()` 变 thin wrapper（no-op 回调）。`commands::setup_python_env` 从 ~95 行缩到 ~20 行，只负责构造 `Arc<dyn Fn>` 回调转发到 Tauri 事件。

#### Bug 5：~~Blink 退出后 funasr-server 成为孤儿进程~~（✅ 已修复）

**问题**：Blink 没有注册 shutdown handler 来 kill 子进程。下次启动时 `is_server_ready()` 会检测到服务已在运行并复用，但 `stop_funasr_server` 会因 child handle 为 None 而无法停止。

**修复**：`main.rs` 改用 `Builder::build()` + `App::run()` + `RunEvent::Exit` handler，调用 `shutdown_funasr_server_blocking()`（`start_kill` 同步发送 kill 信号，不阻塞退出）。

#### Bug 6：~~uv zip 解压依赖 PowerShell~~（✅ 已修复）

**问题**：`install_uv` 用 PowerShell `Expand-Archive` 解压 uv zip，在精简版 Windows 或企业策略下可能不可用。

**修复**：引入 `zip` crate，用 `ZipArchive` + `enclosed_name()` 纯 Rust 解压，消除 PowerShell 依赖。

#### Bug 7：~~CUDA 版本固定为 cu121~~（✅ 已修复）

**问题**：PyTorch CUDA index 硬编码为 `https://download.pytorch.org/whl/cu121`。如果用户 CUDA 版本是 11.8 或 12.4+，cu121 的 PyTorch 可能无法使用 GPU。

**修复**：新增 `detect_cuda()` 运行 `nvidia-smi` 解析 `CUDA Version: X.Y`。用 `--torch-backend=auto` 让 uv 自动选择匹配的 CUDA 变体（旧版 uv 回退时仍用两步安装）。

#### Bug 8：~~pip install 无进度流式输出~~（✅ 已修复）

**问题**：`install_packages_inner` 用 `.output()` 等待完成，不流式读取 stdout/stderr。安装 torch + funasr 可能 5-10 分钟，用户只能看到"安装中..."。

#### Bug 9：~~多次点击启动服务 spawn 多个子进程~~（✅ 已修复）

**问题**：`start_funasr_server` 只用 `is_server_ready(port)` TCP 检查防重，但 Python 初始化期间 TCP 端口未绑定，多次点击会 spawn 多个子进程，旧进程成为孤儿。

**修复**：`start_funasr_server` 开头用 `FUNASR_SERVER_CHILD` + `try_wait()` 检查已有子进程是否仍在运行，在运行则直接返回 `already_running`。

#### Bug 10：~~funasr-server 启动命令未打印~~（✅ 已修复）

**问题**：`start_server` 不打印实际执行的命令，排查困难。

**修复**：构建命令后 `tracing::info!("funasr-server 启动命令: {cmd_display}")`，显示完整参数。

#### Bug 11：~~tqdm 进度条输出被吞~~（✅ 已修复）

**问题**：ModelScope 下载进度用 `\r` 刷新同一行，`BufReader::lines()` 只读 `\n` 结尾的行，进度条内容被吞。

**修复**：改用 `read_until(b'\n')` 读一大块，然后 `split('\r')` 拆分，每个 `\r` 段作为一条日志转发。同时设 `PYTHONUNBUFFERED=1`。

#### Bug 12：~~音量动画无反应~~（✅ 已修复）

**问题**：`compute_rms` 用 `rms * 3.0` 增益太低（正常语音 RMS ~0.01-0.1，乘 3 只有 0.03-0.3）；`jitter * lv` 在 lv=0 时无抖动；无 CSS idle 动画。

**修复**：
- Rust：噪声门限 0.001 + 线性映射 0.001~0.15 + sqrt 曲线（安静说话 → 25%，正常 → 50-80%）
- JS：`jitter` 独立于 `lv`（`jitter = (sin(...) + 1) * 0.08`）
- CSS：`@keyframes vw-breathe` / `bar-breathe` 呼吸动画，JS 设 inline style 后自动禁用（`[style]` 选择器）
