# Blink 0.10 — 语音指令闭环(STT + 双 Chord + Agent 窗口)

> **范围**:STT 接入 + 双 chord 语音入口 +「语音找文件」北极星场景 + Agent 对话窗口(流式 MD + 确认反馈)
>
> **主题**:在 0.9 文本闭环稳定后,换「嘴」替键盘。**架构不变,只加感知层**——语音是新的输入入口,路由 / 执行 / 信任边界全套用 0.9。
>
> **前置**:0.9 完成(Provider 多档 + 主窗口文本闭环 + 统一 tool 架构)。
>
> **原则**:语音意图必须显式分叉(输入法 vs 指令);本地 STT 不捆绑、按需下载;声纹数据上云强告知。

---

## 一、为什么 0.10 才上语音(解耦的智慧)

语音是 Blink「丝滑」定位的完美放大器——把 P0「按键就能输入」推到「连打字都省了」:右 Alt → 说 → 结果。

但语音也是工程复杂度最高的模态(STT 流式 / VAD / 降噪 / 中文模型 / 本地体积 / 声纹隐私)。把它和 0.9 的「AI 路由闭环」解耦,先在纯文本里把「路由 → 执行」跑顺,语音只是换个输入入口——**0.9 的 Provider / 路由 / Action / 信任边界全套复用,0.10 只加感知层**。

如果 0.9 就发现「AI 路由调本地能力」有坑,能在投语音前止损;反之 0.9 稳了,0.10 的不确定性收敛到 STT 单点。

---

## 二、双 Chord 语音入口(意图分叉)

### 2.1 核心问题:语音有两种意图

用户说话可能是:

- **纯语音输入法**(口语优化 → 上屏):在「写字」,用嘴写,产出干净文本放光标处
- **找 blink 有事**(指令):在「下命令」,触发某个动作

这两种意图的处理路径完全不同,**必须分叉**。

### 2.2 方案对比

| 方案 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **A. 双 chord 入口** | 一个 chord = 语音输入法(上屏);另一个 chord = 语音指令 | 确定性 100%,复用 0.8.5 chord 心智模型,零误判 | 多记一个键 |
| **B. 单入口 + 智能分叉** | 统一说话,松开后轻量模型判断意图 | 最丝滑,一个键 | 误判 + 100-200ms 判断延迟 |
| **C. 单入口 + 语义前缀** | 「找 / 打开 / 翻译」开头 → 指令;否则 → 输入法 | 规则初筛快 | 用户要记指令词 |
| **D. 采用** | **A 为主 + 指令模式内智能回退** | 确定性与丝滑兼得 | — |

**采用 D**:默认双 chord 入口(确定性);指令模式内若没命中 Action,再智能回退到对话。

### 2.3 复用现有 Chord 心智模型

用户心智已建好(「右 Alt tap = 搜索,Alt+A = 截图,Alt+C = 剪贴板」)。加两个 chord 是自然延伸:

| 组合键(待定) | 模式 | 行为 |
|---|---|---|
| `Alt+V` | 语音输入法 | 边说边转文本,口语优化后上屏到光标处 |
| `Alt+Shift+V` | 语音指令 | 说意图 → 轻量路由 → 执行 / 展开 Agent |

**不为「一个键的丝滑」牺牲确定性**——Blink 立身之本是可预测。

### 2.4 输入法模式:口语优化上屏

- **流式 STT**:边说边出字(不等说完)
- **口语优化**:去「嗯 / 啊 / 那个」、补标点、去口头禅,产出干净文本
- 优化可用轻量模型做(或专门后处理)
- 差异化:全局 + 快 + Provider 可选(本地 whisper 保隐私 / 云端讯飞求准)

## 三、北极星场景:语音找文件

> 用户按住语音指令 chord 说:「帮我找一下某个文件,但是我忘记名称了,主要是用来 balabala 的」

完整链路:

```
语音指令 chord → STT 流式转文本
  → 路由模型理解意图(找文件)+ 抽参(把「用来 balabala」转成搜索关键词)
  → 调用本地 tool:Everything / FileEngine 搜索
  → 结果回流到主窗口(文件列表)
  → 用户:Alt+1 打开 / 或继续「让 AI 总结这个文件」→ 展开 Agent 窗口
```

**为什么这是北极星**:它一次性展示了 Blink 的全部护城河——语音(感知入口)+ Everything(本地执行)+ 轻量模型(路由 + 抽参)。这三样 Web AI 客户端全凑不齐。0.10 的所有架构都围绕让这条链路丝滑。

这也是「AI 作为 Action 参数填充器」的最佳舞台:路由模型既做**路由**(找文件这个 tool),又做**参数解析**(模糊描述 → 搜索关键词),全在 0.9 的 tool-call 架构内完成。

## 四、STT 选型(0.10 最大未知)

### 4.1 接入形态(与 0.9 rig 抽象对齐)

STT 走 0.9 定型的 `AIProvider` / rig-core 抽象——**不为语音单独造轮子**:

- **云端 STT**:走 rig `TranscriptionModel` trait,rig 已内置 OpenAI Whisper / Groq whisper-large-v3 / Azure OpenAI / Gemini(audio inline)/ HuggingFace / Mistral / OpenRouter 七家实现,直接可用
- **本地 STT**:引 `whisper-rs` 或 `sherpa-onnx`,**自实现 rig `TranscriptionModel` trait**,保持 Provider 抽象一致——上层调用不区分云端/本地
- **国内云端**(讯飞 / 通义):rig 未内置,可自实现 trait 或走独立 client(0.10.0 落地时视调研结果定)

### 4.2 候选方案

| 方案 | 库 / 服务 | 流式 | 中文 | 模型体积 | rig 支持 |
|---|---|---|---|---|---|
| 本地 | `whisper-rs`(whisper.cpp binding) | 需流式配置 | 中等 | 几十~上百 MB | 自实现 trait |
| 本地 | `sherpa-onnx` | ✅ 原生流式 | 好 | 中 | 自实现 trait |
| 云端 | OpenAI Whisper API | ✅ | 好 | 0(发录音) | ✅ 内置 |
| 云端 | Groq whisper-large-v3 | ✅ | 好 | 0 | ✅ 内置 |
| 云端 | Gemini audio | ✅ | 好 | 0 | ✅ 内置 |
| 云端 | Azure / 讯飞 / 通义 | ✅ | 好(国内) | 0 | Azure ✅ / 讯飞通义需自实现 |

### 4.3 &lt; 100MB 安装包硬约束

本地 STT 模型动辄几十到上百 MB,**直接冲突**。决策:

- **本地 STT 模型按需下载、默认不捆绑**(与 0.11 本地 LLM / embedding 同规矩)
- 用户主动点「下载模型」才开始,下载进度可见、可暂停 / 取消
- 云端 STT 无体积问题,但要花钱 + 隐私(录音上云)

### 4.4 流式 STT 的工程量(别低估)

- **VAD**(语音活动检测,判断说完没)
- 降噪
- 流式增量识别 + 中间结果上屏(避免抖动)
- 这是一整套管线,不是调个 API

### 4.5 选型建议

**先用云端 STT 跑通闭环**(快、中文好、零体积),本地 STT 作为 0.11 的「隐私 / 离线」可选项。本地模型选型(`whisper-rs` vs `sherpa-onnx`)建议 **0.9 末期就调研**,提前除雷——它是 0.10 能不能做成的最大未知(详见 §七调研)。

## 五、Agent 对话窗口

### 5.0 rig 能力开放(与 0.9 §4.3 边界对齐)

Agent 窗口是**用户显式授权 tool loop** 的场景——用户点 Alt+1 展开就是"要跟 AI 对话让它办事",与主窗口"在搜索"的心智不同。因此 rig 用法在 0.10 Agent 窗口全面放开:

- ✅ 允许 `rig::AgentBuilder` 自动 tool dispatch loop(安全动作)
- ✅ 允许 `Prompt` / `TypedPrompt` 管消息历史
- ✅ 允许 `rig::agent::memory` 做会话短期记忆(长期记忆留 0.11 RAG)
- ✅ 允许 Structured output(`prompt_typed`)结构化返回
- ⚠️ `Action::danger_class() == Dangerous` 的动作**不进 AgentBuilder tools 池**,或用带 pre-exec hook 的封装 tool——hook 里产 Suggestion 走人机确认,即使 AI 自主决定要调,也必须 Tab 确认

**为什么这不算破四域信任边界**:四域边界的核心是"参数注入必须显式(`ExecArg::UserExplicit`)"和"AI 不能构造用户未确认的执行参数"。Agent 窗口内**每次工具调用的 arguments 都已经经过 AI 结构化输出+可选 pre-exec 确认**,`UserExplicit` 类型墙在 Agent 窗口的模型改为「用户显式授权了整个会话」——这是**授权粒度从"每次工具"扩到"整个会话"**的产品决策,不是拆掉铁则。

详见 [0.9-ai-layer.md §4.3](./0.9-ai-layer.md#43-provider-落地形态2026-07-定型) 和 [§11.3](./0.9-ai-layer.md#113-rig-能力开放清单按交互模式分层)。

### 5.1 展开时机(不自动展开)

轻量路由判定「需要多轮 / 主窗口不够展示」时,**不自动展开**——而是产一个 Suggestion「Alt+1 展开对话」,用户确认才展开。

理由:自动展开会抢焦点、打断心流,和「丝滑」冲突。这延续四域信任边界——**显式确认才穿过到新交互范式**。

### 5.2 窗口形态

- 复用同一 WebviewWindow,切换到 chat template(0.8.4 view 字段预留 `view: chat`)
- 类 ChatGPT 布局:消息流 + 输入框
- **流式 MD 渲染**(打字机效果 + 代码高亮 + 复制按钮)
- ESC 返回搜索模式

### 5.3 确认反馈(走统一 kbd 体系)

展开 / 拒绝用快捷键确认,走 `kbd.js` 统一渲染(见 [product-principles.md §14.7](./../product-principles.md#147-键盘提示样式统一强制规则)):

| 键 | 动作 |
|---|---|
| `Alt+1` | 展开成 Agent 对话窗口 |
| `Alt+2` | 拒绝 / 取消执行 |

### 5.4 Context 注入(可关)

Chat 消息可自动带上,用户可逐项关:

- 当前剪贴板
- 最近选区
- 前台应用
- 用户显式引用:`@选区` / `@剪贴板`

## 六、语音隐私升级

语音是**比文本敏感一个量级**的数据(声纹是生物特征):

- **默认本地 STT**(若已下载模型);云端 STT 需用户显式开启
- **第一次启用语音必须有强告知门**:发给谁、发什么(录音还是文本)、存不存、能关什么
- 录音不持久化、不入 SQLite;成功只记时长
- 敏感应用黑名单生效时跳过(银行、密码管理器)
- 详见 [product-context-future.md §8](./../product-context-future.md#8-隐私与安全) 升级章节

## 八、验收标准

```bash
# 0.10.0
→ Alt+V 说话 → 边说边出字 → 口语优化后上屏到光标处
→ Alt+Shift+V 说话 → 进指令模式

# 0.10.1(北极星)
→ 语音指令说「找那个用来 balabala 的文件」→ STT 转文本 → 路由理解找文件意图
→ 调 Everything 搜 → 文件列表回流主窗口 → Alt+1 打开
→ 第一次启用语音 → 强告知门弹出,用户确认才发云

# 0.10.2
→ 路由判定「需多轮」→ Suggestion「Alt+1 展开」→ Alt+1 进 Agent 窗口
→ Agent 回复流式打字机 + MD 渲染 + 代码高亮
→ Alt+2 拒绝 / ESC 返回搜索
```
