# Blink 0.10 — 语音输入(STT + 语音打字 + Agent 窗口)

> **范围**:STT 接入 + 语音输入两个目标 + Agent 对话窗口(流式 MD + 确认反馈,后置可选)
>
> **主题**:在 0.9 文本闭环稳定后,换「嘴」替键盘打字。**架构不变,只加感知层**——语音是新的输入入口,产出的是文字;文字进哪条路由、要不要执行,全套用 0.9 的路由 / 执行 / 信任边界。
>
> **前置**:0.9 完成(Provider 多档 + 主窗口文本闭环 + 统一 tool 架构 + Capability 协议层)。
>
> **原则**:语音只产出文字,不直接执行动作(意图分叉交给 0.9 路由);本地 STT 不捆绑、按需下载;声纹数据上云强告知;P0 主链路零回归。

---

## 一、为什么 0.10 才上语音(解耦的智慧)

语音是 Blink「丝滑」定位的完美放大器——把 P0「按键就能输入」推到「连打字都省了」:Alt+Space → 说 → 结果。

但语音也是工程复杂度最高的模态(STT 流式 / VAD / 降噪 / 中文模型 / 本地体积 / 声纹隐私)。把它和 0.9 的「AI 路由闭环」解耦,先在纯文本里把「路由 → 执行」跑顺,语音只是换个输入入口——**0.9 的 Provider / 路由 / Action / 信任边界全套复用,0.10 只加感知层**。

如果 0.9 就发现「AI 路由调本地能力」有坑,能在投语音前止损;反之 0.9 稳了,0.10 的不确定性收敛到 STT 单点。

---

## 二、两个目标:用嘴替键盘打字

0.10 的北极星不是某个炫技场景,而是**让用户可以用嘴代替键盘打字**——在两个 surface 上做好这件事:

### 目标一(G1):唤起后主窗口语音输入

> 用户 Alt+Space tap 唤起主窗口 → 再 Alt+Space hold → 说话 → 松开 → STT 转文字 → 文字填进 blink 主窗口 `#query` → 自动触发搜索

```
Alt+Space tap → 主窗口出现
Alt+Space hold → 录音开始 → 说话 → 松开 → STT 转文字
  → 填进 #query(queryEl.value = text + dispatch input 事件)
  → 0.9 主窗口搜索链路自动接管(防抖 → search_apps → 渲染结果)
```

> 📝 **Review(已修订)**:原版用 Alt+V 作为语音 chord,本版改为 Alt+Space hold 语义(详见 §三)。G1 的文字去向链路不变——`chord-fill-query` 复用不受影响。

**为什么这条几乎零新基建**:0.8.5 的 `blink://chord-fill-query` 已经验证了「后端 emit 文本 → 前端填 `#query` 并触发搜索」的链路(剪贴板 chord 用的就是它)。0.10 只需把「文本来源」从剪贴板换成 STT。

**意图分叉交给 0.9 路由**:用户说「找那个用来 balabala 的文件」→ STT 转成这句文字 → 进 `#query` → 0.9 路由判断是命令(命中 `search_files` Capability / Action)→ 搜文件。**所谓「语音找文件」不再是独立北极星,而是 G1 的一个自然结果**——只要 0.9 路由认得这句话,G1 就免费实现了它。

### 目标二(G2):语音输入法出字上屏

> 用户在前台任意应用(编辑器、聊天框、文档)→ Alt+Space hold(不先 tap)→ 说话 → 松开 → STT 转文字 → 文字打到前台应用光标处

```
前台应用 ← (光标在此)
Alt+Space hold → 录音开始 → 说话 → 松开 → STT 转文字
  → 通过文本注入通道打到前台应用光标处
```

> 📝 **Review(已修订)**:原版 G2 入口也是 Alt+V。本版改为 Alt+Space hold(无先验 tap),利用主窗口是否可见区分 G1/G2,无需额外上下文判定。

**这是 0.10 真正的硬骨头**:`grep` 全仓库,**目前没有任何「向外部前台应用注入文本」的机制**——无 `SendInput`、无模拟 `Ctrl+V`、无 UIA `ValuePattern` 注入。G2 必须从零搭一条文本注入通道。详见 §五。

### 两个目标的工程重心对比

| | G1 主窗口语音输入 | G2 语音输入法上屏 |
|---|---|---|
| 触发方式 | Alt+Space tap → 再 hold | Alt+Space hold(无先验 tap) |
| 文字去向 | blink 自己的 `#query` 输入框 | 外部前台应用光标处 |
| 需要新建 | 仅 STT 识别(与 G2 共享) + Hold 事件 | STT 识别 **+ 文本注入通道(从零搭)** + Hold 事件 |
| 复用现有 | `chord-fill-query` 链路 ✅ | 无,全新建 |
| 工程量 | 小 | 中→大(注入通道是难点) |

## 三、语音入口:Alt+Space 长按唤起(hold-to-talk)

### 3.1 设计方案

> 📝 **Review(已重写)**:原版 §三 标记为「待探索,不写死」,列了三个候选方案(单 chord / 双 chord / 上下文判定)但未决策。本版基于 hold-to-talk 方案直接定稿——利用现有 tap/hold 状态机的 hold 语义,零新键、零系统热键冲突、G1/G2 靠主窗口可见性自然区分。

**核心思路**:Alt+Space 已有 tap/hold 状态机(LL hook 层)。tap → 主窗口(现有);**hold → 语音录音**(新增)。

| 操作 | 触发 | 效果 | 目标 |
|---|---|---|---|
| **Alt+Space tap**(短按) | keyup 时长 ≤ 阈值(~300ms) | 主窗口出现(现有,不变) | — |
| **Alt+Space hold**(长按,无先验 tap) | keydown 后超阈值仍按住 | 开始录音 → 松开 → STT → 注入前台应用 | **G2** |
| **Alt+Space tap → 再 hold** | 先 tap(出窗)→ 再 Alt+Space hold | 开始录音 → 松开 → STT → 填 #query | **G1** |

**G1/G2 区分逻辑**:主窗口是否可见。
- hold 时主窗口**不可见** → G2(文字注入前台应用)
- hold 时主窗口**可见**(先 tap 出窗了)→ G1(文字填 #query)

> **为什么不新增 Alt+V 等独立键**:hold-to-talk 复用现有 Alt+Space,零新键、零系统热键冲突、零学习成本(用户已知 Alt+Space 是 Blink 入口)。长短按的 tap/hold 区分已在 LL hook 状态机中实现,只需新增 Hold 事件。

### 3.2 技术实现:Hold 事件

当前 LL hook 状态机(`src/infra/platform/hotkey/windows.rs`)的 tap/hold 判定:

```
keydown → armed(down_since = now)
keydown 期间出现异键 → aborted(判 hold,不触发)
keyup → 若 aborted 或 elapsed > threshold → 无事件(当前 hold 是空操作)
       若 elapsed ≤ threshold → Tap 事件
```

**改动**:hold 不再是空操作——超阈值时发送 `HotkeyEvent::Hold`。

```
HotkeyEvent 新增变体:
  Tap(Instant)   — 短按,现有
  Hold(Instant)  — 长按,新增
```

**Hold 触发时机**:有两种选择,需 spike 定:

| 方案 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **A: keyup 时判定** | keyup 时若 elapsed > threshold → 发 Hold | 实现最简单(改 1 行),与现有 Tap 逻辑对称 | 用户必须**松开**才开始录音,不是真正的 hold-to-talk |
| **B: 定时器触发(推荐)** | keydown 时起 timer,threshold 到期且仍按住 → 发 Hold(录音开始);keyup → 发 HoldRelease(录音结束) | 真正的 hold-to-talk:按住即录,松开即停 | 需在 hook 线程加 timer(可用 `SetTimer` 或 worker thread) |

> **采用建议**:方案 B(定时器触发)——按住即录、松开即停是 hold-to-talk 的核心体验。spike 验证 hook 线程加 timer 的可行性。

> 📝 **Review**:方案 A 虽简单但 UX 差(松开才开始录音,反直觉)。方案 B 的 timer 实现复杂度可控——hook 线程已有消息循环(`GetMessageW`),`SetTimer` 可直接用。

### 3.3 与现有 Chord 模式的兼容

现有 Chord 模式:Alt+Space tap → 主窗口 → 持续按住 Alt → `chord-visible` → 按 A/C/Q 触发 chord 动作。

**兼容性分析**:
- Chord 模式的入口是 **tap 后持续按住 Alt**(不是按住 Space)
- Voice hold 的入口是 **持续按住 Space**(Alt+Space 中的 Space 主键)
- 两者物理动作不同:Chord = 按住 Alt + 按 A/C/Q;Voice = 按住 Alt+Space

**不冲突**:用户 tap Alt+Space 出窗后,按住 Alt 不松开 → chord 模式(A/C/Q);用户 tap Alt+Space 出窗后,再次按下 Alt+Space 并 hold → voice(G1)。

> 📝 **Review(逻辑性)**:原版 §三 担心新 chord 键与现有 A/C/Q 冲突。hold-to-talk 方案下,语音触发用的是 Space(hotkey 主键)而非新字母键,**天然不进 chord 字母表**,零冲突。

### 3.4 录音 UX 细节

- **录音指示**:hold 开始时,主窗口(若可见=G1)或 mini indicator(若不可见=G2)显示录音状态波形/计时
- **松开转文字**:keyup → 停止录音 → STT 识别 → 文字注入
- **取消录音**:hold 期间按 ESC → 取消,不识别不注入
- **G2 无窗口反馈**:hold 期间主窗口不可见,需一个轻量指示器(系统托盘图标变化 / mini overlay)

## 四、STT 选型(工具箱层已定 FunASR)

### 4.1 接入形态(与 0.9 rig 抽象对齐)

STT 走 0.9 定型的 `AIProvider` / rig-core 抽象——**不为语音单独造轮子**:

- **云端 STT**:走 rig `TranscriptionModel` trait(rig-core 0.39 已在 Cargo.toml)。
  > ✅ **调研 #2 已完成**:rig-core 0.39 内置 `TranscriptionModel` 的供应商共 **7 家**:OpenAI、Azure、Gemini、Groq、HuggingFace、Mistral、OpenRouter。Anthropic 无 transcription。国内供应商(讯飞/通义)需自实现 trait 或独立 client。
- **本地 STT**:引 [`sherpa-onnx`](https://docs.rs/sherpa-onnx)(v1.13.4,官方 Rust crate,`OfflineRecognizer` + `OnlineRecognizer`),**自实现 rig `TranscriptionModel` trait**(一次性场景),保持 Provider 抽象一致——上层调用不区分云端/本地。
- **流式场景**(G2 边说边出字):rig `TranscriptionModel` 是一次性异步(audio bytes → text),**装不下** `OnlineRecognizer` 的增量循环(accept_waveform → decode → get_result)。流式输入法可能需要一条独立的 `StreamingStt` 抽象,而不是硬塞进 `TranscriptionModel`——这是 0.10 架构待定点,详见 §六调研 #5。
  > 📝 **Review(逻辑性)**:hold-to-talk 方案下,用户**松开**才触发 STT 识别,天然是一次性场景。G1「说完进搜索框」完全不需要流式。G2「边说边出字」的流式是 UX 增强而非硬需求——0.10.1 可先用非流式(hold → 松开 → 识别 → 注入完整文字),0.10.2+ 再做流式增量上屏。这大幅简化了调研 #5 的紧迫性。
- **国内云端**(讯飞 / 通义):中文最佳但 rig 未内置,需自实现 trait 或独立 client。

### 4.2 三层架构(工具箱 × 引擎 × 模型)

> **STT 是三层,不是两层**——把 `whisper-rs` 与 `sherpa-onnx` 并列、或把 FunASR 当成单个模型,都是层级错位。正确划分:
>
> | 层 | 职责 | 回答什么问题 | Blink 的定稿 |
> |---|---|---|---|
> | **① 工具箱(toolkit)** | 管理 + 提供运行一组模型,带训练 / 导出 / 服务化工具链 | "用哪家的模型生态?" | **FunASR(modelscope / 阿里达摩院)** |
> | **② 引擎(runtime)** | 把模型 weights 跑起来的推理后端,决定 Rust 集成 / 跨平台 / 流式能力 | "在 Blink 进程里怎么调?" | **sherpa-onnx(官方 Rust crate)** |
> | **③ 模型(weights)** | 具体神经网络,决定中文质量 / 体积 / 是否流式 | "跑什么、中文多准、多大?" | 按场景挑(SenseVoice 起步 / Paraformer-streaming 真流式) |
>
> 典型链路:**FunASR 工具箱(产出 / 导出 ONNX)→ sherpa-onnx 引擎(加载推理)→ 模型(Paraformer / SenseVoice)**。

#### ① 工具箱层 —— 已定 FunASR

| 工具箱 | 出身 | 提供的模型生态 | 自带 runtime | 许可证 |
|---|---|---|---|---|
| **FunASR**(modelscope / 阿里达摩院)⭐**已选** | 中文 ASR 基本盘,SOTA 模型集散地 | Fun-ASR-Nano(LLM-ASR 旗舰)/ SenseVoice(CPU 友好 + 情绪/声学事件)/ Paraformer(低延迟流式)/ Qwen3-ASR 等 | ✅ 有 funasr-runtime(Win CPU x64 等) | MIT 代码 / 模型免费可商用 |
| OpenAI Whisper 生态(备选参考) | 多语种通用基线 | Whisper 全档(tiny→large) | 经 whisper.cpp / faster-whisper | MIT |

> **为什么工具箱选 FunASR**:FunASR 是**按场景挑模型的工具箱**,不是单个模型——Whisper 是"一个模型",FunASR 是"一个工具箱里装了 Nano / SenseVoice / Paraformer 等多个按场景分工的模型"。这正是 Blink 选它的核心理由:**一份集成、按场景切模型**。Whisper 生态是"一个模型打天下",中文场景下质量与速度都逊一档。Blink 用户基本盘是中文:Paraformer / SenseVoice 是 60k 小时中文语料训练的 SOTA,非自回归比 Whisper-Small 快 5×、比 Whisper-Large 快 15×;SenseVoice 自带语种识别 / 情绪 / 声学事件,可直接喂给 **Awareness 域**(未来可做「带情绪感知的语音指令」)。代码 MIT、模型免费可商用,无许可障碍。

#### ② 引擎层 —— 已定 sherpa-onnx

| 引擎 | 能跑的模型 | Rust 生态 | 流式 | 定位 |
|---|---|---|---|---|
| **sherpa-onnx**(k2-fsa / Next-gen Kaldi,Apache-2.0)⭐**已选** | **跨工具箱**:FunASR 全家(经 ONNX 导出)+ Whisper + Zipformer + nemo Parakeet | 官方 [`sherpa-onnx`](https://docs.rs/sherpa-onnx) crate v1.13.4,`OfflineRecognizer` + `OnlineRecognizer`,rust-api-examples 含 `sense_voice.rs` | ✅ 原生(`OnlineRecognizer`) | **Blink 默认引擎**——一套 Rust 集成覆盖所有候选模型 |
| `whisper-rs`(备选) | 仅 Whisper | 成熟 crate | 需配置 | 仅在"只要 Whisper"时备选 |

> **结论**:Blink 引擎层固定 **sherpa-onnx**。它不是 FunASR 的竞品,而是 **FunASR 模型在 Rust/ONNX 侧的部署通道**——FunASR 工具箱导出 ONNX,sherpa-onnx 加载推理。换模型不换引擎。

|---|---|---|---|---|---|---|---|
| **SenseVoice-Small** ⭐推荐起点 | FunASR | ⭐⭐⭐⭐ 强 | ⚠️ 非流式但极快(10s 音频 ~70ms,可分块伪流式) | ~230MB | **语种识别 + 情绪 + 声学事件**(可喂 Awareness 域) | 模型免费可商用 | `OfflineRecognizer` |

### 4.3 &lt; 100MB 安装包硬约束

本地 STT 涉及两部分体积,**都要算账**:

- **模型 weights**(几十~上百 MB):按需下载、默认不捆绑(与 0.11 本地 LLM / embedding 同规矩)。用户主动点「下载模型」才开始,进度可见、可暂停 / 取消。
- **onnxruntime 原生运行时**(sherpa-onnx 依赖):**这部分体积账旧版没算**。需在调研 #1 中确认——预编译 DLL 链接 vs 动态下载运行时,以及它进不进安装包。

> 📝 **Review(细节补充)**:sherpa-onnx crate 默认动态链接 onnxruntime——意味着运行时 DLL(~5-15MB)需随安装包分发或首次运行下载。spike #1 需确认:① 静态链接 onnxruntime 的可行性(可能需 `features` 配置);② 动态下载方案的国内网络可用性。

云端 STT 无体积问题,但要花钱 + 隐私(录音上云)。

### 4.4 VAD + 降噪(hold-to-talk 下的简化)

> 📝 **Review(已修订)**:原版将 VAD 钉进 0.10.0,作为「说完判定」的关键。hold-to-talk 方案下,用户**手动控制**录音起止(hold 开始 / release 结束),VAD 的「说完判定」职责被消解。

**hold-to-talk 下的 VAD 角色**:

| 场景 | 原 VAD 职责 | hold-to-talk 下 |
|---|---|---|
| 判断「说完没」→ 结束录音 | 核心职责 | ❌ 不需要——用户松开即结束 |
| 录音起止的静默裁剪 | 有用 | ✅ 仍有用——裁掉录音首尾的按键噪声 |
| 长时间静音自动停止 | UX 兜底 | ⚠️ 可选——hold 30s 无声音自动停止,防止忘松 |
| 降噪 | 有用 | ✅ 仍有用——环境噪声影响识别准确率 |

**结论**:VAD 从「0.10.0 硬需求」降级为「0.10.2 本地 STT 的优化项」。0.10.0 云端 STT 可依赖供应商侧的 VAD/降噪(OpenAI/Groq 的 whisper API 自带)。0.10.2 本地 STT 需轻量静默裁剪 + 可选降噪,但不是 blocker。

**流式 STT 的工程量(保留参考,0.10.2+ 适用)**:
- VAD(语音活动检测)、降噪、流式增量识别 + 中间结果上屏(避免抖动)——这是一整套管线
- 仅在 0.10.2+ 做真流式(Paraformer-streaming)时才需要

### 4.5 选型建议 ——「云端先行验证 + 产品默认本地」双轨

> 注意区分**工程顺序**与**产品默认值**——这是两条独立的轴:
> - **工程顺序**:0.10.0 先用云端 STT 跑通整条链路(零体积、中文好、不卡在本地集成上),验证「说话 → 转文字 → 进主窗口」成立;本地 STT 集成作为紧随其后的工作项(0.10.2)。
> - **产品默认值**(面向用户):**默认本地 STT**(若已下载模型),云端需用户显式开启——这条隐私铁则见 §八,不因工程顺序而松动。

1. **0.10.0 云端优先验证闭环**(工程顺序)——快、中文好、零体积,先把链路跑通
2. **产品默认 = 本地 STT,默认模型 FunASR SenseVoice-Small**(经 sherpa-onnx 跑 ONNX,int8 ~230MB,中文强 + 10s 音频 ~70ms,契合丝滑定位)
3. **真流式场景**(G2 边说边出字,0.10.2+)切 **FunASR Paraformer-streaming**(zh-en 双语,走 `OnlineRecognizer`)
4. **引擎固定 sherpa-onnx**(一套 Rust 集成覆盖 FunASR + Whisper 全家,换模型不换引擎)

**本地引擎(`sherpa-onnx`)的 Windows + Tauri 集成验证**是 0.10 能不能做成本地 STT 的最大未知——它是 0.10.2 的**前置门**(spike 不通过,本地 STT 整条线降级),详见 §六调研 #1。

## 五、文本注入通道(G2 的硬骨头,从零搭)

> **现状**:`grep` 全仓库,目前**没有任何「向外部前台应用注入文本」的机制**——无 `SendInput`、无模拟 `Ctrl+V`、无 UIA `ValuePattern`。G2 必须新建一条注入通道。
>
> 这是 0.10 与 G1 工程量拉开差距的地方。

### 5.1 候选方案(待 spike,0.10 暂不写死)

| 方案 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **剪贴板 + Ctrl+V** | 暂存原文到剪贴板 → 模拟 Ctrl+V → 恢复原剪贴板 | 最快最稳、兼容性最好 | 短暂占用剪贴板(需备份/恢复原内容,有竞态) |
| **SendInput 逐键** | 逐字符模拟键盘事件 | 不碰剪贴板 | 中文需走 IME 注入、对部分应用(游戏/控制台/UAC 窗口)失效,工程量大 |
| **UIA ValuePattern 优先 + 回退** | 优先 UIA 写入文本框,不支持的应用回退到剪贴板+Ctrl+V | 最干净 | 实现最复杂,且 UIA 不是所有控件都支持 |

> **采用建议**:具体选型留到 0.10.1 实施前 spike,文档只列三种方式 + 取舍。倾向「剪贴板 + Ctrl+V」作默认(实测对大多数应用足够),复杂控件回退考虑 UIA。

### 5.2 平台抽象预留

注入通道走 `src/infra/platform/` 的 `mod.rs` 接口 + `windows.rs` 实现模式(与现有 hotkey/window/selection/clipboard 一致)。预期新增 `platform::inject_text(text) -> Result<()>` 之类的抽象。

### 5.3 看门狗失焦检测的影响

注意:Blink 的失焦隐藏靠每 150ms 轮询 `GetForegroundWindow()` 按进程 PID 判定(见 AGENTS.md §4)。G2 注入文本到前台应用时,**不能让「注入动作」触发 blink 自己的失焦隐藏**——注入期间需与看门狗协调(如注入期间暂停失焦判定,或确保 blink 主窗不抢前台)。这是 0.10.1 必须验证的边界。

> 📝 **Review(细节补充)**:hold-to-talk 的 G2 场景下,主窗口始终**不显示**(用户没有 tap),blink 进程不在前台。注入时序为:hold 录音 → release → STT 识别(后台) → `inject_text()`。注入时 blink 主窗仍隐藏,看门狗不会误触发失焦隐藏。但 `SendInput`/`Ctrl+V` 模拟可能改变前台焦点,需验证注入后前台应用 PID 不变。

## 七、P0 不回归保证(0.10 最高优先)

> AGENTS.md §2 写死:快捷键 <50ms、首个结果 <20ms、常驻 <300MB、焦点成功率 >99.9%。且明说「如果用户按快捷键后不能立即输入,其他所有功能都没有意义」。
>
> 0.10 引入的所有新组件**全部压在这条主链路上**,必须逐条钉到性能预算——这是旧版文档的最大遗漏,本节补上。

| 新增物 | 对 P0 的威胁 | 保证措施 |
|---|---|---|
| **sherpa-onnx + onnxruntime 原生库** | 启动加载若进热路径 → 唤起延迟;DLL 链接失败 → 焦点链路受影响 | **lazy-link**:进程启动不加载 STT,首次语音才 dlopen/加载;STT 模块 panic 不得拖垮主链路 |
| **~230MB 模型 weights** | 撑爆 <300MB 常驻预算(WebView2 基线已 80–150MB) | **lazy-load + 用完可卸载**:模型不随启动驻留,首次语音才按需加载;长期不用可释放;**常驻预算只算运行时,不常驻模型** |
| **麦克风采集线程** | 阻塞 hotkey LL hook 回调 / 看门狗轮询 | 采集在独立 tokio task,**绝不进 LL hook 线程**;hook 回调全程 `CallNextHookEx` 放行不变 |
| **Hold 事件(hook 线程 timer)** | timer 回调阻塞 LL hook → 影响热键响应 | timer 仅发 `HotkeyEvent::Hold`,不执行录音逻辑;录音在独立 tokio task 启动;hook 线程零阻塞 |
| **G2 文本注入到前台** | 注入动作触发 blink 自己的失焦隐藏 | G2 时主窗不显示(无 tap),注入不抢前台;看门狗协调见 §5.3 |

> 📝 **Review(已修订)**:原版 P0 表有「新 chord(Alt+V)前端拦截」行——hold-to-talk 方案下无新 chord 键,改为「Hold 事件(hook 线程 timer)」行。原版的 `CHORD_KEYS` 白名单冲突矩阵不再适用。

**验收红线**:0.10 任何改动不得使「Alt+Space tap → 窗口出现 → 自动 Focus → 输入」这条主链路的延迟/成功率劣化。CI 无法覆盖,靠 `cargo run` 手动回归 + SLO 埋点(`perf` metric)监控。

**特别注意**:Hold 事件的 timer 实现必须保证——tap 路径(keyup ≤ threshold)的延迟不受 hold timer 影响。即:tap 的 `send_event(HotkeyEvent::Tap)` 必须在 keyup 时**立即**触发,不受 timer 是否已 fire 影响。

## 八、语音隐私升级

语音是**比文本敏感一个量级**的数据(声纹是生物特征):

- **默认本地 STT**(若已下载模型);云端 STT 需用户显式开启
- **第一次启用语音必须有强告知门**:发给谁、发什么(录音还是文本)、存不存、能关什么
- 录音不持久化、不入 SQLite;成功只记时长
- 敏感应用黑名单生效时跳过(银行、密码管理器)
- 详见 [product-context-future.md §8](./../product-context-future.md#8-隐私与安全) 升级章节

## 九、Agent 对话窗口(可选 / 后置)

> 本节为**降级保留**内容——Agent 窗口是独立的交互形态,与「语音转文字」正交。不作为 0.10 硬交付,若 0.10.0–0.2 提前完成再做,或整体移出 0.10。

### 9.0 rig 能力开放(与 0.9 §4.3 边界对齐)

Agent 窗口是**用户显式授权 tool loop** 的场景——用户点 Alt+1 展开就是"要跟 AI 对话让它办事",与主窗口"在搜索"的心智不同。因此 rig 用法在 Agent 窗口全面放开:

- ✅ 允许 `rig::AgentBuilder` 自动 tool dispatch loop(安全动作)
- ✅ 允许 `Prompt` / `TypedPrompt` 管消息历史
- ✅ 允许 `rig::agent::memory` 做会话短期记忆(长期记忆留 0.11 RAG)
- ✅ 允许 Structured output(`prompt_typed`)结构化返回
- ⚠️ `Action::danger_class() == Dangerous` 的动作**不进 AgentBuilder tools 池**,或用带 pre-exec hook 的封装 tool——hook 里产 Suggestion 走人机确认,即使 AI 自主决定要调,也必须 Tab 确认

**为什么这不算破四域信任边界**:四域边界的核心是"参数注入必须显式(`ExecArg::UserExplicit`)"和"AI 不能构造用户未确认的执行参数"。Agent 窗口内**每次工具调用的 arguments 都已经经过 AI 结构化输出+可选 pre-exec 确认**,`UserExplicit` 类型墙在 Agent 窗口的模型改为「用户显式授权了整个会话」——这是**授权粒度从"每次工具"扩到"整个会话"**的产品决策,不是拆掉铁则。

详见 [0.9-ai-layer.md §4.3](./0.9-ai-layer.md#43-provider-落地形态2026-07-定型) 和 [§11.3](./0.9-ai-layer.md#113-rig-能力开放清单按交互模式分层)。

### 9.1 展开时机(不自动展开)

轻量路由判定「需要多轮 / 主窗口不够展示」时,**不自动展开**——而是产一个 Suggestion「Alt+1 展开对话」,用户确认才展开。

理由:自动展开会抢焦点、打断心流,和「丝滑」冲突。这延续四域信任边界——**显式确认才穿过到新交互范式**。

### 9.2 窗口形态

- 复用同一 WebviewWindow,切换到 chat template(0.8.4 view 字段预留 `view: chat`)
- 类 ChatGPT 布局:消息流 + 输入框
- **流式 MD 渲染**(打字机效果 + 代码高亮 + 复制按钮)
- ESC 返回搜索模式

### 9.3 确认反馈(走统一 kbd 体系)

展开 / 拒绝用快捷键确认,走 `kbd.js` 统一渲染(见 [product-principles.md §14.7](./../product-principles.md#147-键盘提示样式统一强制规则)):

| 键 | 动作 |
|---|---|
| `Alt+1` | 展开成 Agent 对话窗口 |
| `Alt+2` | 拒绝 / 取消执行 |

### 9.4 Context 注入(复用 0.9,可关)

Chat 消息自动带上的 Context(当前剪贴板 / 最近选区 / 前台应用)与用户显式引用(`@选区` / `@剪贴板`),**复用 0.9 已有的 context 注入开关**,不再单列规格。
