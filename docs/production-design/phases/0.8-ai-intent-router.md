# Blink 0.8 — 意图路由优化 + AI 能力基础

> **范围**：意图路由优化（无 AI） + AI Provider 抽象 + 基础 AI 插件
>
> **原则**：本体保持轻量，复杂 AI 能力放插件，本地模型按需下载，不强制捆绑。

## 一、意图路由优化（无 AI，0.8.0）

### 1.1 选中文本感知

加强 Context 感知能力：当鼠标选中文本时能感知到，方便后续进行意图识别。例如：

- 选中的文本非目标语言时，提供「翻译」
- 选中的内容是 URL 时，提供「默认打开」

#### 需求边界（先厘清，别混淆）

区分两种状态，机制完全不同：

- **已复制**（剪贴板里有内容）→ 即 §1.2 在做的事，blink 已有 `clipboard.rs` 监听，**不需要新机制**。
- **选中但没复制**（鼠标划选/双击选词，剪贴板没动）→ 本节要解决的，也是「`Ctrl+C` 方案」想覆盖却有副作用的场景。

下面只讨论第二种。

#### 方案对比

| 方案                              | 原理                                          | 覆盖面                                       | 影响终端          | 评价           |
|----------------------------------|----------------------------------------------|---------------------------------------------|-------------------|----------------|
| **UIA TextPattern**（划词瞬间抓） | `FindAll` 子树遍历 → `GetSelection()` → `GetText()` | **实测较广**：记事本/Office/VS Code/Typora/Chrome 网页 ✅；仅 Scintilla(Notepad++)/Java 不行 | ❌ 不影响 | **主推** |
| Win32 `EM_GETSEL`/`WM_GETTEXT`   | 直接问控件                                     | 极窄（只对原生 Edit/RichEdit；Chromium/Electron/Qt/WPF 自绘全废） | ❌ | 覆盖太低，放弃   |
| MSAA `IAccessible::get_accValue` | 老无障碍接口                                   | 窄、不稳定                                   | ❌                | UIA 前身，不如直接上 UIA |
| 模拟 `Ctrl+C` + 备份恢复剪贴板    | 发按键再读剪贴板                               | 几乎全覆盖                                   | ⚠️ 终端触发中断    | 仅作最后兜底，且必须排除终端 |

#### 方案演进：从「invoke 后抓」到「划词瞬间抓」（关键转折）

最初按主方案落地：`invoke` 在 show 后 spawn UIA 抓取。**实测翻车**——Electron 应用（Chrome/Typora）全军覆没：show 后 blink 抢焦点，Chromium 失焦退化选区（`GetSelection` count=1 但 `GetText` 空）。

根治：**把抓取时机从「唤起瞬间（焦点将失）」提前到「划词瞬间（焦点未失）」**——全局鼠标钩子监听选词动作，在选词发生的**黄金时机**抓取。

实测反转：Typora 救活，**Chrome 网页也意外通了**（candidates 1→59）——划词的 UIA 查询触发了 Chromium 懒启用的 a11y，网页正文 Document 暴露出来。

#### 选词监听架构（已落地）

- **钩子**：`WH_MOUSE_LL` 专用线程（复用 hotkey 的 `SetWindowsHookEx` + 消息循环范式）。回调极轻（LowLevelHooksTimeout ~300ms 超时会被系统摘钩），只做选词检测，UIA 抓取丢独立线程。
- **选词检测**：拖拽划选（down→up 位移 >6px）+ 双击选词（两次 up 间隔 ≤500ms、位移 ≤系统双击距离）。纯函数可单测。
- **抓取**：命中 → 独立线程调 `get_selected_text(GetForegroundWindow())`（此刻前台是原应用）→ 缓存。
- **缓存**：`selection::CACHE`（`OnceLock<RwLock>`，独立于 SearchService 以避免 infra→domain 反向依赖），TTL 10s，不持久化。
- **唤起**：`invoke` 读 `get_last_selection()` → `update_selected_text` 回填 snapshot。

#### UIA 抓取（get_selected_text）

`CoInitializeEx(MTA)` RAII → `CUIAutomation` → `ElementFromHandle(顶层 HWND)` → `FindAll(Subtree, IsTextPatternAvailable)` 遍历候选 → `GetCurrentPattern` → `GetSelection` → 首个非空 `TextRange` 的 `GetText`。

- **FindAll 而非 FindFirst**：子树常有多个 TextPattern 元素（Chrome 地址栏 Edit + 网页 Document），FindFirst 易命中无选区的（地址栏）。
- **候选上限 64** 保护性能；COM 用 MTA，复用图标提取 RAII 范式（图标是 STA，互不影响）。

#### 覆盖面与 Fallback（实测定案）

| 应用类型 | 实例 | 结果 |
|---|---|---|
| 原生 Win32/WPF | 记事本/Office/VS Code | ✅ |
| Electron | Typora、Chrome 网页 | ✅（划词触发 a11y） |
| Scintilla | Notepad++/Notepad3/Geany | ❌ 控件不暴露 UIA |
| Java Swing | RustRover(IntelliJ) | ❌ 控件不暴露 UIA |

**Ctrl+C 兜底：决定不做**。调研证实（[SO #36067563](https://stackoverflow.com/questions/36067563) 等）——Windows 没有「不碰剪贴板的复制 API」，UIA 是唯一无副作用的；Ctrl+C 必然经过系统剪贴板，且**无法避免污染剪贴板历史**（备份恢复只救当前内容，救不了历史工具已记录的那条）。每次划词塞一条历史，不可接受。

**非 UIA 应用的替代路径**：用户主动 Ctrl+C → 现有 `clipboard.rs` 监听捕获（`clipboard_text`）。契合需求边界——选中未复制 → UIA 划词；已复制 → 剪贴板监听。两条无副作用的路，不需要自动 Ctrl+C。

**分层读取（按需扩展）**：UIA 不支持的应用若想无副作用抓取，可补控件特化消息——L2 Scintilla `SCI_GETSELTEXT` / Edit `EM_GETSELTEXT`（救 Notepad++）、L3 Java Access Bridge（救 IntelliJ）。当前只做 L1 UIA，L2/L3 按需再做。

#### 落地步骤

1. ✅ UIA 抓取原语 `selection::windows::get_selected_text`（`FindAll` 子树遍历，失败返 `None`）。
2. ✅ 选词监听 `selection::listener`（`WH_MOUSE_LL` + 拖拽/双击检测 + 缓存 TTL 10s）。
3. ✅ `invoke` 读 `get_last_selection()` → `update_selected_text` 回填 `ContextSnapshot.selected_text`。
4. ⏸ `RuleRouter` 接入：选区/剪贴板是 URL/外文 → **翻译/GitHub 等插件**动作置顶（纯逻辑，可单测）。
   - **当前状态**：§1.3 已在 `BuiltinEngine` 内实现"剪贴板 URL / 文件路径 → 内置动作置顶"，覆盖 §1.2 表格中"http:// / 文件路径"两行的**内置动作侧**。
   - 剩余"翻译代码 / GitHub 打开仓库"等**插件路由侧**依赖具体插件消费者存在——等 0.8.2+ 有实际插件时再补 RuleRouter 接入。

#### 隐私（§7 合规）

选区文本只进内存 snapshot、不持久化；划词成功 `debug` 级只记长度，内容仅 `trace` 级记前 100 字符；失败（无选区/不支持）走 `debug`/`trace` 降级。

### 1.2 Context 感知路由（无 AI）

**问题**：复制了代码后还得手动输入「翻译」。

**方案**：

- 简单规则引擎，根据 Context 状态调整插件优先级
- 纯规则，不涉及 AI 推理

| Context 状态              | 路由调整                 |
|--------------------------|--------------------------|
| 前台是 VS Code + 剪贴板是代码 | 「解释代码」「格式化」插件置顶  |
| 前台是浏览器 + URL 是 GitHub  | 「打开仓库」「搜 Issue」插件置顶 |
| 剪贴板是 `http://`         | 「打开链接」「下载」动作置顶    |
| 剪贴板是文件路径            | 「打开目录」「在资源管理器定位」置顶 |

**实现量**：中，`RuleRouter` 接入 `ContextSnapshot` + 规则配置。

### 1.3 内置动作抽象升级（Context 路由的载体）

> 前提：§1.2 表里"打开链接 / 打开目录 / 在资源管理器定位"这些是**参数化 Action**，不是插件也不是搜索候选，现有 `BuiltinEngine::ActionKind` 撑不住——扩展它，作为 Context 感知路由的载体。

#### 症结（现状体检）

`src/domain/search/builtin_engine.rs` 当前的 Action 模型问题：

1. **能力 & 执行混淆**：`ActionKind` 枚举既是能力声明也是分派 tag，加动作必动这个枚举。
2. **无参数化能力**：现有 Action 全是无参操作（锁屏/关机）；`打开链接(url)`、`打开目录(path)` 这类**参数从 Context 拿**的动作塞不进。
3. **魔法字符串分派**：`__BLINK_ACTION_OPEN_SETTINGS__` 等塞进 `SearchAction::Open { path }`，前端 `launch_app` 判字符串再回调后端——耦合越写越多，跟"内置动作是一等公民"的定位相反。
4. **Context 无入口**：`search()` 已经拿到 `ctx.snapshot` 但完全没用；要接 §1.2 得给动作声明"哪些 Context 触发我"。
5. **设置页看不见**：动作藏在 const table 里，用户只能看到"引擎开关"这个颗粒度。

#### 数据模型扩容

**关键约束**：不引入新类型名（`Action` / `ActionKind` 已被前端契约 struct 占用），继续扩现有 `BuiltinAction`。**枚举变体只放 0.8.0 会真的用到的**，`is_code`/`QueryRest`/`ForegroundIs` 等预留项等真有消费者再加，避免"永远返回 false 的诱饵"。

```rust
struct BuiltinAction {
    id: &'static str,
    title: &'static str,
    subtitle: &'static str,
    keywords: &'static [&'static str],
    kind: BuiltinActionKind,
    // 新增 ↓
    context: &'static [ContextTrigger],  // 空 = 不参与 Context 路由
    param_source: ParamSource,           // None = 无参
    default_enabled: bool,               // 用户没配置时的默认启用状态
}

enum ContextTrigger {
    ClipboardIsUrl,
    ClipboardIsFilePath,
    SelectionNonEmpty,
    // 预留（0.8.0 不实现）：ClipboardIsCode / ForegroundIs
}

enum ParamSource {
    None,
    Clipboard,
    Selection,
    // 预留（0.8.0 不实现）：QueryRest ——需要 query 抽 rest 解析，无消费者
}

enum BuiltinActionKind {
    // 现有(全部 param_source=None, context=&[])
    OpenSettings, LockWorkstation, Shutdown, Restart, Sleep,
    ClearHistory, ExitBlink, OpenLogs, OpenDataDir,
    // 0.8.0 新增(参数化)
    OpenUrl,          // param_source=Clipboard, context=[ClipboardIsUrl]
    OpenPath,         // param_source=Clipboard, context=[ClipboardIsFilePath]
    RevealInExplorer, // param_source=Clipboard, context=[ClipboardIsFilePath]
}
```

#### 匹配规则（关键行为约定，必须写死）

- **同一 Action 至多产出一个 `SearchItem`**：两路都命中时**分数合并**（取 `max(keyword_score, ctx_score)`，不做加法避免与其他引擎失衡），不产出两条。
- **空 query 场景**（用户 Alt 后不输入）：**只召回 Context 命中的动作**，其他内置动作不出现。这是产品行为改动——现在空 query `return Vec::new()`，改后空 query 是 Context 感知的主战场。
  - **排序保证**：空 query + Context 命中 → `base_score = 1.0`（与最高优先级候选平齐），确保排在首屏首位；防止被剪贴板历史/最近使用挤下去。
- **query 非空场景**：原 keyword/拼音匹配 + Context 命中双路并召回，Context 命中给 base_score 加成而非独占（`ctx=+0.3`）。
- **参数校验**：Action 声明 `param_source: Clipboard`，但 `snapshot.clipboard_text` 为 None → **不召回**（不出现"打开链接"配空参数的僵尸候选）。
- **Context 命中评分**：`SearchItem.source = "builtin"` 保持不变；Context 加成走 `score_detail` 里的一路（`ctx=+0.3`），便于调参可观测。
- **去重键 `SearchItem.id`**：**统一用 `builtin:{action_id}`**，参数不进 id。同一 Action 在融合层保留一条即可；不同参数产生不同项在 0.8.0 无场景（空 query 场景下 clipboard 只有一个值）。

#### 分派链改造（废魔法串）

`SearchAction` 加变体、`ActionKind`（前端契约）加变体：

```rust
// domain/search/engine.rs
enum SearchAction {
    None, Open { path }, Copy { text },
    RunAction { id: String, arg: Option<serde_json::Value> },  // 新增
}

// domain/search/mod.rs (前端契约 ActionKind)
enum ActionKind { Open, Copy, RunAction }  // 新增 RunAction
```

**arg 用 `serde_json::Value` 而非 `String`**：0.8.0 三个新动作填的是 URL/路径字符串（`Value::String(...)`），但未来 Action 收结构化参数（选区文本+目标语言）时无需再改前后端契约；`Option<Value>` 序列化到前端就是 `null` / 字符串 / 对象，无损。

前端命中 `RunAction` → `invoke("run_builtin_action", { id, arg })` → 后端一次 `match id`。`__BLINK_ACTION_XXX__` 魔法串完全废除。**注意有两处消费方**：
1. 搜索结果点击 → `frontend/js/actions.js`（或 `launch_app` 调用点）分派 `Open` → 改成命中 `RunAction` 就走 `run_builtin_action`。
2. **右键菜单** `frontend/js/contextmenu.js:146-156` 目前直接 `launchApp("__BLINK_ACTION_OPEN_SETTINGS__")` 和 `launchApp("__BLINK_ACTION_EXIT__")` → 改为 `invoke("run_builtin_action", { id: "open_settings", arg: null })`。`isRealPath` 那个 `startsWith("__BLINK_ACTION_")` 判断也同步删掉。

后端 `commands::parse_builtin_action` / `execute_builtin_action` / `BuiltinActionKind`（当前 commands.rs 里的私有 enum）→ 全部删除，改由 `run_builtin_action(id: String, arg: Option<Value>)` 里一次 `match id.as_str()` 分派。

#### Context 探测：独立纯函数模块

新增 `src/domain/context/probe.rs`，纯函数、无 Windows API 依赖，可单测：

```rust
pub fn is_url(s: &str) -> bool;        // http://, https://, file://, ftp://
pub fn is_file_path(s: &str) -> bool;  // Windows 绝对路径 / UNC / 常见文件扩展名
// pub fn is_code(s: &str) -> bool;    // 0.8.0 不做,预留
```

**放 `domain/` 而非 `infra/platform/context/`**——判定逻辑没有任何平台调用，放 platform 下会误导读者。`BuiltinEngine` 与后续 `RuleRouter`（`domain/intent/`）共用同一套判定，别写两份。

#### Disable 状态：内存快照，不走热路径 SQLite

`BuiltinEngine::search` 在 sync lane 是首批召回，**不能每次 search 都查 SQLite**。方案：

- `AppConfig` 加字段 `disabled_builtin_actions: Vec<String>`（存 action id），随 `config` 表 KV 一起加载 + 热更新。
- `BuiltinEngine::search` 直接读 `QueryContext` 里的 config 快照（或引擎构造时注入 `Arc<RwLock<AppConfig>>`，与其他引擎的配置读取范式一致）。
- 设置页勾选 disable → 写回 SQLite + 触发 config 热更新事件 → 引擎下次 search 即生效。

#### 设置页

`commands::list_builtin_actions() -> Vec<BuiltinActionInfo>` 返回所有动作元数据 + 当前 enabled 状态：

```rust
struct BuiltinActionInfo {
    id: String,
    title: String,
    subtitle: String,
    keywords: Vec<String>,        // 展示"输入这些词可触发"
    trigger_desc: Option<String>, // "剪贴板是 URL" / "关键词 + 剪贴板是 URL" —— 补充说明；纯 keyword 触发返回 None（keywords 行已表达）
    param_desc: Option<String>,   // "参数来自剪贴板" / None —— 预格式化文案
    enabled: bool,
    default_enabled: bool,        // 让设置页显示"已改动过"的视觉提示
}
```

设置页新增「内置动作」面板：
- 列表展示以上字段
- 每项一个 disable 开关（写回 `AppConfig.disabled_builtin_actions`，与其他配置项走同一套 KV 命名空间 `app_config`，无需新增 `builtin_action:{id}` 命名空间——单个字段是 `Vec<String>` 更简洁）
- **图标策略**：后端不提供图标；前端按 `id` 映射一张 SVG（沿用现有 9 个动作的做法），新增 3 个动作补 3 张 SVG（🔗 打开链接 / 📁 打开目录 / 🗂 资源管理器定位）
- 0.8.0 **只做只读展示 + disable 开关**，不让用户改 keyword、不让用户绑 Chord（那是 0.8.1 的事）

- **命名沿用 `BuiltinAction`**：避免跟前端契约 `Action` / `ActionKind` 起冲突。
- **枚举变体只放 0.8.0 有消费者的**：`ClipboardIsCode` / `ForegroundIs` / `QueryRest` 全部延后——挂着"永远返回 false 的变体"会误导后续读者、遮蔽真实覆盖面。
- **参数来自 Context，不做本地 NER**：`param_source` 只从 Clipboard / Selection 两处取——上一轮讨论已定案，本地 BERT NER 不划算，长句参数走 0.8.3 AI function calling。
- **`RunAction.arg` 用 `Option<serde_json::Value>` 而非 `String`**：Tauri 前后端契约稳定后改起来麻烦，一次到位；0.8.0 传字符串就是 `Value::String(...)`，零成本。
- **Disable 状态用 `AppConfig.disabled_builtin_actions: Vec<String>` 内存快照**：不走 SQLite 热路径；比每 action 一条 `builtin_action:{id}` KV 更省一次查询、单字段热更新也更简单。
- **`context::probe` 放 `domain/context/` 不放 `infra/platform/context/`**：纯字符串判定无平台调用；`RuleRouter`（`domain/intent/`）与 `BuiltinEngine`（`domain/search/`）共用同一套判定。
- **空 query 从"不召回"改到"Context-only"**：这是本次最大的产品行为改动，要在 `blink://shown` 事件后前端立即拿一批 Context 建议动作，验收时重点观察。

// 仅定义在 plugin 模块，core 不依赖
pub trait AIProvider: Send + Sync {

- ❌ 不做复杂的 Provider 管理

### 2.2 云端 AI 插件（OpenAI 兼容）

## 五、Chord 模式：按住修饰键+二次快捷键（0.8.x，新增）

> **灵感来源**：Quicker + 键盘驱动的全局动作层
>
> **核心理念**：从「按 Alt 唤起→输入搜索」的被动模式，扩展为「按住 Alt→直接触发动作」的主动模式。

### 5.1 交互流程

```
用户按住 Alt（不松开）
     ↓
┌─────────────────────┐
│  Blink 窗口出现        │
│  提示：按住 Alt + ...  │
└─────────────────────┘
     ↓     ↓     ↓
  +A     +Q     +空格...
  截图   划词   语音输入
```

**关键细节**：
- Alt **按住不放**是进入 Chord 模式的信号
- 二次按键在 Alt 按住期间按下，**不需要松开再按**
- 窗口出现时显示可用的 Chord 快捷键提示（如底部状态栏）
- Alt 松开 → 退出 Chord 模式，回到正常搜索输入

### 5.2 第一批 Chord 动作

| 组合键 | 动作 | 说明 |
|---|---|---|
| `Alt + A` | **区域截图** | 进入截图模式，拖动选择区域 → 自动复制到剪贴板 |
| `Alt + Q` | **智能划词** | 主动触发划词文本抓取（比监听更可靠）+ 翻译/搜索动作弹出 |
| `Alt + C` | **剪贴板历史** | 直接打开剪贴板历史面板（跳过搜索） |
| `Alt + Space` | **语音输入** | 预留（按住期间语音识别，松开结束） |

### 5.3 技术实现路径

**状态机扩展（`hotkey/windows.rs`）**：

```rust
// 当前状态机（三字段）
down_since: Option<Instant>,
armed_key: Option<VKey>,
aborted: bool,

// 扩展 Chord 模式
chord_mode: bool,              // 是否进入 Chord 模式（Alt 按住超过阈值）
chord_triggered: Option<VKey>, // 已触发的二次键
```

**判定逻辑**：
1. Alt `keydown` → 正常 arm，开始计时
2. **按住超过 200ms**（可配置）→ 标记 `chord_mode = true`，窗口提前出现并显示 Chord 提示
3. Chord 模式期间收到其他键 `keydown` → 匹配 Chord 动作表，触发对应动作
4. Alt `keyup` → 若 `chord_triggered.is_some()` 则不进入搜索；否则焦点到输入框

**与现有逻辑兼容**：
- 快速单击 Alt（< tap_threshold）→ 原有行为：唤起窗口，焦点到输入框
- 长按 Alt（> chord_threshold）→ 进入 Chord 模式，等待二次键
- 长按后松开且未按二次键 → 退化为正常搜索模式

### 5.4 产品价值

1. **肌肉记忆更强**：按住 Alt 的同时按 A/Q/C，手指不需要离开主键区
2. **跳过搜索步骤**：常用动作直接触发，不需要输入关键词
3. **扩展性极强**：后续可以加：
   - `Alt + T` 翻译选区
   - `Alt + S` 搜索选区
   - `Alt + M` 数学计算
   - `Alt + D` 词典
4. **差异化竞争**：Wox/Listary/Flow Launcher 都没有这个交互模式
