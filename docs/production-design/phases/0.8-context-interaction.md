# Blink 0.8 — 感知与操作层

> **范围**：意图路由优化 + Autosuggestion 补全 + 翻译插件 Context 感知路由 + Chord 模式底层能力
>
> **主题**：让 blink 更懂用户在做什么，让操作路径更短、更快。**AI 相关能力（Provider / Chat / Embedding）全部移至 0.9**。
>
> **原则**：本体保持轻量，纯感知/交互层无外部依赖。

### 1.1 选中文本感知（UIA 划词）

**成果**：`ContextSnapshot.selected_text` 通道打通 —— 用户划选文本瞬间被抓取并缓存，`invoke` 时回填 snapshot。

#### 覆盖面（实测定案）

| 应用类型 | 实例 | 结果 |
|---|---|---|
| 原生 Win32/WPF | 记事本 / Office / VS Code | ✅ |
| Electron | Typora / Chrome 网页 | ✅（划词触发 Chromium 懒启用 a11y） |
| Scintilla | Notepad++ / Notepad3 / Geany | ❌ 控件不暴露 UIA |
| Java Swing | RustRover (IntelliJ) | ❌ 控件不暴露 UIA |

Scintilla / Java 兜底：用户主动 Ctrl+C → 走既有 `clipboard.rs`。分层扩展 L2 `SCI_GETSELTEXT` / L3 Java Access Bridge **按需再做**。

#### 关键工程教训（供后续版本参考）

- **黄金时机原则**：抓取时机必须在**焦点未失**时。最初 `invoke` 在 show 后再抓 → Electron 全军覆没（Chromium 失焦退化选区）。改为 `WH_MOUSE_LL` 监听划词瞬间抓取后，Typora/Chrome 反转成功。0.8.3 Chord 抓 Context 也要遵守此原则。
- **Ctrl+C 兜底决定不做**：Windows 没有"不碰剪贴板的复制 API"，`Ctrl+C` 必然污染剪贴板历史（备份恢复救不了历史工具已记录的那条）。不可接受。
- **UIA 用 `FindAll` 而非 `FindFirst`**：Chrome 地址栏 Edit + 网页 Document 同为 TextPattern 元素，FindFirst 易命中无选区的地址栏。候选上限 64 护性能。
- **COM 用 MTA 不与图标提取（STA）冲突**：`selection::CACHE` 独立于 SearchService，避免 infra→domain 反向依赖。

#### 遗留 ⏸

§1.1 落地步骤原有一条 "⏸ `RuleRouter` 接入：选区/剪贴板是外文 → 翻译插件动作置顶" —— **拆到 §三（0.8.2）单独完成**。§1.3 已完成"剪贴板 URL / 文件路径 → 内置动作置顶"的**内置动作侧**。

#### 隐私

选区文本只进内存 snapshot，不持久化；成功 `debug` 级只记长度，内容仅 `trace` 级记前 100 字符。

### 1.3 内置动作抽象升级（Context 路由的载体）

**成果**：`BuiltinAction` 从"无参操作 + 魔法串分派"升级为"参数化 Action + Context 感知 + 一等公民"。

#### 数据模型（供 0.8.3 Chord 复用）

```rust
struct BuiltinAction {
    id: &'static str,
    title: &'static str,
    subtitle: &'static str,
    keywords: &'static [&'static str],
    kind: BuiltinActionKind,
    context: &'static [ContextTrigger],  // 空 = 不参与 Context 路由
    param_source: ParamSource,           // None = 无参
    default_enabled: bool,
}

enum ContextTrigger {
    ClipboardIsUrl, ClipboardIsFilePath, SelectionNonEmpty,
    // 预留 ClipboardIsCode / ForegroundIs（0.8.0 不实现，等消费者）
}

enum ParamSource {
    None, Clipboard, Selection,
    // 预留 QueryRest（无消费者）
}

enum BuiltinActionKind {
    // 无参：OpenSettings, LockWorkstation, Shutdown, Restart, Sleep,
    //       ClearHistory, ExitBlink, OpenLogs, OpenDataDir
    // 参数化：OpenUrl (剪贴板 URL), OpenPath (剪贴板路径), RevealInExplorer
}
```

#### 匹配规则（0.8.2 翻译路由沿用同套约定）

- **同一 Action 至多产出一个 `SearchItem`**：keyword 与 Context 双路命中时取 `max(keyword_score, ctx_score)`。
- **空 query 场景**：只召回 Context 命中动作，`base_score = 1.0` 保证排首屏首位。这是 0.8.0 最大产品行为改动 —— 空 query 从"不召回"改成"Context 感知主战场"。
- **参数校验（Context 门禁）**：Action 声明 `param_source: Clipboard`，但 `snapshot.clipboard_text` 为 None → **不召回**。避免"打开链接"配空参数的僵尸候选。
- **`SearchItem.id` 去重**：`builtin:{action_id}`，参数不进 id。

#### 分派链（废魔法串）

```rust
// 新契约
enum SearchAction { None, Open{path}, Copy{text}, RunAction{id, arg: Option<Value>} }
enum ActionKind { Open, Copy, RunAction }
```

前端命中 `RunAction` → `invoke("run_builtin_action", { id, arg })` → 后端 `match id`。`__BLINK_ACTION_XXX__` 魔法串全部废除（含右键菜单）。

#### 交付清单

- ✅ **代码**：`BuiltinAction` 扩字段；`domain/context/probe.rs`（`is_url` / `is_file_path` + host 结构启发式）；`AppConfig.disabled_builtin_actions`；`run_builtin_action` command；`BuiltinEngine::search` 双路匹配 + Context 门禁 + 拼音派生匹配（`shezhi`/`dakaishezhi`/`guanj`）
- ✅ **UI**：设置页「内置动作」面板（12 项 + emoji 图标 + disable 开关 + 热更新）；`.context-aware` 视觉强调（3px accent + monospace 参数预览）；`shown` 事件后前端主动拉 Context 建议
- ✅ **测试**：`context::probe` 18 例 + `builtin_engine` 12 例；`cargo test` 129 passed

#### 跨版本决策备忘（0.8.2 / 0.8.3 / 0.9 需要知道的）

- **`context::probe` 放 `domain/context/` 不放 `infra/platform/context/`**：纯字符串判定无平台调用；`RuleRouter`（`domain/intent/`）与 `BuiltinEngine`（`domain/search/`）共用，别写两份。**0.8.2 `is_non_target_lang` 加在同一模块**。
- **参数来自 Context，不做本地 NER**：`param_source` 只从 Clipboard / Selection 取。本地 BERT NER 不划算，长句参数走 **0.9 AI function calling**。
- **`RunAction.arg` 用 `Option<serde_json::Value>` 而非 `String`**：前后端契约一次到位。0.8.0 传字符串就是 `Value::String(...)`，未来收结构化参数无损。
- **Disable 状态用 `AppConfig.disabled_builtin_actions: Vec<String>` 内存快照**：不走 SQLite 热路径。**0.8.3 Chord 动作 disable 复用同套机制**（`disabled_chord_actions`）。
- **不升格独立 `domain/action/` 模块**：0.8.0 只扩字段，改动局限在 `search::builtin_engine`。**0.8.3 Chord 真的接入时再看扩散度决定是否抽**。
- **`BuiltinAction` 命名沿用**：避免跟前端契约 `Action` / `ActionKind` 起冲突。

## 二、Autosuggestion / Ghost Text 输入补全（0.8.1）

> **动机**：现有 `match_keyword` 把「汉字精确匹配」和「首拼命中」都塞进 `MatchType::Prefix` → `Auto` 一律升级 Takeover。首拼是**弱信号**（`fy` 可能命中"翻译"，也可能是用户想搜同名应用/命令），强制 Takeover 会截断本地引擎结果。**插件生态扩大后，随便一个首拼冲突就会误炸普通查询**。
>
> **策略**：把首拼降级为**普通匹配 + 分值加成**（不独占），配合 ghost text 提示"更规范的 keyword"，用户按 Tab 才显式进 Takeover。**"独占"这件事从此只来自明确意图信号**：完整键入 keyword，或显式按 Tab。
>
> **为什么优先做**：解耦度最高——不动 Chord 状态机、不动感知层、不动插件协议，只在意图路由 + 输入框做局部改造。快速验证输入交互质感。

### 2.1 交互设想

```
用户输入:  fy hello|
输入框显示: fy hello| →fanyi hello   (灰色半透明补全,行内 overlay)
按 Tab   → 输入框替换为: fanyi hello| （keyword + arg 整段替换）→ 立即触发 Takeover
按 Enter → 走当前搜索结果 top-1（可能是别的应用,不进 Takeover）
按 →     → 循环切换下一个补全候选（多 keyword 命中时）
按 Esc / 继续输入 → 关闭/更新补全
```

**无参场景**：

```
用户输入:  fy|
输入框显示: fy| →fanyi              (显示 ghost text)
Priority 排位: 翻译插件占位卡在首位（本地引擎结果保留在下方）
按 Enter → 走 top-1（可能是翻译占位卡也可能是其他）
按 Tab   → 输入框替换为: fanyi | （尾随空格）→ 触发 Takeover 等参数
```

### 2.2 路由行为对照表

| Query 类型 | 例子 | 当前 (0.8.0) | 目标 (0.8.1) | 备注 |
|---|---|---|---|---|
| 汉字 Exact | `翻译` | Priority | Priority | 保持 |
| 汉字 Prefix + arg | `翻译 hello` | Takeover | Takeover | 保持 |
| Latin Exact | `translate` | Priority | Priority | 保持 |
| Latin Prefix + arg | `translate hello` | Takeover | Takeover | 保持 |
| Pinyin_full Exact | `fanyi` | Priority | Priority | 保持（完整拼音是强意图） |
| Pinyin_full Prefix + arg | `fanyi hello` | Takeover | Takeover | 保持（完整拼音是强意图） |
| **首拼 Exact** | `fy` | Priority | **Priority + ghost text `fanyi`** | 保留 Priority，加 ghost |
| **首拼 Prefix + arg** | `fy hello` | **Takeover** | **Inline + ghost text `fanyi hello`** | **降级到 Inline**（核心改动） |
| 部分拼音 fuzzy | `fan` / `fany` / `yi` | 不匹配 | 不召回，但显示 ghost text `fanyi` | Ghost text 独立于召回 |

**独占（Takeover）从此只有两个入口**：
1. 完整键入 keyword（汉字/英文/pinyin_full）+ 空格 + 参数
2. 通过 Ghost Text + Tab 显式接受补全

### 2.3 判定层：`match_keyword` 三态扩展

```rust
enum MatchType {
    /// 精确命中「原文形式」——汉字明码 / 英文 keyword / pinyin_full
    Exact { hint: Option<String> },      // hint = 若命中派生形式(如 pinyin_full)，补上"更规范"的原文
    /// 前缀带参「原文形式」——同上
    Prefix { arg: String, hint: Option<String> },
    /// 首拼命中（无参或带参）——弱信号
    Initials { arg: String, hint: String },  // hint = 同源 pinyin_full 或原文，用于 ghost text
    // fuzzy 命中不在 MatchType 里（不参与召回），走独立的 suggest 通道
}
```

**规则**：
- `resolve_surface(Auto, Exact)` → `Priority`（不变）
- `resolve_surface(Auto, Prefix)` → `Takeover`（不变）
- `resolve_surface(Auto, Initials)` → **无参 Priority / 带参 Inline**（新，弱信号不独占）

**hint 生成规则**（返回给前端 ghost text 用）：
- 命中原文（`翻译` / `translate` / `fanyi`）→ 已是完整形式，`hint = None`
- 命中 pinyin_initials（`fy`）→ `hint = "fanyi"`（同源 pinyin_full；若 keyword 是纯 Latin 无 pinyin，回退到原文）
- fuzzy 命中（`fan` / `fany` / `yi`）→ 走 §2.4 独立 suggest 通道

### 2.4 Ghost text 独立于召回（关键设计）

**Ghost text 是"发现工具"，不是"召回工具"**。这意味着：

- 用户输入 `fan hello`（部分拼音）→ `match_keyword` **不命中**（既不是 `fanyi` 精确也不是 `fanyi ` 前缀），翻译插件**不出现**在候选列表
- **但** ghost text 计算走独立 fuzzy 通道，`fan` 对 keyword `fanyi` 的 fuzzy 分 > 阈值 → 显示 ghost text `→ fanyi hello`
- 用户按 Tab → 输入替换为 `fanyi hello` → 此时 route 命中 → Takeover 生效

**为什么这样设计**：
- "匹配"与"召回"分离，逻辑清晰。route 匹配保持严格，避免部分拼音污染搜索结果
- ghost text 作为教学层，让用户发现 keyword 的正确形式
- Tab 是显式意图信号 —— 用户看到提示并主动接受

**suggest 通道实现**（新增 `src/domain/intent/suggest.rs`）：

```rust
pub struct SuggestEngine {
    // 从 RuleRouter 拷贝一份 keyword 表（含 normalize_candidates 展开）
    keywords: Vec<(String /* pinyin_full */, String /* 原文 */)>,
    min_score: f64,  // 默认 0.7，配置项 app_config.autosuggest_min_score
}

impl SuggestEngine {
    /// 计算 ghost text 提示。返回 Option<CompletionHint>。
    /// - query = "fy hello"  → hint = { replacement: "fanyi hello", display: "fanyi" }
    /// - query = "fan hello" → hint = { replacement: "fanyi hello", display: "fanyi" }
    /// - query = "fanyi hello" → None（已经完整）
    pub fn suggest(&self, query: &str) -> Option<CompletionHint>;
}

pub struct CompletionHint {
    /// Tab 后的完整替换文本（keyword + " " + arg）
    pub replacement: String,
    /// UI 显示的 "更规范的" keyword 形式（pinyin_full 或原文）
    pub display: String,
    /// 用户已输入部分的长度（前端渲染时用于对齐灰色补全）
    pub prefix_len: usize,
}
```

**Fuzzy 算法**：复用已有 nucleo（与搜索一致），对 query 的 keyword 部分（split_whitespace 第一段）匹配所有 keyword 的 `normalize_candidates`，取最高分。

### 2.5 后端算 + IPC 返回

**Ghost text 计算走后端**（不做纯前端算）：
- keyword 表在后端，`normalize_candidates` / fuzzy 算法在后端，前端算需要搬两份逻辑不划算
- 每次 search invoke 时后端已经在算 route，顺便算 suggest，无额外 IPC 开销

**契约**：`search()` 返回值挂一个可选字段 `completion_hint`：

```rust
// 现有 search() → Vec<AppEntry>
// 改造为 → SearchResponse { entries: Vec<AppEntry>, completion_hint: Option<CompletionHint> }

// 前端 TypeScript 层
interface SearchResponse {
  entries: AppEntry[];
  completionHint?: {
    replacement: string;  // "fanyi hello"
    display: string;      // "fanyi"
    prefixLen: number;    // 前端渲染灰色部分对齐用
  };
}
```

**为什么不复用 `Route` 结构**：`Route` 是路由内部结果，`completion_hint` 是给前端 UI 的独立信号（可能没有 route 命中也有 hint —— fuzzy 部分拼音的情况）。分开清晰。

### 2.6 前端：双层 DOM + Tab 替换语义

**DOM 结构**：

```html
<div class="input-wrap">
  <div class="ghost-overlay">
    <span class="ghost-typed">fy hello</span><span class="ghost-suggest">→ fanyi hello</span>
  </div>
  <input class="query-input" />
</div>
```

- `.ghost-typed` 与用户输入等宽同字体但**颜色透明**（占位对齐）
- `.ghost-suggest` 灰色半透明（`opacity: 0.5`），显示补全后缀
- `<input>` 顶层实际接键盘，背景透明让下层显示

**Tab 替换语义（关键交互约定）**：
- `replacement` 是**完整替换**（`keyword + " " + arg`）而不是只补 keyword
- Tab 后：`inputElement.value = hint.replacement`，光标移到末尾
- **无参场景补尾空格**：若 arg 为空（用户只输入 `fy`），replacement 是 `"fanyi "`（带尾空格），Tab 后直接进 Takeover 等参数

**示例**：

| 用户输入 | ghost display | ghost replacement | Tab 后输入 | Tab 后 route |
|---|---|---|---|---|
| `fy` | `fanyi` | `fanyi ` | `fanyi ` | Takeover（空 arg 等待） |
| `fy hello` | `fanyi` | `fanyi hello` | `fanyi hello` | Takeover 触发 |
| `fy hello wo` | `fanyi` | `fanyi hello wo` | `fanyi hello wo` | Takeover 触发 |
| `fan hello` | `fanyi` | `fanyi hello` | `fanyi hello` | Takeover 触发 |

**多候选切换**：同 query 匹配多个 keyword → 后端返回 `Vec<CompletionHint>`（按分数排序），前端默认显首个；`→` 键循环下一个（`↓` 键保留给结果列表选择）。

**Tab 键绑定**：先 grep `frontend/js/keyboard.js` 确认 Tab 未占用（大概率没占）。若已占用退让给 `→`（但 Tab 语义直觉更强，优先争取）。

**抖动控制**：ghost text 计算搭 search 的 debounce（当前 40ms）车，不额外加 debounce。

### 2.7 参数模型约定备忘（1.0 前重审）

**现状**：`RuleRouter` 匹配约定是 **`命令 参数`** —— `match_keyword` 用 `format!("{kw} ")` 作前缀，剩余字符全部丢给单个 `arg: String`。语义解析（split whitespace、参数含义）完全丢给插件自己做。

**已知能覆盖的**：`translate en zh 你好`（插件自己 split 前两段作源/目标语言）、`git status`（插件自己 split 子命令）—— 一切位置参数都能编码进单个 String。

**已知不足**：
1. **无 shell-quoting 支持**：含空格的参数需要引号（`translate "hello world"`），当前无解析
2. **参数含义无 schema**：无法在输入框侧提示"下一个参数是什么"（这是 Autosuggestion 未来可能想做的方向 —— 输入 `fanyi ` 后提示 `<source_lang> <target_lang> <text>`）
3. **每个插件重复实现 split**：无共享的参数解析工具

**为什么 0.8.1 不动**：
- 无实际卡点（翻译/剪贴板/GitHub 用 String arg 都够）
- Ghost text 一期不需要参数结构感知（无脑触发独占，参数原样过给插件）
- 真正需要"参数 schema"是 AI Function Calling 场景（0.9），到时一起设计

**重审时机**：0.9 AI Function Calling 落地时 or 1.0 前专门开一版重审。备选方案：
- `arg: Vec<String>`（简单，加 shell-quoting）
- `arg: Value + manifest schema`（类型安全，可参数级提示）

**0.8.1 内的行为**：Tab 替换后的 `replacement` 字符串**原样**过给插件，插件按现有 String arg 模型消费，不涉及任何参数模型改动。

### 2.9 决策备忘

- **首拼 Exact 保留 Priority 而非降级 Inline**：`fy` 无参场景下，用户明确输入了完整首拼，Priority 已经不独占（保留其他候选在下方），配合 ghost text 教学最完整。
- **Ghost text 显示"最匹配的那个 key"**：命中派生形式（如首拼 `fy`）时显示同源 pinyin_full（`fanyi`）；命中原文时不显示（已完整）。教学价值：让用户学到 keyword 的规范拼音形式。
- **Ghost text 独立于召回**：部分拼音（`fan`）不进 route 匹配（保持严格），但走独立 suggest 通道触发 ghost text。避免召回污染。
- **Tab 后 keyword + arg 整段替换**：不做"只补 keyword 部分"—— 用户看到 ghost text 就是最终形态，Tab 语义直观（"接受这个提示"）。
- **无参 Tab 补尾空格**：`fy` → Tab → `fanyi `（带空格），直接进 Takeover 等参数，比再敲一次空格更顺手。
- **后端算 ghost text**：不做纯前端算。避免 `normalize_candidates` / nucleo 双份实现，且 search invoke 已经在算 route，顺便算 suggest 零成本。
- **参数模型约定不动**：0.8.1 保持现有 String arg 模型，1.0 前专门重审。见 §2.7。

## 三、翻译插件 Context 感知路由（0.8.2）

> **动机**：§1.1 §1.2 已完成"选中/剪贴板文本感知"的**内置动作侧**闭环（剪贴板 URL/路径 → 打开链接/路径）。翻译插件 `plugins/builtin/translate` 已存在，走的是 keyword 触发（`翻译 xxx` / `translate xxx`）。**缺口**：选中英文 → Alt 唤起 → 翻译插件不会自动置顶。本节把 `RuleRouter` 对 `ContextSnapshot` 的消费能力补齐。
>
> **意义**：这是 0.8 的核心叙事「Context 感知路由」从"只覆盖内置动作"扩到"覆盖插件"的关键一步。补完后，0.8 感知层故事完整。

### 3.1 现状体检

- **感知层**：`ContextSnapshot.selected_text` / `clipboard_text` 已灌好（0.8.0 完成）。
- **判定层**：`domain/context/probe.rs` 有 `is_url` / `is_file_path`，**缺**：`is_non_target_lang`（判"当前选区/剪贴板文本是否需要翻译"）。
- **路由层**：`RuleRouter::route` 拿到 `ctx.snapshot` 但**完全没消费**。当前只做 keyword/regex 匹配。
- **插件声明层**：`translate/manifest.json` 只有 `triggers: [{ type: "keyword", ... }]`，**缺**：`context` 触发声明。

### 3.2 数据模型扩容

**manifest triggers 加 `context` 类型**：

```json
// plugins/builtin/translate/manifest.json
"triggers": [
  { "type": "keyword", "keyword": "翻译", "exclusive": true },
  { "type": "keyword", "keyword": "translate", "exclusive": true },
  { "type": "context", "when": "selection_or_clipboard_is_non_target_lang", "surface": "priority" }
]
```

**Rust 侧 `PluginTrigger` 加变体**（`domain/plugin/manifest.rs`）：

```rust
enum PluginTrigger {
    Keyword { keyword: String, exclusive: bool },
    Regex { pattern: String, exclusive: bool },
    // 新增
    Context {
        when: ContextCondition,
        surface: SurfaceHint,  // priority / inline (context 触发绝不给 takeover)
    },
}

enum ContextCondition {
    SelectionNonEmpty,
    ClipboardIsUrl,
    ClipboardIsFilePath,
    SelectionOrClipboardIsNonTargetLang,  // 翻译专用
}

enum SurfaceHint { Priority, Inline }
```

**为什么 Context 触发不给 Takeover**：Context 触发是**弱意图信号**（用户可能只是复制了英文准备粘贴，不是想翻译）。强行 Takeover 独占返回区会严重误伤 —— 用户按 Alt 明明想搜别的东西。**只给 Priority 置顶，不独占**。

### 3.3 判定层：`is_non_target_lang` 纯函数

**避坑**：不引 `whatlang` / `lingua`（多 200KB+ 依赖，0.8.x 阶段不划算）。

**方案**：按字符集分档，四挡即可覆盖 95%+ 场景：

```rust
// domain/context/probe.rs
pub enum TextLang { Cjk, Latin, Kana, Hangul, Mixed, Empty }

pub fn detect_lang(s: &str) -> TextLang;

/// 相对于用户目标语言（AppConfig.language / plugin config target_lang）判断是否需要翻译
pub fn is_non_target_lang(s: &str, target: &str) -> bool {
    let lang = detect_lang(s);
    match (target, lang) {
        ("zh", TextLang::Latin | TextLang::Kana | TextLang::Hangul) => true,
        ("en", TextLang::Cjk | TextLang::Kana | TextLang::Hangul) => true,
        _ => false,  // Mixed/Empty 或同族 → 不触发
    }
}
```

**决策要点**：
- **字符集判定的鲁棒性**：`"hello"`（纯 Latin）在 target=zh 时判为"非目标语言"→ 需要翻译。文本很短时（<3 字符）返回 false 避免误触发。
- **参数从哪来**：target 语言从 translate 插件配置 `target_lang` 读，**不**再走用户主 `AppConfig.language`（前者更贴插件语义）。
- **单测覆盖**：至少 20 例 —— 覆盖 CJK/Latin/Kana/Hangul/emoji/纯符号/极短/混合 8 种输入 × zh/en 2 种 target。

### 3.4 路由层：`RuleRouter` 消费 Context

**规则注入**：`reload_plugin_triggers` 支持 `Context` 变体，注册进独立的 `context_rules: Vec<ContextRule>` 表（与 keyword/regex 表并存）：

```rust
struct ContextRule {
    plugin_id: String,
    when: ContextCondition,
    surface: Surface,  // 从 SurfaceHint 映射(Priority/Inline)
}
```

**路由匹配**（`RuleRouter::route`）：

```rust
async fn route(&self, query: &str, ctx: &QueryContext<'_>) -> Route {
    // ... 原 keyword/regex 匹配 ...

    // 新增：Context 触发扫描（不受 query 影响，空 query 也扫）
    let context_hits = self.match_context_rules(&ctx.snapshot);

    // 合并：keyword hit 与 context hit 命中同一 plugin → 取 max surface
    // Context hit + 无 keyword hit → 单独作为 candidate 加入 Mixed
    // Context hit 永远走 Mixed（不 takeover）
    let merged = merge_hits(keyword_hits, context_hits);
    // ... 后续仲裁 ...
}
```

**边界约定**：
- **arg 传参**：Context 触发的 arg 从 snapshot 抽取 —— 优先 `selected_text`，缺则 `clipboard_text`（有 arg 时才召回，与内置动作 Context 门禁一致）。
- **参数长度限**：arg 长度 > 2000 字符 → 截断至 2000 + 加省略号（避免超长文本压垮子进程 stdin）。
- **多 plugin 命中同一 Context**：允许，各自作为独立 candidate。翻译 Priority + 未来"搜索选区"插件 Priority 可以并存。
- **空 query + Context 命中**：Priority 候选带 `base_score = 0.9`（略低于内置 Context Action 的 1.0，保证参数化内置动作优先）。

### 3.5 与 §1.1 落地步骤 4 的对齐

§1.1 落地步骤 4 那个 "⏸ RuleRouter 接入" 就是本节。完成后回填其状态为 ✅。

### 3.6 关联文件

- 后端：`src/domain/intent/mod.rs`（+ContextRule）/ `src/domain/context/probe.rs`（+is_non_target_lang）/ `src/domain/plugin/manifest.rs`（+Context trigger）
- 插件：`plugins/builtin/translate/manifest.json`（+context trigger 声明）
- 测试：`context::probe` 补 20 例 / `intent` 补 8 例（context 命中/空 query/长文本截断/多 plugin 并存/target 匹配）

## 四、Chord 模式底层能力（0.8.3）

> **灵感来源**：Quicker + 键盘驱动的全局动作层
>
> **核心理念**：从「按 Alt 唤起→输入搜索」的被动模式，扩展为「按住 Alt→直接触发动作」的主动模式。
>
> **0.8.3 范围界定**：**底层能力**（状态机 + Context 抓取 + 唤起动作编排 + 提示 UI），而非"堆一堆具体动作"。第一批 Chord 动作作为验证载体，但真正沉淀的是**其他 Chord 动作能低成本加入**的注册机制。

### 4.1 交互流程

```
用户按住 Alt（不松开）
     ↓
┌─────────────────────┐
│  Blink 窗口出现        │
│  提示：按住 Alt + ...  │
└─────────────────────┘
     ↓     ↓     ↓
  +A     +Q     +空格...
  截图   划词   语音输入
```

**关键细节**：
- Alt **按住不放**是进入 Chord 模式的信号
- 二次按键在 Alt 按住期间按下，**不需要松开再按**
- 窗口出现时显示可用的 Chord 快捷键提示（如底部状态栏）
- Alt 松开 → 退出 Chord 模式，回到正常搜索输入

### 4.2 第一批 Chord 动作（作为底层能力的验证载体）

| 组合键 | 动作 | 说明 |
|---|---|---|
| `Alt + A` | **区域截图** | 进入截图模式，拖动选择区域 → 自动复制到剪贴板 |
| `Alt + Q` | **智能划词** | 主动触发划词文本抓取（比监听更可靠）+ 翻译/搜索动作弹出 |
| `Alt + C` | **剪贴板历史** | 直接打开剪贴板历史面板（跳过搜索） |
| `Alt + Space` | **语音输入** | 预留（按住期间语音识别，松开结束，实际推理留 0.9） |

### 4.3 底层能力清单（本节的真正范围）

**核心 1：状态机扩展**（`hotkey/windows.rs`）：

```rust
// 当前状态机（三字段）
down_since: Option<Instant>,
armed_key: Option<VKey>,
aborted: bool,

// 扩展 Chord 模式
chord_mode: bool,                    // 是否进入 Chord 模式（Alt 按住超过阈值）
chord_triggered: Option<ChordKey>,   // 已触发的二次键
chord_threshold_ms: u64,             // 配置项,默认 200ms
```

**判定逻辑**：
1. Alt `keydown` → 正常 arm，开始计时
2. **按住超过 200ms**（可配置）→ 标记 `chord_mode = true`，窗口提前出现并显示 Chord 提示
3. Chord 模式期间收到其他键 `keydown` → 匹配 Chord 动作表，触发对应动作
4. Alt `keyup` → 若 `chord_triggered.is_some()` 则不进入搜索；否则焦点到输入框

**与现有逻辑兼容**：
- 快速单击 Alt（< tap_threshold）→ 原有行为：唤起窗口，焦点到输入框
- 长按 Alt（> chord_threshold）→ 进入 Chord 模式，等待二次键
- 长按后松开且未按二次键 → 退化为正常搜索模式

**核心 2：Chord 动作注册机制**（新增 `src/domain/chord/mod.rs`）：

```rust
pub trait ChordAction: Send + Sync {
    fn id(&self) -> &'static str;
    fn key(&self) -> ChordKey;           // VK 码 + 是否需要 shift
    fn label(&self) -> LocalizableText;  // "区域截图"
    async fn execute(&self, ctx: &ChordContext) -> Result<()>;
}

pub struct ChordContext {
    pub snapshot: ContextSnapshot,       // 当前 Context 快照（含选区/剪贴板/前台）
    pub app_handle: tauri::AppHandle,    // 用于窗口操作
}

pub struct ChordRegistry {
    actions: Vec<Arc<dyn ChordAction>>,
}
```

**核心 3：Context 抓取**（进入 Chord 模式的瞬间抓）：

- Chord 模式触发时机（Alt 按住 200ms 那一刻）→ 后台 spawn 一次 Context 抓取（同 §1.1 UIA 划词 + `clipboard_text`）
- 抓取结果灌入 `ChordContext.snapshot`，`execute()` 时可用
- **为什么在这里再抓一次**：Chord 触发时用户可能刚做完选中，划词监听器可能还没来得及触发（拖拽过程中即松开）；主动抓一次做兜底

**核心 4：唤起动作编排**：

- 窗口 show：Chord 模式检测到就立即 show（不等 keyup）
- Chord 提示条：window `shown` 事件带 `chord_mode: true` payload → 前端显示底部提示栏（列可用 Chord + label）
- 动作触发：`ChordAction::execute()` 决定是否需要保持窗口打开、切换到某个搜索状态、还是执行完就 hide
- 窗口 hide 时机：`execute()` 返回后按动作声明的 `post_action_behavior`（`hide` / `keep_open` / `switch_to_search { query }`）

**核心 5：提示 UI**：

- 前端底部状态栏：`.chord-hint-bar`，Chord 模式下展示 4 个组合键 + label + icon
- CSS：底部固定条，进入 Chord 模式时 slide-up 淡入，退出 Chord 模式（Alt keyup 且未触发）淡出
- i18n：label 走既有 `LocalizableText` 通道

## 六、待验收速览（0.8.1 ~ 0.8.3）

各版本子验收清单见对应章节末。0.8 全线收官时应看到：

```bash
cargo test --bin blink   # 全 pass（每子版本递增测试）
cargo run

# 0.8.1 Autosuggestion
→ 输入 "fy hello" → 翻译 Priority + 本地引擎结果保留 + ghost text 显示
→ 按 Tab → 补全为 "翻译 hello" 并触发 Takeover

# 0.8.2 翻译 Context 路由
→ 选中一段英文 → 按 Alt → 翻译插件 Priority 置顶
→ 复制英文 → 按 Alt(不输入) → 翻译插件 Priority + 其他 Context 动作并存

# 0.8.3 Chord 底层
→ 按住 Alt 300ms → 底部 Chord 提示条出现
→ 按住 Alt + A → 截图触发
→ 按住 Alt + Q → 主动划词 → 翻译建议弹出（联动 0.8.2）
```
