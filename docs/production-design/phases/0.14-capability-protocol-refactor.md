# Blink 0.14 — 能力协议重构（Capability/Action 边界钉死 + 投影引擎收敛 + Cap 协议分层）

> **范围**：① Capability 与 Action 的职责边界从"口头约定"升级为"类型系统钉死"（删 `ActionTool` 适配器，AI 永不直接调 Action）+ ② Cap 协议分层——插件只吐纯 `data`，投影规则（pointer / desc / actions）上移到 manifest 做代理 + ③ 四出口投影引擎收敛（主窗口 AI / 对话窗口 AI / CLI / MCP 共用一套 canonical 投影）。
>
> **状态**：📋 规划中。
>
> **动机**：0.13.7 能力体系收敛时发现两个已显形的债——(1) 对话窗口 AI 收到的 tool 结果混入了本该给人看的 UI 文案（emoji、"按 Enter 复制"），根因是 `ItemResult { title, subtitle, payload }` 把"展示文案"和"语义数据"焊在一起，每个出口都要事后翻译；(2) 能力结果有 4 个出口（主窗口 AI 回流 / 对话窗口 AI / CLI / MCP server），但只有 2 个复用了 canonical 投影，CLI 和 MCP 各自手写了一套 match 四变体，Blob 摘要逻辑逐字重复 4 份，且 MCP 投影 Items 时没去 score 与 AI 路径行为漂移。
>
> **前置**：0.13 完成（能力体系已收敛——`ActionOutcome::Items` 变体已删，插件 Action 已迁入 Capability）。
>
> **原则**：**插件只吐纯 data，投影是配置出来的不是代码写死的**（简单插件返回 data + manifest 一行 desc；复杂插件允许直接吐完整 CapabilityResult，双轨制）。manifest 投影**只支持静态值 + JSONPath 取值**，不做格式化/函数计算（格式化由能力单元自己管）。desc 动态来源用 JSONPath 取值，缺失则不展示 desc。

## 一、背景与动机

### 1.1 问题是怎么发现的

0.13.7「能力体系收敛」收尾时排查对话窗口的一个现象：AI 调用翻译插件后，工具结果卡片里显示的是这样的 JSON：

```json
[
  {
    "title": "📝 MultiTurnStream项目",
    "subtitle": "按 Enter 复制译文 | 原文: MultiTurnStreamItem",
    "payload": { "source": "MultiTurnStreamItem", "translated": "MultiTurnStream项目" }
  }
]
```

这段 JSON **不是"主窗口格式泄漏进了对话窗口"**——它就是 AI 模型实际收到的 tool 结果文本本身（对话窗口的 ToolResult 卡片如实展示 AI 吃到的内容，是有意的审计可见性）。真正的问题是：**AI 收到的 tool 结果里，混进了本该只给人看的 UI 文案**。

### 1.2 根因：title/subtitle 与 payload 的语义混淆

现有 `ItemResult` 结构：

```rust
pub struct ItemResult {
    pub title: String,            // doc 写"主行显示文本" ← UI 倾向措辞
    pub subtitle: Option<String>, // doc 写"副行显示文本" ← UI 倾向措辞
    pub payload: Value,           // doc 写"既给前端执行又给 AI 读" ← 职责模糊
    pub score: Option<f32>,
}
```

- **`protocol.rs:182-186` 的设计注释**原本写的是："新增 `payload` 字段——结构化数据给 AI 读，与 `title`（前端展示用）分离。**前端展示用 title/subtitle，AI 读 payload**，两套消费分离。"
- **但 `items_to_llm_json`（result.rs:89）的实现**只剔除了 `score`（注释称其对 LLM 是噪音），把 `title` / `subtitle` / `payload` **全部原样喂给 AI**。

**设计与实现脱节**。0.13.7 收敛时只剔了 `score`，漏了 `title`/`subtitle`。

### 1.3 这是个例还是通病——通病

逐个审查所有返回 `CapabilityResult::Items` 的能力：

| 能力 | title 填什么 | subtitle 填什么 | 是否带 UI 味 |
|---|---|---|---|
| search_files（builtin） | 文件名 | 父目录路径 | 干净 |
| search_apps（builtin） | 应用名 | 应用描述 | 干净 |
| search_clipboard_history（builtin） | 文本预览 | **"X 分钟前"相对时间串** | ⚠️ UI 倾斜 |
| **translate（插件）** | **"📝 译文"** | **"按 Enter 复制译文 \| 原文:..."** | ⚠️⚠️ 最重 |

builtin capability 的 title/subtitle 基本是干净的自然语义，真正的 UI 味集中在**插件层**。但这是**整个 Items 投影的系统性问题**——`ItemResult` 的字段定义本身就没有把"给人看的"和"给 AI 看的"分开。

### 1.4 第二个债：四出口投影分裂

能力结果（CapabilityResult）有 4 个消费出口：

| 出口 | 投影函数 | 是否复用 canonical |
|---|---|---|
| 主窗口 AI 回流（Turn2） | `to_rig_tool_result()` + `rig_tool_result_to_text()` | ✅ 复用 |
| 对话窗口 AI（喂 LLM） | `CapabilityTool::call` → `to_rig_tool_result()` | ✅ 复用 |
| CLI `blink run` | 内联 match 四变体 + println | ❌ 手写重写 |
| MCP server `call_tool` | `result_to_call_tool_result()`（私有） | ❌ 手写重写 |
| 主窗口前端展示 | `items_to_entries()` | ❌ 独立（合理，前端要 AppEntry） |

**只有 2 个出口复用了 canonical 投影**。CLI 和 MCP server 各自手写了一套 match 四变体，带来：
- **Blob 摘要的 `size_kb` 计算**在 4 个文件逐字重复（`result.rs:43` / `mcp/server.rs:113` / `cli/commands.rs:231` / `service.rs:1812`）
- **MCP 投影 Items 时用裸 `serde_json::to_string(&items)`**（含 score 噪音），而 AI 路径走 `items_to_llm_json`（去 score）——**同结构不同投影语义已漂移**

### 1.5 第三个债：Action 与 Capability 边界模糊

现状 `ActionTool` 适配器把 12 个 builtin Action 都暴露给了 AI。逐个审查：

| Action | AI 该不该直接调 | 理由 |
|---|---|---|
| lock / shutdown / restart / sleep | ❌ 绝不该 | 不可逆系统操作 |
| clear_history / exit_blink / open_logs / open_data_dir / open_settings | ❌ 不该 | 主窗口/chord 专用 UI 动作 |
| **open_url / open_path / reveal_in_explorer** | ✅ 该 | AI 常用（打开搜索结果） |

现状是 **`ActionTool` 过度暴露**——AI 理论上能直接 `lock`、`shutdown`，是安全隐患。

### 1.6 重构窗口

0.13.7 刚把 `ActionOutcome::Items` 变体删掉、插件 Action 迁入 Capability，架构**正在向"Action=副作用专用，Capability=数据专用"收敛**。趁这个收尾窗口，把三个债一次性清掉，再开 0.20（向量版）会更干净。

## 二、Capability 与 Action 的职责边界（核心决策）

### 2.1 定位重新明确

```
┌──────────────────────────────────────────────────────────────┐
│  Action trait（0.8 四域，Execution 域）                        │
│  定位：主窗口 / chord 本地执行域                                │
│  语义：已发生的副作用描述（Copy/Open/Emit/Nop）                 │
│  永远不进 AI tool 池                                           │
│  例：lock / shutdown / open_settings / chord 动作              │
├──────────────────────────────────────────────────────────────┤
│  Capability trait（0.9.7，capability 域）                      │
│  定位：开放能力，面向所有调用方（AI/CLI/MCP/主窗口）            │
│  语义：纯数据能力（取数/计算/翻译/打开）                        │
│  进 AI tool 池的唯一合法形态                                    │
│  例：search_files / translate / capture_screen / open_url      │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 边界用类型系统钉死

**删除 `ActionTool` 适配器**（`tool_adapter.rs` 里把 Action 包成 ToolDyn 的那部分）。AI 永远只能通过 `CapabilityTool` 调能力——这把"AI 该不该调这个能力"的决策从"运行时每个 Action 自己标 danger_class"前置成"编译期只有 Capability 才能进 tool 池"。

### 2.3 open_url / open_path / reveal 提升为 Capability

从 12 个 builtin Action 里挑出 AI 真正需要的 3 个，重写成 Capability：

| 旧 Action | 新 Capability | 说明 |
|---|---|---|
| `open_url` | `open_url`（Capability） | 打开 URL，AI 常用 |
| `open_path` | `open_path`（Capability） | 打开文件/文件夹路径 |
| `reveal_in_explorer` | `reveal_in_explorer`（Capability） | 在资源管理器定位 |

这三个本质是"打开"能力的不同参数形态，作为 Capability 返回 `CapabilityResult::Done { summary }`。

其余 9 个 Action（lock/shutdown/restart/sleep/clear_history/exit_blink/open_logs/open_data_dir/open_settings）**保留在 Action trait**，**不进 AI tool 池**，只服务主窗口/chord 本地交互。

### 2.4 不合并 Capability 与 Action 的理由

讨论中曾考虑"全部合成 Capability"。**否决**，理由：
1. 四域架构（`docs/.../0.8-context-interaction.md` §五）是设计基座，AGENTS.md §9 列为铁则。Action trait 承载 Execution 域"已执行副作用"语义，与 Capability"纯数据能力"是不同的事。
2. 那 9 个保留 Action 里大部分（lock/shutdown/...）**本来就不该进 AI tool 池**——让 AI 能直接锁屏关机是危险的。
3. 0.13.7 删 `ActionOutcome::Items` 让 Action 回归纯副作用，说明架构**正在向"Action=副作用专用"收敛**，不是向"合并"收敛。合并方向与演进相反。

## 三、Cap 协议分层——插件只吐纯 data

### 3.1 核心思想：两层解耦

```
┌─────────────────────────────────────────────────────────────┐
│  层1: manifest（投影规则，相对静态）                          │
│   data_shape / pointer / desc / actions                      │
│   ← "怎么展示 / 怎么投影"是配置出来的                          │
├─────────────────────────────────────────────────────────────┤
│  层2: 插件运行时输出（纯数据，绝对纯净）                      │
│   data = 纯净 JSON（译文字符串 / IP 列表 / 天气对象）          │
│   ← 插件开发者只关心"返回正确的数据"                          │
└─────────────────────────────────────────────────────────────┘
         ↓ 投影引擎用 manifest 规则把 data 投影成各出口形态
    AI 读 data / 主窗口读 pointer 指向的值 + desc / CLI 读 data
```

**精髓**：展示和投影是配置出来的，不是代码写死的。翻译插件从返回 `data: "你好"` → manifest 一行 `desc: "译文"` 就够了，零 UI 代码。

### 3.2 三个关键设计点（讨论中已定案）

#### 3.2.1 JSONPath 用 `jsonpath-rust` crate（已定）

引入 [`jsonpath-rust`](https://crates.io/crates/jsonpath-rust)（纯 Rust，~30KB，后端可忽略）。理由：
- 表达力覆盖所有场景（单值、数组列表、嵌套对象、过滤）
- Blink 插件返回都偏简单，写法也相对简单，认知负载可控
- jsonpath 后续在向量检索结果投影、RAG chunk 提取等场景也可能复用
- 纯 Rust 零 C 绑定，编译轻量，符合 Blink 无重依赖偏好

**不用**自造极简 dialect——后续场景可能需要数组通配、过滤，自造会反复打补丁。选型详见 §8.4。

#### 3.2.2 desc 动态来源：JSONPath 取值，不用模板函数（已定）

desc 有三种来源，按优先级：

```
desc 来源优先级:
  1. manifest 的 desc_pointer 指定 data 某字段 → 取值作为 desc（动态）
     例: IP 插件 data=[{ip:"127.0.0.1",type:"本地"},...] 
         manifest 配 desc_pointer: "$[*].type" → desc=["本地","公网"]
  2. manifest 的 desc 静态字符串（静态）
     例: 翻译插件 manifest 配 desc: "译文"
  3. 都没有 → None → 前端/AI 不展示 desc，只有 result 值
```

**manifest 不做格式化**——需要 `format_size(bytes)` 这种格式化时，由能力单元自己在 data 里算好填进去（如 `size_display: "1.2 MB"`）。manifest 只负责"取哪个值"和"静态串"，不做计算。这把 manifest 的复杂度钉死在"配置"层面，不会退化成"代码"。

#### 3.2.3 双轨制（已定）

manifest 投影是**"快速通道"**——翻译/IP/天气这种简单返回用 manifest 配置搞定；复杂返回允许插件直接吐完整 `CapabilityResult`，跳过投影引擎。

| 轨道 | 适用 | 插件怎么写 |
|---|---|---|
| **轨道 A（manifest 投影）** | 简单返回（translate / IP / weather） | 只返回 `data`，manifest 配 pointer/desc/actions |
| **轨道 B（直接构造）** | 复杂返回（search_files 需格式化文件大小等） | 直接吐完整 `CapabilityResult`（含格式化好的 desc） |

两者都合法。轨道 B 的典型场景是 builtin capability（Rust 写的，不走插件协议）和需要复杂格式化的插件。

## 四、新 Cap 协议结构

### 4.1 插件运行时输出（轨道 A，极简）

```rust
/// 插件运行时只构造这个。翻译插件: data="你好". IP插件: data=[{ip,..}]
pub struct PluginRawResult {
    pub data: serde_json::Value,   // 纯数据，零展示逻辑
    pub error: Option<String>,
}
```

### 4.2 manifest 投影规则（轨道 A 的配置）

```jsonc
// 翻译插件 manifest 投影配置示例
{
  "result_shape": "text",        // text / items / blob / done
  "pointer": "$",                // 主值从 data 哪里取（JSONPath）
  "desc": "译文",                // 静态 desc 字符串
  "actions": ["copy"]            // 该 result 支持的动作（可从 data 类型派生）
}
```

```jsonc
// IP 插件 manifest 投影配置示例（返回 items）
{
  "result_shape": "items",
  "items_pointer": "$",          // data 整体是数组
  "item_pointer": "$.ip",        // 每项的主值从该项的 ip 字段取
  "item_desc_pointer": "$.type", // 每项的 desc 从 type 字段取 → "本地"/"公网"
  "item_actions": ["copy"]       // 每项支持的动作
}
```

### 4.3 CapabilityResult（四出口共用的统一返回）

```rust
pub enum CapabilityResult {
    /// 纯文本：翻译译文 / IP 查询 / OCR 结果
    Text { content: String, desc: Option<String> },
    /// 结构化列表：文件搜索 / IP 多层 / 剪贴板历史
    Items { items: Vec<ItemResult> },
    /// 二进制：截图 / 音频
    Blob { mime: String, bytes: Vec<u8>, desc: Option<String> },
    /// 无返回值副作用：已写入 / 已打开
    Done { summary: String },
}

pub struct ItemResult {
    /// ── 给 AI/CLI/MCP 的：语义数据（自解释）──
    pub data: serde_json::Value,       // 纯净语义，AI 直接读这个
    /// ── 给主窗口展示的：可选 desc ──
    pub desc: Option<String>,          // 副标题（替代旧 subtitle）
    /// ── 可执行动作 ──
    pub actions: Vec<ItemAction>,      // copy / open_file / open_url / ...
}
```

**关键变化（对比旧 `ItemResult`）**：
- 删 `title` / `subtitle` / `score`——这些是主窗口展示概念，不该在协议层
- `data` 取代 `payload`，语义更明确（"这就是给 AI 的纯净数据"）
- `desc` 取代 `subtitle`，且明确是"可选副标题"
- `actions` 显式声明，AI/前端看到就知道这个 item 能干什么
- 主标题（旧 `title`）由前端从 `data` 派生（投影规则见 §5.2）

### 4.4 ItemAction（动作声明）

```rust
pub enum ItemAction {
    Copy { pointer: Option<String> },      // 复制，pointer 指定从 data 取哪个值
    OpenFile { pointer: Option<String> },  // 打开文件
    OpenUrl { pointer: Option<String> },   // 打开 URL
    Reveal { pointer: Option<String> },    // 资源管理器定位
}
```

`pointer` 为 None 时默认取 item 的主值（由 manifest 的 `item_pointer` 指定）。

**多 action 交互约定**（主窗口，详见 §8.3）：

当一个 item 的 `actions` 有多个时，**顺序即优先级**：

| 操作 | 行为 |
|---|---|
| 回车 | 执行 `actions[0]`（首个） |
| 右键 | 展开全部 actions 供选择 |

插件作者把最常用动作放第一个。例：文件路径配 `["open_file", "copy"]`，回车直接打开，右键可选复制路径。

**不约定语义优先级**——当前完全信任作者排序（Blink 生态还小，插件几乎都是自研，作者最清楚该能力的首选用法）。未来第三方插件多了再视情况引入约定。

**空 actions 的兜底**：当 `actions` 为空且 result 是纯文本/数值标量时，主窗口隐式提供 copy（**展示层 fallback，非协议层派生**——`CapabilityResult` 里 `actions: []` 如实传空数组，是主窗口前端渲染时发现"没 action + 标量 data"才自己加 copy 按钮。协议层保持纯粹，兜底逻辑只活在主窗口）。

## 五、投影引擎（四出口共用）

### 5.1 一个函数，四个出口

```rust
/// 用 ProjectionRule 把 PluginRawResult 投影成 CapabilityResult（轨道 A）
pub fn project(raw: &PluginRawResult, rule: &ProjectionRule) -> CapabilityResult { ... }
```

四个出口**共用这一个投影引擎**，不再各自手写：

| 出口 | 读什么 | 投影规则 |
|---|---|---|
| **AI 出口**（主窗口回流 / 对话窗口） | `data`（纯 JSON） | 不读 desc，AI 只需语义数据 |
| **主窗口前端** | `data` 派生主标题 + `desc` + `actions` | 投影成 AppEntry |
| **CLI 出口** | `data` + `desc` | 文本展示 |
| **MCP 出口** | `data`（纯 JSON 给外部 agent） | 同 AI，只读 data |

### 5.2 主窗口前端的 fallback 派生

主标题（旧 `title`）由前端从 `data` 派生，规则集中在一个函数：

```rust
/// data 没有显式 desc/label 时，前端从这里派生主标题
fn derive_title(data: &Value) -> String {
    match data {
        Value::String(s) => s.clone(),           // 纯字符串 → 直接用
        Value::Number(n) => n.to_string(),       // 纯数字 → 直接用
        Value::Object(_) => data.to_string(),    // 对象 → JSON 串兜底
        _ => data.to_string(),
    }
}
```

复杂对象的主标题（如 search_files 的文件名）走轨道 B——builtin capability 直接构造好 ItemResult，data 里带格式化好的字段，前端从约定字段取。

### 5.3 消除的重复

收敛后，以下重复全部消除：
- **Blob 摘要逻辑**（旧 4 份逐字重复）→ 收进 `CapabilityResult::blob_summary()` 一个方法
- **CLI match 四变体** → 改调 canonical 投影
- **MCP `result_to_call_tool_result`** → 改调 canonical 投影，且修复 Items 投影的 score 漂移
- **对话历史加载的内联 match**（`commands.rs:764`）→ 复用 `summarize_tool_result`

## 六、插件协议迁移

### 6.1 破坏性变更范围

插件 JSONL 协议要改：现有插件返回 `{title, subtitle, payload, action, score}`，新协议（轨道 A）返回 `{ data }`。

### 6.2 影响的插件

| 插件 | 旧返回 | 新返回（轨道 A） | manifest 投影配置 |
|---|---|---|---|
| translate | `{title:"📝 你好", subtitle:"按Enter复制...", payload:{translated,source}}` | `{ data: "你好" }` | `{ shape:"text", desc:"译文", actions:["copy"] }` |
| translate_batch | `{title:"已翻译N行", payload:{results}}` | `{ data: [...] }` | `{ shape:"items", item_pointer:"$.translated", actions:["copy"] }` |
| IP | `{title, subtitle, payload:{ip}}` 多项 | `{ data:[{ip,type},...] }` | `{ shape:"items", item_pointer:"$.ip", item_desc_pointer:"$.type", actions:["copy"] }` |
| weather | `{title, subtitle, payload}` | `{ data:{city,temp,...} }` | `{ shape:"text", pointer:"$.temp", desc_pointer:"$.city" }` |

### 6.3 迁移是减负

插件运行时输出**变简单了**（不是更复杂）：
- 翻译插件那段 30 行构造 `PluginItem`（填 title/subtitle/payload/action）→ 缩成一行 `data: result`
- 插件开发者不再需要关心"主窗口怎么展示"——那是 manifest 的投影规则的事

### 6.4 迁移策略（已定：一次性切换）

插件二进制需要重新编译分发（破坏性变更）。**定案：一次性切换**——0.14 内全部插件迁完，旧 JSONL 协议直接废弃，不保留兼容层（详见 §8.1）。理由：0.x 阶段插件全自研，维护两套解析是纯负担。

## 八、关键决策记录

以下三点已在设计阶段定案，实施时遵循：

### 8.1 插件协议迁移策略 —— 一次性切换（已定）

**定案**：**A. 一次性切换**。0.14 内全部插件（translate / translate_batch / IP / weather）迁完，旧 JSONL 协议（`{title, subtitle, payload, action, score}`）直接废弃，不保留兼容层。

**理由**：0.x 阶段插件都是自研（无第三方插件依赖），手动迁移成本可控；维护两套解析是纯负担，违背"持续收敛"原则。插件二进制本就需要随 0.14 重新编译分发。

### 8.2 ItemAction 声明方式 —— manifest 全显式（已定）

**定案**：**B. manifest 全显式声明**。每个能力在 manifest 写死 `actions` 数组，不做"data 类型 → 默认 actions"的自动派生。

**主窗口的兜底行为**：当插件**没配 actions**（空数组或缺字段）时，主窗口对**纯文本 / 纯数值**型的 result 提供**隐式 copy**——用户回车可复制该值。这是主窗口的展示层 fallback，不是协议层的自动派生，两者职责分离：
- 协议层（CapabilityResult）：actions 是什么，由 manifest 显式说了算
- 展示层（主窗口前端）：没有 actions 时，对简单标量 result 兜底一个 copy

### 8.3 多 action 的交互约定 —— 回车首个 / 右键全部（已定）

当一个 item 声明了**多个 action**时（例：一个文件路径既配了 `open_file` 又配了 `copy`），主窗口的交互约定：

| 操作 | 行为 |
|---|---|
| **回车** | 执行 `actions[0]`（首个 action，即 manifest 里写的第一个）|
| **右键** | 展开全部 actions 供用户选择（上下文菜单）|

**manifest 里的 actions 顺序即优先级**——插件作者把"最常用的动作"放第一个。例：文件路径场景，作者判断"打开"比"复制路径"常用，就把 `open_file` 放 `actions[0]`，用户回车直接打开；想复制路径时右键选 `copy`。

这个约定让多 action 不会变成"多选困境"——回车永远有确定行为（首个），右键才暴露全部。

### 8.4 JSONPath crate 选型 —— jsonpath-rust（已定）

**定案**：先用 [`jsonpath-rust`](https://crates.io/crates/jsonpath-rust)（纯 Rust 实现，JSONPath 标准，活跃维护）。

**理由**：纯 Rust 零 C 绑定，编译轻量，符合 Blink 无重依赖偏好；JSONPath 标准语法覆盖单值/数组通配/嵌套对象/过滤，Blink 场景够用。

**实施时验证项**（落地时补单测）：
- 中文 value 的取值（IP 插件 `type:"本地IP"` 这种）
- 嵌套对象 `$[*].ip` 数组通配
- pointer 缺失时的优雅降级（返回 None，不 panic）
