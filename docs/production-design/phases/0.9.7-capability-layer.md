# Blink 0.9.7 — Capability 能力协议层（架构收尾）

> **范围**：引入 `Capability` 作为**统一能力协议**（schema + invoke + result）+ 拆截图/剪贴板焊死链路 + 接入 AI tool 池 + inventory 自动注册
>
> **主题**：在 0.9 文本闭环稳定后、0.10 语音开工前，立起一份**共享的能力协议**——让"截图""剪贴板""文件搜索"等能力从"焊死在交互入口里"解放出来，成为可被**AI tool_call / Action 编排 / 未来 CLI / 未来 MCP server** 共同消费的标准化单元。
>
> **前置**：0.9.0~0.9.5 完成（Provider 多档 + 主窗口文本闭环 + 统一 tool 架构 + 前端架构重整）。
>
> **原则**：Capability 是**协议**不是内部抽象；schema 是纯 JSON Schema（不绑 Rust 类型，为 CLI/MCP 派生留口子）；能力与入口解耦；返回类型消费方决定；新增能力实现即注册（inventory）。

---

## 一、为什么 0.9.7 做这件事

### 1.1 本质矛盾：能力被绑死在交互入口上

0.9 的"一切皆 tool / 四源归一"只归一了两源（builtin Action + plugin tool）。**第三源——平台能力（截图/剪贴板/选区）——被焊死在交互入口里，没有显式建模**：

| 能力 | 今天焊在 | 后果 |
|---|---|---|
| 截屏 `BitBlt` | `ScreenshotAction::execute()`（chord） | AI 想截图？做不到。OCR 想复用截图？做不到 |
| 裁剪 `crop` | `capture_region` command | 写死"裁剪→剪贴板"一条链 |
| 读剪贴板文本 | `clipboard` 监听器私有函数 | AI 想"读当前剪贴板当上下文"？无统一入口 |
| 写剪贴板（图） | `write_bgra_to_clipboard` | 只能写图，不能写文本 |
| 文件搜索 | `FileEngine`（SearchEngine trait） | AI 想搜文件？trait 没 schema，进不了 tool 池 |

**三条线（Action / SearchEngine / Platform 函数）的"能力声明"和"返回方式"各不相同**——"能力"这个词在代码里有三种含义、三种语言。这是"加新能力痛、AI 看不见能力"的根因。

### 1.2 Capability 的定位：统一能力协议（不是内部 trait）

> **核心架构决策**：Capability 是**协议**——对外可投影成 CLI / MCP server，对内供 Action 编排 / AI tool_call 消费。它消解了"能力"在三种入口里的方言。

这呼应 [product-platform.md §6.2](../product-platform.md#62-一切皆-tool统一架构)「一切皆 tool」——但更进一步：**不是"Action 进化为 tool 入口"，而是"能力本身标准化成协议，Action/AI/CLI/MCP 都是这个协议的消费者"**。

```
                       Capability 协议
              （schema: JSON Schema / invoke / result）
        ┌──────────┬──────────┬──────────┬──────────┐
        ▼          ▼          ▼          ▼          ▼
   进程内调用   AI tool_call  CLI 暴露   MCP server  远程插件
  (Action编排) (0.9.7 主窗口) (0.11)   (0.11 护城河) (0.11 契约)
```

**这正是 Anthropic MCP（Model Context Protocol）的思路**——把能力标准化成协议，让任何 client/server 互通。[0.11 §4.2](./0.11-local-ecosystem.md) 已规划 MCP server 作为护城河，**Capability 协议是它的内部底座**——0.11 暴露 Capability 时是"投影"，不是"重造"。

### 1.3 为什么不是 0.10 / 0.11 做

- **不推 0.10**：0.10 北极星"语音找文件"硬前置——AI 必须能 tool_call 文件搜索。0.10 语音 STT 本身已是最大未知，不应叠加架构债。**0.9.7 把能力层立好，0.10 不确定性收敛到 STT 单点。**
- **不推 0.11**：0.11 的王牌 MCP server 要"暴露本地能力"。**如果能力没有协议化建模，MCP server 暴露什么？** 先立协议，0.11 只写投影层。

### 1.4 0.9.7 vs 0.11 的边界（关键）

| 0.9.7 做（立协议 + 内部消费） | 0.11 做（对外投影 + 契约统一） |
|---|---|
| Capability 协议三件套（schema/invoke/result），**schema 纯 JSON Schema** | CLI 派生层（schema → clap 参数） |
| 5 个样板能力按协议实现 | MCP server（Capability → MCP tool schema，rmcp 已启用） |
| Action/SearchEngine 改为编排 Capability | 插件契约统一（manifest → Capability schema 实例，插件 = 远程 Capability） |
| AI tool 池接入 | 远程 Capability（插件进程 = Capability server） |

**0.9.7 保证"协议对了"**，这样 0.11 加 CLI/MCP/插件统一是"投影"，不是"重构"。

## 三、Capability 协议设计

### 3.1 协议的两层投影（核心架构决策）

Capability 是协议，必须对"远程调用"友好。因此分两层：

```
┌─ 协议层（对外：CLI / MCP / 远程插件 共享）──────────────┐
│  invoke(args: Value) → Result<Value, Error>           │
│  纯 JSON 进、纯 JSON 出。schema 是 JSON Schema。        │
│  这一层是 0.11 CLI/MCP 派生的输入。                     │
├─ 进程内层（对内：Action 编排 / AI tool_call 消费）──────┤
│  invoke(args: Value, ctx: &InvokeContext)              │
│        → Result<CapabilityResult, CapabilityError>     │
│  带 ctx（app_handle/config）+ 强类型 result。            │
│  这一层是 0.9.7 落地的形态。                            │
└────────────────────────────────────────────────────────┘
```

**两层是一个东西的两个投影**：
- 协议层 = 进程内层"剥掉 ctx + 把 `CapabilityResult` 序列化成 Value"
- 0.9.7 只实现进程内层，但**签名设计保证协议层可零摩擦派生**（`args: Value` 已经是纯 JSON，`CapabilityResult` 已经 `Serialize`）
- 0.11 落 CLI/MCP 时，写一个 `to_protocol_value()` 投影函数即可，不改 Capability 实现方

### 3.2 协议三件套

#### schema（纯 JSON Schema，不绑 Rust 类型）

```rust
/// 能力描述 schema——纯 JSON Schema，是协议的"身份证"。
/// `to_rig_tool()` / `to_mcp_tool()` / `to_clap()` 都从这份 schema 派生。
pub struct CapabilitySchema {
    pub name: String,          // = Capability::id()
    pub description: String,   // 送 LLM / CLI --help / MCP 描述
    pub parameters: serde_json::Value,  // JSON Schema draft-07（与 MCP/OpenAI 对齐）
}
```

**为什么是纯 JSON Schema**：让 0.11 派生 CLI（schema → clap 参数）和 MCP（schema → rmcp tool）零摩擦。如果绑 Rust 类型，派生层要重写类型映射。

#### invoke（入参 → 出参，无 UI 假设）

```rust
/// 原子能力——一切"做一件事拿一个结果"的统一抽象。
///
/// 与 Action 的根本区别：
/// - Action 是「交互动作」——含 UI 副作用（弹窗/emit/copy），面向用户
/// - Capability 是「纯能力」——入参→出参，无 UI 假设，面向所有调用方
///
/// 四种调用方共享同一份 Capability：
/// - Action.execute() 编排它（如 ScreenshotAction 编排 capture_screen）
/// - AI tool 直接 tool_call 它（0.10 语音找文件 / Agent 窗口）
/// - （0.11）CLI 派生 blink screenshot --display 1
/// - （0.11）MCP server 暴露给外部 Agent
#[async_trait::async_trait]
pub trait Capability: Send + Sync {
    fn id(&self) -> &str;
    fn schema(&self) -> CapabilitySchema;
    fn danger_class(&self) -> DangerClass { DangerClass::Safe }

    async fn invoke(
        &self,
        args: serde_json::Value,
        ctx: &InvokeContext<'_>,
    ) -> Result<CapabilityResult, CapabilityError>;
}

/// invoke 时的运行时上下文——config 不在构造时注入，在调用时传。
/// 协议层（0.11 CLI/MCP）投影时，ctx 从环境变量/连接读取，不影响实现方。
///
/// **超时铁则**（对齐 [0.9 AIProvider §3.3](./0.9-ai-layer.md)）：
/// `deadline` 为绝对截止时刻。Capability `invoke` 实现方**必须**在长耗时操作前
/// 检查 `ctx.is_expired()`，或用 `tokio::time::timeout_at(ctx.deadline())` 包裹。
/// 调用方负责传入合理 deadline（AI lane 从 `slo_hard_timeout_ms` 派生）。
pub struct InvokeContext<'a> {
    pub app_handle: &'a tauri::AppHandle,
    pub config: &'a crate::app::config::AppConfig,
    /// 绝对截止时刻。`None` = 无超时（仅本地同步编排，如 Alt+A 截图）。
    /// AI lane / 异步编排路径**必须**传 `Some`。
    pub deadline: Option<std::time::Instant>,
}

impl<'a> InvokeContext<'a> {
    /// 是否已超时。Capability 实现方在长耗时循环/网络调用前 poll 此方法。
    pub fn is_expired(&self) -> bool {
        self.deadline
            .map(|d| std::time::Instant::now() >= d)
            .unwrap_or(false)
    }

    /// 转 `tokio::time::Instant` 供 `timeout_at` 用。`None` 时返回远期 future（不超时）。
    pub fn deadline_or_far_future(&self) -> tokio::time::Instant {
        self.deadline
            .map(|d| tokio::time::Instant::from_std(d))
            .unwrap_or_else(|| tokio::time::Instant::now() + tokio::time::Duration::from_secs(3600))
    }
}
```

#### result（四变体统一返回）

```rust
/// 原子能力的统一返回——四种形态覆盖所有场景。
/// `Serialize` 保证可投影成协议层 Value（0.11 CLI stdout / MCP result）。
#[derive(Debug, Clone, Serialize)]
#[serde(tag = "kind", rename_all = "lowercase")]
pub enum CapabilityResult {
    /// 纯文本：OCR / IP 查询 / 总结 → 前端 Copy、AI 当文本上下文
    Text { content: String },

    /// 结构化列表：文件搜索 / 剪贴板历史 → 前端渲染条目、AI 读 JSON
    Items { items: Vec<ItemResult> },

    /// 二进制：截图 / 音频 / 文件内容 → 字节+mime，投影方式由消费方决定
    Blob { mime: String, bytes: Vec<u8> },

    /// 无返回值副作用：已写入 / 已打开 → 携带人类可读 summary
    Done { summary: String },
}

#[derive(Debug, Clone, Serialize)]
pub struct ItemResult {
    pub title: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub subtitle: Option<String>,
    /// 结构化 payload——既给前端执行（path/text），又给 AI 读（任意 JSON）
    pub payload: serde_json::Value,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub score: Option<f32>,
}
```

**为什么只有四个变体够（不多不少）**：
- 少了 `Blob` → 处理不了截图/音频
- 少了 `Items` → 处理不了列表（文件/历史）
- 少了 `Done` → 处理不了纯副作用（写剪贴板/打开）
- 多了（如 `File{path}`）→ 等于把消费形态焊进能力层，违背"返回类型消费方决定"

### 3.3 错误模型

```rust
/// 能力调用错误——可序列化，投影到 AI（ToolResultContent::Text）+ 前端展示。
#[derive(Debug, Clone, Serialize)]
#[serde(tag = "kind", rename_all = "lowercase")]
pub enum CapabilityError {
    /// 参数缺失/类型错（args 不符 schema）
    InvalidArgs { detail: String },
    /// 权限不足（剪贴板被锁/无截图权限）
    Permission { detail: String },
    /// 超时——`invoke` 检查 `ctx.is_expired()` 返回 true，或 `timeout_at` 触发
    Timeout { detail: String },
    /// 调用方取消——用户 ESC / seq 过期 / future drop（对齐 AI stream abort 语义）
    Cancelled,
    /// 能力不存在（id 未注册——AI 幻觉调了不存在的 tool）
    NotFound { id: String },
    /// 内部错误（Win32 失败/IO 错误）
    Internal { detail: String },
}
```

**Timeout vs Cancelled 的区分**（重要）：
- `Timeout`：**时间到了**——`deadline` 触发，调用方设的预算用尽。投影到 AI："工具超时，可重试或换路径"
- `Cancelled`：**用户主动放弃**——ESC / 输入新 query / 切窗口。投影到 AI：不报错给 LLM（直接 abort 整条 tool_call 链，和 `producer_handle.abort()` 一致）

两者都不写 perf metric 的"成功"桶——Timeout 进"超时"桶，Cancelled 不计入（用户行为，非能力问题）。

**投影规则**（AI lane / 前端协议层职责）：
- → AI：序列化成 `ToolResultContent::Text("工具失败: {kind} {detail}")`，让 LLM 知道失败原因（可重试或换路径）
- → 前端：`is_error=true` 条目，橙色展示（复用现有 AI error 项样式）
- → CLI（0.11）：`stderr` + 非零退出码

### 3.4 与现有架构的关系（不冲突，是补位）

| 现有架构原则 | Capability 的关系 |
|---|---|
| §7.1「一切副作用只从 Action 出」 | **不冲突**。Action 仍是**用户交互副作用**的统一入口；Capability 是**能力调用**的统一入口。两者正交：Action **编排** Capability 产交互副作用，AI/CLI/MCP **直接调** Capability 产纯结果。 |
| §6.2「Action trait 进化为 tool-call 入口」 | **演进为**：Action 是 tool-call 的**交互壳**，Capability 是 tool-call 的**能力核**。AI tool_call 优先命中 Capability（纯能力），需 UI 副作用的才走 Action。 |
| 四域架构 | **零冲击**。Capability 在 Execution 域内部；`ExecArg::UserExplicit` 类型墙挡在 Action 层；AI 直接 tool_call Capability 时走 0.10 §5.0 AgentBuilder 授权模型 |

**一句话**：Capability 不是"第四个统一入口"，而是"能力协议层"——Action/SearchEngine/Plugin 在它之上，是它的消费者和编排者。

### 3.5 超时 / 取消 / SLO 三铁则

> Capability 被 AI tool_call 编排时，**必须满足与 [0.9 AIProvider §3.3](./0.9-ai-layer.md) 同等级别的可靠性约束**——否则一个卡住的 `search_files` 会把 AI lane 挂死，违反 [product-platform §6.4 AI 反馈铁则](../product-platform.md#64-两条路径铁则--ai-反馈铁则)（"不能让用户死等"）。

#### 铁则 1：硬超时——`InvokeContext.deadline`

- **调用方责任**：AI lane 调 Capability 时，从 `AIConfig.slo_hard_timeout_ms` 派生 deadline 传入 `InvokeContext`；本地同步编排（如 Alt+A 截图）可传 `None`
- **实现方责任**：长耗时 Capability（`search_files` 网络等待、未来 `ocr`）**必须**在关键 await 点用 `tokio::time::timeout_at(ctx.deadline_or_far_future(), ...)` 包裹，或 poll `ctx.is_expired()`
- **对齐**：与 `AIProvider::complete` 硬超时铁则（`provider.rs:83`）一致——"不允许调用方忘了传 timeout 就无限挂"

#### 铁则 2：取消——drop future + seq 校验

- **机制**：复用 AI stream 的 cancel 模式——用户 ESC / 输入新 query → `latest_seq` 变更 → Capability 调用所在的 spawn task 被丢弃，future drop 自动中断
- **实现方责任**：Capability `invoke` 不需要主动响应取消（Rust async drop 语义自动清理）；但**避免在 invoke 内部 spawn 无法被 cancel 的脱离任务**
- **与 AI lane 协作**：AI lane 在 `handle_ai_tool_calls` 里 seq 校验失败时返回 `CapabilityError::Cancelled`，不 emit 给前端（用户已切走，无需反馈）

#### 铁则 3：SLO 埋点——`MetricCategory::Capability`

- **新增枚举变体**：`perf::MetricCategory` 加 `Capability`（与现有 Startup/Hotkey/SearchEngine/Plugin/IconExtract 并列）
- **自动埋点**：`CapabilityRegistry::invoke()` 包装层统一 `record(Capability, id, elapsed_ms)`——实现方**无需**手写埋点
- **tracing target**：复用 `blink::ai::slo` target，字段格式 `capability={id} elapsed={}ms outcome={ok|timeout|error}`
- **设置页消费**：现有 AI Tab 调试面板（`settings/tabs/ai`）天然可展示 Capability SLO，无需新前端

**三铁则的验收**：`search_files` 模拟卡住（Everything 不响应）→ AI lane 在 `slo_hard_timeout_ms` 内返回 `CapabilityError::Timeout` → 前端展示"搜索超时"而非转圈死等 → perf 表有 `capability=search_files outcome=timeout` 记录。

### 3.6 inventory 自动注册

新增 `inventory` 依赖。每个 Capability 文件写一行 `inventory::submit!`，`CapabilityRegistry::new()` 启动时遍历收集，**不碰注册中心**：

```rust
// capture_screen.rs
inventory::submit!(CAPABILITY_ENTRIES {
    factory: || std::sync::Arc::new(CaptureScreen) as std::sync::Arc<dyn Capability>,
});

// CapabilityRegistry::new()
for entry in inventory::iter::<CAPABILITY_ENTRIES>() {
    reg.register((entry.factory)());
}
```

**新增能力 = 新建文件 + 写一个 `inventory::submit!`，注册表零改动。**

## 四、0.9.7 样板能力清单

### 4.1 必做（截图 + 剪贴板 + 文件搜索三大原子化最小闭环）

## 五、关键设计决策与取舍

### 5.1 截图 SESSION 取舍（采用"甲：保留 SESSION，capture_screen 读它当 cache"）

现状截图是"两次调用"：`begin_session` 截全屏存全局 SESSION，`crop` 再裁。SESSION 省一次 BitBlt（~50-100ms）。

| 方案 | 采纳？ | 理由 |
|---|---|---|
| **甲：保留 SESSION，capture_screen 读它当 cache** | ✅ **采纳** | 性能零回退（0.8.7 ~320ms 感知延迟不退化）；AI 调用时 SESSION 多半已过期走 BitBlt 新截，行为正确 |
| 乙：每次都 BitBlt，废 SESSION | ❌ | Alt+A 多一次 BitBlt（~50ms）；overlay 渲染链路要改成基于返回 Blob——大改动 |

**capture_screen 的 cache 语义**："给我当前屏幕"——有 SESSION 缓存就用，没有就新截。这个"不纯"可接受、有 cache 语义、能渐进演进（将来废 SESSION 切乙不影响调用方）。

### 5.2 `Blob` 不在能力层决定返回形态

`Blob{bytes, mime}` 只产字节。**文件还是流还是 base64，是消费方约束，不是能力属性**——

| 消费方 | `Blob` → |
|---|---|
| OpenAI/Gemini vision | base64 编码 → `DocumentSourceKind::Base64` |
| 本地模型 | raw bytes → `DocumentSourceKind::Raw` |
| 主窗口 `<img>` | 写临时文件给 URL / blob URL（前端协议层） |
| 写剪贴板 | 直接字节给 CF_DIB（`write_clipboard` 编排） |
| CLI（0.11） | stdout 原始字节（`--output raw`）或写文件（`-o file.png`） |

**rig 0.39 的 `DocumentSourceKind` 印证此设计**：`Url/Base64/FileId/Raw/String` 五来源解耦（`message.rs:391`）。

**已知性能点**：`Blob { bytes: Vec<u8> }` 每次 clone 全部字节（截图 ~14MB）。0.9.7 先 clone 跑通；若热路径出现，改 `Arc<Vec<u8>>` 或投影层避免深拷贝。文档标注，不阻塞落地。

### 5.3 `Items` 一个返回，两种消费

| 消费方 | 怎么读 `Items` |
|---|---|
| 主窗口（回流让用户选） | `Vec<ItemResult>` → `Vec<SearchItem>`（复用 `into_app_entry`），渲染可选条目，Alt+1 打开 |
| AI（读进上下文） | 序列化 JSON 文本喂 LLM：`[{title, subtitle, payload}]` |
| CLI（0.11） | stdout JSON 数组（`--output json`）或纯文本列表（`--output text`） |

**Capability 不做"甲/乙"选择，返回 `Items` 两种都能消费。** 选谁是调用方上下文决定的——主窗口模式走"回流"，Agent 窗口模式走"AI 消化"，CLI 走"stdout"。Capability 层零分支。

### 5.4 与四域架构的关系（强化不破坏）

- **Awareness 域不动**——Capability 是执行侧能力，不感知环境
- **Suggestion 域不动**——AI 是否产 tool_call Suggestion 仍走四筛子 + Arbiter
- **Routing 不变**——Capability 不影响路由
- **Execution 域**——Capability 是 `Action::execute` 的下游，仍在 Execution 域内；`ExecArg::UserExplicit` 类型墙挡在 Action 层。AI 直接 tool_call Capability 时走 0.10 §5.0 AgentBuilder 授权模型，DangerClass 仍管危险动作

## 八、为 0.11 铺的路（明确但不做）

本版的关键价值是**立协议**，让 0.11 的对外投影是"派生"不是"重构"：

| 0.11 落地点 | 复用 0.9.7 的什么 | 派生工作量 |
|---|---|---|
| **CLI 暴露**（`blink screenshot --display 1`） | `CapabilitySchema.parameters` → clap 参数；`CapabilityResult` → stdout JSON/字节 | 投影层一个文件 |
| **MCP server** | `CapabilitySchema` → rmcp tool（`From<CapabilitySchema> for rmcp::Tool`）；invoke 走协议层 | 投影层一个文件（rmcp 已启用） |
| **插件契约统一** | manifest `tools` → `CapabilitySchema` 实例；插件进程 = 远程 Capability server | 较大，重设 IPC，但协议层不动 |
| **第三方 AI 调用** | CLI 或 MCP 任一通道，Capability 实现方零感知 | 零 |

**对插件契约统一的特别说明**（[0.11 §三](./0.11-local-ecosystem.md)）：

> 现状插件 manifest schema_version=1 + JSONL IPC。0.11 统一时，插件变成"远程 Capability"——manifest 的 `tools` 字段直接是 `CapabilitySchema` 的 JSON 实例，JSONL 的 `tool_call`/`tool_result` 是 Capability invoke/result 的序列化形态。**0.9.7 不碰插件契约**（无痛点，< 10 插件），但保证 Capability 协议形态与插件 manifest 对齐，0.11 统一是"收编"不是"重设计"。
