# Blink 0.13 — AI 调用能力扩展（MCP 双向 + CLI 化 + Skill + 记忆召回 + token-aware 窗口）

> **范围**：① MCP client（消费外部 tool）+ ② token-aware context 压缩（补 0.12.3 滑动窗口缺口）+ ③ 记忆 FTS5 召回（SQLite 全文检索，零嵌入模型依赖）+ ④ Skill 约定式（SKILL.md 目录自动发现，对齐 agent 届通用概念）+ ⑤ MCP server（护城河——暴露 Blink 能力给生态）+ ⑥ 自身 CLI 化（Blink as CLI）。
>
> **主题**：0.12 搭好了 AI 能力的架构骨架（独立对话窗口 + 多轮 agent loop + 持久化记忆 + Tool 适配层）。0.13 在此骨架上**扩展调用能力 + 开放能力 + 上下文**——让 AI 能调外部世界（MCP client）、能暴露 Blink 能力给生态（MCP server + CLI 化）、能被 Skill 流程指导赋能（SKILL.md）、能记住更远的对话（FTS5 召回）、且上下文窗口从「消息条数」升级为「token 感知 + 接近上限压缩」。
>
> **产品边界决策**：**Blink 不做 AI 运行时**。本地推理靠外部（ollama / lmstudio），Blink 只作 Provider 对接 + 能力编排。
>
> **核心原则**：**0.13 零嵌入模型依赖**——所有功能在用户只有 chat 模型（无 embedding 模型）时也能完整可用。向量语义召回、RAG 知识库、MCP server、CLI 化、AI 生成 Skill 推到 [0.14](0.14-ai-vector-moat.md)。
>
> **前置**：0.12 完成（对话窗口 + 对话机制 + Tool 适配层 + Provider 模型统一管理 + DB 四层拆分 + ollama 接入）。
>
> **原则**：0.12 的架构骨架不破；MCP / Skill / FTS5 走 0.12 铺好的接入点统一接入（不绕过）；安装包保持 < 100MB。

## 一、范围与边界

### 1.1 0.12 → 0.13 衔接

0.12 搭好了 AI 能力架构的**骨架**：

```
0.12 骨架（已完成）
  ├─ Tool 适配层（CapabilityTool / ActionTool，impl rig::tool::ToolDyn）
  ├─ 对话窗口（AgentProvider + Alt+Q chord + agent loop + tool loop 无限轮）
  ├─ 持久化 memory（SqliteConversationMemory + 滑动窗口 20 条）
  ├─ Provider 模型统一管理（chat + embedding + STT，capabilities 标记）

```

0.13 在此骨架上**扩展调用能力与上下文**，每个扩展走 0.12 铺好的接入点：

| 0.13 模块 | 接入 0.12 哪个骨架 | 依赖的 0.12 产出 |
|---|---|---|
| **MCP client** | Tool 适配层 + rmcp feature | §2.4 Tool 适配层 + rmcp 反向投影（0.13.0 新建） |
| **token-aware 窗口** | 持久化 memory + Provider 模型管理 | 0.12.3 SqliteConversationMemory + 0.12 ModelEntry.context_limit |
| **记忆 FTS5 召回** | 持久化 memory | 0.12.3 SqliteConversationMemory + SQLite FTS5 |
| **Skill 约定式** | preamble 组装（注入） | 0.12.6 `chat_system_prompt_with_group` + preamble_hash 缓存失效 |
| **MCP server**（护城河） | rmcp 正向投影 + sensitive + 审计 | 0.13.0 rmcp 反向投影（补正向）+ 0.11 sensitive + 0.12.0 ai_tool_audit |

**核心区分（必须先理解）——Skill ≠ Tool ≠ Capability**：

```

Skill (SKILL.md)                               →  注入 preamble（流程指导 + 知识）

```


**顺序理由**：
1. **MCP client 第一**——装好就有用。用户配一个 filesystem MCP server，AI 立刻能读文件。不需要嵌入模型，不需要 PoC。
2. **token-aware 窗口第二**——是真实缺口的直接修补：0.12.3 的 `SLIDING_WINDOW_SIZE=20` 不看 token 数，20 条长消息会爆 context、20 条短消息又浪费窗口。此修补是 FTS5 召回的前置（窗口不合理则召回无意义），且完全独立、零嵌入模型依赖。
3. **FTS5 召回第三**——在 token-aware 窗口把旧消息合理挤出后，召回它们。零嵌入模型依赖，确定性收益最高。
4. **Skill 第四**——对齐 agent 届通用概念（SKILL.md），需扫描多 agent 目录 + 格式兼容验证，需 PoC。
5. **MCP server 第五**——护城河。与 0.13.0 client 对称（补正向投影），让 Blink 能力被外部生态消费。零嵌入模型依赖，复用 0.13.0 已建的反向投影基础设施。
6. **CLI 化第六**——与 MCP server 共享「不启动 GUI」架构，天然成组。让 Blink 能力进入终端/脚本场景。

## 二、0.13.0 MCP client（消费外部 tool）

### 2.1 定位

Blink 作为 MCP client，消费生态里海量 server 提供的 tool，挂进对话窗口的 tool 池。让 Blink 变强——外部生态的 tool（文件操作 / 数据库查询 / API 调用 / ...）都能被 AI 自主调用。

**MCP tool 与 Skill 的区别**（避免混淆）：
- MCP tool = **AI 可执行**的外部能力（进 tool 池，AI 自主调用，有副作用）
- Skill = **AI 可读取**的流程指导（注入 preamble，增强 AI 知识与行为，不直接执行）

### 2.2 前置依赖（0.12 已铺好）

| 0.12 产出 | 0.13.0 复用方式 |
|---|---|
| **Tool 适配层**（§2.4） | `McpTool` 包装器也 `impl rig::tool::ToolDyn`，**统一进同一个适配器层** |
| **rmcp feature**（Cargo.toml 已开） | 用 `rmcp::model::Tool` 做 MCP 协议交互 + 0.13.0 反向投影 |
| **DB 四层拆分** | MCP server 配置存配置库 `config` 表；MCP tool 审计走 AI 库 `ai_tool_audit` |
| **PendingConfirms 危险确认闭环**（tool_adapter.rs:80-287） | McpTool 持 `Arc<PendingConfirms>`，复用危险确认弹窗 |

### 2.3 rmcp 反向投影（0.13.0 新建）

0.12 只开了 rmcp feature flag（`Cargo.toml`），**src 零引用，未实现投影函数**。0.13.0 新建反向投影：
- `rmcp::model::Tool::to_capability_schema()`——MCP client 用（消费外部 tool，反向投影为 CapabilitySchema）

投影函数建在 `src/domain/mcp/projection.rs`。正向投影（`CapabilitySchema::to_mcp_tool()`）留到 §六 0.13.4 MCP server 补。

### 2.4 client 编排

- **配置**：用户在设置页填外部 MCP server 列表（`name / command / args / env`，stdio 模式）
- **启动**：Blink 启动时拉起外部 server 子进程，握手，拉 tool 列表
- **反向投影**：`rmcp::model::Tool → CapabilitySchema`（§2.3）
- **tool 包装**：外部 tool 包装成 `McpTool { server, tool_def }` 进 0.12.0 的 Tool 适配层
  - **不走 CapabilityRegistry**（MCP tool 是「外部能力代理」，语义不同于内置 Capability）
  - 直接包装成 `McpTool` 进 Tool 适配层，通过 `build_agent_tools()` 工厂函数进对话窗口 tool 池
  - **若未来要让 MCP tool 也能被主窗口 Turn 2 调用**，则需走 `CapabilityRegistry::register`——0.13.0 可暂不暴露给主窗口，只挂对话窗口

### 2.5 外部 tool 进 tool 池

外部 tool 与 builtin Capability / 插件 tool **并列**进对话窗口 agent 的 tool 池，AI 调用时：
- 走 MCP 协议调外部 server（stdio JSON-RPC）
- 结果走 0.12.0 统一投影函数 `to_rig_tool_result()`
- rig Agent 自动管理 tool loop（0.12.2 已跑通）

### 2.6 故障与超时

- 外部 server 崩溃 → tool 标灰，从 tool 池剔除，UI 提示「MCP server XXX 已断开」
- invoke 超时 → rig Agent 的 tool call 错误处理（返回错误给 AI，AI 自主决定重试或换路）
- 启动时 server 未就绪 → 重试 3 次（间隔 2s），仍失败则跳过该 server，不阻塞其他
- **手动重连**：server 离线后可在设置页手动重连，不只是启动时拉起

### 2.7 设置页与产品呈现

设置页新增「MCP」tab：

**配置层**：
- server 列表（名称 / command / 状态在线·离线 / tool 数量）
- 添加/编辑/删除 server（name / command / args / env 表单，stdio 模式）
- 启动/停止/重连按钮（手动控制 server 生命周期）
- tool 列表预览（展开某个 server 看它提供的 tool 名称 + 描述）

**tool 可见性控制**：
- 每个 MCP server 可展开勾选/取消具体 tool，控制喂给 AI 的 tool 子集
- tool 太多会降低模型决策质量，用户需要能控制哪些 tool 喂给 AI

**对话窗口呈现**：
- composer bar 附近显示当前 tool 池规模（如「内置 8 + MCP 12 = 20 tools」）
- 工具卡片显示来源标记（如「filesystem (MCP)」），区分内置 Capability 和外部 MCP tool

### 2.8 0.13.0 验收

```
设置页「MCP」tab 可添加外部 MCP server（stdio 模式），配置 name/command/args/env
启动时拉起 server，拉到 tool 列表，进对话窗口 tool 池
rmcp::model::Tool::to_capability_schema() 反向投影实现 + 单测
McpTool 包装器 impl rig::tool::ToolDyn，走 ToolDyn 动态分发
对话窗口 AI 调外部 tool，结果走统一投影 to_rig_tool_result() 回流
外部 server 崩溃有降级处理（标灰 + 剔除 + UI 提示），不阻塞对话
invoke 超时有错误处理，AI 可自主重试或换路
server 离线后可手动重连
tool 粒度开关：可勾选/取消具体 tool，控制喂给 AI 的 tool 子集
对话窗口 tool 池规模指示（内置 N + MCP M = K tools）
工具卡片显示来源标记（MCP 来源）
```

## 三、0.13.1 token-aware context 压缩（补 0.12.3 滑动窗口缺口）

### 3.1 定位与缺口

**真实缺口**：0.12.3 的 `SqliteConversationMemory` 用硬编码条数窗口（`memory.rs:27` `SLIDING_WINDOW_SIZE=20`），**不看 token 数**：
- 20 条长消息（如带大段代码/长 tool result）→ 爆 context window，API 报错或被 provider 截断
- 20 条短消息 → 浪费 context window，本可塞更多历史

`memory.rs:9` 注释已诚实标注：「TokenWindow、摘要压缩和语义召回留后续版本」。0.13.1 补这个口子。

**为什么这是 0.13.1 而非更晚**：它是 0.13.2 FTS5 召回的前置——窗口策略不合理时（爆 context 或浪费），召回的旧消息仍受挤压，召回价值打折。先让窗口本身合理，召回才有放大作用。

### 3.2 ⚠️ 架构决策：自建策略，不接 rig hook

rig 提供 `TokenWindow` / `DemotionHook` 等**原语**，但**不提供「压缩策略」本身**——它给你钩子，摘要/丢弃怎么做你自己写。（这与 0.13.2 FTS5 §3.3 的决策一致：rig hook 是 token-based 触发，Blink 窗口策略自控更可控、更好测、无 rig 版本耦合。）

**0.13.1 决策：在 `SqliteConversationMemory` 内部自建 token-aware 窗口策略**：
- 估算而非精确计数（精确需要 tokenizer，每个 provider 不同；估算用启发式即可，误差容忍度高——接近上限就压缩，不要求精确到 token）
- 自控压缩时机（append 后判断），不依赖 rig hook

### 3.3 token 估算策略

精确 tokenizer 的问题：每个 provider 不同（OpenAI `tiktoken` / Anthropic 自有 / ollama 按模型），引入会增重依赖且版本耦合。

**0.13.1 用启发式估算**，三档够用：

| 估算方式 | 公式 | 适用 |
|---|---|---|
| **字符数 / 4**（默认） | `chars / 4` | 英文为主，OpenAI 经验值（1 token ≈ 4 chars） |
| **字符数 / 1.5**（中文） | `chars / 1.5` | 中文为主（1 汉字 ≈ 1-2 token） |
| **混合检测** | 文本中 CJK 占比 > 30% 用中文档，否则用英文件 | 自适应 |

估算误差 ±20% 可接受——压缩阈值留 buffer（如目标 80% 触发，不是 100%），不会因估算误差爆 context。

> **未来升级位**（0.14+ 可选）：若估算误差成为问题，可按 `ModelEntry.provider` 选 provider 官方 tokenizer（OpenAI 有 `tiktoken` Rust binding）。0.13.1 不做，启发式先跑通。

### 3.4 压缩策略（两段式）

```
append() 后：
  1. 估算当前窗口（最近 N 条）总 token
  2. 总 token ≤ model_context_limit * 0.8  → 不动，返回
  3. 总 token > limit * 0.8  → 触发压缩：
     a. 从窗口最旧端逐条移出，直到总 token ≤ limit * 0.7（留 buffer）
     b. 被移出的消息 → 归档（0.13.2 接 FTS5，0.13.1 先只丢弃+日志）
     c. 移出后若窗口首条是孤立 ToolResult（无配对 ToolCall）→ 复用
        现有 drop_leading_orphan_tool_results()（memory.rs:78）丢弃
```

**为什么不直接 LLM 摘要**（opencode 式粗暴截断+摘要）：
- 摘要损失信息且每次压缩多一次 LLM 调用（延迟 + 成本）
- Blink 的「窗口 + 召回」路径更优：旧消息不丢（归档 FTS5/向量），需要时召回——信息无损，延迟可控
- 0.13.1 只做「移出 + 归档位预留」，0.13.2 接 FTS5 归档，0.14.1 接向量归档

**两段式含义**：
- **段 1（token-aware 窗口）**：本节，决定「哪些消息留在 context 里」
- **段 2（FTS5/向量召回）**：0.13.2/0.14.1，决定「哪些旧消息被召回回 context」

两者配合 = 「窗口自适应 + 旧消息不丢 + 相关时召回」，比单一摘要策略精细。

### 3.5 model_context_limit 从哪来

从 0.12 Provider 统一配置取（`ModelEntry`）：每个模型带 context window 大小（如 GPT-4o 128K、Claude 200K、本地 qwen2.5 32K）。配置缺失时用保守默认（如 8K），并在设置页标注「未配置 context size，使用保守窗口」。

### 3.6 SqliteConversationMemory 改造点

| 改造点 | 内容 |
|---|---|
| `load()` | 加载后估算 token，超限则从旧端移出（in-memory 裁剪，不动 DB） |
| `append()` | 写入后若估算超限，记录「被挤出消息」到归档钩子（0.13.1 先 log，0.13.2 接 FTS5） |
| 新增 `estimate_tokens(messages) -> usize` | 启发式估算（§3.1.3） |
| 新增 `context_limit` 字段 | 从 ModelEntry 注入，构造 memory 时传入 |
| 复用 `drop_leading_orphan_tool_results` | 压缩后仍要处理孤立 ToolResult（已有，不动） |

**关键：DB 保留完整历史不变**。`load()` 的裁剪是 in-memory 的（只影响喂给 LLM 的窗口），DB 里消息全量保留——这与 0.12.3 现状一致，0.13.1 只改「窗口裁剪逻辑」不改「持久化」。

### 3.7 设置页

「AI」tab 记忆策略配置区（与 0.13.2 FTS5 共用一块）：


### 3.9 与 0.13.2 FTS5 / 0.14.1 向量召回的衔接

```

  被挤出的消息 → 归档钩子（0.13.1 log，预留）
       ↓ 0.13.2 接入
0.13.2 FTS5 召回
  归档钩子 → 写 memory_fts（BM25 关键词索引）

0.14.1 向量召回
```

## 四、0.13.2 记忆 FTS5 召回（对话历史全文检索）

### 4.1 定位

0.12.3 的 DB 持久化 memory（滑动窗口 20 条）已覆盖「记住最近对话」核心场景。0.13.2 升级为**全文检索召回**——当滑动窗口截断旧消息时，不是直接丢弃，而是归档到 FTS5 全文索引；当新对话与旧消息关键词相关时，自动召回作为上下文。

**与 0.14 记忆向量召回的关系**：0.13.2 是 L2 降级方案（FTS5 关键词召回，零嵌入模型依赖），0.14.1 是 L3 升级（向量语义召回，需嵌入模型 + zvec）。两者共享归档机制和 `<memory>` 注入机制，0.14 升级时只需替换检索后端。

### 4.2 前置依赖

| 产出 | 0.13.2 复用方式 |
|---|---|
| **0.12.3 SqliteConversationMemory** | 滑动窗口截断的旧消息归档到 FTS5 虚拟表 |
| **SQLite FTS5** | 全文检索引擎，sqlx 内置 libsqlite3-sys 默认启用 FTS5，零新依赖 |

### 4.3 ⚠️ 架构 gap（必须先 spike）

**当前 `SqliteConversationMemory` 用 SQL `LIMIT 20` 自己实现窗口**（`memory.rs:113-117` 调 `load_recent_messages(..., SLIDING_WINDOW_SIZE)`），**不接 rig 的 TokenWindow / DemotionHook**（memory.rs 顶部注释也只提"语义召回留后续版本"，未提 hook）。

**原方案假设 rig `DemotionHook` 会自动触发，但这条路径可能根本不通**——rig 的 hook 是 token-based 窗口触发的，Blink 是 message-count 窗口，语义不一致。

**0.13.2 决策：自己控制归档时机，不依赖 rig hook**：
- 在 `append()` 时，若写入后总数 > 窗口上限，把**被挤出的那条**消息归档到 FTS5
- 归档逻辑完全在 `SqliteConversationMemory` 内部，不引入 rig hook 依赖
- 理由：Blink 窗口策略是消息条数（非 token），自己归档更可控、更好测、无 rig 版本耦合

> 备选（spike 后若发现 rig hook 可用再评估）：impl rig `DemotionHook`。但当前倾向自控方案。

### 4.4 SQLite FTS5 能力

SQLite FTS5（Full-Text Search 5）是 SQLite 内置的全文检索引擎：

| 能力 | 说明 |
|---|---|
| `MATCH` 查询 | `WHERE memory_fts MATCH '搜索词'` 全文匹配 |
| BM25 排序 | `ORDER BY bm25(memory_fts)` 按相关度排序 |
| `trigram` 分词器 | 把文本切成 3 字符 n-gram，**中文友好**（不需要空格分词），支持子串模糊匹配 |
| 前缀匹配 | `'搜索*'` 匹配前缀 |
| 布尔运算 | `AND` / `OR` / `NOT` |
| 短语匹配 | `'"精确短语"'` |

sqlx 用的 `libsqlite3-sys` 默认编译时启用 FTS5，**零新依赖**。创建虚拟表：

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
  content,                          -- 消息文本内容
  conversation_id UNINDEXED,        -- 来源对话（不索引，仅存储用于过滤）
  role UNINDEXED,                   -- 消息角色（user/assistant）
  created_at UNINDEXED,             -- 时间戳（用于标注"X 天前"）
  tokenize = 'trigram'              -- trigram 分词器，中文友好
);
```

### 4.5 现有产品的记忆实现方式调研

| 产品 | 方式 | 机制 |
|---|---|---|
| **ChatGPT** | 混合（tool + 注入） | AI 调 `memory` tool 存取记忆 → 记忆是短事实（"用户喜欢 Python"）→ 相关记忆注入 system prompt |
| **mem0** | tool-based | `add_memory` / `search_memory` tool → LLM 从对话提取事实 → 向量库存储 → 检索注入 |
| **Letta (MemGPT)** | 分层（core + archival） | core memory 常驻 context → archival memory 通过 tool 调用检索 → AI 自主管理 |
| **Cursor** | RAG + rules | 代码向量化 → 检索注入 → `.cursorrules` 文件常驻 |
| **Claude** | 无跨对话记忆 | 仅靠 context window + projects |

**核心区分**——记忆有两类：
- **对话历史召回**：记住"之前说过什么" → 适合**自动注入**（prompt-injection）
- **事实记忆**：记住"用户是谁/喜欢什么" → 适合 **tool 调用**（AI 主动存取）

Blink 0.13.2 做的是**对话历史召回**——当滑动窗口截断旧消息后，从归档中检索相关的旧消息注入上下文。走 **prompt-injection**（自动召回注入），不是 tool 调用。

**为什么不用 tool 调用**：
- 用户问"上次我们讨论的 XXX 方案"时，AI 不一定知道该调 `search_memory`（它不知道有旧对话）
- 自动召回让 AI "自然地"拥有上下文，体验更接近 ChatGPT 的记忆感
- Tool 调用方式更适合**事实记忆**（如"记住我喜欢用 Python 3.12"），这是 0.14+ 可考虑的增强

### 4.6 记忆三层架构

```
L1 滑动窗口（0.12 已实现）
    最近 20 条消息，直接在 context 里
    ↓ 截断的消息
L2 FTS5 全文召回（0.13.2 新增 — 零嵌入模型依赖）
    截断的消息 → FTS5 归档
    新 prompt 到来 → FTS5 BM25 检索 → Top-K 召回 → <memory> 标签注入
    ↓ 0.14.1 升级
L3 向量语义召回（0.14.1 — 需嵌入模型 + zvec）
    截断的消息 → embedding → zvec 向量库
    新 prompt → embedding query → 向量检索 → Top-K 召回 → <memory> 标签注入
    （可与 L2 混合：FTS5 关键词 + 向量语义，取并集排序）
```

### 4.7 SqliteConversationMemory 改造

**自控归档方案**（不依赖 rig hook）：

1. **`append()` 改造**：
   - 现有逻辑：逐条插消息 → touch last_active_at
   - 新增：写入后若该对话消息总数 > `SLIDING_WINDOW_SIZE`，取被挤出的那条（第 N+1 条）→ 提取文本 → `INSERT INTO memory_fts`
   - 幂等性：按 `(conversation_id, message_content_hash)` 去重（同一消息不重复归档）

2. **`load()` 改造**：
   - 加载窗口内 20 条消息（现有逻辑不变）
   - 从最后一条 User 消息提取 query 文本
   - FTS5 `MATCH` 检索 `memory_fts` → BM25 排序 → Top-K（默认 3）
   - 召回的旧消息以 `<memory>` 标签注入消息列表头部
   - 召回的消息标注「来自历史对话（X 天前）」

### 4.8 FTS5 虚拟表 schema（AI 库）

```sql
-- FTS5 虚拟表（全文检索，trigram 分词器，中文友好）
CREATE VIRTUAL TABLE memory_fts USING fts5(
  content,                          -- 消息文本内容
  conversation_id UNINDEXED,        -- 来源对话（不索引，仅存储用于过滤）
  role UNINDEXED,                   -- 消息角色（user/assistant）
  created_at UNINDEXED,             -- 时间戳（用于标注"X 天前"）
  content_hash UNINDEXED,           -- 幂等 key（消息文本 hash）
  tokenize = 'trigram'
);

-- 检索示例：
-- SELECT content, role, created_at, bm25(memory_fts) AS score
-- FROM memory_fts
-- WHERE memory_fts MATCH '搜索词'
-- ORDER BY bm25(memory_fts)
-- LIMIT 3;
```

**与 0.14 `memories` 向量表的关系**：0.14.1 升级时新建 `memories` 表（向量 BLOB），FTS5 表保留作为关键词检索后端，两表通过 `conversation_id + content_hash` 关联，混合检索取并集排序。

### 4.9 数据流

```
新消息进来
  ↓
SqliteConversationMemory.append()  ← 持久化到 messages 表
  ↓
检查该对话消息总数
  ├─ ≤ 20 → 直接返回，FTS5 不动
  └─ > 20 → 取被挤出的那条（第 N+1 条）
       ├─ 提取文本 → 计算 content_hash
       └─ INSERT INTO memory_fts（幂等：content_hash 去重）

load() 时：
  1. 加载窗口内 20 条消息
  2. 从最后一条 User 消息提取 query 文本
  3. FTS5 MATCH 检索 memory_fts → BM25 排序 → Top-K（默认 3）
  4. 召回的旧消息以 <memory> 标签注入消息列表头部
  5. 标注「来自历史对话（X 天前）」
```

### 4.10 设置页

「AI」tab 新增记忆策略配置：
- 记忆模式：滑动窗口（默认） / 滑动窗口 + FTS5 召回
- 召回数量 K（默认 3）
- 召回相关度阈值（BM25 分数阈值，默认 -1.0，即不过滤）
- FTS5 分词器：trigram（默认，中文友好）/ unicode61（英文优先）

### 4.11 0.13.2 验收

```

append() 自控归档：写入后超窗口则归档被挤出消息（幂等：content_hash 去重）
load() 改造：FTS5 BM25 检索 → Top-K 召回 → <memory> 标签注入
```

## 五、0.13.3 Skill 约定式（复用 agent 届通用 skill 目录 + preamble 注入）

### 5.1 定位（对齐 agent 届通用概念）

**Skill = 约定式目录包**（SKILL.md + 可选资源），通过**注入 preamble** 增强 AI 的知识与行为，**不直接执行**。

这**不是 Blink 自创的概念**，而是对齐 agent 届通用的 **SKILL.md 模式**（Claude Code / ZCode / 其他 agent 都用这套）：

| 维度 | Skill（SKILL.md 约定式） | Tool / Capability / MCP tool |
|---|---|---|
| **形态** | 约定式目录（`SKILL.md` + 可选资源文件） | Rust 代码 / 外部进程 / MCP server |
| **生效方式** | **注入 preamble**（增强 AI 知识与行为） | **进 tool 池**（AI 自主调用执行） |
| **执行性** | 不直接执行，AI 读了之后用现有 tool/知识去执行 | 直接执行，有副作用 |
| **内容** | 流程指导 / 领域知识 / 工作流 / 最佳实践 | 原子能力 / 外部 API / CLI 命令 |
| **类比** | 给 AI 看的"操作手册 / SOP" | 给 AI 用的"工具箱" |

**举例**：
- 一个 `SKILL.md` 写"调试 Rust 编译错误的标准流程：1. 读 error 2. 定位 3. 修复 4. cargo check"——AI 注入后遇到 Rust 编译错误会按这个流程做
- 一个 MCP filesystem tool——AI 想读文件时**调用**它

两者**互补不冲突**：Skill 教 AI **怎么做**，Tool 让 AI **能做什么**。

### 5.2 核心设计原则：复用生态，不造新概念

**关键决策：Blink 不引入"工作目录/cwd"概念，也不自创新目录约定，而是直接读取 agent 届已有的通用 skill 目录生态。**

用户在其他 agent（Claude Code / ZCode / Cursor / ...）里配好的 Skill，Blink 直接读、直接用。用户的 Skill 投入零迁移成本，Blink 也无需维护"预设包"。

| 原则 | 说明 |
|---|---|
| **复用 > 自创** | 用户已有的 `~/.claude/skills/`、`~/.zcode/skills/` 等，Blink 直接扫描读取，不要求用户重新配置 |
| **不引入 cwd** | 不做"项目级/工作目录"绑定——Blink 是全局启动器，对话窗口不绑定特定项目路径。Skill 全部来自用户级目录（跨项目共享） |
| **SKILL.md 只读** | Blink 只**读取并注入** SKILL.md 内容，不修改、不回写其他 agent 的目录 |
| **格式兼容** | 优先兼容 Claude Code / ZCode 的 SKILL.md frontmatter 格式，Blink 特有字段（如 `triggers`）做成可选，不破坏跨 agent 兼容 |

### 5.3 前置条件：PoC 验证

**启动条件**：先做 PoC——验证目录发现 + 渐进式披露的完整流程。

PoC 要回答的问题：
1. **目录发现**：扫描多个 agent 的 skill 目录（`~/.claude/skills/`、`~/.zcode/skills/`、Blink 自身目录），性能与冲突处理如何？
2. **格式兼容**：Claude Code / ZCode 的 SKILL.md frontmatter 字段差异多大？Blink 能否无损读取？
3. **触发判定**：AI 什么时候该用哪个 Skill？（关键词匹配 / preamble 注入 / 显式 `/skill` 指令）
4. **渐进式披露**：SKILL.md 全文注入 vs 只注入摘要，token 成本与效果权衡

**若 PoC 不通过**：降级为 P3 或推 0.14。

### 5.4 目录发现（多 agent 目录聚合）

Skill 通过**扫描多个 agent 的约定目录**自动发现。Blink 聚合三类来源：

| 来源 | 路径（Windows） | 说明 | 默认启用 |
|---|---|---|---|
| **Blink 自身目录** | `%APPDATA%\blink\skills\` | Blink 随版本携带的默认 Skill（如有） | ✅ |
| **导入 Claude Code** | `%USERPROFILE%\.claude\skills\` | 用户在 Claude Code 配的 Skill | ⚙️ 可配置开关 |
| **导入 ZCode** | `%USERPROFILE%\.zcode\skills\` | 用户在 ZCode 配的 Skill | ⚠️ PoC 确认路径 |
| **自定义目录**（扩展位） | 用户在设置页添加的额外目录 | 未来支持任意 skill 目录 | 0.13.3 可不做 |

> **路径说明**：`%USERPROFILE%` = `C:\Users\{user}`，对应 Unix 的 `~`。`~/.claude/skills/` 在 Windows 即 `%USERPROFILE%\.claude\skills\`。PoC 需确认 Claude Code / ZCode 在 Windows 的实际落盘路径（可能用 `dirs_next::home_dir()`）。

**聚合规则**：
- **合并不去重**：不同 agent 的同名 Skill 各自保留，标注来源（如 `rust-debug-workflow (claude)` vs `rust-debug-workflow (blink)`），让用户/preamble 知道出处
- **按来源开关**：用户可在设置页勾选启用哪些 agent 的目录（默认 Blink 自身 + Claude Code）

**发现时机**：
- 启动时扫描所有启用的目录（静态）
- 设置页「刷新」按钮手动重扫
- 不监听文件变化（0.13.3 范围，0.14+ 可加 fs watch）

### 5.5 SKILL.md 格式（兼容通用约定）

每个 Skill 是一个目录，含 `SKILL.md` + 可选资源：

```
{skill_dir}/
  ├─ SKILL.md              ← 必需，主文件
  ├─ resources/            ← 可选，辅助资源（脚本/模板/示例）
  │   ├─ template.txt
  │   └─ example.json
  └─ scripts/              ← 可选，Skill 引用的脚本
```

**SKILL.md 格式**（YAML frontmatter + Markdown body）：

```markdown
---
name: rust-debug-workflow
description: 调试 Rust 编译错误的标准流程
triggers:                          # Blink 可选扩展字段（其他 agent 会忽略）
  keywords: [cargo, rustc, compile error, E0xxx]
  patterns: ["error\\[E\\d+\\]"]
priority: normal                   # Blink 可选扩展字段
---

# Rust 编译错误调试流程

当遇到 Rust 编译错误时，按以下流程：

1. 完整读取 error message，定位 error code（如 `E0308`）
2. ...
3. 修复后跑 `cargo check` 验证

## 常见 error code 速查
- E0308: 类型不匹配
- ...
```

**字段兼容策略**：
- `name` / `description`：所有 agent 通用，必填
- `triggers` / `priority`：Blink 扩展字段，**可选**。缺失时 Blink 退化为"只进阶段 1 摘要，不自动触发阶段 2，靠 `/skill` 显式激活"
- 其他 agent 的特有字段（如 Claude Code 的某些字段）：Blink 忽略，不报错

**反向兼容**：Blink 自身目录的 SKILL.md 也只写通用字段 + 可选 triggers，保证用户能把 Blink 的 Skill 复制到其他 agent 用。

### 5.6 渐进式披露（控制 token 成本）

**问题**：所有 Skill 全文注入 preamble 会爆 token（聚合多 agent 目录后数量可能很多）。

**方案**：两阶段披露：

| 阶段 | 注入内容 | 时机 | token 成本 |
|---|---|---|---|
| **阶段 1（常驻）** | 所有 Skill 的 `name + description` 摘要 | 每个 preamble 都带 | 低（每个 Skill ~50 token） |
| **阶段 2（按需）** | 命中触发条件的 Skill 的完整 SKILL.md | 触发后才注入 | 中（命中才付） |

**触发判定**（阶段 1 → 阶段 2）：
- **关键词匹配**：用户消息含 `triggers.keywords` 任一关键词（需 SKILL.md 配了 triggers）
- **正则匹配**：用户消息匹配 `triggers.patterns`
- **显式调用**：用户输入 `/skill rust-debug-workflow`（对话窗口指令）
- **AI 自主**（0.14+）：AI 看到摘要后主动调 `load_skill` tool 拉全文（需 tool 化，0.13 先不做）

**0.13.3 范围**：关键词/正则/显式三种触发。无 triggers 字段的 Skill 只能靠 `/skill` 显式激活。AI 自主 load 留 0.14。

### 5.7 preamble 注入（复用 0.12.6 机制）

Skill 注入走 **0.12.6 已铺好的 preamble 组装链路**，零新增缓存失效逻辑：

```
chat_system_prompt_with_group(group_prompt)     ← 0.12.6 现有
    ↓ 0.13.3 扩展
chat_system_prompt_full(group_prompt, skills)   ← 新签名
    = 基础 prompt
    + 【分组指令】{group_prompt}                 ← 0.12.6
    + 【可用技能】                               ← 0.13.3 新增
      [{source}] {skill1.name}: {skill1.description}   （阶段 1 摘要，所有 Skill）
      [{source}] {skill2.name}: {skill2.description}
      ...                                                （[source] 标注来源：blink/claude/zcode）
    + 【已激活技能详情】                          ← 触发后追加
      {triggered_skill.full_content}             （阶段 2 全文）
```

**缓存失效自动**：preamble 字符串变化 → `hash_preamble()` 变 → AgentProvider cache miss → 重建。**无需手工失效**（`chat_service.rs:645-649` 已实现 hash）。

### 5.8 Skill 生命周期

```
启动时
  ↓
按设置页启用的来源，扫描各 agent skill 目录：
  ├─ %APPDATA%\blink\skills\        （Blink 自身）
  ├─ %USERPROFILE%\.claude\skills\  （导入 Claude Code，若启用）
  └─ %USERPROFILE%\.zcode\skills\   （导入 ZCode，若启用）
  ↓
解析每个 SKILL.md → SkillEntry { name, description, triggers?, full_content, source }
  ↓
存内存 SkillRegistry（不进 DB，每次启动/刷新重扫）

chat_prompt 时：
  1. 取 SkillRegistry 全集
  2. 阶段 1：所有 Skill 摘要注入 preamble（标注来源）
  3. 阶段 2：用户消息触发关键词/正则 → 命中 Skill 全文注入 preamble
  4. preamble_hash 变化 → AgentProvider 重建
  5. AI 读到 Skill 内容，按其指导行动
```

### 5.9 Skill 存储

- **Skill 定义（SKILL.md）**：文件系统，不进 DB。各 agent 目录自动发现。
- **SkillRegistry**：内存结构，启动时扫描，设置页可手动刷新。
- **来源开关**：配置库 `config` 表（`skill:sources` key，记录启用哪些 agent 目录）。

**为什么 Skill 不进 DB**：SKILL.md 是文件系统约定（各 agent 共享），进 DB 反而破坏"复用生态"语义，且与源不同步。

**为什么不引入 cwd**：Blink 是全局启动器，对话窗口不绑定特定项目；用户级 skill 目录（跨项目共享）已覆盖核心场景。项目级 skill（`.blink/skills/` in repo）若未来有需求，可作为"自定义目录"扩展位加入，但 0.13.3 不做。

## 六、0.13.4 MCP server（护城河——暴露 Blink 能力给生态）

### 8.1 定位

Blink 作为 MCP server，把自己的能力（Capability / Action / 搜索）暴露给外部 MCP client（其他 AI 工具 / IDE / 自动化脚本 / opencode / Claude Code 等）。这是 Blink 的**护城河**——让 Blink 的本地能力（截图 / OCR / 剪贴板 / 应用搜索 / 文件搜索 / Skill / MCP 代理）成为 AI 生态的共享资源。

**与 0.13.0 MCP client 的对称关系**：
- 0.13.0 MCP **client**：Blink 消费外部 tool（让 Blink 的 AI 更强）
- 0.13.4 MCP **server**：Blink 暴露自身能力（让外部 AI 能用 Blink）

两者共用 rmcp 投影基础设施（0.13.0 已建反向投影，0.13.4 补正向投影），是一对对称的开放能力。

### 8.2 前置依赖（0.13.0 / 0.12 / 0.11 已铺好）

| 产出 | 0.13.4 复用方式 |
|---|---|
| **rmcp 反向投影**（0.13.0 已建） | 0.13.4 补正向投影 `CapabilitySchema::to_mcp_tool()` |
| **sensitive 字段**（0.11） | 授权 UI——外部调用 sensitive capability 需用户确认 |
| **审计日志**（0.12.0 `ai_tool_audit`） | 对外调用审计（扩 `ai_tool_audit` 或新建 `mcp_audit` 表） |
| **Skill / MCP 代理**（0.13.0/0.13.3） | 可选暴露 Blink 的 Skill 和 MCP 代理能力给外部 |

### 8.3 传输模式

**调研 #17**（0.13.4 启动前定案）：
- **stdio 模式**：外部 client 拉起 Blink 子进程，走 stdin/stdout JSON-RPC（最简单，与 0.13.0 MCP client 对称）
- **HTTP/SSE 模式**：Blink 起一个本地 HTTP server，外部 client 连接（更灵活，支持多 client）
- **建议**：0.13.4 先做 stdio 模式（与 MCP client 对称，实现最简），HTTP 模式推后续

### 8.4 能力暴露策略

不是所有 Capability / Action 都适合暴露给外部：

| 能力 | 暴露? | 理由 |
|---|---|---|
| `capture_screen` / `crop_image` | ✅ | 截图能力是 Blink 特色 |
| `read_clipboard` / `write_clipboard` | ✅（sensitive） | 剪贴板读写，sensitive 需授权 |
| `search_apps` | ✅ | 应用搜索是 Blink 特色 |
| `search_files` | ✅ | 文件搜索 |
| `search_clipboard_history` | ⚠️ sensitive | 剪贴板历史含隐私，sensitive 需授权 |
| Skill（0.13.3） | ⚠️ 可选 | 暴露 Blink 的 Skill 给外部 |
| 内置 Action（shutdown / restart） | ❌ | 系统级操作不暴露 |

**暴露清单**：用户在设置页「MCP server」tab 勾选要暴露的能力。

### 8.5 授权机制

- **sensitive capability**：外部调用时，Blink 弹确认卡片（与主窗口 AI 调 dangerous action 一致），用户确认后执行
- **non-sensitive capability**：直接执行，走审计日志

### 8.6 审计

对外调用走审计日志（AI 库）：
- 复用 `ai_tool_audit` 表（加 `caller` 字段区分 `internal` / `mcp_external`）
- 或新建 `mcp_audit` 表（独立审计，与 AI tool 审计分离）
- **建议**：复用 `ai_tool_audit`，加 `caller` 字段，避免表爆炸

### 8.7 设置页

设置页「MCP server」tab（与「MCP client」tab 同组）：
- 总开关（启用 MCP server）
- 传输模式选择（stdio / HTTP）
- 暴露能力清单（Checkbox 列表，带 sensitive 标记）
- 审计日志查看（最近 N 条对外调用）

### 8.8 0.13.4 验收

```
 CapabilitySchema::to_mcp_tool() 正向投影实现 + 单测
 设置页「MCP server」tab，可勾选暴露的能力
 stdio 模式启动，外部 MCP client 可拉到 Blink 的 tool 列表
 外部 client 调 Blink capability，结果走 rmcp 协议返回
 sensitive capability 弹确认卡片，用户确认后执行
 对外调用走审计日志（ai_tool_audit + caller=mcp_external）
 非暴露能力不出现在 tool 列表中
```

## 七、0.13.5 自身 CLI 化（Blink as CLI）

### 9.1 定位

Blink 自身成为命令行工具——`blink chat` / `blink search` / `blink screenshot` / `blink translate`。让 Blink 的能力不限于 GUI 窗口，也能在终端 / 脚本 / 自动化场景中使用。

**为什么放 0.13 而非独立版本**：CLI 化本质是「复用 Capability/Tauri commands 逻辑，加一层 clap 入口」，与 MCP server（0.13.4）共享「不启动 GUI、直接调后端函数」的架构，两者天然成组。

### 9.2 前置依赖

| 产出 | 0.13.5 复用方式 |
|---|---|
| **CapabilitySchema**（0.11） | CLI 派生——schema → clap 参数（0.11 已预留 `to_clap()` 设计） |
| **CapabilityRegistry**（0.12.0） | CLI 调用 capability——`blink {cap_id} --args` |
| **Tauri commands**（0.12） | CLI 复用 commands 逻辑——不经过 Tauri IPC，直接调函数 |
| **MCP server**（0.13.4） | CLI 模式可作为 MCP server 运行（`blink mcp-server`） |

### 9.3 CLI 架构

```
blink <command> [options]

# 核心命令
blink chat [--model <id>] [--conversation <id>]    # 对话模式（终端交互）
blink search <query>                                 # 应用搜索
blink screenshot [--display <n>] [--output <path>]  # 截图
blink translate <text> [--from <lang>] [--to <lang>] # 翻译
blink clipboard [--history]                          # 剪贴板操作

# 能力代理
blink run <capability> [--args JSON]                # 调用任意 Capability
blink skill list                                     # 列出已注册 Skill（0.13.3）
blink skill run <name> [--args JSON]                 # 运行 Skill

# MCP
blink mcp-server                                     # 作为 MCP server 运行（stdio，0.13.4）
blink mcp-client list                                # 列出已配置 MCP server（0.13.0）

# 配置
blink config get <key>                               # 读配置
blink config set <key> <value>                       # 写配置
blink providers list                                 # 列出 AI Provider
```

### 9.4 设计要点

- **不启动 GUI**：CLI 模式下不创建 Tauri 窗口，直接调后端函数
- **共享后端逻辑**：CLI 和 GUI 共用 `src/domain/` 和 `src/app/` 的函数，不重复实现
- **输出格式**：默认人类可读，`--json` 切换 JSON 输出（供脚本消费）
- **MCP server 模式**：`blink mcp-server` 等价于 0.13.4 的 stdio MCP server，但以独立进程运行

### 9.5 0.13.5 验收

```

 blink search <query>：应用搜索，--json 输出 JSON
 blink screenshot：截图，--output 指定输出路径
 blink run <capability>：调用任意 Capability，--args 传 JSON 参数
 blink skill list / blink skill run：Skill 管理和运行
```

## 九、架构优化（0.13 顺带清理的债务）

> review 0.13 规划时发现的现有架构债务，0.13 落地时**顺带清理**（不单独开版本，附着在相关模块上）。

### 9.1 数据目录路径散落（附着：0.13.3 Skill L1 全局目录）

**现状**：`%APPDATA%\blink\` 路径获取散落 5+ 处，无统一封装：
- `src/infra/data/pools.rs:93-96`（模块私有 `fn data_dir()`）
- `src/app/commands.rs:1758-1759`、`1844-1845`、`1877-1878`
- `src/infra/utils/logging.rs:113`
- `src/domain/execution/builtin.rs:340`
- 另有 `dirs_next::data_dir()` 写法散布（`python/mod.rs:113` 等）

**问题**：同一逻辑多份拷贝，改一处漏其他；模块私有函数无法跨模块复用。

**优化**：抽出 `src/infra/utils/paths.rs`，提供：
```rust
pub fn app_data_dir() -> PathBuf { ... }      // %APPDATA%\blink
pub fn logs_dir() -> PathBuf { ... }          // app_data_dir().join("logs")
pub fn skills_global_dir() -> PathBuf { ... } // app_data_dir().join("skills")  ← 0.13.3 新增
pub fn db_dir() -> PathBuf { ... }            // app_data_dir().join("*.db")
```
全项目改用这个 helper，删除散落拷贝。

### 9.2 CapabilityTool.is_dangerous() 不读 sensitive（附着：0.13.0 McpTool）

**现状**：`CapabilitySchema.sensitive` 字段 0.11.2 就加了（`schema.rs:30-33`），但 `CapabilityTool::is_dangerous()`（`tool_adapter.rs:333-335`）只看 `danger_class()`，**不读 sensitive**：
```rust
fn is_dangerous(&self) -> bool {
    matches!(self.cap.danger_class(), DangerClass::Dangerous)  // ← 没看 sensitive
}
```
`sensitive` 字段在整个 tool_adapter 里**零引用**（grep 确认）。

**问题**：`search_apps` / `search_clipboard_history` 等已标 `sensitive=true`，但实际不触发确认弹窗——字段是死字段。

**优化**（0.13.0 做，因为 McpTool 也要用危险标记）：
- 统一语义：`sensitive` 和 `danger_class` 二选一或合并
- 推荐方案：`CapabilityTool::is_dangerous()` 改为 `danger_class == Dangerous || schema.sensitive`
- 或更彻底：废掉 `sensitive` 字段，统一用 `danger_class`（Capability trait 已有 `danger_class()` 方法，`schema.rs:69-71`）

### 9.3 外部 tool 路径不一致（附着：0.13.0 McpTool，预防性）

**现状**：三种"外部 tool"走三条不同路径：
- 插件 tool → `ActionRegistry` → `ActionTool`（0.9.3 落地，改动成本高，**不动**）
- MCP tool → 规划独立 `McpTool`（0.13.0 新建）
- ~~Skill → 原 Capability 路径~~（0.13.3 已改为 preamble 注入，**不进 tool 池**，问题消失）
