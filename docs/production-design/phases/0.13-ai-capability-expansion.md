# Blink 0.13 — AI 调用能力扩展(MCP client / RAG / MCP server / Skill / 记忆向量召回)

> **范围**:① MCP client(消费外部 tool) + ② RAG(知识库检索作为内部 tool) + ③ 记忆向量召回(对话历史语义检索) + ④ MCP server(护城河——暴露 Blink 能力) + ⑤ Skill 化(CLI 探索→AI 生成 skill)。
>
> **主题**:0.12 搭好了 AI 能力的架构骨架(独立对话窗口 + 多轮 agent loop + 持久化记忆 + Tool 适配层)。0.13 在此骨架上**扩展调用能力**——让 AI 能调外部世界(MCP client)、能检索本地知识(RAG)、能记住更远的对话(向量召回)、能被外部世界调用(MCP server)、能把 CLI 变成 skill(Skill 化)。
>
> **产品边界决策**:**Blink 不做 AI 运行时**。本地推理靠外部(ollama / lmstudio),Blink 只作 Provider 对接 + 能力编排。
>
> **前置**:0.12 完成(对话窗口 + 对话机制 + Tool 适配层 + Provider 模型统一管理 + DB 四层拆分 + ollama 接入)。
>
> **原则**:0.12 的架构骨架不破;调用能力扩展走 Tool 适配层统一接入(不绕过);安装包保持 < 100MB;Skill 需 PoC 验证再落地。

## 一、范围与边界

### 1.1 0.12 → 0.13 衔接

0.12 搭好了 AI 能力架构的**骨架**:


## 二、0.13.0 MCP client(消费外部 tool)

### 2.1 定位

Blink 作为 MCP client,消费生态里海量 server 提供的 tool,挂进对话窗口的 tool 池。让 Blink 变强——外部生态的 tool(文件操作 / 数据库查询 / API 调用 / ...)都能被 AI 自主调用。

### 2.2 前置依赖(0.12 已铺好)

| 0.12 产出 | 0.13.0 复用方式 |
|---|---|
| **Tool 适配层**(§2.4) | `McpTool` 包装器也 `impl rig::tool::Tool`,**统一进同一个适配器层** |
| **rmcp feature**(Cargo.toml 已开) | 用 `rmcp::model::Tool` 做 MCP 协议交互 + 0.13.0 双向投影 |
| **DB 四层拆分** | MCP server 配置存配置库 `config` 表;MCP tool 审计走 AI 库 `ai_tool_audit` |

### 2.3 rmcp 双向投影(0.13.0 新建)

0.12 只开了 rmcp feature flag(`Cargo.toml`),**src 零引用,未实现投影函数**。0.13.0 新建双向投影:
- `rmcp::model::Tool::to_capability_schema()`——0.13.0 MCP client 用(消费外部 tool,反向投影)
- `CapabilitySchema::to_mcp_tool()`——0.13.3 MCP server 用(暴露 Blink 能力,正向投影)

两个投影函数同建在 `src/domain/mcp/projection.rs`,0.13.0 先实现反向(client 用),0.13.3 补正向(server 用)。

### 2.4 client 编排

- **配置**:用户在设置页填外部 MCP server 列表(`name / command / args / env`,stdio 模式)
- **启动**:Blink 启动时拉起外部 server 子进程,握手,拉 tool 列表
- **反向投影**:`rmcp::model::Tool → CapabilitySchema`(§2.3)
- **tool 包装**:外部 tool 包装成 `McpTool { server, tool_def }` 进 0.12.0 的 Tool 适配层(§2.4,`impl rig::tool::Tool`)
  - **不走 CapabilityRegistry**(MCP tool 是「外部能力代理」,语义不同于内置 Capability)
  - 直接包装成 `McpTool` 进 Tool 适配层,通过 `build_agent_tools()` 工厂函数进对话窗口 tool 池
  - **若未来要让 MCP tool 也能被主窗口 Turn 2 调用**,则需走 `CapabilityRegistry::register`——0.13.0 可暂不暴露给主窗口,只挂对话窗口

### 2.5 外部 tool 进 tool 池

外部 tool 与 builtin Capability / 插件 tool **并列**进对话窗口 agent 的 tool 池,AI 调用时:
- 走 MCP 协议调外部 server(stdio JSON-RPC)
- 结果走 0.12.0 统一投影函数 `to_rig_tool_result()`
- rig Agent 自动管理 tool loop(0.12.2 已跑通)

### 2.6 故障与超时

- 外部 server 崩溃 → tool 标灰,从 tool 池剔除,UI 提示「MCP server XXX 已断开」
- invoke 超时 → rig Agent 的 tool call 错误处理(返回错误给 AI,AI 自主决定重试或换路)
- 启动时 server 未就绪 → 重试 3 次(间隔 2s),仍失败则跳过该 server,不阻塞其他

### 2.7 设置页

设置页新增「MCP」tab:
- server 列表(名称 / command / 状态在线/离线 / tool 数量)
- 添加/编辑/删除 server(name / command / args / env 表单)
- 启动/停止按钮(手动控制 server 生命周期)
- tool 列表预览(展开某个 server 看它提供的 tool 名称 + 描述)

### 2.8 0.13.0 验收

```
 设置页「MCP」tab 可添加外部 MCP server(stdio 模式),配置 name/command/args/env
 启动时拉起 server,拉到 tool 列表,进对话窗口 tool 池
 rmcp::model::Tool::to_capability_schema() 反向投影实现 + 单测
 McpTool 包装器 impl rig::tool::Tool,走 ToolDyn 动态分发
 对话窗口 AI 调外部 tool,结果走统一投影 to_rig_tool_result() 回流
 外部 server 崩溃有降级处理(标灰 + 剔除 + UI 提示),不阻塞对话
 invoke 超时有错误处理,AI 可自主重试或换路
```

## 三、0.13.1 RAG(知识库检索作为内部 tool)

### 3.1 定位

VectorRouter 在 0.9 移出后在这里找到归宿——对本地文档库 / 笔记做语义检索,作为 AI 回答的上下文。**记忆的「向量召回」语义在 0.13.2**,0.13.1 只做用户主动加入知识库的 RAG。

### 3.2 前置依赖(0.12 已铺好)

| 0.12 产出 | 0.13.1 复用方式 |
|---|---|
| **Provider 模型统一管理**(§2.7) | embedding 模型从 `ModelEntry.capabilities` 含 `Embedding` 的模型中选 |
| **ollama 接入**(§2.3) | 本地 embedding 走 ollama `nomic-embed-text`(rig 现成) |
| **Tool 适配层**(§2.4) | RAG 作为 `search_knowledge_base` Capability,经 Tool 适配层包装进 tool 池 |
| **对话窗口 tool loop**(0.12.2) | AI 自主调 RAG tool,结果走 tool loop 回流 |
| **DB 四层拆分** | 向量数据存 AI 库 `blink_ai.db`(`embeddings` 表) |

### 3.3 embedding 生产 vs 向量存储的边界

| 层 | 技术选择 | 理由 |
|---|---|---|
| **embedding 生产** | 走 rig `EmbeddingsModel`(ollama `nomic-embed-text` / 云端 API) | 复用 0.12 Provider 抽象 + ollama 接入,零摩擦 |
| **向量存储 / 检索** | 自写 + SQLite BLOB(暴力 cosine 起步) | 贴 Awareness 域,SQLite 已有生态;**不引 rig-vector / sqlite-vec** |

**embedding Provider 复用 0.12 的统一配置**:用户在 AI 供应商页标记 `nomic-embed-text` 为 Embedding 能力后,RAG 直接从此配置取 provider + model。本地 ollama 零成本产 embedding;云端按 token 计费时用户可切云端 embedding Provider。

### 3.4 暴力 cosine 起步

- **起步**:暴力 cosine(1000 条向量内 CPU < 10ms),持久化走 SQLite BLOB(AI 库 `embeddings` 表)
- **扩展**:真到 10 万+ 再上 `sqlite-vec`(届时引入,不提前引依赖)

### 3.5 embedding 一致性约束(切模型必重建)

**向量库必须锁 embedding model_id**:向量存 `(model_id, vector)`,切 embedding Provider(维度不同 / 语义空间不同)触发**重建索引 UI 提示**,不隐式失效数据。

### 3.6 RAG 作为内部 Capability

**建模决策**:RAG 检索建模为一个 Capability `search_knowledge_base`,进对话窗口 tool 池。AI 判断需要本地知识时自主调用,结果走 tool loop 回流。

这样 RAG **不需要单独的调用路径**,完全复用 0.12 铺好的链路:
- 用户加文档 → 后台异步 embedding(走 ollama)→ 写入向量库
- AI 调 `search_knowledge_base(query)` → 暴力 cosine 检索 → `CapabilityResult::Items`
- 结果投影走 0.12.0 统一 `to_rig_tool_result()`
- rig Agent 自主消费 RAG 上下文做总结

### 3.7 向量存储 schema(AI 库)

```sql
CREATE TABLE embeddings (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  source_path TEXT NOT NULL,       -- 源文件路径
  chunk_text TEXT NOT NULL,        -- 分块文本
  embedding BLOB NOT NULL,         -- 向量(序列化 f32 数组)
  model_id TEXT NOT NULL,          -- 锁 embedding 模型(切模型触发重建)
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_embeddings_model ON embeddings(model_id);
CREATE INDEX idx_embeddings_source ON embeddings(source_path);
```

### 3.8 文档处理流水线

- **支持的格式**:`.txt` / `.md` / `.pdf`(文本提取) / `.docx`(文本提取)
- **分块策略**:按段落分块,每块 ~500 token,相邻块重叠 50 token
- **异步处理**:用户加文档后后台异步 embedding,进度可见,不阻塞 UI
- **增量更新**:文件修改时间变化时重新 embedding 该文件,删除文件时清理对应向量

### 3.9 设置页

设置页新增「知识库」tab:
- 文档/目录列表(路径 / 状态已索引/索引中/失败 / 向量数)
- 添加文件 / 添加目录按钮
- 删除按钮(删文档 + 清理对应向量)
- 当前 embedding 模型显示 + 切换模型提示重建
- 索引进度条(异步 embedding 时)

### 3.10 0.13.1 验收

```
 设置页「知识库」tab,可添加本地文档(单文件 / 目录)
 后台异步 embedding(走 ollama nomic-embed-text 或云端),进度可见,不阻塞 UI
 文档分块(.txt/.md/.pdf/.docx),增量更新(文件改动重新索引)
 向量存储走 AI 库 embeddings 表(SQLite BLOB),锁 model_id
 暴力 cosine 检索(1000 条向量内 CPU < 10ms)
 search_knowledge_base Capability 进对话窗口 tool 池,经 Tool 适配层包装
 对话窗口问"我笔记里有没有提到 XXX" → AI 自主调 search_knowledge_base
 切 embedding Provider 提示重建索引,不隐式失效
```

## 四、0.13.2 记忆向量召回(对话历史语义检索)

### 4.1 定位

0.12.2 的 DB 持久化 memory(滑动窗口)已覆盖「记住最近对话」核心场景。0.13.2 升级为**语义召回**——当滑动窗口截断旧消息时,不是直接丢弃,而是归档到向量库;当新对话与旧消息语义相关时,自动召回作为上下文。

### 4.2 前置依赖

| 产出 | 0.13.2 复用方式 |
|---|---|
| **0.12.2 SqliteConversationMemory** | 滑动窗口截断的旧消息归档到向量库 |
| **0.13.1 RAG 向量基础设施** | embedding 生产 + 向量存储 + 暴力 cosine 检索 |

### 4.3 rig `DemotingPolicyMemory` 钩子

用 rig `DemotingPolicyMemory` 的钩子机制:
- 窗口截断掉的旧消息 → embedding → 归档到向量库(`memories` 表,与 `embeddings` 表分离)
- 新 prompt 到来时 → embedding query → cosine 检索相关旧消息 → 注入上下文

**检索策略**:
- Top-K 召回(默认 K=3),按相似度排序
- 只在对话窗口生效(主窗口无 memory,不受影响)
- 召回的消息以 `<memory>...</memory>` 标签注入 system prompt,标注「来自历史对话」

### 4.4 向量存储 schema(AI 库)

```sql
CREATE TABLE memories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL,    -- 来源对话
  message_content TEXT NOT NULL,    -- 原始消息内容
  embedding BLOB NOT NULL,          -- 向量
  model_id TEXT NOT NULL,           -- 锁 embedding 模型
  created_at INTEGER NOT NULL,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE
);
CREATE INDEX idx_memories_conv ON memories(conversation_id);
```

### 4.5 与滑动窗口的关系

```
新消息进来
  ↓
SqliteConversationMemory.append()  ← 持久化到 messages 表
  ↓
滑动窗口检查(last_messages(20))
  ├─ 未超限 → 直接返回窗口内消息
  └─ 超限 → 截断旧消息
       ├─ 截断的消息 → embedding → 写入 memories 表(归档)
       └─ 新 prompt embedding → cosine 检索 memories 表 → Top-K 召回
            → 注入 <memory> 标签到 system prompt
```

### 4.6 设置页

「AI」tab 新增记忆策略配置:
- 记忆模式:滑动窗口(默认) / 滑动窗口 + 语义召回
- 召回数量 K(默认 3)
- 召回相似度阈值(默认 0.7)

### 4.7 0.13.2 验收

```
 滑动窗口截断的旧消息自动归档到向量库(memories 表)
 新对话与旧消息语义相关时,Top-K 召回注入上下文(<memory> 标签)
 召回的消息标注「来自历史对话」,AI 可引用
 删除对话时级联清理 memories 表对应行
 设置页可配置记忆模式 + 召回参数
 主窗口不受影响(无 memory)
```

## 五、0.13.3 MCP server(护城河——暴露 Blink 能力)

### 5.1 定位

Blink 作为 MCP server,把自己的能力(Capability / Action / 搜索)暴露给外部 MCP client(其他 AI 工具 / IDE / 自动化脚本)。这是 Blink 的**护城河**——让 Blink 的本地能力(截图 / OCR / 剪贴板 / 应用搜索 / 文件搜索)成为 AI 生态的共享资源。

### 5.2 前置依赖(0.12 / 0.11 已铺好)

| 产出 | 0.13.3 复用方式 |
|---|---|
| **rmcp 正向投影**(0.13.0 已实现反向,0.13.3 补正向) | `CapabilitySchema::to_mcp_tool()` 把 Blink 能力投影为 MCP tool |
| **sensitive 字段**(0.11) | 授权 UI——外部调用 sensitive capability 需用户确认 |
| **审计日志**(0.12.0 `ai_tool_audit`) | 对外调用审计(扩 `ai_tool_audit` 或新建 `mcp_audit` 表) |

### 5.3 传输模式

**调研 #17**(0.13 启动前定案):
- **stdio 模式**:外部 client 拉起 Blink 子进程,走 stdin/stdout JSON-RPC(最简单,与 MCP client 对称)
- **HTTP/SSE 模式**:Blink 起一个本地 HTTP server,外部 client 连接(更灵活,支持多 client)
- **建议**:0.13.3 先做 stdio 模式(与 MCP client 对称,实现最简),HTTP 模式推后续

### 5.4 能力暴露策略

不是所有 Capability / Action 都适合暴露给外部:

| 能力 | 暴露? | 理由 |
|---|---|---|
| `capture_screen` / `crop_image` | ✅ | 截图能力是 Blink 特色 |
| `read_clipboard` / `write_clipboard` | ✅(sensitive) | 剪贴板读写,sensitive 需授权 |
| `search_apps` | ✅ | 应用搜索是 Blink 特色 |
| `search_files` | ✅ | 文件搜索 |
| `search_knowledge_base` | ⚠️ 可选 | 暴露知识库给外部(0.13.1 后) |
| `search_clipboard_history` | ⚠️ sensitive | 剪贴板历史含隐私,sensitive 需授权 |
| 内置 Action(shutdown / restart) | ❌ | 系统级操作不暴露 |

**暴露清单**:用户在设置页「MCP server」tab 勾选要暴露的能力。

### 5.5 授权机制

- **sensitive capability**:外部调用时,Blink 弹确认卡片(与主窗口 AI 调 dangerous action 一致),用户确认后执行
- **non-sensitive capability**:直接执行,走审计日志

### 5.6 审计

对外调用走审计日志(AI 库):
- 复用 `ai_tool_audit` 表(加 `caller` 字段区分 `internal` / `mcp_external`)
- 或新建 `mcp_audit` 表(独立审计,与 AI tool 审计分离)
- **建议**:复用 `ai_tool_audit`,加 `caller` 字段,避免表爆炸

### 5.7 设置页

设置页「MCP server」tab(与「MCP client」tab 同组):
- 总开关(启用 MCP server)
- 传输模式选择(stdio / HTTP)
- 暴露能力清单(Checkbox 列表,带 sensitive 标记)
- 审计日志查看(最近 N 条对外调用)

### 5.8 0.13.3 验收

```
 CapabilitySchema::to_mcp_tool() 正向投影实现 + 单测
 设置页「MCP server」tab,可勾选暴露的能力
 stdio 模式启动,外部 MCP client 可拉到 Blink 的 tool 列表
```

## 六、0.13.4 Skill 化(CLI 探索 → AI 生成 skill)

### 6.1 定位

Skill = 「动态生成的 Capability」。用户指定一个 CLI 工具(如 `git` / `ffmpeg` / `magick`),Blink 跑 `--help` 让 AI 生成 skill 定义(CapabilitySchema + 执行逻辑),进对话窗口 tool 池。

### 6.2 前置条件:PoC 验证

**启动条件**:先做 PoC——用真实 CLI 跑 `--help` → AI 生成 skill 的完整流程,看产物质量。

PoC 要回答的问题:
1. AI 从 `--help` 输出生成的 CapabilitySchema 质量如何?(参数覆盖 / 描述准确度)
2. 生成的 skill 执行时参数注入是否正确?
3. 用户需要多少手动修正?
4. Skill 归属:Action(副作用)还是 Capability(能力)?

**若 PoC 不通过**:0.13.4 推迟,不强行落地。

### 6.3 Skill 归属决策(PoC 后定)

| 方案 | 含义 | 优缺点 |
|---|---|---|
| **Action** | Skill 是带副作用的 CLI 执行,走 Action trait | ✅ 与危险等级(danger_class)对齐;❌ Action 不进对话窗口 tool 池(主窗口路径) |
| **Capability** | Skill 是能力,走 Capability trait | ✅ 进对话窗口 tool 池;❌ Capability 当前无 danger_class |
| **混合** | Skill 走 Capability 但加 danger_class 标记 | ✅ 两全;❌ 需改 CapabilitySchema 加 danger_class(0.11 已有 sensitive,可复用) |

**建议**:混合方案——Skill 走 Capability(进对话窗口 tool 池),用 `sensitive` 字段标记危险 CLI(`rm` / `format` 等)。

### 6.4 Skill 生命周期

```
用户添加 CLI(git)
  ↓
Blink 跑 `git --help`(子进程,超时 10s)
  ↓
AI 从 --help 输出生成 CapabilitySchema(name / description / parameters)
  ↓
用户预览 + 编辑 schema(可选修正)
  ↓
保存 skill 定义(配置库 config 表,key=skill:{name})
  ↓
运行期:CapabilityRegistry::register(动态注册,0.12.0 已实现)
  ↓
进对话窗口 tool 池,AI 自主调用
```

### 6.5 Skill 存储

- Skill 定义存配置库 `config` 表(`skill:{name}` key,JSON 序列化)
- Skill 执行 = 子进程调 CLI + 参数注入(走 `std::process::Command`)
- 执行结果走 `CapabilityResult`(文本输出 → `Text`;二进制输出 → `Blob`)

### 6.6 设置页

设置页「Skill」tab:
- CLI 列表(名称 / CLI 路径 / 状态已生成/待生成)
- 添加 CLI 按钮(输入路径 → 跑 --help → AI 生成 → 预览)
- 编辑 skill schema(JSON 编辑器)
- 删除按钮
- 测试运行按钮(手动调一次看输出)

### 6.7 0.13.4 验收

```
 [PoC 前置]用 git/ffmpeg/magick 跑 --help → AI 生成 skill,产物质量可接受
 Skill 归属定案(Capability + sensitive 标记)
 设置页「Skill」tab,可添加 CLI 路径
 Blink 跑 --help → AI 生成 CapabilitySchema → 用户预览/编辑 → 保存
 运行期 CapabilityRegistry::register 动态注册 skill
 对话窗口 AI 可自主调 skill(子进程执行 CLI + 参数注入)
 执行结果走 CapabilityResult → to_rig_tool_result() 回流
 sensitive CLI 执行弹确认卡片
```
