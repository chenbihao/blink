# Blink 0.21 — Capability 唯一执行入口与统一功能目录

> **范围**：建立调用来源、运行时与出口策略类型墙；将旧 `execution::Action` 分流为 Capability / Interaction / descriptor；统一 Search、Chord、菜单、AI、CLI、MCP 的原子执行落点；提供功能目录和 AI/MCP 授权管理。
>
> **状态**：✅ 已完成（0.21.0–0.21.22 全部落地）。
>
> **动机**：本地入口与 AI 曾分属 Action/Capability 两套执行体系，metadata、真实执行目标、风险策略和设置状态可能漂移。本版把 Capability 收敛为唯一原子执行目标，持续人机流程留在 Interaction，入口只保留 descriptor/binding。
>
> **前置**：0.14 Capability 协议、0.17.8 AI 确认记忆、0.19 能力闭环、0.20.0 统一可见错误反馈。
>
> **原则**：架构与信任边界以 [`spec-architecture.md`](../specs/spec-architecture.md) 为准；代码级出口策略是硬上限，用户授权不得绕过风险确认；功能、Capability、binding id 分栏；本地 binding 保留各自真源；插件不得取得通用 Blink UI 控制权。

## 二、背景与动机

### 2.1 本版解决的问题

原子副作用曾同时存在 Action 与 Capability 两套实现和 Registry fallback；Search/Chord/Menu 的触发 metadata 与实际执行、风险、授权缺少统一身份投影；AI/MCP 需要独立授权真源、运行时门禁与热更新，设置页则需要一个面向用户的统一目录。

### 2.2 明确不是问题的

- Capability 负责一次原子调用；截图、取色、编辑、录音等持续会话继续属于 Interaction，不机械包装成 Capability。
- Copy/Preview 等展示短路径可留在 ResultAction；Open/Reveal 等业务副作用必须落到 Capability。
- Search、Chord、Context 和插件生命周期继续使用各自 binding/config 真源；功能目录只聚合与批量适配，不制造第二份总开关。
- CLI `capabilities` 保留 CapabilityRegistry 语义，无需改成 FeatureCatalog 展示投影。

## 三、核心设计与决策

### 3.1 Capability 是唯一原子执行目标（已定）

所有原子副作用最终经 `CapabilityRegistry::invoke`。Search/Chord/Menu 只保存 descriptor/binding 和 target；Interaction 状态只存在于所属领域。旧 `src/domain/execution/`、ActionRegistry 和双 fallback 已删除。

### 3.2 Policy 与运行时是 invoke-time 类型墙（已定）

`CapabilityPolicy` 是 origin、runtime、danger、sensitive、AI/MCP 默认与确认策略的唯一真源。调用者必须携带真实 `InvocationOrigin` 和 `RuntimeCapabilities`；Registry 在实际 invoke 前检查，UI 隐藏和 tool list 过滤仅是前置投影。GUI 能力只获得语义化 `SurfacePort`，插件能力永远拿不到该端口。

### 3.3 功能、Capability、binding 身份分栏（已定）

一个 Feature 可以聚合一个 Capability target 和多个本地 binding。功能目录分别展示 `feature_id`、`capability_id`、`binding_id`；本地列投影 binding 状态，AI/MCP 列投影 Capability 授权状态。旧 Chord `screenshot` 配置键作为 migration alias 保留，不与 headless `screenshot` Capability 混淆。

### 3.4 AI 与 MCP 授权独立（0.21.10 修订）

- AI 首次缺少配置时生成推荐 allowlist：普通 Safe（含 sensitive）默认进入 tool 池，Dangerous、local-only、诊断采集/恢复默认关闭；sensitive 调用仍需确认。生成后以持久化集合为真源，新增能力不自动加入老用户配置。
- MCP 的 `exposed_capabilities` 是独立真源，list-time 与 call-time 都复核 policy。Dangerous、Forbidden 和不允许 `Mcp` origin 的能力不可由配置绕过。
- **0.21.10 策略翻转**：MCP 不再“一律默认关”。首次没有种子记录时，静默持久化“允许 MCP 来源、非 Dangerous、非 sensitive、非 Forbidden”的安全能力；写入 `exposure_seeded=true` 后不再自动补新能力，用户清空列表也不会重生成。

### 3.5 功能目录是真源投影，不复制策略（已定）

FeatureCatalog 聚合 builtin descriptor、Chord binding、builtin/plugin Capability，并投影 schema、policy、availability 与 AI/MCP 真源。未知或已移除 id 保留为可诊断残留。目录页是 AI/MCP 授权的唯一完整管理入口；MCP Server 页只保留状态、Endpoint、暴露摘要和深链。

### 3.6 关键纠偏与维护约定

- 0.21.6 首版曾按臆造的 IPC 字段路径渲染，三出口状态和组级操作不可用；0.21.8 已按 `capability_projection`、`bindings` 和真实枚举契约重做。后续不得恢复顶层假字段。
- Context 门禁动作的关键词不能单独唤起；目录显示环境触发条件并沿用 action 级开关，不制造 ContextBinding 第二开关。
- 新增内置 Capability 时必须同步补 `CAPABILITY_TITLES` 的中英文短名；schema 长句只进入 description，未收录 id 才回退人类化。

## 四、复用与范围边界

### 4.1 已复用基础设施

| 基础设施 | 本版用途 |
|---|---|
| `CapabilityRegistry` / `CapabilityPolicy` | 唯一调用目标与代码级门禁 |
| `ConfigStore<T>` / `blink://config-changed` | AI/MCP 授权持久化、热更新和目录刷新 |
| Search/Chord/Context DisableConfig | 本地 binding 真源与批量 adapter |
| AI Agent cache fingerprint | 撤销授权后使旧 Agent cache 失效 |
| MCP ExposureSnapshot | 暴露集合排序、list/call 双门禁和热更新 |
| 前端 CSS token / Lucide sprite / 通用 switch、button | 目录矩阵、风险提示和链接按钮 |

### 4.2 不进入 0.21 的项

| 项 | 理由 |
|---|---|
| MCP Dangerous 逐次确认协议 | 本版代码级禁止；未来需独立 session/确认通道设计 |
| 任意插件控制 Blink 窗口或事件 | 违反最小权限与信任边界 |
| 统一所有本地 binding 为一个总开关 | 会丢失 Search/Chord/Context 各自语义 |
| 巨型 `system_operation` / `open` Capability | 会损失单项授权、确认和审计粒度 |
| descriptor 运行时动态包装为 AI tool | AI tool 只能来自代码允许且用户授权的 Capability |

### 5.16 0.21.15 — 首唤起 chord 输入法吞键修复 ✅

启动后首次唤起主窗口时按住 Alt 按 chord 键会落进输入法、不触发 chord；第二次唤起正常。根因：首唤起时 tao/SetForegroundWindow 注入合成 Alt-up，把 `GetAsyncKeyState` 异步键状态表刷成 up，每个非修饰键 keydown 前的物理快照 reconciliation 据此误清 hook 确认的真实 `Down`，chord 会话退出（与 0.19.17 同根因：注入 Alt 干扰真实 Alt）。修复：`apply_physical_snapshot` 物理 Up 只清 `InjectedDown`/`InferredDown`、不清真实 `Down`（只能由真实 keyup / Raw up 清除）；前端补 chord 配置启动预热与 SHOWN 条件清理 readOnly 防御。补 2 条回归测试。

### 5.17 0.21.16 — AI 对话配置优化与思考开关适配 ✅

rig 0.39 → 0.42 升级：Agent runtime 迁到 `rig-agent` crate（`Agent` 不再泛型、消费 `MultiTurnStreamItem`），`tool_result` 回流携带真实 `tool_name`（Gemini/Anthropic 依赖 name 配对，空串会 400）。对话闭环优化：Persistent 模式「发出即保存」（预写 user 消息 + 流式实况落库节流 + 非正常结束补 flush）、入参/结束/完整输入输出日志闭环、AI HTTP 请求/响应体日志开关（`LoggingHttpClient` 注入四协议）。思考开关适配：`thinking_request_patch` 收敛各供应商 thinking 字段格式（DeepSeek `thinking.type` / OpenAI 兼容 `reasoning_effort` / Anthropic `budget_tokens` / Ollama `think` / Gemini 未接返回 None）；主窗口默认关思考、对话窗口开关显式控制；**不按开关隐藏思考块**——开关失效时模型仍思考能及时暴露。

### 5.18 0.21.17 — 思考强度等级控件与统一 token 预算 ✅

#### 5.18.1 统一 token 预算 ✅

### 5.22 0.21.21 — 上下文容量链路修复 ✅

**问题链路**（0.21.19 收尾后审查发现）：`compute_context_status` 的容量上限读全局 `MemoryConfig.context_limit`，而该值只在 `ensure_provider` Agent 缓存**未命中**构造新 Agent 时从 `resolved.model.context_window` 注入——同一模型在设置页改 `context_window` 后容量冻结旧值（agent 缓存命中提前返回，注入被跳过）；多对话不同模型交错时全局单值后写者赢，容量展示与裁剪预算双双算错。这是"容量固定在第一次发送的值"的根因。此外每轮只在发送前重算，回复完成后无重算——环/popup 停在发送时刻快照，少算刚完成的 assistant 回复。

- **容量取值去全局化**：`compute_context_status` 直读 `resolved.model.context_window`（方法已持有 `resolved`），`MemoryConfig.context_limit` 降为 fallback；`ensure_provider` 的注入挪到缓存命中 early-return 之前（或随取值去全局化一并移除）。
- **模型弹窗补 `context_window` 输入与真实值获取定案**：新建模型现恒 null（`model-edit.js` 硬编码 `context_window: null`）→ 运行时静默回落 32K；实测工具定义 + preamble 固定开销 ~1W token，32K 下历史可用预算仅 ~17K，压缩/摘要对实际 128K+ 的模型触发过早一个数量级。真实值四条获取路径（业界通行组合 = 封闭集合硬编码 + 运行时拉取 + 公共目录，参照 Codex `MODEL_FAMILY` / LiteLLM）：① **复用 rig 0.42 `ModelListingClient::list_models`**——Gemini（`inputTokenLimit`）与 OpenRouter（API 自带 `context_length`）直拿真实值，省去自写 HTTP；Ollama 仍走 `/api/show`（rig 的 ollama listing 不带 context 字段）；② **内置精简模型目录**（从 LiteLLM `model_prices_and_context_window.json` 精选主流条目：OpenAI/Anthropic/Gemini/DeepSeek/GLM/Qwen/Moonshot/Kimi 等，构建期裁剪嵌入）——模型 id 前缀匹配 → 弹窗**预填推荐值，用户可改，不静默覆盖**（Codex 静默覆盖用户配置曾翻车，openai/codex#19185）；③ 官方 API 无元数据端点的手动输入，空值 placeholder 标注「未配置 = 按档位估算」；④ OpenAI 兼容端点 opportunistically 探测 `/v1/models` 的 `context_length` 字段（OpenRouter/vLLM 部分版本支持，失败静默）。**兜底按 base_url 归属分档（修订：自定义 base_url 32K → 128K）**：不取 64K/100K——被支配的中间值，对 128K+ 多数派仍过早压缩、对 ≤32K 小窗模型照样溢出，无独立保护对象；且量化后 32K 的保护带很窄（真实窗口 <30K 的模型在 32K 兜底下照样溢出：固定开销 ~1W + 历史预算 ~17K 已超其窗口，真正受保护的只有 30K–128K 窄带），「偏小良性偏大恶性」只对这条窄带成立。定案三档：① 官方封闭集合（Anthropic / Gemini 原生 kind；OpenAICompatible 且 `base_url` 为空 = OpenAI 官方）→ 128K；② OpenAICompatible **公网域名** base_url（GLM/DeepSeek/Moonshot/硅基流动/聚合网关——当前主力人群，当前代 ≥128K）→ 128K；③ `localhost`/`127.0.0.1`/私网 IP base_url（本地推理 llama.cpp/vLLM/LM Studio，窗口 4K–32K 居多）与 Ollama 原生 kind（拉取前）→ 32K。可选增强（P2）：收到 context 溢出 400 时按 0.5 降档 effective limit 重裁重试一次，硬失败变自愈。不做 provider 级默认窗口——OpenAI 兼容自定义端点的模型窗口差异极大，会制造「看似已配置实为猜测」的新模糊态。顺带收敛 `FALLBACK_CONTEXT_LIMIT`（token_budget.rs）与 `DEFAULT_CONTEXT_LIMIT`（memory.rs）两处同值 32768 常量为单一真源。
- **回复完成后重算推送**：Done 后（非流式中）重算一轮 context_status 并 emit，环/popup 不再滞后一轮；复用 `emit_summary_updated` 同一入口，注意与下一轮发送的竞态（`requests.status()` 守卫）。
