# Blink 0.21 — Capability 唯一执行入口与统一功能目录

> **范围**：建立调用来源、运行时与出口策略类型墙；将旧 `execution::Action` 分流为 Capability / Interaction / descriptor；统一 Search、Chord、菜单、AI、CLI、MCP 的原子执行落点；提供功能目录和 AI/MCP 授权管理，并收敛 AI 对话预算与记忆链路。
>
> **状态**：✅ 已完成。
>
> **动机**：Action/Capability 双执行体系曾导致 metadata、真实执行目标、风险策略和设置状态漂移；AI 对话的思考、上下文容量、裁剪与摘要口径也缺少单一真源。
>
> **前置**：0.14 Capability 协议、0.17.8 AI 确认记忆、0.19 能力闭环、0.20.0 统一可见错误反馈。
>
> **原则**：架构与信任边界以 [`spec-architecture.md`](../specs/spec-architecture.md) 为准；前后端工程约定分别以 [`spec-frontend.md`](../specs/spec-frontend.md) 与 [`spec-backend.md`](../specs/spec-backend.md) 为准。

## 二、背景与防误改澄清

0.21 把 Capability 定为唯一原子执行目标，使入口描述、风险策略、授权和真实执行不再分叉；功能目录只投影各域真源。后半程把 AI 对话的思考参数、上下文容量、预算、裁剪、摘要和记忆状态收敛为可解释链路。

以下边界是刻意设计，不应误改：

- Capability 负责一次原子调用；截图、取色、编辑、录音等持续会话属于 Interaction。
- Copy/Preview 等展示短路径可留在 ResultAction；Open/Reveal 等业务副作用必须落到 Capability。
- Search、Chord、Context 和插件生命周期保留各自 binding/config 真源；FeatureCatalog 不制造第二份总开关。
- CLI `capabilities` 保留 CapabilityRegistry 语义，不改成 FeatureCatalog 展示投影。

## 三、核心设计与决策

### 3.1 Capability 是唯一原子执行目标

所有原子副作用最终经 `CapabilityRegistry::invoke`。Search/Chord/Menu 只保存 descriptor、binding 和 target；Interaction 状态留在所属领域。旧 `src/domain/execution/`、ActionRegistry 和双 fallback 已删除。

### 3.2 Policy 与运行时在 invoke-time 强制执行

`CapabilityPolicy` 是 origin、runtime、danger、sensitive、AI/MCP 默认姿态与确认策略的真源。调用者携带真实 `InvocationOrigin` 和 `RuntimeCapabilities`，Registry 在实际执行前门禁；UI 隐藏和 tool list 过滤不是安全边界。GUI 能力只获得语义化 `SurfacePort`，插件能力不能取得通用 Blink UI 控制权。

### 3.3 Feature、Capability 与 binding 身份分栏

一个 Feature 可聚合一个 Capability target 和多个本地 binding。目录分别展示 `feature_id`、`capability_id`、`binding_id`；本地列投影 binding 状态，AI/MCP 列投影 Capability 授权。旧 Chord `screenshot` 配置键仅作为 migration alias 保留。

### 3.4 AI 与 MCP 授权相互独立

AI 首次生成推荐 allowlist，之后以持久化集合为真源；用户清空不会被重建，只有“恢复推荐”显式重置。MCP 首次种入允许 MCP 来源、非 Dangerous、非 sensitive、非 Forbidden 的安全集合，之后同样不自动补新。MCP list-time 与 call-time 都复核 policy，用户配置不能绕过代码级禁止。

### 3.5 功能目录只做真源投影

FeatureCatalog 聚合 builtin descriptor、Chord binding 与 builtin/plugin Capability，并投影 schema、policy、availability 和 AI/MCP 授权。未知或已移除 id 保留为可诊断残留。目录页是完整授权入口，MCP Server 页只保留运行状态、Endpoint、摘要和深链。

### 3.6 AI 对话预算与记忆链路单源

- per-model 配置决定 `reasoning_effort`、thinking style 与 `context_window`；默认态省略 effort 字段，避免伪默认和供应商 400。
- `TokenBudget` 统一计算 system、tools、history、pending、输出预留、安全余量与多模态成本；未知成本降低 confidence，不伪装精确。
- 裁剪、上下文状态和摘要共用预算口径；滚动摘要在回复 Done 后按水位触发，手动摘要异步执行并显式暴露 in-flight 状态。
- 摘要 Agent 不携带工具；跨对话召回由 `RecallScope` 明确控制；CJK 判定和前端 effort 档位各自只有一个实现。

### 3.7 关键维护知识

- 目录必须按 `capability_projection`、`bindings` 和真实枚举契约渲染，不得恢复顶层假字段。
- Context 门禁关键词不能单独唤起；目录沿用 action 级开关，不新增 ContextBinding 第二开关。
- 首唤起 chord 修复依赖真实 Raw/hook keyup 清除 `Down`；合成 Alt-up 或物理快照不得清除 hook 已确认的真实按下态。
- 新增内置 Capability 时同步补 `CAPABILITY_TITLES` 中英文短名；schema 长句只用于 description。

## 四、复用与范围边界

主要复用 `CapabilityRegistry` / `CapabilityPolicy`、`ConfigStore<T>` 与配置变更事件、各域 DisableConfig、AI Agent cache fingerprint、MCP ExposureSnapshot，以及前端既有 token、Lucide sprite 和通用控件。

未进入 0.21：MCP Dangerous 逐次确认协议、任意插件控制 Blink UI、统一所有本地 binding 为总开关、巨型 `system_operation`/`open` Capability、descriptor 运行时动态包装为 AI tool。这些均会破坏最小权限、授权粒度或领域真源。

## 五、实现总结

0.21 前半程完成 Action 双轨迁移、FeatureCatalog 和 AI/MCP 三出口授权：原子副作用统一经 Registry，功能目录写回各域真源，目录和 MCP 页面按真实 IPC 契约收敛；随后完成授权种子、参数协议、identity、DomainEnv 拆分和 infra 反向依赖清理。

后半程完成 AI 对话链路：Rig runtime 升级，思考开关与强度按模型适配，TokenBudget 贯穿工具、裁剪与容量展示，FTS 支持 CJK 召回，滚动摘要和手动压缩形成闭环，上下文容量改为 per-model 并支持模型目录与供应商探测。最终拆分 ChatService 和前端选择器，补齐工具来源、记忆健康度、异步压缩状态与静态 lint 护栏。

0.21.22 的两批工作已合并：模型/工具来源和思考逃生口，与追加完成的 effort 透传、工具统计同源、Ollama 并发拉取、摘要前缀常量化及 CSS fallback 基线，统一归档为一个里程碑。

## 六、验收结论

- 原子副作用唯一经 `CapabilityRegistry`；invoke-time origin/runtime/policy 门禁生效，授权不能绕过代码级禁止。
- Feature、Capability、binding 分栏并写回各自真源；目录和 MCP Server 不维护重复完整清单。
- per-model 思考、容量、预算、裁剪、摘要和记忆状态链路已闭环；结构拆分未改变既有 IPC/事件契约。
- 最终自动验证：`cargo test --bin blink` 1964 passed / 0 failed / 5 ignored；`cargo clippy --bin blink --all-targets -- -D warnings` 零告警；前端 35 个测试文件全绿；`cargo xtask lint` 通过。

真实模型摘要烟测需要用户凭据，保留为手动验证：长对话在 Done 后触发摘要并降低占用；“立即摘要”展示 loading 并在事件到达后解除；并发点击显示“摘要进行中，本轮仅裁剪”；关闭摘要后“立即裁剪”同步返回。
