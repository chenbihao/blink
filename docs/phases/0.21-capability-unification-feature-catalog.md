# Blink 0.21 — Capability 唯一执行入口与统一功能目录（Execution Unification & Feature Catalog）

> **范围**：建立调用来源、运行时要求与出口策略类型墙；把旧 `execution::Action` 全量分流为 Capability / Interaction / descriptor；统一 Search、Chord、菜单、AI、CLI、MCP 的原子执行落点；提供面向用户的功能目录和独立 AI/MCP 授权管理；最终删除 Action 执行链路与双 Registry fallback。
>
> **状态**：🔧 进行中（0.21.0 已完成、0.21.1 已完成、0.21.2 已完成、0.21.3 已完成）。
>
> **动机**：0.14 已保证 AI 只经 Capability，但本地搜索和 Chord 仍保留 Action 体系，造成入口 metadata、真实执行目标、危险策略和设置页状态可能漂移。0.21 完成物理收敛：Capability 是唯一原子执行入口，持续人机流程留在所属 Interaction，入口只保存 descriptor/binding。
>
> **前置**：0.14（Capability 协议与投影）、0.17.8（AI 确认记忆）、0.19（便签/pin/ImageStash 能力闭环）、0.20.0（统一可见错误反馈）。不依赖 0.20 的剪贴板、截图或颜色后续子版本。
>
> **原则**：每个子版本保持编译和现有入口可用；先建立策略类型墙再迁业务；原子能力不合并成巨型 dispatcher；功能/Capability/binding id 分栏；代码级出口策略是硬上限；用户授权不能绕过风险确认；MCP 首版禁止 Dangerous；插件不得取得通用 Blink UI 控制权；完成迁移前不得删除旧链路。

## 二、当前基线与问题

### 2.1 当前物理状态

- `Capability` 仍复用 `execution::DangerClass`。
- `InvokeContext` 只有 `env + deadline`，不能表达调用来源和 GUI/headless 运行时。
- `CapabilityError` 仍包含 `ExecError` 转换。
- `ActionRegistry` 注册 13 个内置 Action。
- `ChordRegistry` 注册 6 个同时实现 `Action` 的 ChordAction。
- `BuiltinEngine::ACTIONS`（16 条：13 无参 action id + 3 参数化 Capability id）同时承担关键词/Context metadata 与旧 action id 映射。
- `run_builtin_action` 存在 ActionRegistry/CapabilityRegistry fallback。
- AI 构建时可以从 Registry 装配全量 Capability，缺少用户单项 allowlist。
- MCP 已有 `exposed_capabilities` 和 list/call 双门禁，应保留为外部授权真源。

### 2.2 目标边界

| 概念 | 唯一职责 | 不负责 |
|---|---|---|
| Capability | 稳定 id、有限参数、明确结果的一次原子调用 | 持续等待用户拖选/输入 |
| Interaction | 截图、取色、编辑、录音等持续会话 | 第二套通用原子执行 Registry |
| Binding descriptor | Search/Chord/Menu 的触发、按键、呈现、target | 业务执行与风险真源 |
| ResultAction | Copy/Preview 等展示短路径，或 Capability 参数绑定 | 重复实现 Open/Reveal 等副作用 |
| FeatureCatalog | 面向用户聚合身份、标题、分组、来源、target 和状态投影 | 复制 Capability schema/风险策略 |

### 2.3 完成定义

只有同时满足以下条件才算完成：

1. 所有原子副作用最终只调用 `CapabilityRegistry::invoke`。
2. Interaction 状态只存在于所属领域服务。
3. Search/Chord/Menu 不实现重复业务逻辑。
4. AI/MCP/local 在 invoke-time 都经过来源和策略门禁。
5. `src/domain/execution/` 旧 Action 类型和双 fallback 删除。

## 三、核心类型与安全决策

### 3.1 调用来源与运行时能力（已定）

```rust
pub enum InvocationOrigin {
    LocalSurface,
    LocalCommand,
    LocalAi,
    Cli,
    Mcp,
}

/// 组合式运行时要求（bitflags 风格）——Gui 与 MainProcess 非互斥
pub struct RuntimeRequirement(u8);

impl RuntimeRequirement {
    pub const NONE: Self = Self(0);            // 无环境依赖
    pub const MAIN_PROCESS: Self = Self(1);    // 需 Blink 主进程
    pub const GUI_SURFACE: Self = Self(2);     // 需 SurfacePort（蕴含 MAIN_PROCESS）
    pub const DESKTOP_SESSION: Self = Self(4); // 需交互桌面会话
}

pub struct RuntimeCapabilities<'a> {
    pub surface: Option<&'a dyn SurfacePort>,
}

pub struct InvokeContext<'a> {
    pub env: &'a dyn CapabilityEnv,
    pub origin: InvocationOrigin,
    pub runtime: RuntimeCapabilities<'a>,
    pub deadline: Option<Instant>,
}
```

- `LocalSurface`：搜索、Chord、菜单等用户直接入口。
- `LocalCommand`：Tauri command 的兼容/Interaction 内部编排。
- `LocalAi`：主窗口 AI 和独立对话窗口，确认粒度仍按现有模式区分。
- `Cli`：无 GUI 默认环境。
- `Mcp`：外部 MCP server 调用，即使 server 运行在主进程也不能伪装成本地用户入口。

`RuntimeRequirement` 语义（修订定案：组合 bits，非互斥 enum）：

| bit | 含义 | 典型 Capability | 运行时缺该 bit |
|---|---|---|---|
| `NONE` | 纯数据/计算，无环境依赖 | `search_apps`、`read_text_file` | 任何环境可执行 |
| `MAIN_PROCESS` | 需主进程服务 wiring（DB/事件桥/状态） | `update_setting`、`update_sticky` | CLI 进程/独立 MCP server 返回 Unsupported |
| `GUI_SURFACE` | 需 SurfacePort（打开/切换窗口） | `open_settings`、`create_sticky` | 无 GUI runtime 返回 Unsupported |
| `DESKTOP_SESSION` | 需交互桌面会话（截图、Shell 打开） | `screenshot`、`open_url` | 无头/服务会话返回 Unsupported |

- 本质：Capability 对运行基础设施的**静态声明**，让 CLI、MCP、AI、本地入口在执行前得到一致、可恢复的"不支持"结果，而不是运行到 getter panic 或窗口调用失败。
- `GUI_SURFACE` 蕴含 `MAIN_PROCESS`；可按位组合（如 `DESKTOP_SESSION | MAIN_PROCESS`）。invoke 前比较 `InvokeContext.runtime` 实际可用集合，缺任一 bit 即返回结构化 `Unsupported`，禁止 panic。

### 3.2 CapabilityPolicy 是静态硬上限（已定）

```rust
pub struct CapabilityPolicy {
    pub allowed_origins: OriginSet,
    pub runtime_requirement: RuntimeRequirement,
    pub danger: DangerClass,
    pub sensitive: bool,
    pub ai_default: AiDefault,
    pub mcp_default: McpDefault,
    pub confirmation: ConfirmationPolicy,
}
```

- `Capability::policy()` 是风险、出口和运行时要求的唯一真源。
- `CapabilitySchema.sensitive` 兼容期从 policy 投影；完成后不得保存第二份可漂移值。
- Registry 在实际 invoke 前检查 origin、runtime 和用户授权；UI 隐藏/tool list 过滤只是第一层。
- `DangerClass` 从 `execution` 迁到 capability policy/trust 模块，AI 确认与审计消费同一类型。
- `ConfirmationPolicy` 复用 0.17.8 确认记忆存储，key 为 capability_id，不做宽泛旧 key 迁移；清除确认记忆时数据库与 session cache 同时失效。

### 3.3 SurfacePort 最小权限（已定）

GUI Capability 只获得语义化端口，例如：

```rust
trait SurfacePort {
    fn open_settings(&self) -> Result<(), SurfaceError>;
    fn open_sticky_manager(&self) -> Result<(), SurfaceError>;
    fn open_chat(&self, prefill: Option<&str>) -> Result<(), SurfaceError>;
    fn open_clipboard_mode(&self) -> Result<(), SurfaceError>;
    fn start_region_capture(&self) -> Result<(), SurfaceError>;
    fn start_image_editor(&self, source: EditorSourceRef) -> Result<(), SurfaceError>;
    fn start_content_editor(&self, request: ContentEditorRequest) -> Result<(), SurfaceError>;
}
```

禁止向所有 Capability 暴露 `emit(event)`、任意 window label、完整 `DomainEnv` 或 Tauri handle。插件 Capability 永远拿不到 SurfacePort。

### 3.4 AI 推荐 allowlist（已定）

首次升级且不存在 AI 单项配置时，生成并持久化“推荐” allowlist：

- 代码允许 `LocalAi` 且 `DangerClass::Safe` 的普通生产能力默认开启。
- Safe + sensitive 的普通读取能力也默认开启，但调用时仍走现有 sensitive 确认；“允许进入 tool 池”不等于免确认。
- Dangerous、仅本地、诊断信息采集和诊断恢复类默认关闭；诊断类是上述 Safe 默认规则的显式例外。
- 用户修改后以持久化的 capability id 集合为真源；未来新增 Capability 不自动进入已有用户的 allowlist，需显式启用。
- 纯对话模式仍为空 tool 池。

配置：

```json
{
  "schema_version": 1,
  "profile": "recommended",
  "enabled_capabilities": ["..."]
}
```

`profile` 只记录初始化来源，不在每次启动重新套默认；一旦持久化，后续只读 `enabled_capabilities`。

存储与可见性（已定）：

- 落点 `blink_config.db` KV 分片，key `ai.capability_access`，走 `ConfigStore<T>` + `blink://config-changed` 广播（前端按 key 订阅，与现有分片一致）。
- 首次生成推荐集合**不做用户提示**（当前用户量少，静默生成）；设置页功能目录可见最终授权状态。

### 3.5 MCP 首版禁止 Dangerous（已定）

- `McpServerModeConfig.exposed_capabilities` 继续是 MCP 单 Capability 授权真源，默认空。
- 代码级不允许 `InvocationOrigin::Mcp` 调用 Dangerous Capability；设置 UI 显示不可用 `—`，不能被配置强行打开。
- Safe + sensitive 可由用户显式暴露；显式加入 MCP allowlist 即该出口授权，仍记录审计，但 0.21 不设计逐次 GUI 确认。
- GUI/attention-changing Capability 默认不允许 MCP；若未来开放，需单独决策，不能仅因 server 运行在主进程就获得 GUI 权限。

### 3.6 功能、能力、binding 身份分栏（已定）

```rust
FeatureId("blink.region_capture")
CapabilityId("start_region_capture")
BindingId("chord.screenshot")
```

- 旧 chord 配置键 `screenshot` 作为 binding migration alias 保留，不与既有 headless `screenshot` Capability 冲突。
- 一个 Feature 可包含一个 Capability target 和多个 local bindings。
- 本地列展示 binding 聚合状态；AI/MCP 列展示 Capability id 授权状态。
- FeatureCatalog 不假设三类 id 同名。

### 3.7 本地开关保留各 binding 真源（已定）

为避免统一 UI 反而破坏入口语义，0.21 不强行把搜索禁用、Chord 键位、Context binding、插件生命周期写进一个新总开关：

- 搜索内置动作继续迁移并保留原 disabled id 的兼容存储。
- Chord enabled/key 继续由 chord config 管理。
- Context binding 继续按 binding key 管理。
- 插件 enabled 继续由插件页管理。
- 功能目录的“本地”状态是这些 binding 的聚合投影；组/行级操作调用各 binding store 的批量 adapter。
- 部分启用显示三态，不制造覆盖上游插件生命周期的第二份总开关。
- 功能目录可直接启停本地 binding（写回各 binding store）；修改 Chord 键位**跳转 Chord 设置页**，目录内不改键。binding store 仍是唯一真源。

### 4.3 SearchAction / ItemAction

| 当前变体 | 目标 |
|---|---|
| `SearchAction::Open` | `InvokeCapability { open_path/open_url, args }` |
| `SearchAction::Copy` | 保留纯 ResultAction Copy |
| `SearchAction::LazyCopy` | 保留受控展示短路径，或绑定 `read_*` 后再 Copy；不得进入 AI tool |
| `SearchAction::RunAction` | 改为显式 Capability/Interaction target，不再 action id fallback |
| `ItemAction::OpenFile/OpenUrl/Reveal` | 逐步投影为 `Invoke { capability_id, args }` |
| `ItemAction::Copy/Preview` | 保留展示层专用变体 |

兼容 wire 枚举名可以暂留一版，但后端执行必须落到 Capability，禁止复制 Open/Reveal 业务实现。

`BuiltinEngine::ACTIONS` 实为 **16 条**：13 条无参旧 action id + 3 条参数化 Capability id（`open_url`/`open_path`/`reveal_in_explorer`，现走 `run_builtin_action` 的 Capability fallback）。0.21.3 拆表时：13 条按 §4.1 迁移后 descriptor 指向新 capability id；3 条参数化项保留参数化 descriptor，target 直接为既有 Capability（`InvokeCapability { id, args }`），不再经 fallback。

`ActionOutcome` → `CapabilityResult` 兼容桥映射（0.21.1）：

| ActionOutcome | 映射 |
|---|---|
| `Copy { text, hit_id }` | `Done { summary: "已复制" }`；hit_id 频率回写由兼容层继续调 `record_clipboard_hit` |
| `Open { path }` | `Done { summary }` |
| `Emit { event, payload }` | GUI starter Capability 返回 `Done("已启动、等待用户")`；兼容桥负责原 emit 副作用 |
| `Nop` | `Done { summary: "" }` |

### 4.4 不进入 0.21

| 项 | 理由 |
|---|---|
| MCP Dangerous 逐次确认协议 | 首版代码级禁止，未来有真实需求再设计 session/确认通道 |
| 任意插件控制 Blink 窗口/事件 | 违反最小权限和信任边界 |
| 把所有本地 binding 配置迁入单一总开关 | 会丢失 Search/Chord/Context 各自语义 |
| 巨型 `system_operation` / `open` Capability | 会损失单项授权、确认和审计粒度 |
| 运行时把 descriptor 动态包装为 AI tool | AI tool 只能来自代码允许且用户授权的 Capability |
| 重命名所有兼容 IPC/wire 枚举 | 可保留协议壳，但内部执行必须先收敛 |
| 把 `blink capabilities` CLI 输出改为 FeatureCatalog 投影 | CLI 保留 CapabilityRegistry 语义；但 `capabilities`/`run` 命令必须执行 CLI origin 与 runtime gate |
