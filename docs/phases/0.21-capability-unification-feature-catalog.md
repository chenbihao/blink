# Blink 0.21 — Capability 唯一执行入口与统一功能目录

> **范围**：建立调用来源、运行时与出口策略类型墙；将旧 `execution::Action` 分流为 Capability / Interaction / descriptor；统一 Search、Chord、菜单、AI、CLI、MCP 的原子执行落点；提供功能目录和 AI/MCP 授权管理。
>
> **状态**：🚧 进行中（0.21.0–0.21.18 已完成）。
>
> **动机**：本地入口与 AI 曾分属 Action/Capability 两套执行体系，metadata、真实执行目标、风险策略和设置状态可能漂移。本版把 Capability 收敛为唯一原子执行目标，持续人机流程留在 Interaction，入口只保留 descriptor/binding。
>
> **前置**：0.14 Capability 协议、0.17.8 AI 确认记忆、0.19 能力闭环、0.20.0 统一可见错误反馈。
>
> **原则**：架构与信任边界以 [`spec-architecture.md`](../specs/spec-architecture.md) 为准；代码级出口策略是硬上限，用户授权不得绕过风险确认；功能、Capability、binding id 分栏；本地 binding 保留各自真源；插件不得取得通用 Blink UI 控制权。

## 二、背景与动机

### 2.1 本版解决的问题

原子副作用曾同时存在 Action 与 Capability 两套实现和 Registry fallback；Search/Chord/Menu 的触发 metadata 与实际执行、风险、授权缺少统一身份投影；AI/MCP 需要独立授权真源、运行时门禁与热更新，设置页则需要一个面向用户的统一目录。

### 2.2 明确不是问题的

- Capability 负责一次原子调用；截图、取色、编辑、录音等持续会话继续属于 Interaction，不机械包装成 Capability。
- Copy/Preview 等展示短路径可留在 ResultAction；Open/Reveal 等业务副作用必须落到 Capability。
- Search、Chord、Context 和插件生命周期继续使用各自 binding/config 真源；功能目录只聚合与批量适配，不制造第二份总开关。
- CLI `capabilities` 保留 CapabilityRegistry 语义，无需改成 FeatureCatalog 展示投影。

## 三、核心设计与决策

### 3.1 Capability 是唯一原子执行目标（已定）

所有原子副作用最终经 `CapabilityRegistry::invoke`。Search/Chord/Menu 只保存 descriptor/binding 和 target；Interaction 状态只存在于所属领域。旧 `src/domain/execution/`、ActionRegistry 和双 fallback 已删除。

### 3.2 Policy 与运行时是 invoke-time 类型墙（已定）

`CapabilityPolicy` 是 origin、runtime、danger、sensitive、AI/MCP 默认与确认策略的唯一真源。调用者必须携带真实 `InvocationOrigin` 和 `RuntimeCapabilities`；Registry 在实际 invoke 前检查，UI 隐藏和 tool list 过滤仅是前置投影。GUI 能力只获得语义化 `SurfacePort`，插件能力永远拿不到该端口。

### 3.3 功能、Capability、binding 身份分栏（已定）

一个 Feature 可以聚合一个 Capability target 和多个本地 binding。功能目录分别展示 `feature_id`、`capability_id`、`binding_id`；本地列投影 binding 状态，AI/MCP 列投影 Capability 授权状态。旧 Chord `screenshot` 配置键作为 migration alias 保留，不与 headless `screenshot` Capability 混淆。

### 3.4 AI 与 MCP 授权独立（0.21.10 修订）

- AI 首次缺少配置时生成推荐 allowlist：普通 Safe（含 sensitive）默认进入 tool 池，Dangerous、local-only、诊断采集/恢复默认关闭；sensitive 调用仍需确认。生成后以持久化集合为真源，新增能力不自动加入老用户配置。
- MCP 的 `exposed_capabilities` 是独立真源，list-time 与 call-time 都复核 policy。Dangerous、Forbidden 和不允许 `Mcp` origin 的能力不可由配置绕过。
- **0.21.10 策略翻转**：MCP 不再“一律默认关”。首次没有种子记录时，静默持久化“允许 MCP 来源、非 Dangerous、非 sensitive、非 Forbidden”的安全能力；写入 `exposure_seeded=true` 后不再自动补新能力，用户清空列表也不会重生成。

### 3.5 功能目录是真源投影，不复制策略（已定）

FeatureCatalog 聚合 builtin descriptor、Chord binding、builtin/plugin Capability，并投影 schema、policy、availability 与 AI/MCP 真源。未知或已移除 id 保留为可诊断残留。目录页是 AI/MCP 授权的唯一完整管理入口；MCP Server 页只保留状态、Endpoint、暴露摘要和深链。

### 3.6 关键纠偏与维护约定

- 0.21.6 首版曾按臆造的 IPC 字段路径渲染，三出口状态和组级操作不可用；0.21.8 已按 `capability_projection`、`bindings` 和真实枚举契约重做。后续不得恢复顶层假字段。
- Context 门禁动作的关键词不能单独唤起；目录显示环境触发条件并沿用 action 级开关，不制造 ContextBinding 第二开关。
- 新增内置 Capability 时必须同步补 `CAPABILITY_TITLES` 的中英文短名；schema 长句只进入 description，未收录 id 才回退人类化。

## 四、复用与范围边界

### 4.1 已复用基础设施

| 基础设施 | 本版用途 |
|---|---|
| `CapabilityRegistry` / `CapabilityPolicy` | 唯一调用目标与代码级门禁 |
| `ConfigStore<T>` / `blink://config-changed` | AI/MCP 授权持久化、热更新和目录刷新 |
| Search/Chord/Context DisableConfig | 本地 binding 真源与批量 adapter |
| AI Agent cache fingerprint | 撤销授权后使旧 Agent cache 失效 |
| MCP ExposureSnapshot | 暴露集合排序、list/call 双门禁和热更新 |
| 前端 CSS token / Lucide sprite / 通用 switch、button | 目录矩阵、风险提示和链接按钮 |

### 4.2 不进入 0.21 的项

| 项 | 理由 |
|---|---|
| MCP Dangerous 逐次确认协议 | 本版代码级禁止；未来需独立 session/确认通道设计 |
| 任意插件控制 Blink 窗口或事件 | 违反最小权限与信任边界 |
| 统一所有本地 binding 为一个总开关 | 会丢失 Search/Chord/Context 各自语义 |
| 巨型 `system_operation` / `open` Capability | 会损失单项授权、确认和审计粒度 |
| descriptor 运行时动态包装为 AI tool | AI tool 只能来自代码允许且用户授权的 Capability |

### 5.16 0.21.15 — 首唤起 chord 输入法吞键修复 ✅

启动后首次唤起主窗口时按住 Alt 按 chord 键会落进输入法、不触发 chord；第二次唤起正常。根因：首唤起时 tao/SetForegroundWindow 注入合成 Alt-up，把 `GetAsyncKeyState` 异步键状态表刷成 up，每个非修饰键 keydown 前的物理快照 reconciliation 据此误清 hook 确认的真实 `Down`，chord 会话退出（与 0.19.17 同根因：注入 Alt 干扰真实 Alt）。修复：`apply_physical_snapshot` 物理 Up 只清 `InjectedDown`/`InferredDown`、不清真实 `Down`（只能由真实 keyup / Raw up 清除）；前端补 chord 配置启动预热与 SHOWN 条件清理 readOnly 防御。补 2 条回归测试。

### 5.17 0.21.16 — AI 对话配置优化与思考开关适配 ✅

rig 0.39 → 0.42 升级：Agent runtime 迁到 `rig-agent` crate（`Agent` 不再泛型、消费 `MultiTurnStreamItem`），`tool_result` 回流携带真实 `tool_name`（Gemini/Anthropic 依赖 name 配对，空串会 400）。对话闭环优化：Persistent 模式「发出即保存」（预写 user 消息 + 流式实况落库节流 + 非正常结束补 flush）、入参/结束/完整输入输出日志闭环、AI HTTP 请求/响应体日志开关（`LoggingHttpClient` 注入四协议）。思考开关适配：`thinking_request_patch` 收敛各供应商 thinking 字段格式（DeepSeek `thinking.type` / OpenAI 兼容 `reasoning_effort` / Anthropic `budget_tokens` / Ollama `think` / Gemini 未接返回 None）；主窗口默认关思考、对话窗口开关显式控制；**不按开关隐藏思考块**——开关失效时模型仍思考能及时暴露。

### 5.18 0.21.17 — 思考强度等级控件与统一 token 预算 ✅

0.21.16 思考开关对 OpenAI 兼容硬编码 `reasoning_effort=high/none`，但该字段合法取值**按模型而异**（如只支持 `{xhigh, medium, low}` 的模型，`high` 和 `none` 都会 400）——开关设置不好直接毁掉整条请求。标准协议（OpenAI Chat Completions / Anthropic Messages）均无能力探测端点，现成映射表只有 OpenRouter `/models` 的 `reasoning.supported_efforts`。

核心决策（配置化优先 + 逃生口）：
- **per-model `reasoning_effort` 配置**（`ModelEntry` 新字段，`Option<String>`）：`Some("")` = 不发送（omit，用模型默认档，绝不出 400）、`Some("none")` = 显式关闭、`Some(level)` = 档位/自定义值原样发送、`None` = auto（退回旧二值行为）。
- **对话窗口思考控件升级为强度下拉**：`关闭思考 / 极低~最大 / 自定义输入`，遇到报错直接选档或手输供应商私有值，留空 = omit。`thinking_supports_effort` 判定控件形态——支持等级的模型（OpenAI 兼容非 DeepSeek）显示下拉，其余（DeepSeek/Anthropic/Ollama）退化原简单开关。
- **持久化**：新命令 `set_model_reasoning_effort` 复用 `set_config('ai_config')` 全链路（落库 + registry 热更新 + 缓存 + CONFIG_CHANGED）；设置页模型弹窗「调用参数」段联动同一字段。
- **范围边界**：400 错误自愈（解析错误里列出的支持档位自动降级）与 OpenRouter `/models` 元数据探测未纳入本版（rig 0.42 内置 OpenRouter model_listing 但丢弃 `reasoning.supported_efforts`，需自行补一次请求）。

验证：`cargo test --bin blink` 1795 passed / 0 failed；前端改动模块 node 语法检查通过。

#### 5.18.1 统一 token 预算 ✅

**动机与结论**：Rig 0.42 只提供响应后的统一 `Usage`，不提供发送前 tokenizer，Blink 需自建发送前预算；旧 `memory.rs` / `prompt.rs` 两套启发式只统计历史/前导/待发，遗漏工具定义、协议开销、输出预留与多模态成本。定案：domain 层唯一 `TokenBudget` / `TokenEstimator`（`src/domain/ai/token_budget.rs`），`memory` 裁剪、上下文状态、受 token 限制的文本读取（`read_text_file`）统一走同一估算入口。

**关键约定**：
- 预算分解 `history / system / pending / tools / protocol_overhead / multimodal / reserved_output / safety_margin`，并给出 `estimated_input`、`effective_input_limit`（= context − reserved − margin）、`remaining`、`usage_percent`、`confidence` 与 context limit 来源。
- 工具定义按实际送入 Rig 的 `ToolDefinition`/JSON Schema 投影计入，避免 UI 与真实 tool 池漂移；未知图片成本不得静默按 0 伪装成精确值，应降 `confidence` 用保守余量。
- 完整保留 Rig 0.42 的 usage 字段（`total / cached_input / cache_creation_input / tool_use_prompt / reasoning_tokens`）；零 usage 表示供应商未报告，不得当成真实零消耗。
- 用响应后真实 `input_tokens` 对同一 provider/model 的发送前估算做有界、可失效的平滑校准（`UsageCalibrator`）；校准只修正启发式误差，不覆盖工具、输出预留和安全余量的结构性预算。
- `context_window` 缺失时用 32K 保守 fallback，popup 明确区分 `Configured / Fallback` 来源并显示工具、输出预留与安全剩余，不把 fallback 呈现成真实规格。
- 首期不接 Provider count-tokens 网络请求，不在按键/发送热路径引入网络往返。

**验证**：纯函数测试覆盖下溢/除零、tool schema 单调、fallback 来源、usage_percent 饱和；`cargo test --bin blink` 全绿，前端 composer popup 测试通过。

**已知遗留**：压缩提示横条（"上下文窗口已使用 X%，旧消息将被自动压缩"）暂禁用，压缩逻辑待重新设计（见 `frontend/js/chat/components.js` `renderContextWarning`）。

### 5.19 0.21.18 — 上下文裁剪接入统一 token 预算（执行侧）✅

**动机**：0.21.17 只接了度量侧（`compute_context_status` → 前端占用指示器），执行侧 `load_inner` 仍拿裸 `context_limit` × trigger(0.8)/compress(0.7) 裁剪——system prompt、工具 schema、pending、输出预留、安全余量都不在裁剪预算内，小窗口模型 + 多 MCP 工具时 UI 显示准确但请求仍可能超窗 400。

**做法**：`MemoryConfig` 新增运行时字段 `history_budget`（`serde(skip)`，不持久化），每轮 prompt 由 `compute_context_status` 注入：先经 `compute_history_token_budget()` 预扣全部非历史开销（system + tools + pending + 输出预留 + 安全余量），再减召回块预留（`recall_top_k × 500` worst case，因 `<memory>` 块在裁剪之后插入、不受窗口预算约束）。`load_inner` 裁剪基准换为 fallback 链 `history_budget → context_limit → DEFAULT_CONTEXT_LIMIT`；`update_context_limit`（模型切换）同时失效旧预算，`apply_config`（设置页改配置）保值。时序保证：`compute_context_status` 在 `stream_prompt` 之前被 await，rig 的 memory load 发生在 `stream_prompt` 内部，注入先于消费。

**关键决策**：
- trigger/compress 比例值不变（0.8/0.7），只换基数——预算本身已含安全余量，0.8 是刻意双重缓冲；设置页 hint 已同步改为"占历史可用预算的比例"。
- `history_budget` 无下限 floor：预算为 0 时裁到空是正确行为（此时请求本会被工具挤爆），仅打 warn 让其可见。
- pending 在窗口内与预算侧**双算一致**（load 裁剪时消息含预写 user、预算也扣 pending），防预算偏松，不得"优化"成单算。
- `compress_context_now`（手动压缩按钮）是 `compute_context_status` 的第二调用方，其注入值少扣 system/pending（偏松）；正常流程每轮 prompt 会先重注紧预算再 load，仅"流式期间点击手动压缩"存在毫秒级竞态暴露，待加 active request 守卫。

**验证**：新增 3 测试（`history_budget` 优先于 `context_limit` 作为裁剪基准、模型切换后旧预算失效、`apply_config` 保值）；存量 memory 测试零改动通过（走 fallback 路径）；`cargo test --bin blink` 1846 passed / 0 failed / 5 ignored，`cargo check` 零警告。

**已知遗留**：`compress_context_now`（手动压缩）缺 active request 守卫，存在毫秒级注入竞态（见上"关键决策"末条）；FTS 中文召回失效已随 §5.19.1 修复。

#### 5.19.1 FTS 中文召回修复 ✅

**动机**：`build_fts_or_query` 按空白拆词做 FTS5 OR 检索，中文没有空格——整句变成一个长 phrase，trigram 下等价于"要求归档文本包含整句原样子串"，几乎永不命中，中文用户的"召回本对话较早内容"形同虚设。现有中文测试全绿是假阴性（查询用的都是恰为归档子串的短词组）。

**做法**：重写 `build_fts_or_query` 为逐字符扫描的 run 切分——ASCII/非 CJK 词保持原行为（≥3 字符、去内嵌引号）；CJK run 长度 3..=6 整段短语（子串匹配），>6 生成 3 字符滑窗（stride 1）OR 词项；词项去重、总量上限 32（防超长消息生成巨型 FTS 查询）。infra 层私有 `is_cjk_char` 与 domain `token_budget::is_cjk` 镜像（分层禁止跨层引用）。不改表结构/tokenizer/已归档数据。

**验证**：核心回归用例（长自然句查询召回含关键词的归档消息，旧实现下必失败）从红转绿；新增 8 测试覆盖混合中英/滑窗/短词过滤/引号清理/去重/上限；`cargo test --bin blink` 1854 passed / 0 failed / 5 ignored。

#### 5.19.2 记忆子系统收尾三件套 ✅

**A. 中断残留 live_turns 清理 + 手动压缩 active 守卫**：流式中断后 `live_turns` 残留上一轮行 id，下一轮 `persist_assistant_delta` 会 UPDATE 旧行——断点内容被新回合部分回复覆盖。修法：`persist_user_message` 开头清标记（断点行留 DB 供回溯，仅不复用 id），`clear` 对称清理。`compress_context_now` 加 active request 守卫（复用 `current_request_context()`），关闭流式期间手动压缩与 prompt 预算注入之间的毫秒级竞态窗口。

**B. Ephemeral 记忆 50 条上限**：主窗口临时对话记忆原先无界（代码注释自认"后续迭代加 sliding window"）。`append` 超限丢最旧并复用孤立 ToolResult 丢弃逻辑（与 Persistent 窗口语义一致）；promote 导出裁剪后窗口。

**C. System Prompt Token 展示改口径**：原 `get_system_prompt_info` 渲染 `routing_system_prompt`——意图路由器的 prompt，运行时调用方已随 0.17.6 AI lane 移除，属幽灵指标；工具集也不过 allowlist、不含 MCP。改为：聊天 preamble（`chat_system_prompt_with_skills` + Skill 阶段 1 摘要，经新增 `ChatService::skill_summaries()` 访问器）+ AI 授权 Capability 工具（插件 settings 注入后按 allowlist 过滤，与 `tool_adapter` 生产语义一致；policy 级过滤不复刻，估算偏保守方向），估算统一走 `token_budget`，返回 `system_tokens`/`tools_tokens` 分项供前端 meta 展示。`routing_system_prompt` 标 `#[allow(dead_code)]` 保留不删。hint 注明不含 MCP 工具。

**验证**：新增 3 测试（中断断点不被覆盖、Ephemeral 上限 + 孤立 ToolResult 丢弃）；`cargo test --bin blink` 1857 passed / 0 failed / 5 ignored；设置页手动烟测显示分项数值。

**明确不做**：双 load 合并（每轮 status + rig 各跑一遍 load 管线）——涉及请求热路径缓存失效语义，单独评估；上下文窗口展示跟随模型——hint 已写明主档口径，自洽不改。
