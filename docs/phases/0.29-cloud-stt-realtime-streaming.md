## 二、背景与动机

### 2.1 为什么做

云端模式的 `CloudSttEngine` 只累积样本、录音结束才一次性上传，说话期间无任何预览；即使流式开关打开也不走伪流式（伪流式引擎绑定本地 GGUF worker）。OpenAI 官方 Whisper HTTP 接口本身没有流式，官方流式走 Realtime WebSocket（`/v1/realtime?intent=transcription`）；用户自部署的 sensevoice-server 实现了同款协议且实测为真增量预览。

### 2.2 明确"不是问题"的（避免误改）

- **G2 预览重叠不是消费侧防护不足**。`voice.rs` 的三层防线（Draft 到达即按边界整条删除重叠段、Preview 整体替换后再按已见 Draft 最大边界过滤、同段定稿后迟到 delta 不复活）对段切换竞态是完备的；重叠根因在引擎侧的方言误判（§3.2）。
- **长语音不分段不是客户端没处理切段信号**。服务端切段时会发 `completed` 与新 item，客户端正确处理（新段重置预览、span 衔接）；分段是服务端行为，客户端无需"重新送入识别"。不分段的原因是服务端端点阈值写死（§3.6）。
- **TRACE 档记录转写正文不违规**。[后端 spec §3.2](../specs/spec-backend.md) 铁则 5 对用户内容留有"trace 级谨慎使用"例外（剪贴板先例）。压制 tungstenite 的理由是不受控的整帧 dump，不是"TRACE 不得记正文"（§3.5）。
- **SSE（`stream=true`）不是增量流式**。它是 Speaches 社区标准的整段事件流格式，SenseVoice 是非流式模型，收完整个文件才推理；流式价值只在 WS。

## 三、核心设计 / 决策

### 3.1 只做 WS 真流式，不可用时回退整段上传（已定）

**定案**：云端流式只走 Realtime WS；连接失败自动回退现有整段上传，用户无感。不做"VAD 切句 + 滚动窗口 HTTP 请求"的伪流式 transport。

**理由**：用户拍板。WS 是单连接真增量；伪流式 HTTP 对按次计费的端点请求量放大。

### 3.2 单方言：funasr 系累计 delta（已定，含实机踩坑）

**定案**：delta 一律按**累计替换**处理（每次 delta 是当前段的完整最新版，含尾部修正）；会话配置统一 funasr 风格 `session.update{turn_detection: server_vad}`。不做 OpenAI 官方方言分支。

**理由（踩坑）**：最初按 `kind == "openai"` 判定官方方言走**增量拼接**。但自部署服务配 `kind=openai` 很常见，而 funasr 服务无论 kind 都发累计 delta——拼接导致 G2 预览逐帧重复全文（用户实机反馈，其配置正是 `kind=openai` + 自部署地址）。且官方方言本就不可用：官方 Realtime pcm16 要求 24kHz，而客户端统一发 16kHz。半套适配只会产出错误拼接或变速音频，故整体删除；官方端点会拒绝该配置并回 error 事件，可见失败好于静默乱字。

### 3.3 原生 `StreamingSttPort` + port 内回退（已定，含踩坑）

**定案**：`CloudStreamingPort` 原生实现 `StreamingSttPort`，不走 `GgufStreamingAdapter`；回退也在 port 内原生实现（`CloudSttEngine` 做样本累积，终态发本 port 总线）。

**理由（踩坑）**：回退最初借道适配器——其事件发在适配器自己的总线、generation 也各自计数，结果不支持 WS 的端点（Groq/MiMo 都没有 `/realtime`）每次回退都**静默丢失整段识别结果**。另：WS 中途出错后 `finish_session` 若返回 Err，会触发 `voice.rs` 兜底再交付一次空文本——改为 Error 已是终态则返回 Ok、不再补 Final。

### 3.4 事件映射与总线复用

delta → Preview（PreviewDraft）/ Partial（Legacy），走 preview latest-slot；`completed` → Draft span / 带 confirmed 的 Partial；`finish` 发 commit 后有界等待（3s 预算 + `committed` 后 1s 宽限收静音尾），再按累计文本发 Final。item 切换重置段预览，span 音频范围按客户端已推样本计数衔接。事件投递复用 `streaming_port::EventBus`（reliable 队列 + preview latest-slot + generation 墙），与本地引擎同一套背压/去重语义。

`finish` 超时兜底的文本 = 已定稿累计 + 未定稿预览尾巴。**已知边界**：服务端积压时预览远未识别完，兜底会**丢失尾部内容**（§5.3 实测）；该风险在服务端 8s 分段后预期基本不触发（§3.6）。

### 3.5 日志分层：库帧 dump 恒压，正文由 blink 自身受控记录

**定案**：`tungstenite` / `tokio_tungstenite` 恒压 warn（并入 `logging.rs::parse_level` 的 transport_noise 组）；转写内容由 `realtime_ws` **仅在 TRACE 档**记录 delta 预览 / completed 定稿 / Final 最终正文，不含音频。

**理由**：库在 TRACE 下逐帧刷 poll/read/WouldBlock（每帧 6-10 行），并把完整帧 payload 以 hex + JSON 各 dump 一份，其中 base64 音频毫无诊断价值。正文对排查错字/断句/重复有价值，按 spec 的 trace 例外由 blink 自身结构化日志承载（与 AI 对话日志同模式）。

### 3.6 服务端调优：`--vad-maxseg` 是唯一有效的强制分段旋钮（已定，待回归）

**定案**：部署文件参数环境变量化，默认 `SV_VAD_MAXSEG=8000`（强制切段上限）、`SV_PARTIAL_MS=600`、`SV_THREADS=4`。

**理由**（基于 `sensevoice-server.cpp` 源码审查 + 真实语料实测）：

- **端点静音阈值写死，会话前 60 秒恒为 ~1850ms**。`recompute()` 按 `acc` 查表得静音阈值，而 `acc` 每处理满 6000 帧（60 秒）才累加一次，只会取 0/60000/120000…；前 60 秒 `acc=0` → 阈值 `2000-150=1850ms`，60 秒后骤降到 50ms。自然说话的句间停顿（300~900ms）达不到，所以中途基本不切段。`session.update` 里的 `silence_duration_ms` / `threshold` 服务端不消费（实测传入无效）。
- **partial 同步阻塞读循环**。每次预览对整个开放段重识别，且跑在连接自己的读循环线程上；段越长单次越慢，读循环被拖住 → append 积压 → TCP 反压 → commit 排在积压队尾。定稿耗时 ≈ 积压块数 × 单次 partial 耗时。
- 可调的启动参数只有 `--vad-maxseg`（默认 30000ms）、`--partial-ms`（默认 400）、`--vad-slot-ms`（默认 2000，空闲清理用）、`--threads`。段长有上界才能让单次 partial 耗时有上界，故 `--vad-maxseg` 是关键；8s 与本地引擎的切分窗口（soft 10s / hard 14s）同量级。

## 四、复用与范围边界

### 4.1 已有基础设施复用盘点

`StreamingSttPort` 契约与 `EventBus`（可见性放宽为 `pub(crate)`，新增 `set_preview` / `send_reliable` / `delivery_stats` / `capacity` 与 `EventStats::fresh`）；`CloudSttEngine`（回退累积器）与 `cloud::send_stt_request`；`SttConfig.streaming_mode`（复用现有字段，默认 Pseudo 即云端流式默认开，无 schema 迁移）；`logging.rs::parse_level` 的第三方噪音压制机制；`voice.rs` 的 `finalize_engine(Option)`（云端流式 engine 为 None 已兼容）。

### 4.2 不进 0.29.1 的项

| 项 | 理由 |
|---|---|
| OpenAI 官方 Realtime 方言 | 需 24kHz 重采样 + 增量 delta + `transcription_session` 事件的完整适配，且无官方端点可验证 |
| 伪流式 HTTP transport | 用户选定只做 WS（§3.1） |
| `finish` 超时后整段 HTTP 补救 | 实测同一 15.6s 音频 HTTP 整段仅 1.2s 且结果完整，可作为兜底；但多段会话需要精确的尾段起点（服务端 `speech_started.audio_start_ms` 是相对其内部缓冲的偏移，对齐有重复上屏风险）。待服务端调优回归后按数据决定 |
| reader 收发解耦 | `select!` 中 `send_text().await` 被反压阻塞时会连带停掉事件接收（预览停更）。服务端 8s 分段后预期不再反压，待回归确认 |
| 用服务端段偏移做精确 span 范围 | 当前按客户端样本计数近似，范围偏粗但文本不重叠 |

## 五、0.29.1 实施总结

### 5.1 引擎与接线

`crates/blink-domain-stt/src/realtime_ws.rs`：协议层纯函数（URL 推导、事件解析、消息构造、PCM16 转换）+ `SpanLedger`（段/累计文本状态）+ `CloudStreamingPort`。begin 连 WS（3s 超时，keyless 自部署可省 Bearer）；push 攒批（≥100ms 样本合并成一帧 append）；`warm_up` 恒 no-op。`stt::create_streaming_port` 成为 VoiceService 唯一引擎入口：Local = 现行为；Cloud + 流式开 = `CloudStreamingPort`；Cloud + 流式关 = 整段上传。`voice.rs` 引擎创建块收敛为单工厂调用，模式判断下沉 domain。

**其他踩坑**：Rust 2024 中 `gen` 是保留字；全局配置缓存在并行测试中会被别的用例改写，依赖它的测试须用 `init_cache` + `update_cache` 双设置（`init_cache` 是 OnceLock，并发下可能是 no-op）。

### 5.2 流式探测与设置页

`test_cloud_stt_streaming` command → 域层 `probe_streaming_support()`：WS 握手 + 会话配置后等首事件；SSE 用 250ms 静音 + `stream=true` 判 `text/event-stream` 与 `transcript.text` 事件。

设置页云端卡片：预设与协议两个并列下拉收敛为"预设决定协议"（协议下拉仅自定义预设露出）；补 mimo_plan 预设；修复回显 bug（`base_url=null` 用默认值时被误判为自定义，改按 effective base_url 匹配）；「流式识别」开关迁出本地高级卡成为跨模式字段；新增「流式能力测试」按钮。`voice-cloud-presets.js` 的默认 URL 表须与 Rust `cloud::default_base_url` 同步。

### 5.3 真实服务实测数据

服务：自部署 sensevoice-server（SenseVoiceSmall q8 + FSMN-VAD），调优前默认参数。

| 场景 | 结果 |
|---|---|
| WS 握手 | 6ms，`session.created` |
| 短语音（约 5s）松开 → 定稿 | 746ms |
| 合成双段（语音 + 2.5s 数字纯静音 + 语音） | 服务端自动切段，新段用新 item id，delta 为段内累计 |
| 15.6s 连续语音（TTS） | commit → 定稿 **26.5s**；3s 截断点丢失尾部 22 字；同音频 HTTP 整段 **1.2s** |
| 语料「多停顿」15.8s（停顿 480~1800ms 共 10 处） | 说话中途未切段；commit 后 8.3s 定稿，切成 2 段 |
| 语料「连续说话」25.9s | 推送被 TCP 反压拖到 52s 才推完；commit 后 30s 仍未定稿 |
| `silence_duration_ms=500` / `threshold=0.3` | 无效，切段位置与定稿耗时不变 |

**方法论教训**：合成的"数字纯静音"会触发切段，真实录音的停顿（有底噪）在默认参数下不会——服务端能力不能只用合成音频下结论。

### 5.4 部署文件

`docs/deploy/sensevoice-server/`：Dockerfile（启动参数环境变量化）、docker-compose.yml（model-init 导出模型、sensevoice 主服务、nginx Bearer 鉴权网关）、nginx 模板、README（部署步骤、端口、Blink 对接、参数表）。未放 `resources/`——该目录随二进制嵌入发布，不接纳部署配置。
