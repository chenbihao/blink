# Blink 0.17 - 增强与打磨（Enhancement & Polish）

> **范围**：修复 0.16 遗留存量问题（自启弹窗、截图双 loading、剪贴板清理与 DB VACUUM、chord 删除图片、AI 权限确认断链），建立窗口预热铁则与托盘增强，增强搜索与系统能力，调研并优化截图 OCR，深化 Markdown 渲染引擎并重设计主窗口 AI 展示形态以统一支撑编辑器、便签与 AI 对话返回，补齐首次启动引导与快捷键速查等产品体验基础设施。
>
> **状态**：🚧 进行中。
>
> **动机**：0.16 完成剪贴板增强、内容流转与桌面便签后，Blink 的"感知->编辑->常驻"链路已闭环。但实际使用中暴露出存量 bug、便签交互粗糙、AI 对话权限断链、OCR 准确度不足等问题。0.17 是从"能用"到"好用"的打磨阶段，不引入大架构变更，聚焦可靠性、交互完整性和体验闭环。
>
> **前置**：0.16（便签、编辑器、剪贴板图片、共享 Markdown）；0.15（截图重做、chord requires_input）；0.12（AI 对话窗口、PendingConfirms 权限闭环）。
>
> **原则**：不引入大架构变更；WYSIWYG 若立项需充分论证与 0.16 决策的冲突；窗口预热铁则完成后迁入 spec-frontend；调研类任务（OCR）先出结论再定实现方案；存量 bug 修复优先于新功能。

## 二、背景与动机

### 2.1 为什么 0.17 做这件事

0.16 将"感知->编辑->常驻"链路打通后，实际日常使用暴露出四类问题：

1. **可靠性存量债**：0.16 新增的图片剪贴板、便签、chord 删除等功能存在边界 bug；自启链路有命令行窗口泄漏；截图翻译 loading 竞态；AI 权限确认在主窗口断链。这些问题影响"按快捷键后立即可用"的核心承诺。
2. **交互不完整**：便签管理界面样式异常、操作交互混乱、空便签留存；编辑器 Markdown 渲染缺勾选块；主窗口 AI 回答塞进结果列表纯文本展示、无 Markdown 渲染。这些是 0.16 快速迭代留下的半成品。
3. **能力短板**：OCR 准确度不足（根因是未正确选中文语言，非 WinRT 能力不足，§3.9 已查实）；搜索缺少系统级快捷方式；更新提醒缺少变更内容展示。
4. **产品体验基础设施缺失**：新用户安装后无首次启动引导（不知道 Alt+Space 唤起）；应用内无快捷键速查；托盘菜单无"显示主窗口"项、无状态反馈；设置页 13 tab 未分组。这些是从 MVP 到完整产品的体验断裂点。

### 2.2 分组逻辑

0.17 的子版本按**内聚性**而非优先级排列：

- **第一组（零碎优化）**：问题修复、搜索增强、窗口预热+托盘、首次启动引导、设置页分组--五者互相正交，各改各的模块，可并行推进。其中 0.17.0（存量 bug）和 0.17.3（首次启动引导）为 P0。
- **第二组（截图专项）**：OCR 是截图功能的专项优化，与截图翻译、截图标注共享截图 overlay 链路，独立成组。
- **第三组（Markdown 渲染引擎与下游）**：编辑器、便签、AI 对话返回三者都消费同一个共享 Markdown renderer（0.16.2 抽取的 `frontend/js/shared/markdown.js`）。渲染引擎的增强（勾选块、主窗口 AI 展示区）是下游消费者的共享基础，必须先做；便签深化依赖渲染能力；AI 返回 MD 渲染也在此引擎上接入。三者放一起做，避免反复改同一模块。

### 2.3 明确"不是问题"的（待确认）

> 以下项初看像 bug，但需核实是否为有意设计，避免误改：

| 项 | 结论 |
|---|---|
| DB 清空后文件不缩小 | **已查实为 bug**（非正常行为）。SQLite `DELETE` 只标记空闲页不缩文件是正常的，但 Blink 的增量清理路径（`cleanup_old` 系列、单条删除、删对话）全部不 VACUUM，只有 4 个"全部清空"按钮做了。详见 §3.1 C2 |
| 便签关闭后管理界面仍留存 | 0.16.8 决策"关闭只隐藏、删除才移除"是有意设计。但空便签留存不合理，§3.2 回收站方案将重新设计此语义 |

## 三、核心设计 / 决策

> 本节列出 0.17 的关键决策。**标「待定」的需讨论后定案**，定案后改「已定」并补理由。

### 3.1 存量问题修复策略（已定）

五个存量 bug 均已完成代码调查，根因与修复方案如下。

**A. 开机自启弹出命令行窗口（已定位根因）**

Blink 主程序是 GUI 子系统（`#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`，`main.rs:1`），自身不弹控制台。弹窗来自 funasr-server 自启路径中的**孤儿进程清理**：

- `src/infra/platform/process.rs:24` -- `find_pid_by_port` 中 `Command::new("netstat")`，**未加 `CREATE_NO_WINDOW`**
- `src/infra/platform/process.rs:65` -- `kill_process_by_pid` 中 `Command::new("taskkill")`，**未加 `CREATE_NO_WINDOW`**

这两个在 `start_funasr_server` -> `kill_process_by_port`（`maintenance.rs:171`）路径触发，当上次 Blink 崩溃后残留 funasr-server 占端口时，开机自启会弹出控制台窗口。

**额外隐患**（非自启路径，一并修）：
- `src/domain/mcp/client.rs:353` -- MCP stdio server 启动未加 `no_window_tokio()`（当前 lazy 启动，隐患）
- `src/domain/ai/cli_recognizer.rs:333` -- `build_cli_command` 中 `cmd.exe /C` 和 `Command::new(cli_path)` 未加 `no_window_tokio()`（手动触发，隐患）

**修复方案**：上述 4 处全部用 `no_window()` / `no_window_tokio()`（已定义在 `src/infra/platform/mod.rs:39/52`）包裹。funasr python 进程本身已正确保护（`funasr.rs:498` 用了 `no_window_tokio`）。

**B. 截图双"翻译中"loading 动画（已定位根因）**

经代码调查，截图 overlay 有**三个**"翻译中"loading 源，其中两个样式不同且可同时触发：

| Loading | 位置 | 样式 | 触发 |
|---|---|---|---|
| **A** DOM `#sel-loading` | `chord-screenshot.html:25` | 白色 36px CSS border spinner + "翻译中…" 文字 | `showSelLoading('翻译中…')` -- `ss-ocr.js:289`（0.15 redo 路径）和 `:358`（`requestOverlayTranslation`） |
| **B** Canvas arc | `annotation-engine.js:1283` | 蓝色 `#4a9eff` 弧线 + `rgba(0,0,0,0.55)` 底盘 | `setOverlayLoading(true)` -- `ss-ocr.js:674`（`doTranslate`） |
| **C** Panel textarea | `ss-ocr.js:672` | `opacity: 0.5` + 占位文字 | `doTranslate` |

**根因**：`doTranslate`（`ss-ocr.js:665`）同时激活 Loading B（`setOverlayLoading(true)`）和 Loading A（`requestOverlayTranslation()` -> `showSelLoading('翻译中…')`），无互斥。

**修复方案**：保留 Loading B（canvas 内嵌，视觉一体）作为图上翻译主 loading；Loading A 降级为 fallback。

调度规则：
1. `doTranslate` 路径（图上翻译，overlay 已有内容）：用 Loading B（`setOverlayLoading`）。`requestOverlayTranslation` 内部检查 `isOverlayLoading()`，若 true 则跳过 `showSelLoading`（互斥）。
2. `_runOcrFresh` 路径（0.15 redo，overlay 无内容）：用 Loading A（`showSelLoading`），此路径不触发 `setOverlayLoading`。
3. Loading C（panel textarea 占位）保留不动。

**改动**：`ss-ocr.js:354-371` `requestOverlayTranslation` 开头加 `const useOverlayLoading = annot.isOverlayLoading();`，`if (!useOverlayLoading) showSelLoading('翻译中…');`。`.finally()` 中 `if (!useOverlayLoading) hideSelLoading();`。

**C. 清空剪贴板不清图片 + DB 不缩小（已查实根因）**

经代码调查确认两个独立问题：

**C1. 剪贴板图片无独立清理入口**：0.16.4 将图片放 `blink_cache.db` 的 `clipboard_images` 表，但前端存储页只有 history / clipboard(文本) / ai-audit / cache-db 四个清空按钮，没有针对 `clipboard_images` 的单独入口。而 `clipboard_images::cleanup_old_images`（按天清理）是死代码--从未被调用（`clipboard_images.rs:197`，标 `#[allow(dead_code)]`），只有 `cleanup_excess_images`（超量截断，200 条上限）在 `windows.rs:240` 每次插入后运行，且截断也不 VACUUM。`clear_all_images`（`clipboard_images.rs:189`）同样是 dead code，且 `clear_cache_db`（`diagnostic.rs:180-189`）清了 `performance_metrics` + `icon_cache` 但**跳过了 `clipboard_images`**。存储统计 `get_storage_info`（`diagnostic.rs:25-109`）也不含图片行数/大小。所以 cache 库的图片 BLOB 只增不减且对用户不可见。

**C2. 增量清理后 DB 不缩小（系统性问题）**：SQLite 的 `DELETE` 只把页标记为空闲页加入 freelist，文件不缩。Blink 的 VACUUM 策略只覆盖了 4 个"全部清空"按钮（`clear_history` / `clear_clipboard_history` / `clear_ai_audit` / `clear_cache_db`，分别在 `search.rs:543` / `clipboard.rs:93` / `management.rs:10` / `diagnostic.rs:189` 调 `data::vacuum`），而真正高频运行的启动后台清理（`spawn_startup_cleanup` 里的 `cleanup_old` 系列，`pools.rs:58-89`）、单条删除、`delete_chat_conversation` 全部只 DELETE 不 VACUUM。导致 `blink_history.db`、`blink_ai.db`、`blink_cache.db` 三个库文件在长期使用中只增不缩。其中 `blink_cache.db`（含 icon_cache 和 clipboard_images 两个 BLOB 表）膨胀最严重。代码库中无任何 `PRAGMA freelist_count` / `PRAGMA page_count` / `PRAGMA auto_vacuum` 使用。

**清理操作分组**（存储页"清理操作"区）：
- **缓存类**：清空缓存（performance_metrics + icon_cache）
- **用户数据类**：清空历史记录 / 清空剪贴板记录 / 清空剪贴板图片 / 清空 AI 调用记录
- **维护类**：优化存储（四库 VACUUM）

**一键清理**（`cleanup_all_data`）：运行时禁用（`disabled`），仅卸载前手动启用。原因：该操作删整个 `%APPDATA%\blink`（含 config.db 配置 + 全部用户数据），软件运行中执行会导致配置丢失、数据库连接断开等不可恢复状态。

**config.db 清理铁则**：`blink_config.db` 是配置库，包含 `config`（KV）和 `ai_permission_memory` 表。任何"清理缓存"/"一键清理"操作不得触碰 config.db。`optimize_storage`（VACUUM）可对 config.db 执行（VACUUM 不删数据，只回收空闲页）。

### 3.2 便签状态流转设计 -- 回收站方案（已定）

**问题**：0.16.7-0.16.11 的便签模型中，关闭=隐藏（visible=false），删除=物理删除（不可恢复），管理界面展示全部用 badge 区分。这导致空便签关闭后也留存、管理界面堆积，且"关闭"和"隐藏"语义混淆。

**现状确认**（代码调查）：
- StickyNote 模型只有 `visible` 布尔字段，无 `trashed`/`deleted_at` 等软删除字段
- 关闭按钮 -> 后端 `CloseRequested` handler `prevent_close` + `set_visible(false)` + `hide()`（保留数据和窗口 webview）
- 删除 = 物理 `DELETE FROM sticky_notes WHERE id=?`，不可恢复
- 管理界面 `list()` 无 WHERE 过滤，返回全部便签，用 badge 区分 visible 状态

**定案：关闭=软删除进回收站 + 管理界面回收站 tab + 30 天自动清理**

| 操作 | 行为 | 数据 |
|---|---|---|
| 便签关闭按钮 | 软删除：`trashed=true` + `deleted_at=now`，窗口 hide | 保留，进回收站 |
| 管理界面"恢复" | `trashed=false`，恢复到桌面 | 保留 |
| 管理界面"彻底删除" | 物理 DELETE | 永久删除，需确认 |
| 管理界面"清空回收站" | 批量物理 DELETE 所有 `trashed=true` 项 | 永久删除，需确认 |
| 启动后台清理 | `trashed=true` 且 `deleted_at` 超 30 天的物理 DELETE | 自动清理 |

**定案要点**：
- 便签窗口**去掉"删除"按钮**，关闭即进回收站；想彻底删去回收站里删。
- 回收站保留 **30 天**，超期启动时自动物理删除。
- 管理界面提供"清空回收站"一键按钮。
- 相比 Win 自带便签的"关闭即删除无回收站"，回收站方案更友好；相比当前"隐藏堆积"，关闭即移入回收站更干净。

**模型改动**：StickyNote 加 `trashed: bool`（默认 false）+ `deleted_at: Option<i64>` 字段；`list()` 默认只返回 `trashed=false`，新增 `list_trashed()` 返回回收站项；启动后台清理补 `cleanup_trashed(retention_days=30)`。

**与 0.16 语义的衔接**：
- `visible` 字段保留原有语义（控制桌面窗口显示），与 `trashed` 正交--回收站里的便签 `visible` 无意义。
- 0.16.8 的"关闭只隐藏"语义被回收站取代：关闭不再 `set_visible(false)`，而是 `set_trashed(true)`。
- **旧数据迁移策略（已定）：直接清理**。`visible=false` 的旧便签在迁移脚本中直接 `DELETE FROM sticky_notes WHERE visible=false`。理由：0.16 尚未正式发版，无线上用户数据需保留。`visible=true` 的便签迁移为 `trashed=false`（正常活跃）。
- 0.16.11 的 `IS_APP_EXITING` / `prevent_close` / `flush_all_sticky_windows` 退出逻辑保留，只改关闭按钮的语义（隐藏 -> 软删除）。

### 3.4 编辑器 Live Preview 方案（已定：Cherry Markdown 替换 marked）

**背景**：0.16 §四明确"不引入富文本/WYSIWYG"，使用纯文本 + Markdown。用户实际需求是** Live Preview**（编辑 MD 源文本 + 实时带样式预览），而非完全看不到 MD 符号的 WYSIWYG。

**现状确认**：0.16.2 的共享 Markdown renderer 使用 **marked** + **DOMPurify** + **highlight.js**，全部通过 `<script>` 标签引入 vendor 脚本（`window.marked` / `window.DOMPurify` / `window.hljs`），不 import，符合无 bundler 铁则。封装在 `frontend/js/shared/markdown.js`，6 个调用点（chat/components.js、content-editor/main.js、settings/about.js）全部经此层，不直接调 marked。

**marked 的两个核心缺陷**：
1. **无流式渲染**：marked 是无状态一次性 `parse(text)` -> HTML，没有 streaming / incremental API。当前 AI 回复流式是每 chunk 全量 `marked.parse(accumulated)` + `innerHTML` 替换，长回答性能差且闪烁未闭合 MD 符号。
2. **无 Live Preview 编辑能力**：marked 是纯渲染器，不提供编辑/预览分栏。

**框架调研结论**（已调研 Cherry Markdown / tui.editor / Tiptap / Milkdown / editor.md / markdown-it）：

| 框架 | UMD 单文件 | Live Preview | 流式渲染 | 无 bundler 摩擦 | 结论 |
|---|---|---|---|---|---|
| **Cherry Markdown**（Stream 版） | ✅ `<script src>` 全局 `window.Cherry` | ✅ `edit&preview` 模式 | ✅ **原生专项支持**（自动补全未闭合 MD 片段，局部渲染） | ✅ 最低（与现有 vendor 模式一致） | **选定** |
| tui.editor | ✅ | ✅ | ⚠️ 增量解析但不专项 | ✅ | 备选（有 WYSIWYG 模式，0.18+ 若需再评估） |
| Tiptap | ⚠️ 需 import map + 4 包 | ⚠️ 需 MD 扩展转换 | ❌ 原生 streamContent 付费，免费层闪烁 | ⚠️ 中（PM 依赖管理复杂） | 排除 |
| Milkdown | ❌ 官方无 UMD | - | - | - | 排除 |
| editor.md | ❌ 需 6+ 文件 + jQuery | ✅ | ❌ marked 全量解析闪烁 | ❌ 高 | 排除（2019 废弃） |
| markdown-it | ✅ | ❌ | ❌ 同 marked | ✅ | 无优势 |

**Cherry Markdown 选定理由**：
- Stream 版专为 AI Chat 流式场景设计，自动补全未闭合 MD 片段，解决 marked 流式闪烁痛点
- 本身是 Tauri 桌面客户端项目，技术栈一致
- UMD 单文件 + 全局对象，与现有 marked/purify/highlight 的 vendor 模式完全一致，零摩擦
- 无外部运行时依赖（DOMPurify 已打包）
- `edit&preview` 模式满足 Live Preview 需求（左编辑 MD + 右实时渲染，双向同步滚动）

**Cherry 构建版本选择**：Stream 版（`cherry-markdown.stream.min.js`），gzip ~475KB。一个版本覆盖所有场景（只读流式渲染 + Live Preview 编辑 + 纯预览），不混用多版本避免渲染行为不一致。

**切换改动范围**（封装层已就位，改动极小）：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `frontend/js/shared/markdown.js` | 内部实现从 `marked.parse()` + `DOMPurify.sanitize()` 改为 Cherry 引擎渲染。`renderMarkdown(text)` / `initMarkdown()` 接口签名不变。`highlightCodeBlocks` 变为空操作（Cherry 内置代码高亮）。新增 `renderMarkdownStream(container)` 返回带 `write(text)` 方法的流式实例。新增 `createMarkdownEditor(element, opts)` 返回 `edit&preview` 实例。 |
| 2 | `frontend/chat.html:127-129` | `<script src="vendor/marked.min.js">` + `purify.min.js` + `highlight.min.js` 替换为 `<script src="vendor/cherry-markdown.stream.min.js">` + `<link href="vendor/cherry-markdown.min.css">` |
| 3 | `frontend/content-editor.html:56-58` | 同上替换 |
| 4 | `frontend/settings.html:1778-1779` | 同上替换（settings 当前无 highlight，替换后补齐） |
| 5 | `frontend/index.html` | 新增 Cherry vendor 加载（主窗口当前无任何 MD vendor） |

**6 个现有调用点完全不动**（chat/components.js × 4、content-editor/main.js × 2、about.js × 2），它们 import 的是 `markdown.js` 函数名，签名不变。

**回滚成本**：纯 git revert `markdown.js` + HTML vendor 标签，旧 vendor 文件不删只注释引用，零业务逻辑影响。

**旧 vendor 文件处理**：`marked.min.js` / `purify.min.js` / `highlight.min.js` 保留在 `vendor/` 目录但不再加载，标注 deprecated 注释。确认 Cherry 稳定后可删除。

**WYSIWYG 方向性结论**：当前需求是 Live Preview（编辑 MD + 实时预览），Cherry `edit&preview` 已满足。真正的 WYSIWYG（完全看不到 MD 符号，如 tui.editor `wysiwyg` 模式）推迟到 0.18+，若 Live Preview 体验不满足再评估。此项不影响 0.17.7a 范围。

本子版本是第三组的共享基础，同时服务编辑器、便签和 AI 对话返回。

**A. 勾选块渲染修复**

原方案（DOMPurify 白名单加 `input`）随 Cherry 替换 marked 自动解决--Cherry 原生支持 GFM task list 渲染，不经过 DOMPurify 白名单过滤。无需单独改动。

**B. 主窗口 AI 展示形态重设计 -- 架构统一方案**

**现状问题**（代码调查确认）：主窗口 AI 回答被塞进结果列表的一条 `<li>` 里，和"打开微信"共用同一套列表 UI，`frontend/index.html` 没有加载 marked/DOMPurify，渲染用 `textContent` + `white-space: pre-wrap`。长回答、代码块、列表在最高频入口呈现为带原始 Markdown 符号的纯文本，体验割裂于对话窗口。

**根本架构问题**：主窗口 AI 走 `SearchService::trigger_ai`（外部调度 + 单槽 `PendingAiConfirmation` + seq 匹配），对话窗口走 `ChatService::prompt`（内部调度 + `PendingConfirms` + confirm_id + trusted）。两套独立的调度模型、权限机制、事件通道、前端 UI。导致主窗口 AI 无法多轮追问、无权限记忆、流式渲染重复实现。

**定案：主窗口 AI 改走 ChatService 内部调度 + 模式切换 + 共用渲染**

核心变更：主窗口 AI 从 `SearchService::trigger_ai` 切换到 `ChatService::prompt`，与对话窗口统一调度模型。主窗口使用临时对话（`EphemeralConversationMemory`，不持久化），对话窗口使用持久化对话（`SqliteConversationMemory`）。事件通道参数化 `target_window`，所有 AI 事件（流式 chunk / 权限确认）按 target 定向 emit。

独立容器 + 独立输入框的理由：
- `#query` 背后有 Ghost overlay（三层 DOM）、拼音/选区建议、autosuggest 逻辑--AI 追问模式下全部应抑制，共用意味着每个逻辑都要加 `if (aiMode)` 分支
- `#ai-query` 行为简单：Enter 发送追问，不需要 Ghost、防抖搜索、autosuggest
- `#results` 的分页模型（不滚动、靠内容撑高）和 `#ai-display` 的滚动模型（max-height + overflow-y）是两套高度策略，独立容器用 `display: none/flex` 切换，CSS 隔离干净

闪烁分析：`display:none/flex` 同帧生效浏览器一次 paint；焦点转移 `#query` -> `#ai-query` 同步块内 blur+focus 下一帧完成；进入 AI 模式时立即在 `#ai-content` 放 typing 三点动画保持窗口有合理高度。

### 3.6 窗口预热复用铁则 + 托盘增强（已定，铁则完成后迁入 spec-frontend）

**定案 A：所有窗口启动时预创建并隐藏，需要时直接 show，全部预热。**

**定案依据**：实测全窗口打开一遍开销仅几十 MB 内存，在 AGENTS.md 常驻内存 < 300MB 预算内可接受，无需分级或设置开关。

**现状**（代码调查确认）：已有 `preheat_secondary_windows`（`windows.rs:1654`，启动 3s 后异步执行）预热了 5 个窗口：`chord-screenshot`、`context-menu`、`voice-overlay`、`chord-pin`、`chat`。但 3 个窗口未预热：`settings`（`open_settings` `windows.rs:1797` 按需创建）、`content-editor`（`show_content_editor_window` `windows.rs:820` 按需）、`sticky-manager`（`show_sticky_manager_window` `windows.rs:880` 按需）。`sticky-{id}` 动态窗口 per-note 创建（`show_sticky_window` `windows.rs:957`，URL 带 id 参数）。

**预热可行性确认**（代码调查）：
- `settings`：静态 URL，无参数 -> 可预热
- `content-editor`：静态 URL，payload 走 Tauri State（`PendingEditorPayload` Mutex，`content_editor.rs:44`），show 时 `__contentEditorReload` eval 触发 `get_content_editor_payload` 拉取 -> 可预热
- `sticky-manager`：静态 URL，无参数，自取列表（`listStickyNotes()`） -> 可预热
- `sticky-{id}`：URL 带 id 参数（`sticky.html?id={id}`，`windows.rs:989`），per-note 窗口，label 为 `sticky-{id}` -> 不预热（保持 DB 恢复时按需创建）

**实现要点**：
- `preheat_secondary_windows`（`windows.rs:1654`）追加预热 `settings`、`content-editor`、`sticky-manager` 三个窗口，用同样的 `WebviewWindowBuilder::new(...).visible(false)` 模式。
- 预热在启动 3s 后异步执行（已有逻辑），不阻塞 Alt+Space 主链路。
- 预热窗口初始为隐藏状态，首次 show 时直接复用。show 函数已有 fallback 创建逻辑（`get_webview_window` 不存在则 build），预热后必然命中复用路径。
- 预热失败打 `warn!` 日志不阻断（show 时 fallback 创建）。
- 便签窗口因其动态数量特性（每条便签一个窗口），预热策略为：预热窗口外壳复用机制已有（0.16.11），便签按 `visible=true && trashed=false` 恢复时创建。
- 完成后实测常驻内存确认 < 300MB（8 个预热窗口 + 动态便签）。

**铁则迁入 spec-frontend**：

> **窗口预热复用**：所有窗口在启动后异步预创建并隐藏（`visible:false`），首次 show 直接复用预创建的 webview，不按需创建。例外：动态数量的窗口（`sticky-{id}`）按需创建，但窗口外壳复用机制已有。预热在启动 3s 后异步执行，不阻塞 Alt+Space 主链路。预热失败打 warn 日志但不阻断，show 时 fallback 创建。

### 3.9 OCR 优化方案（已定：方案 A，语言选择修复 + 诊断面板）

**现状**（代码调查确认）：0.11 接入 Windows OCR（WinRT `OcrEngine`），word 级识别。中文准确度差。经代码调查，**根因不是 WinRT 能力不足，而是当前代码没有正确选语言**：

- `backend_windows.rs:54` 用 `WinRtOcrEngine::TryCreateFromUserProfileLanguages()`，依赖**用户配置文件语言列表**（不是系统显示语言，不是已安装 OCR 包列表）。若用户配置文件里 `en-US` 排前（很多中文系统用户装了英文语言包），引擎选英文--**装了中文 OCR 包也用不上，中文一个字都识别不出来**。
- 代码从不调 `AvailableRecognizerLanguages()` 探测已安装的 OCR 语言包，也不调 `TryCreateFromLanguage()` 显式选语言。
- 无任何图片预处理（灰度化、二值化、放大、去噪）。唯一的图像操作是 `Convert(Bgra8)` 格式转换。
- `join_words_smart`（`ocr_engine.rs:166-208`）已解决 SDK 中文"每字夹空格"问题，CJK↔CJK 无空格拼接且有单测覆盖。**这块不是问题。**

**Windows OCR 语言包机制**（调研确认）：

OCR 语言包是独立的 Windows capability（`Language.OCR~~~zh-CN~0.0.1.0`），与界面语言（`Language.Basic`）、输入法、手写都分开。中文版 Windows 11 通常预装中文 OCR 包，但英文版 + 中文输入法**不预装**。安装方式：Windows 设置"语言和区域"添加中文语言并勾选 OCR，或 PowerShell `Add-WindowsCapability -Online -Name "Language.OCR~~~zh-CN~0.0.1.0"`。检测已安装：`OcrEngine::AvailableRecognizerLanguages`（WinRT 静态属性）。PowerToys Text Extractor（微软自家工具）也有同样的"中文 OCR 不工作"用户报告（GitHub #21234），根因相同。

**候选方案保留**（本版本只做 A，B/C/D 不做）：

| 方案 | 准确度 | 成本 | 体积影响 | 0.17.5 状态 |
|---|---|---|---|---|
| **A. 优化 WinRT OCR 用法** | 中（语言选择修复后预期显著提升） | 低 | 无 | **本版本做** |
| **B. PaddleOCR 本地化** | 高 | 高（推理引擎集成） | 大（模型 + ONNX/Paddle runtime） | **不做**，记录为候选；A 优化后仍不达标再评估 |
| **C. 在线 OCR API** | 高 | 中（API 集成） | 无 | **不做**；截图可能含敏感信息，与本地优先定位冲突 |
| **D. AI 多模态直接读图** | 高 | 中 | 无 | **不做**；划归 0.20（roadmap §7.3 CAP 闭环"OCR 内部直链"） |

> 注：原 §3.9 将方案 D 与 roadmap §7.3 混为一谈。roadmap §7.3 的"OCR 内部直链"是**架构修复**（Rust 内部把截图 bytes 交给 OCR capability，不经 LLM channel），不是 OCR 准确度优化，应归 0.20。

**定案：方案 A = 语言选择修复 + 诊断面板（不含图片预处理）**

不本版本做图片预处理的原因：先修复语言选择（根因），用诊断面板验证效果。若修复后中文识别仍不理想，再在后续迭代加预处理（放大小图、灰度化、Otsu 二值化）。符合"先出简单优化看是不是配置问题"的迭代策略。

**A. 语言选择修复（中文优先 + fallback）**

当前 `recognize_raw`（`backend_windows.rs:14-121`）每次调用都创建引擎（`TryCreateFromUserProfileLanguages`，行 54-55）。改为：

1. 调 `WinRtOcrEngine::AvailableRecognizerLanguages()` 获取设备已安装 OCR 语言列表
2. 按优先级匹配中文：`zh-Hans-CN` > `zh-Hans` > `zh-Hant-TW` > `zh-Hant` > 任意 `zh-*` 前缀
3. 命中则 `WinRtOcrEngine::TryCreateFromLanguage(&matched_lang)`
4. 未命中（设备无任何中文 OCR 包）则 fallback 到 `TryCreateFromUserProfileLanguages()`，并打 `warn!` 日志记录"无中文 OCR 语言包"

WinRT 中文引擎非排他--选了中文引擎仍能识别英文（WinRT OCR 引擎按语言模型优先匹配，混合文本也能处理），所以优先选中文不影响英文截图。

- 主窗口 + 对话窗口共用 `PendingConfirms` + `trusted: HashSet<(conversation_id, tool_name)>`
- 会话级记忆已有：同对话同 tool 确认一次后跳过
- 临时对话（主窗口）的 trusted 随 `EphemeralConversationMemory` 在会话结束后丢失--这是期望行为（临时对话不持久化）
- 持久化对话（对话窗口）的 trusted 当前是进程内 `HashSet`，重启即失

**Dangerous/Sensitive 项调查**（确认记忆粒度安全）：

| 类型 | 数量 | 参数 | 触发确认 |
|---|---|---|---|
| Dangerous Action（内置） | 6 个 | **全部无参**（lock/shutdown/restart/sleep/clear_history/exit_blink） | `danger_class == Dangerous` |
| Sensitive Capability（内置） | 2 个 | `query` + `max_results`（search_apps / search_clipboard_history，均为只读查询） | `schema.sensitive == true` |
| Dangerous Plugin（动态） | 不固定 | 由插件 manifest 声明，tool_name 含插件前缀 | 插件 `danger_class` 字段 |

关键发现：内置 6 个 dangerous action 全部无参，不存在"确认了写文件 A 代表想自动写文件 B"的问题。文件操作（open_path）和 URL（open_url）都是 Safe，不触发确认。因此按 `tool_name` 粒度记忆是安全的。

---

**定案 1：记忆粒度 = `tool_name`**

记忆 key 为 `tool_name`（去掉 conversation_id），不纳入 args。内置 dangerous action 全无参，sensitive 是只读查询，粒度安全。插件 tool_name 含插件前缀（如 `plugin_xxx:tool_yyy`），粒度已够。未来若插件需更细粒度，可在 manifest 加 `remember_args` 字段标记，0.17.8 不做。

**定案 2：持久化存储 = `blink_config.db` 新表 `ai_permission_memory`**

```sql
CREATE TABLE ai_permission_memory (
    tool_name TEXT PRIMARY KEY,     -- 记忆的 tool 名
    trusted_at INTEGER NOT NULL,     -- 用户确认时间（unix timestamp）
    expires_at INTEGER NOT NULL,    -- 过期时间（trusted_at + 记忆天数）
);
```

权限记忆是配置类数据（用户偏好），不是对话数据。放 config 库语义正确，删对话时不影响权限记忆（符合"记忆跨会话"语义）。

**定案 3：过期策略 = 过期后重新询问 + 查询时判断 + 启动时批量清理**

- **过期行为**：过期后下次该 tool 触发时重新弹确认卡片（不静默失效）。用户感知到"过期了"。
- **判断时机**：`is_trusted` 查询时同时查 `expires_at < now`，过期则返回 false（不命中）并从 DB 删除该行。实时无延迟。
- **启动批量清理**：`spawn_startup_cleanup` 追加 `DELETE FROM ai_permission_memory WHERE expires_at < now`，保持表干净。

**定案 4：配置项 = 一套配置，`memory_enabled` + `memory_days`（默认 7 天），UI 在 ai-chat tab**

```rust
// AiConfig shard 或新 shard
pub struct AiPermissionConfig {
    pub memory_enabled: bool,       // 总开关，默认 true
    pub memory_days: u64,           // 记忆天数，默认 7
}
```

0.17.6 架构统一后两路已合并，一套配置覆盖主窗口（临时对话不持久化 trusted，不受影响）和对话窗口（持久化对话用此配置）。默认 7 天：太短（1 天）频繁重新确认体验差，太长（30 天）安全性降低。

UI 位置：设置页"AI 对话能力"tab（`ai-chat`），加"权限记忆"section：
- 开关：记忆 AI 工具权限
- 滑块/输入框：记忆天数（1-30）
- 按钮：清除所有记忆的权限（DELETE FROM ai_permission_memory）

**定案 5：双层 trusted 设计 = 会话级 HashSet + 持久化 DB**

保留会话级 `trusted: HashSet<(conversation_id, tool_name)>`（进程内，重启即失）不变，新增持久化 DB 层。

`is_trusted` 检查顺序：
1. 会话级 HashSet 命中 -> 直接返回 true（跳过 DB 查询，热路径快）
2. 会话级未命中 -> 查持久化 DB（`tool_name` 匹配 + `expires_at > now`）
3. DB 命中且未过期 -> 视为 trusted + 加入会话级 HashSet（本次会话不再查 DB）
4. DB 未命中或已过期 -> 返回 false，触发确认弹窗

`trust()` 写入：用户确认后同时写入会话级 HashSet + 持久化 DB（若 `memory_enabled`）。

`clear_trust(conversation_id)` 处置：清会话级 HashSet 中该 conversation 的所有项，不影响持久化 DB。原 dead code 现有调用场景（删对话时）--删对话清会话级合理，持久化记忆跨会话保留。

| 清理时机 | 操作 | 理由 |
|---|---|---|
| 删除对话时 | `clear_trust(conversation_id)` 清会话级 HashSet | 会话级与对话绑定 |
| 手动清除 | 设置页"清除所有记忆"按钮 -> DELETE FROM ai_permission_memory | 用户主动撤销全部持久化记忆 |
| 过期自动清理 | 查询时判断删除 + 启动时批量清理 | 自动维护 |
| 关闭记忆开关 | `memory_enabled = false` 时 `is_trusted` 不查 DB 直接返回 false，DB 数据保留（重新开启后恢复） | 开关不删数据，只是不查询 |
| 卸载插件时 | 删除该插件所有 tool 的记忆行（`WHERE tool_name LIKE 'plugin_xxx:%'`） | 插件卸载后记忆无意义 |
