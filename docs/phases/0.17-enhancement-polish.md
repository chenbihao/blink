# Blink 0.17 - 增强与打磨（Enhancement & Polish）

> **范围**：修复 0.16 遗留存量问题（自启弹窗、截图双 loading、剪贴板清理与 DB VACUUM、chord 删除图片、AI 权限确认断链），建立窗口预热铁则与托盘增强，增强搜索与系统能力，调研并优化截图 OCR，深化 Markdown 渲染引擎并重设计主窗口 AI 展示形态以统一支撑编辑器、便签与 AI 对话返回，补齐首次启动引导与快捷键速查等产品体验基础设施。
>
> **状态**：🚧 进行中。
>
> **动机**：0.16 完成剪贴板增强、内容流转与桌面便签后，Blink 的"感知->编辑->常驻"链路已闭环。但实际使用中暴露出存量 bug、便签交互粗糙、AI 对话权限断链、OCR 准确度不足等问题。0.17 是从"能用"到"好用"的打磨阶段，不引入大架构变更，聚焦可靠性、交互完整性和体验闭环。
>
> **前置**：0.16（便签、编辑器、剪贴板图片、共享 Markdown）；0.15（截图重做、chord requires_input）；0.12（AI 对话窗口、PendingConfirms 权限闭环）。
>
> **原则**：不引入大架构变更；WYSIWYG 若立项需充分论证与 0.16 决策的冲突；窗口预热铁则完成后迁入 spec-frontend；调研类任务（OCR）先出结论再定实现方案；存量 bug 修复优先于新功能。

## 二、背景与动机

### 2.1 为什么 0.17 做这件事

0.16 将"感知->编辑->常驻"链路打通后，实际日常使用暴露出四类问题：

1. **可靠性存量债**：0.16 新增的图片剪贴板、便签、chord 删除等功能存在边界 bug；自启链路有命令行窗口泄漏；截图翻译 loading 竞态；AI 权限确认在主窗口断链。这些问题影响"按快捷键后立即可用"的核心承诺。
2. **交互不完整**：便签管理界面样式异常、操作交互混乱、空便签留存；编辑器 Markdown 渲染缺勾选块；主窗口 AI 回答塞进结果列表纯文本展示、无 Markdown 渲染。这些是 0.16 快速迭代留下的半成品。
3. **能力短板**：OCR 准确度不足（根因是未正确选中文语言，非 WinRT 能力不足，§3.9 已查实）；搜索缺少系统级快捷方式；更新提醒缺少变更内容展示。
4. **产品体验基础设施缺失**：新用户安装后无首次启动引导（不知道 Alt+Space 唤起）；应用内无快捷键速查；托盘菜单无"显示主窗口"项、无状态反馈；设置页 13 tab 未分组。这些是从 MVP 到完整产品的体验断裂点。

### 2.2 分组逻辑

0.17 的子版本按**内聚性**而非优先级排列：

- **第一组（零碎优化）**：问题修复、搜索增强、窗口预热+托盘、首次启动引导、设置页分组--五者互相正交，各改各的模块，可并行推进。其中 0.17.0（存量 bug）和 0.17.3（首次启动引导）为 P0。
- **第二组（截图专项）**：OCR 是截图功能的专项优化，与截图翻译、截图标注共享截图 overlay 链路，独立成组。
- **第三组（Markdown 渲染引擎与下游）**：编辑器、便签、AI 对话返回三者都消费同一个共享 Markdown renderer（0.16.2 抽取的 `frontend/js/shared/markdown.js`）。渲染引擎的增强（勾选块、主窗口 AI 展示区）是下游消费者的共享基础，必须先做；便签深化依赖渲染能力；AI 返回 MD 渲染也在此引擎上接入。三者放一起做，避免反复改同一模块。

### 2.3 明确"不是问题"的（待确认）

> 以下项初看像 bug，但需核实是否为有意设计，避免误改：

| 项 | 结论 |
|---|---|
| DB 清空后文件不缩小 | **已查实为 bug**（非正常行为）。SQLite `DELETE` 只标记空闲页不缩文件是正常的，但 Blink 的增量清理路径（`cleanup_old` 系列、单条删除、删对话）全部不 VACUUM，只有 4 个"全部清空"按钮做了。详见 §3.1 C2 |
| 便签关闭后管理界面仍留存 | 0.16.8 决策"关闭只隐藏、删除才移除"是有意设计。但空便签留存不合理，§3.2 回收站方案将重新设计此语义 |

## 三、核心设计 / 决策

> 本节列出 0.17 的关键决策。**标「待定」的需讨论后定案**，定案后改「已定」并补理由。

### 3.1 存量问题修复策略（已定）

五个存量 bug 均已完成代码调查，根因与修复方案如下。

**A. 开机自启弹出命令行窗口（已定位根因）**

Blink 主程序是 GUI 子系统（`#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`，`main.rs:1`），自身不弹控制台。弹窗来自 funasr-server 自启路径中的**孤儿进程清理**：

- `src/infra/platform/process.rs:24` -- `find_pid_by_port` 中 `Command::new("netstat")`，**未加 `CREATE_NO_WINDOW`**
- `src/infra/platform/process.rs:65` -- `kill_process_by_pid` 中 `Command::new("taskkill")`，**未加 `CREATE_NO_WINDOW`**

这两个在 `start_funasr_server` -> `kill_process_by_port`（`maintenance.rs:171`）路径触发，当上次 Blink 崩溃后残留 funasr-server 占端口时，开机自启会弹出控制台窗口。

**额外隐患**（非自启路径，一并修）：
- `src/domain/mcp/client.rs:353` -- MCP stdio server 启动未加 `no_window_tokio()`（当前 lazy 启动，隐患）
- `src/domain/ai/cli_recognizer.rs:333` -- `build_cli_command` 中 `cmd.exe /C` 和 `Command::new(cli_path)` 未加 `no_window_tokio()`（手动触发，隐患）

**修复方案**：上述 4 处全部用 `no_window()` / `no_window_tokio()`（已定义在 `src/infra/platform/mod.rs:39/52`）包裹。funasr python 进程本身已正确保护（`funasr.rs:498` 用了 `no_window_tokio`）。

**B. 截图双"翻译中"loading 动画（已定位根因）**

经代码调查，截图 overlay 有**三个**"翻译中"loading 源，其中两个样式不同且可同时触发：

| Loading | 位置 | 样式 | 触发 |
|---|---|---|---|
| **A** DOM `#sel-loading` | `chord-screenshot.html:25` | 白色 36px CSS border spinner + "翻译中…" 文字 | `showSelLoading('翻译中…')` -- `ss-ocr.js:289`（0.15 redo 路径）和 `:358`（`requestOverlayTranslation`） |
| **B** Canvas arc | `annotation-engine.js:1283` | 蓝色 `#4a9eff` 弧线 + `rgba(0,0,0,0.55)` 底盘 | `setOverlayLoading(true)` -- `ss-ocr.js:674`（`doTranslate`） |
| **C** Panel textarea | `ss-ocr.js:672` | `opacity: 0.5` + 占位文字 | `doTranslate` |

**根因**：`doTranslate`（`ss-ocr.js:665`）同时激活 Loading B（`setOverlayLoading(true)`）和 Loading A（`requestOverlayTranslation()` -> `showSelLoading('翻译中…')`），无互斥。

**修复方案**：保留 Loading B（canvas 内嵌，视觉一体）作为图上翻译主 loading；Loading A 降级为 fallback。

调度规则：
1. `doTranslate` 路径（图上翻译，overlay 已有内容）：用 Loading B（`setOverlayLoading`）。`requestOverlayTranslation` 内部检查 `isOverlayLoading()`，若 true 则跳过 `showSelLoading`（互斥）。
2. `_runOcrFresh` 路径（0.15 redo，overlay 无内容）：用 Loading A（`showSelLoading`），此路径不触发 `setOverlayLoading`。
3. Loading C（panel textarea 占位）保留不动。

**改动**：`ss-ocr.js:354-371` `requestOverlayTranslation` 开头加 `const useOverlayLoading = annot.isOverlayLoading();`，`if (!useOverlayLoading) showSelLoading('翻译中…');`。`.finally()` 中 `if (!useOverlayLoading) hideSelLoading();`。

**C. 清空剪贴板不清图片 + DB 不缩小（已查实根因）**

经代码调查确认两个独立问题：

**C1. 剪贴板图片无独立清理入口**：0.16.4 将图片放 `blink_cache.db` 的 `clipboard_images` 表，但前端存储页只有 history / clipboard(文本) / ai-audit / cache-db 四个清空按钮，没有针对 `clipboard_images` 的单独入口。而 `clipboard_images::cleanup_old_images`（按天清理）是死代码--从未被调用（`clipboard_images.rs:197`，标 `#[allow(dead_code)]`），只有 `cleanup_excess_images`（超量截断，200 条上限）在 `windows.rs:240` 每次插入后运行，且截断也不 VACUUM。`clear_all_images`（`clipboard_images.rs:189`）同样是 dead code，且 `clear_cache_db`（`diagnostic.rs:180-189`）清了 `performance_metrics` + `icon_cache` 但**跳过了 `clipboard_images`**。存储统计 `get_storage_info`（`diagnostic.rs:25-109`）也不含图片行数/大小。所以 cache 库的图片 BLOB 只增不减且对用户不可见。

**C2. 增量清理后 DB 不缩小（系统性问题）**：SQLite 的 `DELETE` 只把页标记为空闲页加入 freelist，文件不缩。Blink 的 VACUUM 策略只覆盖了 4 个"全部清空"按钮（`clear_history` / `clear_clipboard_history` / `clear_ai_audit` / `clear_cache_db`，分别在 `search.rs:543` / `clipboard.rs:93` / `management.rs:10` / `diagnostic.rs:189` 调 `data::vacuum`），而真正高频运行的启动后台清理（`spawn_startup_cleanup` 里的 `cleanup_old` 系列，`pools.rs:58-89`）、单条删除、`delete_chat_conversation` 全部只 DELETE 不 VACUUM。导致 `blink_history.db`、`blink_ai.db`、`blink_cache.db` 三个库文件在长期使用中只增不缩。其中 `blink_cache.db`（含 icon_cache 和 clipboard_images 两个 BLOB 表）膨胀最严重。代码库中无任何 `PRAGMA freelist_count` / `PRAGMA page_count` / `PRAGMA auto_vacuum` 使用。

**E. 主窗口 AI 权限确认断链（已查实根因 + 已定修复方案）**

经代码调查，主窗口和对话窗口的权限确认是**两套完全独立的后端闭环和前端 UI**：

| 维度 | 主窗口 | 对话窗口 |
|---|---|---|
| 事件名 | `blink://ai-confirm-action` | `blink://chat-confirm-action`（emit_to 定向） |
| IPC command | `confirm_ai_action`（自己执行 Capability） | `confirm_chat_action`（只送信号，agent loop 内 await） |
| 匹配键 | `seq`（无 confirm_id） | `confirm_id`（AtomicU64 递增） |
| UI 形态 | 结果列表中的一个 `<li>` 项（⚠ 徽章 + 副行文案） | 消息流内联卡片（标题 + 工具名 + 拒绝/允许按钮） |
| 触发方式 | 键盘 Enter（依赖 selected 选中态）/ 鼠标点击整行 | 仅鼠标点击按钮 |
| 信任/记住 | **无**，每次都弹 | **有**，`trusted: (conversation_id, tool_name)`，同对话同 tool 确认一次后跳过 |

**回车无效的双根因**：

### 3.2 便签状态流转设计 -- 回收站方案（已定）

**问题**：0.16.7-0.16.11 的便签模型中，关闭=隐藏（visible=false），删除=物理删除（不可恢复），管理界面展示全部用 badge 区分。这导致空便签关闭后也留存、管理界面堆积，且"关闭"和"隐藏"语义混淆。

**现状确认**（代码调查）：
- StickyNote 模型只有 `visible` 布尔字段，无 `trashed`/`deleted_at` 等软删除字段
- 关闭按钮 -> 后端 `CloseRequested` handler `prevent_close` + `set_visible(false)` + `hide()`（保留数据和窗口 webview）
- 删除 = 物理 `DELETE FROM sticky_notes WHERE id=?`，不可恢复
- 管理界面 `list()` 无 WHERE 过滤，返回全部便签，用 badge 区分 visible 状态

**定案：关闭=软删除进回收站 + 管理界面回收站 tab + 30 天自动清理**

| 操作 | 行为 | 数据 |
|---|---|---|
| 便签关闭按钮 | 软删除：`trashed=true` + `deleted_at=now`，窗口 hide | 保留，进回收站 |
| 管理界面"恢复" | `trashed=false`，恢复到桌面 | 保留 |
| 管理界面"彻底删除" | 物理 DELETE | 永久删除，需确认 |
| 管理界面"清空回收站" | 批量物理 DELETE 所有 `trashed=true` 项 | 永久删除，需确认 |
| 启动后台清理 | `trashed=true` 且 `deleted_at` 超 30 天的物理 DELETE | 自动清理 |

**定案要点**：
- 便签窗口**去掉"删除"按钮**，关闭即进回收站；想彻底删去回收站里删。
- 回收站保留 **30 天**，超期启动时自动物理删除。
- 管理界面提供"清空回收站"一键按钮。
- 相比 Win 自带便签的"关闭即删除无回收站"，回收站方案更友好；相比当前"隐藏堆积"，关闭即移入回收站更干净。

**模型改动**：StickyNote 加 `trashed: bool`（默认 false）+ `deleted_at: Option<i64>` 字段；`list()` 默认只返回 `trashed=false`，新增 `list_trashed()` 返回回收站项；启动后台清理补 `cleanup_trashed(retention_days=30)`。

**与 0.16 语义的衔接**：
- `visible` 字段保留原有语义（控制桌面窗口显示），与 `trashed` 正交--回收站里的便签 `visible` 无意义。
- 0.16.8 的"关闭只隐藏"语义被回收站取代：关闭不再 `set_visible(false)`，而是 `set_trashed(true)`。`visible=false` 的旧语义（隐藏但不在回收站）不再产生新数据，但旧数据需迁移--`visible=false` 的便签迁移为 `trashed=false`（仍在管理界面活跃列表，但不自动显示窗口），或直接迁移为 `trashed=true`（进回收站）。**待实现时定迁移策略**。
- 0.16.11 的 `IS_APP_EXITING` / `prevent_close` / `flush_all_sticky_windows` 退出逻辑保留，只改关闭按钮的语义（隐藏 -> 软删除）。

### 3.4 编辑器 WYSIWYG 可行性（待重点讨论）

**背景**：0.16 §四明确"不引入富文本/WYSIWYG"，使用纯文本 + Markdown。用户倾向便签做所见即所得（WYSIWYG）。

**现状确认**：0.16.2 的共享 Markdown renderer 使用 **marked** + **DOMPurify** + **highlight.js**，全部通过 `<script>` 标签引入 vendor 脚本（`window.marked` / `window.DOMPurify` / `window.hljs`），不 import，符合无 bundler 铁则。0.16 不做 WYSIWYG 的原因正是无 bundler 铁则--主流 WYSIWYG 框架（Tiptap / ProseMirror / Milkdown）都依赖 npm 构建生态。

**冲突点**：
- spec-frontend 铁则：**无 bundler、无 npm、无构建步骤**
- WYSIWYG 通常需要富文本编辑器框架，这些依赖 npm 生态
- 纯手写 `contenteditable` WYSIWYG 成本极高且易出错

**待讨论方向**：
1. **是否真需要 WYSIWYG**：Markdown 编辑 + 实时预览（分栏）能否满足？还是必须原地渲染？
2. **轻量方案可行性**：用 `contenteditable` + `marked` 双向转换的极简 WYSIWYG？但 Markdown 往返转换不完美（表格、代码块等）。
3. **铁则是否可破例**：若引入轻量 WYSIWYG 库（单文件 UMD build），是否算违反"无 bundler"铁则？

> 此项需单独深入讨论，结论可能推迟到 0.18+。但因其影响 0.17.6 渲染引擎增强的范围，需在 0.17.6 开工前给出方向性结论。

### 3.5 Markdown 渲染引擎增强（待定）

本子版本是第三组的共享基础，同时服务编辑器、便签和 AI 对话返回。

**A. 勾选块渲染修复（已查实根因）**

问题：共享 Markdown renderer（`frontend/js/shared/markdown.js`）不支持 `- [ ]` / `- [x]` 勾选块渲染。

根因已查实：renderer 使用 **marked**（已配置 `gfm: true`，GFM task list 解析本身是支持的）+ **DOMPurify**（HTML 净化）。问题出在 DOMPurify 的 `ALLOWED_TAGS` 白名单里**没有 `input` 标签**--GFM task list 渲染出来是 `<ul><li><input type="checkbox" checked>...`，`input` 被过滤掉了，所以勾选框不显示。

修复：DOMPurify `ALLOWED_TAGS` 加 `input`，`ALLOWED_ATTR` 加 `type`、`checked`、`disabled`。改动极小。

**B. 主窗口 AI 展示形态重设计（已定方向）**

**现状问题**（代码调查确认）：主窗口 AI 回答被**塞进结果列表的一条 `<li>` 里**，和"打开微信"这种应用结果共用同一套列表 UI，`frontend/index.html` 没有加载 marked/DOMPurify，渲染用 `textContent` + `white-space: pre-wrap` 保留换行。长回答、代码块、列表在最高频入口呈现为带原始 Markdown 符号的纯文本，体验割裂于对话窗口。

**定案：AI 回答时主窗口底部展开临时展示区**

主窗口是窄条形启动器 UI，不适合放长篇内容。当 AI 返回回答时，在主窗口底部展开一个临时展示区（而非塞进结果列表项），区域内用共享 `markdown.js` 渲染 Markdown。

**设计要点**：
- 展示区在结果列表下方展开，不挤压结果列表的可用空间（或 AI 回答时结果列表收起）。
- 渲染用共享 `markdown.js`（`frontend/index.html` 需加载 marked/DOMPurify vendor 脚本）。
- 展示区支持滚动，长回答不撑爆窗口高度。
- Esc 或失焦隐藏窗口时展示区一并收起；下次唤起重置。
- 权限确认卡片（§3.1 E）也在此区域展示，而非塞进结果列表。

**与结果列表的关系**：AI 流式回答期间，结果列表仍可显示搜索结果（用户可能想边看 AI 回答边操作结果项）；回答完成后展示区获得焦点，Enter 不再触发结果列表激活。

**C. WYSIWYG 方向性结论**

见 §3.4，需在此子版本开工前给出"推进 / 推迟 / 放弃"的方向性结论，以确定渲染引擎增强的范围。

### 3.9 OCR 优化方案（已定：方案 A，语言选择修复 + 诊断面板）

**现状**（代码调查确认）：0.11 接入 Windows OCR（WinRT `OcrEngine`），word 级识别。中文准确度差。经代码调查，**根因不是 WinRT 能力不足，而是当前代码没有正确选语言**：

- `backend_windows.rs:54` 用 `WinRtOcrEngine::TryCreateFromUserProfileLanguages()`，依赖**用户配置文件语言列表**（不是系统显示语言，不是已安装 OCR 包列表）。若用户配置文件里 `en-US` 排前（很多中文系统用户装了英文语言包），引擎选英文--**装了中文 OCR 包也用不上，中文一个字都识别不出来**。
- 代码从不调 `AvailableRecognizerLanguages()` 探测已安装的 OCR 语言包，也不调 `TryCreateFromLanguage()` 显式选语言。
- 无任何图片预处理（灰度化、二值化、放大、去噪）。唯一的图像操作是 `Convert(Bgra8)` 格式转换。
- `join_words_smart`（`ocr_engine.rs:166-208`）已解决 SDK 中文"每字夹空格"问题，CJK↔CJK 无空格拼接且有单测覆盖。**这块不是问题。**

**Windows OCR 语言包机制**（调研确认）：

OCR 语言包是独立的 Windows capability（`Language.OCR~~~zh-CN~0.0.1.0`），与界面语言（`Language.Basic`）、输入法、手写都分开。中文版 Windows 11 通常预装中文 OCR 包，但英文版 + 中文输入法**不预装**。安装方式：Windows 设置"语言和区域"添加中文语言并勾选 OCR，或 PowerShell `Add-WindowsCapability -Online -Name "Language.OCR~~~zh-CN~0.0.1.0"`。检测已安装：`OcrEngine::AvailableRecognizerLanguages`（WinRT 静态属性）。PowerToys Text Extractor（微软自家工具）也有同样的"中文 OCR 不工作"用户报告（GitHub #21234），根因相同。

**候选方案保留**（本版本只做 A，B/C/D 不做）：

| 方案 | 准确度 | 成本 | 体积影响 | 0.17.5 状态 |
|---|---|---|---|---|
| **A. 优化 WinRT OCR 用法** | 中（语言选择修复后预期显著提升） | 低 | 无 | **本版本做** |
| **B. PaddleOCR 本地化** | 高 | 高（推理引擎集成） | 大（模型 + ONNX/Paddle runtime） | **不做**，记录为候选；A 优化后仍不达标再评估 |
| **C. 在线 OCR API** | 高 | 中（API 集成） | 无 | **不做**；截图可能含敏感信息，与本地优先定位冲突 |
| **D. AI 多模态直接读图** | 高 | 中 | 无 | **不做**；划归 0.20（roadmap §7.3 CAP 闭环"OCR 内部直链"） |

> 注：原 §3.9 将方案 D 与 roadmap §7.3 混为一谈。roadmap §7.3 的"OCR 内部直链"是**架构修复**（Rust 内部把截图 bytes 交给 OCR capability，不经 LLM channel），不是 OCR 准确度优化，应归 0.20。

**定案：方案 A = 语言选择修复 + 诊断面板（不含图片预处理）**

不本版本做图片预处理的原因：先修复语言选择（根因），用诊断面板验证效果。若修复后中文识别仍不理想，再在后续迭代加预处理（放大小图、灰度化、Otsu 二值化）。符合"先出简单优化看是不是配置问题"的迭代策略。

**A. 语言选择修复（中文优先 + fallback）**

当前 `recognize_raw`（`backend_windows.rs:14-121`）每次调用都创建引擎（`TryCreateFromUserProfileLanguages`，行 54-55）。改为：

1. 调 `WinRtOcrEngine::AvailableRecognizerLanguages()` 获取设备已安装 OCR 语言列表
2. 按优先级匹配中文：`zh-Hans-CN` > `zh-Hans` > `zh-Hant-TW` > `zh-Hant` > 任意 `zh-*` 前缀
3. 命中则 `WinRtOcrEngine::TryCreateFromLanguage(&matched_lang)`
4. 未命中（设备无任何中文 OCR 包）则 fallback 到 `TryCreateFromUserProfileLanguages()`，并打 `warn!` 日志记录"无中文 OCR 语言包"

WinRT 中文引擎非排他--选了中文引擎仍能识别英文（WinRT OCR 引擎按语言模型优先匹配，混合文本也能处理），所以优先选中文不影响英文截图。

### 3.12 快捷键速查 -- 快捷键 tab 展示 chord 绑定（已定）

**问题**（代码调查确认）：应用内完全没有快捷键速查表。设置页"快捷键"tab 是**录制器**（改唤起键 + 调 tap 阈值，`settings.html:1502-1522`，3 行：唤起快捷键录制 + tap 阈值滑块 + grace period 滑块），不是速查表。用户无法在应用内查到 Alt+Q/A/C 等操作。

**chord 默认绑定**（代码调查确认，`chord/mod.rs:482-503` 注册 6 个 action）：

| Action | 默认键 | 语义 | 可改绑 | 标签 |
|---|---|---|---|---|
| `voice_input` | Space（Alt+Space） | Hold（硬锁，`mod.rs:458-460/154-156`） | 否 | 语音输入/唤起 |
| `chat` | Q（Alt+Q） | Tap | 是 | AI 对话 |
| `screenshot` | A（Alt+A） | Tap | 是 | 区域截图 |
| `clipboard_history` | C（Alt+C） | Tap | 是 | 剪贴板历史 |
| `edit` | E（Alt+E） | Tap | 否（无 binding 字段，默认键） | 编辑 |
| `sticky` | S（Alt+S） | Tap | 否（无 binding 字段，默认键） | 钉为便签 |

前 4 个有 `ChordBinding` 字段可用户改绑（`chord/mod.rs:93-104`），`edit`/`sticky` 只有注册默认键无 binding 字段。effective key 通过 `ChordBindings::effective_key(id, default_key)`（`mod.rs:133-138`）解析。

**定案：在快捷键 tab 展示当前 chord 绑定的快捷键，引导用户去 chord 页修改**

- 快捷键 tab 保留原有录制器功能，在下方新增"当前快捷键"展示区（cheatsheet 表格）。
- 展示区列出 6 个 chord action 的当前 effective key + 功能名 + 可改绑标记。
- 可改绑的行附"修改"链接，点击在 settings 窗口内直接切到 chord tab（`document.querySelector('.tab[data-tab="chord"]').click()`，不需要调 `open_settings_tab` 后端命令，因为已在 settings 窗口内）。
- 不可改绑的行（voice_input 硬锁、edit/sticky 默认键）不显示"修改"链接，标注"固定"。
- 不新建独立速查表面板，复用已有 tab 结构。

**实现方案**：

| # | 文件:行 | 改动 |
|---|---|---|
| 1 | `frontend/settings.html:1502-1522` | hotkey tab 下方加 `<div id="chord-cheatsheet">` 含表格 |
| 2 | `frontend/js/settings/tabs/hotkey.js:16` | `initHotkeyTab(cfg)` 从 `cfg.chord_bindings` 读 6 个 action 的 effective key（`binding.key` 非空用 `binding.key`，否则用默认键），渲染表格 |
| 3 | `frontend/css/views/settings/` | cheatsheet 表格样式 |
| 4 | `frontend/js/i18n/zh.js` + `en.js` | 加 `hotkey.cheatsheet.title` / `.editable` / `.locked` / `.modify` |
