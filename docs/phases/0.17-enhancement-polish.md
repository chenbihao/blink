## 二、背景与动机

### 2.1 为什么 0.17 做这件事

0.16 打通"感知→编辑→常驻"链路后，日常使用暴露四类问题：(1) 可靠性存量债——图片剪贴板、便签、chord 删除等边界 bug，自启链路命令行窗口泄漏，截图翻译 loading 竞态，AI 权限确认在主窗口断链；(2) 交互不完整——便签管理样式异常、编辑器 Markdown 渲染缺勾选块、主窗口 AI 回答纯文本展示；(3) 能力短板——OCR 准确度不足（根因是未正确选中文语言，非 WinRT 能力不足）、搜索缺少系统级快捷方式；(4) 产品体验基础设施缺失——无首次启动引导、无快捷键速查、托盘菜单缺项、设置页未分组。

### 2.2 明确"不是问题"的（避免误改）

| 项 | 结论 |
|---|---|
| DB 清空后文件不缩小 | **已查实为 bug**。SQLite `DELETE` 只标记空闲页不缩文件是正常的，但 Blink 增量清理路径全部不 VACUUM，只有"全部清空"按钮做了。详见 §3.1 C2 |
| 便签关闭后管理界面仍留存 | 0.16.8 "关闭只隐藏、删除才移除"是有意设计，但空便签留存不合理，§3.2 回收站方案重新设计此语义 |
| 剪贴板图片来源显示不准 | **已查实为 bug**。监听器 `foreground_title()` 只取窗口标题（常是文件夹名），且 blink 自己写剪贴板（截图/回贴/AI）时认不出是自写入；文件管理器复制图片时的 `CF_HDROP` 文件名信息被完全丢弃。详见 §3.14 |

## 三、核心设计 / 决策

### 3.1 存量问题修复策略（已定）

五个存量 bug 的修复结论：

- **A. 开机自启弹命令行窗口**：funasr-server 自启路径中 `netstat`/`taskkill` 调用未加 `CREATE_NO_WINDOW`。修复：`process.rs` 补 `no_window()`；MCP client 和 CLI recognizer 子进程补 `no_window_tokio()`。
- **B. 截图双"翻译中" loading**：`doTranslate` 同时激活 canvas loading 和 DOM loading 无互斥。修复：overlay loading 已激活时跳过 DOM loading，canvas loading 为主、DOM loading 降为 redo 路径 fallback。
- **C1. 清空剪贴板不清图片 + 清理边界修正**：`clipboard_images` 表无独立清理入口，`clear_cache_db` 误清用户数据。修复：新增 `clear_clipboard_images` command；`clear_cache_db` 只清 `performance_metrics` + `icon_cache`；启动时接通 `cleanup_old_images(7天)`。
- **C2. DB 不缩小**：增量清理路径全部只 DELETE 不 VACUUM。修复：新增 `vacuum_if_needed(pool, 0.2)` 启动时自动检测 + `optimize_storage` 存储页手动触发四库 VACUUM。不采用 `PRAGMA auto_vacuum`（需建表时设置且不还给 OS，不如定期 VACUUM 简单有效）。
- **D. chord 右键删除图片无效**：前端读 `actions[0]?.hitId` 获取待删除 id，但图片项 `actions[0]` 是 `RunAction`（无 `hitId`）；后端无 `delete_clipboard_image` 命令。修复：新增后端命令 + 前端按 `isImage` 分发。
- **E. 主窗口 AI 权限确认断链**：`showAiConfirm` 替换 AI 占位为确认卡片后不重置 `selected`。0.17.0 最小修复加 `selected = idx`；0.17.6 主窗口 AI 改走 ChatService 后旧路径（`PendingAiConfirmation`/`seq`/`confirm_ai_action`）全部删除，此修复随之移除。

**清理边界定案**（四库数据分类 + 清理铁则）：

| 库 | 表 | 数据性质 | 清理入口 |
|---|---|---|---|
| config.db | `config`（KV）/ `ai_permission_memory` | **配置类（不可清理）** | 无（铁则：禁止任何清理操作触碰 config.db；`ai_permission_memory` 仅"清除所有权限记忆"按钮） |
| history.db | `history` / `clipboard_history` / `sticky_notes` | 用户数据 | 各自 `clear_*`（有确认）；`sticky_notes` 无清理入口 |
| ai.db | `ai_tool_audit` | 审计日志 | `clear_ai_audit`（有确认） |
| ai.db | `conversations` / `messages` / `conversation_groups` / `memory_fts` | 用户数据 | 仅单删 |
| cache.db | `performance_metrics` / `icon_cache` | **缓存（可重建）** | `clear_cache_db` / `clear_perf_data` |
| cache.db | `clipboard_images` | **用户数据**（原误归缓存） | `clear_clipboard_images`（有确认，独立按钮） |

存储页清理操作按"缓存类 / 用户数据类 / 维护类（VACUUM）"三组重排。`cleanup_all_data`（一键清理）运行时禁用——该操作删整个 `%APPDATA%\blink`（含配置 + 全部用户数据），运行中执行会导致不可恢复状态，仅卸载前手动启用。

> **config.db 清理铁则**：任何"清理缓存"/"一键清理"操作不得触碰 config.db。`optimize_storage`（VACUUM）可对 config.db 执行（不删数据，只回收空闲页）。

### 3.2 便签状态流转设计 — 回收站方案（已定）

**问题**：0.16 便签模型中关闭=隐藏（visible=false）、删除=物理删除（不可恢复），导致空便签关闭后留存、管理界面堆积，"关闭"和"隐藏"语义混淆。

**定案：关闭=软删除进回收站 + 管理界面回收站 tab + 30 天自动清理**

| 操作 | 行为 | 数据 |
|---|---|---|
| 便签关闭按钮 | 软删除：`trashed=true` + `deleted_at=now`，窗口 hide | 保留，进回收站 |
| 管理界面"恢复" / "彻底删除" / "清空回收站" | `trashed=false` / 物理 DELETE / 批量物理 DELETE | 保留 / 永久 / 永久 |
| 启动后台清理 | `trashed=true` 且 `deleted_at` 超 30 天的物理 DELETE | 自动清理 |

要点：便签窗口去掉"删除"按钮，关闭即进回收站；`visible` 字段保留原语义（控制桌面窗口显示），与 `trashed` 正交；0.16.8 "关闭只隐藏"语义被回收站取代。**旧数据迁移**：`visible=false` 的旧便签直接 `DELETE`（0.16 未正式发版，无线上数据需保留），`visible=true` 迁移为 `trashed=false`。

### 3.3 便签管理界面重设计 + 便签交互修复（已定）

**代码调查纠正**（原问题清单有误，避免误改）：

1. "管理界面渲染斜线"根因**不是 italic**，是分数 DPI 下透明背景的 GPU 光栅化 tile seam（0.12.8 对话窗口已遇到并修复，有注释为证）。修复：全链路不透明背景 + 避免在便签/管理界面用 `opacity:0`+`transform` 创建合成层（用 `visibility:hidden` 替代）+ 中文文本容器补 `font-style: normal` 防御。
2. 便签页**根本没有自定义右键菜单**，只有原生浏览器右键菜单（需屏蔽）+ "更多"下拉菜单。修复：屏蔽原生右键 + 加轻量 CSS 弹层右键菜单（边缘检测定位，5 项：在编辑器中打开 / 改颜色子菜单 / 隐藏 / 删除）。
3. 便签页**完全没有**唤起管理入口（`showStickyManager` 零调用者）。修复："更多"菜单追加"便签管理"项。

**新建便签中心定位**：复用 `launcher_position`（跟随鼠标所在屏、工作区中心、DPI 感知），与主窗口唤起同一定位逻辑。

### 3.4 编辑器 Live Preview 方案（已定：Cherry Markdown 替换 marked）

**定案**：用 Cherry Markdown Stream 版替换 marked + DOMPurify + highlight.js。

**理由（踩坑）**：marked 无流式渲染 API（每 chunk 全量 `parse` + `innerHTML` 替换，长回答闪烁未闭合 MD 符号），且无 Live Preview 编辑能力。Cherry Stream 版专为 AI Chat 流式设计（自动补全未闭合 MD 片段），UMD 单文件 + 全局 `window.Cherry`，与现有 vendor 模式零摩擦。gzip ~475KB，一个版本覆盖只读流式渲染 + Live Preview 编辑 + 纯预览。

**接口不变**：`renderMarkdown(text)` / `initMarkdown()` 签名不变，6 个现有调用点不动。新增 `renderMarkdownStream(container)` 和 `createMarkdownEditor(element, opts)`。Cherry Stream 版无 Editor/Toolbar 组件，`createMarkdownEditor` 用自定义 textarea + Cherry Stream 预览 + 自定义工具栏实现 Live Preview。WYSIWYG 推迟 0.18+。

### 3.5 主窗口 AI 架构统一（已定）

**定案**：主窗口 AI 从 `SearchService::trigger_ai` 切换到 `ChatService::prompt`，与对话窗口统一调度模型。

**理由**：原主窗口 AI 走 `SearchService`（外部调度 + 单槽 `PendingAiConfirmation` + seq 匹配），对话窗口走 `ChatService`（内部调度 + `PendingConfirms` + confirm_id + trusted），两套独立调度导致主窗口 AI 无法多轮追问、无权限记忆、流式渲染重复实现。统一后主窗口使用临时对话（`EphemeralConversationMemory`，不持久化），对话窗口使用持久化对话（`SqliteConversationMemory`）。

**关键设计**：

- **`EphemeralConversationMemory`**：进程内 `HashMap` + `RwLock`，实现 rig `ConversationMemory` trait。不压缩、不 FTS 召回。
- **`ChatService` 扩展**：加 `ConversationKind`（`Persistent`/`Ephemeral`）枚举 + `target_window` 参数，按 kind 选 memory，Agent 缓存 key 追加 kind。
- **事件通道参数化**：`CHAT_STREAM` / `CHAT_CONFIRM_ACTION` 统一用于主窗口 + 对话窗口，按 `target_window` 定向 emit。旧 `AI_STREAM` / `AI_CONFIRM_ACTION` 删除。
- **SearchService AI 路径删除**：`PendingAiConfirmation` / `trigger_ai` / `confirm_ai_action` / `emit_ai_*` 全部删除。保留 `make_ai_suggestion` / `maybe_ai_suggestion`（Ghost 建议仍需要）。
- **watchdog AI 标志**：`MAIN_WINDOW_AI_ACTIVE: AtomicBool`，AiMode 下 watchdog 跳过失焦隐藏。
- **前端模式切换**：`#search-mode`/`#ai-mode` 独立容器 + 独立输入框，`display:none/flex` 切换。`ai-mode.js` 状态机：Tab on AI Ghost 进入 AiMode，ESC 退出（abort + 清空 + 回 SearchMode），失焦不隐藏窗口，Alt+Q 提升为持久对话。多轮追问：当前轮收进 `.ai-round-summary` 折叠条。
- **共用渲染组件**：`message-render.js` 抽取 `renderToolStatus`/`renderConfirmCard`/`createThrottledRenderer`，对话窗口和主窗口共用。
- **Chord-Q 提升**（0.17.6a）：`promote_ephemeral_conversation` command，导出临时消息 → 写 `SqliteConversationMemory` → 清空临时 → 打开对话窗口 → 回 SearchMode。
- **单活跃请求约束**：`RequestTracker` 全局单槽，主窗口 AI 运行时对话窗口发消息得到 `AlreadyActive`，前端提示"AI 正在 {active_window} 中处理"。

### 3.9 OCR 优化方案（已定：方案 A，语言选择修复 + 诊断面板）

**根因（踩坑）**：`backend_windows.rs` 用 `TryCreateFromUserProfileLanguages()` 选语言，依赖用户配置文件语言列表而非已安装 OCR 包列表。若用户配置文件 `en-US` 排前，引擎选英文——装了中文 OCR 包也用不上，中文一个字都识别不出。`join_words_smart` 智能拼接已解决 SDK 中文"每字夹空格"问题，不是瓶颈。

**定案：方案 A = 语言选择修复 + 诊断面板**

- **语言选择修复**：`select_chinese_preferred_engine()` 先调 `AvailableRecognizerLanguages()` 按优先级匹配中文（`zh-Hans-CN` > `zh-Hans` > `zh-Hant-TW` > `zh-Hant` > 任意 `zh-*`），命中则 `TryCreateFromLanguage`，未命中 fallback 到 `TryCreateFromUserProfileLanguages()` + `warn!`。WinRT 中文引擎非排他，选了中文仍能识别英文。
- **诊断面板**：截图 overlay 新增 `ocrDebug` 开关（持久化到 SQLite），开启后工具栏显示诊断按钮，面板展示已安装语言列表、中文包状态、引擎语言、选区 OCR 测试，无中文包时显示安装引导。

### 3.10 AI 权限记忆机制（已定：跨会话持久化，双层 trusted 设计）

**定案**：用户确认权限后，在配置天数内跨会话不再重复询问。记忆粒度 = `tool_name`（内置 dangerous action 全无参，sensitive capability 是只读查询，不存在"确认了 A 代表想自动 B"的问题；插件 tool_name 含插件前缀，粒度已够）。

**双层 trusted 设计**：

- **会话级**：`HashSet<(conversation_id, tool_name)>`（进程内，重启即失）
- **持久化层**：`blink_config.db` 新表 `ai_permission_memory`（`tool_name` PK + `trusted_at` + `expires_at`）
- `is_trusted` 检查顺序：会话级命中 → 跳过 DB；未命中 → 查 DB → 命中且未过期 → 加入会话级；未命中或过期 → 返回 false
- `trust()` 同时写会话级 + DB（若 `memory_enabled`）

**过期策略**：过期后重新弹确认卡片（不静默失效）；查询时判断 + 删除过期行；启动时批量清理。

**配置**：`AiPermissionConfig`（`memory_enabled` 默认 true + `memory_days` 默认 7 天），UI 在 ai-chat tab。`memory_enabled = false` 时不查 DB，DB 数据保留。清理时机：删对话清会话级 / 手动清除 / 过期自动 / 关闭开关不删数据 / 卸载插件按 prefix 清理。

### 3.14 剪贴板来源信息增强（已定）

#### 问题

剪贴板历史项的 `source_app` 字段（展示在图片项标题 `图片 WxH ({来源})` 括号里）有三个独立缺陷：

1. **自写入不可识别**：blink 自己写剪贴板有 4 个入口（`screenshot_copy` / `screenshot_copy_region` / `copy_clipboard_image` 历史回贴 / `write_clipboard` Capability），都触发 `WM_CLIPBOARDUPDATE` → 监听器无脑按前台窗口标题记来源。截图复制时前台可能是 overlay 窗口或已切回原 app，记成别的应用；历史回贴更会因 sha256「删旧留新」**覆盖掉原来的真实来源**。
2. **来源用窗口标题而非进程名**：监听器自带的 `foreground_title()` 只调 `GetWindowTextW`，取的是窗口标题（资源管理器复制图片时标题常是文件夹名"图片"，看着像来源是个叫"图片"的应用）。项目里已有完整基础设施 `crate::infra::platform::context::foreground_app()`（返回 `ForegroundAppInfo { process_name, window_title, ... }`），但监听器没用它。
3. **文件名信息被丢弃**：从文件管理器复制图片文件时，Windows 剪贴板同时含 `CF_HDROP`（文件路径列表）+ `CF_DIB`（位图），监听器只读 `CF_DIB`，文件名/路径从未被读取（全项目搜 `CF_HDROP / DragQueryFile` 零命中）。

#### 定案

三件事合并进 0.17.9，因为都改监听器来源采集链路、共用同一处 `source_app` 计算逻辑：

**A. 自写入识别 —— 进程内标记机制（内聚在 `clipboard` 模块）**

- **定案**：`infra/platform/clipboard/mod.rs` 新增进程级 `Mutex<Option<SelfWriteMark>>` + TTL（500ms 兜底）。
- `write_*` 函数加 `label` + `skip_persist` 参数，内部先 `mark_self_write` 再写剪贴板（拆「打标外壳 + 不打标内核」避免 `write_png → write_bgra` 转调重复打标）。
- 监听器 `on_clipboard_change()` 开头 `take_self_write()`：命中则 `source_app` 用标签；`skip_persist=true`（历史回贴场景）时跳过入库但保留 `notify_change`（AwarenessSnapshot 刷新）。
- **标签存语义 key**（`blink:screenshot` / `blink:repost` / `blink:ai`），`clipboard_engine.rs` 新增 `resolve_source_desc()` 查映射表转中英文文案，**不改 DB schema、不改前端契约**。
- **理由**：标记机制完全内聚在 infra 层 `clipboard` 模块内（写入函数 + 监听器同模块），不引入跨层依赖；调用方只多传一个 `&str`，4 个入口无人会漏打标。

**B. `source_app` 改用 process_name**

- **定案**：监听器删掉自带的 `foreground_title()`，改调 `crate::infra::platform::context::foreground_app()` 拿 `process_name`（如 `chrome.exe` / `explorer.exe`），`source_app` 存进程名而非窗口标题。
- **理由**：进程名稳定（不随用户打开哪个文件夹/标签页变化），且已有现成基础设施（注释明确写着「供 clipboard listener 用」但一直没接上）。
- **注意 `collect_foreground_app()` 的自检**：该函数内部 `pid == self_pid` 时返回 None（`context/windows.rs:68`）。自写入场景下前台可能还是 blink 自己 → `foreground_app()` 返回 None → `source_app` 为 None，但这恰好被 A 的自写入标记覆盖（标签优先），无冲突。

**C. 读 `CF_HDROP` 存源文件名**

- **定案**：监听器图片分支解码 DIB 前，先尝试 `IsClipboardFormatAvailable(CF_HDROP)`，命中则 `DragQueryFileW` 取首个文件路径，提取文件名存入新字段 `source_path`（`Option<String>`）。
- **schema 迁移**：`clipboard_images` 表 `ALTER TABLE ADD COLUMN source_path TEXT`；`ClipboardImage` / `ClipboardImageMeta` 加 `source_path: Option<String>` 字段。
- **展示**：`clipboard_engine.rs::to_image_search_item` 标题拼接改为「文件名优先，有则 `文件名 · 应用名`，无则仅应用名」。

#### 展示形态

```
图片 1920x1080 (photo.jpg · explorer.exe)   ← 文件管理器复制（有 HDROP）
图片 1920x1080 (chrome.exe)                  ← 浏览器复制（仅 DIB，无文件名）
图片 1920x1080 (截图)                        ← 自写入（blink:screenshot → i18n）
图片 1920x1080 (未知)                        ← 拿不到任何来源
```

#### 范围边界

- ❌ 不改前端：source_app 在后端就被解析成文案拼进 title，前端契约不变。
- ❌ 不给文本历史加 source_app 展示：文本项 `format_subtitle` 目前不含 source_app，是独立改进，本次不动。
- ❌ 不注册自定义剪贴板格式（方案 B）：进程内标记已够。
- ❌ 不做 i18n 表抽取：`resolve_source_desc` 内联 if/else 即可，与 `clipboard_engine.rs` 现有 `is_zh` 模式一致。
