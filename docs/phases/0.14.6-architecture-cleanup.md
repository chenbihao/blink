# Blink 0.14.6 — 架构清理与工程债收敛（分层剥离 + Schema/Error/事件收敛 + 文件拆分）

> **范围**：① 分层清理——配置域下沉 + domain 去 tauri 依赖 + Win32 收进 infra + 拆 commands.rs 巨石 + ② 工程债收敛——ActionSchema/CapabilitySchema 合并 + 错误处理统一（thiserror + CapabilityError 走 serde）+ 事件名常量化 + invoke 路径收敛 + ③ 文件拆分——前端臃肿文件（chord-screenshot.js / ai.js / chat.css）按模块拆分。
>
> **状态**：📋 规划中。
>
> **动机**：0.14 能力协议重构清掉了能力层的概念债务（投影分裂）。0.14.6 趁热打铁清剩下的——审查发现骨架健康，但有一批分层违例和积累的工程债。三档问题同源：领域逻辑没从框架/平台/应用层干净剥离。0.14.6 一次性收敛。
>
> **前置**：0.14 完成（能力协议重构——Capability/Action 边界钉死、投影引擎收敛）。
>
> **原则**：**不改变对外行为**——纯内部重构，用户无感知。所有改动以"消除分层违例 + 消除真冗余 + 提升可维护性"为目标，不引入新功能。前端继续保持无 bundler 纯静态约束。
>
> **子版本切分说明**：三档七项（§2.1~§2.4 / §3.1~§3.4 / §4）均归在单一子版本 **0.14.6** 下推进，不再细分为 0.14.6.0~0.14.6.7——各项独立验收、独立提交，但共享一个子版本号。里程碑表见 §五。

## 一、背景与动机

### 1.1 为什么 0.14.6 做这件事

0.14 收尾时做了一次全面架构审查（trait 抽象 / 分层泄漏 / 死代码 / 前端 / 错误处理），结论是**架构骨架健康**（四域架构、Capability/Action 边界、Provider/Agent 类型墙、Registry 体系都经核实是合理设计），但发现一批分层违例和工程债。这些不是"推倒重来"级别，但违背了 AGENTS.md §6「持续收敛，不随便堆砌坏味道」的原则。0.14.6 作为 0.14 的延续子版本，趁热打铁收敛这批债（而非另立大版本 0.15，保留 0.15 号段给后续大主题）。

三档问题分优先级：

| 档 | 性质 | 严重度 |
|---|---|---|
| **第一档：分层违例** | domain 反向依赖 app、直接 use tauri、Win32 泄漏、commands 巨石 | 🔴 架构债 |
| **第二档：工程债** | Schema 真冗余、错误处理断层、事件名散落 | 🟡 可维护性 |
| **第三档：文件臃肿** | 前端几个大文件、inline style | 🟢 按需 |

**三档同源**：都是"领域逻辑没从框架/平台/应用层干净剥离"。0.14.6 一次性收敛。

### 1.2 明确"不是问题"的（审查澄清，避免误改）

审查中几个"看起来像冗余"但经核实是合理设计的，0.14.6 **不动**：

- **Action vs Capability 两个 trait**——语义分界清晰（副作用 vs 纯数据），0.13.7 已收敛过重叠区
- **rig_provider vs agent_provider**——刻意的类型墙（主窗口编译期拿不到 Agent loop），是设计铁则
- **SearchEngine trait**——独立领域（召回融合），不走 Registry 是对的
- **ChordAction**——不是第三个平行 trait，是 Action 的 supertrait
- **Registry 不泛型统一**——只有 2 个同态实例时 ROI 一般，等第 4 个再说

## 二、第一档：分层清理（架构债）

### 2.1 配置域下沉

**问题**：配置类型（`AIConfig`、`HotkeyConfig`、`ContextConfig`、`ClipboardConfig` 等）定义在 `app/`，被 `domain/` 反向依赖（8 处 `use crate::app::ai_config`），`infra/` 也反向依赖 `app::config`。全项目最系统性的分层违例。

**证据**（grep 于 0.14.5 后）：
- `domain/ai/` 多处 `app::ai_config`（agent_provider.rs:40 / chat_service.rs:27 / factory.rs:29 / gating.rs:35 / provider.rs:32 / registry.rs:27 / rig_provider.rs:56，另 factory.rs:325 / registry.rs:360 在测试 mod 内）
- `domain/search/` 4 处 `app::config`（calc_engine.rs:9 / file_engine.rs:17 / start_menu_engine.rs:19 / service.rs:17）
- `infra/platform/context/mod.rs:26`、`infra/platform/hotkey/mod.rs:28` 反向依赖 `app::config`
- 分片物理散落：config.rs(9个) + ai_config.rs + stt_config.rs + infra/clipboard.rs + platform/screenshot.rs

**方案**：建独立的 config 域（`src/domain/config/`），把所有配置分片 struct 迁入。`AppConfig` 门面、`ConfigKey` trait、各分片统一归此域。app/infra/domain 都依赖 config 域，方向正确。

**收益**：一次性消除 domain→app + infra→app 反向依赖 + 分片散落两个问题。

### 2.2 domain 层去 tauri 依赖

**问题**：domain 应框架无关，但多个文件直接 `use tauri::`，通过 `AppHandle` emit 事件 / 取 managed state。

**证据**（grep 于 0.14.5 后）：
- `domain/ai/chat_service.rs:36` `use tauri::Emitter`（另 :944 在测试 mod 内）
- `domain/ai/tool_adapter.rs:57` `use tauri::Emitter`
- `domain/chord/mod.rs:26` `use tauri::Emitter`
- `domain/search/service.rs:15` `use tauri::{AppHandle, Emitter, Manager}`
- `domain/execution/builtin.rs:14` `use tauri::Manager`
- `domain/plugin/mod.rs:15`、`plugin/capability.rs:21`
- 3 个 capability builtin（search_apps.rs:14 / search_clipboard_history.rs:21 / search_files.rs:15）

**方案**：domain 发领域事件（定义自己的事件 trait/enum），app 层做 Tauri 桥接（订阅领域事件 → `app_handle.emit()`）。domain 取 managed state 改为依赖注入（构造时传入需要的句柄接口，而非运行时 `app_handle.state::<T>()`）。

**注意**：这是本档最大的改动，涉及面广。建议分步：先建领域事件抽象，逐个 domain 子模块迁移，最后彻底去掉 domain 对 tauri 的直接依赖。

### 2.3 Win32 调用收进 infra/platform/

**问题**：`infra/platform/` 有完整的 `mod.rs`(抽象) + `windows.rs`(实现) 范式，但部分 domain 绕过抽象直接 `use windows::`。

**证据**：
- `domain/search/icon.rs:15-23` —— SHGetFileInfo / 图标抽取全写在 domain（整个文件本质属 infra）
- `domain/search/windows.rs:13-17` —— Shell API（PKEY_AppUserModel_ID / SHCreateItemFromParsingName）
- `domain/execution/builtin.rs:106` —— `LockWorkStation` 锁屏直接调 Win32
- `domain/capability/builtins/ocr_engine.rs:297-299` —— WinRT OCR

**方案**：把这些 Win32 调用迁入 `infra/platform/` 对应子模块（icon 抽取 / shell 解析 / OCR backend），domain 只调 trait。`search/icon.rs` 和 `search/windows.rs` 整体迁移到 infra。

### 2.4 拆 commands.rs 巨石

**问题**：`src/app/commands.rs` **6553 行 / 174 个 `#[tauri::command]`** 平铺在一个文件，无分区注释，最大可维护性风险点。

**方案**：按域拆分到 `src/app/commands/` 子目录：
- `commands/search.rs`（搜索相关）
- `commands/clipboard.rs`（剪贴板）
- `commands/ai.rs`（AI / chat）
- `commands/stt.rs`（语音）
- `commands/plugin.rs`（插件）
- `commands/mcp.rs`（MCP）
- `commands/config.rs`（配置）
- `commands/diagnostic.rs`（诊断/日志/数据目录）
- `commands/mod.rs`（re-export + 统一 `generate_handler!` 注册）

`main.rs` 的 `generate_handler![...]` 改为从各子模块聚合。

## 三、第二档：工程债收敛

### 3.1 Schema 合并（ActionSchema + CapabilitySchema → ToolSchema）

**问题**：两个 Schema 结构几乎一致，`to_rig_tool()` **逐字完全相同**，`empty()` 几乎相同。Capability 已复用 `DangerClass`，schema 却分两份——自相矛盾。

**证据**：
- `execution/schema.rs:52-59` 和 `capability/schema.rs:65-72` 的 `to_rig_tool()` 逐字一致
- 两个 `empty()` 构造器几乎逐行相同
- Capability 已复用 `execution::DangerClass`（capability/mod.rs:71 注释"保持单一安全枚举"）

**方案**：抽 `ToolSchema { name, description, parameters }` 公共基（唯一的 `to_rig_tool()`，rig 触点从 2 处收敛到 1 处）：
- `ActionSchema = ToolSchema`（alias 或薄包装）
- `CapabilitySchema { base: ToolSchema, sensitive: bool }`（包装 + 扩展）
- 与 DangerClass 复用策略对齐

### 3.2 错误处理统一

**问题**：10+ 种 Error 全手写 `Display` + 空 `impl Error`（thiserror 在依赖树却没用）；跨类型 `From` 几乎空白；command 层 `Result<_,String>` 把 `CapabilityError.kind` 这种结构化字段拍平，前端拿不到。

**证据**：
- `Cargo.toml:45-46` thiserror 已声明依赖但未启用（注释说给 SSE transport，实际 SSE 也是手写 From）
- 7 处 `impl std::error::Error for X {}` 手写样板（chat_service / provider / tool_adapter / capability::error / execution::mod / mcp::config / stt::mod）
- 跨类型 `From` 仅 4 个（AIError→ChatError + SSE 3个），ExecError↔CapabilityError 零转换
- command 层 134 个 `Result<_,String>`，靠散落的 `.map_err(|e| e.to_string())` 拍平
- `CapabilityError` 自己设计了 `{kind, detail}` 可序列化模型（error.rs:16-17），却在 IPC 边界被 `to_string()` 抹平——设计与落地脱节

**方案**：
- 启用 thiserror（依赖已在树），用 `#[derive(thiserror::Error)]` 消除手写样板
- 补关键跨类型 `From`（CapabilityError ↔ ExecError 等）
- command 层错误改走 serde 序列化（保留 `kind` 字段），前端拿到结构化错误做分类展示，而非拍平的中文字符串

### 3.3 事件名常量化

**问题**：24 种 `blink://*` 事件前后端各自硬编码字面量，`config-changed` 后端 emit 15 次，无常量无校验，拼错无编译期保护。

**方案**：建一个前后端共享的事件名常量清单（Rust 常量 + 前端 JS 常量模块）。可考虑用 codegen 从 Rust 常量生成前端常量，消除手动同步。

### 3.4 invoke 路径收敛

**问题**：invoke 有两条 import 路径（`api.js` re-export + `tauri.js`），3 处绕过桥接直接戳 `window.__TAURI__`。

**证据**：`chat/ipc.js:161`（`window.__TAURI__?.dialog?.save`）/ `chat/main.js:1263`（`window.__TAURI__?.window?.getCurrentWindow`）/ `contextmenu-popup.html:13`（`window.__TAURI__`）各自重复 `window.__TAURI__` 兼容逻辑。

**方案**：收敛为单一 import 来源（`tauri.js`），清除 3 处 `__TAURI__` 绕过。
