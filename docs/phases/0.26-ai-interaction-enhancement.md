## 二、背景与动机

### 2.1 为什么 0.26 做这件事

- **提示词是散落的**：system prompt 集中在 `ai/prompt.rs`，但标题生成、编辑器整理、摘要 preamble 分散三处；用户没有任何可保存/复用常用提示词的入口。提示词库 + 编辑器预设 + /prompt 命令三件套把提示词变成资产。
- **命令入口缺失**：roadmap §3.3「Agent 交互入口与能力可发现性」立项条件已满足——现状仅 /skill 一种硬编码前缀匹配（无键盘导航），压缩入口埋在 80% 告警条里。统一斜杠命令注册表是三处功能（/compact、/prompt、/mcp）的公共载体。
- **输入输出单一**：对话只能进文本和音频附件；文件要靠 AI 自己调 read_text_file（涉及敏感能力确认摩擦），图片完全进不了对话。rig 0.43 多模态 UserContent + 四 provider wire 已支持 image，是补齐时机。
- **地基缺口**：文件选中感知（桌面/资源管理器单选多选）是后续一切文件操作的入口；`_global_proxy` 配置"本体与所有插件共用"的承诺与实现不符（AI 链路恰恰吃不到）；更新检查 api.github.com 无镜像降级。

### 2.2 明确"不是问题"的（调研澄清，避免误改）

- **rig 记忆 trait 不集成是对的**：rig 0.43 的 `Compactor`/`DemotionHook`/`MessageFilter` 只是 trait 定义，agent runtime 只派发 Load/Append/Clear，配套 `rig-memory` crate 不存在（registry 与依赖中均无）；blink 的水位 + token 裁剪 + FTS5 归档 + 摘要注入体系（`ai/memory.rs`）比这些钩子更强且带 40 个行为测试。**不要"补课"实现 rig 记忆 trait**——迁移会丢异步归档与水位事务性，还引入无运行时契约保护的耦合（0.42→0.43 该 trait 已改过签名）。
- **音频附件"仅本轮注入、不落库"是刻意设计**（0.23.12）：文本/图片附件沿用同一哲学，历史只落展示徽标（文件名/图片占位），防止每轮重放 token 预算失真与非 vision 模型持续 400。
- **截图 SESSION 不适合做 @ 面板素材**：截图像素 Session 在 overlay 关闭即清空（`screenshot/mod.rs` 无 TTL、显式 end）；"刚截的图"的持久引用实际是剪贴板图片历史条目（截图写剪贴板时 `ClipboardWriteSource::Screenshot` 自动入库）。不要给 SESSION 加生命周期。
- **OCR 前端链路不需要动**：detail 参数按调用方分流（LLM 默认瘦、前端 Tauri command 显式 full），`registry`/`tool_adapter`/MCP 投影全部透传。
- **本地引擎下载已有完整镜像降级**（HF→hf-mirror、GitHub→ghfast/gh-proxy/ghproxy、python/node→华为云，`utils/mirrors.rs` 统一分派），0.26.4 只补代理与更新检查，不动镜像链。

## 三、核心设计 / 决策

### 3.1 OpenAICompatible 路由修复 —— 显式 `Route::Chat`（已定，待实测核验）

**定案**：`build_openai_client` 显式 `.with_route(openai::Route::Chat)`；若核验证伪（实际已走 /chat/completions）则只补注释与测试锁定。
**理由**：rig 0.43 `OpenAIConfig::new` 挂 OPENAI 方言，其 `completion_route` 默认 `Route::Responses`（`wire/dialects.rs:29-40`），blink factory 无 route 覆盖（`ai/factory.rs:148-151`）——按代码读，OpenAICompatible 请求会打到 `{base_url}/responses`，而 factory 注释与前端预设都声称"所有走 /v1/chat/completions 的端点"。DeepSeek/硅基流动等网关无 /responses 端点。与 factory.rs:200 注释矛盾，疑点成立但需实测（用户侧第三方网关是否一直正常待确认——可能多数主用 *-anthropic 端点掩盖了问题）。核验手段：0.21.16 的 `http_log` trace 级 wire 日志，对一个无 /responses 的网关发一次请求。修复是 `openai::Route`（已导出）一行级。

### 3.2 文件选中感知 —— Shell COM 主路，不做 Ctrl+C 兜底（已定）

**定案**：`IShellWindows` + `IShellFolderViewDual::SelectedItems()`（完整路径 + 原生多选 + Explorer/桌面双覆盖，桌面走 GetShellWindow→DefView 分支）；失败优雅降级为无选中。否决模拟 Ctrl+C 读 CF_HDROP 兜底。
**理由**：Ctrl+C 方案要动用户剪贴板（必须可靠保存恢复，失败丢数据）、时序敏感、且对 builtin 插件无效。Shell COM 的 COM MTA 约范在 `platform/uia.rs` 有整套模板，`Win32_UI_Shell` feature 已开，无新依赖。挂接点：invoke 链 show 前判前台进程 `explorer.exe`（复用 `context::foreground_app()`；桌面 Progman/WorkerW 用 `GetClassNameW` 区分）→ show 后异步抓取 → 注入 awareness。**「发往 AI 对话」建议不做 prefill 过渡版**，等 0.26.9 结构化附件一次做对（用户拍板：避免 read_text_file 敏感确认摩擦与权限问题）。

### 3.3 附件注入哲学 —— 仅本轮注入 + 历史徽标（已定）

文本与图片附件同音频先例：`attachment_context_block` 模式扩展，ref/全文只进本轮模型输入，`persist_user_message` 只落展示名徽标。文本附件护栏：单文件字节 ≤256KB 且估算 token ≤4000（`estimate_text_tokens`），软超截断到 2000 token 并附「可用 read_text_file(path, range) 续读」提示——截断+分页语义与 read_text_file 现有行为一致，不做拒绝式。

### 3.4 vision 能力标记 —— ModelCapability 加变体 + 保守默认 + 不做摘图自愈（已定）

**定案**：`ModelCapability` 加 `Vision` 变体（复用现成 `ModelEntry.capabilities: Vec<ModelCapability>`，default `[Chat]` 即天然保守）；`cargo xtask models` 从 LiteLLM 源带出 `supports_vision` 做推荐预填（复刻 context_window 的"预填不覆盖"铁则）；模型编辑 UI 加复选框。误配（标记了 vision 但模型不支持）→ 服务端 400 → 现有 `map_rig_error`/`diagnose_status` → Error chunk，前端提示；**不做"摘图重试"自动自愈**（各家 400 文案不可结构化解析，与 thinking effort 400 自愈的前提不同）。
**理由**：thinking 先例的发送侧哲学是"默认 omit 绝不出 400"，vision 同样默认不发；客户端无法预知服务端能力，目录预填 + 用户标记 + 友好报错是现实边界。

### 3.5 代理走显式 client 工厂，不走进程环境变量（已定）

**定案**：infra 新增 `net` 模块（`OnceLock<RwLock<Option<(http,https)>>>` 共享 ProxyState + `proxied_client(timeout)` builder，照 `diagnostic.rs:311-322` 的 Proxy::all + warn 回退模式），app 启动与配置变更时 push（复刻 `SENSITIVE_APPS` 注入先例）；替换全部外部主机裸 client 构建点；回环链路（Everything 探测、本地引擎 health/stop/lease）**不接代理**。
**理由**：否决 env 路线——Rust 2024 `set_var` 引入 unsafe 面、reqwest 默认系统代理不含 localhost 豁免会截胡回环链路、长生命周期 client 不随 env 重建热更新语义更差。热更新语义显式化：一次性构建点下次请求生效；AI 走 `registry.reload`（Agent 缓存自然重建）；MCP 需重连；插件保持现状（杀进程重启生效）。顺手修正两处失实注释（`main.rs:432` 陈旧 env 注释、`plugin/process.rs:641` "遵循全局代理"与实现不符）。

### 3.6 更新检查降级 —— 分层降级而非换 latest.json 主链（已定）

**定案**：check_update 主链保持 api.github.com + 显式代理（多版本更新日志 updates[] 依赖 releases 列表，latest.json 的 notes 恒为空不能承接）；直连与代理全失败后回退拉 latest.json（走现成 `github_proxy_candidates` 镜像链），降级语义=只判版本有无更新，响应加 `degraded` 标记，前端 notes 区显示不可用文案。
**理由**：ghfast/gh-proxy 三家是 github.com 文件链代理，对 api.github.com 支持未经验证；latest.json 的 releases/latest/download 形态是 `mirrors.rs:139-144` 明确支持并有测试锁定的。

### 3.7 提示词库 —— SQLite 独立表 + scope + 内置条目不可删（已定）

`prompt_library` 表入 `blink_ai.db`（与 conversations 同库，照 conversation_groups 建表惯例）：`id/name/content/scope(chat|editor)/builtin/sort_order/created_at/updated_at`。内置条目（整理/翻译/总结等）`builtin=true` 不可删可改排序；用户自建任意。设置页新 tab 走 `mcp.js` 列表 CRUD 模式。不用 config KV（需要行级元数据与条目级增删）。

### 3.8 /compact 复用现有摘要体系，不引入 rig 记忆 trait（已定）

现有 `compress_context_now`（80% 告警条按钮）已覆盖 80% 基础；/compact 补三小块：压缩边界 `force_boundary` 覆盖（当前只压超限段→全量压保留最近几条，下游 `compute_summary_range`/水位推进原生支持任意区间）、`summary_enabled=false` 时显式命令 bypass、两个前置错误态（Agent 未缓存/生成中）友好回显。语义对齐成熟产品：压缩全历史、DB 原文不删（水位机制天然保证）。

### 3.9 编辑器预设 —— 范围 × 预设两维，三内置 + 库自定义（已定，product.md 决策升级）

整理范围（选中/本次听写）与整理预设正交：内置「整理」（现有指令，含纠错/标点/分段/缩口水词）、「精简」、「中英互译」三档 + 提示词库 scope=editor 自定义预设。`StartEditorTransformRequest` 加可选 `preset` 字段（serde default 向后兼容）。product.md §2.9 原「不建立其他改写预设或自定义指令」决策同步升级（已获用户确认）。

### 3.10 AI 生图移出本版（已定）

语言大模型生态对生图端点覆盖差（DeepSeek/Anthropic 无生图；rig image_generation 仅 OpenAI 系/Gemini/Venice，硅基流动需 additional_params 方言），收益配不上集成面。转 roadmap 条件候选：等"多类型 API 配置"（生图/STT/TTS 独立端点配置）立项后再做。
