# Blink 0.18.8 - 截图多屏 DPI 收敛（Screenshot Multi-Monitor DPI Convergence）

> **范围**：收敛截图 overlay 的多屏混合 DPI 坐标处理--修 `build_displays_json` 单一 DPI 折算导致的副屏几何失真、`pin.html` 拖拽跨屏 dpr 切换跳变；前端散落 `devicePixelRatio` 收口到几何模块；剪贴板钉图居中改光标屏/虚拟屏。
>
> **状态**：📋 规划中。
>
> **动机**：多屏混合 DPI（如 2K 27寸 100% + 3.6K 16寸 200%）下，截图 overlay 用"窗口级单一 dpr"折算所有屏的几何，副屏 CSS 矩形失真，导致窗口/控件预选区虚线框、桌面边界高亮、工具栏 clamp、选区->pin 坐标整体偏移。`pin.html` 拖拽靠前端 `e.screenX * dpr` 累加物理坐标，跨屏 dpr 变化时 `imgScreenX/Y` 不重标定而跳变。0.18.x 截图功能（0.18.2 控件吸附、0.18.3 便签、0.18.6 命令执行）已趋稳，正是收尾收敛坐标/DPI 债务的时机。
>
> **前置**：0.15（截图重设计、`ss-selection-geometry.js`、pin 图）；0.18.2（控件吸附，复用 `ss-control-hints.js` 的 `rectScreenToCss` 路径）。动核心前读 `spec-architecture.md`、`spec-frontend.md`（CSS 七层 / 无 bundler）、`spec-backend.md`（日志分级）。
>
> **原则**：不改变同 DPI 多屏下的现有正确行为（零回归）；坐标真源继续以 Rust Win32 物理像素为准，前端只做 Rust 注入数据的 CSS 折算消费；不引入新依赖；不动 0.18.7 输入状态机范围。

## 二、背景与动机

### 2.1 为什么 0.18.8 做这件事

**触发**：用户反馈"2K 27寸 + 3.6K 16寸"双屏下截图预选区可能有问题。排查确认这是**原理性取舍的代价**，不是手滑 bug。

**根因链**：

截图 overlay 是一个横跨所有显示器的单一全屏窗口。Windows 给这个窗口指派**一个** DPI（由窗口主体所在屏决定，通常主屏）。当前实现：

1. Rust `build_displays_json`（`windows.rs:1754`）把**每块屏**的物理几何都除以**同一个** `overlay_dpi/96` 注入前端 `window.__blinkScreenMeta.displays`；
2. 前端 `ss-selection-geometry.js` 全程用**同一个** `window.devicePixelRatio`（= overlay 窗口 dpr）做物理↔CSS 换算。

当主屏 100%、副屏 150% 时，副屏物理矩形被按 1.0 折算成 CSS，结果比副屏真实可视区**大 1.5 倍**。直接后果（都在副屏做选区时）：

| 受影响功能 | 位置 | 表现 |
|---|---|---|
| 窗口预选区虚线框 | `ss-hover.js:56` `rectScreenToCss`（用 `window.devicePixelRatio`） | 副屏窗口吸附框位置/尺寸偏移 |
| 控件预选区框 | `ss-control-hints.js:54` | 同上 |
| 桌面屏边界高亮 | `ss-display.js:31` `findDisplayCssAt` | 副屏框出的矩形与屏幕物理边界不重合 |
| 工具栏 clamp | `ss-display.js:44/62` | 可能误判副屏能否容纳工具栏 |
| 选区->pin 屏幕坐标 | `ss-output.js:79` `cssToScreen` | pin 出来的图位置偏 |

**作者已知**--`ss-display.js:3-6` 注释明说这是为修"每屏各自 dpr 与窗口级单一 dpr 的坐标系分裂"而改的，属于"两害取其轻"。同 DPI 多屏（双 100% / 双 150%）完全无此问题。随着高分屏普及，混合 DPI 场景只会增多。

## 三、核心设计 / 决策

### 3.1 per-monitor dpr 分段换算（已定）

**定案**：overlay 不再用"窗口级单一 dpr"折算所有屏，改为**每屏用自己的 dpi 折算成 CSS**注入 `displays`；前端 `screenToCss`/`cssToScreen` 按**鼠标所在屏的 dpr**分段换算。

**理由**：根因是"一个 dpr 管所有屏"。真正的修法是让每块屏的 CSS 几何按它自己的 dpr 折算，前端换算时按坐标落在哪块屏就用那块屏的 dpr。这与当前"单一 dpr"简化模型冲突，但能根治混合 DPI 副屏失真。

**数据契约变化**：

`__blinkScreenMeta.displays` 每屏增加 `dpi` 字段（当前只有 `x/y/w/h/primary`，均为 overlay CSS 坐标）。改造后：

- **方案 A（CSS 几何 + 每屏 dpr 都注入）**：`displays` 每项仍含 `x/y/w/h`（overlay CSS 坐标，但用**各自屏的 dpr** 折算），**额外**注入 `dpi`。前端 `screenToCss(x,y,meta)` 内部按 `(x,y)` 落在哪块屏，取该屏 `dpi/96` 作为 dpr 分段换算。
- **方案 B（注入物理几何 + 每屏 dpr，前端自己折算）**：`displays` 每项含物理 `x/y/w/h` + `dpi`，前端 `displayToCss(d)` 用 `d.dpi` 折算。`screenToCss` 同样按坐标查屏取 dpr。

**选方案 A**：保持 `displays` 注入 CSS 坐标的现状（`displayToCss` 仍接近恒等），只加 `dpi` 字段；前端换算函数从"单一 dpr 参数"改为"按坐标查屏取 dpr"。改动面更小，`ss-display.js` 的 clamp 逻辑（用 CSS 矩形）无需大改。

**关键不变式**：
- bitmap 坐标仍与屏幕物理像素 1:1（`screenToBitmap` 只减 `meta.vx/vy`，**不除 dpr**），crop 按物理像素裁剪 SESSION，自洽。**这条不变**。
- `displays` 的 CSS 矩形改用每屏各自 dpr 折算后，副屏 CSS 矩形 = 副屏物理矩形 / 副屏 dpr，与副屏实际可视区 1:1 对齐。
- 前端 `screenToCss`/`cssToScreen` 不再接收单一 `dpr` 参数，改为内部按坐标查屏取 dpr。调用点相应调整签名。

**受影响范围比"两个换算函数签名"更广，但 per-monitor 作用域有边界**（review + spike-B 核实）：

`ss.selCss` 是 overlay CSS 坐标（由 `e.offsetX/Y` 直接生成，`ss-interaction.js:128`）。截图代码里的 `dpr` 用法分两类，**改法不同**：

1. **映射到屏幕物理坐标的**（窗口/控件预选区定位、copy/pin 输出的 `cssToScreen`）：屏幕坐标与 dpr 相关，**改 per-monitor**（按坐标查屏取 dpr）。
2. **映射到主 canvas bitmap 的**（蒙版绘制 `selCss.x*dpr`、cropData 提取、compositeSelection 裁剪）：主 canvas backing store = 全屏 bitmap 物理像素，CSS `width:100%` 铺满 overlay 视口，bitmap↔CSS 映射比全局固定为 `window.devicePixelRatio`（overlay dpr），**物理上无法按屏分段**（spike-B 确认，`chord-screenshot.css:29-34` + `index.js:342`）。这类**必须保持 overlay dpr，不改**。

因此 §3.3 的三类分类需修正：原 A/B 类里"映射到 bitmap"的散点归入"保留 overlay dpr"，只有"映射到屏幕物理坐标"的才改 per-monitor。详见 §5.1 的四类分类表。

**跨屏选区**按 spike-B 结论定案策略 2（禁止跨 dpr 边界选区，clamp 到单屏），见 §3.4。

**Rust 侧 helper**：`build_displays_json` 改造时，每屏 `css_x = (d.x - meta.virtual_x) / scale_factor(d.dpi)`（用每屏自己的 `d.dpi` 而非 `overlay_dpi`）。`overlay_dpi` 仍读（用于 overlay 窗口自身的 canvas 物理尺寸对齐，见 `index.js:380` 标注 canvas `pw=rect.w*dpr`），但**不再用于折算 displays**。

### 3.2 pin 拖拽跨屏 dpr 切换修正（已定）

**定案**：`pin.html` 拖拽增加 dpr 变化监听，dpr 变化时用 Rust 回读窗口物理位置重标定 `imgScreenX/Y`。

**理由**：当前 `pin.html:262-285` 拖拽靠 `e.screenX * devicePixelRatio` 累加物理坐标。pin 窗口被拖到不同 DPI 副屏时，`WM_DPICHANGED` 触发 `devicePixelRatio` 变化，但 `imgScreenX/Y` 是历史累加值不重标定 -> 位移换算用新 dpr 算增量却加到旧物理坐标上 -> 跳变。

**实现选型**（spike-A 已结论，见 §3.4）：
- **方案 A（Tauri `onScaleChanged` + Rust 回读）-- 定案**：pin 窗口是标准 Tauri `WebviewWindow`（`windows.rs:1892`），Tauri 2 自动把 `WindowEvent::ScaleFactorChanged` 转发到该窗口 webview，前端用 `getCurrentWindow().onScaleChanged(cb)` 监听（复用 `shared/tauri.js:77` 封装）。回调 payload 含 `scaleFactor`（新 dpr）+ `size`（新物理尺寸）。dpr 变化时 invoke 新 command 读窗口当前物理位置，重算 `imgScreenX = winRect.left + PAD`。
  - **时序优势**：`ScaleFactorChanged` 在 wry 处理 `WM_DPICHANGED` 时同步派发，比 JS 侧 `matchMedia`（要等 Chromium 重新评估 media query）更早更确定。
  - **关键注意**：回调里**必须用 `payload.scaleFactor`，不要回读 `window.devicePixelRatio`**--Tauri 事件先于 Chromium 布局完成，`window.devicePixelRatio` 可能仍是旧值。
- ~~方案 B（Rust 侧 `WM_DPICHANGED` 主动推送）~~：Tauri 已自动 emit `tauri://scale-change`，无需重复造。
- ~~方案 C（拖拽改 Rust 主导 `startDragging`）~~：改变拖拽交互模型，左上角固定缩放语义需重验，代价过大。
- **兜底**：mousemove 里顺带比对 `devicePixelRatio` 缓存值（零成本，拖拽本就读 dpr），作为 `onScaleChanged` 的补充防线。

**spike-A 否决的方案**：`matchMedia('(resolution: Xdppx)')` 固定值查询无法持续监听任意 dpr 变化（change 只触发一次且不告知新值）；`window.resize` + dpr 比对不可靠（dpr 变但尺寸没变时不触发）；`MutationObserver` 不适用（dpr 非 DOM 属性）。

### 3.3 前端散落 devicePixelRatio 收口（已定，spike-B 修正）

**定案**：散落的 `devicePixelRatio` 读取按用途分四类处理（spike-B 确认主 canvas bitmap 映射无法分段，原三类分类已修正）：

| 类别 | 典型用法 | 处理 |
|---|---|---|
| **A. 屏幕坐标换算**（CSS 点 -> 屏幕物理坐标，不经过 canvas bitmap） | `cssToScreen` 调用（pin/滚轮转发）、`ss-hover.js`/`ss-control-hints.js` 预选区定位 | **改走按屏查 dpr**（`dprAtCss`） |
| **B. 输出裁剪尺寸**（CSS 尺寸 -> 屏幕物理尺寸，copy/pin 裁剪宽高） | `ss-output.js:32/165` `selCss.w*dpr`（快路径裁剪宽高，直接传后端从 SESSION 裁剪，不经主 canvas） | **改走按屏查 dpr**（选区所在屏，`cssSizeToPhysical`） |
| **C. 主 canvas bitmap 映射**（CSS 坐标/尺寸 -> 主 canvas backing store 物理像素） | `ss-draw.js:39-42/74-77` 蒙版绘制、`index.js:386-387/397` 标注 canvas + cropData、`ss-reading.js:71-72/84-85/145-146` 命中检测/hit canvas | **保留 overlay dpr**（主 canvas bitmap↔CSS 映射全局固定为 `window.devicePixelRatio`，spike-B 确认无法分段） |
| **D. canvas 绘制粗细/线宽** | `ss-draw.js:56/91/108` `lineWidth=2*dpr`、`ss-reading.js:119`、`ss-color-picker.js:354-355` 取色像素 | **保留直读** `window.devicePixelRatio`（绘制粗细对齐 overlay 窗口渲染分辨率） |

**关键区分**（spike-B 核心结论）：C 类与 A/B 类的界限是"是否映射到主 canvas bitmap"。
- 主 canvas（`#canvas`）backing store = 全屏 bitmap 物理像素（`canvas.width = img.width`），CSS `width:100%` 铺满 overlay 视口，bitmap↔CSS 映射比 = `window.devicePixelRatio`（由 `place_at_physical` + 单一 overlay_dpr 折算保证，全局固定）。
- 凡是 `drawImage`/`getImageData`/`drawSelection` 蒙版这类操作主 canvas bitmap 的，dpr 必须用 overlay dpr。
- 凡是 `cssToScreen`/`screenshotCopyRegion`/`screenshotPin` 这类算屏幕物理坐标传后端的，dpr 用选区所在屏 dpr。

**理由**：`ss-selection-geometry.js:9` 铁则"禁止在各处直接用 devicePixelRatio 拼公式"未完全贯彻，~15 处散点直读。A/B 类收口进 0.18.8.0（改 per-monitor），C/D 类保留 overlay dpr + 注释收尾（0.18.8.2）。

**取色器例外**（`ss-color-picker.js:354`）：取色读 overlay canvas 内部像素，属 D 类，保留直读 + 注释。

### 3.4 Spike 结论（已完成）

**spike-A：WebView2 dpr 变化监听方式 -- 已结论**

- `matchMedia('(resolution: Xdppx)')` 固定值查询：change 只触发一次且不告知新 dpr，**无法持续监听**。正确写法是"每次 change 后用新 dpr 重新注册"（递归 re-arm），但比 Tauri 原生事件晚且多一层。
- `window.resize` + dpr 比对：dpr 变但窗口逻辑尺寸没变时不触发 resize，**不可靠**。
- `MutationObserver`：dpr 是 `window` 数值属性非 DOM 属性，**不适用**。
- **Tauri `onScaleChanged`（定案）**：pin 窗口是标准 Tauri 窗口，`WindowEvent::ScaleFactorChanged` 自动转发到 webview，前端 `getCurrentWindow().onScaleChanged(cb)` 直接可用。payload 含 `scaleFactor` + `size`，时序最贴近 `WM_DPICHANGED` 源头。**回调里用 `payload.scaleFactor`，不回读 `window.devicePixelRatio`**（Tauri 事件先于 Chromium 布局完成）。

**spike-B：overlay canvas dpr 时序 -- 已结论（影响 §3.1/§5.1 方案）**

- 主 canvas（`#canvas`）CSS 是 `width:100%; height:100%`（`chord-screenshot.css:29-34`），backing store = bitmap 物理像素（`canvas.width = img.width`，`index.js:342`）。
- **bitmap↔CSS 映射比 = `img.width / innerWidth` = `meta.width / (meta.width/scale)` = `overlay_dpr/96` = `window.devicePixelRatio`**。这个映射由 `place_at_physical`（窗口物理尺寸 = meta.width）+ 单一 overlay_dpr 折算共同保证，**全局固定，物理上无法按屏分段**。
- **结论：主 canvas 的绘制操作（蒙版 `ss-draw.js`、cropData 提取 `index.js:395-400`、compositeSelection 裁剪 `ss-output.js:165-168`）必须保持 overlay dpr，不能改 per-monitor。** 标注 canvas 与主 canvas 同坐标系，也不能改。
- **per-monitor 的作用域因此收窄为两类**：(1) 窗口/控件预选区定位（屏幕物理坐标↔overlay CSS，不经过 canvas bitmap）；(2) 输出阶段 copy/pin 的物理坐标计算（`cssToScreen`，屏幕坐标不经过 canvas bitmap）。主 canvas 内部的 `selCss.* * dpr` 直乘（A/B 类里映射到 bitmap 的）**保持 overlay dpr 不改**。
- **这意味着 §3.3/§5.1 的三类分类需修正**：A/B 类里"映射到主 canvas bitmap"的直乘点应归入 C 类（保留 overlay dpr），只有"映射到屏幕物理坐标"的才改 per-monitor。详见 §5.1 修订。

**spike-B：跨屏选区策略 -- 已结论**

- **定案：策略 2（禁止跨 dpr 边界选区，clamp 到单屏）**。理由：截图选区 99% 在单屏内，跨 dpr 屏选区是低频场景；策略 1（左上角屏 dpr 统一）有蒙版/输出坐标系分裂的内在矛盾；策略 3（分段裁剪）实现成本高且拼接接缝物理上无法消除。
- **实现要点**：初始框选阶段（`index.js:820-821` mousemove isDragging 分支，当前无 clamp）加 clamp--用 `findDisplayCssAt` 取起点屏，若当前点跨到不同 dpr 屏则 clamp 到起点屏边界。**同 dpr 屏间不 clamp**（双 100% 屏跨屏安全）。
- **配套要求**：策略 2 必须与 per-monitor 输出改造配套--选区 clamp 到单屏后，输出时（copy/pin）用该屏 dpr 而非 overlay dpr，单屏选区在任意屏上才真正正确。
