## 二、背景与边界

0.23 把 Blink 从“把识别结果一次性写到输入框”推进为可持续工作的文本处理链：来源文本可精确编辑，语音可连续追加，AI 修改必须先展示候选并由用户确认。实现以单会话、明确版本号和单写入点约束异步任务，避免旧结果覆盖新内容。

本阶段不解决：

- 富文本格式的无损往返；Markdown 仅支持安全子集预览。
- 多文档、多窗口并行编辑。
- 无确认的 AI 自动改写。
- 远程桌面下依赖系统排除捕获能力的“无条件可见”长截图。

## 三、核心决策与最终约束

### 3.1 单个预热编辑器与 EditorSession

- 全局复用一个预热编辑器窗口，激活相同来源；来源不同且已有活动会话时返回 EditorBusy。
- 会话身份由 session_ref + generation + content_revision 共同限定。所有异步回传在落地前复核身份与版本。
- 用户编辑、语音提交、AI 确认都走统一事务入口，统一更新 revision 与撤销栈。
- 窗口隐藏不等于会话结束；复用 WebView 必须在进入前同步复位，在退出时立即失活并取消旧任务。

### 3.2 Source、Markdown 与写回

- Source 是唯一文本真源；Markdown 只是安全渲染视图，不反向承载隐式格式状态。
- SourceDescriptor 描述来源，CommitTarget 描述写回目标；读取能力不自动获得写权限。
- 文件保存通过 UTF-8 原子写能力完成，并受 mutation gate 约束。
- 自动 Markdown 预览上限 32 KB；可编辑 Markdown 上限 128 KB；Source 上限 200 万字符；Diff 上限 200 KB；AI 输入上限 24k tokens。

### 3.3 连续听写与 AI 整理

| 场景 | 语音结果 |
|---|---|
| G2 输入框 | Preview 仅展示；会话结束时将最终 Draft 一次性注入 |
| Editor | Preview 作为临时装饰；Draft 持续提交到正文 |
| G1 / G3 | 保持 Legacy 流程 |

- 任一时刻只有一个活动语音会话和一个活动 AI 请求。
- AI 启动时冻结 revision、选区与内容 hash，只生成候选；确认时再次校验，成功后作为单个事务写入。
- AI 候选与 Diff 不修改 Source；用户继续编辑后，过期候选不能提交。

### 3.4 Preview/Draft 双层识别

- 单 worker 串行调度识别任务，保留“一个运行中的任务、一个待执行 Draft、最新 Preview”。
- AudioRange 使用半开区间和绝对采样位置；owned_range 与 model_input_range 分离，禁止靠文本相似度拼接。
- Preview 允许被更新或丢弃；Draft 只能按不重叠音频范围提交。最终尾段与 Draft 优先级高于 Preview。
- committed_watermark 与 reserved_watermark 分别表示已提交和已占用边界；积压硬上限为最大窗口的 2 倍。
- RequestAudioGate 在任务执行前再次验证范围与代次；最终识别失败时不注入部分 G2 文本。

| 参数 | 默认值 | 可配置范围 |
|---|---:|---:|
| Preview 窗口 | 3000 ms | 2000～4000 ms |
| Preview 刷新 | 700 ms | 500～1000 ms |
| Draft 最短片段 | 5 s | 3～10 s |
| 强停顿 | 700 ms | 500～1500 ms |

VAD 最终采用 800 ms / 300 ms 双阈值、8 / 12 / 12 秒窗口、轻量语音计数、渐进停顿和 1.2 秒谷底切分；FSMN 不进入本阶段生产链路。

### 3.5 短语级收口

- 0.23.10 引入 Phrase Anchor、Phrase Ledger 与 ShortPhraseEnd，Preview 可按短语稳定展示。
- 尾段只有真正提交成功后才清除；失败时保留可恢复状态。
- worker 预热、请求限速、单调任务 ID 与单调音频范围共同阻止旧识别覆盖新短语。

### 3.6 0.23.11 主链路稳定性收口

- 热键状态每 2 秒自愈；异常须连续两次确认。程序注入不推进物理按键时间游标，重装 hook 前重建物理快照。
- 截图原始 IPC 透传选项，RGBA 数据先校验、失败再回退；图钉失败对用户可见，并支持按窗口 label 定向刷新。
- OCR 支持静默选区、空白拖动恢复选区移动、空白双击复制；截图和图钉共用文字选区算法。
- 图钉增加 OCR/翻译文字层；原文使用 font_h，译文使用稳定墨迹坐标，并加入面板避让。
- 截图复用窗口新增显式 session 生命周期：初始与退出状态用 screenshot-session-inactive 隐藏旧图层；同步复位完成后才揭示新截图；退出先递增 OCR/翻译 revision，再取消任务与清理 loading snapshot；翻译面板轮询同时校验任务版本、会话版本和 DOM 连接状态。
- OCR/翻译叠层颜色保真：原文字色按词单元对齐（正则分词，camelCase/snake_case 不拆）；译文模式对代码特征行（结构簇判定）启用分段着色并合并碎片段，多语法色代码行译文不再集体回退黑白灰。配套 corpus 颜色采样评测（testdata/ocr/corpus + PaddleOCR 真实推理探针）。

关键教训：preventDefault() 不会阻止同一页面上的其他键盘监听器；正常模块接管后必须注销应急 ESC。Tauri 隐藏窗口也不会销毁 WebView，所有截图临时层都必须按“复用会话”而不是按“页面卸载”清理。

## 八、0.23.12/0.23.13 规划：统一资源 ref 层（📋 原 0.23.99 转正）

### 8.1 背景与动机

现有两套资源引用平行运作：

- ImageStash（`src/domain/capability/image_stash.rs`）：内存字节、15 分钟 TTL、16 项/64 MiB/单项 32 MiB、无 scope、非消费读取（可先 OCR 再 pin）、64 位 xorshift token，喂 OCR/pin/图片类 Capability。投影层只把 `image/*` Blob 移入 stash（`result.rs` 的 `to_rig_tool_result_with_stash`），其余 Blob 降级为尺寸摘要。
- AudioResourceRegistry（`src/app/audio_resource/`）：磁盘路径句柄 + FileIdentity 校验、5 分钟 TTL、32 项/256 MB（按文件逻辑大小计）、scope 字符串、一次性 resolve，喂转写与 VAD 调试预览。

已知缺陷：`resolve` 先 remove 再校验 scope/generation，错误 scope 会烧掉一次性 ref。

目标：把「合并两套 Registry」提升为「统一、短期、最小授权的资源句柄协议」。ResourceStore 是 Capability 之间的**数据平面**（跨调用传递大资源的临时句柄），不是新的执行平面；不改变 0.21 Capability 唯一原子执行语义。定位关系：内存字节/本地文件/未来远程对象 → ResourceStore（身份、授权、生命周期、配额）→ opaque ResourceRef → OCR/pin/STT/文本读取等 Capability 消费。

### 8.2 设计决策（已定案，含理由）

1. **backing 双模**：`Memory(Bytes)` 与 `LocalFile(FrozenLocalFile)` 双模落地；`RemoteObjectKey` 只留类型边界不实现。配额双口径分离：`resident_memory_bytes`（沿用 16 项/64 MiB/单项 32 MiB）与 `referenced_local_bytes`（沿用 32 项/256 MB/单项 128 MB）独立计数，禁止混入同一 max_total_bytes。TTL 同样按 backing 分口径：Memory 沿用 15 分钟、LocalFile 沿用 5 分钟，读取不续期；投影层 `result.rs` 硬编码的 `expires_in_seconds: 900` 与内存腿 15 分钟绑定，0.23.13 验收「image_ref 语义不变」以此为准。理由：全内存受常驻 <300MB SLO 与长录音体积（16kHz 约 2MB/分钟）挤压；远程实现牵动 SSRF/下载炸弹/凭据问题，本阶段不背。
2. **ResourceUse 封闭枚举**：audio_ref 的 scope 上升为所有 ref 的通用属性，但用封闭枚举而非任意字符串；use 集合由签发方（UI/Interaction/内部 Capability）决定，AI 只能消费不能自选。首版枚举只收有真实消费方的变体（DecodeImage/OcrImage/PinImage/TranscribeAudio/PreviewAudio），开工时逐变体点名消费方；无消费方的不占位——ReadText 随 read_text_resource 立项时再加入。ReusePolicy（Reusable/OneShot/MaxReads(n)）成为 grant 属性，不再由媒体类型隐含；VAD 调试的 clone 语义平移为 store 的 `issue_from_ref` 入口（从仍有效的 ref 派生新 grant、TTL 重算），不靠预先签发 MaxReads(2) 弱化转写 one-shot。**注意**：每新增消费型 Capability 需扩枚举并评审签发方白名单——这是有意的收敛摩擦，不是债，不得当债优化掉。
3. **token 换 CSPRNG**：≥128 位 OS 安全随机（`getrandom` crate，跨平台且 domain 分层安全，不走 windows crate），替换两套 xorshift/时间戳方案。理由：ref 会被 AI/MCP 持有，本质是 bearer capability；ImageStash 64 位偏弱，AudioRegistry 名义 128 位但有效熵低。
4. **resolve 顺序：校验全过才消费**：查找 → TTL/revoke_group/use/identity 校验 → 成功取得 lease → 同一临界区内提交使用次数；错误 use 不消耗 one-shot ref。该校验与消费必须同锁原子完成，否则并发 one-shot 会双双通过。修复并入 0.23.12。
5. **撤销语义收敛**：`revoke_group` 取代裸 generation（generation ≡ 全局 group），不再两套机制并存。现状澄清：generation 在生产代码零调用（`bump_generation` 仅测试使用），本就是 dead 机制——迁移后 revoke_group 必须接真实调用方：0.23.12 至少有一个非测试调用方（候选挂点：语音会话结束时按 owner 撤销未消费 audio_ref，开工时定）；0.23.13 把 `media.rs` 请求结束的 `stash.remove` 清理平移为单 ref revoke，对话音频闭环的会话结束撤销并入同一模式。无真实调用方视为未完成。
6. **CapabilityResult 不加 Resource 变体**：本阶段只做「投影边界按策略统一入 store」，消除 `image/*` 特殊分支；Blob 仍是一次调用的直接二进制返回。理由：当前无生产者需要显式签发变体（截图/剪贴板走 Blob 投影、转写返回文本、VAD 调试走 command）；协议变体牵动四出口投影（AI/主窗口/CLI/MCP），等真实场景出现再加，届时投影层已统一、增量小。
7. **读取接口只落地 `read_all_bounded(max_bytes)`**：`read_range`/`open_stream` 只留签名不实现。理由：文本分页由 `read_text_file` 既有实现承担，音频转写整读够用；「以后可能流式」不进本阶段。
8. **read_text_file 不动**：本地绝对路径与 ref 解决不同问题（稳定定位 vs 短期授权句柄、隐藏真实来源）。`read_text_resource`/`bind_local_resource` 推迟到有真实需求再立项——后者是权限放大器，VAD 播放与本地图片喂 OCR 均已有便宜路径。
9. **CLI/MCP 降级**：无 ResourceStore 的运行时在 invoke 边界返回结构化 Unsupported（spec-architecture §A3.2 既有规定），投影层不静默吞成摘要。
10. **wire 参数名保留**：消费方 schema 继续用 `image_ref`/`audio_ref` 参数名（LLM 语义友好），底层统一为 ResourceRef；旧参数名保留一个迁移周期。
11. **引擎生命周期不在 Capability 内管理**：`transcribe_audio` 服务侧维持「不启动、不安装、不切换」的既有设计（`AudioTranscriptionService` 三处注释钉死）——引擎未运行返回结构化 `SttBackendUnavailable`、未配置返回 `SttNotConfigured`、云端文件转写维持 `Unsupported`（H04 未实现）。ensure 责任在**可信入口**：CLI 已在 invoke 前显式 start；对话窗口附件闭环在签发附件时后台预热引擎（同一模式），capability 保持纯粹。不新增引擎生命周期 capability——现有引擎管理在 `app/commands/local_engine/` 的 Tauri command 层（设置页专用），暴露给 AI 牵动 danger 分级与确认策略，本阶段不背。

### 8.3 两段式切分

**0.23.12 —— 协议层 + store + 音频腿**（先基础后应用；音频腿消费方最少、scope/one-shot/identity 语义直接继承、不碰投影层）：

1. `src/domain/resource/` 协议：ResourceRef（serde transparent，opaque）、ResourceMetadata、ResourceBacking（Memory/LocalFile，Remote 只留 key）、ResourceGrant（use 集/ReusePolicy/revoke_group/owner）、ResourceError、双口径配额。
2. `DefaultResourceStore` 实现：issue/inspect/open/revoke/revoke_group/issue_from_ref（clone 语义平移）；getrandom token；锁内校验全过才消费。
3. `CapabilityEnv` 新增 `resource_store()`（过渡期与 `image_stash()` 并存）。
4. 迁移音频腿全部消费方到 store：`transcribe_audio`（domain capability）、`audio_transcribe` command、`clone_audio_ref_for_vad_debug`、`AudioTranscriptionService`（真正的 resolve 调用方，构造签名随 store 变更）、CLI `blink transcribe` wiring（`src/cli/commands.rs` 构造 store 替代 AudioResourceRegistry——CLI 是真实消费方，不是「无 store 最小运行时」，不得降级 Unsupported）；删除 `src/app/audio_resource/`，既有测试平移至 `domain/resource`。

**0.23.13 —— 图片腿 + 投影统一 + 对话音频闭环**：

1. 迁移 `ocr_image` / `pin_image` / `analyze_image_palette` / `write_clipboard` 到 `resource_store()`。
2. `to_rig_tool_result_with_stash` 改为按策略统一入 store，消除 `image/*` 特殊分支；四出口投影同步检查。
3. 删除 ImageStash 与 `image_stash()` getter，`resource_store()` 成为唯一资源入口。
4. 对话窗口音频附件闭环（资源层的第一个 GUI 消费证明，后端大多现成）：
   - 前端附件入口（`frontend/js/chat/` composer）→ 调 chat 版 `pick_audio_file`（复用既有可信 picker 命令，签发 `use={TranscribeAudio}`、`owner=chat 会话` 的 grant）；
   - ref 以附件 chip 注入对话上下文，模型将其作为 `transcribe_audio` 的 tool 参数——需用户先在 AI 能力设置开启该 cap（`ai_default: Off`，0.21.5 allowlist），确认流程照旧；
   - 附件 grant 用 **Reusable + 会话结束 revoke**（转写失败重试不烧 ref——这正是 ReusePolicy 上移为 grant 属性的价值；TTL 默认随 backing，实测一轮对话不够再放宽 grant TTL）；
   - 附件签发时后台预热本地 STT 引擎（对齐 CLI invoke 前 start 的模式，见决策 11）；预热失败不阻塞附件，转写时返回结构化错误。

### 8.4 边界与量级

- 不改 0.21 Capability 唯一原子执行语义；开工前必读 0.21 phase 与 spec-architecture。
- 0.23.12 预估 1.5～2 天，0.23.13 预估 1.5～2.5 天（含对话音频附件闭环，前端入口是大头）。若 0.23.12 落地顺利且耗时明显低于预期，可合并交付——拆分是风险控制手段，不是目的。
- 便宜替代（如仅需「本地图片文件喂 OCR/pin」）：`pick_image_file` 命令 + store.put 的约 50 行适配可独立交付；VAD 调试播放走 ref 读字节，同样不依赖完整重构。
