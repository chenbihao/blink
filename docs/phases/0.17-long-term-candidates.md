# Blink 0.17 — 远期想法候选（Long-term Candidates）

> **状态**：🔮 前瞻候选（非承诺规划）。本 phase 四项性质完全不同，尚未立项；待 0.15/0.16 完成后回头评估真实需求再决定主题。

> **来源**：讨论后续版本蓝图时，用户提出的"额外功能扩展可能性"。本文逐项做价值/成本/边界判断，**不预设都会做**。
>
> **结构说明**：本 phase 是候选评估文档，不套用 `spec-phase.md` 标准模板（无核心设计/里程碑/子版本/验收）。章节为候选清单 + 留白理由 + 与现有规划关系 + 未决问题 + 后续预告。

## 一、候选清单与初步判断

### 1.1 配置同步（WebDAV）

**场景**：多设备间同步配置 / 历史记录。

| 维度 | 判断 |
|---|---|
| 价值 | 高——多设备用户刚需 |
| 成本 | ⭐⭐⭐ 高——需 WebDAV client、冲突解决、增量同步、加密 |
| 边界风险 | 低——属"便利性增强"，不偏离核心 |
| 建议 | 0.17 主菜候选。但自用单设备阶段可后置；做多设备分发前再做 |

### 1.2 便利贴（Sticky Note）

**场景**：新增 chord（如 Alt+N）进入常驻便签模式；或参考 Win 便签做一个更顺手的。

| 维度 | 判断 |
|---|---|
| 价值 | **待论证** |
| 成本 | ⭐⭐ 中——需新建 chord + 常驻透明窗口 + 持久化 |
| 边界风险 | 中——**违反 product.md §6.2 信念的风险**：Win 便签（`stickynote.exe`）已完善，Blink 做便利贴的操作路径不一定更短 |
| 建议 | **必须先回答"它比 win+R stickynote 快在哪"**。除非做成"Alt 唤起直接进便签 chord + 复用 0.16 md 渲染"，否则差异化不足。若 md 共享模块（0.16.1）落地，便利贴可白嫖其渲染——这是降本关键 |

### 1.3 快速预览（QuickLook 式）

**场景**：选中文件（资源管理器/桌面）→ 空格预览。

| 维度 | 判断 |
|---|---|
| 价值 | 中——QuickLook（macOS）体验好，Win 上有 Seer/QuickLook 替代 |
| 成本 | ⭐⭐⭐⭐ **极高**——各类文件预览库（PDF/Office/视频/代码）很重 |
| 边界风险 | **高——可能超出软件边界**。product.md §1.4 护城河是"感知+执行+速度"，文件预览偏离核心，且预览库体积与"安装包 <100MB"冲突 |
| 建议 | **不做完整版**。若做，仅极轻量（文本/图片预览，复用已有图片解码能力）。倾向不做 |

### 1.4 能力打通（md 渲染复用）

**场景**：对话窗口 / 剪贴板编辑器 / 便签共享同一套 md 渲染。

| 维度 | 判断 |
|---|---|
| 价值 | 高 |
| 成本 | 低 |
| 边界风险 | 无 |
| 建议 | **不是独立 phase，是横切**。0.16.1 做编辑器时把 md 抽共享模块（`frontend/js/shared/markdown.js`），便利贴/便签自动受益。无需等 0.17 |

## 二、为什么 0.17 留白

四项里只有"配置同步"是明确的独立 phase 候选；"便利贴"需先论证价值；"快速预览"倾向不做；"md 复用"是横切不属于 phase。因此：

1. **现在不定 0.17 主题**——等 0.15/0.16 做完后，便利贴的真实需求、能力打通的更多触点会浮现，那时判断更准
2. **剪贴板图片支持（0.16.2）做完后**，"图片→pin""图片→md 编辑"等联动需求会自然出现，可能重塑 0.17 的形态
3. 配置同步若做多设备分发前才需要，时间窗可能远于 0.17

## 五、后续预告：0.18 — CAP 闭环综合（AI 感知屏幕）

> 本节是 0.15 讨论时产生的预告，**待做完 0.17 后再回头讨论 0.18 是否立项及范围**。

**触发**：0.15 讨论截图 CAP 能力时发现——`capture_screen` Capability 虽在 AI tool 池里，但返回的 `Blob` 被投影成文本摘要（`"已获取 image/png (1.2 MB)"`），**像素从不到达模型**，AI"截了图但看不见"。OCR 闭环也因此断链（`ocr_image` 需 bytes 输入，但 capture 只回摘要）。

**0.18 候选范围**（轻量闭环优先，完整多模态延后）：

| 档位 | 内容 | 难度 | 备注 |
|---|---|---|---|
| **轻量闭环** | AI 获取屏幕信息（光标位置/前台窗口/显示器）→ 调 capture → 截图写入剪贴板 | 低-中 | 70-80% 基础设施已存在，主要是接线 |
| **多模态** | Blob→Image 投影 + 多模态模型喂图 | 中-高 | 两处 policy（代码注释"前端暂不展示图片"）需翻转；rig 0.39 API 已就绪 |
| **OCR 闭环修复** | 截图 bytes 内部直链 ocr_image（不过 LLM） | 低 | 避免把 megabytes 过 LLM channel |

**轻量闭环的具体缺口**（都是接线活，评估时已确认）：

| 需求 | 现状 | 工作量 |
|---|---|---|
| 显示器/分辨率信息 | ✅ `screenshot{op:list_displays}` 已返回 DisplayGeometry JSON | 0 |
| 光标位置 | ❌ `GetCursorPos` 仅 infra 内部用（`window/windows.rs:408,491,768,1304`），无 Capability | ~30 行 wrapper |
| 前台窗口信息 | ❌ `foreground_app()` 数据已有（`context/mod.rs:300`），无 Capability | ~30 行 wrapper |
| AI 调截图 | ✅ `capture_screen`/`screenshot{op:capture}` 已在 tool 池 | 0 |
| 截图→剪贴板 | ⚠️ `write_clipboard` Capability 已支持 BGRA，但 AI 拿不到 bytes。**最干净做法**：加 `screenshot{op:capture_to_clipboard}` op，内部链接 截图→写剪贴板，不让 megabytes 过 LLM | 中 |

**核心架构原则（评估时定）**：AI 只下达指令（`capture_to_clipboard`），内部 Rust 直接 截图→写剪贴板，AI 只收到文本确认。**绝不让 megabytes 图片过 LLM channel**——这是正确架构，也避免 token 爆炸。

**为什么放 0.18 而非 0.15**：0.15 是纯前端标注重做 + 新工具，CAP 闭环是后端接线活，两者正交。硬塞进 0.15 会让 phase 范围过载。且 0.18 可能不止 cap 闭环（"其他功能的 cap 闭环"），需综合讨论范围。
