# Blink 0.14 — 能力协议与架构收敛（Capability/Action 边界 + Cap 协议 + 分层清理）

> **范围**：① Capability 与 Action 的职责边界从"口头约定"升级为"类型系统钉死"（删 `ActionTool` 适配器，AI 永不直接调 Action）+ ② Cap 协议分层——插件只吐纯 `data`，投影规则（pointer / desc / actions）上移到 manifest 做代理 + ③ 四出口投影引擎收敛（主窗口 AI / 对话窗口 AI / CLI / MCP 共用一套 canonical 投影）+ ④ 0.14.6 延续清理——在不改变能力语义的前提下，收敛分层违例、重复协议和前后端巨石文件。
>
> **状态**：🚧 进行中（0.14.0~0.14.6 ✅；0.14.7 📋）。
>
> **动机**：0.13.7 收尾时发现三个协议债——(1) `ItemResult { title, subtitle, payload }` 把"给人看的 UI 文案"和"给 AI 看的语义数据"焊在一起，导致对话窗口 AI 收到带 emoji / "按 Enter 复制"的噪音；(2) 能力结果 4 个出口（AI/CLI/MCP/前端）只有 2 个复用 canonical 投影，CLI/MCP 各自手写、Blob 摘要重复 4 份、MCP 还漏去 score；(3) `ActionTool` 把 lock/shutdown 等危险系统操作也暴露给了 AI tool 池。协议重构完成后的整体审查又确认：架构骨架健康，但领域层仍夹有框架/平台依赖，Schema、错误、事件和前端文件也存在工程债，因此在 0.14.6 做延续收敛。
>
> **前置**：0.13 完成（能力体系已收敛——`ActionOutcome::Items` 变体已删，插件 Action 已迁入 Capability）。
>
> **原则**：**插件只吐纯 data，投影是配置出来的不是代码写死的**。manifest 投影只支持静态值 + JSONPath 取值，不做格式化（格式化由能力单元自己管）。

## 一、背景与动机

0.13.7 收尾审查发现三个互相牵连的债，趁架构向"Action=副作用专用、Capability=数据专用"收敛的窗口一次性清掉。三个债：(1) `ItemResult` 字段语义混淆（UI 文案污染 AI）；(2) 四出口投影分裂（CLI/MCP 手写、重复、漂移）；(3) `ActionTool` 过度暴露（危险系统操作进 AI tool 池）。详见 §二/三/五的核心决策。

---

## 二、Capability 与 Action 的职责边界（核心决策）

**Action**（0.8 四域，Execution 域）：已发生的副作用描述（Copy/Open/Emit/Nop），**永远不进 AI tool 池**——lock/shutdown/open_settings/chord 动作等。
**Capability**（0.9.7）：纯数据能力（取数/计算/翻译/打开），**进 AI tool 池的唯一合法形态**——search_files/translate/capture_screen/open_url 等。

**边界用类型系统钉死**：删除 `ActionTool` 适配器，AI 永远只能通过 `CapabilityTool` 调能力。把"AI 该不该调"的决策从运行时 danger_class 标记前置成编译期约束。

**3 个 Action 提升为 Capability**：`open_url` / `open_path` / `reveal_in_explorer`（AI 常用的"打开"能力，作为 Capability 返回 `Done`）。其余 9 个 Action（lock/shutdown/...）保留在 Action trait，不进 tool 池。

**不合并 Capability 与 Action**：曾考虑全合成 Capability，否决——四域架构里 Action 承载"已执行副作用"语义，且 9 个保留 Action 本就不该让 AI 调（详见 §十一 ADR）。

---

## 三、Cap 协议分层——插件只吐纯 data

**两层解耦**：层 1 = manifest 投影规则（pointer/desc/actions，相对静态）；层 2 = 插件运行时输出（纯 data JSON）。投影引擎用 manifest 规则把 data 投影成各出口形态。精髓：展示和投影是配置出来的，不是代码写死的。

**三个关键设计点**：
- **JSONPath 取值**用 `jsonpath-rust` crate（纯 Rust ~30KB，零 C 绑定）。选型理由见 §十一 ADR。
- **desc 三来源优先级**：`desc_pointer`（JSONPath 动态取值）> `desc`（静态字符串）> None（不展示）。manifest **不做格式化**——需要 `format_size(bytes)` 时由能力单元自己在 data 算好填进去。
- **双轨制**：轨道 A（manifest 投影，简单返回如 translate/IP/weather）+ 轨道 B（直接构造 CapabilityResult，复杂返回如 builtin search_files）。

> **轨道 B 实现澄清**（0.14.5）：插件协议侧最终只保留轨道 A（插件经 JSONL 返回纯 data，core 用 ProjectionRule 投影）。轨道 B 退化为"仅 builtin capability 可直接构造 CapabilityResult"——builtin 本就不走 JSONL 协议。早期 commit `df85f912` 曾遗留旧 `PluginItem` 协议路径冒充轨道 B（0.14.5 已删）。

---

## 四、新 Cap 协议结构

**插件运行时输出**（轨道 A）：`PluginRawResult { data: Value, error: Option<String> }`——只吐纯 data，零展示逻辑。

**manifest 投影规则**（ProjectionRule）：`result_shape`（text/items/blob/done）+ `pointer`/`desc`/`desc_pointer`（text/blob 用）+ `items_pointer`/`item_pointer`/`item_desc_pointer`/`item_actions`（items 用）。字段全为 JSONPath 或静态值。

**CapabilityResult**（四出口共用）：四变体 `Text{content,desc}` / `Items{items}` / `Blob{mime,bytes,desc}` / `Done{summary}`。`Text`/`Blob` 加了可选 `desc`。

**ItemResult 关键变化**（对比旧 `{title,subtitle,payload,score}`）：
- 删 `title`/`subtitle`/`score`（主窗口展示概念，不该在协议层）；主标题由前端从 `data` 派生（`derive_title()`，优先取 `name`/`title` 字段）
- `data` 取代 `payload`（语义明确："给 AI 的纯净数据"）；`desc` 取代 `subtitle`
- `actions: Vec<ItemAction>` 显式声明可用动作（Copy/OpenFile/OpenUrl/Reveal，各带可选 `pointer` 指定从 data 取值）

**多 action 交互约定**（主窗口）：回车执行 `actions[0]`（首个），右键展开全部。manifest 里 actions 顺序即优先级，作者把最常用动作放第一个。

**空 actions 兜底**：无 actions + 纯标量 data → 主窗口隐式提供 copy。这是**展示层 fallback，非协议层派生**——协议层如实传空数组，兜底只活在主窗口前端。

---

## 五、投影引擎（四出口共用）

四个出口（AI / 主窗口前端 / CLI / MCP）共用一套 canonical 投影，不再各自手写 match 四变体。`project()` 用 ProjectionRule 把 PluginRawResult 投影成 CapabilityResult。各出口读什么：AI 只读 `data`；主窗口前端读 `data`（派生主标题）+ `desc` + `actions`；CLI 读 `data`+`desc`；MCP 同 AI。

**消除的重复**：Blob 摘要收进 `CapabilityResult::blob_summary()`（旧 4 处逐字重复删除）；CLI/MCP 改调 canonical；MCP Items 投影的 score 漂移修复（改用 `items_to_llm_json` 去 score）；对话历史加载复用 `summarize_tool_result`。

## 六、插件协议迁移

**一次性切换**（破坏性，不留兼容层）：translate/IP/weather 全部从旧 `{title,subtitle,payload,action,score}` 迁到轨道 A `{data}`，manifest 配 ProjectionRule。插件运行时输出反而变简单（翻译插件从 30 行构造 PluginItem 缩成一行 `data: result`）。理由见 §十一 ADR。

**0.14.5 收尾清理**：commit `df85f912` 落地时旧 tool-call 协议链路未按承诺删除（`PluginUpstreamMessage::ToolResult` / `ToolResultPayload` / `PendingToolMap` / `execute_tool` / `plugin_item_to_item_result` 整套休眠），0.14.5 已全部删除（query 路径的 `PluginResponse`/`PluginItem` 保留）。详见 git log。

## 八、后端分层与工程契约收敛

### 8.1 分层收敛

- 配置类型与 `ConfigStore` 下沉至 `src/domain/config/`；`src/app/{config,ai_config,stt_config}.rs` 只保留兼容 re-export，依赖方向不再由 domain/infra 反向指向 app。
- 以对象安全的 `DomainEnv` 隔离 `AppHandle`、Emitter 和 managed state，`TauriDomainEnv` 留在 app 层实现；Capability 调用上下文进一步只暴露 `CapabilityEnv`，不能取得窗口、事件、退出或 Action 执行权限，延续了 Capability-only 的类型墙。
- 图标提取、Shell 枚举、锁屏等 Win32 实现归入 `src/infra/platform/`；domain 只消费平台接口或封装结果。
- 原 `src/app/commands.rs` 按 config/search/ai/plugin/mcp/stt/clipboard/diagnostic 等域拆为 `src/app/commands/` 子模块，并继续把 AI 对话/管理、截图 OCR/右键菜单、FunASR 维护拆成职责子模块；所有 command 文件均低于 1000 行，IPC 公开路径保持不变。
- domain 生产路径中的异步任务统一改用 `tokio::spawn`；Tauri runtime 只剩需要异步初始化设计的 `ChatService` 构造期 `block_on`。

### 8.2 工程契约收敛

- `ToolSchema` 成为 Action/Capability schema 的三字段公共基；`CapabilitySchema` 只扩展 `sensitive`，rig 投影触点收敛到一处。
- 核心错误类型改用 `thiserror` 并补必要的类型转换；跨层错误仍需保留分类信息，禁止无差别拍平成字符串。
- Rust 与前端各有集中事件名清单；前端 invoke 统一经 `frontend/js/tauri.js`，禁止业务模块直接访问 `window.__TAURI__`。

## 九、前端拆分与回归护栏

### 9.1 文件拆分

前端三个巨石按职责拆分：截图 overlay 拆为 `ss-*` 模块，AI 设置拆为 `settings/tabs/ai/*`，对话样式拆为 `css/views/chat/*`；入口文件只负责装配和初始化。

### 9.2 拆分护栏

结构拆分必须保持外部契约不变，尤其要逐项核对：

1. Tauri `generate_handler!` 中的 command 与前端所有 `invoke()` 字面量；
2. Rust `blink://*` 事件常量与前端事件常量；
3. HTML/CSS/JS 入口的加载顺序、导出名和初始化时序；
4. 自定义协议与 IPC 的职责边界。截图像素继续通过 `blink-screenshot` 自定义协议读取，不能因拆分臆造 `screenshot_get_image` command。

这条护栏来自实际回归：截图模块拆分后一度把自定义协议误改成不存在的 command，静态核对后已恢复原取图链路。

### 9.3 0.14.7 工作

以下项目需要独立设计或重新做真实 UI/Windows 回归，不夹带在 0.14.6 的机械收尾中：

- **domain 彻底去 Tauri runtime**：把 `ChatService` 构造期同步 `block_on` 改成明确的异步初始化，并清理测试/Spike 中的 `tauri::async_runtime`；验收以 `rg "tauri::" src/domain` 仅剩说明性注释或为 0。
- **WinRT OCR 迁入 infra**：拆开 OCR 领域结果/文本拼接与 Windows SDK backend，避免 infra 反向依赖 domain；需要 Windows 真机验证识别文本、word rect 与旋转角。
- **command 结构化错误协议**：以已可序列化的 `CapabilityError` 为基础定义稳定 IPC error wire schema，先迁 Capability 相关 command，再扩展其他 `Result<_, String>`；同步前端错误渲染与兼容策略。
- **前端显隐状态收敛**：按窗口分批把历史 `style.display` 迁为 `.hidden` / `.is-open` 等 class，移除读取 inline style 判断状态的逻辑；每批重做对应窗口的亮/暗主题冒泡。

## 十一、关键决策记录（ADR）

- **11.1 插件协议迁移 —— 一次性切换**：旧 JSONL 协议直接废弃不留兼容层。理由：0.x 插件全自研，维护两套解析是纯负担。
- **11.2 ItemAction 声明 —— manifest 全显式**：不做"data 类型→默认 actions"自动派生。**职责分离**：协议层 actions 由 manifest 显式决定；展示层（主窗口）对无 actions 的标量 result 兜底隐式 copy。
- **11.3 多 action 交互 —— 回车首个/右键全部**：回车执行 `actions[0]`，右键展开全部。actions 顺序即优先级，作者把最常用动作放第一个。
- **11.4 JSONPath crate —— jsonpath-rust**：纯 Rust 零 C 绑定，符合无重依赖偏好。中文取值/数组通配/缺失降级已补单测。

## 十二、验收

- **0.14.0~0.14.5 协议重构**：投影引擎单测覆盖 4 shape × 3 desc 来源；AI tool 池只含 Capability（对话窗口 tool 列表无 lock/shutdown）；对话窗口调 translate/IP 时 AI 收到纯净 data（无 UI 噪音）；0.14.5 grep 验证旧 tool-call 死链路全清。落地时 `cargo test --bin blink` 为 1123 passed / 0 failed，三个插件 `cargo check` 通过。
- **0.14.6 架构清理**：`cargo fmt --check` 与 `cargo check --bin blink` 通过；拆分前 113 个 command 全部保留，前端 154 个字面量 invoke 全部命中后端注册，所有 command 文件低于 1000 行；Capability/Action 边界、Cap 投影链路、command/event 对照及前端模块链接静态检查通过。截图取图链路修复后，用户完成主链路冒泡测试，未发现功能回归。此前全量测试 1103/1108 通过，余下 4 项为 FunASR 沙箱目录写入失败、1 项为物理音频采集无数据，不属于结构拆分引入的断言失败。
