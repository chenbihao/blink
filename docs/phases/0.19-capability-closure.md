# Blink 0.19 - 能力闭环（补齐 AI 感知与执行的最后缺口，消除双入口债）

> **范围**：补齐图片获取与窗口感知能力、便签/pin 能力化、OCR 用户侧入口收编、alias 与双实现技术债清理。
>
> **状态**：🚧 进行中。
>
> **动机**：0.18 收尾后，能力底座仍有缺口--AI 看不到窗口布局、读不了剪贴板图片、不能操作便签/pin；同时 product.md §6.3 登记的多条"双入口/双实现"债待清理。0.19 作为"能力闭环"版本，给 0.20 向量版一个完整的能力层底座。
>
> **前置**：0.18（含 0.18.7/0.18.8）完成。
>
> **原则**：
> - 图片"获取"与"识别/消费"正交分离--不把 OCR/翻译/pin 等消费能力与图片来源绑死。
> - 复合操作在 Rust 侧完成，AI 只下指令收文本--不让 MB 级图片无必要经过 LLM channel（roadmap §7.3 架构原则）。
> - 用户侧 command 与 AI 侧 Capability 走同一个入口，消除双入口行为漂移。
> - 不引入"结果引用"跨调用机制（后置评估）。

## 二、背景与动机

### 2.1 为什么 0.19 做这件事

0.18 收尾时对截图/pin/翻译/OCR/便签五个能力做了一次载体形态审查，发现三类缺口：

1. **感知缺口**：AI 看不到屏幕窗口布局。`enumerate_pickable_windows()`（`infra/platform/window/list.rs:70`）已存在，返回 `Vec<PickableWindow>`（hwnd/x/y/w/h/title/process_name），但只被截图 overlay 前端经 `screenshot_window_list` command 拉取做 hit-test，**未包装为 Capability**，AI 完全看不到。这阻塞了"AI 截某 app""AI 把便签钉在某窗口旁"等所有定位场景。

2. **执行缺口**：AI 不能操作便签和 pin。`show_sticky_window`/`show_pin_window` 在 infra 层需要 AppHandle，而 Capability 的 `invoke` 只能拿到 `ctx.env: &dyn CapabilityEnv`（仅含 `db_pools`/`plugin_engine`/`search_service`）。便签/pin 窗口操作在 `DomainEnv` trait 里（chord action 专用），**CapabilityEnv 看不到**。用户场景"帮我把这件事钉个便签放右上角""读剪贴板图片钉桌面"无法实现。另外，AI 连"剪贴板里有哪些图片"都看不到--`search_clipboard_history` Capability 只查文本 `clipboard` 表（kind 硬编码 `"text"`），图片历史在独立的 `clipboard_images` 表，`ClipboardEngine` 搜索路径能查到但面向前端 GUI，**未暴露成 Capability**。

3. **双入口债**：product.md §6.3 登记的截至 0.18 技术债：
   - `capture_screen`/`crop_image` alias Capability 标 `TODO(0.13) 删除`，已过期 6 版本仍在
   - `open_url` command 路径走 `ShellExecuteW`、Capability 路径走 `open::that`，两套独立底层
   - OCR 用户侧 command 直调 `ocr_engine::backend()`，AI 侧走 `OcrImage` Capability，两条入口独立仅共用 backend

roadmap §7.3「CAP 闭环：AI 感知屏幕」候选与本主题高度重合，其轻量闭环档（AI 获取显示器/光标/前台窗口信息 + 截图入剪贴板）与 OCR 内部直链正是 0.19 要做的。

### 2.2 明确"不是问题"的（审查澄清，避免误改）

| 项 | 澄清 |
|---|---|
| **截图 overlay 的裸 command（copy/save/cancel）** | 这是 UI 交互指令（控制 overlay 状态机），不是"能力"，**不该进 Registry**。0.19 不动。 |
| **pin 窗口拖拽/缩放 command** | 同上，是窗口变换 UI 指令。0.19 只做"pin_image 创建"cap，不动拖拽/缩放。 |
| **便签窗口内编辑/防抖保存 command** | 是窗口内业务，直调 StickyService 合理。0.19 只做 create/set_geometry/list cap，不动 CRUD command。 |
| **OCR 是纯图片输入能力** | `ocr_image` 入参是 `png: [u8]`，不关心图片来源。这是正交的好设计，**0.19 不改 OCR 核心契约**，只收编用户侧入口。 |
| **screenshot { op: crop } 依赖 SESSION** | 这为 Alt+A 交互设计，用户截图后从 SESSION 裁剪。AI 路径用 `op:capture`（新截）或 `op:window`（按窗口），不依赖 SESSION。不改 op:crop 语义。 |
| **翻译用户侧 command 经 CapabilityRegistry** | 翻译是"用户 command 经 Registry 直连"的正确范式（因翻译逻辑在插件进程内）。0.19 的 OCR 收编照搬此模式，**翻译本身不动**。 |

## 三、核心设计 / 决策

### 3.1 图片"获取"与"识别/消费"正交分离（已定）

**定案**：不把 OCR/翻译/pin 等消费能力与图片来源绑死。补齐独立的图片获取能力（read_clipboard 读图、read_clipboard_history_image），消费能力（ocr_image 等）保持纯图片输入，组合权交给 AI。

**理由**：考虑"从剪贴板拿图片去 OCR"场景时，曾倾向做 `screenshot_and_ocr` 复合能力。但图片来源有 N 个（截图/剪贴板/剪贴板历史/文件）、消费者有 M 个（OCR/翻译/pin/存文件/多模态），N×M 复合能力会爆炸。OCR 现状（入参 `png: [u8]`，不问来源）已是正交好设计，0.19 保持不动，只补来源侧。

### 3.2 CapabilityEnv 桥接扩展--窗口副作用能力化（已定）

**定案**：扩展 `CapabilityEnv` trait，新增便签/pin 窗口操作方法。便签/pin 的 Capability invoke 通过 `ctx.env` 调窗口操作，不直接拿 AppHandle。

**理由**：现状 `DomainEnv` 有 `sticky_service()`/`create_sticky_and_show()`/`show_sticky_manager()`，但都在 `DomainEnv`（chord action 专用），`CapabilityEnv`（Capability 能拿到）只有 `db_pools`/`plugin_engine`/`search_service`。便签/pin cap 化必须让 Capability 能触达窗口操作。

**设计**：不把整个 `DomainEnv` 暴露给 Capability（那会让 AI 能调 `hide_main_window`/`exit_app` 等危险操作）。而是在 `CapabilityEnv` 上新增**最小必要**的窗口操作方法：
- `create_sticky_and_show(content, x, y, w, h) -> Result<String>` -- 创建便签并定位
- `show_pin_window(png_bytes, x, y) -> Result<()>` -- 显示 pin 图窗口（`show_translating` 参数对 AI 场景无意义，桥接层固定传 false）

这两个方法语义是"产生窗口副作用"，与 §3.3 的边界放宽配套。`TauriDomainEnv` 已 `impl CapabilityEnv`，直接转调 `infra::platform::window` 现有函数。

**演进方向**：当前两个方法直接加在 `CapabilityEnv` 上。随窗口类 cap 增多（如未来"移动便签窗口""pin 图翻译刷新"等），考虑抽 `WindowOps` trait，CapabilityEnv 加 `window_session() -> Option<&dyn WindowOps>`，避免 CapabilityEnv 表面膨胀。0.19 先直接加，不过早抽象。

### 3.3 Capability「不碰 UI」边界定义放宽（已定）

**定案**：在 `spec-architecture.md §A4` 明确--Capability 的"不碰 UI"指"不直接操作前端 DOM/事件流"，而非"不产生任何窗口副作用"。`open_url`/`open_path`/`reveal_in_explorer` 已有副作用（开浏览器/资源管理器）是先例，便签/pin cap 化同属此类。`CapabilityResult::Done` 变体（"已写入/已打开/已锁定"）就是为副作用准备的。

**理由**：invoke 文档原话"不碰 UI、不 emit、不弹窗"与 `open_url` 等 Capability 的实际行为有张力。0.19 要做便签/pin cap 化（操作 Blink 自己的窗口），必须在 spec 层把这条边界讲清楚，否则站不住。区分两层：
- **禁止层**（保持）：Capability 不直接操作前端 DOM、不 emit 前端事件、不弹模态框--这是"AI 不该越权操控用户界面流"。
- **允许层**（放宽）：Capability 可产生操作系统级窗口副作用（开浏览器、开资源管理器、显示便签/pin 窗口）--这是"AI 调用系统能力"的合理语义，与 `Done` 变体一致。

### 3.4 便签/pin 的 DangerClass 判定--标 Safe + sensitive，不标 Dangerous（已定）

**定案**：`create_sticky`/`set_sticky_geometry`/`pin_image` 标 `DangerClass::Safe`（不触发人机确认流程），但 `list_sticky`（读便签内容）和 `create_sticky`（写便签内容）标 `sensitive: true`。

**理由**：§A4 对 `DangerClass::Dangerous` 的定义是"有副作用的危险动作（改系统状态）"，例子是 lock/shutdown/写文件。便签创建/pin 图是可逆的（用户能关/删），不算危险。`open_url`/`open_path`/`reveal_in_explorer` 这些有窗口副作用的 Capability 都没标 Dangerous（它们是 Safe）。便签/pin 同属"可逆窗口副作用"，标 Dangerous 会与 open_url 标准不自洽。`sensitive` 覆盖隐私维度（读/写用户内容），与 §A4 两维判定一致。

### 3.5 OCR 用户侧收编照翻译模式（已定）

**定案**：用户侧 `ocr_image` command 不再直调 `ocr_engine::backend().recognize()`，改经 `CapabilityRegistry.get().invoke()` 调 `OcrImage` Capability，与 AI 走同一个入口。

**理由**：翻译已给出正确范式--用户侧 `translate_text` command 经 `CapabilityRegistry.get().invoke()` 查翻译插件，用户和 AI 走同一个 Capability。OCR 照搬。消除双入口行为漂移（加缓存/降级/语言参数只改一处）。

### 3.6 screenshot { op: window } 新增（已定）

**定案**：在现有 `screenshot` Capability 的 op 枚举中新增 `window` 操作，入参 `hwnd`，直接截指定窗口（用 `DwmGetWindowAttribute` 取窗口 rect -> 截对应区域），不依赖 SESSION 交互假设。

**理由**：AI 截某 app 的场景，若用 list_windows + op:capture + op:crop 组合，语义拧巴（AI 要伪造 SESSION）且多步。`op:window` 一步到位，语义清晰。

### 3.7 结果引用机制--0.19 不引入（已定）

**定案**：0.19 不引入"上一步结果引用"跨调用机制（如 `ocr_image { source: "last_screenshot" }`）。AI 需要组合时连续调用多个 Capability（read_clipboard -> ocr_image），图片在 LLM channel 传。

**理由**：结果引用涉及 CapabilityResult 跨调用状态管理，是新的架构机制，风险高。0.19 先铺基石+清债，图片过 LLM channel 的带宽优化后置评估。若实测成为瓶颈，再按 roadmap §7.3 的 `capture_to_clipboard` 复合操作模式局部优化（Rust 侧完成截图->剪贴板，AI 只收文本确认），不引入通用引用机制。

**收敛 open_url 双实现**（✅ 已完成）：

  1. `#[tauri::command] open_url`（`app/commands/search.rs:851`）直调 `ShellExecuteW`--独立入口
  2. `BuiltinAction { id: "open_url" }`（`builtin_engine.rs:138`）搜索召回，命中后经 `convert_legacy_arg_to_capability_args`（`search.rs:938`）转交 Capability 执行--**这条已收敛**
  3. `OpenUrl` Capability（`builtins/open_url.rs:66`）走 `open::that`--AI 路径
- **实施结论**：前端仍调用 `#[tauri::command] open_url`（`api.js`、`plugins.js`、`renderer.js` 三处），非死代码。已改经 `CapabilityRegistry.get().invoke()` 调 `OpenUrl` Capability，删 `ShellExecuteW` 直调。
- **审查确认**：`open_containing_folder`（独立 command，功能等价 `reveal_in_explorer` 但名称不同）和 `open_dir_in_explorer`（独立 command，功能等价 `open_path` 但只处理目录）不是双入口债--它们是独立 UI 入口的 command，不与 Capability 同名，0.19 不动。

### 5.2 0.19.1 - 图片获取基石：read_clipboard 读图 + 历史图片

**read_clipboard 增加图片分支**：
- `infra/platform/clipboard/windows.rs` 的私有 `read_clipboard_dib_with_hdrop` + `decode_dib` + `bgra_to_png` 提升为 `pub fn read_current_image() -> Option<Vec<u8>>`（返回 PNG 字节）
- `read_clipboard` Capability invoke 增加图片检测：先试 CF_DIB，有则返回 `Blob{mime: "image/png", bytes}`，无则 fallback 文本（现有逻辑）
- schema 更新：description 说明"返回文本或图片"

**新增 read_clipboard_history_image Capability**：
- 新建 `builtins/read_clipboard_history_image.rs`
- 入参 `{ id: String }`，调 `infra::data::clipboard_images::get_png_by_id`
- 出参 `Blob{mime: "image/png", bytes}` 或 `Done{summary: "无此图片"}`（id 不存在时）

**新增 list_clipboard_images Capability**（补 AI 图片列表入口）：
- 新建 `builtins/list_clipboard_images.rs`
- 入参 `{ limit?: int }`（默认 10），调 `infra::data::clipboard_images::query_recent_images`
- 出参 `Items`，每项 data 含 `{id, width, height, source_app, source_path, created_at}`，desc 为 `{width}x{height}` 或 source_app
- 标 `sensitive: true`（读剪贴板图片历史属隐私）
- **背景**：`search_clipboard_history` Capability 只查文本 `clipboard` 表（kind 硬编码 `"text"`），图片历史在独立 `clipboard_images` 表，AI 无从得知 image_id。此 cap 补上"AI 看到剪贴板有哪些图片"的入口，是"读最近剪贴板图片 pin 桌面"场景的前置依赖

### 5.3 0.19.2 - 窗口感知基石：list_windows Capability

**新建 list_windows Capability**：
- 新建 `builtins/list_windows.rs`
- 入参 `{}`（无参），调 `enumerate_pickable_windows()`
- 出参 `Items`，每项 data 含 `{hwnd, title, process_name, x, y, w, h}`，desc 为 `{title} ({process_name})`
- 标 `sensitive: true`（读窗口列表属隐私敏感数据，与 search_apps 同级）
- 无 actions（list_windows 是感知能力，不直接操作窗口）

### 5.4 0.19.3 - screenshot { op: window }

**screenshot Capability 新增 op:window**：
- `builtins/screenshot.rs` 的 invoke match 增加 `"window"` 分支
- 入参 `{ op: "window", hwnd: isize }`
- 实现：`spawn_blocking` -> 取窗口 DWM rect（复用/提升 `get_window_dwm_rect` 逻辑）-> 从虚拟屏幕截图裁剪对应区域 -> `encode_png`
- 出参 `Blob{mime: "image/png", bytes}`
- 不走 SESSION cache（与 op:capture 指定显示器同理，每次新截）

### 5.5 0.19.4 - OCR 入口收编（✅ 已完成）

**用户侧 ocr_image command 改经 Registry**：
- `app/commands/search/media.rs` 的 `ocr_image` command 不再直调 `ocr_engine::backend().recognize()`
- 改经 `app.state::<CapabilityRegistry>()` -> `invoke("ocr_image", json!({"png": png_data}))`，照搬 `translate_text` 模式（含 `TauriDomainEnv` 构造 `InvokeContext`）
- OcrImage Capability 返回 `Text{ content = OcrResult 的 JSON 序列化字符串 }`，command 侧 `serde_json::from_str` 解析回 `Value` 返回前端，返回类型不变
- **`ocr_diagnose` 保留为诊断专用直调**：`available_languages()` / `engine_language()` 是 `OcrBackend` trait 的诊断方法，不在 OcrImage Capability（只做 `recognize`）职责范围内，为诊断面板单独建 Capability 属过度工程
- 底层 `ocr_engine::backend()` 不动，OcrImage Capability 仍调它
- **错误码变化**：OCR 错误经 CapabilityError::Internal 包装后映射为 `internal_error`（原先为 `ocr_engine_error`/`image_decode_error`/`ocr_unsupported`），错误消息保留原文——与 `translate_text` 走同一套 `CapabilityError → CommandError` 映射，行为一致

- 标 `sensitive: true`（读便签内容属隐私）

### 5.7 0.19.6 - pin 能力化 + 截图入剪贴板复合操作

**CapabilityEnv 新增 pin 窗口操作**：
- `CapabilityEnv` trait 新增 `fn show_pin_window(&self, png_bytes: Vec<u8>, x: i32, y: i32) -> Result<(), String>`
- `TauriDomainEnv` impl 转调 `infra::platform::window::show_pin_window`（`show_translating` 参数固定传 false--对 AI pin 场景无意义）
- 注意：`show_pin_window` 签名要求位置为必填物理像素坐标（内部只做 `-PIN_PAD` 偏移，不算居中）。位置兜底逻辑在 Capability invoke 层处理（见下）

**新增 pin_image Capability**：
- 新建 `builtins/pin_image.rs`
- 入参 `{ png: [u8], x?: int, y?: int }` -- PNG 字节 + 可选位置
- 位置兜底：`x`/`y` 为 None 时，invoke 内部先 `parse_png_size(&png)` 拿尺寸，调 `get_primary_monitor_center(w, h)` 居中主屏（复用 `pin_clipboard_image` command 现有模式）
- 调 `ctx.env.show_pin_window(png, x, y)`
- 出参 `Done{summary: "已 pin 图到桌面"}`
- 标 `DangerClass::Safe`（§3.4：可逆窗口副作用不标 Dangerous，与 open_url 同级）

**screenshot { op: capture_to_clipboard }**（roadmap §7.3 复合操作）：
- `builtins/screenshot.rs` 的 invoke match 增加 `"capture_to_clipboard"` 分支
- 入参 `{ op: "capture_to_clipboard", display_id?: int }`
- 实现：`spawn_blocking` -> 截图 -> `encode_png` -> `write_bgra_to_clipboard` 或新增 PNG 写剪贴板 -> 不返回 Blob，返回 `Done{summary: "已截图到剪贴板"}`
- 目的：AI 只下指令收文本确认，MB 级图片不经过 LLM channel（roadmap §7.3 架构原则）
