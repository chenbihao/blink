# Blink 0.19 — 能力闭环（从“有能力”走向“真实可用”）

> **范围**：补齐窗口、图片、便签和轻量文本场景的真实闭环；让 command 与 Capability 复用同一语义实现；解耦图片编辑核心；以显式白名单开放常用 Blink 设置的自然语言读取与修改；收敛 AI 设置的信息架构、对话工具暴露边界与 MCP client 连接生命周期。
>
> **状态**：🚧 进行中（0.19.1–0.19.8 已完成；0.19.9–0.19.11 已规划）。
>
> **动机**：0.18 后 AI 的基础感知与执行能力已经形成，但便签仍停留在局部操作，文本文件缺少受控读取入口，command/Capability 仍有重复实现，图片编辑也与截图 SESSION 耦合，常用设置还不能通过自然语言安全修改；设置页又把对话行为、Skill、MCP、MCP Server、权限和底层记忆参数混在同一页，MCP client 预热还存在 focus 重试与并发重复连接。0.19 的后半段不继续堆能力数量，而是把高频链路做到可完成、可续读、可复用、可理解。
>
> **前置**：0.18（含 0.18.7/0.18.8）完成。
>
> **原则**：用户入口与 AI 入口共享业务语义，但不强制所有 UI command 经 CapabilityRegistry；大数据以引用或分页方式流转；轻量文本读取有显式单次上限，但不在 Capability 层全局截断结果；图片编辑先完成 UI/会话解耦；自然语言设置不暴露任意 KV 或密钥；纯对话模式只改变 Blink AI Agent 的工具装配，不削弱 CLI、MCP Server 等其他 Capability 出口。

## 二、背景与动机

0.19.1–0.19.4 已经回答“AI 能不能看到和执行”的问题，并补齐图片跨调用引用与窗口预热竞态；“真实闭环”仍有以下缺口：

1. 便签可以创建、列出和设置几何，却不能完整读取、修改和移入废纸篓；轻量文本文件也没有安全、可续读的入口。
2. 部分 command 与 Capability 虽然语义相同，仍各自实现校验、平台调用或窗口编排，行为可能逐渐漂移。
3. 标注与输出能力依附截图 SESSION，剪贴板图片、历史图片等来源无法复用同一编辑体验。
4. 设置页和 CLI 已能读写配置，但 AI 没有受控的设置目录与修改入口；直接暴露底层 KV 又会绕过热更新、校验和密钥边界。
5. “AI 对话能力”同时承载对话行为、Skill、MCP client、MCP Server、工具权限和底层记忆参数；其中部分高级开关已无运行时消费，超时展示值与后端真实默认值也不一致。
6. 对话窗口每次 focus 都会触发 MCP 全量补连，真实 prompt 又会在 `ensure_provider` 中再次触发；当前只检查已完成连接，不把 `Connecting` 视为占用，两个调用可为同一 server 建立重复 HTTP/SSE/stdio 会话并重复 bump tool pool epoch。

### 2.1 明确不是问题的

| 项 | 结论 |
|---|---|
| 所有 command 都必须经过 CapabilityRegistry | 不成立。UI 状态机 command 可以保留独立入口，但重叠业务语义必须下沉并复用。 |
| TextStash 是读取大文本的前置条件 | 不成立。文件路径天然可重放，按行分页读取比复制到进程内 stash 更直接。 |
| TextStash 能节省模型上下文 | 不成立。模型要理解文本时仍需接收内容；stash 只能延后传输，不能消除 token。 |
| 图片编辑入口必须先做 Capability | 不成立。0.19.7 先解耦用户侧编辑会话与截图来源，AI 能力化另行立项。 |
| 自然语言设置等于暴露任意 config key | 不成立。0.19.8 只开放稳定白名单，不允许模型读写原始 KV、密钥或任意 JSON 分片。 |
| 纯对话模式应关闭所有 Capability 出口 | 不成立。0.19.10 只让 Blink 自身 AI Agent 不装配工具；CLI、内部调用和 Blink MCP Server 的 canonical 能力不受影响。 |
| Skill、MCP client 与 MCP Server 是同一种能力 | 不成立。Skill 教 AI 如何做，MCP client 给 Blink AI 引入外部工具，MCP Server 则把 Blink 能力提供给外部应用。它们可以同属“AI 扩展”设置页，但必须分区表达方向。 |
| 对话窗口首次可见时预热 MCP 一定不合理 | 不成立。首次可见激活后在后台预热可以隐藏首轮 prompt 的连接耗时；问题是每次 focus 都重试、连接过程不可合并，以及状态读取带有启动连接的副作用。 |
| 截图 overlay 的 capture/crop/长截图状态机 | 仍是截图专属交互，不强行抽成通用图片能力。 |
| `CapabilityResult::Blob` 保留原始字节 | Blob 是 AI、CLI、MCP、前端共用的通用二进制协议，不因 ImageStash 改变。 |

## 三、核心设计与决策

### 3.1 图片来源与消费者正交（已定）

截图、剪贴板、历史记录等能力只负责产出图片；OCR、pin 等能力只负责消费图片，避免为每组来源和消费者增加复合能力。

### 3.2 窗口副作用通过最小桥接暴露（已定）

`CapabilityEnv` 只暴露创建便签、读取便签服务和显示 pin 窗口所需的最小方法，不向 Capability 开放完整 `DomainEnv`。窗口类能力继续增加时再评估抽取 `WindowOps`。

### 3.3 Capability 的 UI 边界（已定）

Capability 不直接操作前端 DOM、事件流或模态交互，但可以产生打开路径、显示便签/pin 等操作系统级窗口副作用。通用约束以 `spec-architecture.md §A4` 为准。

### 3.4 风险与敏感性分开判定（已定）

便签与 pin 的窗口副作用可逆，因此是 `Safe`；读取或写入用户内容的能力另标 `sensitive: true`。涉及删除时优先采用可恢复的“移入废纸篓”语义，不在本阶段增加永久删除能力。

### 3.5 用户入口复用 Capability 语义，而非机械统一入口（修订）

`open_url` 和 OCR 用户 command 已经由 CapabilityRegistry 调用对应能力。0.19.6 不再追求“所有 command 都经 Registry”，而是把重叠的校验、平台调用和业务编排下沉为共享语义实现：Capability、command、Chord 或其他入口只做各自协议适配。截图 overlay 的 copy/save/cancel、pin 变换、编辑器窗口生命周期等 UI 状态机 command 保持独立。

### 3.6 ImageStash 图片引用闭环（0.19.4 归档，已定）

应用进程级 `ImageStash` 保存模型调用间的图片字节；图片 Capability 仍返回完整 `Blob { mime, bytes, desc }`，agent 投影层将 `image/*` Blob 移入 stash，并返回机器可读的 `image_ref`。引用可复用，创建起 15 分钟固定过期且读取不续期；最多 16 项、总计 64 MiB、单项 32 MiB，超限按最早创建顺序淘汰。

`pin_image`、`ocr_image` 和 `write_clipboard` 图片模式兼容 `image_ref` 与原始字节二选一输入，公共解析与 MIME/PNG 校验由同一 helper 完成。引用不持久化、不写入日志，应用重启后失效，也不能绕过图片生产能力的敏感授权。

### 3.7 便签闭环与轻量文本按模式读取（0.19.5 定案）

便签正文读取、更新和移入废纸篓复用同一份领域语义，但“复用 `StickyService`”不等于只写数据库：更新与回收必须检查 `rows_affected`，对不存在或已回收记录返回明确错误；正文更新携带 `expected_updated_at` 或等价 revision 做乐观并发校验，避免 AI 覆盖用户刚在便签窗口中的编辑。移入废纸篓还要通过最小环境桥接隐藏对应窗口并通知便签管理器刷新，使 DB、桌面窗口和管理界面保持一致。

新增 `read_text_file` 时，文件路径就是稳定引用。能力只接受绝对路径，先读取文件元数据，再以流式方式执行指定模式，不把整文件一次性载入内存或模型上下文。

输入采用一个互斥的扁平契约，避免 `line`、`head`、`tail` 同时出现后产生组合歧义：

| 参数 | 语义 |
|---|---|
| `path` | 必填，文件绝对路径。相对路径、目录和不存在路径明确拒绝。 |
| `mode` | 必填，`metadata \| range \| head \| tail`。 |
| `line` | `range` 必填，1-based 起始行；其他模式传入即报 `InvalidArgs`。 |
| `limit` | `range/head/tail` 必填，请求的最大行数；`metadata` 禁止传入。受服务端行数、token 与字节硬上限共同约束。 |

`metadata` 不返回正文，只返回 `size_bytes`、`modified_at`、文件类型和轻量文本/二进制探测结果，让 AI 先判断是否读取。`search_files` 同期透传搜索后端已经提供的可选 `size_bytes` / `modified_at`；Everything 当前已请求这两个字段但尚未保留，本地 fallback 缺失时 AI 可再调用 `metadata` 获得可靠结果。

正文输出采用结构化结果，包含 `content`、实际 `start_line/end_line`、是否到达 EOF、是否因预算截断、`next_line`、`size_bytes`、`modified_at`、读取字节数和估算 token 数。`range/head` 在尚有后续内容时返回 `next_line`；`tail` 直接返回文件末尾的实际行范围，不提供续读游标。默认预算为约 **2,000 estimated tokens**，单次硬上限为约 **4,000 estimated tokens** 且不超过 **32 KiB**；任一上限先到即停止。调用方不能请求绕过硬上限。

首版只承诺 UTF-8（兼容 UTF-8 BOM），拒绝二进制和其他编码；不记录文件内容。若单行自身超过单次字节硬上限，返回明确的 `line_too_long` 错误，不返回半行，避免 `next_line` 造成内容重复或丢失。

能力标记 `sensitive: true`。0.19 继续沿用现有按工具名确认与权限记忆，不在本子版本引入路径级授权；规范化路径、目录范围、symlink/reparse point 与逐路径授权作为 Agent 能力增强统一评估，见 `roadmap.md §4.5`。

上述限制是 `read_text_file` 作为“轻量、分页读取器”的公开语义，不是 Capability 层的全局输出截断策略。Capability canonical result 不因 AI 上下文预算被偷偷裁剪；CLI、MCP 与内部调用都得到相同的分页结构和续读信息。若某个 AI 或展示出口还需适配模型上下文，应只在该出口投影，并保留 canonical data 契约。

### 3.8 command/Capability 一致性以共享语义实现为准（0.19.6 定案）

对语义重叠入口建立行为矩阵，逐项核对参数校验、副作用、来源标记、错误映射、日志、敏感性与危险级别。收敛目标是“同一语义一个实现、不同协议薄适配”，不是合并所有注册表，也不改变现有 command 返回契约。

优先核对并收敛：剪贴板读写与截图复制、图片加载与 pin、便签创建/更新/几何/回收站编排，以及 OCR 用户入口与 Capability。`ActionRegistry`、`ChordRegistry` 和 `CapabilityRegistry` 的整体合并不属于本子版本。

实施后，剪贴板阻塞隔离、来源标记、BGRA 校验和历史图片加载统一归 `domain::clipboard`；通用 pin 的尺寸解析、缺省定位和窗口创建统一归 `CapabilityEnv::show_pin_image`；便签创建、正文更新与回收的 DB/事件/窗口编排统一归 `TauriDomainEnv` 的最小桥接。OCR command 继续经 `CapabilityRegistry` 调 canonical `ocr_image`，仅在 IPC 边界投影回既有 JSON 返回。

### 3.9 图片编辑先分离来源、会话与输出（0.19.7 定案）

把当前实现拆成三层：图片来源适配（截图、剪贴板或历史）、通用编辑会话/画布（标注工具、撤销重做、编辑状态）、输出适配（复制、保存、pin）。截图 SESSION 继续负责屏幕捕获、区域选择与长截图；进入编辑阶段后转换为通用编辑载荷，不再让标注核心依赖截图采集状态。

0.19.7 至少接入一个非截图来源验证通用入口，优先复用当前剪贴板图片；保持截图、长截图、OCR/翻译和原有输出行为不回退。本阶段不新增图片编辑 Capability，不把用户编辑会话绑到 ImageStash，也不提前设计 AI 驱动的编辑协议。

### 3.10 自然语言设置使用显式目录与字段级更新（0.19.8 定案）

新增只读设置目录/查询能力与写入能力。对模型暴露稳定的设置 id、类型、可选值、当前值和简短说明，而不是 SQLite KV key 或完整配置 struct；写入只接受单个或少量字段级 patch，复用设置页的校验、持久化、运行时热更新和 `CONFIG_CHANGED` 通知语义，并返回旧值、新值及是否立即生效。

首批白名单只覆盖高频、可逆且含义稳定的设置，例如主题、窗口透明度、搜索结果数/分页、搜索历史开关与天数、自动建议开关、剪贴板监听及保留/展示数量。写入能力每次调用都要求 AI 确认，不复用按工具名记忆的自动放行；确认卡片必须展示 setting id、旧值和新值。读取目录不暴露用户内容，也不返回底层未列入白名单的配置。

首版明确排除：API key 与任何 secret、AI Provider 详情、代理、解释器路径、插件/MCP 配置、权限记忆、调试日志，以及热键/Chord 改键。CLI 的原始 `config get/set` 也不作为实现真源，因为其裸 KV 写入不承担设置页已有的运行时副作用；0.19.8 应抽取或复用 canonical 应用层配置更新服务，让 command 与 Capability 都成为薄适配。

### 3.11 AI 设置按行为、扩展与对外服务重组（0.19.9 定案）

AI 设置保留“AI 供应商”，把原“AI 对话能力”改名为“AI 对话设置”，并新增“AI 扩展” tab。对话设置只承载对话模式、自动标题、上下文与历史等用户能理解的行为；AI 扩展承载 Skill、MCP 外部工具、工具授权，以及单独标注为“对外服务”的 Blink MCP Server。`AI 插件` 会与搜索域插件混淆，`AI 技能` 又无法覆盖 MCP Server，因此 tab 统一命名为“AI 扩展”。

清理“高级”中的失效或错位配置：当前固定走 `stream_prompt`，因此移除无非流式消费路径的“流式输出”开关并保持流式为默认行为；移除无运行时消费的“允许直接执行 Safe 动作”和“工具结果回流 AI”设置，旧字段如为兼容保留也不得继续出现在 UI；System Prompt/工具 token 信息移至 AI 扩展或调试；权限记忆移至 AI 扩展的工具授权分区。

硬超时是真实可靠性设置，保留在折叠的高级设置中。模型请求与 Capability 工具调用的统一默认值为 **20 秒**：首字等待本身可能超过 5 秒，不能用 2.5 秒作为伪默认。设置页、序列化默认、运行时 fallback 和提示文案必须显示同一有效值；未显式覆盖时 UI 显示 20 秒，而不是显示一个与后端实际执行不同的值。

记忆功能保留但重写用户语义：普通设置只突出“自动上下文管理（Token 感知）”“召回本对话较早内容”和真实的模型上下文容量；固定条数、触发阈值、裁剪目标、Top-K 如继续开放，应放入折叠的专家设置。UI 必须说明当前实现是裁剪并归档，不是 LLM 摘要；FTS5 召回限定在当前持久对话，不宣称跨对话长期记忆；主窗口 Ephemeral 对话不展示为受这些持久记忆参数控制。上下文容量不得再用固定 60% 和 TokenAware 模式下无效的 `window_size` 推导“约 N 轮”。

### 3.12 纯对话模式与 Skill 运行时开关（0.19.10 定案）

新增“纯对话模式”（默认关闭），不用“轻量模式”命名，避免与轻量模型档位混淆。开启后，Persistent 与 Ephemeral 两类 Blink AI 对话都不装配内置 Capability、不连接或收集 MCP client 工具，也不注入 Skill 摘要或触发全文；模型选择、流式回答、对话历史和自动标题保持可用。该模式不修改 CapabilityRegistry canonical data，不关闭 CLI、内部调用或 Blink MCP Server。Agent cache key 必须包含对话模式或在切换时可靠失效，禁止复用此前带工具的 Agent。

Skill 总开关必须形成真实运行闭环：关闭后立即清空或旁路运行时 SkillRegistry，不能只保存 `enabled=false` 却让已扫描 Skill 在本进程继续触发；重新开启后按当前来源和单 Skill 禁用清单重新扫描。纯对话模式与 Skill 总开关是两个正交条件：前者控制当前 Blink AI Agent 是否装配任何扩展，后者控制 Skill 子系统自身是否可用。

### 3.13 MCP client 连接按生命周期 single-flight（0.19.11 定案）

MCP 的“状态查询”“连接意图”和“工具快照”必须拆开。读取 tool pool 或在线状态只读当前快照，不得隐式启动连接；对话窗口首次真正显示后可以发起一次后台预热，但普通 focus、popup 刷新和状态查询不再全量重连。配置新增/启用、用户手动启动或重试、首轮真实 prompt 是明确的连接触发点；失败 server 默认进入 30 秒冷却期，避免切窗或重复 prompt 形成连接风暴，手动重试和配置变化可绕过冷却。

`McpClientManager` 以 server name 维护连接中的 single-flight。无论预热、`ensure_provider`、设置页操作还是其他 command 同时请求同一 server，后来的调用都复用或等待同一个连接任务，不能再各建一套 HTTP/SSE/stdio 会话。`Connecting` 不只用于展示，还必须对应真实的运行时占用；成功后只提交一次连接、只在 tool pool 实际变化时 bump 一次 epoch，失败也由唯一任务统一发布状态。

每个 server 同时维护单调递增的配置 generation 或等价 fingerprint。连接任务启动时捕获 generation，提交连接和状态前必须再次校验；连接中途若发生禁用、删除或同名配置修改，旧任务必须取消或在完成后关闭旧 transport 并丢弃结果，禁止旧配置回流覆盖新状态。手动重试可以绕过冷却，但不能绕过 generation 提交校验。

不同 server 采用有上限的并发连接，避免当前串行流程把首轮准备时间累加为所有 server 耗时之和；默认并发上限取 3，并保留独立失败隔离。prompt 若遇到正在进行的预热，应加入同一批任务而不是另起连接，但 MCP 工具准备有独立的 5 秒等待预算；预算内完成的 server 进入本轮稳定 tool snapshot，超时后本轮立即用已就绪工具继续，剩余连接可在后台完成并通过 epoch 让下一轮 Agent 重建。这里的 5 秒只限制 MCP 前置准备，不替代模型请求与 Capability 工具调用的 20 秒硬超时。纯对话模式跳过预热和 prompt 侧 MCP 连接；MCP 不可用只减少本轮外部工具，不应阻断纯模型回答。

### 5.5 0.19.5 — 便签真实闭环 + 轻量文本文件读取（已完成）

- 新增 `read_sticky`、`update_sticky`、`trash_sticky` 并通过 inventory 注册；`list_sticky` 同步返回 `updated_at`，形成“创建 → 查询/读取 → 带版本修改 → 可恢复回收”闭环。
- `StickyService` 与 data 层现在检查实际写入结果，明确区分不存在、已回收和 revision 冲突；同秒写入也用单调递增 `updated_at` 保证版本变化。回收后同时识别普通窗口与借用的 `sticky-spare-*`，隐藏窗口并广播 `STICKY_TRASHED` 刷新管理器。
- 新增敏感只读能力 `read_text_file`，只接受绝对路径，运行时与 schema 同时约束 metadata/range/head/tail 及 line/limit 组合；metadata 只返回大小、修改时间、文件类型和轻量文本探测，不含正文。

- `search_files` 修正 Everything HTTP 元数据列参数，保留 `size_bytes` 与 FILETIME 转换后的 `modified_at`；本地 fallback 在既有后台扫描中同步缓存可得元数据。缺失时仍可用 `read_text_file { mode: "metadata" }` 补查。

### 6.8 0.19.11 验收

- [ ] 同一 server 被窗口预热、prompt 和设置操作并发触发时只建立一条 HTTP/SSE/stdio 连接，状态与 tool pool epoch 只发生一次有效迁移。

- [ ] 不同 server 最多 3 个并发连接，单个失败不阻断其他 server；prompt 复用同一预热任务且 MCP 准备等待不超过 5 秒，预算到期后仍可用已就绪工具或纯模型回答。
- [ ] server 在 Connecting 时被禁用、删除或修改配置，旧任务不得提交旧连接、旧状态或额外 epoch；旧 transport 被关闭。
- [ ] 纯对话模式下窗口激活与 prompt 均不触发 MCP client 连接；关闭纯对话模式后可按正常生命周期恢复。
