# Blink 0.18 — 增强与 Chord 体验（Enhancement: Chord）

> **范围**：bug 修复合集（AI 模式右键复制 / AI 输出后失焦关窗 / pin 右键失效 / 便签隐藏按钮断链 / AI 工具调用空泡泡 / 主窗口 AI 模式滚轮失效）；pin 图翻译捷径与右键能力补全；截图控件级智能吸附（UIA，配置开关默认关）；便签即时预览编辑（IR）；托盘菜单重组；命令执行（`> ` 前缀调起终端）；NSIS 卸载清理收敛；Alt/Chord 键值底层状态流转重构。
>
> **状态**：🚧 进行中。
>
> **动机**：0.17 打磨后日常使用仍暴露多处交互断点——AI 输出无法复制选中、AI 答完即被看门狗误关、pin 右键失效、便签管理"隐藏"按钮只改 DB 不收窗、便签编辑形态退回纯文本。同时 chord 能力的"快"尚未充分释放：截图翻译需三步、托盘菜单扁平且缺 chord 入口、缺少命令直达。0.18 在不引入大架构变更的前提下，补全这些断点并为命令执行模式（终端模式）打地基。
>
> **前置**：0.17（Cherry Markdown 统一、主窗口 AI 架构、便签体验深化）；0.15（截图重设计、annotation-engine 解耦、pin 图）；0.16（剪贴板图片、共享 Markdown）。
>
> **原则**：0.18.0～0.18.6 不做大架构变更，bug 修复与既有能力补全优先于新功能；0.18.7 是为解决安装后 Alt/Chord 多真源状态异常而追加的、限定在输入基础设施内的可靠性重构，不改 Chord 动作、键位配置和产品交互语义；命令执行 MVP 只做"调起终端"不做主窗口内联终端（PTY）。

## 二、背景与动机

### 2.1 为什么 0.18 做这件事

**贯穿叙事**：0.18 的每个子版本都在缩短某条高频操作的路径，呼应 `product.md §6.2 最小操作路径`这条核心信念。除了 0.18.0（修 bug）和 0.18.5（收敛卸载）两项基建，其余子版本的产品价值都可量化为"步数下降"：

| 子版本 | 缩短的路径 | 原路径 → 新路径 |
|---|---|---|
| 0.18.1 | 截图翻译并 pin | 截图→pin→右键→翻译（4 步）→ 截图→翻译并 pin（2 步） |
| 0.18.2 | 截图选区精度 | 手拖微调对齐控件边 → 悬停吸附控件 |
| 0.18.3 | 便签编辑 | 纯文本编辑无法预览渲染 → 预览即编辑 |
| 0.18.4 | 开 AI 对话窗口 | 记住 Alt+Q → 托盘直达 |
| 0.18.6 | 执行命令 | 开终端→cd→输命令（3 步）→ `> cmd`（1 步） |
| 0.18.7 | Alt/Chord 可靠性 | 前后端四套状态互相补偿 → 单一后端状态机驱动 |

0.17 闭环渲染引擎统一与主窗口 AI 架构后，日常深度使用暴露四类问题：

1. **AI 交互断点**（P0，阻塞使用）：AI 输出区选中文本右键无"复制"——`contextmenu.js::unifiedMenu` 只读搜索框 `queryEl.selectionStart/End`，对 div 选区无效；AI 流式输出 `Done` 后，`ai.rs` 的后台 stream task 收尾时 `set_main_ai_active(false)`，看门狗恢复失焦隐藏，用户还在看结果就被关窗。
2. **pin 图断链**（P0）：pin 右键菜单 CSS bug（`pin.css` 把 `#ctx-menu` 基础规则写成 `display:none`，与 `.hidden` 类显隐约定冲突），摘掉 `hidden` 类菜单仍不显示；截图翻译到 pin 需"截图→pin→右键→翻译"三步，无直达路径。
3. **便签编辑形态回退**（P1）：0.17.7a 曾接入 Cherry 左右分栏 Live Preview，因产品目标实为"即时预览编辑"（IR）而非分栏，0.17.11 回滚至纯 textarea。需按正确形态重做。
4. **chord 入口零散**（P2）：托盘菜单扁平、缺 AI 对话窗口入口；便签隐藏按钮只改 DB `visible=false` 不 hide 桌面窗口（管理面板碰不到桌面窗口句柄）；卸载无论升级与否都弹清理框，升级误点致数据全失。
5. **截图选区精度**（P2）：0.15.8 已有窗口级吸附（悬停虚线框→单击吸附到窗口矩形），但对按钮/输入框等子控件仍需手拖微调。控件级吸附（UIA）可作为窗口吸附的更精细补充——配置驱动、默认关闭，不破坏现状。

### 2.2 明确"不是问题"的（避免误改）

| 项 | 结论 |
|---|---|
| 便签"关闭只隐藏、删除才移除"语义 | **有意设计**（0.16.8）。本 phase 不改语义，只修"隐藏按钮"的副作用断链（隐藏应同时收起桌面窗口）。见 §3.2 |
| pin 不做完整 word 拖选阅读模式 | **有意设计**（pin.html 注释）。要 word 交互需重新 Alt+A 截图。本 phase 不改 |
| annotation-engine 与截图 overlay 的耦合 | annotation-engine **已解耦**（1632 行独立引擎，命令栈驱动）。本 phase pin 编辑如需复用，重点在"抽容器接口"而非重写引擎。见 §3.1 |

## 三、核心设计 / 决策

### 3.1 pin 图：翻译捷径 + 右键链路修复

**3.1.1 pin 右键失效修复（0.18.0 内）**

- **定案**：`frontend/css/views/pin.css` 的 `#ctx-menu` 基础规则 `display: none` → `display: flex`。初始隐藏仍由 HTML 上 `class="hidden"` 负责，显隐由 `.hidden` 类控制（与 `chord-screenshot.css` 约定对齐）。
- **理由**：ID 选择器特异性 1,0,0 > `.hidden` 类 0,1,0，摘掉 `hidden` 类后 `display:none` 仍生效。这是唯一根因，改一行即可。拖拽能用是因为拖拽走 `imgScreenX/Y + screenshotPinTransform` 纯逻辑路径，不碰 DOM 显隐。

**3.1.2 翻译捷径（0.18.1）**

- **定案**：截图工具栏在现有"翻译"按钮**右侧**新增"翻译并 pin"按钮，不改原有翻译功能。点击后：截图选区 → OCR + 翻译嵌图（`ss-ocr.js::doOverlayTranslate`，译文经 `annotation-engine` 的 overlayLayer 渲染到标注 canvas）→ 翻译异步完成后调 `ss-output.js::doPinSelection`（它内部 `compositeSelection` 已把"选区+标注+overlay"合成进 canvas 并转 PNG，无需额外栅格化步骤）→ pin 到桌面。
- **理由**：保留原 OCR↔翻译 tab 联动（活图优于死图），同时提供"一步到位"捷径。比"把译文烧进图"的静态方案（方案 B）更可逆、复用现成能力、工作量小。
- **关键技术点**：`overlayLayer` 是 annotation-engine 内部的**数据结构**（非 DOM），由 `redrawAnnotFull()` 渲染到 canvas；`compositeSelection` 合成的就是含 overlay 的标注 canvas。所以"翻译并 pin"= `doOverlayTranslate` + 等翻译完成回调 + `doPinSelection`，无新合成逻辑。
- **pin 后关联**：pin 住的图保留现有右键"识别文字/翻译"入口（pin 内 OCR 面板），用户仍可切换原文/译文 tab。

### 3.2 便签：即时预览编辑 IR（0.18.3）

- **定案（形态）**：便签编辑采用**即时预览编辑（IR，Instant Rendering）**--在渲染后的预览区上直接编辑（输入 markdown 语法后实时渲染，如 `# ` 空格变 H1）（点击文本即进入编辑，光标在渲染元素内），**不是**左右分栏（左 md 源码 / 右预览）。这是 0.17.11 回滚左右分栏方案的根本原因。
- **理由**：用户目标是"预览上直接编辑"，左右分栏是 agent 误读需求。回滚后纯 textarea 是退化态，本 phase 按正确形态重做。

> **术语区分**：IR（即时渲染）≠ WYSIWYG（所见即所得）。
> - **IR**（Typora / Vditor IR / Obsidian Live Preview）：用户输入 markdown 语法，实时渲染但标记短暂可见后消失，**存储为 markdown 文本**。用户心智是"写 markdown，实时看效果"。
> - **WYSIWYG**（Word / CKEditor / TinyMCE）：语法完全隐藏，靠工具栏/快捷键排版，**存储为 HTML/JSON**。用户心智是"像 Word 一样排版"。
>
> Blink 便签要的是 **IR**（存 markdown、输入语法实时渲染），不是 WYSIWYG。早期文档用"WYSIWYG"描述此需求是不准确的，0.18 spike-A 阶段修正。Tiptap 底层是 WYSIWYG 引擎（ProseMirror），但通过 inputRules + `@tiptap/markdown` 序列化层实现了 IR 体验 + markdown 存储，满足需求。

#### spike-A 结论（已完成）

Cherry Markdown 全系不支持 IR（即时渲染），编辑形态只有双栏和纯预览。选型 **Tiptap（自打包 IIFE）**：esbuild 打包 `@tiptap/core+pm+starter-kit+markdown`（v3.29.2，四包同版）为 IIFE 单文件放 `vendor/`，`cargo xtask tiptap` 执行。API 要点：初始化传 `contentType: 'markdown'`，序列化用 `editor.getMarkdown()`。

**无 bundler 铁则定案**：esbuild 一次性打包成 IIFE 单文件是预处理产物（同 `cargo xtask icons`），运行时零构建，不引入构建流程。详见 spec-frontend §1.5。

**排除 Vditor**（实质停更）、**Milkdown**（强依赖 bundler）、**Toast UI Editor**（传统富文本非 IR）。

### 3.3 托盘菜单重组（0.18.4）

**现状**：tauri 原生 `TrayIconBuilder` + `MenuItem`（`src/app/tray.rs`），5 项扁平：显示主窗口 / 设置 / 便签管理 / 关于 / 退出。

**定案**：仅重组菜单项顺序与分组，不做自定义样式窗口。重组后结构：

```
显示主窗口
─────────
便签管理
AI 对话窗口      ← 新增（现仅 Alt+Q 可达，补非快捷键入口）
─────────
设置             ← 从关于上方提至此组顶部
关于 Blink
─────────
退出 Blink
```

- **理由**：新增"AI 对话窗口"项符合可辨识度原则（非快捷键用户也能开）；设置上提因其使用频率高于关于；便签管理 + AI 对话窗口归为"chord 能力组"。不做自定义样式——托盘菜单使用频率低，视觉统一收益边际递减，且 Popup 菜单的 DPI/焦点处理需单独调，性价比低。
- **实现**：`src/app/tray.rs::build_menu` 调整 MenuItem 顺序与分隔符，新增"AI 对话窗口"项的 id（如 `chat_window`）+ `main.rs::on_menu_event` 路由（拉起 chat 窗口，复用 chord Alt+Q 的 `invoke_chat_window` 链路）。

### 3.4 NSIS 卸载清理收敛（0.18.5）

- **定案**：把 `nsis/uninstall-cleanup.nsh` 从 `NSIS_HOOK_PREUNINSTALL` **挪到 `NSIS_HOOK_POSTUNINSTALL`**，去掉无条件 `MessageBox`，改用 Tauri 默认模板已提供的 `$UpdateMode` / `$DeleteAppDataCheckboxState` 变量做守卫。
- **根因**：目录错配——Tauri 默认删 `$APPDATA\com.blink.launcher`，但 Blink 数据实际在 `$APPDATA\blink`。Tauri 2.11.5 默认 `installer.nsi` 已内置"勾选才删 + 升级跳过"守卫，两个变量在所有 hook 宏内可见。
- **POSTUNINSTALL 而非 PREUNINSTALL**：Blink 清理是"补删默认模板删不到的目录 + 凭据清理"，属于默认删除完成后的补充，放 POST 更顺且避免重复守卫。
- **凭据清理修复**：0.17.11 密钥存储从自写 FFI（CM target = `blink/{pid}/{purpose}`）切换到 keyring crate（CM target = `{pid}/{purpose}.blink`）。旧 `findstr "blink/"` 对新 `.blink` 条目失效；修复为 `findstr "blink"` 覆盖两种命名 + `tokens=1,*` 取完整 target name。
- **轻量验证结论**：`com.blink.launcher` 仅存在于 `$LOCALAPPDATA`（WebView2 缓存，Tauri 默认逻辑已覆盖），`$APPDATA` 下不存在。`$APPDATA\blink` 是实际数据目录，需本钩子补删。
- **范围**：仅改 `nsis/uninstall-cleanup.nsh`，不动 `tauri.conf.json`，不动 Rust。
- **版本耦合提示**：此结论基于 tauri 2.11.5。Tauri 升级时需复核默认 `installer.nsi` 模板是否改动这两个变量的定义或作用域。

### 3.5 命令执行 MVP（0.18.6）

- **定案（MVP 范围）**：主窗口输入框打 `> ` 前缀 + 命令 → 回车后**调起外部终端窗口**执行该命令（Windows Terminal 优先，fallback cmd.exe），**不在主窗口内联渲染命令输出**。不维持 shell 会话。
- **理由**：完整主窗口内联终端（xterm.js + conpty PTY）工作量大、与无 bundler 铁则有张力、对常驻内存有威胁。MVP 先验证"`> ` 前缀 → 命令直达"的产品价值与交互形态，内联终端作为增强项放 phase 末尾再评估。
- **触发**：`> ` 前缀在 `frontend/js/main-window/search.js::onInput`（或 `keyboard.js` 回车处理）拦截，不走 ghost 体系（ghost 是被动建议，`> ` 是用户明确意图）。命中后调后端命令拉起终端。
- **前缀交互状态机（产品体验定案）**——`> ` 是 Blink 首次引入"用户主动声明意图模式"，第一眼体验决定它成不成立：

  | 输入态 | 结果区显示 | 说明 |
  |---|---|---|
  | `> ` 单独（无命令） | 空结果 + 一行 hint："输入命令，回车在终端执行" | 明确告知用户这个模式的语义，避免对着空结果发愣 |
  | `> ec...`（命令未输完） | 空结果（不把 `ec` 当搜索词查应用） | `> ` 出现瞬间进入"命令模式"，搜索结果区清空且不再响应增量搜索；避免半截输入触发无关应用结果造成视觉跳动 |
  | `> echo hi` + 回车 | 关主窗口 → 调终端执行 | 执行后主窗口按既有逻辑隐藏 |
  | 退格删到 `>` 消失 | 恢复正常搜索模式 | 模式边界清晰，用户可随时退出 |

  **模式切换铁则**：进入命令模式后，结果区的渲染/键盘逻辑要完全切支（不触发 search、不显示 ghost、回车不走默认搜索项执行）。退出（删掉 `>`）则完整恢复。这避免命令模式与搜索模式互相污染。
- **后端命令**：新建 `src/app/commands/terminal.rs`，`#[tauri::command] pub async fn run_in_terminal(command: String)`。实现：`ShellExecuteW("open", "wt.exe", "-d <cwd> cmd /K <command>")`，探测 `wt.exe`（`where wt.exe`）存在则用 WT，否则 fallback `cmd.exe /K <command>`。复用 `src/app/commands/search.rs` 的 `ShellExecuteW` 范式。
- **安全**：命令执行是用户主动输入，不走 Action trait 的危险动作白名单（那是给 AI tool-call 用的）。但需在产品文档明确"任意命令执行"的边界。

> **关于编码**：因 MVP 调起外部终端、不在主窗口内联输出，**GBK 编码问题在 MVP 阶段不存在**（终端自己处理编码）。只有未来做内联终端（捕获 stdout 到主窗口渲染）时才需引入 `encoding_rs` 按系统 ACP 解码。这是 MVP 选"调起终端"而非"内联执行"的额外好处。

### 3.6 截图控件级智能吸附（0.18.2）

**3.6.1 与窗口吸附的关系——不是并存，是降级链**

0.15.8 已实现**窗口级吸附**（`ss-hover.js` + `screenshot_window_list` → `enumerate_pickable_windows`，EnumWindows ~5-15ms，悬停虚线框→单击吸附）。控件吸附不取代它，而是作为更精细的一层叠加：

```
控件级吸附（UIA，细）  →  窗口级吸附（Win32，现状，粗）  →  纯手拖（兜底）
   开启且 UIA 命中          现状默认开启             两者都未命中
```

前端 hit-test 优先级：**控件优先于窗口**（控件矩形是窗口矩形的子集，鼠标同时落在两者内时应吸附到更小的控件）。

**3.6.2 遮挡问题如何绕开——用 fg_hwnd 不用 ElementFromPoint**

UIA `ElementFromPoint` 返回该坐标最顶层元素，但截图 overlay 是 always_on_top 全屏透明窗 → 会返回 overlay 自己。**解法**：不查鼠标位置，查"被截图的前台窗口"：

- `screenshot::session_fg_hwnd()`（`mod.rs:113`）在截图唤起前已记下前台窗口 HWND
- 用 `ElementFromHandle(hwnd)` 取元素，**不关心 overlay 盖没盖**——我们只读控件的 BoundingRectangle，不 hit-test 坐标

**3.6.3 超时 + 深度双重约束——替代白名单（已定）**

> **定案**：不维护进程族白/黑名单。用 200ms deadline + 3 层深度限制让 UIA 树质量差的应用（Electron 巨树）自然超时降级，UIA 树质量好的应用（Win32/Office/WPF）在 budget 内返回。

- **为什么不要白名单**：白名单会过时、维护成本高、对公平性差（新应用需手动加）。资源约束（超时+深度）是自适应的——UIA 表现好的应用自然受益，差的自然降级，零配置。
- **为什么逐层 BFS 而非一把 subtree**：UIA 的 COM 调用**无法 cancel**。spawn 一个线程做 `FindAll(TreeScope_Subtree)` 再设超时"放弃结果"，那个跨进程 COM 调用仍在后台跑（对 Electron 可能跑数秒）——资源占用、潜在死锁，脏。逐层 BFS（`TreeScope_Children` 每次拉一层，每层/每元素前检查 deadline）超时自然停，无杀线程副作用。
- **层数 = 3 的依据**：记事本 1 层够（编辑框）、计算器 2 层（分组→按钮）、WPF/Office 一般 3 层到有用控件、Electron 第 3 层仍是 chrome 容器（被超时挡掉，无害）。深度与超时双重保险，谁先到都停。

**3.6.4 配置驱动、默认关闭——零回归**

`ScreenshotConfig`（定义于 `src/domain/config/shards.rs:336`，非 `config.rs`）新增 `control_snap: bool`（default: false）。前端 overlay 加载时读配置，`false` 时**根本不发起** `screenshot_control_hints` 调用——默认体验与现状逐字节一致。

**3.6.5 时序——异步收集，不阻塞 overlay 显示**

```
1. Alt+A → begin_session()（截屏，记 fg_hwnd）
2. show_screenshot_overlay()（overlay 立刻显示，用户立刻能拖）   ← P0 不阻塞
3. [后台 spawn_blocking] UIA 逐层 BFS 收集控件矩形（200ms deadline）
4. emit("blink://control-hints", rects) 下发前端
5. 前端收到 → pickableControls 缓存就绪，hover 时启用控件 hit-test
6. 未收到/为空 → 维持窗口吸附，用户无感
```

用户手快在 hints 到达前开始拖拽——本次即为自由拖拽，hints 到达不打断已开始的交互（只在"未开始拖拽时"激活 hover 预选）。

**3.6.6 数据契约——ControlHint 结构**

后端 `enumerate_control_hints` 返回 `Vec<ControlHint>`，经 `screenshot_control_hints` command 序列化下发前端。坐标全部是**虚拟屏幕物理像素**（与截图 SESSION 同坐标系），前端 `rectScreenToCss` 转 CSS（复用 `ss-selection-geometry.js`，与窗口吸附同款转换）。`ControlHint` 含 `{x, y, w, h, control_type, name}`，其中 `name` 仅后端 trace 级日志用于诊断，**不下发前端展示**（避免泄露界面文本）。

前端 `ss-control-hints.js` 接收后转 CSS 坐标缓存，结构与 `ss-hover.js::pickableWindows` 同构（`{x,y,w,h}` 即可），hit-test 复用 `pointInRect`。

### 3.7 键值底层状态流转重构（0.18.7）

- **定案**：以单线程 `InputStateMachine` 统一 Raw Input、WH_KEYBOARD_LL、tap/hold timer、窗口 visible 和主窗口视图上下文；后端成为 Alt 与 native exclusive Chord Session 的唯一真源。
- **删除目标**：前端 50ms Alt 轮询、`set_chord_mode` 反向控制、`ALT_LOGICALLY_HELD`、`CHORD_MODE/CHORD_KEYS` 独立状态以及 200ms 合成 Alt keyup 猜测。
- **行为边界**：不改 ChordRegistry、动作、bindings、requires_input 文本解析和语音业务；WindowHidden 结束 Chord Session，但绝不伪造物理 Alt 释放。

**核心架构决策**：

- **单线程输入引擎**：Hook 线程同时承载 LL Hook、message-only window + Raw Input、Timer 和纯 reducer。Hook 同步返回 Pass/Swallow，业务副作用通过 channel 发出。Hook 回调无锁、无 DB、无 Tauri、无 await。
- **双源采集**：Hook 是动作边沿与 Pass/Swallow 唯一权威；Raw Input 只校正修饰键 level。同一 Win32 时间域做乱序过滤，按 hDevice 保存每设备状态，设备移除时清除。
- **四类独立 ID**：`gesture_id`（主键 down→up）、`chord_session_id`（Chord Session，不复用 gesture id）、`window.revision`（show/hide 乱序）、`ui_revision`（前端事件/快照去重），互不串用。
- **窗口状态与物理键解耦**：所有 visibility 写入收敛到统一 helper；`on_focused(true)` 不写 Visible；Alt-held 唤起须 `show → Visible ack → Chord Session 建立 → SHOWN` 顺序，超时不伪造 Chord active。
- **Chord Session 后端拥有**：前端只上报 `ready/query_empty/ai_mode` 离散上下文，不反向修改物理状态；前端 chord 操作用 `inputState.isAltDown() || e.altKey` 抵抗 synthetic keyup。
- **Effect 分发**：Tap/window 立即执行保持 `<50ms`；Voice/Chord 各进独立串行 worker，互不阻塞。已提交的 Tap/Chord 不因后续事件回查丢弃。
- **Recorder/Voice 集成**：Recorder 纳入输入线程——`Recording` 模式下禁 Tap/Hold/Chord/VoiceCancel effect，录制完成递增 gesture id 使后续 keyup 不触发正常快捷键。Voice 用 `VoicePhase` 三态（Idle/Starting/Recording，后两者绑定 gesture id）替代独立 atomic——generation-aware wiring 按 gesture id 保证 Start→Release/Cancel 配对，不被乱序/过期事件破坏；ESC 仅在 Starting/Recording 时产生 VoiceCancel。
- **配置快照**：Hook 线程只持有 app 层派生的不可变 `InputConfigSnapshot`（含 hotkey/tap_threshold/chord_enabled/exclusive_tap_keys/voice_hold_enabled）；五类配置更新统一调 `refresh_input_config` 推送完整 snapshot。主热键在 Armed 时冻结该 gesture 的配置，配置更新从下一次 gesture 生效。`state.rs` 不依赖 domain/Tauri/Win32。
- **首次状态同步**：前端注册 listener → `register_main_input_view` 获取快照 → 以 `ui_revision` 去重；`ready` 不因普通 hide/show 重置。

### 3.8 截图多屏混合 DPI 坐标收敛（0.18.8）

**背景**：多屏混合 DPI（如主屏 100% + 副屏 150%）下，截图 overlay 用"窗口级单一 dpr"折算所有屏的几何，副屏 CSS 矩形失真，导致窗口/控件预选区虚线框、桌面边界高亮、工具栏 clamp、选区->pin 坐标整体偏移。

**核心决策**：

1. **per-monitor dpr 分段换算**——`build_displays_json` 每屏用自己的 `dpi` 折算成 CSS 注入 `displays`（每项增加 `dpi` 字段）；前端 `screenToCss`/`cssToScreen` 不再接收单一 `dpr` 参数，改为内部按坐标落在哪块屏取该屏 `dpi/96` 分段换算。新增 `dprAtScreen`/`dprAtCss`/`cssSizeToPhysical` helper 供直乘散点收口。找不到屏时 fallback `window.devicePixelRatio`（兼容单屏/降级）。

2. **dpr 用法四类分类**（关键知识，后人改截图 dpr 必读）：
   - **A 类**（屏幕坐标换算，CSS 点→屏幕物理坐标）：改走按屏查 dpr（`dprAtCss`/`cssToScreen`）。涉及 `ss-hover.js`/`ss-control-hints.js` 预选区定位、`ss-output.js`/`ss-ocr.js` 的 `cssToScreen`、`ss-toolbar.js`、`scroll/index.js`。
   - **B 类**（输出裁剪尺寸，CSS 尺寸→屏幕物理尺寸）：改走 `cssSizeToPhysical`。涉及 `ss-output.js` copy/composite 裁剪宽高。
   - **C 类**（主 canvas bitmap 映射，CSS 坐标→主 canvas backing store 物理像素）：**保留 overlay dpr**（`window.devicePixelRatio`）。原因：主 canvas backing store = 全屏 bitmap 物理像素，CSS `width:100%` 铺满 overlay 视口，bitmap↔CSS 映射比全局固定为 `window.devicePixelRatio`，**物理上无法按屏分段**。涉及 `ss-draw.js` 蒙版绘制、`ss-reading.js` 命中检测、`index.js` 标注 canvas/cropData。
   - **D 类**（canvas 绘制粗细/手柄/线宽）：**保留直读** `window.devicePixelRatio`（对齐 overlay 渲染分辨率）。

3. **跨 dpr 边界选区 clamp**（spike-B 策略 2）：选区从一块屏拖向不同 dpr 的另一块屏时，clamp 到起点屏边界。同 dpr 屏间不 clamp（双 100% 屏跨屏安全）。边界坐标归属 `displays` 数组靠后命中项（`findDisplayCssAt` 用"最后一个命中"语义），避免抖动。

4. **pin 拖拽跨屏修正**：`pin.html` 拖拽去掉多余的 `* dpr`——Win32 PerMonitorV2 下 `e.screenX/Y` 已是物理像素，不需要乘 `window.devicePixelRatio`。旧代码 `* dpr` 在单 dpr 下因 dpr=1 碰巧能工作，跨 dpr 屏时 `window.devicePixelRatio` 变化导致 `imgScreenX/Y` 漂移。

5. **剪贴板钉图居中**：`clipboard.rs::get_primary_monitor_center` 从 `SM_CXSCREEN`（主屏单屏）改为 `GetCursorPos`+`MonitorFromPoint`+`GetMonitorInfoW` 取光标屏工作区中心。

**不动的防护**：`place_at_physical`、`dpi.rs`、虚拟屏坐标系（物理像素 1:1 的 `screenToBitmap`/`crop`）、PerMonitorV2 进程级 awareness、DWM 扩展边框窗口吸附精度——均已正确，0.18.8 不触碰。
