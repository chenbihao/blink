## 二、背景与维护澄清（0.29.1 语音流式）

云端 `CloudSttEngine` 只累积样本、录音结束才上传，说话期间无预览。OpenAI Whisper HTTP 接口没有流式，官方流式走 Realtime WebSocket（`/v1/realtime?intent=transcription`）；自部署 sensevoice-server 实现了同款协议且为真增量预览。

**不是问题的**（避免误改）：

- **G2 预览重叠不是消费侧防护不足**。`voice.rs` 的三层防线（Draft 到达即按边界整条删除重叠段、Preview 整体替换后再按已见 Draft 最大边界过滤、同段定稿后迟到 delta 不复活）是完备的；重叠根因在引擎侧方言误判（§3.2）。
- **长语音不分段不是客户端漏处理**。切段是服务端行为，切段时会发 `completed` 与新 item，客户端正确处理；不分段的原因是服务端端点阈值（§3.6）。
- **TRACE 档记录转写正文不违规**。[后端 spec §3.2](../specs/spec-backend.md) 铁则 5 对用户内容留有 trace 级例外；压制 tungstenite 的理由是不受控的整帧 dump（§3.5）。
- **SSE（`stream=true`）不是增量流式**。它是整段事件流格式，SenseVoice 收完整个文件才推理；流式价值只在 WS。

## 三、核心决策与维护要点（0.29.1 语音流式）

### 3.1 只做 WS 真流式，不可用时回退整段上传

连接失败自动回退整段上传，用户无感。不做"VAD 切句 + 滚动窗口 HTTP 请求"的伪流式 transport（对按次计费端点请求量放大）。

### 3.2 单方言：累计 delta

delta 一律按**累计替换**处理（每次是当前段的完整最新版，含尾部修正），会话配置统一 funasr 风格。**不做 OpenAI 官方方言**。

**踩坑**：曾按 `kind == "openai"` 走增量拼接。自部署服务配 `kind=openai` 很常见，而 funasr 服务无论 kind 都发累计 delta，拼接导致 G2 预览逐帧重复全文。官方方言本就不可用（官方要求 24kHz，客户端发 16kHz），半套适配只会产出错误拼接，故整体删除；官方端点会拒绝配置并回 error，可见失败好于静默乱字。

### 3.3 原生 port 与 port 内回退

`CloudStreamingPort` 原生实现 `StreamingSttPort`，回退也在 port 内完成（`CloudSttEngine` 累积样本，终态发本 port 总线）。

**踩坑**：回退曾借道 `GgufStreamingAdapter`，其事件发在适配器自己的总线、generation 也各自计数，不支持 WS 的端点（Groq/MiMo）每次回退都**静默丢失整段结果**。另：WS 中途出错后 `finish_session` 必须返回 Ok 且不补 Final，否则 `voice.rs` 会兜底再交付一次空文本。

### 3.4 事件映射与收尾

delta → Preview / Partial（走 preview latest-slot）；`completed` → Draft span / 带 confirmed 的 Partial；`finish` 发 commit 后有界等待（3s 预算，`committed` 后 1s 宽限收静音尾），再发 Final。item 切换重置段预览，span 范围按客户端已推样本计数近似。事件投递复用 `streaming_port::EventBus`，与本地引擎同一套 generation 墙与背压语义。

**已知边界**：`finish` 超时兜底的文本 = 已定稿累计 + 未定稿预览尾巴。服务端积压时预览远未识别完，兜底会**丢失尾部内容**；服务端按 §3.6 调优后回归语料不再触发。

### 3.5 日志分层

`tungstenite` / `tokio_tungstenite` 恒压 warn（`logging.rs::parse_level` 的 transport_noise 组）：库在 TRACE 下逐帧刷内部细节，并把完整帧以 hex + JSON 各 dump 一份（含 base64 音频）。转写内容由 `realtime_ws` **仅在 TRACE 档**受控记录（delta 预览 / completed 定稿 / Final 正文，不含音频），与 AI 对话日志同模式。

### 3.6 服务端调优：`--vad-maxseg` 是唯一有效的强制分段旋钮

部署默认 `SV_VAD_MAXSEG=8000`、`SV_PARTIAL_MS=600`、`SV_THREADS=4`（环境变量注入，调参免重建镜像）。依据（`sensevoice-server.cpp` 源码 + 真实语料）：

- **端点静音阈值写死，会话前 60 秒恒为 ~1850ms**（`acc` 每满 60 秒才累加一次），自然停顿达不到，中途基本不切段。`session.update` 的 `silence_duration_ms` / `threshold` 服务端不消费。
- **partial 同步阻塞读循环**：每次预览对整个开放段重识别，段越长越慢 → append 积压 → TCP 反压 → commit 排在队尾。
- 段长有上界，单次 partial 耗时才有上界；`--vad-maxseg` 与 `--partial-ms` 需联动（单次 partial 耗时须小于节流间隔）。

**已知边界**：强切不找静音点，切点处会多一个句末标点、字符增删 0~1 字；根治需上游在强切前回退到低能量点，不在客户端处理。

## 四、复用与范围边界（0.29.1 语音流式）

复用 `StreamingSttPort` 契约与 `EventBus`（可见性放宽为 `pub(crate)` 并补充投递/统计方法）、`CloudSttEngine`、`SttConfig.streaming_mode`（默认 Pseudo 即云端流式默认开，无 schema 迁移）、`parse_level` 噪音压制机制、`voice.rs` 的 `finalize_engine(Option)`。

| 未纳入 | 理由 |
|---|---|
| OpenAI 官方 Realtime 方言 | 需 24kHz 重采样 + 增量 delta + `transcription_session` 事件的完整适配，且无官方端点可验证 |
| 伪流式 HTTP transport | 见 §3.1 |
| `finish` 超时后整段 HTTP 补救 | 调优后尾段定稿在 3s 预算内，无触发场景；多段会话的尾段起点对齐有重复上屏风险 |
| reader 收发解耦 | `send_text().await` 被反压阻塞时会连带停掉事件接收；调优后回归反压为 0，留作服务端劣化时的防御项 |
| 用服务端段偏移做精确 span 范围 | 当前近似范围偏粗但文本不重叠 |

### 5.2 0.29.2 — 截图细节打磨（翻译仅图层 + 工具栏居中 + 大内容翻译治理 + 划词收起 + 选区保留标注）

**决策**：翻译按钮与文本面板解耦——翻译只管译文图层（overlay mode），面板的开/关完全归[识别]按钮（`doPanelToggle`）与面板自身 X。此前翻译首击同时开面板（译文 tab），面板译文 tab 激活时再点翻译又是关面板，两个控件生命周期纠缠。

- **翻译按钮 toggle 语义按 overlay mode**（`doOverlayTranslate`）：译文图层显示中再点 → 关图层（`setOverlayMode(null)`，面板不动）；已有识别结果 → 直接挂图层、缺译文走 `requestOverlayTranslation` 补翻，不重跑 OCR；无结果 → OCR + 翻译仅落图层（`activateOverlay` 两处 `openPanel: false`，含 `_runOcrFresh` 翻译分支）。错误路径本就面板无关（`showTransientHint` + `panel?.` 判空），无需额外兜底。
- **按钮激活态**（`updateToolbarButtonActive`）：无面板时从"两个按钮都不亮"改为跟随 overlay mode——仅图层模式下翻译按钮保持点亮反馈；有面板时仍跟随 tab。
- **面板落地 tab**（`doPanelToggle`）：缓存开面板本就不重跑 OCR；0.29.2 起译文图层显示中开面板落**译文 tab**（译文区由 `showOcrResult` 从 overlay 回填，与屏上内容一致），否则原文 tab；开面板后补 `updateToolbarButtonActive`（此前开面板路径漏刷按钮态）。
- **工具栏默认落位水平对齐**（`positionToolbar::place`）：选区宽 ≥ 工具栏视觉宽 → 右对齐（原行为不变）；窄于 → 与选区居中，再按目标屏钳制。视觉宽每次实测（`intrinsicWidth * uiScale`），自定义工具栏宽度不固定（布局编辑器 / more 收纳 / 跨屏缩放）天然覆盖；`keepAnchor` / `userMoved` 保留路径与垂直策略（下方→上方→浮动）不受影响。

**大内容翻译"插件忙"治理**（实机反馈：大选区翻译转圈 → 取消 → 再次翻译报"插件忙"）。根因链：翻译插件 manifest `concurrency: 1` + `timeout_ms: 10000`；大选区单次巨批撞超时后，前端降级**逐行**请求且循环只在全部结束后校验版本号——用户取消后循环仍逐行占用插件唯一并发槽（`try_acquire` 槽满即报 Busy），期间任何新翻译立即"插件忙"。三层修复：

- **前端分批 + 可中断 + 渐进上屏**（`translateOverlayLines` 重写）：按 20 行/批调 `translate_lines`（命令侧批内去重不变），每个 await 后校验 `selectionRevision`/`translationRevision`（ESC/重选/新任务都会递增），过期立即中止；批失败仅对该批逐行兜底（同样可中断）；每批完成渐进回填 overlay（未翻行保持原状），DOM loading 文案带进度 `翻译中 n/m…`。全部失败仍上抛展示失败原因，部分失败保留原文提示。
- **插件 tool-call 槽位有界排队**（`PluginHandle::acquire_tool_slot`）：`execute_tool_raw` 槽满不再立即 Busy，改为在调用方剩余预算内排队（§4.4"排队计入同一总期限"的落地），等待者上限 `TOOL_WAITER_CAP=8` 超限仍 Busy；超时由外层 deadline 统一裁决。`query` 路径（搜索 keyword）保持快速失败——占位→错误项的即时反馈语义不变。
- **等待者计数守卫**（`ToolWaiterGuard`）：排队计数在任何退出路径（获得槽位/超时/调用方取消）都递减，取消泄漏不会让后续调用误判等待者已满。
- **划词选区单击收起**（`ss-reading.js::finishHitPointer`）：文字上或真空白处的静止单击（未跨 3px 拖动阈值）收起已有划词选中，与文本编辑器"点击收起选区"一致。此前 `finishHitPointer` 在未过阈值时既不更新也不清除 `selectionStart/End`，单击无任何反馈，只有切换标注工具与面板内取消两条清除路径。拖动形成/更新选区、`pointercancel`/`lostpointercapture` 清理路径不受影响；`clearReadingSelection` 同时收起面板 textarea 选区（guard 与正向同步一致），图↔面板不再一清一留。
- **编译警告清零**：`realtime_ws` 移除未用 `endpoint` 参数（测试注入入口保签名改 `_endpoint`）、仅测试使用的 `with_finalize_wait` 标 `#[cfg(test)]`；`bootstrap` 删除下载速度诊断残留变量；suggestion `ai.rs` 去掉 `&str` 上 noop `.clone()`；`agent_provider` 测试未用绑定改 `_addr`。`STATIC_VCRUNTIME` 弃用环境变量迁移为 build.rs 的 `WindowsAttributes::static_vc_runtime(true)`（默认即 true，行为不变）。**踩坑**：先试了 tauri.conf.json 的 `build.windows.staticVCRuntime`，workspace 侧 tauri-build 2.7.4 接受，但本机 cargo-tauri CLI 的 config schema 不认识该键、`cargo tauri dev` 直接拒绝启动——config 键的兼容性受 CLI 版本制约，代码属性不受；该环境变量若仍在构建终端里设置会继续触发告警（且优先级更高），从 shell/profile 移除即可。

**选区调整保留标注图层**——语义按交互类型分派（`ss-selection-geometry.js::preserveCommandDelta` 纯函数，可测）：底图是同一张全屏截图，选区移动/缩放只是裁剪窗口变化、内容不缩放，因此保留 = 纯平移/裁剪，无需缩放坐标。**纯移动（尺寸不变）= 跟随**：命令坐标不平移、画布随新原点移动，标注跟随选区整体转移（选区与标注视为刚性一组，移动不丢标注）；**缩放（尺寸变化）= 裁剪**：命令按新旧裁剪区原点差平移，标注钉在屏幕内容原位，出界部分由画布边界自然裁掉（"变小了则裁剪"）。**语义演进留档**：初版按"统一钉住屏幕内容"实现（移动也按原点差平移 → 标注留在原屏幕位），实机两轮反馈暴露两处反直觉——移动选区会把标注留在原地、移出选区即被裁掉（观感是"标注丢了"），且拖动期间的实时跟随预览与提交语义不一致（松手标注回跳）；当初"箭头指错内容"的担忧让位于刚性一组的直觉，定稿按交互类型分派。

- **引擎原语**（`annotation-engine.js`）：`translateCommands(dx, dy)` 平移全部命令坐标——所有命令类型统一以 `points` 数组承载坐标（两点工具取首尾、笔刷取轨迹），平移即遍历加法；撤销/重做栈原地平移、`undoIndex` 不变；顺带清过期的 Shift 连线锚点。`rebase(w, h, cropData)` 与 `reset` 的区别：保留 commands/undoIndex/水印，只更新画布 backing 尺寸与裁剪数据后全量重放；马赛克/模糊在新 cropData 上取到的仍是同一屏幕位置的像素，天然正确。
- **接入**（`index.js::enterAnnotationMode(rect, {preserveFrom})`）：`preserveFrom` 传交互前原选区时按 `preserveCommandDelta` 分派（缩放才 translate，纯移动只 rebase），不传（新框选/窗口吸附）维持 `reset` 清空。三条路径接入：move/resize 完成（`ss-interaction.js::finishSelectionInteraction` 传 `interaction.original`）、move/resize 中断恢复（`abortSelectionInteraction`，新旧矩形全等 → 不平移，等效未动过——此前中断也会清掉标注）、方向键微移（`flushSelectionNudge` 改为 rebase-only：画布随新原点移动 + 刷新裁剪底图，命令不平移，与拖动移动同一跟随语义）。
- **连续交互（实机反馈修复：拖动期间标注层不再隐藏、方向键微移工具栏不再消失、拖动/松手所见即所得）**：拖动激活阈值（3px）处 `invalidateSelectionContent` 改传 `preservePresentation: true`——只失效 OCR/翻译/划词内容态，标注层与工具栏保持可见（此前激活即隐藏、松手才恢复，交互断裂）。标注层与实线框同帧同步（`ss-live-selection.js::syncAnnotationLayer`，与边框同一 rAF 帧写入，仅过激活阈值后介入），且实时预览与提交语义一一对齐：**移动**= 标注层整体平移跟随（提交时命令不平移，松手停在跟随位、无回跳）；**缩放**= 内容钉在屏幕原位，用 `clip-path: inset()` 按实时选区逐帧裁掉选区外部分（读自身样式算交集，不触发布局；扩边时 inset 各项自然钳 0），松手提交的 translate+rebase 落定同一边界，无"放开鼠标才刷新定位"的跳变。clip 的清理统一归 `enterAnnotationMode` / `exitAnnotationMode`（提交/中断必经）。GIF 准备模式自带的区域拖动（手动平移标注层、不走 `selectionInteraction`）天然不冲突。方向键微移路径此前同样调无参 invalidate：工具栏被隐藏且无人再显示（一次微移即永久消失），修复为 preserve + `positionToolbar(selCss, true)` 同步重定位。配套两处：`enterAnnotationMode` preserve 重入改 immediate 定位（非 immediate 的「-9999 移出 + rAF 测量」会把拖动期间保持可见的工具栏闪走一帧）；行为改进——用户手动拖过的工具栏位置（`data-user-moved`）在选区调整后不再被重置回默认右下角（与 GIF 区域平移同一保留语义）。
- **不变项**：OCR 嵌字/划词仍由 `invalidateSelectionContent` 在交互激活时失效（内容窗口变了）；GIF 录制区域的 `updateCropData` 用法独立，不受影响；水印（配置型单例）与撤销栈随 rebase 保留。

### 5.3 0.29.3 — 截图数位笔输入修复

**背景**（用户反馈 + 录屏，2026-11-20）：数位笔在截图选区/标注中"像鼠标失灵"——拉不出选区（选区出现一瞬又消失、只遗留定位标识）、标注画笔按下没反应、提笔后笔画轨迹仍在生长、笔一提光标变回箭头。代码排查定位到接收端四处确定缺陷；触发源（数位板驱动"接触=切换左键"语义 vs WebView2 笔事件丢失）待诊断日志证实，**防御性修复与触发源无关、先行落地**。

**根因（代码侧接收端，均已实锤）**：

- 笔画悬挂"鬼画"：pointermove 笔画分支不查 `e.buttons`——数位笔提笔后仍在悬停感应范围（`buttons=0` 的 move 持续到达），pointerup 一旦丢失，`isAnnotDragging` 悬挂后悬停移动继续喂点；且 `pointercancel` 处理器因 `hasActiveDragInteraction` 刻意不含笔画态（0.23.15 约定）直接 return，笔画态无人收口。
- 选区塌缩：pointerdown 无"拖拽中重入"守卫——上一轮 up 丢失后新按下把在途拖选重置 0×0（录屏"选区一闪即逝"）。
- 光标变箭头：`pointerleave` 在 select 工具下设 `default`——数位笔每次提笔出感应范围都触发 pointerleave（鼠标几乎不会），与 `updateSelectionCursor` 的 crosshair 语义自相矛盾。
- 短笔触被吞：铅笔 <2px 位移按"点击设连线锚点"丢弃、笔刷类 minDrag=3——笔尖精度下随手就是 2px 内的短笔触（"按下没反应"）。

**修复（`index.js` 为主，行为对鼠标等价、阈值放宽仅对 pen）**：

- **笔画收口统一** `finishAnnotationStroke`（pointerup / pointercancel / pointermove buttons 守卫 / pointerdown 重入守卫四路共用），提交语义与原 pointerup 分支一致（minDrag 丢弃 / 铅笔小位移锚点 / endDraw 提交）；`pointercancel` 发生在笔画中改为提交已画部分（用户墨迹是真实工作，不因系统中断丢弃）。
- **pointermove buttons 守卫**：按 `ss._annotPointerId` 匹配同一指针（防另一只鼠标的悬停 move 误杀在画笔画），`buttons&1` 丢失即按提笔收口。
- **pointerdown 重入守卫**：`isAnnotDragging`/`isDragging` 悬挂时新按下先把上一轮按当前位置收口——拖选 ≥5×5 直接提交为选区（重入语义 = 用户意图的"松手点"）；<5×5 丢弃且**不走 200ms 单击隐藏 overlay 定时器**（新交互已开始，迟到的隐藏定时器会关掉整个 overlay）。
- **笔画也起 pointer capture**（修订 0.23.15 "笔画不 capture"旧约定，`index.js` 文件头注释同步）：提高 pointerup 送达率；收口已多路兜底，capture 不再是唯一保障。
- **contextmenu 刚收笔 400ms 守卫**：笔长按右键（Windows press-and-hold）紧跟笔画结束触发，吞掉避免标注态误复制选区/非标注态误取消截图。
- **pen 阈值放宽**：铅笔点击阈值 2px→0.5px、minDrag 对 pen 上限 1px（`TOOL_CAPS` 不动，收口处按 `pointerType==='pen'` 放宽）。
- **`#canvas` 加 `touch-action: none`**：笔/触摸拖拽不被浏览器手势接管，减少 pointercancel。
- **空引用兜底**：`exitAnnotationMode` 清 `isAnnotDragging`/`_annotPointerId`（ESC 中断在途笔画不再悬挂）；`finishAnnotationStroke` 对 `selCss` 已清空的场景直接丢弃笔画（`annotationPoint` 会解引用 `selCss.x`）。

**临时诊断日志（`pen-diag`，问题定位后整体移除）**：`index.js` 模块级捕获 window 阶段 pen/touch 指针事件（down/up/cancel/lostpointercapture 全记；move 只记 buttons 状态翻转）入 300 条环形缓冲 + `console.info`；异常收口（重入/丢按钮/取消中笔画/吞 contextmenu）单独计数。**用户取消会话且存在异常时自动复制缓冲到剪贴板**并提示（走 `copy_to_clipboard` command，WebView 的 `navigator.clipboard` 不可靠），正常使用不碰剪贴板。判读要点：`pointermove-buttons-flip` 提笔瞬间（1→0）有无紧邻 `pointerup`——无则证实驱动"接触=切换"语义或事件丢失；`type` 字段直接判驱动模式（pen=Ink / mouse=鼠标模拟）。

**0.29.3-r2 实测迭代**（2026-11-20 第一轮实机反馈：画笔可画但**抬笔后下一笔被连成一笔**、**选区仍一闪即逝只留定位标识悬浮**）。定位结论：

- **两笔相连**：提笔的 pointerup 仍未送达，r1 的收口靠"下次 pointerdown 重入守卫"完成，而重入收口把**新按下点**当上一笔终点 → 上一笔被直线连到新按下位置；且若悬停流谎报 buttons=1 或换了 pointerId，r1 的 buttons 守卫拦不住，悬停路径直接进笔迹。
- **选区闪逝**：同一提笔事件在选区路径以 pointercancel / lostpointercapture 收尾，r1 只给笔画补了收口，这两条仍走 `abortSelectionInteraction` 整段丢弃选区（画笔/选区"待遇不同"正解释了本轮反馈的差异化结果）；悬浮的定位信息 = 非标注态悬停 move 仍驱动的像素放大镜。

r2 修复（`index.js`）：

- **收口终点一律用最后已知点**：`finishAnnotationStroke` 增 `atCurrent`（沿用 `annotCurrentX/Y`，悬停/新按下坐标不进笔迹）；重入守卫的拖选收口改用 `endX/endY`；pointercancel 笔画收口同样 atCurrent。
- **提笔判定升级**：`buttons 丢 1` 或 `penLiftByPressure`（本会话见过真实压力 >0 后，pen `pressure===0` 即悬停——**自校准闩锁**，无压感恒 0 上报的驱动自动禁用该信号防误杀）；pointerId 匹配豁免收窄到"另一只鼠标 idle"（pen/touch 任意 id 的提笔信号都收口）。
- **拖选的 cancel/lostpointercapture 改收口**：`isDragging` 时按最后位置 `finishSelectionDrag`（≥5×5 提交为选区、过小静默丢弃不走 200ms 隐藏定时器），不再 abort；move/resize 交互仍走 abort 恢复原矩形。
- **拖选 pointermove 提笔守卫**：悬停流到达即按当前位置（≈提笔点）收口拖选，选区不再跟随悬停漂移。
- **诊断回传扩面 + 双通道**：`cleanupSessionVisuals` 且 `!ss.sent`（非输出清场，覆盖失焦看门狗 hide）也触发回传，不只 ESC；回传同时走两路——剪贴板（`copy_to_clipboard`，用户直接粘贴）与 tracing 日志文件（新增临时 `pen_diag_log` command，`blink.*.log` 里 `[pen-diag]` 前缀整段落盘，外部用户直接回传日志文件即可）。背景：后端剪贴板链路只记指纹哈希不记正文（隐私铁则），诊断内容须显式落日志才进文件。

**0.29.3-r3 收口**（2026-11-20 实机复测确认选区/画笔正常）：临时诊断整体移除——`index.js` 的 pen-diag 模块（事件捕获/环形缓冲/异常计数/console 输出/取消回传）、`ss-output.js` 的 doCancel 钩子、后端临时 `pen_diag_log` command 及注册。**保留的功能件**：`penLiftByPressure` 自校准压力闩锁（被动 pen 事件监听只置布尔，无日志副作用）、`lastStrokeEndAt`（contextmenu 刚收笔守卫）。
