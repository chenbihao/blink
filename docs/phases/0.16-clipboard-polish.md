# Blink 0.16 — 剪贴板增强 + 杂项打磨（Clipboard Enhancement & Polish）

> **范围**：① 剪贴板右键菜单修复 + **item 右键机制治本（actions 数组驱动）** + 文本编辑器窗口（md/纯文本切换）+ 图片支持（CF_DIB）+ 图片→pin 联动；② 顺带清六个独立小修（主窗口右键全选门控、存储清理 VACUUM、对话窗口模型名 ellipsis、provider 启用/禁用、单选多选样式统一）；③ **卸载清理能力（NSIS 钩子 + 设置页清理入口）**。
>
> **状态**：📋 规划中。
>
> **动机**：剪贴板历史（Alt+C）是四个 chord surface 之一，但当前只能复制文本、右键 label 误导（显示"打开"实际复制）、无编辑能力、不支持图片。对标 ditto 这类成熟剪贴板管理器，剪贴板增强是高频收益。同时积累的几个设置页小 bug + 卸载无清理能力，适合在此 phase 顺手清。
>
> **前置**：0.16.3（图片→pin）依赖 0.15 pin 能力；0.16.1（编辑器）的 md 渲染抽共享模块后惠及 0.17；0.16.4（item 右键治本）借力 0.14 已落地的 capability `actions: Vec<ItemAction>` 协议。
>
> **原则**：① 图片支持是全 phase 最重的一块，需在细化时决定是否拆出独立 phase（0.18）；② md 渲染做成共享模块（对话窗口/剪贴板编辑器/未来便签复用）；③ item 右键从硬编码重构为 actions 数组驱动（治本，对接 0.14 capability 协议）；④ 卸载清理复用 STT 空间清理范式（探测→展示→确认→清理），不另起炉灶；⑤ 无 bundler 铁则不变。

## 一、背景与动机

### 1.1 为什么 0.16 做这件事

剪贴板 chord（Alt+C）0.8.5 落地，0.7 已有文本历史引擎。但五个方向的显性短板：

1. **右键菜单 label 误导 + 机制硬编码**——`contextmenu.js:198` 对所有结果项无脑塞"打开"，剪贴板项本应是"复制"。功能上其实能复制（`activateItem` 对 copy kind 写剪贴板），只是 label 错。深层原因：item 右键 100% 按 `source` 字符串硬编码分支，不读后端 actions。剪贴板 label bug 只是这套硬编码的副作用之一。
2. **主窗口右键全选过度显示**——`contextmenu.js:169` 的 `selectAll` 无条件 push，没有"有文本/有选区"门控（同文件 cut/copy 有 `hasSelection` 门控），空输入框右键也显示全选。
3. **无编辑能力**——ditto 式"在独立窗口编辑历史文本后回贴"不存在。
4. **不支持图片**——采集端只读 `CF_UNICODETEXT`（`windows.rs:252-266`），图片复制静默跳过；schema 无 BLOB/kind 列。
5. **小 bug + 基础设施缺失积累**——设置页 provider 无启用/禁用、存储清理后 DB 不缩（无 VACUUM）、对话窗口模型名溢出多行、**单选多选样式三态并存（radio 几乎全裸、个别 checkbox 无 CSS 定义）**、**卸载完全无清理逻辑**（`%APPDATA%\blink\` 数据 + Credential Manager 密钥全部残留）。

### 1.2 现状澄清（审查结论）

| 项 | 现状 |
|---|---|
| 右键"打开"label | bug 在前端 `contextmenu.js`，不是 cap 能力配置问题。后端 `SearchAction::Copy` / `ItemAction::Copy` 都正确声明了 |
| **item 右键机制（深挖）** | **100% 硬编码**。`contextmenu.js:191-240` 的 `itemMenu()` 完全靠 `li.dataset.source` 字符串 + `lnkPath` + `actionKind` 做分支。后端每个 item 只带**单个 `Action`**（`mod.rs:122`），"读 actions 数组生成右键"是 0.14 规划但前端至今未实现。各 source 分支：file/start_menu 有完整菜单、UWP/calc 部分覆盖、**剪贴板是 bug**（只有错误 label 的"打开"）、插件/AI 大多只有"打开" |

## 二、核心设计 / 决策

### 2.1 md 渲染共享模块（横切机会）

对话窗口已有 md 渲染能力（`frontend/js/chat/`）。0.16.1 做编辑器时把它抽成共享模块（如 `frontend/js/shared/markdown.js`），剪贴板编辑器、未来 0.17 便利贴自动复用。

### 2.2 图片支持归属 —— 留 0.16 还是拆 0.18（待定）

**定案**：细化时拍板。
**理由**：图片支持单独够一个重 phase（采集/schema 迁移/去重/渲染/搜索适配）。两选一：A 留 0.16.2 接受 0.16 为大 phase；B 0.16 只做文本侧，图片独立成 0.18。

### 2.3 编辑器是否做代码高亮（待定）

**定案**：细化时拍板，倾向不做。
**理由**：代码高亮（highlight.js/shiki）引入前端依赖，与无 bundler 铁则有张力。倾向只做 md + 纯文本。

### 2.4 右键菜单实现路线 —— 补分支 vs 读 actions 数组（待定）

**定案**：细化时拍板。
**理由**：补 clipboard 分支最小改动；读 actions 数组更通用（图片 item 自动适配），但是结构性改动。

### 2.5 md 共享模块的边界（待定）

**定案**：细化时拍板。
**理由**：需定抽哪些函数（渲染/解析/语法树）出 `frontend/js/chat/`，确保对话窗口、剪贴板编辑器、未来便签共用同一套。

### 2.6 item 右键机制 —— 重构为 actions 数组驱动（已定，治本）★

**定案**：借本次把 item 右键从"按 `source` 硬编码分支"重构为"读后端 `actions` 数组动态生成"，对接 0.14 已落地的 capability 协议（`ItemResult.actions: Vec<ItemAction>`，`result.rs:218`）。
**理由**：剪贴板 label bug（0.16.0a）只是硬编码模式的副作用之一；治标路线（逐 source 补分支）每加一种 item 类型（图片、未来便签）都要改前端，治本路线一劳永逸。

#### 与 0.14 CAP 协议的关系（是同一套，逐层收窄）★

**澄清一个易误解点**：0.16.4 不是"另起炉灶用 CAP 能力做右键"，而是"接通 0.14 已设计好的、但桥接时被压扁的同一套 action 链路"。manifest 的 `item_actions` 配置经 3 步到达前端，前三步 0.14 已全通，**唯独最后一步取了首个压扁成单值**——这才是要治本的断点。

```
manifest 层          协议层                    契约层
ActionDef    →    ItemAction       →      search::Action    →  AppEntry.actions
(4 变体)          (4 变体)                 (3 变体，收窄)       (前端唯一看到的)
{kind,pointer}    {pointer:JSONPath}       {payload:已解析值}
  projection      items_to_entries          (回车=actions[0]
  (:247/:314)     (:1892)                   右键=展开全部)
  纯字段拷贝       ★断点：first() 取首个压扁
                  pointer 在此解析为具体值
```

**三步投影链**（0.14 已落地，0.16.4 不动前三步，只解最后一步的压扁）：
1. **manifest → ItemResult.actions**（`projection.rs:247` `project_items` + `:314` `action_def_to_item_action`）：纯字段拷贝零解析，pointer 原样透传（仍是 `$.text` 这样的 JSONPath 字符串，是"未兑现的取值承诺"）。轨道 A（manifest 投影）与轨道 B（builtin 直接构造）在此都产出 `Vec<ItemAction>`，builtin 写法也是 `$.field` 形式（如 `search_clipboard_history.rs:116` 的 `$.text`、`search_files.rs:152` 的 `$.path`）。
2. **pointer 解析 + kind 收窄**（`service.rs:1923` `extract_pointer` + `:1936-1987` match）：pointer 在此解析成具体值（`$.text` → `data["text"]` → `"你好"`，手写 `$.field` 解析非 jsonpath crate）；4 个 ItemAction 变体收窄为 3 个 ActionKind（`OpenFile`+`OpenUrl`→`Open`，`Reveal`→`Run`+写死 `run_id:"reveal_in_explorer"`，`Copy`→`Copy`）。
3. **★ 断点（0.16.4 要解的）**：`service.rs:1934` 的 `if let Some(first) = item.actions.first()` 只取首个——前三步都是数组全量处理，唯独这里压成单值塞进 `AppEntry.action: Action`（单数）。manifest 配两个动作（copy + open_file）到这只剩一个。

**交互约定（对齐 0.14 §A5.3，正式确认）**：`AppEntry.actions` 返回完整数组；**回车激活 `actions[0]`（首个），右键展开全部**。actions 顺序即优先级（作者把最常用动作放第一个）。空 actions + 纯标量 data → 主窗口隐式提供 copy（展示层 fallback，非协议层派生）。

#### 核心改动链（后端类型 → 投影 → 前端三处）

1. **后端类型升级**：`AppEntry.action: Action`（`mod.rs:122` 单值）→ `AppEntry.actions: Vec<Action>`。`SearchItem.action`（`engine.rs:63`）可选保留单值（各查询引擎本就只产单动作），仅在 `into_app_entry` 包成 `vec![action]`。
2. **投影全量化（解断点）**：`items_to_entries()`（`service.rs:1934`）从 `item.actions.first()` 取首个 → 全量 `item.actions.iter().map(...).collect()`，每个 `ItemAction` 映射成一个 `Action`（复用现有 match 逻辑 `:1936-1987`）。前三步（manifest 投影 / pointer 解析 / kind 收窄）不动。
3. **前端动态生成**：`contextmenu.js:191-240` 的 `itemMenu()` 删 source 硬编码分支，改遍历 `actions` 数组动态生成菜单项（label 用 `action.hint`，空 actions + 标量 → 隐式 copy）；`results.js` 的 `createItem`/`itemData`（`:344`/`:491`）存读 `actions` 数组；`actions.js` 的 `activateItem` 回车执行 `actions[0]`（右键菜单项各自执行对应 action）。

**为何 SearchItem 不一并改数组**：各查询引擎（start_menu/file/calc/clipboard/builtin）本来就只产单动作，AI tool-call 路径（`items_to_entries`）才是多 action 的真正来源。先只改 `AppEntry` + 投影 + 前端，覆盖度足够；`SearchItem` 升级为非必要，留作未来某引擎确需多动作时再动。

**与 0.16.0a 的关系**：0.16.0a（剪贴板 label）是治标止血，0.16.4 是治本重构。0.16.4 落地后 0.16.0a 的补丁被取代（重构后剪贴板项自动走 actions 数组，label 从后端来）。

> **注意区分两个 CAP 闭环**：0.16.4 治的是 **item-action 闭环的桥接断点**（manifest/CAP 协议 → AppEntry → 前端右键），与 0.18 规划的**多模态 CAP 闭环**（AI 调 `capture_screen` 后 Blob 能否真正回流 LLM"看见屏幕"，`0.17:97`）正交，勿混淆。

### 2.7 卸载清理 —— 复用 STT 范式 + 补 CM 批量清（已定）★

**定案**：卸载清理分两条线，均复用 STT 空间清理（`maintenance.rs:802 cleanup_stt_space`）的"探测→展示→确认→清理→刷新"范式，不另起炉灶。
**理由**：STT 空间清理是项目里唯一成熟的"清大数据"范式，后端工具函数（`dir_size_bytes`/`bytes_to_mb`/`delete_secret`）、前端交互骨架（`voice.js:1058 initSpaceManagement`）、CSS（`.stt-space-*`）、i18n key 组都已存在，可直接复用或换前缀复刻。

**两条线**：
- **A. NSIS 卸载钩子**（卸载时自动清理）：Tauri 2 支持 `bundle.windows.nsiTemplate` 自定义卸载段。卸载时弹可勾选的"同时删除用户数据与模型"选项，删除 `%APPDATA%\blink\` + `CredEnumerateW` 清 `blink/*` 密钥。NSIS 模板是仓库目前完全没有的打包基础设施（新增）。
- **B. 设置页清理入口**（运行时手动清理）：在存储设置页加"卸载前清理/一键清理全部数据"入口（不依赖 NSIS），调后端删除数据目录 + 清密钥。给不愿走卸载流程的用户一个手动出口。两条线共享后端清理函数。

**Credential Manager 能力边界（需新增）**：现有 `delete_secret(pid, purpose)`（`windows.rs:167`）只能按精确别名删单条，无枚举无批量。`CredEnumerateW` 全仓零调用（仅注释提及 `windows.rs:6`）。需新增 `enumerate_blink_secrets()`（`CredEnumerateW` + `blink/*` 前缀过滤）+ `delete_all_blink_secrets()`（枚举 + 逐条删 + 错误聚合），把 `secret/mod.rs:124` 预留的设计注释落地成代码。

**复用清单（详见 §4.6）**：后端 `paths::*` / `dir_size_bytes` / `bytes_to_mb` / `delete_secret` / 停 server 范式；前端 `confirmDialog` / `initSpaceManagement` 骨架 / `.stt-space-*` CSS / `*.space.*` i18n。顺带收口 `maintenance.rs:726` 手拼 `python` 路径与 `paths.rs:33` 的重复债务。

### 2.8 表单样式统一 —— 补 radio 组件 + 收编裸框（已定）

**定案**：新增 `components/radio.css`（与 `checkbox.css` 对称），给现有裸框套 `.radio`/`.checkbox` 组件类，修 Debug 日志开关的无 CSS bug。
**理由**：问题不在"完全没有样式"（主流 toggle/checkmark 完整），而在三态不一致。统一到组件层（`components/`），符合 spec-frontend §1.2 七层架构（表单控件属 components 层）。radio 是最大缺口（全仓无 radio.css）。

### 4.5 0.16.4 item 右键机制治本（actions 数组驱动）

**目标**：把 item 右键从"按 `source` 硬编码分支"重构为"读后端 `actions` 数组动态生成"，对接 0.14 已落地的 capability 协议。落地后剪贴板/插件/AI 等 item 的右键菜单自动从后端 actions 派生，不再需要前端逐类型补分支（0.16.0a 的剪贴板补丁被取代）。

**核心洞察（深挖结论）**：capability 协议层早已支持数组（`ItemResult.actions: Vec<ItemAction>`，`result.rs:218`），0.14 注释明确"回车执行 `actions[0]`，右键展开全部"（`result.rs:227`）。但桥接 `items_to_entries()`（`service.rs:1934`）投影时 `item.actions.first()` 只取首个，把数组压扁成单个 `AppEntry.action`——这是前端始终拿不到全部 actions 的根因。治本 = 让这个压扁点全量化 + 前端改读数组。

**实现方案（可分派，三段链）**：

**Step 1：后端类型升级**（`src/domain/search/mod.rs`）
- `AppEntry.action: Action`（`:122` 单值）→ `AppEntry.actions: Vec<Action>`
- 兼容策略：`#[serde(default)]` + 空时默认 `vec![Action::default()]`，避免破坏现有前端读取
- `SearchItem.action`（`engine.rs:63`）保留单值不动——各查询引擎本就只产单动作

**Step 2：投影全量化**（`src/domain/search/service.rs` 的 `items_to_entries`，`:1892-2049`）
- `item.actions.first()`（`:1934`）→ `item.actions.iter().map(|a| map_item_action(a)).collect::<Vec<_>>()`
- 复用现有 `:1936-1987` 的单 `ItemAction→Action` match 逻辑，包进 `.iter().map()`
- fallback 链（`:1989-2019`，空 actions + 标量 → 隐式 copy）保留为单元素 vec，对齐 §A5.3
- 全量核对 service.rs 内所有直接构造 `AppEntry { action: ... }` 的点（`ai_result_entry:1572` / `ai_placeholder_entry:1543` / `placeholder_entry` / `error_entry` / `clear_marker` 等，粗看 10+ 处），全部改 `actions: vec![...]`；tests helper `mod.rs:336` / `start_menu_engine.rs:446` 同步

**Step 3：前端动态生成**（`frontend/js/main-window/`）
- `results.js:344-357`（`createItem` 存 dataset）：单值字段（`actionKind/actionPayload/...`）→ 存 `JSON.stringify(app.actions)` 进 `dataset.actions`（或保留单值字段做过渡兼容）
- `results.js:491-527`（`itemData`）：读出 `actions` 数组传给 `activateItem`
- `actions.js:14-81`（`activateItem`）：`data.action?.kind` → `data.actions?.[0]?.kind`（回车执行首个，对齐 0.14 §四）；copy/run/open 三分支从 `actions[0]` 取值
- `contextmenu.js:191-240`（**`itemMenu` 核心重构点**）：删 `source === "file"/"start_menu"/"calc"` 硬编码分支，遍历 actions 数组动态生成菜单项——每个 action → `{label: action.hint || 默认文案, run: () => execute(action)}`；空 actions + 标量 → 隐式 copy（§A5.3 fallback）
- `contextmenu.js:250-271`（`readData`）：同步读 actions 数组
- `hints.js:21-27` + `statusbar.js:121`：`action.kind` → `actions[0].kind`，`action.hint` → `actions[0].hint`

**文件管理类菜单的特殊处理**：现状 file/start_menu 的"打开所在文件夹/复制路径/复制文件名/重置记录"等是纯前端能力（不来自后端 action）。这些应保留为前端按 `lnkPath` 存在性附加的固定项（不属于 actions 数组），与动态 actions 项拼接。重构后菜单 = 动态 actions 项 +（若 lnkPath 存在）文件管理固定项。

**类型契约选择**：前端只认 `search::Action`（payload/run_id 等已解引用），不直接消费 `capability::ItemAction`（pointer）——保持 0.14 "后端全投影"设计（§十三 330 行）。`ItemAction→Action` 的映射完全在 `items_to_entries` 完成。

**依赖**：无（借力 0.14 已落地协议）。建议紧跟 0.16.0 后做，避免 0.16.0a 补丁写完即被取代。

**风险**：service.rs 内 AppEntry 构造点分散（10+ 处），需全量核对无遗漏（grep `action: Action` / `action:` in service.rs）。前端 dataset 序列化方案（单 JSON vs 多字段）需权衡可读性与改动量。

### 4.6 0.16.5 卸载清理能力（NSIS 钩子 + 设置页入口）

**目标**：卸载时提供"清理用户数据/模型/密钥"选项；同时给运行时一个手动清理出口。复用 STT 空间清理范式，不另起炉灶。

**两条线共享后端清理函数**：

**Step 1：后端清理函数（共享）**（新建 `src/app/commands/uninstall.rs` 或扩展 `diagnostic.rs`）
- `get_uninstall_space_usage()`：照抄 `get_stt_space_usage`（`maintenance.rs:725`）的 `{items:[{label,path,size_mb}], total_mb}` 结构，探测项扩展为：
  - `paths::logs_dir()` / `skills_global_dir()` / `python_dir()`（含模型）
  - 4 个 SQLite 库 `paths::db_path(name)`
  - legacy `~/.cache/modelscope`
  - **直接调 `paths::*`，不要再手拼**（顺带收口 `maintenance.rs:726` 与 `paths.rs:33` 的重复债务）
- `cleanup_for_uninstall(scope)`：照抄 `cleanup_stt_space`（`maintenance.rs:802`）顺序：
  1. 先停 funasr-server（若在跑，复用 `take+kill+mark_stopped` `:803-809`）
  2. 按 scope 删各目录（scope 区分"仅缓存/含模型/全量数据"）
  3. 清 Credential Manager 密钥（见 Step 2）
  4. 错误聚合（主目标失败 push errors，legacy/CM 的 NotFound 宽进严出）
- 复用 `dir_size_bytes`（`diagnostic.rs:503`）/ `bytes_to_mb`（`:517`）/ `delete_secret`（`windows.rs:167`）

**Step 2：Credential Manager 批量清**（新增，`src/infra/platform/secret/`）
- `enumerate_blink_secrets()`：调 `CredEnumerateW`（filter `CRED_TYPE_GENERIC` 全扫后按 TargetName 前缀 `blink/` 过滤，或用 filter 表达式），返回 `Vec<String>`。补 `windows.rs:20-23` 的 `use CredEnumerateW`
- `delete_all_blink_secrets()`：枚举 + 逐条 `CredDeleteW`，套 `cleanup_stt_space` 的错误聚合范式（每条失败 push，NotFound 跳过）
- 落地 `secret/mod.rs:124` + `windows.rs:6` 预留的"卸载脚本按 `blink/*` 批量清理"设计注释

**Step 3a：NSIS 卸载钩子**（`tauri.conf.json` + 新建模板）
- `tauri.conf.json` 的 `bundle.windows` 加 `nsiTemplate`（指向仓库内 `.nsi` 模板文件）
- 模板基于 Tauri 默认 NSIS 模板，在 `un.onInit` 或 Uninstall 段加可勾选的"同时删除用户数据与模型（%APPDATA%\blink）"分支
- 勾选时：删 `%APPDATA%\blink\` + 调 `CredEnumerateW` 清 `blink/*` 密钥（NSIS 可直接调系统 API 或调一个卸载专用的小 exe）
- **注意**：NSIS 运行在卸载阶段，此时应用进程已退出，DB 句柄/子进程已释放；但若用户选择不卸载只清理（Step 3b 路径），需先停 server

**Step 3b：设置页清理入口**（`frontend/settings.html` + `frontend/js/settings/tabs/storage.js`）
- 存储设置页加"卸载前清理 / 一键清理全部数据"卡片（复用 STT 的卡片容器结构 `settings.html:1364`）
- JS 照抄 `voice.js:1058 initSpaceManagement` 骨架：`get_uninstall_space_usage` 探测 → `renderUsage` 展示 → `confirmDialog`（`tauri.js:204`）确认 → `cleanup_for_uninstall` 清理 → `setTimeout` 刷新
- CSS 复用 `.stt-space-*`（`settings-voice.css:1031`），换前缀为 `.uninstall-space-*`
- i18n 照抄 `*.space.*` key 组（`zh.js:519` / `en.js:518`），换命名空间为 `storage.uninstall.*`

**复用范式三细节（务必照搬）**：
1. **错误分级**：主目标失败聚合报错（`errors.join`），legacy/次要目标失败 `warn` 不阻断（`maintenance.rs:850`）
2. **删前先 stop**：清理占用中资源前先释放句柄/子进程（`maintenance.rs:803`）
3. **幂等守卫**：所有删先 `if exists()`，CM 删把 `NotFound` 当成功（`windows.rs:180`）——卸载必须可重复执行

**依赖**：无（独立打包基础设施线）。NSIS 模板是仓库新增基础设施，但不阻塞其他子版本。

**风险**：① NSIS 卸载钩子的兼容性（不同 Windows 版本/Tauri 版本行为差异），需实测；② `CredEnumerateW` 在无任何 `blink/*` 凭据时的空返回处理；③ "全量清理"误删风险——确认对话框必须明确列出将删除的内容，默认拒绝（对齐 `confirmDialog` `:202`）。
