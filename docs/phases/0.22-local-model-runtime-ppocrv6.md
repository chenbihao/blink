# Blink 0.22 — 本地模型运行时与 PP-OCRv6（从专用维护到多引擎生命周期）

> **范围**：建立受限的本地模型运行时，统一进程、Provider、模型资产、状态与设置管理；迁移 FunASR，接入 PP-OCRv6，并以常驻 GGUF worker 原位替换旧 FunASR Python/PyTorch 推理链路。
>
> **状态**：🚧 进行中（0.22.0～0.22.6 已完成；0.22.7 GGUF 核心与两项产品契约收口已落地，待最终 release gate；0.22.8/0.22.9 为 VAD 与 OCR 轻量化 spike）。
>
> **动机**：FunASR 原有安装、进程、模型和诊断逻辑过度绑定 STT；PP-OCRv6 作为第二个真实引擎，需要一套可复用但不伪造执行能力交集的管理面。
>
> **前置**：0.10 本地 STT、0.11/0.17 OCR、0.21 Capability 体系已完成。
>
> **原则**：不影响 `Alt+Space → Focus → 输入` 主链路；分层、日志、错误、事件与前端约束分别以 `spec-architecture.md`、`spec-backend.md`、`spec-frontend.md` 为准；未知进程绝不按端口自动终止。

## 二、背景与动机

### 2.1 为什么 0.22 做这件事

0.22 将散落在 FunASR/STT 中的安装、进程、模型、日志和清理职责收敛为本地引擎管理面，并用 PP-OCRv6 与原生 GGUF FunASR 验证 Python、受管二进制、按需 OCR 和常驻 STT 可以共享生命周期契约而不共享具体推理实现。

### 2.2 明确“不是问题”的

- 系统/用户 Python 与 Blink 托管 Python 保持隔离；多个引擎不共享可变 site-packages。
- 模型按需下载，不进入 Blink 安装包；安装包只携带锁、协议、许可与必要 worker 产物。
- WinRT OCR 永久保留为零安装 fallback；PP-OCRv6 是可选高质量后端。
- 管理页的状态、安装和日志命令不是 Capability；除非未来确有 CLI/MCP/AI 入口及授权设计。
- 本地引擎不全部常驻：FunASR 由用户策略控制，OCR 默认按需并在空闲后回收。
- 前端继续纯静态 HTML/CSS/JS，无 bundler、npm 或构建步骤。

## 三、核心设计与决策

### 3.1 分层与注册边界（已定）

`domain/local_engine` 定义框架无关协议，`infra/local_engine` 提供进程、部署和 Provider 原语，`app/local_engine` 持有唯一 `EngineManager` 并投影 IPC/事件。注册表是编译期 allowlist；前端只能提交受限 engine/model/action，不能注入 executable、URL、脚本、argv 或环境变量。

### 3.2 状态与资产提交（已定）

环境、进程、服务、模型、desired state 和 operation 彼此正交；状态以 `(service_epoch, revision)` 防止旧实例覆盖。每个引擎同时只允许一个变更操作。

引擎 deployment 与模型资产都只有一个稳定 active pointer。安装在 staging/candidate 中完成校验，原子切换失败时保留旧 active；journal、slot 和 residue 是事务实现，不是面向用户的版本列表。selected、installed 和 active 模型必须分开表达，切换失败不得静默改选其他模型。

### 3.3 进程与信任边界（已定）

受管进程并发排空 stdout/stderr，日志有界；Windows 用 Job Object、instance token、PID 创建时间、可执行路径和 health 身份共同验证。终止和异常恢复均 fail-closed；端口被未知进程占用时只换端口或报错，绝不自动 kill。

### 3.4 Provider 与计算设备（已定）

Provider 只实现声明过的锁定安装计划。PythonVenv 和 ManagedBinary 可以共享只读、版本/hash 精确的公共 artifact，但 active 环境保持隔离。计算设备区分用户 preference、解析后的安装 profile 与 health 回报的 actual backend；显式设备失败不得静默回退。

### 3.5 OCR 路由与生命周期（已定）

默认 OCR 仍为 WinRT。显式 `paddleocr` 失败返回可行动错误；`auto` 只在 PaddleOCR 已热态时使用，否则立即走 WinRT，不为普通截图引入隐式冷启动。PaddleOCR 首次调用使用 singleflight，取消、session/epoch 和 idle TTL 共同防止旧结果覆盖与进程泄漏。

PP-OCRv6 spike 结论保持 `conditional-go`：准确率与几何结果明显优于当时 WinRT 基线，但 CPU 热识别约 4 秒、峰值工作集约 1136MB，不得被描述为轻量默认后端。原始数据见 `xtask/spikes/ppocrv6/decision.md`。

### 3.6 FunASR 原位替换（已定）

产品侧始终只有稳定的 `funasr` engine id。0.22.7 用 `ManagedBinaryProvider + ManagedProcess + NDJSON stdio worker` 原位替换旧 Python HTTP/PyTorch 链路；stdout 仅承载协议，诊断走 stderr。SenseVoice、Paraformer-zh 和 Fun-ASR-Nano 都是同一引擎的受限模型候选，一次只常驻当前选择的一个模型。

旧 SenseVoice/Paraformer 配置按确定映射迁移；未知旧 id 保持原样并显示不可用，不静默换模型。模型与 worker 来源固定 revision/SHA-256，运行期不跟随浮动分支。SenseVoice 常驻实测约 251MiB；该资源成本留在最终 release gate 继续做整进程树测量与产品提示。

### 3.7 FunASR 能力与交互归属（0.22.7 待收口）

FunASR 卡片是模型选择的唯一写入口：已安装模型在卡片内展示“使用/当前/等待重启”等状态，语音页只读展示当前选择及跳转到 FunASR 卡片的入口。`selected` 与进程实际加载的 `active` 必须继续分开；服务运行中切换模型应经用户确认后完成 stop → selection commit → start，失败时恢复可解释状态，不能只改配置制造“已经切换”的假象。产品仍只允许一个 ASR GGUF 常驻；未来一个轻量 VAD 前端与一个当前 ASR 配对不等于多 ASR 同时常驻。

当前 GGUF worker 未消费热词和可控 ITN 参数，因此删除语音页热词/ITN 控件、对应配置投影、协议字段和能力声明，不能继续展示无效开关。SenseVoice 自身输出归一化及现有 GGUF 后处理不是可切换 ITN，不在清理时误删；现有 EnergyVad 三项参数也保留到 0.22.8 得出替代结论后再决策。

模型切换会依赖可靠的主动停止语义：用户 stop、切模重启、空闲回收和应用退出均不得被上层投影成“进程意外退出”。PaddleOCR 应优先调用已存在且带 token 的 `/shutdown`，超时后再由 `ManagedProcess` 回收；最终 `Stopped { code: Some(1) }` 仍可保留诊断信息，但不能进入异常退出错误态。

### 3.8 两项 spike 的决策边界（0.22.8/0.22.9）

FSMN-VAD 的上游 GGUF CLI 能让一个 FSMN-VAD 模型搭配 SenseVoice、Paraformer 或 Fun-ASR-Nano，但 Blink 的持久化 `--stdin-server` 补丁当前明确排斥 `--vad`，且现有 GGUF VAD 接口是否具备可复用的在线 cache、是否每次重新加载模型，必须用代码与实测确认。0.22.8 不把“CLI 有 `--vad`”等同于“可以替换实时切句”。

PP-OCR 的几 MB 模型不等于几 MB 的完整 OCR：还包括检测/识别模型、字典、图像预后处理和推理后端。0.22.9 至少比较现有 Python/PaddleX、官方 PaddleOCR C++ + Paddle Inference、原生 ONNX Runtime（可参考 RapidOCR 的转换与管线）三条路线；其他 ncnn/OpenVINO/Rust 方案只有在 PP-OCRv6 模型、几何结果、Windows x64 CPU 和许可均可核实时才进入实测。

## 四、复用与范围边界

### 4.1 已有基础设施复用

| 基础 | 0.22 用法 |
|---|---|
| `ConfigStore<T>` 与配置事件 | 引擎偏好、OCR 路由和 STT 模型选择 |
| `OcrBackend` / `OcrResult` | PP-OCRv6 接入并保持截图结果契约 |
| WinRT OCR | 默认后端和降级逃生口 |
| 截图 session/epoch | OCR 启动、取消与结果回流竞态墙 |
| 设置页模块/CSS token | 本地运行时卡片、日志、诊断和清理 |
| 事件名常量与结构化错误 | local-engine 状态、日志和可行动错误投影 |

### 4.2 不进 0.22

| 项 | 理由 |
|---|---|
| 第三方任意本地引擎注册 | 需要独立签名、授权和任意代码执行信任设计 |
| 通用模型商店 | 下载、版本和校验语义依赖具体工具链 |
| PP-Structure、表格、公式、OCR-VL | 输出协议与资源预算超出截图文字识别 |
| 多引擎共享 site-packages | 依赖升级与 GPU wheel 会相互污染 |
| 完整 GPU 调度、多个 ASR GGUF 同时常驻 | 需要 RAM/VRAM 仲裁和独立产品设计；单个 VAD 与当前 ASR 配对由 0.22.8 单独验证 |
| Linux/macOS 本地引擎 | 当前实现与验收以 Windows 为目标 |
| AI/MCP 安装、启动或清理引擎 | 管理操作尚无外部授权与危险确认模型 |

### 5.1 0.22.7 — 两项产品契约收口（已完成）

按顺序拆为两个可独立验收的 handoff：

1. **失效能力清理**：删除热词与 ITN 的 UI、配置写入、运行时投影、worker 协议字段、能力声明和对应测试/i18n；旧配置必须可安全读取并在下次保存时自然收敛，不能影响 VAD 参数和 GGUF 固有后处理。
2. **唯一模型选择入口**（已完成）：FunASR 卡片承接安装、选择与当前/等待重启状态；语音页只读展示并可跳转。补齐运行中切换的确认、stop/restart、失败回滚/状态刷新，并一并修正 PaddleOCR 主动停止被误报异常退出的问题。

### 5.2 0.22.8 — FSMN-VAD spike（规划）

只做隔离原型与报告，生产默认仍为 `EnergyVad`：

1. **建立基线**：用固定、可再分发或本地生成的中文短句、长句、停顿、低音量、背景噪声、纯静音和爆音样本，记录现有 EnergyVad 的端点延迟、误切、漏切、误激活、首个 preview/最终稿延迟、CPU 与整进程树工作集。
2. **验证真实形态**：阅读并记录 GGUF FSMN-VAD 的加载生命周期、帧长、阈值、最大段长、在线 cache/reset 能力；区分上游离线整段分割、累计音频重复推理、模型常驻但无 cache、真正增量流式四种形态，禁止用离线 CLI 成功冒充在线可行。
3. **配对与协议 PoC**：至少对三种 ASR worker 各做一次“同一个 FSMN-VAD + 当前 ASR”的识别冒烟；验证 utterance reset、取消、stop/restart、模型切换、坏 VAD 资产和 VAD/ASR 状态不一致。PoC 可修改/复制 spike worker，但不得直接改变生产协议或默认配置。
4. **对比方案**：比较纯 FSMN、EnergyVad 粗筛 + FSMN 端点、FSMN 仅作最终低置信/静音门、继续 EnergyVad 四案；报告模型常驻增量成本与是否仍满足单 ASR 常驻策略。
5. **决策输出**：`xtask/spikes/fsmn-vad/decision.md` 必须给出 `go / conditional-go / no-go`、原始数据/复现命令、风险和生产实施拆分。若不可行，至少评估现有 VAD 的自适应噪声底、起止双阈值滞回、pre-roll、平滑/hangover、最短语音、全静音/低能量清理以及非伪流式路径一致性。

### 5.3 0.22.9 — PP-OCR 精简运行时 spike（规划）

目标是消除“模型很小但运行环境与重复缓存超过 1GB”的不成比例成本，同时保持现有 OCR 产品契约：

1. **测量当前真基线**：在干净目录记录 Python/Paddle/PaddleX 环境、模型、下载缓存、临时文件和可删除残留各自体积；记录冷/热启动、单图延迟、峰值工作集、停止回收和 `OcrResult` 几何/置信度结果，不能只报安装目录总数。
2. **候选资格门**：官方 C++ + Paddle Inference、原生 ONNX Runtime 管线、RapidOCR 类原生封装均需验证 PP-OCRv6 实际模型转换/算子兼容、Windows x64 CPU 可复现构建、文本检测 + 识别 + 字典、polygon/word box/score、中文与混排、许可证和可锁定供应链；不满足任一硬条件的路线只记录为淘汰，不做产品接入。
3. **最小 PoC**：合格路线至少有一个隔离 worker，通过固定 JSON/NDJSON 或现有受限 HTTP 夹具输出与 `OcrResult` 可映射的结果；比较进程隔离与 in-process DLL 的崩溃面、升级面和体积，不因“更小”绕过 Manager/Provider 信任边界。
4. **量化判定**：以当前干净安装总占用为基线，强制报告环境 + 模型 + 不可避免缓存的总量、重复率、冷/热延迟、峰值 RAM、语料准确率/字符错误率和框几何差异。`go` 至少要求总磁盘下降 60%、无第二份不可控模型缓存，且文本/框契约无产品级退化；未达硬门但有清晰优化路径为 `conditional-go`，否则 `no-go`。
5. **决策输出**：`xtask/spikes/ppocr-compact-runtime/decision.md` 给出推荐路线、分发清单、许可清单、锁/hash、实施工作包与迁移/回退策略；如无方案通过，提出当前 Python 环境的瘦身方案（禁用重复 cache、精确依赖锁、按需组件、清理策略），不得直接删除 WinRT fallback。

### 5.4 0.22 最终 release gate（两项 spike 决策后）

- 构建正式安装包，验证全新安装、0.22.x 升级、启动、退出与卸载；确认 worker、许可和锁文件进入制品，模型/cache/staging 不进入制品。
- 验证 Alt+Space 输入、设置页运行时、G1/G2 本地语音、Alt+A OCR/WinRT fallback；只修复实机发现的明确小问题。
- 将 `verify_model_payload` 接入非热路径的恢复/显式验证流程；不得在启动、搜索或每次识别热路径重复 hash GB 级模型。
- 实测 Blink 整进程树未加载、ASR ready/识别中/停止后和 OCR 冷/热态资源；若与 `<300MB` 总目标冲突，提交按需启动、空闲回收或目标修订的产品决策。
