## 二、背景与动机

### 2.1 为什么 0.22 做这件事

把散落在 FunASR/STT 中的安装、进程、模型、日志和清理职责收敛为本地引擎管理面，用 PP-OCRv6 与常驻 GGUF FunASR 验证「共享生命周期契约、不共享推理实现」的多引擎形态；OCR 随后切 ONNX 删除 Python 重栈，STT 依据实测模型价值收敛为「OCR ONNX + GGUF 三模型」。

0.22.11～0.22.13 动机来自三条真实用户反馈与首启缺口：设置窗口无可见关闭路径（唯一出口是 ESC）、编辑器关闭确认缺「保存」出口（被迫在继续编辑/放弃更改二选一）、chord 只有主窗可见时可用；外加首启只有快捷键列表，缺常用开关与引擎引导（Win OCR 中文识别弱，需要把「一键下载 PP-OCR 增强」讲清楚）。

### 2.2 明确"不是问题"的

- 模型按需下载，不进入安装包；安装包只携带锁、协议、许可与必要 worker 产物。
- WinRT OCR 永久保留为零安装 fallback；高质量后端（ONNX）是可选。
- 管理页的状态、安装和日志命令不是 Capability；除非未来确有 CLI/MCP/AI 入口及授权设计。
- 本地引擎不全部常驻：FunASR 由用户策略控制，OCR 默认按需并在空闲后回收。
- 前端继续纯静态 HTML/CSS/JS，无 bundler、npm 或构建步骤。
- 设置窗口 **hide 而非 close** 是刻意的复用/预热设计；0.22.11 的关闭按钮只 hide，不引入销毁语义。
- `confirmDialog` 两按钮 boolean 契约本身没有 bug，约 25 处调用点依赖；0.22.11 的三态扩展向后兼容，不传第三动作时语义不变。
- chord 门禁要求主窗可见是 0.18 输入状态流转的刻意设计；0.22.12 不改 chord 模式本身，只经 `RegisterHotKey` 增加平行入口。

## 三、核心设计与决策

### 3.1 分层与注册边界（已定）

`domain/local_engine` 定义框架无关协议，`infra/local_engine` 提供进程、部署和 Provider 原语，`app/local_engine` 持有唯一 `EngineManager` 并投影 IPC/事件。注册表是编译期 allowlist；前端只能提交受限 engine/model/action，不能注入 executable、URL、脚本、argv 或环境变量。

### 3.2 状态与资产提交（已定）

环境、进程、服务、模型、desired state 和 operation 彼此正交；状态以 `(service_epoch, revision)` 防止旧实例覆盖，每个引擎同时只允许一个变更操作。引擎 deployment 与模型资产都只有一个稳定 active pointer；安装在 staging/candidate 中完成校验，原子切换失败时保留旧 active；journal、slot 和 residue 是事务实现，不是面向用户的版本列表。selected、installed 和 active 模型必须分开表达，切换失败不得静默改选其他模型。

### 3.3 进程与信任边界（已定）

受管进程并发排空 stdout/stderr，日志有界；Windows 用 Job Object、instance token、PID 创建时间、可执行路径和 health 身份共同验证。终止和异常恢复均 fail-closed；端口被未知进程占用时只换端口或报错，绝不自动 kill。

### 3.4 Provider 与计算设备（已定）

Provider 只实现声明过的锁定安装计划；现存 Provider 为 `ManagedBinary`（GGUF worker）与 `OnnxRuntime`（版本化不可变的共享 ORT DLL），可共享只读、hash 精确的公共 artifact，active 环境保持隔离。`PythonVenv` Provider 已随 0.22.10 退役。计算设备区分用户 preference、解析后的安装 profile 与 health 回报的 actual backend；显式设备失败不得静默回退。

### 3.5 OCR 路由与生命周期（已定）

默认 OCR 为 WinRT；`auto` 在已安装本地引擎时优先使用并允许按需冷启动。显式 `paddleocr` 在环境未安装时降级 WinRT，并在成功结果附带 `backend_degrade_hint` 供截图界面提示准确率下降与安装入口；已安装但启动/识别失败仍返回可行动错误，不掩盖基础设施故障。PaddleOCR 首次调用 singleflight，取消、session/epoch 与 idle TTL 共同防止旧结果覆盖与进程泄漏；主动停止优先调用带 token 的 `/shutdown`，超时再由 `ManagedProcess` 回收，`Stopped { code: Some(1) }` 保留诊断信息但不进异常退出错误态。

PP-OCRv6 spike 结论为 `conditional-go`：准确率明显优于当时 WinRT 基线，但 CPU 热识别约 4 秒、峰值工作集约 1136MB，**不得描述为轻量默认后端**。原始数据见 `xtask/spikes/ppocrv6/decision.md`。

### 3.6 FunASR 模型治理与交互归属（已定）

产品侧始终只有稳定的 `funasr` engine id，由 `ManagedBinaryProvider + ManagedProcess + NDJSON stdio worker` 承载（stdout 仅承载协议，诊断走 stderr），一次只常驻当前选择的一个模型；旧 Python/PyTorch/HTTP 链路已删除。SenseVoice、Paraformer-zh、Fun-ASR-Nano 是同引擎的受限模型候选，来源固定 revision/SHA-256，不跟随浮动分支；SenseVoice 常驻实测约 251MiB。

- FunASR 卡片是模型选择的唯一写入口，语音页只读展示并跳转；`selected` 与进程实际加载的 `active` 分开表达。
- 未知旧模型 id 保持「不可用而不静默换模」；退役模型（如 `onnx/paraformer-online`）的存量选择同语义，磁盘残留经设置页存储管理显式清理。
- 运行中切模经用户确认后 stop → commit selection → start，失败恢复可解释状态；用户 stop、切模重启、空闲回收和应用退出不得被上层投影成「进程意外退出」。
- 前端只暴露「是否实时预览」：模型支持真流式走 native partial，否则伪流式；runtime/transport/VAD 类型仅作只读诊断，不设 GGUF/ONNX、True/Pseudo 技术开关。
- GGUF worker 不消费热词与可控 ITN，相关 UI/配置投影/协议字段/能力声明已删除（旧配置安全读取并自然收敛）；SenseVoice 归一化与 GGUF 固有后处理不是可切换 ITN，未误删。EnergyVad 参数保留。

### 3.7 多 implementation 边界与 executor topology（已定）

架构不允许同一 engine id 直接换 runtime（`EngineDefinition` 只有一组 runtime/transport/install plan，registry 按 id 唯一映射 adapter，deployment 只有一个 active pointer），因此 0.22.9 引入受限的内部 implementation 层：

- 产品层仍只有稳定 engine id；implementation 编译期闭合，各自声明 runtime、transport、install plan 与可承载模型。
- 模型 descriptor 绑定 implementation；用户选模型后由编译期映射解析，前端不能提交 runtime、可执行路径或 URL。
- start 时冻结 selected model、resolved implementation、runtime profile 和 deployment identity；运行中切模走 stop → commit → start，失败保持可解释回滚。
- 产品状态只投影一个 selected model 和一个 active model/implementation，一次只允许一个 ASR implementation 活跃。
- 该层只服务编译期内置实现，不演化为任意第三方 runtime 注册或前端可注入通道。

最终 topology：**OCR in-process lazy Session + idle TTL；三模型 GGUF worker**（ParaformerOnline 的独立 ONNX worker 已随退役移除）。in-process OCR 不具备 native crash isolation，不得对外宣称；上层只呈现闭合的 `StreamingSttExecutor`/OCR executor 能力，transport、DLL 路径不穿透 domain 与前端。生产音频热路径不得使用 JSON 浮点数组或 Base64，应采用有界二进制 framing 或等价的流式背压协议。

### 3.8 ONNX 双 runtime 结论与 ASR 侧退役（已定，0.22.10 收口）

- **OCR ONNX 保留**：`oar-ocr + ORT` 原位替换 Python PaddleOCR（0.22.8），稳定 `paddleocr` id 与 `OcrResult` 契约不变。
- **GGUF 三模型保留**：GGUF 不是脚本，而是锁定构建的 C++ worker 二进制及其供应链锁与 NDJSON 协议；Fun-ASR-Nano 无等价 ONNX 实现且有独特中文识别价值，不借双 runtime 改造删除或静默迁移既有模型。
- **ASR 侧 ONNX 退役**：ParaformerOnline 注册门 NO-GO——first_partial p50≈1.27s（门限 400ms）、CER 相对 Nano 基线 Δ≈6.2pp，其差异化价值（低延迟真流式）恰是实测最差项，已从模型目录、implementation 注册、安装/启动链路整体移除；FSMN-VAD 采用门关闭（生产伪流式直持 EnergyVad，从未接线，移除无生产风险）。证据见 `xtask/spikes/onnx-spike/followup/decision.md`。
- **恢复真流式的重启条件（关键）**：从 git 历史恢复被删提交，先完成 CIF 首窗校准把 first_partial p50 压进 400ms，再重跑全量注册门（句尾前非空 partial、final-after-release p95≤800ms、RTF p95<0.8、中文 CER 相对同语料 Nano 恶化≤1pp、100 次 start/stop/cancel 与 10 次 kill/restart 无 orphan/协议死锁/旧 generation 泄漏）；不得降低阈值换取完成。「流式 VAD + 离线 ASR」必须标为伪流式；VAD 与 ASR runtime 正交，收益不得错误归因。

### 3.9 OCR ONNX 安装与执行边界（已定）

- **供应链**：生产 asset lock 保存完整 URL、版本/revision、SHA-256、大小与 license；CPU-only，锁定必要 DLL，禁止隐式下载和 CUDA/TensorRT provider；ORT DLL 与 ONNX 模型按需下载不进安装包，lock metadata 随程序发布。
- **联合提交，指针最后切换**：ORT 与模型分别 staging、校验和 promote；只有两者联合 self-test 通过才提交 deployment pointer，未被引用的中间产物是可清扫 residue。
- **安装自检隔离**：真实 Session + 最小推理 self-test 运行在一次性隔离验证进程中，主进程不从 staging 加载 DLL；该进程不是用户 CLI，也不是第二种 executor topology。
- **desired/loaded/pending_restart**：主进程未初始化 ORT 时首次安装可立即加载 active runtime；已加载不同 DLL identity 时，更新/回滚只改 desired 并投影 `pending_restart`，当前 loaded deployment 不说谎；只切模型 generation 不要求重启。
- **单 Session 有界执行**：一个 OAROCR pipeline/Session 由专用 blocking executor 承载，一次一个请求、最多 4 个 pending，queue 满返回结构化 Busy；ORT 默认 `inter_op=1`、`intra_op≤4`，不建 Session pool，不阻塞 Tokio worker。
- **取消语义诚实**：queued 请求立即移除；active 请求取消后立即返回 Cancelled 并丢弃迟到结果；不可中断的 native call 允许有界收敛，不得宣称 ORT kernel 已被强制终止。
- **hot 定义**：只有 Session Ready 才算 OCR hot；「资产已安装」「DLL 已加载」不算，`auto` 不得据此走本地引擎。
- **结果契约**：优先 oar-ocr 原生 region/word boxes；缺 word boxes 时以 region 生成单个 fallback word，禁止按字符等宽伪造框；坐标校验有限值、正面积和图片边界后进既有 line grouping 与 `OcrResult`。

升级用户的旧 Python deployment 曾作为降级资产独立保留（不参与运行时 fallback），0.22.10 已完成默认迁移并删除。

### 3.10 交互收尾：全局快捷键 / 三态确认 / 引导向导（已定，0.22.11～0.22.13）

- **全局快捷键 = RegisterHotKey 有条件启用**：仅次级可提升的 chord 动作组合键（默认建议 `Ctrl+Alt` 前缀降低冲突面），注册到既有 message-only 窗口 `BlinkInputWindow`，`WM_HOTKEY` 进既有无锁 effect 通道 → `HotkeyService` → 复用 `ChordRegistry::trigger`（含 `disabled_chord_actions` 门禁），符合 spec-architecture「多协议入口，单一原子执行语义」。选它的关键理由是「注册即冲突探测」（`ERROR_HOTKEY_ALREADY_REGISTERED`），hook 路线给不了；LL hook 全局吞 `Alt+字母` 则双重违反「热键默认不吞键」铁则。**主热键（Alt+Space）仍走 hook**：product.md 取舍表与 0.10「为何不用 RegisterHotKey」的否决仅针对主热键（体验与 fallback 顾虑），本决策以「可探测冲突」换「系统注册」，是对该取舍的补充而非推翻。已知局限：`RegisterHotKey` 探测不到 LL hook 类软件（Snipaste/QQ 截图等）的占用，冲突反馈定位「尽力而为」，UI 需明示。
- **冲突探测两层**：OS 级在保存配置与启动注册时试注册，失败报「组合键已被占用」，配置保留但标记未生效；内部级扩展 `ChordRegistry::binding_conflicts()` 覆盖「全局键互斥」「全局键 vs 主热键」，顺带补齐既有「chord 键 vs 主热键」跨检查缺口。配置变更即重注册（先注销旧键），单键失败不阻塞其他键并投影「未生效 + 原因」（`occupied` / `invalid` / `error`，经 `blink://global-hotkey-status` 回显）；全局键并入 `InputConfigSnapshot` 经 `refresh_input_config` 热更新，应用退出注销。
- **共享对话框三态向后兼容**：`showCustomDialog()` 增加可选第三动作，不传第三动作时返回值与既有 boolean 语义完全一致，约 25 处调用零改动。编辑器关闭确认三态化：保存并关闭（Enter，复用 `handleSave()` 的隐藏→后台保存→失败回显闭环）/ 放弃更改 / 继续编辑（Esc）；标题栏 X、Esc、Alt+F4 三个关闭入口收敛到同一确认。
- **设置页关闭 = hide**：右上角关闭按钮接线既有 `#close-btn` 空转监听，走 `hideSettingsWindow()`，与 ESC 同语义；不改窗口创建与预热路径，按钮区域不落在拖拽区。
- **向导只编排不复制引擎逻辑**：4 步（欢迎+核心快捷键 / 常用开关 / 引擎增强 / 完成）步步可跳过/后退；开关走 `set_config` 即时生效；OCR 一键下载 PP-OCRv6 复用引擎页同一条 install 命令与进度事件（backend 默认 `auto`，装完即生效，不做引擎选择 UI）；FunASR（237MB~954MB）只深链 `open_settings_tab` 不进默认下载路径；任意退出路径置 `onboarding_version`；老用户存量配置一次性迁移为未完成（0），升级后补看一次新版向导，常用开关页提示 AI/语音输入需进设置页手动配置。
- **范围否决保留**：chord 模式全局化（去掉 `window.visible` 门禁）不做——无法探测冲突且全局吞 Alt 字母违反铁则；不引入 Tauri global-shortcut 插件（现有 hook 基建 + RegisterHotKey 已覆盖）。

### 3.12 AI 净化截图与窗口管理（已定，0.22.14 追加项，已实现待实机验收）

**问题定位**：现有 AI 已能走 `list_windows → screenshot { op: "window", hwnd }`，但 `window` 实际按 DWM 窗口矩形截取桌面区域；目标被遮挡时会截到遮挡物。区域截图仅隐藏主窗与右键菜单，从对话窗口发起时 chat/settings/便签等 Blink 窗口仍可能入镜。现有 `hide_chat_window` 会中止活跃 AI 请求，不能用于同一工具调用中的截图自隐藏。

**截图参数**：`screenshot` 增加 `blink_visibility: "auto" | "exclude" | "include"`，默认 `auto`。

- `auto`：全屏、指定显示器或外部窗口截图时临时排除全部 Blink 窗口；目标本身属于 Blink 时仅保留目标，排除其他 Blink 窗口。
- `exclude`：强制排除全部 Blink 窗口；若目标是 Blink 窗口则返回结构化参数冲突。
- `include`：保持当前现场，Blink 对话、设置、便签等窗口可进入截图。
- 用户未说明时 AI 使用 `auto`；“原样/包括对话框/保留 Blink”使用 `include`；“不要截到 Blink”使用 `exclude`。确认卡需展示解析后的实际行为。

**原子截图事务**：AI 不负责先调用窗口管理来隐藏 Blink。app 层截图编排在一次 `screenshot` 调用内完成：记录 Blink 可见窗口、当前前台窗口与目标窗口状态 → 对需排除的 Blink HWND 使用 DWM cloak（不触发 hide/close 业务语义）→ 必要时临时 restore/activate 外部目标 → `DwmFlush` → 复核目标身份并截图 → 无论成功、失败、超时或取消均恢复 cloak、目标原状态与合理的前台焦点。不得调用会 abort ChatService 的语义化 `hide_chat_window`，也不得把已隐藏但尚未截图的半完成状态暴露给 AI。

**目标准备语义**：外部窗口截图默认保证目标可见并前置；若目标最初最小化，截图后恢复最小化。默认不最大化目标，不扰动其尺寸；最大化只由用户显式请求或独立窗口管理调用触发。长期若切换到可捕获被遮挡窗口内容的专用后端，可在不改变 Capability 契约的前提下替换此编排实现。

**独立窗口管理 Capability**：新增 `manage_window`，首版只提供 `activate`、`minimize`、`maximize`、`restore`。不把这些动作塞进 `screenshot`；截图只消费内部目标准备编排。首版不提供 `close`、`move`、`resize`、持久 `always_on_top`，避免数据丢失、混合 DPI 几何与遗留置顶状态。

**窗口引用与权限边界**：`list_windows` 返回短期有效的 opaque `window_ref`，AI 的 `screenshot.window` 与 `manage_window` 优先使用该引用，不把模型生成的裸 `hwnd` 当作权限凭据。执行时重新核验 HWND、PID、窗口身份、可见性与引用代际/时效，失效返回结构化错误并要求重新列举。通用 `manage_window` 不控制 Blink 自身窗口；Blink 自隐藏只走截图事务。窗口列表/截图继续是 sensitive；改变外部窗口状态属于有副作用能力，按 Capability policy 做授权、确认与审计。

**分层落点**：Win32 枚举、身份验证、cloak、激活与窗口状态原语归 `infra/platform/window`；截图事务与恢复 guard 归 app 编排层；domain 只保留 `manage_window`/`screenshot` 的闭合 schema、policy 与窄语义 port，不获得 AppHandle、任意 label 或通用事件发送权。符合 `spec-architecture.md §A3.5` 的“多入口、单一原子执行语义”。

### 3.13 EnergyVad 自适应升级与语音文本防回退（已定，0.22.15，待实现）

**调研结论**：不以 GGUF FSMN-VAD 直接替换现有 EnergyVad。第一轮 GGUF spike 的当前 worker 接口只能整段离线调用，且每次调用重新加载模型；接到累积音频热路径会放大为重复全段推理，缺少流式 cache/reset。第二轮可增量 ONNX FSMN-VAD 对比中误触发更少，但短句漏检更多，采用门已在 0.22.10 关闭。0.22.15 不新增模型、runtime、worker 参数或安装资产，先升级常驻内存内的 EnergyVad；原始证据继续以 `xtask/spikes/fsmn-vad/decision.md` 和 `xtask/spikes/onnx-spike/followup/decision.md` 为准。

**现状定位**：当前 EnergyVad 只以单一固定 RMS 阈值判静音，没有环境底噪学习和开/关滞回；风扇、键盘、远场低声与麦克风增益变化需要用户手调。伪流式句尾还有一条非原子路径：`SentenceEnd` 先推进 `current_sentence_start`、清空 `latest_preview`，随后才异步请求句子定稿；若定稿为空或失败，上一条非空预览及其音频边界缺少回滚。句子定稿 task 也没有像 preview task 那样携带内部 generation，旧 session 迟到的 pending 结果存在进入新 session 的结构性风险。G1 另有确定的前端接线回归：后端正常结束仍发送 `blink://chord-fill-query`，但 `frontend/js/main-window/lifecycle.js` 中对应 listener 在提交 `e5806c29`（剪贴板独立模式）移除后未为语音终稿保留；录音中的首句只显示在 ghost preview，`VOICE_RECORDING_END` 清理 ghost 后，终稿无法写回 `#query`，用户观察为“空文本吞掉备选文本”。

**EnergyVad 升级边界**：

- 在 domain 内引入有界底噪估计与 speech-on/speech-off 双阈值滞回；只在非语音/低能量帧更新噪声基线，阈值受安全上下界约束，避免把持续人声学成底噪。既有 `silence_threshold` 保留为用户灵敏度基准，`min_silence_ms` 与 `min_sentence_ms` 保持兼容，不静默丢弃旧配置。
- 保留 `process_chunk` 纯内存、同步、无 I/O 的热路径；统计窗口固定容量，稳态不得产生随录音时长增长的分配或扫描。VAD 只负责端点事件，不获得 worker/transport/Tauri 依赖。
- 句尾裁剪与 VAD 共用同一套噪声语义，移除互相矛盾的固定尾静音阈值；增加最小有效语音/短噪声抑制，咳嗽、敲键和瞬时爆音不得单独提交空句。
- 本链路从 session 开始就连续保存全部 PCM，当前没有按 speech-start 丢弃开头，故不为“看起来完整”额外增加 pre-roll；只有未来引入起点裁剪时才重新评估。也不在 `min_silence_ms` 之外叠加不可解释的 hangover，句尾延迟仍由一个可配置预算控制。

**文本提交必须单调**：

- VAD 句尾只创建 pending segment；句子音频边界、confirmed 文本与 preview 清理作为同一事务提交。异步定稿非空才 commit；空串、清洗后为空、错误或超时均不得缩短当前可见文本，也不得不可逆跳过该段音频，留给后续预览/最终 release 重试。
- G1 恢复 `CHORD_FILL_QUERY → search.fillQuery()` 终稿接线，正常结束以 final text 覆盖录音态预览并只触发一次搜索；剪贴板继续使用独立 `CHORD_ENTER_MODE`，二者不再共用业务语义。G3 保留录音开始时的 `voiceBaseText`，G1 同样明确“原有输入 + 本轮语音”的基线策略，空 partial 只能是 no-op。
- domain/adapter/app/frontend 四层都执行 generation/session 校验；前端再以单调 revision（或等价 session token）拒绝迟到事件。`confirmed` 在同一录音代际内只增不减，空事件不得作为清空命令；取消/ESC 才允许按既有产品语义清理。
- 修复采用双层防线：domain 保证不会提前丢音频/预览，frontend 保证空或陈旧事件不能覆盖输入。不得只用 UI 条件判断掩盖底层句子提交丢失。

**观测与回归**：日志只记录 generation、segment/revision、样本数、VAD 转移原因、定稿结果类别（non-empty/empty/error/timeout）与耗时，不记录音频和识别正文。新增确定性状态机测试、伪流式异步定稿测试和主窗事件测试；实机语料至少覆盖安静近讲、远场低声、持续风扇、键盘瞬态、咳嗽、慢速停顿、多句续说、全静音及“说一句后继续按住并长停顿”。
