# Blink 0.22 — 本地模型运行时与 PP-OCRv6（从专用维护到多引擎生命周期）

> **范围**：建立受限的本地模型运行时，统一进程、Provider、模型资产、状态与设置管理；迁移 FunASR，接入 PP-OCRv6，并以常驻 GGUF worker 原位替换旧 FunASR Python/PyTorch 推理链路；后续将 OCR 切换到 ONNX、删除 Python/uv 重依赖，同时让稳定的 `funasr` 产品入口按模型绑定 GGUF 或 ONNX 实现，保留 Fun-ASR-Nano 的独特中文识别价值。

> **状态**：🚧 进行中（0.22.0～0.22.8 已完成：GGUF 核心与两项产品契约收口、OCR ONNX 实现与切换均已落地；剩余 0.22.9 STT 双 runtime、VAD 与真流式实现 / 0.22.10 运行时收敛与 Python/uv 清理）。

> **动机**：FunASR 原有安装、进程、模型和诊断逻辑过度绑定 STT；PP-OCRv6 作为第二个真实引擎，需要一套可复用但不伪造执行能力交集的管理面。ONNX 对 OCR 可显著消除 Python venv，对 STT 则提供 FSMN-VAD 与真流式候选；但 Fun-ASR-Nano 暂无等价 ONNX 实现且具备独特中文识别价值，因此收敛目标修订为“删除无价值的重依赖、按模型保留有价值的 runtime”，不追求形式上的单 runtime。

> **前置**：0.10 本地 STT、0.11/0.17 OCR、0.21 Capability 体系已完成。

> **原则**：不影响 `Alt+Space → Focus → 输入` 主链路；分层、日志、错误、事件与前端约束分别以 `spec-architecture.md`、`spec-backend.md`、`spec-frontend.md` 为准；未知进程绝不按端口自动终止。

## 二、背景与动机

### 2.1 为什么 0.22 做这件事

0.22 将散落在 FunASR/STT 中的安装、进程、模型、日志和清理职责收敛为本地引擎管理面，并用 PP-OCRv6 与原生 GGUF FunASR 验证 Python、受管二进制、按需 OCR 和常驻 STT 可以共享生命周期契约而不共享具体推理实现。后续用 ONNX 替换 OCR Python 重栈；STT 不再预设全量替换 GGUF，而是依据模型价值和真实资格实验形成 GGUF/ONNX 双 runtime 的最小有效集合。

### 2.2 明确"不是问题"的

- 系统/用户 Python 与 Blink 托管 Python 保持隔离；多个引擎不共享可变 site-packages。
- 模型按需下载，不进入 Blink 安装包；安装包只携带锁、协议、许可与必要 worker 产物。
- WinRT OCR 永久保留为零安装 fallback；PP-OCRv6 是可选高质量后端。
- 管理页的状态、安装和日志命令不是 Capability；除非未来确有 CLI/MCP/AI 入口及授权设计。
- 本地引擎不全部常驻：FunASR 由用户策略控制，OCR 默认按需并在空闲后回收。
- 前端继续纯静态 HTML/CSS/JS，无 bundler、npm 或构建步骤。

## 三、核心设计与决策

### 3.1 分层与注册边界（已定）

`domain/local_engine` 定义框架无关协议，`infra/local_engine` 提供进程、部署和 Provider 原语，`app/local_engine` 持有唯一 `EngineManager` 并投影 IPC/事件。注册表是编译期 allowlist；前端只能提交受限 engine/model/action，不能注入 executable、URL、脚本、argv 或环境变量。

### 3.2 状态与资产提交（已定）

环境、进程、服务、模型、desired state 和 operation 彼此正交；状态以 `(service_epoch, revision)` 防止旧实例覆盖。每个引擎同时只允许一个变更操作。

引擎 deployment 与模型资产都只有一个稳定 active pointer。安装在 staging/candidate 中完成校验，原子切换失败时保留旧 active；journal、slot 和 residue 是事务实现，不是面向用户的版本列表。selected、installed 和 active 模型必须分开表达，切换失败不得静默改选其他模型。

### 3.3 进程与信任边界（已定）

受管进程并发排空 stdout/stderr，日志有界；Windows 用 Job Object、instance token、PID 创建时间、可执行路径和 health 身份共同验证。终止和异常恢复均 fail-closed；端口被未知进程占用时只换端口或报错，绝不自动 kill。

### 3.4 Provider 与计算设备（已定）

Provider 只实现声明过的锁定安装计划。PythonVenv 和 ManagedBinary 可以共享只读、版本/hash 精确的公共 artifact，但 active 环境保持隔离。计算设备区分用户 preference、解析后的安装 profile 与 health 回报的 actual backend；显式设备失败不得静默回退。

### 3.5 OCR 路由与生命周期（已定）

默认 OCR 仍为 WinRT。显式 `paddleocr` 失败返回可行动错误；`auto` 只在 PaddleOCR 已热态时使用，否则立即走 WinRT，不为普通截图引入隐式冷启动。PaddleOCR 首次调用使用 singleflight，取消、session/epoch 和 idle TTL 共同防止旧结果覆盖与进程泄漏。

PP-OCRv6 spike 结论保持 `conditional-go`：准确率与几何结果明显优于当时 WinRT 基线，但 CPU 热识别约 4 秒、峰值工作集约 1136MB，不得被描述为轻量默认后端。原始数据见 `xtask/spikes/ppocrv6/decision.md`。

### 3.6 FunASR 原位替换（已定）

产品侧始终只有稳定的 `funasr` engine id。0.22.7 用 `ManagedBinaryProvider + ManagedProcess + NDJSON stdio worker` 原位替换旧 Python HTTP/PyTorch 链路；stdout 仅承载协议，诊断走 stderr。SenseVoice、Paraformer-zh 和 Fun-ASR-Nano 都是同一引擎的受限模型候选，一次只常驻当前选择的一个模型。

旧 SenseVoice/Paraformer 配置按确定映射迁移；未知旧 id 保持原样并显示不可用，不静默换模型。模型与 worker 来源固定 revision/SHA-256，运行期不跟随浮动分支。SenseVoice 常驻实测约 251MiB；该资源成本留在最终 release gate 继续做整进程树测量与产品提示。

### 3.7 FunASR 能力与交互归属（0.22.7 待收口）

FunASR 卡片是模型选择的唯一写入口：已安装模型在卡片内展示"使用/当前/等待重启"等状态，语音页只读展示当前选择及跳转到 FunASR 卡片的入口。`selected` 与进程实际加载的 `active` 必须继续分开；服务运行中切换模型应经用户确认后完成 stop → selection commit → start，失败时恢复可解释状态，不能只改配置制造"已经切换"的假象。产品始终只允许一个 ASR implementation 活跃；一个轻量 VAD 前端与一个当前 ASR 配对不等于多 ASR 同时常驻。

当前 GGUF worker 未消费热词和可控 ITN 参数，因此删除语音页热词/ITN 控件、对应配置投影、协议字段和能力声明，不能继续展示无效开关。SenseVoice 自身输出归一化及现有 GGUF 后处理不是可切换 ITN，不在清理时误删；现有 EnergyVad 三项参数保留到 0.22.9 的 EnergyVad/FSMN-VAD 同语料资格门给出结论，不预设一定删除。

模型切换会依赖可靠的主动停止语义：用户 stop、切模重启、空闲回收和应用退出均不得被上层投影成"进程意外退出"。PaddleOCR 应优先调用已存在且带 token 的 `/shutdown`，超时后再由 `ManagedProcess` 回收；最终 `Stopped { code: Some(1) }` 仍可保留诊断信息，但不能进入异常退出错误态。

### 3.8 ONNX 引擎切换决策（0.22.8/0.22.9/0.22.10）——修订

ONNX follow-up 的职责是判断路线与架构是否值得进入实现，不替代实现期的生产链路验收。Spike A/B 已用最终 Rust 依赖跑通动态 ORT、负面加载、真实 `oar-ocr` pipeline 与既有 OCR corpus；Spike C 已跑通 Rust ParaformerOnline 的 fbank/LFR/CMVN、CIF、encoder/decoder cache 和 chunk 推理；Spike D 已证明 VAD runner 与 ONNX ASR 可以分开编排，结合现有 GGUF STT port 足以支持“VAD 与 ASR runtime 正交”的架构设计，但其合成 corpus 和未覆盖 GGUF 的结果不用于判断具体组合质量、默认 VAD 或默认 ASR。上述结果已足够解除 0.22.8/0.22.9 的开工阻塞；0.22.8 的 gate 收敛为链路/契约与轻量冒烟，0.22.9 仍按其业务目标完成详细 production gate。

当前决策修订为：

1. **OCR ONNX 正式进入实现**：`oar-ocr + ORT` 的路线级可行性已通过；0.22.8 原位替换稳定 `paddleocr` engine id 下的 Python 实现，不新增面向用户的 `paddleocr-onnx` 引擎。几何映射、取消/generation、轻量资源冒烟和迁移体验在实现期闭合，不再作为开工阻塞；模型准确率和严格性能 benchmark 不进入本子版本。
2. **GGUF 栈与现有三模型保留**：GGUF 不是脚本，而是锁定构建的 C++ worker 二进制及其构建入口、供应链锁、模型资产描述和 NDJSON 协议。Nano 暂无等价 ONNX 实现，并具有独特中文识别价值；0.22.9 保留 SenseVoice、Paraformer-zh、Fun-ASR-Nano 三条既有 GGUF 路径，只新增通过资格门的 ParaformerOnline ONNX，不借双 runtime 改造删除或静默迁移现有模型。未来删减只由 0.22.10 的独立产品退役决策改变。
3. **VAD 与 ASR runtime 正交**：EnergyVad/FSMN-VAD 和 GGUF/ONNX ASR 必须交叉实测；允许 `FSMN-VAD ONNX + Nano/SenseVoice GGUF` 混合路径，不能把神经网络 VAD 的收益错误归因于 ONNX ASR。
4. **ParaformerOnline 正式进入工程化**：Rust 真流式链路的技术可行性已通过，可以实现对应 implementation；只有完成真实时间节奏下的句尾前 partial、cache/reset/cancel、CER 与 p50/p95 延迟验收后才注册为生产候选。“流式 VAD + 离线 ASR”必须明确标为伪流式。
5. **runtime topology 定案为 Hybrid，不再重开 in-process/worker 选型**：OCR 使用 in-process lazy Session；ParaformerOnline 使用独立受管 ONNX worker；现有三模型保持 GGUF worker。Spike E 已用真实推理、优雅退出、强制回收、重启和 orphan 检查证明 worker 链路可行。该决策以 native crash 隔离、确定释放重型模型和保护 `Alt+Space` 主链路为依据，不把未执行的 in-process/worker 性能对比写成证据；后续 spike 只验证生产协议、真实时间节奏和资源/质量 gate，不重复比较 topology。
6. **用户选择业务模型，不选择技术底座**：设置页继续只有稳定的 `funasr` 卡片；模型或业务模式决定内部 GGUF/ONNX implementation。runtime/profile 可作为诊断信息展示，不新增普通用户的 GGUF/ONNX 开关。

### 3.9 单一产品引擎下的多 implementation 边界（0.22.9 前置）——已定

当前架构不能直接表达同一 engine id 按模型切换 runtime：`EngineDefinition` 只有一组 `runtime_kind`、`service_transport`、`install_plan` 和 `model_contract`；`EngineRegistry` 以 engine id 唯一映射一个 adapter；deployment 也以 engine 为粒度只有一个 active pointer。因此不能通过“再注册一个 `funasr-onnx` adapter”绕开，否则会破坏稳定 engine id、唯一模型选择入口和 selected/active 语义。

0.22.9 必须先引入受限的内部 implementation 层：

- 产品层仍只有 `funasr`；内部 implementation 具有编译期闭合 id，并分别声明 runtime、transport、artifact/install plan 与可承载模型。
- 每个模型 descriptor 绑定一个内部 implementation；用户选模型后，Manager 从编译期映射解析 implementation，不接受前端提交 runtime、可执行路径或 URL。
- start 时同时冻结 selected model、resolved implementation、runtime profile 和 deployment identity；运行中切模仍走 stop → commit selection → start，失败保持可解释回滚。
- GGUF worker、ONNX in-process/worker 可以拥有各自 deployment；产品状态仍只投影一个 selected model 和一个 active model/implementation，一次只允许一个 ASR 实现活跃。
- 共享 ONNX runtime 若采用进程内加载，必须具备版本化目录、全局唯一初始化、`pending_restart` 和旧 generation 结果隔离；若采用 worker，则复用受管进程、身份验证和异常恢复契约。
- 该 implementation 层只服务编译期内置实现，不演化为任意第三方 runtime 注册或前端可注入通道。

### 3.10 ONNX executor topology——Hybrid（已定）

`executor topology` 只描述 ONNX Session 在哪里运行以及 Blink 如何调用：in-process 由 `blink.exe` 直接持有 ORT/Session；worker 由受管子进程持有并经受限 IPC 调用；hybrid 则按模型资源与故障边界分别选择。它位于 adapter/implementation 之下，不进入用户模型选择，也不改变 domain 的 STT/OCR port。

Spike E 已以最小、真实链路验证 ParaformerOnline worker：加载实际 ORT 与模型后发出 ready，连续 chunk 能产生 non-empty partial/final，`Quit` 可优雅退出，强制 kill 后 host 存活且完成 wait，随后可重启并确认无 orphan。该证据足以关闭部署形态决策；延迟、内存、CPU、RTF 与 p50/p95 不属于此次 feasibility，也不作为 Hybrid 优于其他 topology 的论据。

- OCR 模型轻且按需使用，按 in-process lazy Session + idle TTL 实施，同时保留独立 executor 边界。
- ParaformerOnline 模型与 Session 资源显著高于 OCR，按独立受管 ONNX worker 实施，使 native crash 不影响 `Alt+Space` 主链路，并让 stop/切模确定释放内存。
- Fun-ASR-Nano 继续使用现有 GGUF worker，作为具有独特中文识别价值的正式可选模型，不降级为仅故障 fallback。
- FSMN-VAD 可与 GGUF Nano 或 ONNX ASR 配对；其部署跟随实际组合与资源测量，不因模型格式是 ONNX 就强制与 ParaformerOnline 同进程。
- Hybrid 的三个 executor 在上层仍只呈现闭合的 `StreamingSttExecutor`/OCR executor 能力；不得让 transport、DLL 路径或任意 worker 参数穿透到 domain 或前端。
- Spike E 的 NDJSON `Vec<f32>` 只用于证明链路；生产 worker 的连续音频热路径不得使用 JSON 浮点数组或 Base64，应采用有界二进制 framing、共享缓冲区引用或等价的流式背压协议，并保留 generation/cancel/lifecycle 语义。

### 3.11 0.22.8 OCR ONNX 安装、执行与验收边界（已定）

0.22.8 以打通可信的生产链路为目标，不跨过 OCR 业务边界重新评价 PP-OCRv6 模型本身。既有 corpus 只用于证明接线、结果映射与升级前后没有明显功能性回归；CER、语言子集能力和模型横向选型不作为本子版本 release gate。性能与资源只做轻量冒烟记录和明显异常排查，不设置严格 p50/p95、模型吞吐或跨机器绝对阈值。

- **运行时与模型分层**：`RuntimePlan::OnnxRuntime` 是闭合的共享动态运行时计划，不伪装成 `ManagedBinary`。ORT DLL 使用版本化、不可变 artifact；PP-OCRv6 det/rec/dictionary 使用 `model_storage` generation；PaddleOCR deployment manifest 同时冻结二者 identity。
- **联合提交，指针最后切换**：ORT 与模型分别 staging、校验和 promote，未被 deployment 引用的中间产物只作为可清扫 residue；只有两者联合 self-test 通过后才提交 engine deployment pointer。
- **安装自检隔离**：真实 Session + 最小推理 self-test 必须运行在一次性隔离验证进程中，禁止 Blink 主进程从 staging 加载 DLL。验证进程可以复用 `blink.exe` 的隐藏内部入口，但不是用户 CLI，也不是第二种常驻 OCR executor topology。
- **主进程加载与重启**：正式 OCR 仍使用 in-process lazy Session。主进程尚未初始化 ORT 时，首次安装可立即加载 active runtime；已经加载不同 DLL identity 时，更新/回滚只修改 desired deployment 并投影 `pending_restart`，当前 loaded deployment 不说谎。只切换模型 generation 不要求重启。
- **旧 Python 只作降级资产**：升级用户的 Python deployment 在 0.22.8 中作为独立 legacy deployment 保留，供旧版 Blink 降级兼容，不参与新版本运行时 fallback。ONNX 安装/启动失败时，显式 `paddleocr` 返回可行动错误，`auto` 继续走 WinRT，禁止静默重新启动 Python。用户可在明确警告后主动清理 legacy 资产，0.22.10 再完成默认迁移与删除。
- **单 Session 有界执行**：首版只保留一个 OAROCR pipeline/Session，由专用 blocking executor 承载，避免阻塞 Tokio 与并发 Session 放大资源；不建立 Session pool。一次只执行一个请求，最多保留 4 个 pending，queue 满返回结构化 Busy；ORT 默认 `inter_op=1`、`intra_op` 不超过 4，避免抢占 Alt+Space 主链路。旧 request/session epoch 不得覆盖新结果。
- **取消语义诚实**：不为 0.22.8 预先 fork `oar-ocr`。queued 请求可立即移除；active 请求取消后调用方立即得到 Cancelled，executor 标记 request generation 失效并丢弃迟到结果，当前不可中断的 native call 允许有界收敛后再接下一项。不得把“停止等待”描述成 ORT kernel 已被强制终止；若真实链路出现不可接受的长时间占用，再单独评估上游/最小 fork 的 run cancellation。
- **TTL 与 hot 定义**：idle TTL drop pipeline 和模型 Session；ORT DLL/全局 Environment 可以继续留在进程。只有 Session Ready 才算 OCR hot，不能把“资产已安装”或“DLL 已加载”当成 `auto` 可使用的热态。
- **结果契约不变**：优先使用 oar-ocr 原生 region/word boxes；缺少 word boxes 时以 region 生成单个 fallback word，禁止按字符等宽伪造框。坐标须校验有限值、正面积和图片边界，再进入既有 line grouping 与 `OcrResult` 契约。
- **native 故障边界不夸大**：in-process OCR 无法隔离真正的 native access violation；损坏 DLL/模型、ABI、hash 和 Session 构建失败由安装 validator 与负面测试阻断，生产路径不宣称具备 worker 级 crash isolation。
- **供应链与制品**：生产 asset lock 必须保存完整 URL、版本/revision、完整 SHA-256、大小和 license；CPU 包锁定必要 DLL，禁止隐式下载和 CUDA/TensorRT provider。lock metadata 可随程序发布，ORT DLL 与 ONNX 模型仍按需下载，不进入安装包。

### 3.12 0.22.9 产品范围、默认策略与 production gate（已定）

- **既有模型不退役**：0.22.9 保留 SenseVoice、Paraformer-zh、Fun-ASR-Nano 三个现有 GGUF 模型及其安装、选择、识别、恢复和切换能力；本版唯一新增的生产 ASR 候选是 ParaformerOnline ONNX。SenseVoice/Paraformer offline ONNX 与 2pass 不进入本版生产范围，已有调研只作为后续证据。
- **不静默迁移默认模型**：升级用户的 selected model 原样保留；ParaformerOnline 通过注册门也只新增候选，不自动替换任何已有选择。是否改变 fresh install 默认模型必须在 production report 完成后另作产品确认，agent 不得自行决定。
- **VAD 不暴露技术选择器**：普通用户不选择 EnergyVad/FSMN-VAD。内部使用受限 `auto` 策略；显式修改过 EnergyVad 参数的旧配置继续保留 EnergyVad 语义，未定制配置只有在 FSMN-VAD 通过采用门后才可解析到 FSMN-VAD。EnergyVad 在 0.22.9 不删除。
- **用户只控制是否实时预览**：不恢复 `True/Pseudo` 技术模式开关。模型支持真流式时实时预览走 native partial，否则走现有伪流式；关闭实时预览时只展示 final。runtime、transport 与 VAD 类型均只作诊断或内部解析信息。
- **跨 runtime 切模回滚**：运行中切模冻结旧 snapshot，依次执行 stop old → commit selected target → start target。目标启动失败时恢复旧 selected 并按冻结 snapshot 重启旧实现；若恢复也失败，则保持 `selected=旧模型、active=None`，结构化错误同时保存目标失败和恢复失败，不得把目标投影为 active。
- **注册门**：对时长大于 1.2 秒的有效语音，ParaformerOnline 必须在句尾前产生非空 partial；first-partial `p50 <= 400ms`、`p95 < 800ms`，final-after-release `p95 <= 800ms`，RTF `p95 < 0.8`，中文 CER 相对同语料 Nano 基线恶化不超过 1 个百分点；100 次 start/stop/cancel 与 10 次 kill/restart 不得产生 orphan、协议死锁或旧 generation 结果泄漏。任一项失败则保持未注册，不能降低阈值换取完成。
- **FSMN-VAD 采用门**：同一真实 corpus、同一 ASR 下，下游 CER 相对 EnergyVad 恶化不超过 0.5 个百分点，句界 F1 不得低于 EnergyVad 超过 0.02；未同时满足则继续解析到 EnergyVad，FSMN-VAD 保持内部未启用候选。
- **默认模型决策门**：通过注册门只获得“可见候选”资格，不自动获得默认资格。默认决策还必须补齐整进程树内存、冷启动、磁盘、中文质量和 G1/G2 实机体验；若与 `<300MB` 目标冲突，先停止默认放行并提交产品决策，agent 不得自行修订资源目标。

### 5.1 0.22.7 — 两项产品契约收口（已完成）

按顺序拆为两个可独立验收的 handoff：

1. **失效能力清理**：删除热词与 ITN 的 UI、配置写入、运行时投影、worker 协议字段、能力声明和对应测试/i18n；旧配置必须可安全读取并在下次保存时自然收敛，不能影响 VAD 参数和 GGUF 固有后处理。
2. **唯一模型选择入口**（已完成）：FunASR 卡片承接安装、选择与当前/等待重启状态；语音页只读展示并可跳转。补齐运行中切换的确认、stop/restart、失败回滚/状态刷新，并一并修正 PaddleOCR 主动停止被误报异常退出的问题。

### 5.2 0.22.8 — OCR ONNX 实现与切换（已完成）

Rust feasibility 已通过；本子版本用 `oar-ocr + ONNX Runtime` 原位替换稳定 `paddleocr` engine id 下的 Python PaddleOCR。目标是闭合“锁定资产 → 安装验证 → deployment 提交 → lazy Session → OCR 路由 → 设置页状态 → 升级/回滚”的完整链路；WinRT 继续承担产品 fallback，不新增第二张 ONNX OCR 卡片。模型准确率与严格性能优化不进入本子版本范围。

实施按以下一个开工基线包与六个内聚工作包串行推进；每包必须独立完成测试和自审后再交给下一包，禁止多个 agent 同时改同一 deployment/manager 主链：

0. **Gate — 固定开工基线**：在改动 0.22.8 代码前运行 fmt、全目标 clippy、Rust/前端测试和 release-check；只修复或隔离确属 0.22.7 的基线问题，并记录命令与结果。基线未绿不得把失败带入 A 包。
1. **A — 闭合运行时协议与兼容读取**：新增 `OnnxRuntime` 的 domain identity、install plan、manifest extension、Manager/provider 分派、cleanup 与引用扫描；定义 desired/loaded deployment 和 `pending_restart` 语义；旧 Python manifest/deployment 可继续读取并标记 legacy，但不参与新运行时 fallback。该包只建立闭合协议与迁移护栏，不接入真实下载或 OCR。
2. **B — 锁定供应链并实现联合安装**：建立生产 asset lock；实现版本化 ORT Provider、PP-OCRv6 model generation 准备、联合 staging/promote/deployment pointer 事务，以及一次性隔离 validator 的真实 Session + 最小推理。覆盖下载取消、hash/ABI/模型损坏、validator 超时/异常和事务恢复；资产不进入安装包。
3. **C — 实现 in-process OCR executor**：实现单 pipeline/Session、专用 blocking executor、有界 queue、lazy load、health、idle TTL drop、request/executor/model/runtime generation 与诚实取消。domain 不依赖 `ort`/`oar-ocr`；不做 Session pool，不为硬取消 fork `oar-ocr`，不阻塞 Tokio worker。
4. **D — 原位切换 PaddleOCR adapter 与路由**：把稳定 `paddleocr` adapter 从 Python HTTP 改为 ONNX executor，完成 oar-ocr region/word box 到 `OcrResult` 的严格映射；保持显式失败、`auto` hot-only/WinRT fallback、截图 session/epoch、singleflight 与 idle TTL 语义。legacy Python 不作为 fallback。
5. **E — 设置页与管理状态原位适配**：仍使用一张 PaddleOCR 卡片，展示 ONNX runtime、模型资产、desired/loaded/pending restart 与 legacy 空间；安装/更新/回滚/清理动作复用既有受限 IPC，不新增技术底座选择器。异步状态继续按 service epoch/revision、operation id 与 deployment identity 拒绝旧回流。
6. **F — 链路验收与 release gate**：完成 fresh install、旧 Python 升级、安装失败不切 active、首次启用、热态识别、取消、TTL drop、runtime 更新等待重启、回滚、legacy 主动清理、WinRT fallback 和正式制品排除，并复跑 Gate 的全部工程门禁。既有 corpus 只做接线/映射冒烟；资源只记录未加载、Session Ready、识别后、TTL drop 四个快照并排查明显泄漏/异常，不做严格性能或模型质量 benchmark。

**验收边界**：
- 必须证明稳定 engine id、`OcrResult`、显式 PaddleOCR、`auto` hot-only、WinRT fallback 和截图 session/epoch 契约不变。
- 必须证明资产 identity、安装事务、隔离 self-test、desired/loaded/pending restart、legacy 读取和 generation 隔离均可解释且失败不说谎。
- 既有 corpus 必须全部跑完且无 panic/协议错误/非法坐标；仅记录输出差异供人工抽查，不以 CER 或语言子集识别率阻塞 0.22.8。
- 性能与资源只做轻量冒烟：记录代表性图片的首次/热态耗时和四态内存，确认没有数量级退化、持续增长或影响 Alt+Space 输入主链路的明显异常；不要求 p50/p95、跨机器绝对阈值或模型吞吐对比。
- fresh install 的 ONNX OCR 资产和升级用户保留的 legacy Python deployment 分开计量；只有显式/迁移清理旧 venv 后才宣称释放对应空间。

### 5.3 0.22.9 — STT 双 runtime、VAD 与真流式实现（规划，已具备开工条件）

本子版本不以替换 GGUF 为目标。Spike C 已证明 Rust ParaformerOnline 可以实现，Spike E 已将 topology 定案为 Hybrid，无需重做 in-process/worker 选型。先建立稳定 `funasr` 下的内部 implementation 边界并工程化 ONNX 候选；真实同语料 production gate 决定 ParaformerOnline 是否注册和 FSMN-VAD 是否启用，默认模型仍须在报告完成后另行确认。现有 SenseVoice、Paraformer-zh、Fun-ASR-Nano 三个 GGUF 模型全部保留。

**工作包**：

1. **消费 feasibility 并完成 production gate**：以 Spike C 的 Rust fbank/LFR/CMVN、CIF/cache 和 chunk 推理作为实现依据；不把快速灌入离线 WAV 的墙钟耗时直接当真实首 partial。实现期按实时节奏验证句尾前 partial、reset/cancel，并用真实同语料交叉比较 EnergyVad/FSMN-VAD × GGUF/ONNX ASR，记录下游 CER、首 partial/final p50/p95、RTF、CPU、内存、磁盘和冷启动。
2. **引入内部 implementation 协议**：在一个公共 `funasr` definition/adapter 下声明闭合 implementation 集合；每项拥有 runtime、transport、install plan、可承载模型与资源预算。Registry 仍只注册一个公共 `funasr`。
3. **模型绑定 implementation**：现有 SenseVoice、Paraformer-zh、Nano 继续绑定 GGUF worker，ParaformerOnline 绑定独立 ONNX worker；本版不新增 offline ONNX/2pass 映射。前端只能选择模型/是否实时预览，不能提交 implementation/runtime/VAD；未知旧模型 id 继续保持不可用而不静默换模。
4. **Manager 多 deployment 支持**：环境与 active deployment 按内部 implementation 管理；start 冻结模型、implementation、profile、deployment 和 generation；产品层仍一次只允许一个 ASR active，切模继续使用可靠 stop/restart/rollback。
5. **FSMN-VAD 可插拔前端**：在不绑定 ASR runtime 的前提下实现神经网络 VAD；普通用户不选择 VAD，内部 `auto` 只有通过 §3.12 采用门才启用 FSMN-VAD，显式定制过 EnergyVad 参数的旧配置继续保持原语义。EnergyVad 本版不得删除。
6. **只工程化 ParaformerOnline ONNX**：SenseVoice/Paraformer offline ONNX 与 2pass 不进入 0.22.9 生产实现；ParaformerOnline 只有通过 §3.12 注册门后才加入正式模型目录，失败则保持内部未注册。
7. **统一 STT transport port**：domain 继续依赖框架无关的 STT/VAD port；GGUF NDJSON、ONNX in-process 或 ONNX worker 位于 app/infra 实现，不让 domain 直接依赖 `ort`。Spike E 的 JSON 浮点数组仅是 feasibility 载荷，生产 ONNX worker 必须使用有界、可背压的二进制音频传输或等价共享引用，不能把大音频数组放进 JSON/Base64 热路径。
8. **前端保持一个 FunASR 卡片**：展示模型的业务差异（中文质量、多语言、真流式、资源占用）以及只读的实际 runtime 诊断；用户只控制是否实时预览，不新增 GGUF/ONNX、True/Pseudo 或 Energy/FSMN 技术开关，也不增加第二个 FunASR 引擎。
9. **落实 Hybrid executor topology**：OCR in-process、ParaformerOnline 独立 ONNX worker、Nano 现有 GGUF worker；复用受管进程的身份、日志、主动停止、kill+wait、异常恢复与 orphan 防护，不能把 spike worker 直接当生产实现。

**验收标准**：
- SenseVoice、Paraformer-zh、Fun-ASR-Nano 三条 GGUF 路径的安装、选择、启动、识别、崩溃恢复与模型切换继续通过，迁移不降低既有能力。
- VAD/ASR 组合结论来自同一可复现 corpus；FSMN-VAD 的判断同时包含切句指标和下游 CER，不能只用模型 RTF。
- 只有句尾前产生 partial 的路径可声明真流式；首次 partial 定义为首个有效语音样本进入引擎到 UI 可展示非空文本，并满足 §3.12 的注册门。
- 设置页只有一个 `funasr` engine id 和唯一模型写入口；selected model、active model、active implementation 均可解释且不说谎。
- 一次只活跃一个 ASR implementation；不同 runtime 的安装、清理、切换和失败回滚互不破坏。

### 5.4 0.22.10 — 运行时收敛与 Python/uv 清理（规划）

在 OCR ONNX 和 STT 实现矩阵稳定后删除已被证明冗余的重依赖。确定删除 Python/PaddlePaddle/uv；GGUF worker、供应链锁与模型资产只要仍承载 Nano 或其他通过资格门的模型就继续保留。

**工作包**：

1. **迁移旧 PaddleOCR deployment**：为 PythonVenv manifest、active pointer、journal 和缓存提供版本化读取/迁移或 tombstone；先切 ONNX，再显式清理旧 venv，升级失败可行动且不阻塞 WinRT。
2. **移除 `PythonVenvProvider` 与 uv**：删除 Python distribution/venv/pip/uv 下载、同步、校验与 cache 管理逻辑；`RuntimePlan::PythonVenv` 只有在旧 manifest 已可安全读取/迁移后才停止生产写入并删除或保留 legacy serde 变体。
3. **移除 PaddleOCR Python 资源**：删除 requirements、锁文件、Python server 与 HTTP 专属启动/health/shutdown 代码；保留必要的历史迁移测试与 phase/spike 记录。
4. **保留有效 GGUF 栈**：继续维护 Nano 所需的 `ManagedBinaryProvider`、GGUF worker、NDJSON 协议、构建脚本、worker lock、模型链接/hash 和许可；只删除 0.22.9 明确判定不再使用的模型/实现。
5. **收敛 adapter/registry**：公共 Registry 只保留稳定 `funasr`、`paddleocr` 等产品 engine id；内部 implementation 仅保留资格门通过且有产品价值的最小集合。
6. **清理用户资产**：区分 shared ORT、ONNX 模型、GGUF worker/模型和 legacy Python deployment 的引用；不得因清理 OCR venv 误删仍被 STT/OCR 使用的共享 runtime 或模型。
7. **更新 release-check**：禁止 Python/uv/PaddlePaddle 进入生产资源，继续验证 GGUF 与 ONNX 两条供应链、许可、hash 和资源排除规则。
8. **更新跨版本规范**：implementation 层、双 runtime 状态/部署和 restart 语义稳定后，经确认回写 `spec-architecture.md`/`spec-backend.md`；phase 保留本版决策与文件索引。

**验收标准**：
- 生产代码和发布资源不再依赖 uv、Python venv、pip、PaddlePaddle 或 Python OCR server；历史文档和 legacy migration test 不纳入错误的全仓 grep=0 要求。
- Nano GGUF 与所有保留的 ONNX 实现均可 fresh install、升级、切模、回滚、清理和卸载。
- `cargo test`、前端测试、`cargo xtask release-check` 与正式安装包实机 gate 全绿。
- 安装包不携带 Python/uv/PaddlePaddle 资源；GGUF worker 是否进入制品按既有锁定构建与发布策略执行，不再要求删除。
