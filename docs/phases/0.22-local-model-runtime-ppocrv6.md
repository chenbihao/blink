# Blink 0.22 — 本地模型运行时与 PP-OCRv6（从 STT 专用维护到多引擎生命周期）

> **范围**：建立 Blink 托管的本地 Python 模型运行时，迁移 FunASR 生命周期管理，接入 PP-OCRv6 作为可选 OCR 后端，并在「引擎」设置页提供统一的环境、服务、模型与空间管理。
>
> **状态**：📋 规划中。
>
> **动机**：现有 uv、venv、Python server、模型状态和清理逻辑绑定在 STT/FunASR 中；PP-OCRv6 为第二个真实本地模型引擎，继续复制专用命令会形成两套安装、进程和诊断体系。
>
> **前置**：0.10 本地 STT 与 uv 自管理、0.11/0.17 OCR 能力与 WinRT 后端、0.21 Capability 唯一原子执行入口均已完成。
>
> **原则**：不影响 `Alt+Space → Focus → 输入` P0 主链路；domain 不 `use tauri`；默认引擎级隔离 venv、共享下载缓存；模型由引擎工具箱下载，Blink 只管理运行目录与可观测状态；FunASR 迁移前后行为兼容；未知端口占用进程绝不自动终止。

## 二、背景与动机

### 2.1 为什么 0.22 做这件事

当前本地 STT 已具备一套可工作的 Python 模型生命周期，但职责散落且带有强烈的 FunASR 语义：

- `src/infra/platform/python/mod.rs` 同时硬编码 uv、Python 3.12、torch、funasr 与单一 `venv`。
- `src/domain/stt/funasr.rs` 同时承载脚本释放、启动参数、HTTP/model health 与环境状态投影。
- `src/app/commands/stt/maintenance.rs` 同时持有全局 child、安装环境、轮询模型、转发 Tauri 事件、清理目录、诊断和退出回收。
- `frontend/settings.html` / `frontend/js/settings/tabs/voice.js` 把 Python 环境和服务操作绑定在语音页。
- 服务端口默认固定为 8000；孤儿清理存在“按端口定位并终止进程”的误伤风险，不能复制到多引擎。

PP-OCRv6 已随 PaddleOCR 3.7 成为通用 OCR pipeline 的默认代际，提供 tiny/small/medium 三档及统一多语言模型。它与 FunASR 的框架、依赖、模型缓存、健康协议和运行策略均不同，正好用于验证真正的复用边界。

0.22 的目标不是“把 FunASR 名字替换成 Engine”，而是让 Blink 获得一个受限、安全、可诊断的内置本地模型运行时，同时升级现有 OCR 准确率与多语言能力。

### 2.2 明确“不是问题”的

- **系统 Python 与 Blink 托管 Python 不需要合并**：代码解释器使用用户选择的系统 Python；本地模型运行时使用 Blink 管理的隔离环境，二者用途、信任与变更权限不同。
- **模型文件不需要进入 Blink 安装包**：FunASR/PaddleOCR 仍按自身机制下载模型；Blink 只指定引擎级缓存根目录、展示占用并观察模型状态。
- **WinRT OCR 不删除**：它零额外下载、启动快，是可靠 fallback；PP-OCRv6 是可选高质量后端，不把 OCR 变成“未安装 Python 就不可用”。
- **设置页内部生命周期命令不必伪装成 Capability**：状态查询、安装进度和日志属于管理 UI 协议。仅当未来确有 CLI/MCP/AI 调用需求时，再把允许外部调用的闭合操作建模为受限 Capability。
- **本地模型不自动全部常驻**：FunASR 延续用户可选自动启动；OCR 默认按需启动并在空闲后停止，不用后台常驻换取低频路径的首击速度。
- **前端仍无 bundler/npm/构建步骤**：0.22 只按现有 settings 模块与 CSS 分层扩展。

## 三、核心设计与决策

### 3.1 分层归属 —— domain 定协议、infra 做执行、app 管生命周期（已定）

**定案**：不把带文件、网络、进程与 Tauri 事件的完整 Manager 塞进 domain。

```text
frontend / settings
  └─ 本地模型运行时（底座摘要 + 引擎卡片）
       │ invoke / blink://local-engine-*
       ▼
app/local_engine
  ├─ LocalEngineService（安装/启动/停止/状态/清理编排）
  ├─ EngineRegistry（仅内置 allowlist）
  └─ Tauri command + event projection
       │
       ├───────────────┐
       ▼               ▼
domain/local_engine    infra/local_engine + infra/platform/python
  ├─ EngineId            ├─ ManagedProcess
  ├─ EngineDescriptor    ├─ PythonRuntime / UvEnvironment
  ├─ EngineStatus        ├─ PortProbe / HTTP client
  ├─ LifecyclePolicy     └─ file/process/cache primitives
  └─ LocalEngineAdapter
```

职责边界：

- `domain/local_engine`：稳定 id、声明、状态类型、错误分类、生命周期策略和引擎特有的启动/健康适配接口；不发送 Tauri 事件。
- `infra/local_engine`：启动/停止子进程、排空管道、PID 身份验证、端口探测、HTTP 请求和目录原语；不读取 app 配置，不反向依赖 domain/app。
- `infra/platform/python`：uv 获取、Python distribution、venv 和包同步；从硬编码 FunASR 状态改为通用包集合状态。
- `app/local_engine`：读取各引擎配置、串行化状态变更、调用 adapter + infra、持有运行实例、广播事件，并在退出时回收所有受管进程。
- 业务消费者仍留在所属领域：STT 通过本地 STT client 请求 FunASR；OCR 通过 `OcrBackend` 请求 PaddleOCR。

### 3.2 环境拓扑 —— 默认隔离 venv，共享 uv/Python/下载缓存（已定）

**定案**：每个引擎默认拥有独立 venv；共享 uv 二进制、uv cache 与 uv 管理的 Python distribution。保留命名共享环境作为显式逃生口，不提供简单 `shared: bool`。

```text
%APPDATA%\blink\python\
├─ tools\uv\
├─ cache\uv\
├─ pythons\
└─ envs\
   ├─ funasr\
   │  ├─ active\
   │  ├─ staging\
   │  └─ blink-env.json
   └─ paddleocr\
      ├─ active\
      ├─ staging\
      └─ blink-env.json

%APPDATA%\blink\models\
├─ funasr\
└─ paddleocr\
```

环境作用域表达为 `Isolated` 或 `Shared(name)`。0.22 的 FunASR 与 PaddleOCR 均使用 `Isolated`；共享环境只保留协议，不在本版启用。

**理由**：torch/FunASR 与 PaddlePaddle/PaddleOCR 的 GPU wheel、NumPy、protobuf、OpenCV 等传递依赖升级节奏不同。共享 site-packages 会令安装、更新、清理和回滚相互污染；共享下载资产已经取得主要复用收益。

### 3.3 状态模型 —— 三维观测，不做线性“三级状态机”（已定）

**定案**：UI 可以展示“环境 → 服务 → 模型”三级，但后端保存彼此正交的状态快照：

```rust
EngineStatus {
    desired,        // Stopped | Running
    operation,      // Idle | Installing | Updating | Cleaning
    environment,    // Missing | Ready | Broken { reason }
    process,        // Stopped | Starting | Running { pid } | Stopping | Exited
    service,        // Unknown | Unreachable | Healthy | Degraded
    model,          // Unknown | NotLoaded | Downloading | Loading | Ready | Failed
    revision,
    last_error,
}
```

约束：

- `revision` 每次状态提交单调递增；前端拒绝旧 revision，避免轮询/事件/用户点击竞态覆盖。
- `desired` 与 observed state 分离；“用户要求停止但进程尚在退出”可以准确表达。
- `env ready` 不推出 `server/model ready`；child 存活也不推出端口上的服务属于该 child。
- 每个 engine id 同时只允许一个变更操作；查询可并发，安装/更新/启动/停止/清理必须串行化。
- 错误使用结构化阶段与稳定错误码，日志中保留详细上下文，前端显示可行动文案。

### 3.4 引擎描述符与 adapter —— 数据声明有限，行为显式（已定）

**定案**：描述符声明静态事实，adapter 实现引擎特有行为；不把健康检查和启动逻辑编码成通用字符串 DSL。

描述符至少包含：

- 稳定 `engine_id`、显示元数据与所属能力（STT/OCR）。
- Python 版本、环境作用域和 CPU/GPU 安装 profile。
- 锁定依赖资源、允许的 package index、环境 schema 版本。
- 默认生命周期（manual/auto/on-demand）、启动/模型超时与空闲 TTL。
- 引擎拥有的脚本、配置、日志与模型缓存子目录。
- 资源预算提示与 cleanup policy。

adapter 至少负责：

- 从已校验配置构造 `LaunchRequest`。
- 生成受限环境变量（FunASR 的 ModelScope、PaddleOCR 的模型缓存等）。
- service health 与 model health 的协议映射。
- 安装后 self-test。
- 引擎输出到领域 DTO 的映射。

注册表为编译期内置 allowlist。前端只能传 `engine_id` 与有限动作，不能传 executable、任意 argv、脚本路径或环境变量；0.22 不把它扩展成第三方任意进程托管器。

### 3.5 安装与更新 —— staging、自检、原子切换、可回滚（已定）

安装流程：

```text
解析内置 lock/profile
  → 确保 uv + Python distribution
  → 创建 engine/staging venv
  → uv 同步锁定依赖
  → import/version/self-test
  → 写 blink-env.json
  → 停止旧实例
  → active/staging 原子切换
  → 保留上一份环境至本次启动验证成功
```

要求：

- 依赖真源必须锁版本；不得在生产安装路径使用无上界 `latest`。
- CPU/GPU profile 分开，profile 切换视为环境重建，不在原 venv 原地覆盖框架 wheel。
- 安装失败不破坏当前 active 环境；取消只清理本次 staging。
- manifest 记录 engine id、schema、profile、Python 与包版本、安装时间；状态检查以 manifest + 实际 import 双重验证。
- 清理只作用于该引擎声明拥有的 venv/cache；公共 uv/Python/cache 使用单独的“公共缓存清理”，不得顺带删除其他引擎环境。

### 3.6 进程与端口安全 —— PID 身份优先，未知占用不杀（已定）

`ManagedProcess` 提供：

- stdout/stderr 同时异步排空，避免管道背压死锁。
- 有界日志环形缓冲与结构化生命周期事件。
- child handle、PID、可执行路径、引擎 token 与启动时间身份记录。
- 启动超时、退出监听、优雅停止 deadline、超时后只终止已验证的进程树。
- Blink 正常退出时统一回收；异常退出后的重连/清理必须先验证身份。

端口规则：

- 服务仅绑定 `127.0.0.1`。
- 配置保存 preferred port；启动时检测冲突，必要时从受控范围选择新端口并更新本次 endpoint。
- “探测空闲”与子进程 bind 之间仍可能竞争；遇到 address-in-use 时限次重新分配并重启。
- 每次启动生成随机 token，健康与业务请求均携带 token；健康响应回显 engine id / instance id，用于确认端口服务身份。
- 只有 PID + 可执行路径/instance token 与受管记录一致时才能终止；未知进程占用端口只报冲突或换端口。

0.22.3 必须删除 FunASR 现有“仅凭端口定位 PID 后自动 kill”的路径。

### 3.7 生命周期策略 —— FunASR 可自启，OCR 默认按需 + 空闲回收（已定）

| 引擎 | 默认策略 | 首次调用 | 空闲策略 |
|---|---|---|---|
| FunASR | Manual；沿用用户现有 `auto_start_server` | 未运行时保持当前可行动错误提示，不在录音手势热路径隐式长等待 | 自动启动者随 Blink 生命周期；手动启动者手动停止 |
| PaddleOCR | OnDemand | OCR 请求触发单飞启动；调用方收到明确 loading/progress，启动成功后只重放所属 session 的请求 | 默认 5 分钟无请求停止，可配置为“保持运行”或“使用后立即停止” |

约束：

- OCR 启动不得阻塞 Alt+Space、截图 overlay 展示或前端事件线程。
- 相同引擎并发首次调用合并为一个启动 future，禁止重复拉起。
- OCR 回流继续遵循截图 session/epoch 校验；旧选区启动的识别结果不得覆盖新选区。
- 空闲计时只在 in-flight 请求归零后开始；停止与新请求竞争时，新请求提升 `desired=Running` 并取消空闲停止。

### 3.8 OCR 后端路由 —— PP-OCRv6 可选，WinRT 永久回退（已定）

新增 OCR 配置：

- `backend = auto | windows | paddleocr`
- `paddle_model = tiny | small | medium`，桌面默认候选由 0.22.0 benchmark 定案，规划基线为 `small`。
- `device = cpu | cuda`，0.22 首发必须保证 CPU；CUDA 只有在 Windows wheel/驱动矩阵验证通过后开放 UI。
- `lifecycle = on_demand | keep_running | stop_after_use`。
- 文档方向/矫正/行方向等增强模块默认关闭，截图 OCR 只启检测 + 识别；后续按真实收益开放。

路由语义：

- `windows`：始终使用当前 WinRT backend。
- `paddleocr`：明确选择 PaddleOCR；未安装/启动失败时返回可行动错误，不静默改变用户选择。
- `auto`：PaddleOCR 环境已安装且可用时使用 PaddleOCR，否则使用 WinRT；PaddleOCR 在单次识别中崩溃可降级 WinRT，并记录/展示降级原因。
- 每次识别开始时快照 `Arc<dyn OcrBackend>`，切换配置不改变已经在途的请求。
- PaddleOCR 输出必须完整映射现有 `OcrResult` / line / word rect 契约，前端阅读模式、翻译、pin 与 overlay 不感知后端差异。

### 3.9 模型与缓存边界（已定）

Blink 不实现通用模型下载器。adapter 设置引擎专属缓存根目录并从服务健康协议观察 `NotLoaded/Downloading/Loading/Ready/Failed`。

Blink 负责：

- 下载前展示预计体积（若描述符可知）与网络提示。
- 展示引擎 venv、模型缓存、日志和公共缓存占用。
- 打开引擎目录、停止后清理该引擎缓存。
- 模型 ready 前不发送业务请求。

引擎负责：

- 下载源、断点续传、校验、模型版本解析与加载。
- 将可观测阶段通过 health 协议或服务日志暴露；无法取得字节级进度时只展示阶段，不伪造百分比。

### 3.10 设置页信息架构（已定）

在现有「引擎」页的“代码解释器”下方新增“本地模型运行时”，不新开顶级 tab：

```text
本地模型运行时
├─ 运行时底座（默认折叠）
│  uv / 托管 Python / 公共缓存 / 根目录
├─ 语音识别 · FunASR
│  环境 / 服务 / 模型三段状态，安装、修复、启动、停止、日志、清理
└─ 文字识别 · PP-OCRv6
   后端选择、模型档位、设备、生命周期、安装、启动、停止、测试、日志、清理
```

“代码解释器 Python”文案明确为“系统/用户解释器”；“本地模型运行时”明确为“Blink 托管环境”，避免用户误解 Blink 会修改其 Python。

引擎卡片使用同一 renderer 和状态协议，但允许 adapter 提供有限的额外配置区；不为每个引擎复制一套安装按钮与事件监听。状态事件包含 `engine_id + revision + snapshot`，日志事件包含 `engine_id + instance_id + seq`。

## 四、复用与范围边界

### 4.1 已有基础设施复用盘点

| 现有基础 | 0.22 用法 |
|---|---|
| `infra/platform/python` | 保留 uv 下载、Python 3.12 与路径基础，拆除 torch/funasr 硬编码 |
| `domain/stt/funasr` | 保留 STT HTTP 协议、模型参数和文本后处理语义；生命周期迁出 |
| `app/commands/stt/maintenance` | 作为迁移清单；通用部分下沉，STT 诊断保留薄适配 |
| `domain/capability/builtins/ocr_engine::OcrBackend` | PP-OCRv6 接入点；保持现有 `OcrResult` 契约 |
| WinRT `PlatformOcrBackend` | `windows` 后端与 `auto` fallback |
| `ConfigStore<T>` / `blink://config-changed` | 保存 OCR backend、model、device 与生命周期策略 |
| settings tab 模块化结构 | 新增本地运行时模块；复用卡片、badge、折叠与存储统计视觉语言 |
| 事件名常量模块 | 新增通用 local-engine status/log 事件，删除新增 FunASR 专属事件的需求 |
| 现有截图 OCR session/epoch | PaddleOCR 异步启动与结果回流继续使用同一竞态墙 |

### 4.2 不进 0.22 的项

| 项 | 理由 |
|---|---|
| 第三方插件注册任意本地 Python 引擎 | 会把受限内置 registry 扩大为任意代码执行/进程托管面，需独立信任与签名设计 |
| 通用模型商店/模型下载器 | 下载、校验和版本语义高度依赖工具箱；0.22 只统一缓存根与状态观察 |
| PP-StructureV3、表格/公式/文档解析 | 与截图文字识别的输出协议、资源预算和产品入口不同，另立能力评估 |
| PaddleOCR-VL / 多模态大模型 | 资源体积和结果语义超出轻量 OCR 范围，继续留在 roadmap |
| Linux/macOS 本地引擎支持 | 当前产品和进程实现以 Windows 为目标，但协议避免写死 Win32 类型 |
| 自动决定/安装 CUDA 驱动 | Blink 只探测并选择已验证 profile，不修改系统驱动 |
| 多引擎共享 site-packages | 0.22 明确隔离；只有未来有真实兼容组合时才启用 `Shared(name)` |
| 删除 WinRT OCR | 保留零安装 fallback 与排障逃生口 |
| AI/MCP 安装、启动或清理引擎 | 管理操作暂不开放外部出口；以后需单独做授权与危险确认 |

## 五、分子版本设计

### 5.1 0.22.0 — PP-OCRv6 spike 与基线

目标是先回答会改变架构的事实问题，不提交正式产品入口：

- 在 Windows CPU 上锁定可安装的 Python/PaddlePaddle/PaddleOCR 组合。
- 比较 thin Blink HTTP wrapper、PaddleX basic serving、单次 worker 三种拓扑。
- 测量 tiny/small/medium 的安装体积、模型体积、冷启动、首次识别、热识别、峰值/稳定内存和退出回收。
- 验证中文/英文/日文、竖排、小字号、混合 DPI 截图与 word rect 精度。
- 验证模型缓存重定向、首次下载阶段、离线复用和损坏模型错误。
- 冻结最小 `/health`、`/recognize`、认证 token 与 shutdown 协议。

默认选型倾向 thin wrapper：Blink 是单用户低并发桌面应用，不默认引入完整 PaddleX serving；若 benchmark 表明官方 serving 在可靠性或性能上明显更优，可在本子版本修订定案。

### 5.2 0.22.1 — ManagedProcess

- 从 FunASR maintenance 提取通用进程句柄与 stdout/stderr pump。
- 用 bounded channel + ring buffer 防止日志消费者缺席导致无界内存。
- 引入 `instance_id`、PID/executable 身份和退出原因。
- 实现幂等 start/stop、启动取消、退出 wait、进程树回收与应用退出同步收尾。
- 端口冲突不杀未知进程；只回收能证明属于 Blink 当前/遗留实例的进程。
- 用 fake child/server 覆盖双管道大输出、超时、崩溃、重复启动/停止与竞态。

### 5.3 0.22.2 — PythonRuntime

- 路径迁移为公共 runtime + `envs/{engine_id}`，兼容识别旧 `python/venv`。
- `PythonEnvStatus` 改为 runtime 状态 + `packages: Vec<PackageStatus>`；torch/funasr 投影留在 FunASR adapter。
- 建立 engine manifest、staging install、self-test、原子切换和失败回滚。
- CPU/GPU profile 使用独立 lock/index 规则。
- 清理 API 明确 engine env、engine model cache、shared download cache 三种 scope。
- 旧 FunASR venv 采用一次性受控迁移：可验证兼容则登记/移动，不兼容则提示重建；不得静默删除用户现有模型缓存。

### 5.4 0.22.3 — 协议、服务与 FunASR 迁移

- 新建 domain 状态/描述符/adapter 协议与 app `LocalEngineService`。
- 注册 `funasr` adapter，迁移安装、服务、模型轮询、日志、空间与清理。
- 现有 STT 专属 commands 保留一个过渡小版本的兼容薄转发，前端迁移后删除或标记废弃。
- FunASR 的配置 key、模型选择、热词、ITN、VAD、HTTP 请求与自动启动语义不变。
- 用通用 status 取代 `SERVER_RUNNING` 这种无法确认真实服务状态的单一原子布尔。
- 删除按端口无身份 kill；应用退出通过 service 遍历回收所有 managed instances。

### 5.5 0.22.4 — 设置 UI 与通用事件

- 在 engines tab 增加本地模型运行时 section，移动语音页的环境/服务管理 UI；语音页仅保留语音业务配置及跳转入口。
- 新增 `get_local_engine_catalog/status/logs/storage` 与 install/start/stop/repair/cleanup 管理协议；命令按 `engine_id` allowlist 路由。
- status/log 监听以 `engine_id + revision/seq` 去重，页面切换和销毁时解除监听。
- 长操作展示阶段、可取消性和明确错误，不伪造下载百分比。
- 清理弹窗列出准确目标、预计释放空间和影响；公共缓存与引擎环境分开确认。
- 中英文 i18n、Lucide 图标、主题 token、无 inline display 新债。

### 5.6 0.22.5 — PP-OCRv6 正式接入

- 注册 `paddleocr` adapter、锁定依赖和嵌入 thin server 脚本/配置。
- 新增 `PaddleOcrBackend` 与 `OcrBackendRouter`，保持 `OcrResult` word rect 契约。
- 配置 `auto/windows/paddleocr`、模型档位、设备和生命周期。
- 按需启动采用 singleflight；同一截图 session 的请求等待 ready 后继续，取消/过期 session 不提交结果。
- 完成 idle TTL 回收、in-flight 保护和停止/新请求竞态处理。
- 环境未安装时 `auto` 使用 WinRT；显式 `paddleocr` 返回带安装入口的结构化错误。
- 保留 OCR 诊断：当前 backend、模型、service/model state、fallback 原因、单次耗时与语言信息。

### 5.7 0.22.6 — 硬化与发布验收

- 覆盖 Blink 崩溃、server 崩溃、端口被抢、模型损坏、断网安装、磁盘不足、安装取消、旧环境升级和日志洪泛。
- 验证主链路性能不回退；本地引擎状态探测、自动启动和空间扫描都在后台运行。
- 建立资源预算与默认策略：只启动用户正在使用的引擎，OCR 空闲回收。
- 安装包不包含模型；发布构建必须包含脚本、lock、manifest schema 与必要许可信息。
- 完成 diff 自审、单测、Rust 编译、前端静态契约检查及 Windows 手动矩阵。
