# Blink 0.22 — 本地模型运行时与 PP-OCRv6（从 STT 专用维护到多引擎生命周期）

> **范围**：建立 Blink 托管的多 Provider 本地模型运行时（首版落地 Python venv，并为受管原生二进制预留闭合扩展位），迁移 FunASR 生命周期管理，接入 PP-OCRv6 作为可选 OCR 后端，并在「引擎」设置页提供统一的环境、服务、模型与空间管理；末尾以 STT runtime spike 验证去 PyTorch 路线。
>
> **状态**：🚧 进行中（0.22.0～0.22.6 已完成；PP-OCRv6 spike 结论保持 `conditional-go`；0.22.7 FunASR llama.cpp/GGUF 轻量链路 spike 待启动）。
>
> **动机**：现有 uv、venv、Python server、模型状态和清理逻辑绑定在 STT/FunASR 中；PP-OCRv6 为第二个真实本地模型引擎，继续复制专用命令会形成两套安装、进程和诊断体系。
>
> **前置**：0.10 本地 STT 与 uv 自管理、0.11/0.17 OCR 能力与 WinRT 后端、0.21 Capability 唯一原子执行入口均已完成。
>
> **原则**：不影响 `Alt+Space → Focus → 输入` P0 主链路；domain 不 `use tauri`；引擎环境按 generation 隔离，公共下载资产只在可证明安全时共享；模型由受限 adapter/provider 管理来源与校验，Blink 统一管理运行目录与可观测状态；FunASR 迁移前后行为兼容；未知端口占用进程绝不自动终止；不把 Python、Paddle、ONNX Runtime、llama.cpp 或 vLLM 中任何一种实现误写成所有本地模型必须共用的唯一执行器。

## 二、背景与动机

### 2.1 为什么 0.22 做这件事

当前本地 STT 已具备一套可工作的 Python 模型生命周期，但职责散落且带有强烈的 FunASR 语义：

- `src/infra/platform/python/mod.rs` 同时硬编码 uv、Python 3.12、torch、funasr 与单一 `venv`。
- `src/domain/stt/funasr.rs` 同时承载脚本释放、启动参数、HTTP/model health 与环境状态投影。
- `src/app/commands/stt/maintenance.rs` 同时持有全局 child、安装环境、轮询模型、转发 Tauri 事件、清理目录、诊断和退出回收。
- `frontend/settings.html` / `frontend/js/settings/tabs/voice.js` 把 Python 环境和服务操作绑定在语音页。
- 服务端口默认固定为 8000；孤儿清理存在“按端口定位并终止进程”的误伤风险，不能复制到多引擎。

截至 0.22 规划时，PaddleOCR 官方资料把 PP-OCRv6 作为通用 OCR pipeline 的默认代际，提供 tiny/small/medium 三档；small/medium 使用单一模型覆盖中文、英文、日文等 50 种语言，tiny 不含日文。具体 PaddleOCR/PaddlePaddle 版本、官方模型 id、模型 revision 与 Windows wheel 兼容矩阵均以 0.22.0 spike 当日验证结果为准，不把会变化的上游事实提前固化为 Blink 契约。它与 FunASR 的框架、依赖、模型缓存、健康协议和运行策略均不同，正好用于验证真正的复用边界。

0.22 的目标不是“把 FunASR 名字替换成 Engine”，而是让 Blink 获得一个受限、安全、可诊断的内置本地模型运行时，同时升级现有 OCR 准确率与多语言能力。

### 2.2 明确“不是问题”的

- **系统 Python 与 Blink 托管 Python 不需要合并**：代码解释器使用用户选择的系统 Python；本地模型运行时只使用 Blink按版本/hash托管的 Python distribution。多个 provider可以引用同一只读托管解释器 artifact，但不读取用户解释器配置，也不共享 site-packages。
- **模型文件不需要进入 Blink 安装包**：FunASR/PaddleOCR 仍按自身机制下载模型；Blink 只指定引擎级缓存根目录、展示占用并观察模型状态。
- **WinRT OCR 不删除**：它零额外下载、启动快，是可靠 fallback；PP-OCRv6 是可选高质量后端，不把 OCR 变成“未安装 Python 就不可用”。
- **设置页内部生命周期命令不必伪装成 Capability**：状态查询、安装进度和日志属于管理 UI 协议。仅当未来确有 CLI/MCP/AI 调用需求时，再把允许外部调用的闭合操作建模为受限 Capability。
- **本地模型不自动全部常驻**：FunASR 延续用户可选自动启动；OCR 默认按需启动并在空闲后停止，不用后台常驻换取低频路径的首击速度。
- **前端仍无 bundler/npm/构建步骤**：0.22 只按现有 settings 模块与 CSS 分层扩展。

## 三、核心设计与决策

### 3.1 分层归属 —— domain 定协议、infra 做执行、app 管生命周期（已定）

**定案**：不把带文件、网络、进程与 Tauri 事件的完整 Manager 塞进 domain。

```text
frontend / settings
  └─ 本地模型运行时（底座摘要 + 引擎卡片）
       │ invoke / blink://local-engine-*
       ▼
app/local_engine
  ├─ LocalEngineService（安装/启动/停止/状态/清理编排）
  ├─ EngineRegistry（仅内置 allowlist）
  └─ Tauri command + event projection
       │
       ├───────────────┐
       ▼               ▼
domain/local_engine    infra/local_engine + runtime providers
  ├─ EngineId            ├─ ManagedProcess
  ├─ EngineDescriptor    ├─ RuntimeProvider
  ├─ EngineStatus        ├─ PortProbe / HTTP client
  ├─ LifecyclePolicy     ├─ PythonVenvProvider / UvEnvironment
  └─ LocalEngineAdapter  ├─ ManagedBinaryProvider（协议冻结，按需落地）
                         └─ file/process/cache primitives
```

职责边界：

- `domain/local_engine`：稳定 id、声明、状态类型、错误分类、生命周期策略和引擎特有的启动/健康适配接口；不发送 Tauri 事件。
- `infra/local_engine`：启动/停止子进程、排空管道、PID 身份验证、端口探测、HTTP 请求和目录原语；不读取 app 配置，不反向依赖 domain/app。
- runtime provider：把“如何取得并验证可执行环境”封装在受限 provider 中；`PythonVenvProvider` 负责 uv、Python distribution、venv 和包同步，`ManagedBinaryProvider` 负责锁定 archive/可执行文件/DLL、哈希、CPU feature/driver 前置与 self-test，并可声明只读工具依赖（如 Blink托管 Python stdlib artifact）。工具依赖不因此创建 venv或开放 pip。0.22.2 必须冻结两者可共同表达的 manifest/状态/清理契约，但首版只要求完整实现 `PythonVenvProvider`。
- `app/local_engine`：读取各引擎配置、串行化状态变更、调用 adapter + infra、持有运行实例、广播事件，并在退出时回收所有受管进程。
- 业务消费者仍留在所属领域：STT 通过本地 STT client 请求 FunASR；OCR 通过 `OcrBackend` 请求 PaddleOCR。

### 3.2 环境拓扑 —— generation 隔离，Provider 专属公共资产（修订已定）

**定案**：每个引擎拥有独立、不可变的 generation；Python引擎可共享 uv二进制、uv cache与 uv管理的 Python distribution，但不共享 site-packages。只需标准库脚本的 binary引擎也可以引用同一只读 Python distribution，无需创建 venv；原生二进制引擎可共享经过版本与 SHA-256验证的 runtime artifact（例如同一 ONNX Runtime build），不得共享可变安装目录。保留命名共享环境作为未来显式逃生口，不提供简单 `shared: bool`。

```text
%APPDATA%\blink\python\
├─ tools\uv\
├─ cache\uv\
├─ pythons\
└─ envs\
   ├─ funasr\
   │  ├─ generations\{install-id}\
   │  ├─ staging\{operation-id}\
   │  └─ current.json
   └─ paddleocr\
      ├─ generations\{install-id}\
      ├─ staging\{operation-id}\
      └─ current.json

%APPDATA%\blink\models\
├─ funasr\
└─ paddleocr\

%APPDATA%\blink\runtimes\
├─ shared\{provider}\{artifact-id}\        # 只读、内容寻址、引用计数
└─ engines\{engine-id}\
   ├─ generations\{install-id}\
   ├─ staging\{operation-id}\
   └─ current.json
```

0.22.3 的 FunASR 与 0.22.4 首版 OCR 允许先使用隔离 Python环境；这只是首个 Provider 实现，不是领域契约。`Shared(name)` 不进入本版环境协议；共享 native runtime 只能由编译期 descriptor 引用精确 artifact id，不能由前端指定。

**理由**：torch/FunASR 与 PaddlePaddle/PaddleOCR 的 GPU wheel、NumPy、protobuf、OpenCV 等传递依赖升级节奏不同，共享 site-packages 会令安装、更新、清理和回滚相互污染；而 ONNX Runtime 等 native runtime 只有在版本、provider、ABI、DLL 集合与哈希完全一致时才有安全复用价值。统一的是生命周期和 artifact 管理，不强求所有模型使用同一数学执行器。

### 3.3 状态模型 —— 三维观测，不做线性“三级状态机”（已定）

**定案**：UI 可以展示“环境 → 服务 → 模型”三级，但后端保存彼此正交的状态快照：

```rust
EngineStatus {
    service_epoch,  // 本次 Blink/LocalEngineService 实例的随机 epoch
    desired,        // Stopped | Running
    operation,      // Idle | Installing | Updating | Repairing | Migrating | RollingBack | Cleaning
    operation_id,   // 长操作实例；Idle 时为空
    environment,    // Missing | Ready | Broken { reason }
    process,        // Stopped | Starting | Running { pid } | Stopping | Exited
    service,        // Unknown | Unreachable | Healthy | Degraded
    model,          // Unknown | NotLoaded | Downloading | Loading | Ready | Failed
    revision,       // 仅在同一 service_epoch 内单调递增
    last_error,
}
```

约束：

- 状态版本以 `(service_epoch, revision)` 比较；`revision` 在同一 epoch 内每次状态提交单调递增，前端遇到新 epoch 必须重置旧快照，避免 Blink 重启后较大的旧 revision 压住新状态。
- `desired` 与 observed state 分离；“用户要求停止但进程尚在退出”可以准确表达。
- `env ready` 不推出 `server/model ready`；child 存活也不推出端口上的服务属于该 child。
- 每个 engine id 同时只允许一个变更操作；查询可并发，安装/更新/修复/迁移/回滚/启动/停止/清理必须串行化。长操作携带 `operation_id`、阶段与 `cancellable`，取消只作用于匹配的 operation。
- 错误使用结构化阶段与稳定错误码，日志中保留详细上下文，前端显示可行动文案。

### 3.4 引擎描述符与 adapter —— 数据声明有限，行为显式（已定）

**定案**：描述符声明静态事实，adapter 实现引擎特有行为；不把健康检查和启动逻辑编码成通用字符串 DSL。

描述符至少包含：

- 稳定 `engine_id`、显示元数据与所属能力（STT/OCR）。
- `runtime_kind`、隔离环境和 CPU/GPU 安装 profile；首版允许 `PythonVenv`，协议预留 `ManagedBinary`，不接受前端自定义 kind。
- 锁定安装计划：Python provider 声明 Python/package lock/index/self-test；binary provider 声明 archive、文件清单、SHA-256、可执行入口、所需 CPU feature/driver 与 self-test。
- 环境 schema 版本，以及模型 id/revision 与 server-model 兼容 schema。
- 默认生命周期（manual/auto/on-demand）、启动/模型超时与空闲 TTL。
- 引擎拥有的脚本、配置、日志与模型缓存子目录。
- 资源预算提示与 cleanup policy。

adapter 至少负责：

- 从已校验配置构造 `LaunchRequest`。
- 生成受限环境变量（FunASR 的 ModelScope、PaddleOCR 的模型缓存等）。
- service health 与 model health 的协议映射。
- 安装后 self-test。
- 引擎输出到领域 DTO 的映射。

注册表为编译期内置 allowlist。前端只能传 `engine_id` 与有限动作，不能传 executable、任意 argv、脚本路径或环境变量；0.22 不把它扩展成第三方任意进程托管器。

### 3.5 计算设备 —— 用户偏好、安装 profile、实际后端三层分离（已定）

**定案**：计算设备是每个引擎独立配置，不设全局 CPU/GPU 开关。用户配置保存受限的 `compute_preference = auto | cpu | gpu_auto | cuda | vulkan | directml`；descriptor 只暴露该引擎已验证的选项，并把偏好解析为具体、锁定的 runtime profile；服务 health 必须回报实际后端，不能只展示配置意图。

三层语义：

- **requested preference**：用户意图。`auto` 允许按引擎声明的优先级回退；`gpu_auto` 只在 GPU backend 间选择；显式 `cpu/cuda/vulkan/directml` 失败时返回可行动错误，不静默换后端。
- **resolved profile**：具体 artifact 与兼容合同，例如 `cpu-x64`、`cpu-avx2`、`cuda12-sm86`、`vulkan-x64`、`directml-x64`；profile 决定下载内容、DLL、execution provider、CPU feature/driver 前置、启动参数与 self-test。
- **actual backend**：进程启动后由 token health 回报 `actual_backend/device_name`；状态同时保留 requested、resolved、actual 与 fallback reason，UI 不得把“检测到 NVIDIA/AMD”当作实际已启用加速。

每个 adapter 声明自己的候选顺序和兼容矩阵。例如 llama.cpp 可声明 `cuda（精确架构匹配）→ vulkan（实机 self-test）→ avx2 → cpu`，ONNX引擎可声明 `cuda/directml → cpu`；这不是跨引擎全局顺序。硬件/API探测、artifact兼容检查和最小 self-test 全部通过后才可解析为可用 profile。

profile切换原则上视为新 generation：在 staging安装并验证目标 profile，停止旧实例后原子切换；启动验证失败回滚上一 generation。即使某个 archive同时携带 CPU/Vulkan backend、只需更改启动参数，也必须经过同样的解析、self-test、状态回报与回滚语义。

### 3.6 安装与更新 —— staging、自检、原子指针切换、可回滚（已定）

安装流程：

```text
解析内置 lock/profile
  → provider 准备锁定 runtime artifact
  → 创建 engine/staging/{operation-id}
  → PythonVenv: 确保 uv/Python、创建 venv、同步锁定依赖
    或 ManagedBinary: 下载/解包锁定 archive、验证文件/DLL/CPU feature
  → provider version/self-test
  → 写 generation manifest（含依赖与模型契约）
  → 停止旧实例
  → staging 提升为不可变 generations/{install-id}
  → 原子替换 current.json 小文件指针
  → 本次启动验证失败则原子切回上一 generation
```

要求：

- 依赖真源必须锁版本；不得在生产安装路径使用无上界 `latest`。
- CPU/GPU profile 分开，profile 切换视为环境重建，不在原 venv 原地覆盖框架 wheel。
- 不用目录覆盖伪装“原子切换”；Windows 文件占用、杀软扫描或任一步崩溃后，启动恢复逻辑必须能从 `current.json` 与完整 generation manifest 选出最后一个有效 generation。
- 安装失败不破坏当前 generation；取消只清理匹配 `operation_id` 的 staging。仍被进程占用的旧 generation 标记 deferred cleanup，不强删。
- manifest 通用部分记录 engine id、schema、runtime kind、profile、artifact id/hash、安装时间、模型 id/revision/checksum 来源及兼容 schema；Python扩展记录解释器与包版本，binary扩展记录 archive/可执行文件/DLL及其哈希。状态检查使用 manifest + provider self-test 双重验证。每引擎至少保留当前与上一有效 generation，额外旧代按 cleanup policy 回收。
- 清理只作用于该引擎声明拥有的 generation/model cache；公共 uv/Python/cache 或共享 native artifact 使用独立清理与引用检查，不得顺带删除其他引擎仍在使用的资产。

### 3.7 进程与端口安全 —— PID 身份优先，未知占用不杀（已定）

`ManagedProcess` 提供：

- stdout/stderr 同时异步排空，避免管道背压死锁。
- 有界日志环形缓冲与结构化生命周期事件。
- child handle、PID、可执行路径、引擎 token 与启动时间身份记录。
- 启动超时、退出监听、优雅停止 deadline、超时后只终止已验证的进程树。
- Blink 正常退出时统一回收；异常退出后的重连/清理必须先验证身份。
- Windows 生产实现优先使用 Job Object（kill-on-job-close）约束受管进程树；每次实例同时写原子 lease，记录 engine/instance id、PID、进程创建时间、可执行路径、endpoint 与 token fingerprint。重启后只有 lease、进程创建时间/路径和带 token health 全部匹配才可接管或终止；验证失败只报告遗留项，不自动 kill。

端口规则：

- 服务仅绑定 `127.0.0.1`。
- 配置保存 preferred port；启动时检测冲突，必要时从受控范围选择新端口并更新本次 endpoint。
- “探测空闲”与子进程 bind 之间仍可能竞争；遇到 address-in-use 时限次重新分配并重启。
- 每次启动生成随机 token，健康与业务请求均携带 token；健康响应回显 engine id / instance id，用于确认端口服务身份。
- 只有 PID + 可执行路径/instance token 与受管记录一致时才能终止；未知进程占用端口只报冲突或换端口。

0.22.3 必须删除 FunASR 现有“仅凭端口定位 PID 后自动 kill”的路径。

### 3.8 生命周期策略 —— FunASR 可自启，OCR 默认按需 + 空闲回收（已定）

| 引擎 | 默认策略 | 首次调用 | 空闲策略 |
|---|---|---|---|
| FunASR | Manual；沿用用户现有 `auto_start_server` | 未运行时保持当前可行动错误提示，不在录音手势热路径隐式长等待 | 自动启动者随 Blink 生命周期；手动启动者手动停止 |
| PaddleOCR | OnDemand | OCR 请求在同一次 `recognize` future 内触发并等待单飞启动；loading/progress 走旁路事件，不复制或“重放”图片请求 | 默认 5 分钟无请求停止，可配置为“保持运行”或“使用后立即停止” |

约束：

- OCR 启动不得阻塞 Alt+Space、截图 overlay 展示或前端事件线程。
- 相同引擎并发首次调用合并为一个启动 future，禁止重复拉起。
- `OcrBackend::recognize` 扩展受限请求上下文，至少携带 deadline/cancel token/origin；截图 Interaction 额外持有自身 session/epoch，`ocr_image` Capability 只使用调用 deadline/cancel，不伪造截图 session。
- OCR 回流继续遵循截图 session/epoch 校验；旧选区启动的识别结果不得覆盖新选区。等待启动期间只持有单份请求图片，session 取消或 deadline 到期后不得再发业务请求。
- 空闲计时只在 in-flight 请求归零后开始；停止与新请求竞争时，新请求提升 `desired=Running` 并取消空闲停止。

### 3.9 OCR 后端路由 —— PP-OCRv6 可选，WinRT 永久回退（已定）

新增 OCR 配置：

- `backend = auto | windows | paddleocr`，升级与全新安装均默认 `windows`；安装 PP-OCRv6 不隐式改变现有 OCR 路径，由用户明确切换。`auto` 是显式选择，不是默认值。
- `paddle_model` 的稳定配置值以 0.22.0 验证后的官方模型 id 为真源；UI 可显示 tiny/small/medium 友好档位。桌面候选由 benchmark 定案，不预设 `small` 必然合格。
- `compute_preference` 遵循 §3.5；0.22 首发必须保证 `auto/cpu`，CUDA/Vulkan/DirectML 只有在对应 Windows artifact、驱动矩阵与 self-test 验证通过后才由 descriptor 开放。
- `lifecycle = on_demand | keep_running | stop_after_use`。
- 文档方向/矫正/行方向等增强模块默认关闭，截图 OCR 只启检测 + 识别；后续按真实收益开放。

路由语义：

- `windows`：始终使用当前 WinRT backend。
- `paddleocr`：明确选择 PaddleOCR；未安装/启动失败时返回可行动错误，不静默改变用户选择。
- `auto`：仅当 PaddleOCR 环境已安装且 service/model 已热态 ready 时优先使用 PaddleOCR，否则立即使用 WinRT，不为一次普通 OCR 引入隐式冷启动等待；PaddleOCR 在单次识别中崩溃可降级 WinRT，并记录/展示降级原因。
- 每次识别开始时快照 `Arc<dyn OcrBackend>`，切换配置不改变已经在途的请求。
- PaddleOCR 输出必须完整映射现有 `OcrResult` / line / word rect 契约，前端阅读模式、翻译、pin 与 overlay 不感知后端差异。

### 3.10 模型与缓存边界（已定）

Blink 不实现通用模型下载器。adapter 设置引擎专属缓存根目录并从服务健康协议观察 `NotLoaded/Downloading/Loading/Ready/Failed`；但 descriptor/manifest 必须锁定并记录可复现的模型身份，不能只锁 Python 包而让模型随安装时间漂移。

Blink 负责：

- 下载前展示预计体积（若描述符可知）与网络提示。
- 传入 descriptor 锁定的 model id/revision，校验服务报告的实际 revision 与兼容 schema；上游不提供稳定 checksum 时记录下载来源与上游 revision，并在 spike 结论中明确可复现性限制。
- 展示引擎 venv、模型缓存、日志和公共缓存占用。
- 打开引擎目录、停止后清理该引擎缓存。
- 模型 ready 前不发送业务请求。

引擎负责：

- 下载源、断点续传、文件校验、模型版本解析与加载；不得擅自把“最新模型”替换为 descriptor 锁定值之外的 revision。
- 将可观测阶段通过 health 协议或服务日志暴露；无法取得字节级进度时只展示阶段，不伪造百分比。

### 3.11 设置页信息架构（已定）

在现有「引擎」页的“代码解释器”下方新增“本地模型运行时”，不新开顶级 tab：

```text
本地模型运行时
├─ 运行时底座（默认折叠）
│  uv / 托管 Python / 公共缓存 / 根目录
├─ 语音识别 · FunASR
│  环境 / 服务 / 模型三段状态，安装、修复、启动、停止、日志、清理
└─ 文字识别 · PP-OCRv6
   后端选择、模型档位、设备、生命周期、安装、启动、停止、测试、日志、清理
```

“代码解释器 Python”文案明确为“系统/用户解释器”；“本地模型运行时”明确为“Blink 托管环境”，避免用户误解 Blink 会修改其 Python。

引擎卡片使用同一 renderer 和状态协议，但允许 adapter 提供有限的额外配置区；不为每个引擎复制一套安装按钮与事件监听。状态事件包含 `engine_id + service_epoch + revision + snapshot`；服务运行日志包含 `engine_id + instance_id + seq`；安装过程日志另以 `engine_id + operation_id + seq` 隔离，二者不得混用身份键。

### 3.12 模型资产与功能选择分权 —— 引擎页准备，功能页选择（修订已定）

**定案**：引擎页拥有模型资产生命周期，负责支持模型目录、下载、校验、修复、删除、缓存占用与完整日志；语音输入页只从“已安装、校验通过、兼容且具备 STT 能力”的模型中选择当前使用项，不在功能页隐式触发模型下载。

本地 STT 选择使用 `engine_id + model_id` 联合身份。引擎页可提供“设为语音模型”快捷动作，但与语音页选择器必须调用同一受限选择命令和同一配置真源，不得形成两个当前模型字段。旧 `local_model_id + local_engine.funasr_model` 只作为兼容迁移输入。

必须区分三类状态：

- **installed**：模型资产已下载并校验，可被功能选择；
- **selected**：用户配置希望语音功能使用的 `engine_id + model_id`；
- **active**：当前运行实例 health 实际回报的模型身份。

模型下载、启动或验证失败时不得提交新的 selected；selected 与 active 不一致时明确显示“待重启/未生效”，不得静默声称切换完成。删除 selected/active 或仍被引用的模型必须返回结构化冲突，不静默选择其他模型。

FunASR 的 SenseVoice 与 Paraformer 是同一引擎的受限模型候选，模型健康校验的期望合同来自本次已校验启动选择，不得由引擎 descriptor 静态写死为 SenseVoice。0.22.7 新增其他 STT 引擎时复用联合身份，不再扩展单一 `local_model_id` 假设。

### 4.2 不进 0.22 的项

| 项 | 理由 |
|---|---|
| 第三方插件注册任意本地 Python 引擎 | 会把受限内置 registry 扩大为任意代码执行/进程托管面，需独立信任与签名设计 |

| PaddleOCR-VL / 多模态大模型 | 资源体积和结果语义超出轻量 OCR 范围，继续留在 roadmap |
| 把 ONNX Runtime、llama.cpp 或 vLLM 定为唯一执行器 | 三者分别面向通用 ONNX 计算图、已适配的 GGUF/ggml 架构和高吞吐生成式模型；0.22 统一管理面，不伪造执行能力交集 |
| 本地 LLM/Embedding 产品接入与 GPU 调度 | Provider/adapter 协议为其留扩展位，但多模型 RAM/VRAM 仲裁、抢占、session/KV cache 与产品入口应另立 phase |
| Linux/macOS 本地引擎支持 | 当前产品和进程实现以 Windows 为目标，但协议避免写死 Win32 类型 |
| 自动决定/安装 CUDA 驱动 | Blink 只探测并选择已验证 profile，不修改系统驱动 |
| 多引擎共享 site-packages | 0.22 明确隔离；本版不预埋 `Shared(name)` 协议，只有未来有真实兼容组合时再扩展 |
| 删除 WinRT OCR | 保留零安装 fallback 与排障逃生口 |
| AI/MCP 安装、启动或清理引擎 | 管理操作暂不开放外部出口；以后需单独做授权与危险确认 |

### 5.8 0.22.7 — FunASR llama.cpp/GGUF轻量链路 spike 与条件接入

本节采用“先 spike、门通过后条件接入”两段式：首要且默认验证的链路是官方 `llama-funasr-*` Windows独立二进制 + GGUF模型 + 上游 `funasr_gguf_server.py` 轻量 HTTP wrapper，复用 Blink当前 OpenAI-compatible transcription client。现有 Python/PyTorch FunASR只作为回退与资源对照，不做准确率基线；本节不设置 CER/WER门，不因文本差异阻断链路验证，但必须用固定音频确认返回非空、UTF-8合法且协议可解析。

阶段 A 只验证链路与资源。若安装、启动、请求、取消、停止、清理、离线复用和资源报告全部闭合，阶段 B 在同一子版本注册新的 `funasr-gguf`（稳定 id 以实现时 descriptor为准）可选 STT引擎；不静默迁移用户配置，不替换或删除现有 `funasr` Python/PyTorch引擎。若主路径因 Windows兼容、延迟/进程抖动、资源或协议问题不可用，再把 C++ ONNX常驻 2-pass server作为备选 spike，不要求本子版本同时完成两条路线。

候选边界：

- **首要链路 — llama.cpp/GGUF + 轻量 HTTP wrapper**：官方 Windows自包含 runtime、SenseVoice Q8（首个模型）与 FSMN-VAD按锁定 release/hash安装；wrapper只用 Python标准库，暴露 `POST /v1/audio/transcriptions` 并可转发受限的 `--backend cuda|vulkan`。首版由 `ManagedBinaryProvider` 引用 uv基础设施已锁定的 Blink托管 Python distribution，以 `python -I -S` 隔离模式运行 wrapper；不创建 venv、不安装 pip包、不读取用户代码解释器。后续可由 Rust实现等价薄 wrapper，两者的 C++推理路径相同。
- **备选链路 — C++ ONNX Runtime**：仅在首要链路不合格时展开。ONNX Runtime本身是通用执行层，可由 OCR与 STT分别创建独立 session；只有精确版本、execution provider、ABI与 DLL集合一致时才共享同一只读 runtime artifact。模型、前后处理、进程与内存仍按引擎隔离。
- **模型覆盖不预设为三者等价**：FunASR C++ ONNX 常驻服务当前重点验证 Paraformer online/offline 2-pass 组合；SenseVoice、Paraformer、Fun-ASR-Nano 三种模型是 llama.cpp/GGUF release 明确列出的三个 runtime 入口。每个模型是否存在功能等价、可发布的 ONNX 路径须逐项验证，不能因 Python `AutoModel` 可加载就视为 C++ server 已支持。
- **每请求子进程是真实约束**：上游 HTTP wrapper常驻但模型不常驻，每个 transcription请求都会 spawn推理进程。Blink当前 final-only链路可能可接受，但必须测量首次、连续短句、取消和两个并发请求；不得把 HTTP health可达写成 model warm。伪流式若导致频繁整段重识别，`funasr-gguf` 首版应明确只提供 final，不能用重复 spawn伪造 partial。
- **vLLM**：是面向 Fun-ASR-Nano等生成式模型的高吞吐服务后端，不执行传统 ONNX 图，也不是 OCR/STT 共用的 native runtime。其 Python/CUDA/服务体积与桌面约束单独计量，默认不进入轻量 Windows候选；只作为有明确 GPU吞吐需求时的对照项。

阶段 A 实验要求：

- 固定 Windows x64目标机、runtime/model revision、输入音频与采样口径，先跑 SenseVoice Q8 + FSMN-VAD；至少比较直接 CLI/Rust spawn和上游标准库 HTTP wrapper，两者都按每请求新进程统计。F16、Paraformer、Nano、C++ ONNX和 vLLM均不是本阶段必测项。
- 测量 runtime/模型/托管 Python distribution增量与总磁盘、wrapper ready、单次端到端 final、连续短句与两个并发请求的 P50/P95、实时率、CPU、稳定/峰值 RAM/VRAM、停止回收和进程抖动；若该 Python artifact已被其他引擎引用，仍分别报告物理总占用与本引擎增量。该拓扑不定义独立的 model-ready或 partial指标。
- 用固定短音频做协议 smoke：HTTP 200、JSON shape正确、文本非空且 UTF-8合法；不计算 CER/WER，不比较 PyTorch文本，不把准确率作为 go/no-go。
- 验证 final语义、FSMN-VAD开关、超时/取消、wrapper重启、两个并发请求、迟到结果隔离、临时文件回收、子进程归零和完整缓存后的断网运行；热词、ITN、时间戳和 partial只记录能力现状，不作为首版接入门。
- 产出 Windows自包含包清单、许可/SBOM与精确 hash，证明推理环境无需 Docker、系统/用户 Python、PyTorch、torchaudio、FunASR Python包和管理员权限；单独报告共享托管 Python distribution的物理体积与本引擎增量。
- 输出 `decision.md`，结论为 `adopt-llamacpp-http | fallback-cpp-onnx-spike | no-go`，记录全部原始资源数据和已知功能限制。

阶段 B 条件接入要求：

- 使用 `ManagedBinaryProvider` 安装锁定的 runtime archive和 GGUF模型，轻量 wrapper作为引擎自有脚本，并引用锁定的共享托管 Python stdlib artifact；禁止为它创建 venv或安装 torch、torchaudio、funasr及任何 pip包。
- 注册独立 engine id和配置卡片，复用现有 STT OpenAI-compatible client；首版声明 final-only，不冒充 realtime/2-pass。
- 默认不自动切换现有用户；用户显式选择后才使用新引擎，失败时返回可行动错误并允许手动切回 Python FunASR。
